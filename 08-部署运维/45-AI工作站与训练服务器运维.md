## $\rm \S \, 45.1$ 硬件选型与验货

### $\rm \S \, 45.1.1$ GPU 不是唯一要考虑的

一台训练服务器的瓶颈可能在 GPU，也可能在别处：

| 组件 | 关键参数 | 为什么重要 |
|------|---------|-----------|
| **GPU** | 显存、FP16/FP8 TFLOPS、NVLink | 决定了能训练多大的模型，以及训练多快 |
| **CPU** | PCIe lane 数 | 每张 GPU 至少需要 PCIe x8 或 x16。CPU lane 不够 → GPU 跑不满 |
| **内存** | 容量 = GPU 显存 × 2~3 | DataLoader 在 CPU 侧缓存数据；数据预处理吃内存 |
| **存储** | NVMe SSD 速度 | 数据集读取是常见瓶颈——一大块 HDD 做 RAID 不如一块 NVMe |
| **网络** | 带宽（多机训练） | 多机 DDP 时，InfiniBand > 100GbE > 25GbE > 10GbE > 1GbE |
| **散热** | 机箱风道、机架空间 | GPU 满载时每张卡 $300\sim700 \, \text{W}$。8 卡 = 一台取暖器 |

### $\rm \S \, 45.1.2$ 拿到新机器后的第一件事

不要马上装驱动开跑。先做硬件验货：

```bash
# 确认 GPU 数量和型号
lspci | grep -i nvidia
nvidia-smi                    # 如果驱动还没装，这个命令不存在——用 lspci 即可

# 确认 PCIe 拓扑（GPU 之间的连接方式）
nvidia-smi topo -m            # 查看 GPU 间 NVLink / PCIe 拓扑矩阵

# 确认内存
free -h

# 确认磁盘
lsblk
df -h

# 压力测试（安装驱动后）
# GPU 计算压力
stress-ng --matrix 0          # CPU
gpu-burn 120                  # GPU 满负载 120 秒——如果 GPU 温度失控或掉卡，这里会暴露
```

`nvidia-smi topo -m` 的输出非常重要——它告诉你 GPU 之间是通过 NVLink 直连还是走 PCIe 交换芯片（PLX），直接决定了多卡训练的通信效率。理想情况下，同一节点内的 GPU 应该是 P2P（Peer-to-Peer）可达的。

## $\rm \S \, 45.2$ 驱动、CUDA 与 cuDNN

### $\rm \S \, 45.2.1$ 它们是什么关系

```text
你的 PyTorch 代码
    ↓ 调用
CUDA 运行时 API（libcudart.so）
    ↓ 调用
NVIDIA 驱动（内核模块 nvidia.ko + 用户态 libcuda.so）
    ↓ 控制
GPU 硬件
```

- **驱动**：内核模块，让操作系统认识 GPU。`nvidia-smi` 显示的是它。
- **CUDA Toolkit**：编译器和运行时库（`nvcc`、`libcudart`、`libcublas` 等）。你的 PyTorch/TensorFlow 不需要完整 Toolkit（它们自带精简版运行时），但如果你要从源码编译任何东西（如 `flash-attention`），就需要完整 Toolkit。
- **cuDNN**：NVIDIA 的深度神经网络加速库。你的框架已经在背后调用它了——你不需要手动写 cuDNN 代码。

### $\rm \S \, 45.2.2$ 驱动安装：三种方式

| 方式 | 优点 | 缺点 |
|------|------|------|
| **Ubuntu 官方源**（`ubuntu-drivers`） | 简单可靠，和内核一起更新 | 版本偏旧 |
| **NVIDIA 官方 runfile** | 最新版本 | 手动操作多，内核更新后可能要重装 |
| **CUDA 仓库中的驱动** | 驱动和 CUDA 版本绑定 | 重量级 |

**推荐**：用 `ubuntu-drivers` 安装，然后用 `--no-kernel-module-source` 避免每次内核更新都要重编译：

```bash
# 查看推荐版本
ubuntu-drivers devices

# 安装
sudo apt install nvidia-driver-550   # 版本号按实际情况

# 重启
sudo reboot

# 验证
nvidia-smi
```

> **经验规则**：不要混用不同方式安装的驱动。如果之前用 runfile 装过，先用 `nvidia-uninstall` 卸载干净，再切到 apt 方式。生产服务器上，选择保守的驱动版本——比最新版本滞后 1-2 个版本，等社区验证稳定性。

### $\rm \S \, 45.2.3$ CUDA Toolkit：装在用户空间，不污染系统

不要在系统级装 CUDA Toolkit（`sudo apt install cuda`）。用 conda 或 venv 管理：

```bash
# conda 方式（推荐）
conda install cudatoolkit=12.1 -c nvidia

# 或者只装 PyTorch——它自带所需 CUDA 运行时
pip install torch torchvision --index-url https://download.pytorch.org/whl/cu121
```

PyTorch 的 pip 包实际上已经内置了它需要的 CUDA 库（`libcublas`、`libcudnn` 等）。你不需要系统级的 CUDA Toolkit 来运行 PyTorch。

### $\rm \S \, 45.2.4$ 内核更新可能破坏驱动

这是 Linux 训练服务器最常见的事故之一：

```bash
# 某天你顺手 apt upgrade，重启后 nvidia-smi 报错：
# NVIDIA-SMI has failed because it couldn't communicate with the NVIDIA driver.

# 原因：内核更新了，但 NVIDIA 内核模块没有针对新内核编译。
# 解决方案：用 dkms 自动管理
sudo apt install nvidia-dkms-550   # DKMS = Dynamic Kernel Module Support
# DKMS 会在每次内核更新后自动重新编译 NVIDIA 模块。
```

> **安全规则**：生产服务器上，**禁止 `apt upgrade` 自动更新内核**。用 `sudo apt-mark hold linux-image-$(uname -r)` 锁定当前内核，然后在计划维护窗口手动更新和验证。

## $\rm \S \, 45.3$ 环境隔离：Docker 还是 conda

### $\rm \S \, 45.3.1$ 多用户服务器的挑战

8 个人共用一台服务器，各自需要不同版本的 PyTorch。A 要用 PyTorch 2.0 + CUDA 11.8，B 要 2.3 + CUDA 12.1。解决方案：

| 方案 | 隔离程度 | 复杂度 |
|------|---------|--------|
| **conda 环境** | 用户态 Python 包隔离 | 低 |
| **Docker 容器** | 完整用户态文件系统隔离 | 中 |
| **LXD/Incus 系统容器** | 近乎完整操作系统隔离 | 高 |

### $\rm \S \, 45.3.2$ Docker + GPU：NVIDIA Container Toolkit

NVIDIA 提供了 `nvidia-container-toolkit`，让 Docker 容器可以访问宿主机的 GPU 驱动：

```bash
# 安装（Ubuntu）
curl -fsSL https://nvidia.github.io/libnvidia-container/gpgkey | \
    sudo gpg --dearmor -o /usr/share/keyrings/nvidia-container-toolkit-keyring.gpg
# ... 按官方文档添加源
sudo apt install nvidia-container-toolkit

# 运行一个带 GPU 的容器
docker run --gpus all -it pytorch/pytorch:2.3.0-cuda12.1-cudnn8-runtime bash
# 容器内 nvidia-smi 可以看到 GPU
```

容器共享宿主机的驱动（内核模块），但用户态的 CUDA 库各自独立。这解决了“不同用户需要不同 CUDA 版本”的问题。

### $\rm \S \, 45.3.3$ conda 环境是更轻的选择

对于不需要完整系统隔离的单人/少人场景，conda 更简单：

```bash
conda create -n myproj python=3.11
conda activate myproj
pip install torch torchvision --index-url https://download.pytorch.org/whl/cu121

# 每个用户有自己的 conda 环境，互不干扰
```

> **经验规则**：团队 < 3 人 → conda 环境足够了。团队 ≥ 3 人或需要频繁切换 CUDA 版本 → Docker。需要严格资源隔离（不能某个人占满所有 GPU）→ 加调度系统。

## $\rm \S \, 45.4$ 存储规划

### $\rm \S \, 45.4.1$ 三类数据，三种存放方式

| 数据 | 放在哪 | 备份策略 |
|------|--------|---------|
| **代码** | Git 仓库 | `git push` 即可——不需要另外备份 |
| **数据集** | 共享目录 `/data/datasets/`，只读 | 至少一份离线副本——数据集通常是从网上下载的，可以重新下载，但不一定（某些数据集可能会被下架） |
| **Checkpoint** | 专属目录 `/data/checkpoints/项目名/` | **必须备份**——这是你唯一不可从外部恢复的产出 |
| **日志** | `/data/logs/`，可配置自动清理 | 非关键，丢了就丢了 |

### $\rm \S \, 45.4.2$ 目录约定的推荐

```bash
/data
├── datasets/              # 原始数据集，所有人只读
│   ├── imagenet/
│   └── common-crawl/
├── checkpoints/           # 每个人的实验输出
│   ├── alice/
│   │   └── exp01/
│   └── bob/
│       └── llama-finetune/
├── logs/
└── shared/                # 共享的预训练权重
    └── pretrained/
```

> **经验规则**：数据集和 checkpoint **不要放在系统盘**（`/`）上。如果某人的日志或 checkpoint 把系统盘写满了，整个服务器的 SSH、systemd 都可能跟着崩溃。把 `/data` 挂载到独立的大容量 NVMe 或 RAID 阵列上。

## $\rm \S \, 45.5$ 多人 GPU 管理

### $\rm \S \, 45.5.1$ 怎样知道谁在用 GPU

```bash
nvidia-smi                    # 查看所有 GPU 的占用情况——进程、显存、利用率
gpustat -i 1                  # nvidia-smi 的更友好版本，每秒刷新（pip install gpustat）
```

`gpustat` 一行显示每张卡的显存使用和用户：

```
[0] A100-SXM4-80GB | 72°C, 95% | alice: 42.3G, bob: 18.2G
```

### $\rm \S \, 45.5.2$ 显存不能被“预定”

这是最常见的误解：有人以为“我关了 Jupyter notebook 的 kernel 就释放显存了”。但 Python 进程可能仍然在后台占用显存。此外，PyTorch 默认会缓存显存（CUDA caching allocator）——即使 Python 逻辑上已经 `del tensor`，显存也可能被 PyTorch 的缓存池保留。

彻底释放显存的唯一方式：**杀掉进程**。

```bash
nvidia-smi                     # 找到 PID
kill -15 PID                   # 发送 SIGTERM，给进程清理的机会
# 如果 30 秒后还没释放：
kill -9 PID                    # SIGKILL——进程来不及清理，但 GPU 一定会释放
```

### $\rm \S \, 45.5.3$ 非正式的 GPU 预约

在小团队（2-5 人）中，Slurm 可能过重。一个低门槛的替代方案：

```bash
# 用 CUDA_VISIBLE_DEVICES 限制可见 GPU
CUDA_VISIBLE_DEVICES=0,1 python train.py    # 只使用 GPU 0 和 1

# 写进 .bashrc 做个 alias
alias gpu0-1='export CUDA_VISIBLE_DEVICES=0,1'
alias gpu2-3='export CUDA_VISIBLE_DEVICES=2,3'
```

配合一个白板或 Slack 频道记录“谁在用哪几张卡”，5 人以内完全可维护。

## $\rm \S \, 45.6$ 监控与告警

### $\rm \S \, 45.6.1$ 日常该看什么

```bash
# GPU：温度、功耗、显存、ECC 错误
nvidia-smi -q -d TEMPERATURE,MEMORY,ECC

# 如果某张卡温度明显高于其他卡（差距 > 10°C），可能是：
# - 风道堵塞（灰尘）
# - 这张卡没有其他卡的尾气（GPU 之间的间距问题）
# - 该卡的散热硅脂老化

# 磁盘
df -h /data                          # 还剩多少空间
sudo smartctl -a /dev/nvme0n1        # NVMe 健康状态

# 内存——有没有 ECC 纠错事件
sudo edac-util -v                    # 如果有 ECC 错误——立刻备份数据，准备换内存条
```

### $\rm \S \, 45.6.2$ GPU Xid 错误

NVIDIA 驱动用 **Xid 错误码** 来报告 GPU 故障。你会在 `dmesg` 或 `/var/log/syslog` 中看到它们：

```bash
dmesg | grep -i "xid"
# 常见：
# Xid 79: 掉卡——GPU 从 PCIe 总线上消失。重启或重新插拔。
# Xid 48: 双位 ECC 错误——显存硬件问题。联系供应商换卡。
```

**Xid 48 和 Xid 79 是硬件级别的故障——不是你的代码问题，重启解决不了。** 收到后立即检查保修状态。

### $\rm \S \, 45.6.3$ 简单的告警脚本

不需要 Prometheus + Grafana 全家桶。一个 cron job 就够了：

```bash
#!/bin/bash
# /etc/cron.hourly/gpu-check
TEMP=$(nvidia-smi --query-gpu=temperature.gpu --format=csv,noheader | sort -rn | head -1)
if [ "$TEMP" -gt 85 ]; then
    echo "GPU temp critical: ${TEMP}°C" | mail -s "GPU TEMP ALERT" admin@lab.edu
fi
```

## $\rm \S \, 45.7$ 常见故障与恢复

### $\rm \S \, 45.7.1$ 掉卡

**现象**：`nvidia-smi` 看不到某张卡，或训练中途报 `CUDA error: unknown error`。

**排查**：
1. `lspci | grep -i nvidia`——如果这里也不出现，硬件接触问题。关机，重新插拔。
2. 如果 `lspci` 能看到但 `nvidia-smi` 看不到——驱动问题。`dmesg | tail -50` 查内核日志。
3. `sudo nvidia-smi -r`——尝试重置 GPU（需要 root）。

### $\rm \S \, 45.7.2$ OOM Killer

Linux 的 Out-of-Memory Killer 会在系统内存耗尽时杀掉最占内存的进程：

```bash
dmesg | grep -i "out of memory"
# 如果训练进程被 OOM kill：减少 DataLoader 的 num_workers、减少内存中缓存的数据
```

### $\rm \S \, 45.7.3$ 磁盘满

```bash
df -h /data     # > 90% 就危险了
# 找最大的目录
du -sh /data/* | sort -rh | head -10
# 常见元凶：某人的 checkpoint 目录（模型文件可能一个就是几 GB），或未清理的 Docker 镜像
docker system prune -a   # 清理所有未使用的 Docker 数据（小心：会删除所有停止的容器和未用的镜像）
```

### $\rm \S \, 45.7.4$ NFS 卡死

如果 `/data` 是从 NAS 挂载的 NFS，网络抖动可能导致所有访问 `/data` 的进程进入**不可中断睡眠**（D 状态）。此时 `kill -9` 无效。

**排查**：`ps aux | grep ' D'` 看到 D 状态的进程。`df -h /data` 如果也卡住了——NFS 服务器无响应。需要在 NFS 服务器端排查。

## $\rm \S \, 45.8$ 备份与恢复：代码可以 clone，checkpoint 不能

### $\rm \S \, 45.8.1$ 备份什么

- **不需要备份**：系统配置（`/etc` 可以用 Ansible/cloud-init 重建）、已安装的 apt 包（`apt list --installed` 导出列表即可）、可以从 Git 恢复的代码。
- **必须备份**：数据集（如果来源不稳定）、所有 checkpoint、数据库文件。

### $\rm \S \, 45.8.2$ 最小备份方案

```bash
# 每日凌晨用 rclone 同步 checkpoint 到云存储
# crontab: 0 3 * * * /usr/local/bin/backup-checkpoints.sh

#!/bin/bash
BACKUP_DIR="/data/checkpoints"
REMOTE="s3:my-lab-backup/checkpoints"  # 或 gs:// 或 wasabi://
rclone sync "$BACKUP_DIR" "$REMOTE" --progress --bwlimit 50M
# --bwlimit 限制带宽，避免占满整个网络影响其他人
```

### $\rm \S \, 45.8.3$ 故障演练

**场景**：某人误执行了 `rm -rf /data/checkpoints/*`。

1. 确认备份存在：`rclone ls s3:my-lab-backup/checkpoints`。
2. 恢复：`rclone copy s3:my-lab-backup/checkpoints /data/checkpoints --progress`。
3. 教训：**`/data/checkpoints` 的权限设为 `755`，只允许 owner 删除自己的文件**。

## $\rm \S \, 45.11$ 本章自测答案

> 先闭卷作答本章“关键概念回顾”与“应用与辨析”，再核对以下答案。

### 自测答案 · 关键概念回顾
1. 驱动让 OS 认识 GPU（必须装）；CUDA Toolkit 包含编译器和运行时库（PyTorch pip 包自带运行时，不需要单独装完整 Toolkit）；cuDNN 是深度学习加速库（PyTorch 已内置）。PyTorch 用户只需要装驱动 + pip install torch。
2. 内核更新后 NVIDIA 驱动模块可能不兼容，重启后 `nvidia-smi` 直接失效。用 DKMS 自动重编译驱动模块，且在内核更新后手动验证。
3. 杀掉 Python 进程（`kill -15 PID` 或 `kill -9 PID`）。关掉 Jupyter kernel 或 IDE 窗口不一定释放显存——PyTorch 进程可能在后台存活。
4. PHB = PCIe Host Bridge——两张 GPU 通过 CPU 的 PCIe 交换芯片通信，而不是直连 NVLink。多卡通信带宽会显著受限。这是主板/CPU 拓扑决定的，买机器前就应该确认。

### 自测答案 · 应用与辨析
1. 风道堵塞（灰尘积在散热片上）、这张卡位于“尾气区”（前面所有卡的热风都吹向它）、或者 GPU 内部散热硅脂老化。先清理灰尘，再考虑重新排列 GPU 或增加机箱风扇。
2. 通常是索引越界——模型的输出维度（如 10 分类任务但某条数据的标签是 11）或 embedding 查询了不存在的 token ID。检查标签范围和数据中的无效值。
3. 团队 3 人以上且需要不同 CUDA 版本、需要精确复现训练环境（把 Docker 镜像存档即等于存档完整环境）、需要限制文件系统访问范围（容器只能看到指定目录）。
