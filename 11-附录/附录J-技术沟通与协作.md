# $\rm Appendix \, J$ 技术沟通、文档、代码审查与开源协作

> 你写的代码最终会被人阅读——六个月后的你自己、接手你项目的同事、或者 GitHub 上素未谋面的贡献者。本章讲的是**可操作的技术沟通技能**：如何写一个别人能复现的 bug report、如何审查代码而不只挑格式、如何让一个陌生人通过你的 README 在五分钟内跑起你的项目。

本章不需要任何前置技术知识——只需要你知道 Git 和 Markdown 的基本操作。

## $\rm \S \, J.1$ 如何提问：让回答者愿意帮你

### $\rm \S \, J.1.1$ 一个坏问题和一个好问题

**坏问题**：

> "我的代码跑不起来，怎么办？"

没有环境、没有代码、没有错误信息——回答者只能猜。大多数技术社区的沉默不是因为不友好，而是因为**问题无法回答**。

**好问题**：

> 环境：Ubuntu 22.04, g++ 12.3, 项目地址 github.com/user/paper-manager
> 我运行 `g++ -std=c++17 main.cpp -o main`，报错：
> ```
> /usr/bin/ld: cannot find -lsqlite3
> collect2: error: ld returned 1 exit status
> ```
> 我确认已执行 `sudo apt install libsqlite3-dev`，且 `/usr/lib/x86_64-linux-gnu/libsqlite3.so` 存在。
> 我尝试过：添加 `-L/usr/lib/x86_64-linux-gnu` 参数——仍然同样的错误。
> 请问我遗漏了什么？

这个问题的结构——**环境、预期、实际、尝试过的方法**——让回答者可以立刻定位问题（很可能是 `-lsqlite3` 的库名不对——应该是 `-lsqlite3` 还是 `-lsqlite3-dev`？）。

### $\rm \S \, J.1.2$ 提问的最小模板

```markdown
## 环境
- OS: Ubuntu 22.04
- 工具版本: g++ 12.3, Python 3.11
- 项目地址（如果可公开）: github.com/...

## 我做了什么
（粘贴可复现的最小命令/代码）

## 我期望的结果
（具体描述）

## 实际的结果
（粘贴完整的错误信息，不要截断）

## 我尝试过的方法
- 尝试 A → 结果
- 尝试 B → 结果
```

## $\rm \S \, J.2$ 代码审查：不只是找 bug

### $\rm \S \, J.2.1$ 审查者看什么

| 维度 | 具体问题 |
|------|---------|
| **正确性** | 逻辑对吗？边界条件处理了吗？ |
| **安全性** | 有注入风险吗？敏感数据被记录到日志了吗？ |
| **可读性** | 六个月后的自己（或接手的人）能看懂吗？ |
| **设计** | 和现有代码的结构一致吗？引入了不必要的耦合吗？ |
| **测试** | 新功能有测试吗？修改了现有行为——相关测试更新了吗？ |

格式问题（缩进、命名）交给自动化工具（clang-format、black、ESLint）——**不要把审查者的注意力浪费在机器能解决的问题上**。

### $\rm \S \, J.2.2$ 如何提 PR review 意见

- **区分"必须修"和"建议考虑"**——用 `nit:`（nitpick，小建议）前缀标记非阻塞性建议
- **解释"为什么"，不只说"改成 X"**——"这里应该用 `const&` 因为避免拷贝且不修改参数" > "改成 `const&`"
- **提出问题而非指令**——"如果 `papers` 为空，这个循环会怎样？" > "加个 if 判断"
- **认可做得好的地方**——审查不是只挑错，正向反馈同样帮助团队建立共享标准

### $\rm \S \, J.2.3$ 作为被审查者

- **PR 越小越好**——200 行改动比 2000 行更容易被认真审查
- **在 PR description 中写清楚"做了什么、为什么这样做、怎么测试的"**
- **审查意见不是对你个人的攻击**——是同事花时间帮你提高代码质量

## $\rm \S \, J.3$ Commit Message 与 PR Description

### $\rm \S \, J.3.1$ 一个好的 Commit Message

```text
fix: 修复论文搜索在空输入时的 segfault

当用户在搜索框为空时按回车，parse_query("") 返回 nullptr，
后续代码直接解引用导致崩溃。

根因：parse_query 对空字符串的约定不明确（返回 nullptr 还是空对象？）。
修复：让 parse_query 在空输入时返回空的 Query 对象，并添加测试覆盖此边界。
```

结构：**类型: 简述**（< 50 字符）+ 空行 + **详细说明**（做了什么、为什么、怎么验证的）。类型常用的有：`feat`、`fix`、`refactor`、`test`、`docs`、`chore`。

### $\rm \S \, J.3.2$ 为什么需要好的 Commit Message

`git log --oneline` 让你浏览历史；`git blame` 让你找到每一行的最后修改者和原因。面对 `fix bug` 和 `update` 这样的提交信息，你只能去读代码的 diff 猜测意图——而 `fix: 空输入时的 segfault` 让你立刻知道发生了什么。

## $\rm \S \, J.4$ README：你的项目的门面

### $\rm \S \, J.4.1$ 最小 README 模板

```markdown
# 项目名

一句话描述项目做什么。

## 快速开始
git clone ...
cd project
pip install -r requirements.txt
python main.py

## 用途
- 功能 A
- 功能 B

## 开发
python -m pytest tests/
pre-commit install

## 许可
MIT
```

让一个陌生人在**五分钟内**跑起你的项目——这是 README 的唯一目标。不需要写论文，不需要列所有依赖的许可证。

## $\rm \S \, J.5$ 如何向开源项目贡献

1. **先读 `CONTRIBUTING.md`**——不是所有项目都用相同的流程
2. **先开 Issue 讨论**（如果改动较大）——避免花了一周写的 PR 因为设计方向不一致被拒绝
3. **保持 PR 小而聚焦**——一个 PR = 一个逻辑变更。不要在一个 PR 中同时"修复缩进 + 重构解析器 + 添加新功能"
4. **遵守项目的代码风格**——即使和你的习惯不同。用项目的 linter 配置，不要带自己的 `.clang-format`
5. **接受"被拒绝"是正常的**——维护者可能因为范围、时机或方向拒绝你的 PR，这不代表你的代码不好

## $\rm \S \, J.6$ 关键概念回顾

1. 一个好的技术问题至少包含哪些要素？
> 环境（OS、版本）、可复现的最小步骤、期望结果、实际完整错误信息、已尝试的方法。

2. 代码审查的五个维度是什么？
> 正确性、安全性、可读性、设计一致性、测试覆盖。格式交给自动化工具。

3. Commit Message 的"类型: 简述"结构中，常见类型有哪些？
> feat（新功能）、fix（修 bug）、refactor（重构）、test（测试）、docs（文档）、chore（杂项）。

## $\rm \S \, J.7$ 应用与辨析

1. 收到一条代码审查意见"这个变量名不好"，你不同意。如何回应？
> 先理解审查者的关注点——可能是变量名没有表达意图。提出替代方案并说明理由，而不是直接说"我觉得挺好的"。如果双方无法达成一致，让第三人（或团队规范）来决定。

2. 维护者关闭了你的 PR 并说"这个功能不属于本项目的范围"。你怎么处理？
> 感谢维护者花时间审查。考虑：功能是否可以作为独立插件/扩展？是否更适合 fork 后自己维护？不要争论"我觉得应该加"——范围决定权在维护者。
