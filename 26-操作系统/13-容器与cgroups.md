# $\rm Chapter \, 13$ 容器与 cgroups：隔离是怎么做的

容器如今是部署的默认形态，但拆开 Docker 镜像那层包装，里面没有新内核、没有虚拟硬件，只有两条老机制：namespace 负责「看不见」，cgroups 负责「用得少」。本章把这两条机制拆到系统调用的层面，你会看到容器与虚拟机的本质差别，以及「容器里的 root 不是真 root」这类安全讨论的机制根源。

> **开始前自检**：本章假设你已经会：
>
> 1. □ 用过 `docker run` 或至少理解镜像与容器的关系（计算机速通 §29）；
> 2. □ 知道 fork 出的子进程继承父进程的打开文件与环境（本册 §2）；
> 3. □ 知道 PID 1 在启动链上的特殊地位（本册 §11.1）；
> 4. □ 记得虚拟内存让每个进程以为自己独占内存（本册 §4）。

## $\rm \S \, 13.1$ namespace：让进程只看见自己的世界

虚拟内存给了每个进程一套独立的地址空间；namespace（命名空间）把同样的思路推广到操作系统的其他全局资源：进程编号、网络栈、挂载表、主机名。Linux 一共有八种 namespace，最常用的六种：

1. **PID**：新 namespace 里的进程从 1 开始编号，且看不见外面的进程。
2. **NET**：独立的网卡、路由表、iptables 规则、端口空间。容器里的 80 端口与宿主机的 80 端口互不相干。
3. **MNT**：独立的挂载表。容器看到的根文件系统是镜像解压出来的那棵树，不是宿主机的 `/`。
4. **UTS**：独立的主机名与域名。
5. **IPC**：独立的 System V IPC 对象（信号量、共享内存）。
6. **USER**：独立的用户编号映射。容器里的 UID 0 可以映射到宿主机上一个普通用户。

每个进程在 `/proc/self/ns/` 下有一组文件，readlink 出来的方括号编号就是该进程所在 namespace 的唯一标识。实测（WSL2）：

```text
$ readlink /proc/self/ns/pid /proc/self/ns/net
pid:[4026532228]
net:[4026531840]
```

同一 namespace 里的进程这串数字相同；`docker exec` 进容器再读一次，你会得到另一个编号。判断「两个进程是否在同一个世界里」，比较这串数字是最直接的证据。

namespace 的入口是三个系统调用：`clone`（创建新进程的同时指定进入哪些新 namespace，本册 §2.2 的 fork 是它的特例）、`setns`（把当前进程挪进一个已存在的 namespace）、`unshare`（把当前进程挪进新建的 namespace）。这些操作需要 `CAP_SYS_ADMIN` 能力位；实测在 WSL2 的默认会话里执行 `unshare -fp` 被拒绝，`/proc/self/status` 里 `CapEff: 0000000000000000` 证实了这个会话没有任何能力位。容器运行时（containerd、runc）持有的正是这个能力位：它们以特权身份替你做 namespace 切换。

## $\rm \S \, 13.2$ PID namespace 里的 1 号

容器里的进程常以 PID 1 自居。这不是巧合：进入新 PID namespace 的第一个进程编号就是 1，而 1 号在本册 §2.5 的规则里有一项特殊职责，收养孤儿并转发信号。把这套规则放到容器里，后果立刻具体起来：

1. 容器里没有 init 系统，PID 1 通常就是你的主程序。孤儿进程收养给主程序，主程序不 `wait`，容器里就堆积僵尸。
2. 内核对 PID 1 的信号处理网开一面：没有显式注册 handler 的信号一律忽略。于是 `docker stop` 发的 SIGTERM 常常石沉大海，等超时后运行时改发 SIGKILL。这就是「容器停得慢」的经典出处，解法要么主程序显式处理 SIGTERM（本册 §12.2 的 handler 纪律），要么入口用 `tini` 这类微型 init 转发信号。

## $\rm \S \, 13.3$ cgroups：看不见之外的定量配给

namespace 解决「看得见什么」，cgroups（control groups）解决「能用多少」。它把进程挂到树上，每个节点挂一组控制器，对四类资源记账与限额：

1. **cpu**：按权重分配 CPU 时间（`cpu.max` 写配额，如「每 100ms 最多用 50ms」等于限半核）；
2. **memory**：物理内存上限，超限触发 OOM killer 或换页（可配置）；
3. **io**：块设备带宽与 IOPS 限额；
4. **pids**：进程数量上限，防 fork 炸弹。

cgroup v2 统一挂载在 `/sys/fs/cgroup`，树形结构，进程放叶子、限额放中间节点。实测 WSL2 的控制器列表：

```text
$ cat /sys/fs/cgroup/cgroup.controllers
cpuset cpu io memory hugetlb pids rdma
```

每个容器的沙盒就是一棵子树：runtime 先 `mkdir` 一个子组、写限额文件，再把容器主进程的 PID 写进 `cgroup.procs`，全家（含后续 fork 的子孙，本册 §2 的继承规则）自动受管。你在 `docker run` 里写的 `--cpus=0.5 --memory=256m`，翻译下来就是这两个文件的几行内容。

OOM killer 值得单独一提：memory.max 超限时内核按启发式打分挑一个进程杀掉（评分综合内存占用与 oom_score_adj）。容器内存配额设小后的「进程莫名消失」，第一件事就是查 `dmesg` 里的 OOM 记录与退出码 137（本册 §12.1 的同一编码，这次是信号 9 的内核自动版）。

## $\rm \S \, 13.4$ 容器与虚拟机：两本不同的账

把两条机制合起来看，容器就是「namespace 圈地＋cgroup 配给」的进程组，与虚拟机走的是两条路：

1. **隔离的位置不同**：VM 用 hypervisor 隔离硬件（每台 VM 有自己的内核），容器隔离操作系统接口（全宿主机共享一个内核）。
2. **成本不同**：VM 启动要引导整个内核（秒级），容器只是 clone 加挂载（毫秒级）；VM 的内存账里还有每个内核自己的页表与缓存。
3. **攻击面不同**：容器进程与宿主共享内核，内核漏洞（提权类 CVE）可能穿墙；VM 隔着 hypervisor，攻击面小一个数量级。这是「不可信租户混部用 VM，可信服务用容器」的依据。
4. **接口不同**：容器的可移植性来自镜像分层（应用及其依赖打包成一棵只读文件树）；VM 的可移植性来自磁盘镜像。

「容器里的 root 不是真 root」在机制上对应 USER namespace 与 capability 裁剪：容器内 UID 0 映射出去可能是宿主的 UID 100000，且默认被剥掉 `CAP_SYS_ADMIN` 等高危能力位。它防的是误操作与普通越权，不防内核漏洞，这两件事不要混为一谈。

## $\rm \S \, 13.7$ 本章自测答案

### $\rm \S \, 13.7.1$ 关键概念回顾答案

1. namespace 管「系统资源的视图」，如 PID（进程编号独立）、NET（端口与路由独立）；cgroups 管「资源用量上限」，如 cpu（半核配额）、memory（256MB 上限触发 OOM）。（§13.1、§13.3）
2. 它是 namespace 的唯一标识。同一世界（同一 namespace）的进程编号相同；判断两个进程是否互相可见，比较这串数字即可。（§13.1）
3. 内核对 PID 1 未注册 handler 的信号一律忽略，SIGTERM 默认动作被跳过；运行时等到超时才改发 SIGKILL。修复＝显式注册 handler 或用 tini 当 1 号。（§13.2）
4. 写入 cpu.max：配额 50000／周期 100000，含义是每 100ms 最多消耗 50ms CPU 时间，等于半核。（§13.3）
5. 容器共享宿主内核、只隔系统调用视图，内核漏洞可穿墙；VM 各有内核、隔在 hypervisor 之下，攻击面小得多。成本上容器毫秒级启动、无独立内核开销。（§13.4）

### $\rm \S \, 13.7.2$ 应用与辨析答案

1. PID namespace 挡住了进程清单；但 `/proc/meminfo` 不属于任何 namespace（procfs 的全局部分），`top` 的总量行读的是它，所以显示宿主机内存。LXCFS 等方案靠在容器内挂载改写过的 meminfo 解决这个观感问题。（§13.1）
2. 先看退出码与 `dmesg`：137 加 OOM 记录即 memory.max 触发，确认是限额不是崩溃；再看 `memory.events` 里的 oom 计数定位触顶时刻；最后查哪个子进程被选中（`memory.oom.group` 决定是否连坐）。（§13.3）
3. 启动：容器是 clone 加挂载（毫秒），VM 要引导内核（秒）；运行：容器无虚拟化损耗（直接系统调用），VM 有 hypervisor 转发；迁移：VM 迁整个内存镜像，容器迁镜像层与状态，粒度与用途都不同。（§13.4）
4. 用 VM 起底座（缩小内核攻击面），VM 内再套 namespace 沙箱（限制系统调用视图），叠加 seccomp（本册 §1.3 的过滤扩展：白名单式限制可用系统调用）与只读文件系统。单层容器不够。（§13.4）
