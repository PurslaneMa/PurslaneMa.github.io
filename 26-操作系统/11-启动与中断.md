# $\rm Chapter \, 11$ 启动与中断：从上电到 init

前十章把操作系统当成一个「已经在跑」的程序来讨论：进程在调度、页面在换入换出、内核在响应系统调用。但有一个问题一直被跳过：内核自己是怎么跑起来的？上电那一刻内存里什么都没有，「操作系统的第一行指令」是谁加载的？以及一个更日常的问题：键盘敲一个键，正在全速跑死的程序是怎么「停下来」响应你的？两件事共用同一套机制：中断。

> **开始前自检**：本章假设你已经会：
>
> 1. □ 知道 CPU 分用户态与内核态，系统调用是进内核的门（计算机速通 §11.1、本册 §1.3）；
> 2. □ 接受「进程 = 演出」的比喻，知道内核态与用户态的切换点（本册 §1、§2）；
> 3. □ 会用 `cat /proc/xxx` 读内核暴露的状态（本册 §1.4 的边界讨论）；
> 4. □ 写过 `sleep` 加 `&` 的后台命令，对「程序在等什么」有直觉。

## $\rm \S \, 11.1$ 上电之后：启动链

上电瞬间，CPU 从一个固定的地址开始取指令（x86 是固件映射的复位向量）。此时磁盘上的内容一个字节都没进内存，操作系统还躺在外存里。于是启动是一条接力链，每一棒只做一件小事，然后把控制权交给下一棒：

1. **固件（BIOS 或 UEFI）**：硬件自检（POST），初始化内存与最基本的设备，然后按启动顺序找一个盘，把盘开头的一段固定大小的代码（传统 BIOS 是主引导扇区 MBR，512 字节；UEFI 是一个 FAT 分区里的 `.efi` 文件）加载进内存并跳过去。
2. **引导加载器（bootloader，如 GRUB）**：这段代码能看懂文件系统了。它的任务是把内核映像从磁盘读进内存、把启动参数（内核命令行）准备好，然后跳到内核入口。
3. **内核初始化**：CPU 从实模式逐级切换到保护模式与长模式（x86），建好页表、打开中断控制器、注册中断处理函数，然后创建第一个进程。
4. **init（PID 1）**：内核建的第一个用户态进程，通常是 systemd。此后所有用户进程都是它的后代（本册 §2 的 fork 链条从它开始），系统启动服务由它按依赖关系拉起。

每一棒都只依赖上一棒留下的最小约定。这个设计的动力是兼容：固件不知道你要装什么系统，bootloader 不知道你要跑什么内核，内核不知道你要启动哪些服务。接力链让每一层可以独立替换。

引导扇区为什么只有 512 字节？这是 1981 年 IBM PC 定下的硬件约定，后来的 UEFI 把它放宽成了真正的可执行文件，但「固件只负责找到下一棒」这个分工没有变。

**本节小结**：启动是四棒接力（固件 → bootloader → 内核 → init），每一棒只依赖上一棒的最小约定、只做一件小事；512 字节这个看似古怪的限制，就是第一棒与第二棒之间那份约定的历史尺寸。

## $\rm \S \, 11.2$ 中断：CPU 的门铃

CPU 执行指令是顺序的，但世界不是：磁盘完成了、网卡来了包、时钟走了一格、你敲了键盘。CPU 需要一种机制，让「正在跑的代码」被打断，先去处理紧急的事，再回来接着跑。这就是中断（interrupt）。

中断分成两大类，来源不同，但处理路径相同：

1. **硬件中断**：外设通过中断控制器（x86 上的 APIC）发给 CPU 的电信号。磁盘完成、网卡收包、时钟滴答都在此列。特点是异步：任何时候都可能来，与当前执行的代码无关。
2. **异常（exception）**：当前指令自己触发的同步事件。除零、缺页（本册 §4）、非法指令是错误类；系统调用的 `syscall` 指令是陷阱类，它故意触发一次「受控的中断」来进内核。

处理路径是统一的：CPU 保存现场（把关键寄存器压栈或换到内核栈），按中断号查一张表（中断向量表 / IDT），跳到对应的处理函数；处理函数做完事，恢复现场，回到被打断的地方继续。整个切换由硬件与内核协作完成，用户程序毫无感知。

验算：中断与普通函数调用有什么区别？普通调用是程序自己安排的，返回地址固定；中断的「调用点」是随机的，可能落在任意两条指令之间，所以保存的现场必须完整到「被中断的程序自己完全察觉不出被打过」。

**本节小结**：中断是「世界不按顺序来」逼出的机制：硬件中断异步来自设备，异常同步来自当前指令（系统调用是故意触发的陷阱），但两条路汇入同一个「存现场、查表、进处理函数、恢复现场」的流程——和函数调用的本质差别只在调用点不由程序自己挑。

## $\rm \S \, 11.3$ 时钟中断：多任务的心跳

所有硬件中断里有一种特殊的存在：时钟中断。定时器每隔一小段时间就打断 CPU 一次，内核利用它做三件事：更新系统时间、检查有没有定时到期的任务，以及本册 §3 的主角，给调度器一个重新决策的机会。

没有时钟中断，一个进入死循环的程序就永远占着 CPU（它再也不调用任何系统调用，内核没有任何介入机会）。时钟中断是「内核总能拿回控制权」的最后保障。这就是为什么抢占式调度（本册 §3.4）依赖它。

中断频率不需要很高。现代内核是 tickless（无固定节拍）设计：空闲时干脆停掉周期中断省电，忙时按需设定时器。中断处理本身也有开销（保存现场、走处理函数、恢复），频率太高会把 CPU 耗在切换上。

实测看一下中断的规模。在 WSL2 里隔 2 秒读两次 `/proc/stat` 的 `intr` 计数（所有中断的累计值，16 核合计）：

```text
第一次读：215513
第二次读：217241
差值 1728 次 / 2 秒 ≈ 864 次中断每秒
```

机器同时跑着浏览器、编辑器与十几条终端会话，全机每秒八百多次中断、单核摊到几十次。这个数字远低于「每毫秒一次」的旧时代固定节拍：tickless 生效后，大部分中断是设备事件（磁盘、网卡），不是心跳。

想看「哪来的中断」，`/proc/interrupts` 按设备与 CPU 列出计数。实测里能看到 `rtc0`（实时时钟）与 `acpi` 各占一行，每行 16 个数字对应 16 个 CPU 各自处理了多少次。

**本节小结**：时钟中断是内核「总能拿回控制权」的最后保障，抢占式调度整个压在它上面；tickless 设计把周期心跳换成按需定时，所以实测每秒八百多次中断的主体已是设备事件而非心跳。

## $\rm \S \, 11.4$ 从敲键盘到屏幕：一次中断的旅程

把机制串起来走一遍完整流程。你在终端敲下字母 `a`：

1. 键盘控制器通过中断报告「有键按下」，CPU 停下当前工作，进入键盘驱动。
2. 驱动读扫描码，翻译成键值，交给 TTY 层（本册 §12 的主角）。
3. TTY 把字符放进输入队列，唤醒等在 `read()` 上的 shell 进程。
4. shell 从 `read()` 返回拿到字符，回显（echo）又走一遍输出路径，最终显卡把字符画到屏幕上。

四步里第 1、2 步在中断上下文，第 3、4 步在进程上下文。中断上下文有一条铁律：不能睡眠。原因是中断「借用」了被打断程序的现场，没有独立的进程身份，调度器无法把它挂起再唤醒。所以驱动的中断处理只做最少的事（把数据搬走、登记状态），剩下的工作排成任务等进程上下文去慢慢处理。

这也是通用原则：中断处理越短越好。网卡驱动在中断里只应答硬件并把包丢进队列，协议栈解析全在下半部做。你写代码时把「响应」与「处理」分开，与内核把中断分成上下两半是同一件事。

**本节小结**：一次按键走了「驱动（中断上下文）→ TTY → 唤醒进程（进程上下文）」四步；分界线来自中断上下文不能睡眠的铁律——没有进程身份，调度器无处挂起它——于是「快响应」留在上半部，「慢处理」推给下半部，这把分工也是你自己写事件代码时的模板。

## $\rm \S \, 11.6$ 应用与辨析

1. 把一段死循环跑在一个没有时钟中断的裸机上，操作系统还能靠什么拿回控制权？
2. UEFI 相比 BIOS 的启动流程改了什么？为什么 512 字节的限制消失了？
3. 网卡每秒来 10 万个包，每个包都触发一次中断会发生什么？内核的对策（中断合并、NAPI）解决的是哪一步的问题？
4. `kill -9` 一个正在内核态处理磁盘中断的进程，会发生什么？

## $\rm \S \, 11.7$ 本章自测答案

### $\rm \S \, 11.7.1$ 关键概念回顾答案

1. 四棒：固件（自检并找到启动盘开头的一段代码）、bootloader（读文件系统、装载内核映像与启动参数）、内核（建页表与中断机制、造出 PID 1）、init（拉起用户态服务）。每一棒的输入是上一棒的最小约定，输出是「把控制权与足够的信息交给下一棒」。（§11.1）
2. 相同点：走同一条「保存现场、查表、进处理函数、恢复现场」的路径。不同点：硬件中断异步、来自设备；异常同步、由当前指令触发，系统调用是其中故意触发的陷阱类。（§11.2）
3. 抢占的依据是时钟中断给的机会。死循环不产生任何陷阱（不调系统调用、不缺页），内核唯一的介入点就是时钟中断；没有了它，调度器永远得不到执行权。（§11.3）
4. 中断借用被打断程序的现场运行，没有独立进程身份，调度器无法挂起与唤醒它；睡眠意味着「主动让出 CPU 等待事件」，这在没有进程上下文的地方没有意义。（§11.4）
5. 现代内核是 tickless 设计：空闲时停掉周期中断，忙时按需设定时器。实测的中断多为设备事件而非固定心跳，所以总量远低于固定节拍时代的每秒上千次每核。（§11.3）

### $\rm \S \, 11.7.2$ 应用与辨析答案

1. 只能靠异常：若死循环里有访存、除法等指令，缺页或除零异常仍会进内核；若程序完全由寄存器运算组成，内核确实没有任何硬件层面的介入点，只能重启。这就是「抢占依赖中断」的极端表述。（§11.3）
2. BIOS 从 MBR 的 512 字节接力，UEFI 直接加载 FAT 分区里的 `.efi` 可执行文件，bootloader 的第一段从「机器码残片」升级成真正的程序；阶段划分仍保留，只是第一棒能做的变多了。（§11.1）
3. 每秒 10 万次中断会把 CPU 全耗在保存恢复现场上（中断风暴），真正处理包的时间反而不够。中断合并让网卡攒一批包再报一次中断，NAPI 用轮询替代高频中断，两者都在减少第 1 步的次数。（§11.4）
4. 什么都不会发生：信号（§12 的机制）只在返回用户态时被检查，而进程根本不会回到用户态；内核处理完中断该干嘛干嘛。`kill -9` 的「必死」承诺针对的是用户态执行路径。（§11.2、§12.1）

中断给了内核「随时介入」的能力，但到目前为止我们只把它用在硬件事件上。下一章把镜头转向一类特殊的软件事件：另一个进程对你发来的通知，信号。它是 Unix 世界里最古老、也最容易用错的进程间通信。
