# $\rm Chapter \, 5$ TCP 可靠性：序列号、确认与重传

第 4 章把承诺摆上桌：TCP 对上层交付一条可靠有序的字节流。本章兑现它。地基是坏的，IP 只肯尽力而为（本册 §3.1），丢、乱、重复一概不管；链路层校验发现误码即丢帧（本册 §2.2），连「损」也转化成「丢」。TCP 在这样的地基上补出可靠，靠四样彼此咬合的机关：序列号定位、确认对账、重传补漏、窗口限速。本章逐一拆开，并用一个模拟实验回答「窗口为什么值得存在」。

> **开始前自检**：本章假设你已经会：
>
> 1. □ IP 尽力而为：不保证送达、按序、不重复（本册 §3.1）；
> 2. □ CRC 发现误码即丢帧，补救靠上层重传（本册 §2.2）；
> 3. □ TCP 字节流语义：可靠、有序、无边界（本册 §4.3）；
> 4. □ 会用 random.Random 固定种子跑小模拟（计算机速通 §17；本册 §2.6 用过）。

## $\rm \S \, 5.1$ 可靠交付要解决什么

把「可靠」拆开，它要同时对抗四件事：

1. 丢（loss）：数据报在路由器缓冲区溢出时被丢弃，或误码帧被 CRC 整帧丢弃（§2.2）；
2. 乱（reordering）：两份数据报走了不同路径，后发的先到（§3.1 明确不保证按序）；
3. 重（duplication）：超时重传与路径切换都可能让同一份数据到达两次；
4. 损（corruption）：位翻转。逐跳 CRC 已把绝大多数拦下变成丢，漏检的残余与转发设备内存里的翻转由 TCP 头里的校验和再拦一道，即拦下的同样变成丢。

「损」被校验归约成「丢」，真正需要机制对付的只剩丢、乱、重，而它们的修复手段是同一个：重传。于是全部问题归结为三问：怎么发现缺了什么（序列号与确认号，§5.2–5.3），什么时候重传（超时与重复确认，§5.4–5.5），以及怎么不因补漏把网络压垮（窗口，§5.6）。

## $\rm \S \, 5.2$ 序列号：给字节流的每个字节编号

确认之前先有刻度。TCP 的编号直接长在字节流（§4.3）上：**序列号（sequence number）**是本报文段第一个字节在整条字节流中的位置。**报文段（segment）**是 TCP 交给 IP 的数据单元，一段连续字节加至少 20 字节的头部（§1.4 见过它）。真实 TCP 从双方各自随机抽取的**初始序列号（initial sequence number，ISN）**起数（为什么随机，第 7 章见），本章统一从 1 起数便于手算。

手算算例：应用写入 10 个字节，TCP 装成三个报文段，A 载字节 1–3（序列号 1）、B 载 4–6（序列号 4）、C 载 7–10（序列号 7）。序列号把字节流变成一条带刻度的轨道，报文段在上面各占一段；下一节确认号就在这条轨道上对账。

## $\rm \S \, 5.3$ 累积确认：一个号码确认一段前缀

**确认号（acknowledgment number）**的语义叫**累积确认（cumulative acknowledgment）**：「比确认号小的字节已全部收到，请从确认号这个字节继续发」。它确认的不是一个报文段，而是一段前缀。沿用 §5.2 的算例，故意让 B、C 先到：

1. B（4–6）先到：确认号停在 1，缺口在开头，4–6 号先进接收缓冲区缓存，不上交应用；
2. C（7–10）再到：确认号仍是 1，7–10 一并缓存；
3. A（1–3）最后到：1–10 齐了，确认号一口气跳到 11。

两个推论值得单独钉住：

1. 丢一个确认不要紧：确认号 11 的确认本身丢了，下一个确认号只会更大，照样覆盖 1–10，累积确认天然冗余；
2. 乱序不慌：先到的乱序段缓存在接收端，洞一补齐就连续上交，「字节流无空洞」的承诺就是这样兑现的。

**本节小结**：确认号报的是「前缀收到哪」，不是「刚收到哪」；确认丢失不致命与乱序只缓存不重传，都是这条语义的白送品。

## $\rm \S \, 5.4$ 超时重传与 RTT 估计

发现丢包最直接的办法：发出去的字节过了**重传超时（retransmission timeout，RTO）**还没被确认，就当它丢了，重发。RTO 取多大是个权衡：设得比真实**往返时间（round-trip time，RTT）**短，大量没丢的报文被冤枉重发；设得太长，每次真丢包都白等很久。麻烦在于 RTT 本身漂移，无线信道抖动、路由切换都会让它变，定值两头不讨好。

TCP 对 RTT 做指数加权平均，新样本只占 ${1/8}$（**平滑往返时间（smoothed RTT，SRTT）**是估计值，$R$ 是刚测到的样本）：

$$
\text{SRTT} \leftarrow \frac{7}{8}\,\text{SRTT} + \frac{1}{8}\,R
$$

读法：新估计是旧估计的 7/8 加上新样本的 1/8——一次测量至多把估计挪动八分之一，单个毛刺样本掀不起大浪。

手算两步：初值取 ${\text{SRTT} = 200\,\text{ms}}$，先测到样本 ${160\,\text{ms}}$，再测到 ${240\,\text{ms}}$：

$$
\begin{aligned}
\text{SRTT}_1 &= \tfrac{7}{8}\times 200 + \tfrac{1}{8}\times 160 = 175 + 20 = 195 \\
\text{SRTT}_2 &= \tfrac{7}{8}\times 195 + \tfrac{1}{8}\times 240 = 170.625 + 30 = 200.625
\end{aligned}
$$

每个旧样本的权重每过一步乘 ${7/8}$，「指数平均」由此得名：越老的样本越轻，历史的影响指数衰减，估计值跟着最新的网络状态走。RTO 在 SRTT 之上再加一笔随波动增大的余量（标准公式见 RFC 6298），且每超时一次 RTO 翻倍，避免反复撞墙。还有一条纪律：重传报文段的样本不计入估计，确认到达时分不清它对应哪一次发送（§5.8 结清这笔账）。

## $\rm \S \, 5.5$ 快速重传：三个重复确认的门限

超时重传有先天缺陷：RTO 是一个 RTT 的量级，真丢了也要干等一整个 RTO。更快的信号其实早就在路上：§5.3 说过，洞后面的乱序段会触发确认号停在洞口的确认。洞后面每到一个报文段，接收方就再发一个一模一样的确认，发送方收到同一确认号的副本，即**重复确认（duplicate ACK）**，立刻知道洞还在。

**快速重传（fast retransmit）**的规则：收到 3 个重复确认就立即重发洞口那段，不等超时。门限为什么是 3 而不是 1？报文段可能只是被网络轻微重排（§3.1），一两个重复确认可能虚惊一场；连续 3 个意味着洞后面至少已有 3 个报文段赶到，这段大概率真丢了。3 是「重排的罕见程度」与「反应速度」之间的经验折中，一条约定，不是定理。

## $\rm \S \, 5.6$ 滑动窗口与流量控制

可靠只管「送到」，没管「别撑着」，§1.1 的第三个问题（快慢不匹配）到这里还账。**流量控制（flow control）**由**滑动窗口（sliding window）**实现：发送方把「已发送但未确认」的字节限制在一个区间内，确认到达，区间就向前滑。区间长度的上限由接收方说了算，每个确认里捎带一个**接收窗口（receive window，rwnd）**，含义是「我的缓冲区还能再吃多少字节」。发送方守住一条不变式：已发送而未确认的字节数，不得超过 rwnd 标出的额度。

手算一轮窗口的开合（接收缓冲区 400 字节；窗口区间左闭右开，右端是下一个不能发的字节号）：

| 事件 | 缓冲区空闲 | 确认携带的 rwnd | 发送窗口 |
| --- | --- | --- | --- |
| 连接建立 | 400 | 400 | ${[1, 401)}$ |
| 发 1–200；回 ACK=201、rwnd=200 | 200 | 200 | ${[201, 401)}$ |
| 发 201–400；回 ACK=401、rwnd=0 | 0 | 0 | ${[401, 401)}$ 零窗口，停发 |
| 应用读走 400 字节，窗口更新 | 400 | 400 | ${[401, 801)}$ 恢复 |

三处细节：1. 第二行左缘推进到 201，1–200 已确认，滑出窗口；右缘没动，因为信用只剩 200；2. rwnd=0 是硬闸门，发送方必须停；3. 应用读走数据后，接收方发一个不带数据的纯确认（窗口更新）重新开门，否则双方互相等待，死锁。窗口的另一头其实还有一道约束，即网络本身的容量；rwnd 只保护接收端，保护网络的那半个窗口是第 6 章的主角。

**本节小结**：rwnd 是接收端给的信用额度，已发送未确认的字节不得超过它；零窗口停发，靠应用读走数据后的窗口更新重新开门。

## $\rm \S \, 5.7$ 实验：停等与连续 ARQ 的吞吐

窗口的开合直接决定吞吐。**停等（stop-and-wait）**是窗口等于 1 的极端：发一包、停下来等确认，确认不到就超时重发。**自动重传请求（Automatic Repeat reQuest，ARQ）**是这类「确认加重传」机制的总称，窗口大于 1 的连续 ARQ 允许多包在途。用固定种子模拟：每轮 1 个 RTT，发送方把窗口填满，每个在途槽以 ${1-p}$ 的概率当轮被确认，丢失的下一轮补发（确认不丢、超时记 1 个 RTT、各槽独立投递）。任意目录运行：

```python
import random

def arq(n, W, p, seed=20261025):
    rng, done, slots = random.Random(seed), 0, 0
    while done < n:
        done += sum(rng.random() > p for _ in range(min(W, n - done)))
        slots += 1
    return n / slots                       # 吞吐 = 包数 / 总轮数

for p in (0.1, 0.3):
    for W in (1, 4, 8):
        print(f"p={p} W={W}: {arq(2000, W, p):.2f} 包/RTT")
```

本机（Windows 11、Python 3.12）输出整理成表，理论值 ${W(1-p)}$ 供手算对照：

| 丢包率 p | 窗口 W | 实测吞吐（包/RTT） | 理论 ${W(1-p)}$ |
| --- | --- | --- | --- |
| 0.1 | 1（停等） | 0.90 | 0.90 |
| 0.1 | 4 | 3.59 | 3.60 |
| 0.1 | 8 | 7.17 | 7.20 |
| 0.3 | 1（停等） | 0.71 | 0.70 |
| 0.3 | 4 | 2.84 | 2.80 |
| 0.3 | 8 | 5.67 | 5.60 |

读法三条：

1. 停等每 RTT 至多交付 1 包，再打上 ${1-p}$ 的折扣：p=0.1 时 0.90 包/RTT，与手算一致，即大部分时间管道在空等确认；
2. 窗口线性放大吞吐：实测与理论 ${W(1-p)}$ 几乎重合，W 从 1 到 8 吞吐涨约 8 倍，把「等确认」的时间用来继续发，管道不再空转；
3. 前提别忘：本模型里管道除窗口外没有别的瓶颈。真实链路能承载的在途字节是「速率 × RTT」（**带宽时延积（bandwidth-delay product）**）：10 Mbps、RTT 40 ms 约容纳 50 KB，即约 34 个满载段；窗口超过它，多出来的字节只会堆进路由器队列，那是第 6 章的故事。

## $\rm \S \, 5.8$ 重传的语义坑：重复报文与去重

超时重传有个绕不开的含混：触发它的两种原因，数据丢了，或确认丢了，接收端分不清，发送端也分不清。假设发送方超时后重发了字节 1–3，随后原报文段姗姗到达：接收方手里有了两份 1–3。若照单全收上交应用，字节流变成「1–10 再接 4–10」，重复数据直接毁掉 §4.3 的承诺。

去重要回答「这两份是不是同一份」，而这个问题只有在字节有了编号之后才可回答：接收方发现该段序列号落在已收范围内，判定重复，丢弃，再补一个确认。补确认不可省，这次重传很可能正是一次确认丢失引起的，不补，发送方会再超时一次。没有序列号的世界里连「重复」都无法定义：一个只会说「再发一遍文件」的协议，收到两遍内容完全相同的传输时，永远无法分辨这是重传还是两次独立发送。序列号给了每个字节身份，去重才从无解变成一条查表规则。顺带结清 §5.4 的账：正因确认分不清对应哪次发送，重传报文段的 RTT 样本一律不作数，这条纪律叫 **Karn 算法（Karn's algorithm）**。

## $\rm \S \, 5.11$ 本章自测答案

> 先闭卷作答 §5.9 与 §5.10，再核对。

### $\rm \S \, 5.11.1$ 关键概念回顾答案

1. 丢来自缓冲区溢出与误码弃帧，乱来自多路径竞速，重来自超时重传与路径切换，损来自位翻转；逐跳 CRC 把损拦下变成丢（§2.2），TCP 校验和拦住残余，于是重传机制只需对付丢、乱、重。（§5.1）
2. 确认号 N 表示「N 之前全部收到，从 N 继续发」；后面的确认号覆盖前面的，单个确认丢了不致命；乱序段只能缓存，因为提前上交会在字节流里留下洞。（§5.3）
3. RTT 随路径与信道漂移，定值两头失败：太短冤枉重发，太长白等。公式 SRTT ← 7/8·SRTT + 1/8·R；(7/8)×200 + (1/8)×160 = 195。（§5.4）
4. 乱序同样触发重复确认，一两个可能是虚惊；连续 3 个意味着洞后至少 3 段已赶到，真丢的概率压倒重排，即门限是经验折中。（§5.5）
5. 已发送而未确认的字节数不超过 rwnd；零窗口时发送方停在原地，恢复靠接收方应用读走数据后发出的窗口更新（rwnd=400 的纯确认）。（§5.6）

### $\rm \S \, 5.11.2$ 应用与辨析答案

1. 对的一半：累积确认确实省，一个确认号覆盖一段前缀，确认丢了也不用单独补发。漏的一半：省是副产品，本质是鲁棒性，交付不依赖任何一个确认报文段活着，乱序也只是缓存而非重传。（§5.3）
2. 上限 = 64 KB ÷ 50 ms = 1.31 MB/s，约 10.5 Mbps；链路有 100 Mbps，瓶颈是 rwnd（接收缓冲区太小）。破法：调大缓冲区并开启窗口缩放，把 rwnd 抬到不小于带宽时延积 100 Mbps × 50 ms = 625 KB。（§5.6、§5.7）
3. 1. 按序列号判定重复并丢弃；2. 把缓存里的后续字节接上交付（洞已补齐时）；3. 重发确认。省掉第三件：若这次重传正是确认丢失触发的，发送方等不到确认会再次超时、RTO 翻倍，吞吐跌进退避循环。（§5.8）
