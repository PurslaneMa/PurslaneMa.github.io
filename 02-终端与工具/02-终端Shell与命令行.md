# $\rm Chapter \, 2$ 终端、Shell 与命令行

> 上一章里，你看到程序从源代码变成可执行文件、再变成运行中的进程——但那些实验多半是点击界面、或者敲一条别人写好的命令完成的。真实开发不是这样：没人替你把“编译、运行、装依赖、连服务器”做成按钮，你得自己用文字把这些事说清楚。本章先帮你打开那个说话的界面（终端），再教你安全地驾驶它。

> **开始前自检**：本章假设你已经会：
>
> - □ 完成第 1 章实践：写出并运行过一个 C++ 程序（§1.9）
> - □ 理解源代码 → 可执行文件 → 运行中进程的基本链条（§1.2）
> - □ 知道程序结束时会给操作系统一个状态（退出码）（§1.3.3）

## $\rm \S \, 2.1$ 为什么需要终端

回想一下在 OJ 上做题的日子：“运行程序”是一个按钮，“喂数据”是另一个框，评测机在你看不见的地方完成一切。你只需要提交代码，剩下的动作都被平台包办了。

真实开发里没有这个平台。编译要你自己发起，依赖要你自己装，服务器要你自己连，程序跑挂了要你自己去看日志。这些动作有个共同点：**它们都能用一句话精确描述**——“运行哪个程序、传什么参数、数据从哪来、结果到哪去”。而命令就是那句话。

能用一句话描述，就有两个直接好处。一是**可记录**：你说过的话可以原样写进脚本，下次一键重放，CI（Continuous Integration，持续集成——第 21 章讲）甚至让机器替你重放。二是**可核对**：出错时你手里有完整的一句话，能拿去问人、能贴进搜索引擎。GUI 里的那次点击，既没法记录，也没法描述给别人。

## $\rm \S \, 2.2$ 如何打开终端

先把最现实的问题解决掉：终端窗口从哪来？不同操作系统方法不同，但都要不了几秒钟。

### $\rm \S \, 2.2.1$ Windows：PowerShell 与 Windows Terminal

按键盘上的 **Win 键**（带 Windows 标志的那个），直接输入 `PowerShell`（Windows 11 输入 `Terminal` 也能搜到 Windows Terminal），看到结果按回车。一个深色窗口出现，里面有一行字：

```text
Windows PowerShell
版权所有 (C) Microsoft Corporation。保留所有权利。

PS C:\Users\你的用户名>
```

这就是终端窗口。末尾那行 `PS C:\Users\你的用户名>` 叫**提示符**（prompt）——它出现，就是在告诉你“我准备好了，等你输入”（§2.3 细讲）。

另外两种常见打开方式：

- **Win+R** 打开“运行”对话框，输入 `wt` 回车，打开 **Windows Terminal**（微软的现代终端程序，支持多标签页）；如果电脑上没有它，输入 `powershell` 回车，直接打开 PowerShell。
- 鼠标**右键点击开始按钮**，菜单里选“终端”（Windows 11）或“Windows PowerShell”（Windows 10）。

PowerShell 和 Windows Terminal 常被混着叫，但它们是两个东西：**Windows Terminal 是窗口**，负责显示文字、开标签页；**PowerShell 是窗口里跑的 Shell**，负责听懂你输入的命令。这个区别到 §2.7 会真正用上，现在先不纠结。

### $\rm \S \, 2.2.2$ WSL：开始菜单里的 Ubuntu

如果你装了 WSL（Windows Subsystem for Linux，在 Windows 内运行 Linux 的官方方式，安装见[终端进阶](25-终端进阶.md)的 §25.1），打开更简单：按 Win 键输入 `Ubuntu` 回车。窗口里出现的是另一种风格的提示符：

```text
alice@DESKTOP-XXXX:~$
```

### $\rm \S \, 2.2.3$ Linux 与 macOS

- **Linux 桌面**：按 **Ctrl+Alt+T** 直接打开；或在应用菜单里搜 “Terminal”。
- **macOS**：按 **Cmd+空格** 唤出 Spotlight，输入 `Terminal` 回车。

### $\rm \S \, 2.2.4$ 打开之后：你应该看到什么

不管从哪条路打开，成功的标志都一样：一个窗口，里面有一行提示符，光标在末尾闪烁——它在等你。这时候随便试一条命令：输入 `pwd` 回车（§2.4 会解释这条命令），能看到一行输出，就说明终端是活的。

打不开时先检查：名字拼对了没有（是 `PowerShell`，不是 `power shell`）；Windows 自带 PowerShell，如果搜索不到，用 Win+R 输入 `powershell`；提示“没有安装 WSL”，说明确实还没装，先去看[终端进阶](25-终端进阶.md)的 §25.1。

## $\rm \S \, 2.3$ 提示符：终端在等你输入

提示符不是摆设。它通常会告诉你三件事：当前用户是谁、在什么机器上、现在停在哪。不同系统的长相不一样：

```text
PS C:\Users\Alice\projects>          # PowerShell
alice@server:~/projects$             # Bash / Zsh
```

最后那个 `>` 或 `$` 是“请说话”的记号。教程里写的 `$ git status`，开头的 `$` 往往只是提示符的示意——**别把 `$` 一起敲进去**。

如果提示符结尾是 `#`，在 Unix 文档里通常表示当前是 root（管理员）。遇到命令失败不要急着切 root 重试，先搞清楚它为什么失败（§2.13 有完整流程）。

## $\rm \S \, 2.4$ 第一条命令：pwd、ls、echo

提示符在等你，你却不知道该说什么——那就先回答三个最自然的问题：**我在哪？这里有什么？能让电脑开口说话吗？**

**我在哪：`pwd`。** 输入 `pwd` 回车（PowerShell 里对应 `Get-Location`，作用相同），终端打印出你当前所在的目录：

```bash
pwd
/home/alice
```

**这里有什么：`ls`。** 输入 `ls` 回车（PowerShell 对应 `Get-ChildItem`），列出当前目录下的文件与文件夹：

```bash
ls
Desktop  Documents  projects  papers.txt
```

**让电脑说句话：`echo`。** 输入 `echo hello` 回车：

```bash
echo hello
hello
```

`echo` 是打印程序，它把后面的话原样显示出来。别看它简单，它让你第一次看清命令的骨架：`echo` 是**程序**，`hello` 是**参数**（argument）——传给程序的值。往后所有命令都是这个骨架：先是一个程序名，后面跟着给它的参数。

刚打开终端就把这三条各敲一遍，等于走完了一整圈“终端体验循环”：你输入命令 → Shell 启动程序 → 程序输出 → 终端显示给你。这时候故意敲一个拼错的命令，比如 `echho`，PowerShell 会报：

> `无法将“echho”项识别为 cmdlet、函数、脚本文件或可运行程序的名称。请检查名称的拼写，如果包括路径，请确保路径正确，然后再试一次。`

“找不到这个命令”各 Shell 都会报，只是文案不同：`cmd.exe` 说 `'echho' 不是内部或外部命令，也不是可运行的程序或批处理文件。`，Bash 只说 `echho: command not found`。见到哪一种都别慌——这个错误背后藏着一个关键机制：Shell 凭什么知道 `echo`、`ls` 对应哪个程序？答案是 PATH，§2.9 专门讲。

> **练习**：把 `pwd`、`ls`、`echo hello` 各输入一遍，对照上面的输出——三条都打印出结果，说明终端和 Shell 都在工作。再故意敲一个拼错的命令（如 `echho`），确认看到的是上面那条“无法将…项识别为 cmdlet”的报错，记住它的样子——后面你会经常见到它。

## $\rm \S \, 2.5$ 工作目录与 cd：移动

刚才 `pwd` 打印的那个目录，叫**工作目录**（working directory）。可以把它想成文件管理器里“当前打开”的那个文件夹：你双击进了某个文件夹，文件管理器就停在那里，显示的内容都从那里算起。终端也一样，它永远停在某个目录里，你敲的相对路径（relative path，相对当前位置的描述）都从那里出发。

先确认自己在哪，再试着挪个地方：

```powershell
# PowerShell
Get-Location          # 查看
Set-Location D:\projects
# 常用别名
cd D:\projects        # cd 与 Set-Location 等价
```

```bash
# Bash/Zsh
pwd
cd /home/alice/projects
```

`cd`（change directory，切换目录）成功时**通常一声不吭**。没输出不等于没执行——再敲一次 `pwd`，或看提示符里的目录有没有变，用结果验证。

路径里常出现的记号：

- `.`：当前目录；
- `..`：上一级目录；
- Windows `C:\`：C 盘根目录；
- Unix `/`：文件系统根目录；
- Unix `~`：当前用户主目录（home directory）的缩写。

```text
./app          当前目录中的 app
../data        上一级目录中的 data
src/main.cpp   当前目录下 src 子目录中的文件
```

Windows 原生路径用反斜杠 `\`，Unix 用正斜杠 `/`；不少 Windows 开发工具也接受正斜杠，但别假设所有工具都认。`cd` 到一个不存在的目录会报错（`找不到路径` / `No such file or directory`）。这个报错几乎人人见过，排查套路也固定：先 `pwd` 确认自己在哪，再检查路径拼写。

> **练习**：建一个安全的练习目录再进去：`mkdir terminal-lab` 然后 `cd terminal-lab`（PowerShell 也能直接 `mkdir`），用 `pwd` 确认，`cd ..` 回到上级，再 `cd terminal-lab` 回来。每一步动手前，先说出你预计当前会在哪个目录。成功判据：每一步 `pwd` / `Get-Location` 打印的目录，都和你动手前说出的那个一致。

## $\rm \S \, 2.6$ 查看文件：cat

目录里放着文件，可文件里写了什么？`cat`（PowerShell 对应 `Get-Content`）把文件内容原样打印到终端。先造一个文件出来看：`echo` 的输出不只能上屏幕，还能写进文件——`>` 叫重定向（redirect），把本该到屏幕的输出改道进文件（§2.10 展开讲）：

```bash
echo "line one" > sample.txt
echo "line two" >> sample.txt      # >> 追加，而不是覆盖
```

现在用 `cat` 读它：

```bash
cat sample.txt
line one
line two
```

```powershell
Get-Content sample.txt
```

有一条经验规则要记牢：**`cat` 只适合小文件**。几万行的日志会被它一次性刷满屏幕，直接把你淹没。大文件要用分页工具（如 `less`，第 7 章的工具箱里介绍），这里先知道有这回事。

> **练习**：在 `terminal-lab` 里创建 `input.txt`，写入两行数字（`echo 42 > input.txt`、`echo 7 >> input.txt`），用 `cat` 查看，再 `ls` 确认文件确实存在。成功判据：`cat` 依次打印出 `42` 和 `7` 两行。

## $\rm \S \, 2.7$ Terminal、Shell 与命令：报错时该怪哪一层

你已经亲手敲过 `pwd`、`ls`、`echo`、`cd`、`cat`，也该见过几次报错了。报错很讨厌，但它是线索——问题在于，你常常说不清它在怪谁。

试着把一次报错在脑子里回放一遍。你敲下回车，发生了这些事：窗口程序把你的文字收集起来（终端），交给一个软件去读（Shell），Shell 把命令拆开、找到对应的程序并启动它（命令行程序），程序的输出再原路返回显示给你。这条链上有三个角色，平时被混叫成“终端”，其实分工不同：

- **终端（Terminal）**：承载文字的窗口，比如 Windows Terminal、VS Code 内置终端、macOS 的 Terminal.app。它只负责显示文字、接收按键，别的什么都不懂。
- **Shell**：在终端里读你输入的命令、解析语法、启动程序的软件。Windows 常见的是 PowerShell（和更老的 `cmd.exe`），Linux 常见 Bash，macOS 默认 Zsh。同一个终端窗口里可以换不同的 Shell。
- **命令行程序**：`git`、`python`、`g++`、`curl`，以及你自己编译的程序，都是被 Shell 启动的。Shell 自己也带几个内置命令（如 `cd`）。

链路长这样：

```text
你
 ↓ 键盘输入
终端窗口（显示文字、接收输入）
 ↓ 把文字交给
Shell（解析命令、管道、变量等）
 ↓ 创建进程
git / python / g++ / 你的程序
 ↓ 输出
Shell → 终端窗口 → 你
```

分清楚这三层，最直接的好处是**报错时知道往哪看**：窗口打不开，怪终端配置；敲了回车说语法不对，怪 Shell（或者你）；程序跑起来才崩、输出很奇怪，怪程序自己。网上一条 Bash 命令粘到 PowerShell 报错，也多半是因为它们是不同的 Shell——命令名、变量、引号、管道的规矩都不一样，不能原样互通。

## $\rm \S \, 2.8$ 命令的结构：程序、子命令、选项和参数

你马上会遇到真正的复杂命令，比如 `git log --oneline --max-count 5`。头一次看到多半会懵：这一长串里，到底哪个是程序、哪些是它的话？

拆开看，其实骨架跟你最早敲的 `echo hello` 一样：

```text
git log --oneline --max-count 5
```

```text
git          程序
log          子命令（subcommand，程序的子功能）
--oneline    选项（option，开关，不带值）
--max-count  带值选项
5            上一个选项的值
```

再看一个例子：

```text
python script.py input.txt --limit 20
```

- `python` 是解释器程序；
- `script.py` 是位置参数（positional argument，位置决定含义），告诉解释器运行哪个文件；
- `input.txt` 是脚本自己定义的位置参数；
- `--limit 20` 是脚本定义的选项。

**选项的具体写法由程序自己定**，没有统一标准：常见的有 `-h`、`--help`、`-o output.txt`、`--output=output.txt`。所以遇到陌生命令，第一件事是敲 `tool --help` 看它自己的约定（§2.13 有完整的安全流程）。

参数里如果含空格，必须用引号包起来，否则会被 Shell 拆成好几个参数：

```text
python script.py "D:\My Data\papers.json"    # 一个参数："D:\My Data\papers.json"
```

引号的作用，是告诉 Shell“引号里的这些字符属于同一个参数”。PowerShell 与 Bash 在单引号、双引号、变量展开上的细节不同——“含空格就加引号”这条底线两边通用，更深的引号语义放到[终端进阶](25-终端进阶.md)的 §25.5。

> **练习**：把第 1 章 §1.3.1 的 `show-args` 源码保存为 `show-args.cpp`，编译它（`g++ show-args.cpp -std=c++17 -Wall -Wextra -o show-args.exe`，Bash 下把输出名写成 `show-args`），再分别运行 `.\show-args.exe one two three`（Bash：`./show-args one two three`）和 `.\show-args.exe "one two" three`，对比两次收到的参数个数。预期第一次打印 `argc = 4`（程序名、`one`、`two`、`three`），第二次打印 `argc = 3`（`one two` 被整体当成一个参数）——引号就是这样改变参数分组的。

## $\rm \S \, 2.9$ PATH：为什么输入程序名就能运行

敲 `python` 回车时，Shell 是怎么找到那个程序的？答案是它手头有一张清单，叫 **PATH** 环境变量（environment variable——进程的环境配置，§2.12 正式讲）。PATH 里列着一串目录，Shell 按顺序去每个目录里找，命中第一个名字匹配的可执行文件就运行。

可以把它想成“Shell 找程序时依次翻看的目录清单”。注意两点：它**不**管“项目里有哪些源码”，也不是 Python 专属——任何命令名的查找都走它。

想知道某条命令实际对应哪个文件，别靠猜：

```powershell
Get-Command python
Get-Command git
```

```bash
command -v python
command -v git
```

跟 PATH 纠缠的，多半是这几类问题：

- 软件装了，但它的目录不在 PATH 里——输入名字找不到；
- PATH 里躺着多个同名版本，先被找到的不是你要的那个；
- 改了 PATH，旧终端没生效（要重开终端或重新加载配置，见[终端进阶](25-终端进阶.md)的 §25.4）；
- `python` 和 `pip` 实际来自两个不同的安装。

排查这类问题有个好习惯：**把版本号和可执行文件的完整路径一起记下来**，别只敲 `--version`——因为那两行输出可能来自不同的文件。

### $\rm \S \, 2.9.1$ 为什么运行当前目录的程序要写 `./app`

Bash/Zsh 的 PATH **故意不含当前目录**——想想为什么：如果含，你在陌生目录里敲个 `ls`，万一那里恰好有个同名恶意程序，被执行的就会是它。PowerShell 也一样不搜当前目录，所以运行当前目录的程序必须显式写出路径前缀；`cmd.exe` 相反，它会先搜当前目录，同名文件可能被意外执行：

```text
./app          # Bash/Zsh：“当前目录中的 app”
.\app.exe      # PowerShell：必须写路径前缀（写成 ./app.exe 也能识别）
```

`./` 或 `.\` 不是装饰品，它是在说“从当前目录出发找这个文件”。

> **练习（PATH 排障）**：对 `git`、`python`、`g++` 各记录三样东西：找不找得到、可执行文件的完整路径、版本号。如果某工具有多个版本，把 PATH 的搜索顺序写下来。**不要删任何版本**——先弄清现在跑的是哪个。成功判据：每个工具都能写出一行“命令名 → 完整路径 → 版本号”，写不出完整路径的那个，就是 PATH 里缺了它。

## $\rm \S \, 2.10$ 标准流、重定向与管道

一个程序跟外界说话，默认有三个口子，合称**标准流**（standard streams）：**标准输入**（stdin）默认接键盘，程序从这里读数据；**标准输出**（stdout）默认接屏幕，程序把正常结果写到这里；**标准错误**（stderr）默认也接屏幕，专门用来喊“我出错了”。三条流分开，是为了让你能只保留结果、或者只抓错误。

Shell 能把这些口子重新接线，这叫**重定向（redirection）**：

```text
program > output.txt      # 标准输出写入文件（覆盖已有内容！）
program >> output.txt     # 追加到文件末尾
```

```bash
program < input.txt              # Bash/Zsh：从文件提供标准输入
```

```powershell
Get-Content -Raw input.txt | .\program.exe    # PowerShell：-Raw 整块读入文件，再喂给程序
cmd /c "program.exe < input.txt"              # 或者让 cmd.exe 做文件重定向，字节原样送过去
```

> **版本差异**：`<` 在 PowerShell 里是保留运算符，直接写 `program < input.txt` 会报 `“<”运算符是为将来使用而保留的`。另外 PowerShell 5.1 的 `$OutputEncoding` 默认是 ASCII，通过管道喂给原生程序的中文每个字会变成 `?`（可先设 `$OutputEncoding = [System.Text.Encoding]::UTF8`，但 5.1 下这个写法会带上 UTF-8 BOM），纯数字或英文输入不受影响；PowerShell 7+ 默认已是 UTF-8。还有一点：5.1 的 `>` 写出的文件是 UTF-16 文本，用 `cmd /c` 重定向喂给程序会读到 `34 00 32 00` 这样的字节（程序认不出 `42`），这种文件走 `Get-Content -Raw |` 这条更稳。

**管道（pipe）**是另一种接线：把左边程序的输出口，接到右边程序的输入口，让两个程序像积木一样拼起来干活：

```text
producer | consumer
```

```bash
ls | cat                 # Bash：cat 没给文件名时从标准输入读——把 ls 的输出原样再打一遍
```

```powershell
Get-Content -Raw input.txt | .\sum.exe   # 上面给程序喂输入，靠的也是管道
```

`ls | cat` 没什么实用价值，它只让你看清管道两端是谁；真正省事的筛选、查找和统计要等学过工具再说——按内容找行的 `grep`、查看进程的 `ps` 在第 7 章，进程和 `$_` 在第 11 章，到那时再把管道拼长。

两个平台的管道思想相同，但传输的东西不一样：Bash 管道传的是文本字节流，PowerShell 管道传的是结构化对象（连原生程序时再转回文本）——所以同一段管道写法，两边不能想当然通用。还有一个实用忠告：管道里任何一段都可能失败，复杂的命令先分段跑、确认每段输出正常，再拼起来。

`>` 只重定向标准输出，**抓不住错误**——错误走的是标准错误那条流。想单独保存错误、或把两条流并进同一个文件，用这些写法：

```bash
program 2> error.txt        # 只把错误写进文件（Bash/Zsh）
program > all.txt 2>&1      # 顺序不能反：先让标准输出进 all.txt，再把错误并过来
```

```powershell
.\program.exe 2> error.txt      # 只收错误流
.\program.exe *> all.txt        # PowerShell 专有：所有流（含错误）都进同一个文件
.\program.exe > out.txt 2>&1    # 也可以显式把错误并进标准输出
```

两边 `2>`、`2>&1` 名字相同，含义却有差别：Bash 合并的是文件描述符、顺序敏感，PowerShell 合并的是对象流；`*>` 只有 PowerShell 有。想查更多细节可以试 `Get-Help about_Redirection`，但 Windows 自带的离线帮助常常没有这个主题（会提示先 `Update-Help`），以上面这些写法实测为准。两个 5.1 特有的细节也记一下：`>` 默认写成 UTF-16 文本（7+ 是 UTF-8），原生程序写进 stderr 的内容会被包成错误记录，文件里可能多出 `所在位置`、`CategoryInfo` 之类的行。不管用哪个 Shell，动手前先想清楚：你要的是只存结果、只存错误、还是都要？日志收集和 CI 整天靠这个区别活着。

> **安全规则**：`>` 会**覆盖**已有文件。执行前看清楚目标路径，重要文件要么用 `>>` 追加，要么换个新文件名。

> **练习**：`cd` 回第 1 章的 `lab01`（那里有编译好的加法程序）。先手动输入一次 `42 7` 记住结果，再造一个输入文件（`echo 42 > input.txt`、`echo 7 >> input.txt`），然后从文件喂输入：Bash 用 `./sum < input.txt`，PowerShell 用 `Get-Content -Raw input.txt | .\sum.exe`（5.1 不支持 `<`，直接写会报“保留运算符”的错）。把结果存进 `output.txt`（在命令末尾加 `> output.txt`），再用 `cat` / `Get-Content` 读一遍。成功判据：`output.txt` 里是 `49`。

## $\rm \S \, 2.11$ 退出码：程序怎么告诉你“成了还是砸了”

程序结束时会留给 Shell 一个数，叫**退出码**（exit code）：`0` 表示成功，非 `0` 表示失败——至于非 0 具体是哪种失败，通常要看程序自己的约定。查看上一条程序的退出码：

```powershell
$LASTEXITCODE
```

```bash
echo $?
```

有个容易踩的坑：这个值只代表**最近一条**相关程序的状态，你再跑一条别的命令它就变了，所以要查就趁早。退出码真正的威力在自动化里（第 21 章讲）：脚本靠它做决定——编译成功才跑测试，测试通过才部署。反过来，如果你写了个打印“失败”却返回 0 的工具，它会骗过所有下游脚本。

Shell 的 `&&`（前一条成功才执行后一条）和 `||`（前一条失败才执行后一条）很实用，但兼容情况不一样：Bash/Zsh 一直支持，**Windows 自带的 PowerShell 5.1 不支持 `&&`**——写了会报 `标记“&&”不是此版本中的有效语句分隔符`，要 PowerShell 7 及以上才支持。跨平台时宁可把命令分行写，别赌一行通吃。

> **练习**：跑一次加法程序，正常结束——`$LASTEXITCODE` / `echo $?` 应是 `0`。然后注意：第 1 章的加法程序对非数字输入只是让 `std::cin` 失败，`main` 仍然返回 0，退出码还是 `0`，所以它练不出“失败”。想看到真正的非 0，按 §1.9.6 把 `return 0;` 改成 `return 7;` 重新编译运行，退出码应是 `7`；或者执行 `g++ missing.cpp -o sum2`（编译一个不存在的文件），g++ 的报错走 stderr、退出码是 `1`——一次把“退出码非 0”和“错误走 stderr”两件事都看到。

## $\rm \S \, 2.12$ 环境变量：进程的“出厂设置”

程序怎么知道你叫什么、系统语言是什么、`python` 装在哪？它不可能每件事都自己问一遍——答案是操作系统在**启动进程的那一刻**，塞给它一组键值对，这就是**环境变量**。进程读一次，之后一直带着用；进程自己也能改，但只对自己和它再启动的子进程生效。查看和临时设置：

```powershell
$env:PATH                                    # 查看（PowerShell）
$env:APP_ENV = 'development'                 # 临时设置（PowerShell）
```

```bash
echo "$PATH"                                 # 查看（Bash；加引号避免被再次分词）
export APP_ENV=development                   # 临时设置（Bash）
```

注意“临时”两个字：这种设置只影响**当前 Shell 进程**及其之后启动的子进程，关掉终端就没了，也传不到已经跑着的程序。想让某个设置每次开终端都在，得写进 Shell 的配置文件（[终端进阶](25-终端进阶.md)的 §25.4 专门讲）。

> **安全规则**：别把 API Token、密码、私钥写进会提交到 Git 的脚本。命令历史、日志甚至 `ps` 输出的命令行参数都可能泄露敏感信息（第 13 章讲）。

## $\rm \S \, 2.13$ 如何安全学习陌生命令

面对一个没用过的工具，“复制粘贴试一下”是最危险的反应——你根本不知道那串字会做什么。用一套固定流程代替它：

1. 确认工具来源和用途（谁发布的、解决什么问题）；
2. 查看 `tool --help` 或相应帮助；
3. 查看版本和可执行文件路径（§2.9）；
4. 识别子命令、选项、位置参数和默认行为；
5. 先运行只读命令（如 `ls`、`--help`）；
6. 在专门创建的临时目录做最小实验；
7. 修改、覆盖、删除、上传、安装或提权前，再次确认目标；
8. 保存**完整错误信息**，别只截最后一行。

看到下面这些信号，警惕起来：

- 递归删除或覆盖（`rm -rf` 之类——本教材不会教无上下文使用）；
- 目标路径由没检查过的变量或通配符拼出来；
- 要求管理员/root 权限，却不说为什么；
- 从网上下载脚本，直接扔给 Shell 执行；
- 把密码、Token、私钥放进命令参数；
- 用关防火墙、关证书检查、关系统安全机制来“解决”问题。

## $\rm \S \, 2.14$ 常见误区

这些坑几乎人人踩过，值得提前排雷。

**误区一：“命令没输出，就是没执行。”** 恰恰相反——`cd` 这类命令成功时就是默认沉默的。判断执行结果，看退出码和预期状态（`pwd`、`ls` 的输出），别凭“有没有动静”。

**误区二：“软件装了，输入名字就该能跑。”** 装好只是第一步，Shell 还得通过 PATH 找到它（§2.9）。找不到时先 `Get-Command` / `command -v` 看看实际解析到了什么。

**误区三：“终端就是 Linux。”** Windows 也有自己的终端和 Shell（PowerShell）。终端、操作系统、Shell 是三个层次，别混为一谈（§2.7）。

**误区四：“网上抄来的命令，粘上去就能用。”** 它可能针对不同的 Shell、操作系统、版本、目录或权限——甚至可能是恶意的（§2.13）。

**误区五：“加管理员权限，能治所有权限错误。”** 管理员权限常常只是掩盖了错误配置，还扩大了破坏范围。先搞清楚你要访问什么资源、正确的所有者是谁。

**误区六：“Ctrl+C 会撤销刚才的操作。”** 它只是请求中断当前前台程序。已经写进文件的数据、已经发出的请求，不会因为 Ctrl+C 自动回滚。

### $\rm \S \, 2.17.1$ 自测答案 · 关键概念回顾

### $\rm \S \, 2.17.2$ 自测答案 · 应用与辨析
6. 终端是承载文字输入输出的窗口；Shell 是读取、解析命令并启动程序的软件；命令行程序是被 Shell 启动的程序。
