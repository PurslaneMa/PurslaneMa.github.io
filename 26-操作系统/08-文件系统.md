# $\rm Chapter \, 8$ 文件系统：inode、目录与崩溃一致性

计算机速通册 §3 你学会了「文件是字节流、路径是从根出发的寻址」。本章拆开这层抽象看里面：磁盘上的数据块怎么被记账、「删掉文件」到底删了什么、以及为什么断电之后文件系统需要一本日志。上一章的死锁是「执行流互等」的病；这一章的病不一样，是机器自己把自己的账本撕了一半。

## $\rm \S \, 8.1$ 两个账本：inode 表与块位图

把一个分区格式化成文件系统（ext4、NTFS 都一样），磁盘被划成三块地盘：

1. **超级块（superblock）**：文件系统自己的说明书（块总数、inode 总数、每块多大）。`df -i` 读的就是这份账（§8.6 实测）；
2. **inode 表**：一排定长记录，每条描述一个文件。inode（index node）是「文件」在磁盘上的真身；
3. **数据块区**：文件内容真正存放的地方；旁边配一张**块位图**（bitmap），每位标记一个数据块空闲与否。

注意一个反直觉的事实：inode 里**没有文件名**。名字根本不属于文件，属于目录，这是 §8.2 硬链接存在的全部原因。

## $\rm \S \, 8.2$ inode 存什么：元数据与数据块指针

一条 inode 记录存：文件大小、权限与时间戳、指向数据块的指针（ext4 用「直接指针 + 间接指针 + 半间接」三级，大文件走更深的间接层；现代系统还常以区段 extent 连续分配替代逐块指针）。最重要的字段是**链接数**：有多少个名字指着这条 inode。

「删文件」删的其实是名字。两个名字指同一个 inode 时，删一个名字只是把链接数减一：

```python
import os
p1 = 'fsdemo/report.txt'
open(p1, 'w').write('hello inode')
print('创建后  ', os.stat(p1).st_nlink)
os.link(p1, 'fsdemo/hard.txt')            # 硬链接：目录里加一条名字→同 inode
print('硬链接后', os.stat(p1).st_nlink)
os.remove(p1)                             # 删原名字
print('删原名后', os.stat('fsdemo/hard.txt').st_nlink, open('fsdemo/hard.txt').read())
```

本机（Windows / NTFS，Python 3.12.10）输出：

```text
创建后  1
硬链接后 2
删原名后 1 hello inode
```

链接数 1→2→1，删掉 `report.txt` 这个名字后文件内容完好，数据块只在**链接数归零**时才真正回收。在 ext4 上用 `stat` 看得更直白（WSL2、内核 6.6.87 采集）：

```text
$ ln real.txt hard.txt        # 建硬链接
$ stat -c "%n inode=%i nlink=%h" real.txt hard.txt
real.txt inode=14230 nlink=2
hard.txt inode=14230 nlink=2   # 同一个 inode，链接数同涨
```

**软链接（symbolic link）**是另一种东西：它是一个独立的小文件（自己的 inode），内容存的是目标路径字符串。于是它指向的名字被删掉后，它自己还在、但已悬空：

```text
$ ln -s real.txt soft.txt
$ stat -c "%n inode=%i nlink=%h" soft.txt
soft.txt inode=14231 nlink=1    # 独立 inode，nlink 不随目标变
$ rm real.txt && cat soft.txt
cat: soft.txt: No such file or directory   # 悬空：解引用失败
```

对照表：

| | 硬链接 | 软链接 |
| --- | --- | --- |
| 是什么 | 目录里多一条「名字 → 同一 inode」的记录 | 独立文件，内容是目标路径 |
| inode | 与原文件相同 | 自己独有一个 |
| 目标被删 | 内容仍在（链接数减一） | 悬空，访问报错 |
| 能否跨文件系统 / 指目录 | 不能（inode 号是分区内的） | 能（路径是全局的） |

Windows 上 `os.symlink` 建软链接需要开发者模式或管理员权限（实测报 `WinError 1314`），`ln -s` 在 Linux 随手可用。平台差异如实标注。

## $\rm \S \, 8.3$ 目录：一张名字到 inode 号的表

目录本身也是文件，它的「内容」是一张 `(名字, inode 号)` 的表。`ls -li` 把这两列直接亮出来（WSL2 采集）：

```text
$ ls -li
14230 -rw-r--r-- 2 purslane purslane 6 hard.txt
14231 lrwxrwxrwx 1 purslane purslane 8 soft.txt -> real.txt
```

「目录 = 特殊文件」解释了一批日常现象：目录的大小通常很小（就是一张表）；「目录不可硬链接」是文件系统刻意禁止：允许多个父目录指向同一目录，路径解析会成环，`..` 不知指谁；「删除非空目录被拒」是因为要先保证表清空、名字不留悬空引用。

## $\rm \S \, 8.4$ 路径解析：逐级查目录

打开 `/home/alice/report.txt` 的完整旅程：

1. 从根目录的 inode（固定编号，ext4 里可查）读出根目录的数据块，得到根目录那张名字表；
2. 在表里找名字 `home`，得到它的 inode 号；读该 inode，找到 home 目录的数据块；
3. 在 home 的表里找 `alice`……如此往复，每降一层付一次「读 inode + 读目录块」；
4. 最后在 alice 的表里找到 `report.txt` 的 inode 号，按指针取数据块。

所以**路径再深，解析的每一步都只是「查一层表」**，绝对路径没有任何捷径可抄，这正是 shell 提示符旁的 `..`、`.` 只是解析约定，以及符号链接造成路径解析循环（对应文件系统的防护逻辑）的来源。计算机速通 §3 的「PATH 地址簿」是 shell 找可执行文件的另一套查找，别与内核的路径解析混为一谈。

## $\rm \S \, 8.5$ 崩溃一致性：删文件的三步与中间断电

「删一个名字」在底层至少要改**两本账**：目录表里抹掉这条记录、inode 链接数减一（若归零还要改块位图、回收 inode）。三步操作、两本账，任意一步之后断电，账本就撕了一半：

1. 抹完目录、未减链接数：inode 还活着但没有任何名字指向它，**空间泄漏**（占着块，永远找不回）；
2. 减完链接数、未抹目录：名字指向一个已回收的 inode，**悬空引用**（读到的可能是别人复用后的数据，严重时错乱）。

朴素的「换顺序」救不了：无论先改哪本，断电窗口都存在。这个困局你应当觉得眼熟：数据库分册 §6 的转账（改两个账户，中间崩溃）一模一样，答案也是同一个：**先写日志再动账**（Write-Ahead Logging，WAL）。

## $\rm \S \, 8.6$ journaling：把「断电恢复」变成「回放日志」

日志文件系统（ext4、NTFS）的做法：

1. **写日志**：把「我要做的三步」作为一个事务记录，先落盘到日志区；
2. **做改动**：按日志逐项改目录表与 inode；
3. **提交**：全做完成后，在日志里标记该事务完成。

断电重启后扫一遍日志：未提交的事务整体**丢弃**（undo 语义），已提交但未做完的**重做**（redo 语义）。两本账要么都没动、要么全部做完。至于文件**内容**本身要不要也进日志，ext4 给了三档：

1. `journal`：数据＋元数据全日志，最安全，写放大最重；
2. `ordered`（默认）：只日志元数据，但保证数据先于元数据落盘，防悬空引用读旧数据；
3. `writeback`：只日志元数据、不保证顺序，最快，崩溃后可能读到新元数据 + 旧内容。

inode 这本账有多大？`df -i` 直接回答（WSL2 采集）：

```text
$ df -i /tmp | tail -1
/dev/sdd  67108864 111677 66997187  1% /    # 共 6710 万个 inode，用了 11 万
```

inode 在格式化时就按容量预分配（本机约每 16 KB 数据一个）。「块用完了但 inode 先用完」在小文件海场景真实存在，那时 `df` 显示有空间、`touch` 却报 `No space left on device`，查 `df -i` 便知。

## $\rm \S \, 8.8$ 应用与辨析

1. 磁盘还有 200 GB 空间，`touch new.txt` 却报 `No space left on device`。给出定位步骤与根治选项。
2. 备份脚本用 `cp -a` 复制了大量硬链接文件，备份目录的大小远大于源目录。解释原因（提示：`cp` 默认把每个名字复制成独立文件）。
3. 有人主张「日志文件系统写两遍（日志 + 原地），性能一定减半」。用「元数据 vs 数据的体量差」反驳或修正这句话。

## $\rm \S \, 8.9$ 本章自测答案

### $\rm \S \, 8.9.1$ 关键概念回顾答案

1. 存：大小、权限、时间戳、链接数、数据块指针（或区段）。不存文件名，名字是目录表 `(名字, inode 号)` 里的一行，属于目录。（§8.1、§8.3）
2. 硬链接是目录里多一条指向**同一 inode** 的名字，目标名字删掉内容仍在；软链接是**独立 inode** 的小文件、内容是目标路径，目标删掉即悬空、访问报错。一个跟真身共存亡，一个只是写着地址的纸条。（§8.2）
3. 因为每一层的答案都在下一层目录的数据块里：拿到 `home` 的 inode 号才能找到 home 的表。输入是「当前目录 inode」，输出是「下一级名字的 inode 号」，逐级迭代直到文件名。（§8.4）
4. 目录表抹记录、inode 链接数减一（归零再回收块与 inode）。先抹后减断电＝空间泄漏；先减后抹断电＝悬空引用。（§8.5）
5. `ordered` 保证文件数据先于指向它的元数据落盘，崩溃后要么看不到新文件、看到的就是完整新内容；`writeback` 无此保证，可能新 inode 配旧数据。（§8.6）

### $\rm \S \, 8.9.2$ 应用与辨析答案

1. `df` 看块、`df -i` 看 inode：若 inode 用满（IUse% 100%）即中招。小文件海是典型成因。根治选项：清理海量小文件（构建产物、会话文件）；或备份后用更大 `bytes-per-inode` 比例重新格式化；xfs 这类动态分配 inode 的文件系统没有此上限。（§8.6）
2. 源目录里 N 个名字共享同一份数据块；`cp -a` 若不感知硬链接（或多路径未在同一命令里），每个名字各复制一份独立数据，占用与文件数成正比。`rsync -H` 或 `cp -a --preserve=links`（同批复制）可保留链接关系。（§8.2）
3. 「写两遍」只对进日志的部分成立。`ordered`（默认）只把**元数据**写日志，体量上目录项与 inode 是字节级、数据块是 KB~MB 级，多写的常数量小；数据本身仍一遍落盘。性能损失存在（fsync 次数与顺序约束），但不是「所有字节都翻倍」。（§8.6）
