# $\rm Chapter \, 12$ 信号与终端：作业控制的真实机制

你在终端按过 Ctrl+C 杀掉卡住的程序，用过 `kill` 结束进程，也许还见过 `kill -9` 的传说（「-9 最狠，杀不死说明程序有鬼」）。这些动作背后是同一套机制：信号（signal）。它是最古老的进程间通信，也是最不可靠的：不排队、会合并、大部分能被忽略。本章讲清它到底怎么运作，以及终端为什么和它绑在一起。

> **开始前自检**：本章假设你已经会：
>
> 1. □ 知道进程与 PID，`kill` 是给进程发东西而不是「杀」的同义词（计算机速通 §11.3）；
> 2. □ 见过 Ctrl+C、Ctrl+Z 与 `jobs`、`fg`（计算机速通 §11.4）；
> 3. □ 知道进程有前台后台之分，终端是它们的控制端（计算机速通 §11.4）；
> 4. □ 中断处理不能睡眠的机制原因（本册 §11.4）。

## $\rm \S \, 12.1$ 信号是什么：一张编号表和三个处置动作

信号是一个发往进程的编号，取值 1 到 64。收到信号的进程要么执行默认动作（多数是终止，有的会 core dump），要么忽略，要么执行自己注册的处理函数（handler）。三者叫处置（disposition）。

常用的信号一只手数得过来：

1. `SIGINT`（2）：Ctrl+C 发的就是它，默认终止。本意是「中断」。
2. `SIGTERM`（15）：`kill` 默认发它，默认终止。本意是「请你退出」，可以被拦截，给进程清理的机会。
3. `SIGKILL`（9）：默认动作是终止，且**不可拦截、不可忽略**。内核直接把进程摘除，不给任何代码运行的机会。
4. `SIGSEGV`（11）：非法访存（本册 §4.5 的段错误就是它），默认终止加 core dump。
5. `SIGCHLD`（17）：子进程终止时发给父进程，默认忽略。本册 §2.5 的「收尸」靠它提醒。
6. `SIGSTOP` / `SIGCONT`（19/18）：暂停与继续，Ctrl+Z 发的就是 SIGSTOP 一族。

SIGKILL 为什么拦不住？处理函数是进程自己的代码，若允许拦截 SIGKILL，一个死锁进程注册了「忽略 SIGKILL」的 handler 就永远杀不死了。内核保证这条退路：信号检查发生在进程从内核态返回用户态的时刻（本册 §11.2 的中断返回路径顺路办了这件事），而 SIGKILL 在检查点直接走终止逻辑，根本不看进程注册了什么。

实测验证「SIGTERM 可拦、SIGKILL 不可拦」。一个装了 SIGTERM 处理函数的进程：

```text
$ kill -TERM <pid>   → 打印 "caught TERM, ignoring"，进程活着
$ kill -9 <pid>      → 进程立即消失，wait 返回码 137（= 128 + 9）
```

返回码 137 是 shell 的记法：低 7 位是致死信号编号。看到 137 就知道是 SIGKILL 干的，这个编码习惯在你排查 CI 里的离奇退出时会反复用到。

**本节小结**：信号就是一张编号表加三个处置动作（默认、忽略、自定义 handler）；常用的几个记住分工即可——TERM 是可商量的一次请求，KILL 是内核直接执行的死刑，CHLD 是收尸的提醒；「KILL 为什么拦不住」的答案藏在信号检查的发生位置：内核态返回用户态的检查点。

## $\rm \S \, 12.2$ 信号不排队：最容易踩的坑

信号不是消息队列。每种信号在进程上只有一个「待处理」位（pending bit）：已经待处理的信号再来一个，会与上一个合并，只记一次。这叫不排队（non-queued）。

实测给出最直接的证据。向同一个进程连发两次 SIGTERM、一次 SIGINT，处理函数只是计数：

```text
发送：kill -TERM ×2，kill -INT ×1
结果：SIGTERM caught: 1    SIGINT caught: 1
```

两次 TERM 只被 handler 看到一次。原因：第一次 TERM 把 pending 位置 1，第二次到达时位已是 1，无事发生；handler 执行完后位清零，但信号早已错过。这不是 bug，是设计：信号被当成「事件发生」的通知而不是「发生了几次」的记录，实现简单且不需要无限深的队列。

工程后果写进习惯：依赖信号计数是错的；handler 里该做的事要么幂等，要么由信号唤醒后去读真正的状态（管道、标志文件）。

handler 本身还有一条并发纪律：它在主流程的任意两条指令之间插进来执行，相当于一个「单线程内的软中断」（对照本册 §11.4 的中断上下文）。所以 handler 里只调用异步信号安全函数，最稳的做法是只置一个 `volatile sig_atomic_t` 标志，真工作交回主循环。在 handler 里调 `printf` 或 `malloc` 是经典事故源：万一主流程正在 `malloc` 中途被打断，堆锁就死在自己手里。

**本节小结**：信号按「每种一个 pending 位」实现，不排队、会合并，所以次数不可依赖；handler 是插在任意指令间的软中断，只置标志不干重活。两条合起来就是信号编程的全部纪律：把它当「事件发生了」的通知，别当「发生了几次」的记录。

## $\rm \S \, 12.3$ 终端与进程组：Ctrl+C 怎么找到该杀的进程

Ctrl+C 杀的不是一个进程，是一组进程。你在一个交互终端里跑 `python3 server.py`，再开个管道 `| tee log`，按 Ctrl+C，两者一起死。机制分三层：

1. **会话（session）**：登录时建立，一个终端对应一个会话，领头的是 shell。
2. **进程组（process group）**：会话里每个作业（一行命令起的那些进程）是一个组，组内有组长（组 ID 等于组长 PID）。管道连起来的命令同组。
3. **控制终端**：会话绑定的 TTY 设备。终端驱动收到 Ctrl+C 时，把 SIGINT 发给前台进程组的**每一个成员**，这就是「一条命令全家死」的出处。

同一会话里有前台组与后台组。`sleep 100 &` 把作业放进后台组；后台组读终端输入会被内核拦下（收到 SIGTTIN 而暂停），防止两个进程抢键盘。`fg`/`bg` 做的事就是把某个后台组切到前台或反之，本质是内核改变「哪个组是前台」的记录。

实测确认进程组的归属（在交互 shell 里）：

```text
$ echo $$
PID 外壳：1234                 ← shell 自己
$ sleep 100 &
$ ps -o pid,pgid,comm -e | grep sleep
PID   PGID  COMMAND
1300  1300  sleep          ← 新作业新组，组长即自己
```

`kill -pid`（负数参数）可以直接给整组发信号，这个技巧在批量停服务时省事，但也容易误伤：组里若有不相关进程，一起遭殃。

**本节小结**：Ctrl+C 的送达范围由三层结构决定——会话管终端、进程组管作业、控制终端把 SIGINT 打给前台组的每个成员；`fg`/`bg` 切换的就是「谁是前台组」这条记录，后台组抢键盘被 SIGTTIN 拦下。下一节问的问题是：怎么让进程干脆不进任何会话。

## $\rm \S \, 12.4$ setsid 与守护进程：脱离终端的艺术

服务程序不挂在任何终端上跑（关掉 SSH 还活着），做法是把进程从会话里解放出来：调用 `setsid()` 创建新会话，从此不再有控制终端，Ctrl+C 与终端断开信号（SIGHUP）都够不着它。这就是守护进程（daemon）。

传统 daemon 启动流程的每一步都有对应的问题：

1. fork 后父进程退出（脱离 shell，回提示符）；
2. `setsid()` 新会话（摆脱控制终端）；
3. 再次 fork（组长不再持有终端重新关联的资格）；
4. 重定向标准流到 `/dev/null`（终端的 0/1/2 已无意义，留着会写出错）；
5. `chdir("/")`（不占住挂载点，文件系统才能卸载）。

现代系统里 systemd 代劳了大部分：服务配置里写 `Type=simple`，systemd 自己就是 1 号会话的首领，你的进程一出生就在新会话里，前四步都不用写。但 `nohup cmd &` 这类手动 daemon 化在临时任务里仍然常见，其核心就是「换会话＋挡掉 SIGHUP」两件事。

**本节小结**：daemon 化的五步每步堵一个终端遗留的漏洞（shell 控制、SIGHUP、终端重关联、失效的标准流、占住的挂载点），核心目标只有一个：把进程从会话里解放出来，让终端的生死与它无关。

## $\rm \S \, 12.7$ 本章自测答案

### $\rm \S \, 12.7.1$ 关键概念回顾答案

1. SIGTERM 是「请求退出」，进程可拦截以做清理；SIGKILL 由内核直接终止，处理函数完全不经手，因此不可拦截。137 = 128 + 9，shell 用「128 加信号编号」表示死于信号。（§12.1）
2. 每种信号只有一个 pending 位，待处理期间再来会被合并。两次只触发一次 handler；若两次间隔大于 handler 的执行时间，则可能各触发一次。依赖次数的程序都建立在错误假设上。（§12.2）
3. 由终端驱动决定：发给前台进程组的全体成员。前台组的归属由会话记录，`fg`/`bg` 改的就是它。（§12.3）
4. handler 可插在主流程任意指令间。若主流程正在 malloc 内部（持堆锁）被打断，handler 再调 malloc 就死锁；printf 的缓冲区锁同理。安全做法是只写 `volatile sig_atomic_t` 标志。（§12.2）
5. fork 退出父进程：脱离 shell；setsid：脱离控制终端；再 fork：确保永远拿不回终端；重定向标准流：原终端 fd 已失效；chdir 根：不锁挂载点。（§12.4）

### $\rm \S \, 12.7.2$ 应用与辨析答案

1. SIGKILL（9）与 SIGSTOP（19）都不可拦截，这是内核保底。此外可以动它的资源：关闭它的文件描述符、用 cgroup 限内存促其 OOM，或干脆等它下次调系统调用（多数拦截方案只在系统调用边界生效）。（§12.1）
2. `read` 会被信号打断：handler 返回后 read 返回 −1 且 errno 为 EINTR，主循环检查标志后正常退出。把 EINTR 当出错处理是经典 bug，正确姿势是重试前先看标志。（§12.2）
3. 会。终端是字节流设备，内核不按行交错整理，两个进程的输出按写入先后拼在一起（这正是日志加进程名前缀的原因）。键盘输入有保护：后台组读终端收到 SIGTTIN 被暂停。（§12.3）
4. nohup 忽略 SIGHUP 并把输出重定向到 nohup.out。任务存活的前提是不再依赖控制终端：终端关闭时内核向会话前台组发 SIGHUP，后台组若也绑定终端同样会被牵连，所以 setsid 或 nohup 二者至少居一。（§12.4）
