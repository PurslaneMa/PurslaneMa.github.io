> - □ 理解前台进程、后台进程与退出码（退出码见第 2 章 §2.11；前台/后台与守护进程见第 11 章 §11.5.3）

## $\rm \S \, 25.1$ WSL：在 Windows 里演练 Linux

从[第 9 章](../02-终端与工具/09-软件运行时SDK与包管理器.md)的 apt、[第 14 章](../03-计算机系统/14-SSH远程开发与服务器生存指南.md)的服务器操作到 Docker——它们默认都是 Linux 环境。**WSL**（Windows Subsystem for Linux）让你在 Windows 上直接跑 Linux：`wsl --install` 默认装的是 WSL 2，真正的 Linux 内核运行在一个轻量级虚拟机里，与 Windows 的文件系统和网络互通（WSL 1 那种逐系统调用翻译的实现已不再是默认）。

```powershell
# PowerShell（管理员；需要 Windows 10 2004+ 或 Windows 11），一行安装，重启后得到 Ubuntu
wsl --install
```

```bash
# 以下两条在 WSL 终端里执行（Windows 原生的 PowerShell 里没有 /mnt/c，也没有 uname）
uname -a       # Linux ... —— 真正的 Linux 内核
ls /mnt/c/     # Windows C 盘在这里
```

| 场景 | 没有 WSL | 有 WSL |
|------|---------|--------|
| Bash 脚本 | Git Bash 行为不完全一致 | 原生，和服务器一样 |
| Python 环境 | `\` 路径、CRLF、某些包不兼容 | Linux 原生，与服务器一致 |
| Docker | Windows 路径/权限问题 | WSL 内 Docker，和部署环境一致 |

VS Code 装 WSL 扩展后，`code .` 在 WSL 里打开——GUI 在 Windows 渲染，文件系统、终端、编译全在 Linux 侧。项目文件放 `~/projects`（WSL 内部），不要跨文件系统从 `/mnt/c/` 编译（跨文件系统 I/O 明显更慢，文件监听也不可靠）。

## $\rm \S \, 25.3$ 作业控制：fg、bg 与 nohup

`Ctrl+Z` 挂起程序后：

```bash
python train.py        # 正在前台运行
# 按 Ctrl+Z
# [1]+  Stopped    python train.py

jobs                   # 预期：[1]+  Stopped  python train.py
bg                     # 让作业 1 在后台继续跑，终端随即可以输入新命令
nvidia-smi             # 检查 GPU（作业 1 仍在后台跑）
fg %1                  # 把作业 1 拉回前台；再按 Ctrl+Z 可重新挂起
```

`jobs`/`fg`/`bg` 只管当前这个 Shell 会话里的作业——换一个终端窗口就看不到了。后台程序也绑定在当前终端——关终端就死。**nohup** 让它忽略 SIGHUP（终端关闭信号）：

```bash
nohup python train.py > train.log 2>&1 &
echo $!          # 预期：打印后台进程 PID，记下来，结束时用 kill <PID> 停掉
```

什么时候用 nohup vs tmux（详见[第 14 章](../03-计算机系统/14-SSH远程开发与服务器生存指南.md)）：

| 场景 | 工具 |
|------|------|
| 一次性的后台任务 | `nohup ... &` |
| 需要偶尔看看输出、手动操作 | tmux |
| SSH 可能断 | tmux |

## $\rm \S \, 25.4$ 配置持久化：`.bashrc` 与 dotfiles

Shell 启动时读初始化脚本：

| Shell | 交互式 Shell 读 |
|-------|----------------|
| Bash | `~/.bashrc` |
| Zsh | `~/.zshrc` |
| PowerShell | `$PROFILE` |

```bash
nano ~/.bashrc         # 编辑
source ~/.bashrc       # 立即生效
```

**alias**——给长命令起短名：

```bash
alias g='git'
alias gc='git commit -m'
alias ll='ls -lah'
alias ..='cd ..'
alias activate='source venv/bin/activate'
```

**什么放 .bashrc，什么不放**：

```bash
# ✅ 放 .bashrc——每次都要的配置
export PATH="$HOME/bin:$PATH"
alias g=git

# ❌ 不放 .bashrc——项目配置
# 应该放 .env 文件（项目目录下，并把 .env 写进 .gitignore）
export DATABASE_URL=<你的数据库连接串>
export API_KEY=<你的密钥>        # 真实值只放在 .env 或密钥管理服务里，不进 Git、不进命令行历史
```

**dotfiles**：把 `~/.bashrc`、`~/.gitconfig`、`~/.ssh/config` 放进 Git 仓库，换电脑时一键恢复。只放配置——`~/.ssh/id_*` 私钥永远不要进仓库。

## $\rm \S \, 25.5$ Shell 深度

本节命令都是 Bash/Zsh 语法（在 WSL 或 Linux 里执行）；PowerShell 的对应写法见 §25.6 的对照表。`nano`、`shellcheck` 这类工具 Windows 原生环境里没有，用 WSL 或第 9 章 §9.3.1 的系统包管理器安装。本节大部分内容在 Git Bash 里也能跑（heredoc、`$()`、`[ -t ]`、`mktemp` 都是 Bash 自带的能力）；少数只属于 Linux 的写法会在原处标注。

### $\rm \S \, 25.5.1$ 引号

```bash
echo $VAR          # 无引号——空格分割，通配符展开
echo "$VAR"        # 双引号——变量展开，空格和通配符保护
echo '$VAR'        # 单引号——一切字面
```

### $\rm \S \, 25.5.2$ 子 Shell

```bash
pwd                  # /home/alice
(cd /tmp && pwd)     # /tmp——只在子 Shell 内生效
pwd                  # 还是 /home/alice
```

### $\rm \S \, 25.5.3$ `set -euo pipefail` 与 trap

```bash
#!/bin/bash
set -euo pipefail   # 任何命令失败→退出；未定义变量→报错；管道失败→整体失败

tempfile=$(mktemp)
trap "rm -f $tempfile" EXIT   # 无论怎么退出都清理临时文件
```

陷阱一：`set -e` 不捕捉管道中间命令失败（除非加 `pipefail`）。  
陷阱二：`set -e` 在 `if`/`while`/`||`/`&&` 条件位置不生效。  
陷阱三：`set -u` 下 `${VAR:-default}` 不报错（`:-` 是默认值语法）；反过来，赋值命令会掩盖命令替换的失败——`local x=$(false)` 的返回状态来自 `local`（成功），不会触发 `-e`。

### $\rm \S \, 25.5.4$ tee

```bash
python train.py 2>&1 | tee train.log       # 输出到文件 + 屏幕
python train.py 2>&1 | tee -a train.log    # -a: 追加
```

### $\rm \S \, 25.5.5$ shellcheck

```bash
shellcheck script.sh   # 检查：未加引号的变量、cd 没检查返回值、未使用变量
```

### $\rm \S \, 25.5.6$ heredoc 与 here-string：把多行内容交给命令

前面几条重定向（`>`、`>>`、`<`）处理的是**文件**。但有时内容还没成为文件——它就是脚本里的一段文本，你想把它交给某个命令的标准输入。最典型的场景是生成一个配置文件：

写 `>` 加多行 `echo` 能做，但要处理每行的引号和转义，很快变得难读。Bash 提供了 **heredoc**（Here Document，此处文档）：在命令后面写上 `<<` 和一个任意的结束标记，之后的内容一直读到单独出现这个标记为止，整段作为该命令的标准输入。

```bash
# 前置：Bash（Git Bash 也有）；当前目录是你自己建的练习目录
NAME=alice
cat <<EOF
hello $NAME
今天日期各版本不同，这里只演示变量展开
EOF
# 预期输出两行：第一行是 hello alice——$NAME 被展开了
```

关键在于结束标记是否加引号：

```bash
cat <<'EOF'
hello $NAME
$(echo 子命令也会原样保留)
EOF
# 预期输出：两行原文，$NAME 不被展开、$(...) 不被执行
```

加引号（`'EOF'` 或 `"EOF"`，效果相同）会让整段内容**完全字面化**：变量不展开、命令替换不执行、反斜杠不特殊。这个区别在写配置时非常重要——你要生成的 `docker-compose.yml`、`.env`、`nginx.conf` 里往往含有 `$`（如 `${VAR}`），用不加引号的 heredoc 会被 Shell 抢先替换掉。

```bash
# 生成一个含变量引用的配置文件：用引号阻止 Shell 展开
cat > compose-snippet.yml <<'EOF'
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}    # 由 Compose 在运行时读取，不是 Shell
EOF
# 成功判据：cat compose-snippet.yml 里看到的是 ${DB_PASSWORD} 原文
```

第三种形式是 `<<-EOF`：它让 Shell 忽略每行**前导的制表符（Tab）**，这样你可以把 heredoc 缩进在代码块里而不破坏输出。注意它只去 Tab，不去空格——用空格缩进时 `<<-` 不会有任何效果，这是最常踩的一个坑。

```bash
# 前置：脚本里书写时用 Tab 缩进（多数编辑器按 Tab 键；不要用空格）
if true; then
	cat <<-EOF
	这一行前面的 Tab 会被去掉
	EOF
fi
# 预期输出：一行“这一行前面的 Tab 会被去掉”，前面没有缩进
```

**here-string**（`<<<`）是同一族里最简单的形式：把**一个字符串**直接当作标准输入，不用另起一段：

```bash
cat <<< "one line to stdin"
# 预期输出：one line to stdin（末尾会补一个换行）
```

它适合“某个命令需要一个文件/stdin，而我手上只有一个变量”的场合：

```bash
wc -c <<< "abc"          # 预期输出 4——三个字符加一个换行
python -c "import sys; print(len(sys.stdin.read()))" <<< "hello"   # 预期输出 6
```

heredoc 的一个实用变体是直接执行——把多行脚本喂给解释器，不落盘：

```bash
python - <<'PY'
data = {"papers": 3}
print(f"读到 {data['papers']} 篇")
PY
# 用 'PY' 引起来，避免脚本里的 $ 或反斜杠被外层 Shell 处理
```

这条写法你在读别人的部署文档时会经常看到（它比 `python -c "..."` 更适合多行代码，因为不必处理整段内容的引号嵌套）。什么时候**不该**用 heredoc：内容需要被反复编辑、或者脚本要给别人看时——写成独立文件更清楚。

### $\rm \S \, 25.5.7$ 命令替换：`$()` 与反引号

Shell 还能把一个命令的**输出**当作另一个命令的**参数**，这叫**命令替换**（command substitution）：

```bash
echo "当前目录是 $(pwd)"
echo "python 在 $(command -v python)"
FILES=$(ls *.txt)          # 把输出存进变量（赋值时不要加引号）
echo "$FILES"              # 读取时加引号，防止空格被拆开
```

`$(...)` 能嵌套，因为括号有明确的配对：

```bash
echo "$(echo $(echo 嵌套三层也没问题))"    # 预期输出：嵌套三层也没问题
```

反引号是更老的写法，效果相同但**不能嵌套、引号处理也更容易出错**：

```bash
echo "`pwd`"               # 老写法，能工作，但新代码不要用
```

写 `$(...)` 而不是反引号是运维与 CI 脚本的通行选择：嵌套时不必转义、可读性更好、在大多数编辑器里高亮正确。有一点要留心：命令替换会**去掉输出末尾的所有换行**，而且默认按空白分词——所以“一个命令输出多个文件名”时不要指望 `$(...)` 保持文件名完整（§25.8 会给出原因和替代）。命令替换的失败还可能被赋值语句掩盖（`local x=$(false)` 的返回码来自 `local`，不会触发 `set -e`，§25.5.3 的陷阱三），这是排查“脚本为什么没停下”时常被漏掉的一处。

### $\rm \S \, 25.5.8$ 让脚本可重跑：幂等性

自动化脚本有一个不同于“一次性命令”的评价标准：**重复执行它，结果是否与执行一次相同**。满足这个性质的操作用一个词概括——**幂等**（idempotent）。这不是术语游戏：cron 定时任务可能因为上次没跑完而被触发两次、部署脚本可能被中断后重跑、CI 可能因为网络抖动重试整条流水线。如果脚本不幂等，这些情况会各自变成一次事故。

先看两个最常见的反例：

```bash
# 反例 1：重复追加——每跑一次，文件多一份内容
echo "export PATH=$HOME/bin:$PATH" >> ~/.bashrc
# 跑两次就有两行，跑一百次 PATH 里有一百份同一目录

# 反例 2：重复插入——每跑一次，数据库多一行
# INSERT INTO papers (doi, title) VALUES ('10.1/x', 'Attention');
# 重跑一次就多一条重复记录
```

修法分别是“就地覆盖/先去重”与“先查再插”，都不是复杂技巧，而是**把“当前是什么状态”这一步显式写进脚本**：

```bash
# 修法 1a：整段重写而不是追加（内容确定时最省事）
cat > config.conf <<'EOF'
data=papers.txt
year_min=2017
EOF
# 跑一百次结果都一样——这就是幂等

# 修法 1b：必须追加时先检查是否已有（先查再改）
line='export PATH=$HOME/bin:$PATH'
grep -Fqx "$line" ~/.bashrc || echo "$line" >> ~/.bashrc
# -F 按字面匹配（不把内容当正则）、-x 要求整行相同、-q 不打印
```

Shell 里几个天然幂等的工具，写脚本时优先用它们：

| 操作 | 不幂等的写法 | 幂等写法 | 区别 |
|---|---|---|---|
| 建目录 | `mkdir dir` | `mkdir -p dir` | 目录已存在时报错 vs 直接成功 |
| 建符号链接 | `ln -s a b` | `ln -sf a b` | 已存在时报错 vs 覆盖旧链接（`-f`） |
| 下载文件 | 每次都下 | 先查校验和/时间戳再决定 | 省时间，也避免半途中断留下坏文件 |
| 写配置 | `>>` 追加 | `>` 整体重写，或先 `grep` 查 | 见上 |
| 创建用户 | `useradd` | `useradd` 前先 `id` 检查 | 重复执行不报错 |

```bash
# 前置：Bash；在你自己的练习目录里验证“跑两次结果相同”
mkdir -p idem-lab && cd idem-lab
mkdir -p out && mkdir -p out        # 第二次不报错，退出码都是 0
touch target.txt                    # 链接的目标要先存在，否则 ln 会失败
ln -sf target.txt out/link          # -f：已有同名链接时直接替换，所以第二次也不报错
ls -l out/                          # 预期：只有一个 link -> target.txt
```

> **平台说明**：`ln -s` 在 Windows 上创建真正的符号链接需要开发者模式或管理员权限（[文件系统、路径与权限](03-文件系统路径与权限.md) §3.6.2）；Git Bash 里没有权限时会报 `Operation not permitted`。这一条在 Linux/macOS/WSL 上验证。Windows 上要检查“再次运行是否报错”，用 `mkdir -p` 就够了。

**`set -e` 与幂等性配合**：`set -e` 让脚本“一失败就停”，而幂等写法让“重复执行”不再失败——两者合起来才是可靠的自动化。反过来说，如果脚本里到处是不幂等的命令，`set -e` 反而会让你在重跑时立刻撞上“目录已存在”这类无关紧要的报错而中断，于是有人干脆去掉 `set -e`，把真正的错误也一起放过了。**先让操作幂等，再让脚本遇错即停**，顺序不能倒。

> **经验规则**：写自动化脚本时养成一个习惯——写完先跑两遍。第一遍通过只说明它能工作，第二遍通过才说明它可以被重跑。这也是把脚本交给 cron、CI 或别人之前的最低验收标准。

### $\rm \S \, 25.5.9$ 临时文件：为什么不要用 `$$` 拼名字

§25.5.3 的 `mktemp` 已经出现过，但只当作“生成一个临时文件名”用了。它真正解决的是一个安全问题，值得讲清代价。

先看不用 `mktemp` 时常见的写法：

```bash
TMP=/tmp/myapp.$$          # $$ 是当前 Shell 的 PID
echo "中间结果" > "$TMP"
```

PID 是**可预测**的：它是一个不大的连续整数，攻击者可以枚举。这带来两类攻击。**符号链接攻击**：在你创建文件之前，攻击者先把 `/tmp/myapp.1234` 建成指向 `/etc/somefile`（或你自己的某个文件）的符号链接；你的 `>` 一执行，写的其实是那个目标文件——如果脚本以特权身份运行，这就变成了对任意文件的覆盖。**抢名**：攻击者先占用这个名字并设成他不许你写的权限，让脚本失败或读到别人投放的内容。`/tmp` 是全局可写的（[文件系统、路径与权限](03-文件系统路径与权限.md) §3.14），任何用户都能在里面放东西，所以这类名字必须**不可预测**。

`mktemp` 正是为解决这两件事设计的：它在创建文件时用一个足够随机的名字，并且**创建是原子的**——如果名字已被占用（无论被文件还是符号链接占用）它就直接失败，而不是傻乎乎地往上面写：

```bash
# 前置：Bash/Zsh（Git Bash 也可用）；当前目录任意
tmpfile=$(mktemp)                 # 默认在 /tmp 下建一个 tmp.XXXXXXXXXX 形式的文件
echo "$tmpfile"                   # 预期：/tmp/tmp.JVnBDV9cEh 这样的一串随机后缀
ls -l "$tmpfile"                  # 预期：权限是 -rw-------（600）
```

两点要注意。第一是权限：`mktemp` 建出来的文件默认 `600`，只有你自己能读写——临时文件里可能含有不该给别人看的内容，这个默认值是有意的。第二是**用完要清理**：临时文件不会自己消失，脚本异常退出时也一样。用 §25.5.3 学过的 `trap` 把清理挂在退出上：

```bash
#!/bin/bash
set -euo pipefail

tmpfile=$(mktemp)                  # 文件形式
workdir=$(mktemp -d)               # 目录形式：-d
trap 'rm -f "$tmpfile"; rm -rf "$workdir"' EXIT
#  ↑ EXIT 在正常结束、报错退出、被 Ctrl+C 中断时都会触发

echo "工作目录：$workdir"
# ... 在这里干活，结束时无需手动清理
```

`trap ... EXIT` 的可靠性和 `flock` 的自动释放是同一类思路：把清理挂在“进程无论如何都会走到的那一步”上，而不是指望脚本的作者记得在每个分支里写清理。注意 `rm -rf "$workdir"` 里 `workdir` 来自 `mktemp -d`，是脚本自己刚创建、名字随机、内容可控的目录——这与[文件系统、路径与权限](03-文件系统路径与权限.md) §3.5.4 禁止的“无上下文递归删除”是两回事；仍然要给变量加引号，避免路径含空格时被拆开。

**临时文件该放在哪**，取决于它要活多久：

| 位置 | 谁清理 | 适合什么 |
|---|---|---|
| `/tmp`（Windows：`$env:TEMP`） | 系统按策略清理（重启常被清空；各发行版与容器的行为不同） | 一次运行内用完就丢的中间结果 |
| `/var/tmp` | 系统很少清（保留跨越重启） | 需要留到下次运行继续用、又不属于正式数据的缓存 |

选择的原则是“按生命周期放”，而不是“随便找个可写目录”。两者都应该按不可信环境对待（用 `mktemp` 生成名字），区别只在存活时间。

### $\rm \S \, 25.5.10$ 输出到终端还是管道：`[ -t ]` 判断

有些程序的行为会因为“输出是不是终端”而不同，这常让同一段代码在本地好好的、上了 CI 却变了样。原因是**标准流是否连接终端（TTY）**是可以判断的，很多程序据此切换行为：

```bash
# 前置：Bash/Zsh；这些是内置测试，不依赖外部命令
[ -t 0 ] && echo "stdin 是终端" || echo "stdin 不是终端"
[ -t 1 ] && echo "stdout 是终端" || echo "stdout 不是终端"   # 同理 -t 2 看 stderr
```

`[ -t N ]` 检查 fd N 是否连在一个终端设备上。在 Bash 里直接运行上面两行，你会看到 stdin/stdout 都是终端；把它改成 `echo hi | bash -c '...'` 或把输出重定向进文件，判断就变成“不是”。这背后的系统调用是 `isatty()`，Python 里对应 `sys.stdout.isatty()`：

```bash
python -c "import sys; print('stdout 是终端：', sys.stdout.isatty())"
python -c "import sys; print('stdout 是终端：', sys.stdout.isatty())" | cat
# 预期：第一行 True（直接连终端）；第二行 False（输出被管道接收）
```

判断它有什么实际用途：

- **彩色输出与进度条只在 TTY 上开**。彩色靠的是 `\033[...m` 这样的转义序列，把带转义码的输出重定向进文件或喂给 `grep`，结果是文件里多出一堆乱码、匹配也变难；进度条（`\r` 反复刷新同一行）在管道里会变成一堆残行。所以有经验的程序会先判断 `isatty()`。
- **交互式提问要判断 stdin**。`read -p`、`input()` 这类提示需要人来回答；在 CI、cron 或 `|` 场景下没有终端，强行提问会读到空内容或直接报错，正确的做法是改为从环境变量/参数取值。
- **`grep --color=auto`、`ls --color=auto` 的 `auto` 就是这个判断**：是终端才上色，进管道就不上色。

一个最小示例，只在输出接到终端时才着色：

```bash
#!/bin/bash
# 前置：Bash/Zsh（Git Bash 也可）；用于给提示信息上色但不污染日志
if [ -t 1 ]; then
    RED=$'\033[31m'; NC=$'\033[0m'    # $'...' 让 \033 被解释成转义字符
else
    RED=''; NC=''                      # 不是终端就什么都不加
fi
echo "${RED}错误：数据文件为空${NC}"
```

```bash
./colormsg.sh                     # 预期：错误信息是红色的
./colormsg.sh > out.log           # 预期：out.log 里是纯文本，不含转义码
./colormsg.sh | grep 错误          # 预期：能正常匹配，因为颜色被关掉了
```

> **CI 里最容易被这个差异咬到的两处**：一是本地看起来有颜色的日志，在 CI 归档后成了带转义码的乱码（应在 CI 里显式关闭颜色，如 `--color=never`，或给构建工具设 `NO_COLOR=1`）；二是本地跑的交互式脚本在 CI 里因为 `[ -t 0 ]` 为假而行为突变（读不到输入、直接退出）。这两处都不需要改“代码逻辑”，只需要知道终端与否是一个可判断、且会被程序用来改变行为的状态。

## $\rm \S \, 25.9$ 本章自测答案

> 先闭卷作答本章“关键概念回顾”与“应用与辨析”，再核对以下答案。

### $\rm \S \, 25.9.1$ 自测答案 · 关键概念回顾
1. `wsl --install` 默认装的 WSL 2 在轻量级虚拟机里运行真正的 Linux 内核（WSL 1 才是系统调用翻译层），但不模拟完整 PC 硬件——启动和资源开销远小于传统虚拟机，文件系统与网络还和 Windows 互通。
2. Ctrl+Z 挂起程序（可恢复），Ctrl+C 请求终止。`fg` 拉回前台，`bg` 放到后台。
3. 无引号：空格分割+通配符展开。双引号：变量展开，空格保护。单引号：一切字面。
4. nohup 适合一次性后台任务；tmux 适合需要查看输出、手动交互、或 SSH 可能断的场景。
5. 结束标记不加引号时，heredoc 内的变量会被展开、`$(...)` 会被执行、反斜杠有转义作用；加引号（`<<'EOF'`）让整段内容完全字面化。写配置文件通常该加引号——配置里常含 `$`（如 `${VAR}`、`$HOME`），那些符号是要留给目标程序自己解释的，被 Shell 抢先替换掉就错了（§25.5.6）。

### $\rm \S \, 25.9.2$ 自测答案 · 应用与辨析
1. 登录 Shell（SSH 登录、macOS 的终端窗口）读 `.bash_profile`，通常在里面 `source ~/.bashrc`；Linux 桌面终端的交互式非登录 Shell 直接读 `.bashrc`。所以配置写进 `.bashrc`、只在 `.bash_profile` 里兜底最省事。
2. 管道中间命令失败（除非 `pipefail`）、`if`/`while`/`||`/`&&` 条件位置，以及命令替换的失败被赋值命令掩盖的情况（`local x=$(false)`）。
3. 脚本里有不幂等的操作：`mkdir dir` 建目录、`ln -s` 建链接、`useradd` 建用户这类命令在目标已存在时会返回非零，`set -e` 于是让脚本中断。两类修法是：一是换成幂等写法（`mkdir -p`、`ln -sf`、追加前先 `grep -Fqx` 查一下、写配置用 `>` 整体重写而不是 `>>` 追加）；二是先查再改（`[ -d dir ] || mkdir dir`、`id 用户名 >/dev/null 2>&1 || useradd 用户名`）。注意正确顺序是“先让操作幂等，再靠 `set -e` 守住真错误”——不要为了重跑方便直接去掉 `set -e`（§25.5.8）。
4. `$$` 是当前 Shell 的 PID，是一个可预测的小整数，攻击者可以枚举并抢先占住这个名字：或在创建前把它做成指向别处的符号链接（脚本写入时其实写到了目标文件——符号链接攻击），或用权限/内容使脚本失败。`mktemp` 的两点做法分别防住这两类风险：一是**名字足够随机**，无法被猜中或提前布置；二是**创建动作原子**，名字已被占用（含被符号链接占用）时直接失败，绝不覆盖（§25.5.9）。

### $\rm \S \, 25.9.3$ 自测答案 · 加练
① 直接运行（stdout 是终端）：`[ -t 1 ]` 为真，脚本加上 `\033[31m` 转义序列，看到红色文字。重定向进文件或接进管道：`[ -t 1 ]` 为假，颜色变量为空，输出纯文本，文件里没有转义码、`grep` 也能正常匹配。判断依据是 fd 1 是否连在终端设备上（系统调用 `isatty()`）——程序据此切换“给人看”与“给程序看”的输出形式（§25.5.10）。
② `out=$(command)` 把命令的标准输出保存进变量（赋值时右侧不加引号），读取时写成 `"$out"` 以保护空格。不能直接依赖它处理多个文件名，是因为命令替换会去掉末尾换行、且未加引号时结果按空白分词，带空格或换行的文件名会被拆成多个词；这类“把文件名列表传给下一个命令”的场合应该用 NUL 分隔（`find ... -print0 | xargs -0`，见[文件系统、路径与权限](03-文件系统路径与权限.md) §3.12.2）。另外命令替换的失败会被赋值语句掩盖（`local x=$(false)`），不会触发 `set -e`（§25.5.3、§25.5.7）。
