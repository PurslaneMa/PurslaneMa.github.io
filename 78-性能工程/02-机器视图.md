## $\rm \S \, 2.1$ 延迟与带宽：先把两个词掰开

第 1 章的 roofline 里 $B$ 是「每秒搬运的字节上限」，但你实际等的是另一件事。把一次访存拆开看：发出地址，等数据回来，这段等待时间叫延迟（本册 §1.1 已定义延迟这个词，这里说的是它访存场景下的具体所指）；单位时间内能搬过的字节总量叫带宽（bandwidth）。两者由一个中间量连起来：**在途请求数**（outstanding requests，已发出还没拿到数据的请求数）。要在带宽 $B$ 下持续搬运，每次传输 $s$ 字节，而一个请求从发出到回来要 $L$ 那么久，则至少要有

$$
n \;\ge\; \frac{L \times B}{s}
$$

读法：$n$ 是必须同时挂在途上的请求个数。内存一边等 $L$ 才交一次货，一边要求每 $\frac{s}{B}$ 秒交一次货，两个节奏要同时成立，在途的请求就得把 $L$ 填满；这个关系是排队论里 Little 定律的直接应用。延迟是「一单等多久」，带宽是「总共能流水多少」，同一个内存两个数可以差出天壤：单发一发地等，你只拿到延迟；并发地发，你才摸到带宽。第 1 章求和循环的 10.9 GB/s 和本章将测出的内存延迟，就是同一块内存的这两个面。

白话：带宽是水管每秒出水多少升，延迟是你拧开阀门到水出来的那半秒；想要大流量，光拧大阀门没用，得同时开很多根管子。

> 本节小结：访存有两个独立的价签，延迟按单次请求计，带宽按字节流计；两者由在途请求数 ${n \ge L \times B / s}$ 连接，想跑满带宽必须把在途数堆上去。

## $\rm \S \, 2.2$ 汇编怎么读：寄存器、操作数与寻址

编译器不执行你的循环，它执行翻译后的机器指令。看懂翻译结果有两个理由：其一，§1.3 的悬案（循环被删、计算被搬走）最终只能在汇编里定案；其二，第 3 章的微优化要判断「编译器到底帮我做了没有」，答案也在这里。生成汇编的命令是 `gcc -S`（Shell/WSL，当前目录有源文件；生成 `.s` 汇编文件，不产生可执行文件，无副作用）：

```bash
gcc -S -O0 -fno-asynchronous-unwind-tables -o demo_O0.s asm_demo.c   # 供人阅读的翻译稿
gcc -S -O2 -fno-asynchronous-unwind-tables -o demo_O2.s asm_demo.c   # 发布形态的翻译稿
```

`-fno-asynchronous-unwind-tables` 只删去与调试相关的 `.cfi` 注释行，让清单干净，不影响指令本身。x86-64 的 gcc 输出用 AT&T 语法：目的操作数在右（`addq %rcx, %rax` 是 `rax += rcx`），寄存器带 `%` 前缀，常数（立即数，immediate）带 `$` 前缀。先看 `frame_demo`（两数相乘之类的纯算术）在 `-O0`（不优化）下的样子：

```text
frame_demo:
	pushq	%rbp                # 序言：把调用者的栈帧基址存回栈上
	movq	%rsp, %rbp          # 本函数的栈帧基址立起来
	movq	%rdi, -24(%rbp)     # 第 1 个参数从寄存器搬进栈槽
	movq	%rsi, -32(%rbp)     # 第 2 个参数同样
	movq	-24(%rbp), %rdx     # 从栈槽读回（-O0 就这么憨）
	movq	%rdx, %rax
	addq	%rax, %rax          # x*2
	addq	%rax, %rdx          # x*3
	movq	-32(%rbp), %rax
	addq	%rdx, %rax          # u = x*3 + y
	movq	%rax, -16(%rbp)     # u 存进栈槽
	movq	-16(%rbp), %rax
	subq	$7, %rax            # v = u - 7
	movq	%rax, -8(%rbp)      # v 存进栈槽
	movq	-16(%rbp), %rax
	imulq	-8(%rbp), %rax      # u * v
	popq	%rbp                # 尾声：恢复调用者的 rbp
	ret                     # 返回，结果已在 %rax
```

序言（prologue，函数开头固定的一小段）与尾声（epilogue）一对，把《编译原理》§5.2 的栈帧图变成了真指令：`pushq %rbp` 存调用者的基址，`-8(%rbp)`、`-16(%rbp)`、`-24(%rbp)` 是本函数在栈上租的三个槽位。清单里出现了五种操作数形式，全部是 x86-64 的基本寻址模式：

1. 立即数：`addq $8, %rdi` 里的 `$8`，常数直接写在指令里；
2. 寄存器：`addq %rcx, %rax`，操作数就在寄存器里，最快；
3. 间接：`movq (%rdi), %rcx`，取 `%rdi` 指向的内存，方括号 dereference；
4. 偏移：`movq -24(%rbp), %rdx`，取 `%rbp-24` 处的内存，访问栈槽全靠它；
5. 基址加变址乘比例：`leaq (%rdi,%rsi,8), %rsi`，算出 `%rdi + %rsi×8` 不访存，`lea` 本是取地址指令，被编译器当免费的小算术器用。

同一函数在 `-O2` 下会瘦成几条寄存器运算，但寻址模式还是这五种。再看一个真循环，`scale_sum`（对数组求 `k*a[i]` 之和）在 `-O2` 下：

```text
scale_sum:
	endbr64
	testq	%rsi, %rsi          # n <= 0？
	jle	.L4                     # 是则直接返回 0
	leaq	(%rdi,%rsi,8), %rsi # 循环终点：a + n*8，即数组尾巴
	xorl	%eax, %eax          # 和清零
.L3:
	movq	(%rdi), %rcx        # 取 a[i]
	addq	$8, %rdi            # 指针前进一个 long
	imulq	%rdx, %rcx          # 乘 k
	addq	%rcx, %rax          # 累加
	cmpq	%rsi, %rdi
	jne	.L3
	ret
```

循环变量 `i` 不见了：编译器把它换成指针 `(%rdi)` 加步进 `addq $8`，这就是《计算机系统结构》§2.3 讲的 load/store 架构在真代码里的样子。读汇编不需要背指令集，抓住三件事就够：数据住在哪（寄存器、栈槽、内存）、每条指令把数据往哪搬、循环体里有几条访存指令。

白话：读汇编像看后厨，源代码是菜单，`-O0` 是学徒做菜每一步都先放回冰箱再拿出来，`-O2` 是熟手全程端在手上不落地。

> 本节小结：`gcc -S` 给出真翻译；先认序言尾声与五种寻址模式，再看循环体里几条访存；悬案定案与微优化验收都以汇编为准。

## $\rm \S \, 2.3$ 调用约定与 saved registers：一次调用强制你付什么

源代码里写 `f(x)` 是一行，机器上是《编译原理》§5.3 讲的那份书面协议（调用约定，calling convention）：前 6 个整数参数依次走 `rdi`、`rsi`、`rdx`、`rcx`、`r8`、`r9`，返回值放 `rax`；寄存器分两派，调用者保存（caller-saved）的 `rax`、`rcx`、`rdx`、`rsi`、`rdi`、`r8`～`r11` 跨调用不作数，被调者保存（callee-saved）的 `rbx`、`rbp`、`r12`～`r15` 谁想用谁先存。§5.3 已把两派的代价账算全（跨调用 $c_v$ 次的值付 $2c_v$ 对一次性付 2，并实测极端情形慢 3.6～3.8 倍），本节只补上「调用本身」的价。把 `helper` 放进另一个编译单元防止内联（§5.3 同款手法），`caller` 三个参数个个跨调用存活：

```c
long helper(long x);           /* 在另一个 .c 里,本单元看不见函数体 */
long caller(long a, long b, long c) {
    long t = helper(a) + helper(b) + c;
    return t * 2 - a;
}
```

`gcc -S -O2` 给出的真身（已删 `.cfi` 行）：

```text
caller:
	pushq	%r13            # 序言:四个被调者保存寄存器挨个存旧值
	movq	%rsi, %r13      # b 挪进 r13(要活过两次调用)
	pushq	%r12
	movq	%rdx, %r12      # c 挪进 r12
	pushq	%rbp
	movq	%rdi, %rbp      # a 挪进 rbp
	pushq	%rbx
	subq	$8, %rsp        # 栈对齐到 16 字节
	call	helper@PLT      # 参数已在 %rdi,直接调
	movq	%r13, %rdi      # 第二次调用的参数
	movq	%rax, %rbx      # 第一笔结果挪进 rbx(要活过第二次调用)
	call	helper@PLT
	addq	$8, %rsp
	addq	%rbx, %rax      # 两笔结果相加
	popq	%rbx
	addq	%r12, %rax      # 加 c
	addq	%rax, %rax      # 乘 2
	subq	%rbp, %rax      # 减 a
	popq	%rbp
	popq	%r12
	popq	%r13
	ret
```

四个值（`a`、`b`、`c` 加第一笔结果）都要跨调用存活，gcc 只能把它们全部赶进被调者保存寄存器，于是序言 4 次 `push`、尾声 4 次 `pop`，外加一次 `subq $8` 把栈指针对齐到 16 字节（协议要求 `call` 时栈 16 字节对齐）。注意 `a` 的参数寄存器 `rdi` 属于调用者保存，第一次 `call` 就可能把它踩掉，所以参数一进门就被请进 `rbp`。实测（`expPE02/result.txt`，N=2^28 次调用、7 轮取最速、外部编译单元的 `inc(x){return x+1;}` 作被调函数）：调用循环每轮 0.41～0.47 ns，同结构纯自增循环 0.35～0.39 ns，差值即 `call` 加 `ret` 加传参搬移的纯开销，约 0.06～0.12 ns，折合不到 1/3 拍。反汇编显示循环体只有 4 条指令，`call inc`、`mov %rax,%rdi`（返回值转下一轮参数，寄存器改名零成本）、计数与跳转，没有任何栈访问。

这组数字给出本章第二个反直觉结论：**调用本身近乎免费**（预测器把 `call`/`ret` 处理得几乎不占节奏），贵的是 ABI 强制的周边：被调者保存寄存器的存取、参数与结果的搬运，以及内联机会的丧失让优化器少看到的整片上下文。§5.3 那个慢 3.6～3.8 倍的实验里，没有一次开销来自 `call` 指令本身，全部来自循环体被迫穿过内存。

白话：打电话本身不要钱，贵的是通话前你把桌上摊开的资料全部收进抽屉、挂了电话再全部摊开；寄存器越多要收的资料越多。

> 本节小结：参数走 `rdi`～`r9`、返回走 `rax`；跨调用存活的值被迫进被调者保存寄存器，序言尾声各付一次存取；`call`/`ret` 纯开销实测不足 1/3 拍，调用的真实代价在 ABI 的周边账上。

## $\rm \S \, 2.4$ 实验：pointer chasing 把每层延迟量出来

现在造一台「延迟测量仪」。原理用足 §2.1 的账：把数组摆成一条链 `a[i]` 存「下一个下标」，循环体只有一句 `p = a[p]`。下一次访存的地址由上一次的结果算出，硬件想提前发第二单也不知道地址，于是**任何时刻在途请求恰好为 1**，$n=1$ 代入 §2.1 的公式，每次搬运耗时就是延迟 $L$ 本身。这就是 pointer chasing（指针追访，沿着链一跳一跳地走）：单链追访测出的是纯延迟，与带宽无关。乱序执行救不了它（《计算机系统结构》§4.2：名字依赖可以靠重命名解开，真依赖解不开，这条链全是真依赖）。

实验自己也先踩了一脚 §1.3 的坑。第一版守卫写的是 `if (p == 42) printf("")`，gcc 认定空串 `printf` 无副作用，把守卫折成空操作，整条链因为「结果无人读」被整体删除，计时器报出 0.000 ns。换成空汇编屏障 `__asm__ volatile("" : : "r"(p) : "memory")` 后链才活过来。两台仪器共用一个 256 MiB 数组、每轮固定 $2^{25}$ 次追访（控制变量：总访问次数不随工作集变），预热 1 轮加计时 5 轮取最速：

1. **步长仪**：链设成 `a[i] = (i + s/8) mod n`，按字节步长 $s$ 从 8 B 扫到 128 MB；步长 $s$ 决定每跳跨多远，也决定被触碰的去重缓存行数（${s \ge 64}$ B 时每跳独占一行，触碰量为 ${64 \cdot 256\,\text{MB} / s}$）。
2. **随机环仪**：把前 $W/8$ 个元素连成单一随机环（Fisher-Yates 洗牌后首尾相接，种子 20261107），工作集 $W$ 从 4 KB 扫到 256 MB；环上地址杂乱无章，预取器无从学起，测得的是最诚实的延迟。

先看随机环仪的账（表摘 6 行，全表在 `expPE02/result.txt`；折算拍按实测 2.6 GHz）：

| 工作集 $W$ | ns/跳 | 折合拍 | 位置判读 |
| --- | --- | --- | --- |
| 48 KB（=L1d 容量） | 1.50 | 3.9 | L1 命中 |
| 1 MB | 9.77 | 25 | L2 命中段 |
| 3 MB（=L2 容量） | 16.87 | 44 | L2 边界 |
| 4 MB | 25.63 | 67 | L3 命中段 |
| 8 MB | 165.18 | 430 | 已塌方 |
| 256 MB | 240.81 | 627 | DRAM（随机依赖） |

三个台阶读出来：48 KB 以内钉死在 1.45～1.64 ns（3.8～4.3 拍），与《计算机系统结构》§5.1 的「L1 约 4 拍」严丝合缝，这一档是本次测量里最干净的平台；工作集过了 L1 容量后延迟开始爬坡，到 3 MB 处 16.9 ns；4 MB 处 25.6 ns 之后曲线在 6～8 MB 之间塌方，8 MB 以上进入 165～290 ns 的 DRAM 档。两处与惯例数值不符的地方照实记账，不硬编机制：其一，L2 段是爬坡不是平台，用 L1 部分命中的混合账算过（48 KB 恒定占 768 行，对 256 KB 工作集贡献 19% 的 L1 命中），混合后的 L2 延迟应是与工作集无关的常数，实测却从约 5 ns 爬到 16.9 ns，说明这层还有我们看不到的机制在起作用；其二，名义 24 MiB 的 L3 在随机依赖访问下 6 MB 就开始接不住，比标称容量提前塌方。测量环境的嫌疑最大：本实验跑在 WSL2 里，虚拟机之下还有宿主的一层地址翻译（扩展页表，EPT，Extended Page Table，虚拟机监控器用来把虚拟机物理地址再翻一层），它对顺序访问几乎隐形，对随机访问每次都可能加一层查表。

大页实验把这个嫌疑钉实了一半。第一版用普通 `malloc`（4 KB 页），随机环在 32 MB 工作集测得 300.0 ns、256 MB 测得 384.0 ns，步长仪在 $s{=}512$ KB 处更是测出荒唐的 283.9 ns（工作集才 32 KB，本该 L1 速度）。假设：病在地址翻译，4 KB 页太碎，翻译缓存（TLB，见《操作系统》§4.5）装不下这么多页，每次追访都在页表里迷路。验证：改成 2 MB 对齐的 `mmap` 加 `madvise(MADV_HUGEPAGE)`（本机透明大页（transparent huge page, THP）为 madvise 模式，进程内自证 `AnonHugePages=262144 kB`，整片数组真用了大页），复测：

| 测点 | 4 KB 页 | 2 MB 大页 | 改善 |
| --- | --- | --- | --- |
| 步长 $s{=}512$ KB（W=32 KB） | 283.9 ns | 33.7 ns | 8.4 倍 |
| 随机环 W=32 MB | 300.0 ns | 270.7 ns | 10% |
| 随机环 W=256 MB | 384.0 ns | 240.8 ns | 37% |

结论分两半：步长仪那几个点的病确实是访客侧 TLB，大页救回 8 倍；DRAM 档只便宜了一到三成，残余的 220～290 ns 是这个环境量得到的地板（宿主侧翻译在 WSL 里够不着）。顺手一提：同样这批大页点在裸机上文献常引约 80～100 ns（《计算机系统结构》§5.1 的「约 100 ns」），虚拟化让随机访存延迟翻倍还多，这本身就是「报数字必须报环境」的血泪注脚。

步长仪的账同样有货，它把《计算机系统结构》§5.2 的三类缺失演成了三幕剧（表摘 6 行）：

| 步长 $s$ | 触碰量 | ns/跳 | 判读 |
| --- | --- | --- | --- |
| 8 B | 256 MB | 2.85 | 顺序流，预取器接管，量的是带宽不是延迟 |
| 64 B | 256 MB | 5.21 | 每跳一整行，预取器仍跟得上 |
| 8 KB | 2 MB | 148.31 | 大步长 + 2 的幂，组冲突 |
| 32 KB | 512 KB | 302.31 | 冲突最狠处 |
| 512 KB | 32 KB | 33.70 | 工作集只装 L1，却慢 20 倍 |
| 128 MB | 128 B | 1.65 | 只剩两行，回到 L1 |

中间三行的病根是同一句话：这台 L1d 的组周期是 64 组 × 64 B = 4096 B，凡步长是 4096 B 的倍数（所有 2 的幂且 $\ge$ 4 KB 的步长都是），每一跳落进**同一个组**。组相联度只有十几路，几百上千行抢一个组，这就是 §5.2 说的第三类缺失（冲突缺失）的现场：容量明明装得下（32 KB < 48 KB），位置却互相踢。所以步长仪在大步长区测出的不是延迟，是冲突的价格；$s{=}512$ KB 那行 33.7 ns 对随机环仪同工作集的 1.64 ns，20 倍差价全是「摆放方式」的账。步长仪 small-s 端也别误读：2.85 ns 折合 22 GB/s 的等价带宽，那是预取器看穿固定节奏后把多条请求挂上在途（§2.1 的 $n$ 变大了），量的是带宽；随机环仪不给你这个便宜，1.5 ns 是纯延迟。两台仪器对照，正好把 §2.1 的两个价签各收进一张表。

白话：随机环是在陌生城市里被蒙上眼随机敲门，每次都真等；固定步长是每天走同一条街，走到后来闭着眼也知道下一家在哪，测出来的已经是「熟练」不是「距离」；而 2 的幂步长偏偏每天敲同一栋楼的同一个门牌，堵在楼道里出不来。

> 本节小结：单链追访 $n{=}1$，量得纯延迟；随机环仪给出 L1 约 1.5 ns、L2 段至 16.9 ns、DRAM 档 220～290 ns（WSL2 放大，大页救回一部分）；步长仪的 2 的幂大步长全组冲突不可信，小步长量的是带宽。两层仪器对照才有可信的账。

## $\rm \S \, 2.5$ 完整的账：为什么内存是新的磁盘

把本章实测与本机可以引用的典型值并成一张总账（「实测」指本章 `expPE02/result.txt`，「引用」指《计算机系统结构》§5.1）：

| 层 | 延迟 | 折合拍（2.6 GHz） | 来源 |
| --- | --- | --- | --- |
| 寄存器 | 0 | 0 | 定义所在 |
| L1d | 1.5 ns | 4 | 实测（随机环，W ≤ 48 KB） |
| L2（3 MiB 边界） | 16.9 ns | 44 | 实测（随机环，W=3 MB） |
| L3 | 25.6 ns | 67 | 实测（随机环，W=4 MB） |
| DRAM（随机依赖） | 220～290 ns | 570～750 | 实测（虚拟化放大，裸机常引约 100 ns） |
| SSD | 约 100 µs | 约 2.6×10^8 | 引用 |

「内存是新的磁盘」说的就是这张表的比例。二十年前的账本是：内存约 100 ns，磁盘约 10 ms，中间隔 5 个数量级，所以「数据在不在内存」是天壤之别，磁盘 IO 要按次数计价。今天的账本换了一头：SSD 把磁盘那头的差距压到约 3 个数量级，可 CPU 这头把 L1 到 DRAM 拉开了约 2 个数量级（本机实测 160 倍，裸机口径约 60～75 倍）。从 CPU 的视角看，DRAM 的几百拍就是当年磁盘的一转：随手一次缓存不命中，流水线空转几百拍，够执行上千条加法。磁盘的暴政死了，内地的暴政换了个姓氏接着统治，优化纪律没变：把热数据往上层放，把访存次数当钱花。

现在平第 1 章的悬账。求和循环实测 10.9 GB/s，即每 5.9 ns 交割一条 64 B 缓存行；单链追访测得 DRAM 随机延迟约 241 ns。代入 §2.1 的公式：

$$
n \;\ge\; \frac{L \times B}{s} = \frac{241\,\text{ns} \times 10.9\,\text{GB/s}}{64\,\text{B}} \approx 41
$$

读法：要撑住 10.9 GB/s，硬件必须同时保持约 41 条缓存行的请求在途。单链追访 $n{=}1$，等价带宽只有 ${\frac{64\,\text{B}}{241\,\text{ns}} \approx 0.27}$ GB/s，同一块 DRAM，10.9 除以 0.27 恰好约 41 倍，两个方向的账对上了。第 1 章那个循环快，快在顺序访问让硬件预取器敢把 40 来单同时挂在途，而不是内存突然变勤快；roofline 的 $I \times B$ 只看见带宽这一面，延迟那一面本章补齐：**延迟决定一根链能跑多快，带宽要靠并发去买，买钱来自访问模式的规律性**。这一句是第 3 章所有微优化的定价基础。

白话：内存像一家出餐极慢但可以同时接几十单的外卖店，单点单等 4 分钟，几十单一起点就能让厨房不间断出货；你写代码的任务就是让请求长得让厨房愿意并行接单。

> 本节小结：L1 四拍、L2 四十拍、L3 七十拍、DRAM 数百拍；求和循环 10.9 GB/s 的悬案答案是在途约 41 行；延迟与带宽是两张价签，访问模式决定你能买到哪张。

## $\rm \S \, 2.6$ 关键概念回顾

1. 用 §2.1 的公式说明：为什么单链 pointer chasing 测出的是延迟，而顺序扫描测出的主要是带宽？各自对应 $n$ 等于多少？
2. `caller` 里参数 `a` 一进门就被挪进 `rbp`，这个动作由协议的哪一条规定逼出来？如果 ABI 只剩调用者保存寄存器，这段函数的序言会变成什么样？
3. 本章实测 `call`+`ret` 纯开销不足 1/3 拍，但《编译原理》§5.3 的实验里全调用者保存版慢 3.6～3.8 倍。两笔账如何同时成立？调用的真实代价在哪？

## $\rm \S \, 2.7$ 应用与辨析

1. 排障：同事在 WSL2 上跑随机访存基准，256 MB 工作集测得 384 ns，他写进报告「这台机器内存延迟 384 ns」。按本章流程列出你要追问的四个问题，并指出哪一问最可能把数字拉回 241 ns。
2. 辨析：有人说「L3 容量 24 MiB，所以我的工作集 16 MiB 一定全在 L3 里」。用本章 8 MB 与 16 MB 两个测点说明这句话错在哪，并给出一个更稳的判据。

## $\rm \S \, 2.8$ 本章自测答案

概念回顾答案：

1. 单链时下一跳地址依赖上一跳结果，硬件无从提前发单，$n{=}1$，耗时即延迟 $L$；顺序扫描的后续地址可预测，预取器把 $n$ 抬到几十，耗时由 $\frac{s}{B}$ 决定，量出的是带宽（§2.1、§2.4）。
2. `rdi` 是调用者保存寄存器，第一次 `call` 就可能被踩掉，`a` 要活过两次调用，必须挪进被调者保存寄存器。若全是调用者保存，这些值只能溢出到栈上，序言变成一串 `movq %rdi, -8(%rsp)` 式的存栈，循环内每次跨调用都要存取，即 §5.3 的 $2c_v$ 计价（§2.3）。
3. `call`/`ret` 本身被预测器处理得近乎零成本，实测不足 1/3 拍；§5.3 的 3.6～3.8 倍全部来自 ABI 周边账：累加器被迫穿内存的存取与依赖链，没有一笔来自 `call` 指令本身（§2.3）。
4. 组周期 = 64 组 × 64 B = 4096 B；512 KB 是它的倍数，每跳落进同一组，组相联十几路装不下触碰的行，这是第三类缺失（冲突缺失）：容量装得下、位置互相踢（§2.4）。
5. $n \ge \frac{241 \times 10.9}{64} \approx 41$ 行；行变 128 B 后 $n \ge \frac{241 \times 10.9}{128} \approx 21$ 行，需要挂着的行数减半，因为每单货运量翻倍（§2.1、§2.5）。

应用与辨析答案：

1. 四问：环境是裸机还是虚拟机（嫌疑最大，EPT 加一层翻译）；用的 4 KB 页还是大页，`AnonHugePages` 是多少；访问模式是随机依赖还是固定步长（预取器与组冲突都会改写数字）；计时协议是否预热加多轮取 min。最可能翻案的是第一问：换裸机或宿主侧复测（§2.4）。
2. 本章实测 8 MB（名义容量三分之一）时延迟已塌到 165 ns，16 MB 时 253 ns，早于 24 MiB 就接不住了；名义容量是标签，随机依赖访问下的塌方点才是有效容量，更稳的判据是用本章仪器扫工作集找自己的塌方点（§2.4）。
3. 最小测量仪：循环体一句 `p = stack_buf[p]`（栈数组成链），与同尺寸堆数组链对照，各跑预热加 5 轮取 min；再用 `gcc -S` 核对栈访问真的存在（`-8(%rsp)` 式指令）。若栈版每跳显著慢于堆版（栈版额外背 RBP 相对寻址与每次函数帧切换的 TLB/缓存扰动），假设成立；若两版数字相同，假设被证伪，慢的原因在别处（§2.2、§2.4）。

**你现在能做什么**：你能在任何一台 Linux/WSL 机器上用 `gcc -S` 读出自己循环的真身，并用一条 `p = a[p]` 的链把自己机器的 L1、L2、L3、DRAM 延迟亲手量出来，拿实测数字去对质任何一张惯例表。下一章把镜头从「数据在哪」转向「指令怎么跑」：分支预测、循环展开与 SIMD，同样的假设-验证循环将逐条检验教科书上的微优化技巧在这台机器上值不值它们的名声。
