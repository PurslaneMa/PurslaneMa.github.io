# $\rm Chapter \, 15$ 从竞赛 C++ 到工程 C++

> 你在 OJ 上写的 C++ 程序，代码量通常在 100-300 行，所有逻辑塞进一个 `main.cpp`，使用 `#include <bits/stdc++.h>`，用 `new` 分配数组，用 `cout` 输出，用 `return 0` 结束。这完全够用——在 OJ 上。工程中的 C++ 程序有几千到几万个文件，编译时间可能比你运行时间还长，内存错误可能在生产环境潜伏几个月才爆发。这一章把你已经会用的 C++ 扩展到工程层面。

> **开始前自检**：本章假设你已经会：
>
> - □ 会写单文件 C++ 程序并编译运行（OJ 基础）
> - □ 用过命令行编译（g++ / cl / 编译按钮）
> - □ 理解变量、指针、引用与基本 STL

## $\rm \S \, 15.1$ 从单文件到多文件项目

### $\rm \S \, 15.1.1$ 为什么需要头文件和源文件分离

在 OJ 上你的代码可能是这样的：

```cpp
#include <bits/stdc++.h>
using namespace std;

int solve(int n, vector<int>& arr) { /* ... */ }

int main() {
    int n; cin >> n;
    vector<int> arr;
    // ...
    cout << solve(n, arr) << '\n';
}
```

工程中把这个拆成三层：

```text
paper-parser/
├── include/paper/parser.hpp     ← 声明（接口）：函数签名、类定义
├── src/parser.cpp               ← 实现：函数体
├── src/main.cpp                 ← 入口：main()
└── CMakeLists.txt               ← 构建配置
```

`parser.hpp`：

```cpp
#pragma once          // 防止被多次包含（替代传统的 #ifndef 守卫）
#include <string>
#include <vector>

namespace paper {    // 命名空间——防止名字冲突
    struct Paper {
        std::string title;
        int year;
        std::vector<std::string> authors;
    };

    // 声明：告诉编译器"这个函数存在，参数和返回值长这样"
    Paper parse_line(const std::string& line);
}
```

`parser.cpp`：

```cpp
#include "paper/parser.hpp"   // 先包含自己的头文件（检查声明和实现一致）
#include <sstream>            // 实现需要的额外头文件

namespace paper {
    Paper parse_line(const std::string& line) {
        // 实现...
    }
}
```

`main.cpp`：

```cpp
#include "paper/parser.hpp"
#include <iostream>

int main() {
    std::string line;
    while (std::getline(std::cin, line)) {
        auto paper = paper::parse_line(line);
        std::cout << paper.title << '\n';
    }
}
```

**为什么这样做**：
- 编译速度：改一个 `.cpp` 只重编译它自己再链接。一个 50 源文件的项目全量重编译要几分钟，增量重编译加链接只要几秒钟。
- 接口和实现分离：别人用你的 `parse_line` 时不需要知道内部实现——只需要 `#include "paper/parser.hpp"`。
- 物理隔离：`.hpp` 中不写实现细节，避免了代码依赖层的循环。

### $\rm \S \, 15.1.2$ CMake：不再手工敲 `g++ -I -L -l`

在第 1 章和第 2 章中你手工敲过 `g++ main.cpp -std=c++17 -o main`。三个文件还好，三十个文件时手敲不可能。**CMake** 是 C++ 生态中最广泛使用的构建系统（不是编译器——它生成 Makefile 或 Visual Studio 工程文件，再调用真正的编译器）。

一个最小 `CMakeLists.txt`：

```cmake
cmake_minimum_required(VERSION 3.16)
project(paper-parser VERSION 1.0 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)        # 使用 C++20
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(paper-parser       # 生成的可执行文件名
    src/main.cpp
    src/parser.cpp
)

target_include_directories(paper-parser PUBLIC include)
# PUBLIC 表示：自己编译时用 include/，而且依赖 paper-parser 的库也能看到这些头文件
```

构建步骤：

```bash
mkdir build && cd build          # 构建目录与源码分离
cmake ..                         # 读取 CMakeLists.txt，生成 Makefile
cmake --build .                  # 实际编译
./paper-parser < papers.txt      # 运行
```

`cmake ..` 只做配置，`cmake --build .` 才真正编译。修改源码后只需要重复第二步。CMake 会跟踪依赖，自动只重编译改动的文件。

> **竞赛生迁移提示**：`CMakeLists.txt` 描述“这个项目需要哪些源文件、依赖哪些库、用哪个 C++ 标准、输出什么类型的产物”。`cmake` 把它翻译成具体的编译命令（传给 g++ 或 MSVC）。你以前手动敲的 `-std=c++17 -Wall -Wextra -O2` 这些参数，现在写在 CMakeLists 里，团队共享一份。

## $\rm \S \, 15.2$ RAII：C++ 最核心的设计哲学

### $\rm \S \, 15.2.1$ 构造函数获取资源，析构函数释放资源

**RAII**（Resource Acquisition Is Initialization，资源获取即初始化）是 C++ 管理一切资源的基石——不仅仅是内存，还包括文件句柄、锁、套接字、数据库连接。

你在 OJ 上用过这种模式但没有它的名字：

```cpp
{
    std::vector<int> arr(1000000);  // 构造时分配内存
    // ... 使用 arr ...
}  // arr 离开作用域，析构函数自动释放内存——即使这里发生异常也会释放
```

工程中的扩展：

```cpp
{
    std::ifstream file("data.txt");  // 构造时打开文件
    // ... 读文件 ...
}  // file 离开作用域，析构函数自动关闭文件——不需要 fclose()
```

```cpp
{
    std::lock_guard<std::mutex> lock(mtx);  // 构造时加锁
    // ... 安全地操作共享数据 ...
}  // lock 离开作用域，自动解锁——即使发生异常
```

在[操作系统、进程与线程](../03-计算机系统/11-操作系统进程与线程.md)中你见过 `std::mutex` 和死锁。RAII 是 C++ 防止“忘记解锁”的标准方案——把资源生命周期绑定到对象生命周期。你不需要写 `unlock()` 或 `close()`——编译器保证析构函数一定被调用。

### $\rm \S \, 15.2.2$ 智能指针：`unique_ptr` 和 `shared_ptr`

OJ 上你可能会写：

```cpp
int* arr = new int[n];
// ... 使用 arr ...
delete[] arr;  // 忘了写 → 内存泄漏
```

工程中几乎不应该出现裸 `new` 和 `delete`。用智能指针：

```cpp
#include <memory>

// unique_ptr：独占所有权，不能复制，只能移动
auto arr = std::make_unique<int[]>(1000000);
// 离开作用域时自动 delete[]
// 零开销——编译器优化后和裸指针性能相同

// shared_ptr：共享所有权，引用计数
auto sp1 = std::make_shared<ExpensiveObject>();
auto sp2 = sp1;  // 引用计数 = 2
// 当最后一个 shared_ptr 销毁时，对象才被释放
```

**选择规则**：
- 默认用 `unique_ptr`——它没有引用计数的开销，可移动但不可复制，语义清晰（“我是唯一的所有者”）。
- 只有当你真的需要多个所有者共享同一个对象时，才用 `shared_ptr`。注意循环引用——A 持有 B 的 `shared_ptr`，B 持有 A 的 `shared_ptr`，谁都不会释放（用 `weak_ptr` 打破循环）。
- 裸指针仍然有用——但只用于“观察”（不拥有所有权），而不是“拥有”。

## $\rm \S \, 15.3$ 现代 C++ 中你应该知道的语言特性

### $\rm \S \, 15.3.1$ 移动语义：避免不必要的深拷贝

OJ 上你可能经常写：

```cpp
vector<int> generate_data {
    vector<int> result;
    // ... 填充数据 ...
    return result;  // C++11 起自动使用移动语义，不拷贝
}
```

在 C++11 之前，`return result` 会拷贝整个 vector。现在编译器自动使用**移动构造函数**——把 `result` 的内部指针“窃取”到新对象，源对象置空，$\mathcal{O}(1)$ 完成。

`std::move` 显式把左值转换为右值引用，发出“我不再需要这个值了，你可以搬走它”的信号：

```cpp
std::vector<int> a = {1, 2, 3};
std::vector<int> b = std::move(a);  // a 的内部数据被搬到 b
// 此后 a 处于"有效但未指定状态"——可以安全析构，但不应该再访问内容
```

### $\rm \S \, 15.3.2$ Lambda：匿名函数对象

在[操作系统、进程与线程](../03-计算机系统/11-操作系统进程与线程.md)中你见过用 `std::thread` 传函数。Lambda 让这件事更简洁：

```cpp
// 最简形式
auto is_recent = [](const Paper& p) { return p.year >= 2020; };

// 捕获外部变量
int cutoff = 2020;
auto recent = [cutoff](const Paper& p) { return p.year >= cutoff; };

// 和算法配合
std::vector<Paper> papers = load_papers();
std::erase_if(papers, [](const Paper& p) { return p.year < 1990; });

// 按引用捕获（可修改外部变量）
int count = 0;
auto counter = [&count](const Paper& p) { if (p.year >= 2020) count++; };
std::for_each(papers.begin(), papers.end(), counter);
```

Lambda 的本质是编译器帮你生成一个匿名的函数对象类。捕获列表决定了哪些外部变量被拷贝进这个对象、哪些被引用。`[=]` 按值捕获所有，`[&]` 按引用捕获所有——但最好明确列出你需要的变量，避免意外的生命周期问题。

### $\rm \S \, 15.3.3$ `auto` 与类型推导

```cpp
auto it = papers.begin();    // 不用写 std::vector<Paper>::iterator
auto [title, year] = parse();  // C++17 结构化绑定——从 pair/tuple 中拆出值
```

`auto` 不改变 C++ 的静态类型本质——编译器在编译时推导出确切类型。它减少了冗长类型名，降低了改类型时的修改范围。

### $\rm \S \, 15.3.4$ `std::optional` 和 `std::expected`：让错误成为类型的一部分

替代返回 `-1` 或 `nullptr` 表示“没有结果”：

```cpp
#include <optional>

std::optional<Paper> find_by_title(const std::string& title) {
    for (auto& p : papers)
        if (p.title == title) return p;
    return std::nullopt;  // 明确表示"没有找到"
}

// 调用方
if (auto result = find_by_title("Attention"); result) {
    std::cout << result->year << '\n';  // 安全——你检查了
}
// 如果忘了检查就直接用 *result，会抛异常——比解引用空指针更可控
```

`std::expected`（C++23，在此之前可以用 `tl::expected` 或 `boost::outcome`）更进一步——它携带**为什么失败**的信息：

```cpp
std::expected<Paper, std::string> parse_line(const std::string& line) {
    if (line.empty()) return std::unexpected("empty line");
    // ...
    return paper;
}
```

这比 `throw` 更适合“预期中可能失败的操作”（文件不存在、格式不匹配、网络超时），因为调用方的处理路径在类型层面可见。

## $\rm \S \, 15.4$ 模板进阶：比 `vector<int>` 更进一步

### $\rm \S \, 15.4.1$ 变参模板

你在 OJ 上用过 `vector<int>` 和 `map<string, int>`。模板还可以写成接受任意数量的类型参数：

```cpp
template<typename... Args>
auto make_paper(Args&&... args) {
    return Paper{std::forward<Args>(args)...};
}
```

模板元编程在 C++ 中深到可以写编译期计算；日常工程中你更多是**使用**模板库（STL、Boost、Eigen），而不是编写复杂的模板。

### $\rm \S \, 15.4.2$ Concepts（C++20）：约束模板参数

模板报错出了名的难读。一个拼错的模板参数可能产生几百行错误信息。Concepts 解决这个问题：

```cpp
template<typename T>
concept Numeric = std::is_arithmetic_v<T>;

template<Numeric T>
T add(T a, T b) { return a + b; }

add(1, 2);        // OK
add("a", "b");    // 编译错误，但信息清晰："const char* 不满足 Numeric"
```

Concepts 在库代码中越来越普遍。作为库的**使用者**，你不需要定义 Concepts，但遇到 `requires` 关键字和简洁的错误信息时，知道这是 C++20 Concepts。

### $\rm \S \, 15.5.2$ 测试框架

在 OJ 上测试 = 提交评测。工程中的测试是一个独立的构建产物：

```cpp
// test_parser.cpp — 使用 Google Test（gtest）框架
#include <gtest/gtest.h>
#include "paper/parser.hpp"

TEST(ParserTest, ParseValidLine) {
    auto paper = paper::parse_line("\"Attention Is All You Need\" (2017)");
    EXPECT_EQ(paper.title, "Attention Is All You Need");
    EXPECT_EQ(paper.year, 2017);
}

TEST(ParserTest, EmptyLineThrows) {
    EXPECT_THROW(paper::parse_line(""), std::invalid_argument);
}
```

编译时同时构建 `paper-parser` 和 `paper-parser_test`。每次改完代码运行测试——不需要等 OJ 的排队延迟，0.1 秒就知道结果。

| 框架 | 特点 |
|---|---|
| **Google Test**（gtest） | 最广泛使用，工业标准 |
| **Catch2** | 单头文件，语法更现代 |
| **doctest** | 极轻量，编译速度最快 |
| **Boost.Test** | Boost 生态的一部分 |

### $\rm \S \, 15.5.3$ 静态分析与格式化

[编辑器、IDE 与调试器](../02-终端与工具/05-编辑器IDE与调试器.md)中介绍了格式化和静态检查的概念。C++ 生态的具体工具：

| 工具 | 类型 | 一句话 |
|---|---|---|
| **clang-tidy** | 静态分析 | 检查常见错误、风格问题和性能隐患（如“用 `const&` 替代值传递”） |
| **clang-format** | 格式化 | 统一代码风格，保存时自动运行 |
| **cppcheck** | 静态分析 | 不需要编译就能检查，适合 CI 中的快速扫描 |
| **include-what-you-use** | 头文件优化 | 分析并建议删除不需要的 `#include`、添加缺失的 |
| **SonarQube** | 代码质量平台 | 持续监控技术债务，多语言支持 |
| **Compiler Explorer**（godbolt.org） | Web | 在线查看你的 C++ 代码编译后的汇编——理解编译器做了什么 |

### $\rm \S \, 15.5.4$ 性能分析

[计算机硬件速通](../03-计算机系统/10-计算机硬件速通.md)中讨论过“测量之前不要优化”。具体怎么测量：

| 工具 | 类型 | 一句话 |
|---|---|---|
| **perf**（Linux） | 采样分析器 | `perf record ./my_program && perf report`——看 CPU 时间花在哪些函数上 |
| **gprof** | 插桩分析器 | 编译时加 `-pg`，运行时记录调用次数和耗时 |
| **Valgrind/Callgrind** | 模拟分析器 | 精确但慢 10-20 倍，适合深入分析 |
| **FlameGraph** | 可视化 | 把调用栈可视化为火焰图——横向越宽 = 耗时越多 |
| **Tracy**（github.com/wolfpld/tracy） | 实时 GUI | 帧级性能分析，游戏和实时应用的首选 |

## $\rm \S \, 15.6$ 从 C++ 看其他系统语言

你在竞赛中只用 C++。工程中还有其他选择，各有偏重：

| 语言 | 与 C++ 的关系 | 核心取舍 |
|---|---|---|
| **C** | C++ 的前身 | 没有类/模板/RAII，操作系统和嵌入式的主力 |
| **Rust**（rust-lang.org） | C++ 的竞争者 | 编译期保证内存安全（无悬垂指针、无数据竞争），包管理器 Cargo 是标杆 |
| **Zig**（ziglang.org） | C 的竞争者 | 语法比 C 更一致，编译期执行任意代码，交叉编译极简 |
| **Go**（go.dev） | 不同方向 | 极简语法、goroutine 轻量并发、超快编译，适合网络服务和 CLI 工具 |
| **Carbon**（实验性） | Google 的 C++ 继任者 | 完全互操作，渐进迁移现有 C++ 代码库 |

> 知道它们存在、各在什么场景下被选择，比现在就学会所有语言更重要。如果你未来做高性能网络服务，Go 或 Rust 值得了解；做操作系统或嵌入式，C 和 Zig 是首选；继续深耕 C++ 本身，也足够整个职业生涯使用。

## $\rm \S \, 15.7$ 动手实践

### 实践一：把单文件程序重构为多文件

1. 把你之前在 OJ 上写的一个 200 行的 C++ 程序，按头文件/源文件拆分。
2. 创建一个 `CMakeLists.txt`。
3. 在 `build/` 目录中构建并运行。
4. 有意在头文件中写一个错误，观察编译错误是否指向了正确的行。

### 实践二：用智能指针替代裸指针

1. 找一段使用 `new`/`delete` 的代码。
2. 用 `std::make_unique` 替换，删除 `delete`。
3. 用 `-fsanitize=address` 编译运行，确认没有泄漏。

### 实践三：写一个 Google Test

1. 安装 Google Test（vcpkg 或系统包管理器）。
2. 为你的 parser 函数写 3 个测试用例：正常输入、空输入、格式错误输入。
3. 构建并运行测试。
4. 故意破坏一个实现，观察哪个测试失败了。

## $\rm \S \, 15.8$ 总结

- **多文件 + CMake** 是工程 C++ 的起点。头文件声明接口，源文件包含实现，构建系统管理编译过程。
- **RAII** 把资源（内存、文件、锁）绑定到对象生命周期。智能指针替代裸 `new`/`delete`。
- **移动语义** 避免不必要的深拷贝。`auto` 和 Lambda 减少样板代码。`std::optional` 让“可能没有值”在类型层面可见。
- **模板** 不只 `vector<int>`。Concepts（C++20）让模板错误信息更友好。
- **C++ 工程工具有 vcpkg/Conan（包管理）、gtest/Catch2（测试）、clang-tidy/clang-format（静态分析）、perf/FlameGraph（性能）**。

### 自测答案 · 关键概念回顾
1. 编译速度（改一个 .cpp 只重编译它再链接）、接口与实现分离（使用方只需头文件）、物理隔离避免依赖循环。
2. 不是。CMake 是构建系统：它生成 Makefile 或工程文件，再调用真正的编译器；`cmake ..` 做配置生成构建文件，`cmake --build .` 才实际编译。
3. 构造函数获取资源、析构函数释放资源，把资源生命周期绑定到对象生命周期——即使异常也保证释放；裸 delete 依赖人记得调用，漏掉就泄漏，智能指针由编译器保证释放。
4. 避免不必要的深拷贝（如返回大容器时把内部指针“窃取”到新对象，$\mathcal{O}(1)$ 完成）；std::move 把左值转换为右值引用，发出“可以搬走内部数据”的信号，源对象进入有效但未指定状态。
5. “可能没有值”成为类型的一部分：调用方必须检查（忘了检查会抛异常而不是静默错误），也不会和合法的 -1 混淆。

### 自测答案 · 应用与辨析
6. 默认用 unique_ptr（独占所有权、零额外开销）；只有确实需要多个所有者共享同一对象时才用 shared_ptr（引用计数），循环引用用 weak_ptr 打破。
7. 用 vcpkg 或 Conan：如 `vcpkg install nlohmann-json`，然后在 CMakeLists.txt 中 `find_package` 并链接；依赖就随构建系统一起解析和安装。
