# $\rm Chapter \, 42$ 移动操作系统：iOS 与 Android 的本质区别

> 你手机上一个 App 有 iOS 版和 Android 版，它们看起来一模一样，但背后的代码是两套完全不同的程序——用不同的语言写、在不同的系统上跑、通过不同的商店分发。一个 iOS App 的安装包不能直接装到 Android 上，反着也不行。这不是因为“苹果和 Google 打架”，而是两套操作系统从内核、到应用框架、到安全模型，有着根本性的不同。

## $\rm \S \, 42.1$ 内核与底层架构

### $\rm \S \, 42.1.1$ 两个操作系统，两个内核

[操作系统、进程与线程](../03-计算机系统/11-操作系统进程与线程.md)中你知道了操作系统内核管理硬件、调度进程、处理系统调用。移动操作系统的内核：

- **Android** 内核基于 **Linux**——和服务器上跑的 Linux 同源，但 Android 长期维护自己的分支（厂商补丁 + Android 专属特性），不能逐项对应。你在服务器上学过的概念大多还在：进程调度、虚拟内存、ext4/f2fs 等文件系统；差异的典型例子是内存——Android 默认用 zram 做内存压缩，而不是桌面服务器常见的 swap 分区。Android 在 Linux 之上加了自己的应用框架和运行时。
- **iOS** 内核是 **XNU**（X is Not Unix），和 macOS 是同一个内核。XNU 是 Mach 微内核 + FreeBSD 内核组件的混合体。iOS 和 macOS 共享内核和大量底层框架，但 UI 层分开。

为什么 Android 选 Linux？2005 年 Google 收购 Android 时，Linux 已经有成熟的驱动生态、内存管理和网络栈——直接借用可以省下几百万行代码和维护成本。为什么苹果用 XNU？XNU 是苹果从 NeXT 继承的（1997 年收购），已经深度集成到苹果的所有操作系统产品线中。

### $\rm \S \, 42.1.2$ 运行时环境

- **Android** 的应用主要用 **Java/Kotlin** 编写，编译为 **DEX 字节码**（`.dex`），在 **ART**（Android Runtime）上运行。ART 是 AOT 与 JIT 的混合：安装时先做一部分预编译，运行中 JIT 执行并记录热点，设备空闲时再按使用情况优化编译。这和 Java 在服务器上“先解释、热点再 JIT”的思路相近，但多了安装期与空闲期的编译。
- **iOS** 的应用用 **Swift / Objective-C** 编写，编译为**原生 ARM 机器码**。没有中间字节码层、没有虚拟机——和 C++ 程序的编译和执行一样直接。这意味着 iOS App 通常启动更快、内存占用更小，但代价是 CPU 指令集换代（如 32 位 → 64 位）时，开发者必须重新编译并发布新版本；字节码方案则由运行时在新设备上重新编译执行。

### $\rm \S \, 42.1.3$ HAL：硬件适配层

Android 通过 **HAL**（Hardware Abstraction Layer，硬件抽象层）来屏蔽不同手机厂商的硬件差异——GPS 芯片、摄像头传感器、指纹识别器。HAL 为每类硬件定义统一的接口约定（相机、定位等各有自己的标准调用），每个硬件厂商实现自己的 HAL 驱动。三星手机的摄像头 HAL 和 Google Pixel 的摄像头 HAL 是两套代码，但上层应用调用的是同一套接口。

iOS 没有这个需求——苹果自己设计芯片（A 系列、M 系列）、控制所有传感器选型、自己写所有驱动。这给了苹果更深入的软硬件整合空间，但续航差距不能只归给驱动：后台模型（§42.2.3）和芯片设计同样在起作用。对开发者的后果是明确的：你不可能在非苹果设备上合法运行 iOS。

## $\rm \S \, 42.2$ 应用沙盒与权限模型

### $\rm \S \, 42.2.1$ 每个 App 都是囚犯

两个系统都使用了**沙盒**（sandbox）机制——每个 App 运行在自己的文件系统区域内，不能访问其他 App 的数据。它在[文件系统与权限](../02-终端与工具/03-文件系统路径与权限.md)的用户/组权限之上叠加了一层：iOS 上所有 App 都以同一个系统用户运行，靠沙盒策略互相隔离；Android 则给每个 App 分配独立的 Linux UID，让内核的用户权限模型直接发挥作用。

- **iOS 沙盒**更严格：每个 App 有自己的 `Documents/`、`Library/`、`tmp/` 目录，App 之间无法直接访问对方的文件。要共享数据必须通过系统提供的“分享扩展”（Share Extension）或 App Group（同一开发者的 App 间共享容器）。
- **Android 沙盒**在 Linux 用户隔离基础上实现：每个 App 分配一个独立的 Linux UID。从[操作系统、进程与线程](../03-计算机系统/11-操作系统进程与线程.md)的角度看，`ps` 输出中每个 App 进程都有自己的 UID——和服务器上为每个服务创建独立账户是同一个原理。

### $\rm \S \, 42.2.2$ 权限申请

你一定见过这种弹窗：“XXX 想访问你的相册”——这就是系统权限申请的 UI。底层机制：

| | iOS | Android |
|---|---|---|
| 权限请求时机 | App 首次访问时弹窗，可选允许、仅本次或拒绝 | 安装包中声明需要的权限（manifest），运行时按需弹窗 |
| 权限粒度 | 按用途拆分（相册、相机、位置、麦克风等）；位置可选精确或大致，照片可选仅选中项 | 精确位置 vs 粗略位置、前台 vs 后台、仅本次授权 |
| 拒绝后 | App 必须处理被拒绝的情况（上架审查会检查） | 取决于开发者写没写处理逻辑，可能崩溃或功能缺失 |

### $\rm \S \, 42.2.3$ 后台执行限制

在[操作系统、进程与线程](../03-计算机系统/11-操作系统进程与线程.md)中你学过时间片、前台/后台。移动操作系统对“后台”的定义远比桌面严格——为了节省电量：

- **iOS 后台极度受限**：App 进入后台后只有短暂的时间（通常约 30 秒）完成收尾工作，之后被**冻结**——不再消耗 CPU、不再执行代码。只有特定场景（音频播放、导航、VoIP 通话）可以通过特殊 API 申请后台运行。这是 iOS 续航表现通常更好的重要原因之一：后台 App 几乎不耗电。
- **Android 后台较宽松，但有明确限制**：长时间运行的任务要申请**前台服务**（必须显示常驻通知），普通后台 Service 从 Android 8 起受严格限制，系统还会在 Doze 等低电耗模式下推迟任务。所以“永不停止的后台进程”要在通知栏可见的代价下才成立。同一个即时通讯 App 的推送到达时间可能不同：iOS App 无法自己维持长连接，只能等 APNs 唤起；Android 上应用可以用前台服务或高优先级消息保持更及时的通知，代价是耗电与常驻通知。快慢还受网络和厂商省电策略影响，不是固定规律。

## $\rm \S \, 42.3$ 应用分发

### $\rm \S \, 42.3.1$ App Store vs 开放生态

- **iOS**：App 主要经 **App Store** 分发，上架必须通过苹果的人工+自动审查（审核代码质量、内容合规、隐私政策、收费模式）。这显著降低了恶意软件进商店的概率，但也意味着苹果可以拒绝任何不符合其政策的应用。（例外：欧盟按《数字市场法》自 2024 年起允许第三方应用市场。）
- **Android**：**Google Play** 是主力商店，但不是唯一渠道。用户可以安装第三方商店（如三星 Galaxy Store、华为应用市场），也可以直接下载 `.apk` 文件手动安装（“侧载” sideloading）。这给了用户更多自由，也让恶意软件更容易通过商店之外的渠道传播——Google Play Protect 会扫描已安装 App，但覆盖率和 iOS 的商店审查不可比。

### $\rm \S \, 42.3.2$ 编译目标

iOS App 编译为 ARM64 原生代码，打包成 `.ipa`（本质是一个压缩包）。Android App 编译为 DEX 字节码 + 可选的原生库，打包成 `.apk` / `.aab`。一个 Android App 可以有多个架构版本（ARM64、ARM32、x86_64），Google Play 会自动匹配用户的设备架构；iOS 设备则统一是 ARM64，不需要为不同架构分别打包。

## $\rm \S \, 42.4$ 跨平台开发：一次写，多端跑

既然 iOS 和 Android 是两套完全不同的系统，怎么有人能用一套代码同时发布两个平台？

| 框架 | 语言 | 原理 | 原生体验程度 |
|---|---|---|---|
| **React Native**（Meta） | JavaScript | JS 代码通过“桥”调用原生 UI 组件 | 中——UI 是原生的，但 JS 与原生之间的调用有额外开销（React Native 正在改进这一点） |
| **Flutter**（Google） | Dart | 完全自绘——Skia 引擎直接画像素，不调用原生 UI 组件 | 较高——多数 UI 场景接近原生，复杂原生控件与平台集成仍有差距 |
| **Kotlin Multiplatform**（JetBrains） | Kotlin | 业务逻辑共享，UI 层各自原生写 | 原生——UI 层还是各自平台代码 |
| **SwiftUI + shared Swift** | Swift | 实验性——Swift 在非苹果平台上的支持有限 | N/A |

**Flutter 的“自绘”选择**：React Native 通过桥接调用 iOS 的 `UITextField` 或 Android 的 `EditText` 来显示输入框。Flutter 不用——它在屏幕上直接画一个输入框，包括光标、文字渲染、键盘弹出动画全部自己实现。代价是安装包更大：引擎会给每个 CPU 架构增加数 MB（调试构建可达几十 MB），简单 App 的包体因此明显大于纯原生；好处是 UI 在所有平台上像素一致。

## $\rm \S \, 42.5$ 动手实践

### $\rm \S \, 42.5.1$ 实践一：查看 Android 进程隔离

前置：一台 Android 手机（或模拟器），在设置中启用开发者选项与 USB 调试；电脑上装好 `adb`（Android SDK Platform Tools，用第 9 章 §9.3 的包管理器安装）。

1. 连接手机并确认授权：`adb devices`。预期输出：列出你的设备序列号，状态为 `device`（显示 `unauthorized` 时看手机屏幕点允许）。
2. `adb shell ps -A -o USER,PID,NAME | grep com.`。预期输出：每个正在运行的 App 一行，`USER` 列是它自己的 UID（形如 `u0_a123`）而不是 `root`——这就是 Linux UID 隔离。
3. `adb shell dumpsys package com.android.chrome | grep userId=`。预期输出：输出 `userId=10xxx`，与第 2 步 Chrome 进程的 UID 一致。
4. `adb shell ls -l /data/data/`。预期输出：未 root 的量产机上返回 `Permission denied`——这本身就是沙盒在起作用；想查看某个 App 的私有目录需要 root，或该 App 是 debuggable 的（用 `run-as <包名>`）。
5. 清理：`adb kill-server` 结束连接；如果只是为了实验开启的 USB 调试，可在开发者选项中关掉。

### $\rm \S \, 42.5.2$ 实践二：对比 App 权限

前置：一部 iOS 或 Android 手机（两个系统都有最好）；不改动任何权限设置也能完成观察。

1. iOS：设置 → 隐私与安全性（或对应的权限分类）。预期输出：看到按权限类型分组的 App 列表，点进某一项能看到每个 App 的授权状态。
2. Android：设置 → 应用 → 权限管理。预期输出：看到按权限类型分组，可切换按“权限”或按“应用”查看。
3. 对比同一个 App（如微信或 Chrome）在两个系统上申请的权限列表。成功标志：能指出至少一处粒度差异（如位置：Android 有前台/后台之分，iOS 有精确/大致之分）。
4. 清理：只观察、不修改；若为实验改过某个授权，改回原状。

### $\rm \S \, 42.5.3$ 实践三：Flutter 体验

前置：按 flutter.dev 的官方步骤安装 Flutter SDK；`flutter doctor` 没有致命问题（Android toolchain / Xcode 至少一项可用）；一台连接的手机或已启动的模拟器。`flutter create` 会联网拉取依赖。

```bash
flutter create hello_mobile
cd hello_mobile
flutter run        # 在连接的手机或模拟器上运行
```

预期输出：`flutter create` 末行输出 `All done!`；`flutter run` 后设备上启动计数器示例 App，终端输出运行目标与热重载相关提示。修改 `lib/main.dart` 中的文字并保存——预期界面文字**立刻**变化，终端出现 hot reload 输出（不同 Flutter 版本措辞不同），不需要重新编译安装。

清理：在 `flutter run` 的终端按 `q` 退出；不再需要这个练习项目时，用 `pwd` 确认自己在 `hello_mobile` 外面后删除该目录。

## $\rm \S \, 42.6$ 总结

- Android 内核是 Linux，iOS 内核是 XNU（和 macOS 共享）。Android 用 HAL 适配不同硬件，iOS 自己控制全栈。
- 两个系统都用沙盒隔离 App。iOS 后台严格冻结，Android 后台相对宽松但限制明确——后台模型是电池续航差异的重要原因之一（芯片设计也在起作用）。
- iOS 的 App 主要经 App Store 分发（欧盟按《数字市场法》允许第三方市场，属例外），Android 支持侧载和第三方商店。
- 跨平台框架中，Flutter（自绘）和 React Native（原生桥接）是主流选择。

## $\rm \S \, 42.9$ 本章自测答案

> 先闭卷作答本章“关键概念回顾”与“应用与辨析”，再核对以下答案。

### $\rm \S \, 42.9.1$ 自测答案 · 关键概念回顾
1. Android 使用 Linux 内核；iOS 使用 XNU（Mach + FreeBSD 组件，和 macOS 共享）。
2. iOS 的沙盒是独立于用户权限的文件系统隔离（每个 App 私有的 Documents/Library/tmp）；Android 的沙盒基于 Linux UID 隔离（每个 App 分配一个独立 Linux 用户 ID）。
3. React Native 通过桥接调用原生 UI 组件（iOS UIKit、Android Views）；Flutter 完全自绘——Skia 引擎直接画像素，不调用系统 UI 组件。

### $\rm \S \, 42.9.2$ 自测答案 · 应用与辨析
4. iOS App 进入后台后被冻结，无法自己维持长连接，只能等 APNs 唤起（系统按优先级调度）；Android 上应用可以用前台服务或高优先级消息保持更及时的通知，代价是耗电与常驻通知。实际快慢还受网络和厂商省电策略影响，不是固定规律。
5. `.ipa` 和 `.apk` 都是压缩包：`.ipa` 里装的是 ARM64 原生可执行文件（编译后的 Swift/Obj-C），直接由 CPU 执行；`.apk` 里装的是 DEX 字节码 + 可选的原生库，由 ART Runtime 执行。不同的指令集、不同的系统 API、不同的打包格式——完全没有互换性。
