# $\rm Appendix \, I$ 数据可靠性、备份恢复与生产事故演练

> 第 27 章讲了数据库备份的基本操作。但“备份成功”和“能恢复”之间有一条巨大的鸿沟——直到你真正尝试恢复的那一刻，你才知道备份文件是否完整、恢复流程是否正确、恢复后的数据是否能用。本章补上这条鸿沟。

你应该已经理解 SQL 基本操作和数据库的 `pg_dump`/`.dump` 等备份命令（[第 27 章](../07-应用开发/27-数据库基础.md)）。

## $\rm \S \, I.1$ 备份成功 ≠ 可恢复

### $\rm \S \, I.1.1$ 备份文件可能悄悄损坏

一个真实的案例：团队每天凌晨 3 点自动备份数据库到 NAS。三个月后磁盘故障，需要恢复。打开备份文件——文件大小正常，但中间有几段数据因为 NAS 的静默数据损坏（silent data corruption）变成了全零。备份跑了三个月，没有一次被验证过。

```bash
# 备份后立即校验
pg_dump papers > backup.sql
sha256sum backup.sql > backup.sql.sha256

# 恢复前校验
sha256sum -c backup.sql.sha256  # 校验通过才恢复
```

校验只能证明“文件与备份时记录的哈希一致”——它挡得住传输、存储途中的损坏，挡不住“备份的那一刻内容就已经坏了或不完整”（比如备份时正在运行的事务没处理完）。后者需要**恢复演练**。

### $\rm \S \, I.1.2$ Restore Drill：定期练习恢复

至少**每季度一次**，在隔离环境中实际恢复一次备份，并验证：
- 应用能正常启动并连接到恢复后的数据库
- 关键查询返回正确结果
- 最近的业务数据在备份中（检查最大 ID、最新时间戳是否在合理范围内）

如果从来没练过恢复——你**没有备份**。你只有一堆“希望有用的文件”。

---

## $\rm \S \, I.2$ 3-2-1 备份原则

这是数据保护领域最经典的经验规则：

- **3** 份数据副本（一份原始 + 两份备份）
- **2** 种不同的存储介质（如本地 SSD + 云对象存储——防止同一类介质同时故障）
- **1** 份**异地**备份（物理距离——防止火灾、水灾、机房断电同时毁掉所有副本）

对于个人项目或小团队：

| 副本 | 位置 | 介质 |
|------|------|------|
| 原始 | 服务器本地 NVMe | SSD |
| 备份 1 | 同机房 NAS（快速恢复） | HDD RAID |
| 备份 2 | 云对象存储（异地） | 云存储（S3/OSS/B2） |

## $\rm \S \, I.3$ RPO 与 RTO：用数字定义恢复目标

| 指标 | 全称 | 含义 | 例子 |
|------|------|------|------|
| **RPO** | Recovery Point Objective | 能容忍丢失多少数据（以时间为单位） | RPO = 1 小时 = 最多丢最近 1 小时的论文数据 |
| **RTO** | Recovery Time Objective | 从故障到恢复服务，最长容忍多久 | RTO = 4 小时 = 从磁盘故障到网站恢复，必须在 4 小时内 |

RPO 决定了备份频率：RPO = 1 小时 → 至少每小时备份一次。RTO 决定了恢复流程的复杂度：RTO = 10 分钟 → 必须有热备或自动故障转移。

> **经验规则**：RPO 和 RTO 不需要追求零——需要的是**明确且团队知道**。没有定义 RPO/RTO 的“重要数据”对业务来说不是重要数据。

## $\rm \S \, I.4$ Schema Migration：改表结构的安全方式

### $\rm \S \, I.4.1$ 为什么“停机维护”不总是可行的

加一个列、删一个索引——听起来简单。但在生产数据库中，`ALTER TABLE` 可能需要锁表。对于一个千万行的表，加索引可能需要 20 分钟——这 20 分钟内写入操作全部阻塞。

### $\rm \S \, I.4.2$ Expand-Migrate-Contract 模式

```text
Phase 1: Expand（扩展）
  - 加新列（允许 NULL）
  - 同时写入旧列和新列
  - 旧代码继续工作（它只读旧列）

Phase 2: Migrate（迁移）
  - 后台填充新列的数据
  - 部署新代码（同时读新旧列，优先新列）

Phase 3: Contract（收缩）
  - 确认所有查询都不再依赖旧列
  - 删除旧列
```

每一阶段都可**独立回滚**——如果在 Phase 2 发现新代码有 bug，回滚到 Phase 1 的旧代码即可，数据没有丢失。

## $\rm \S \, I.5$ 故障演练：Chaos Engineering 的最小版

### $\rm \S \, I.5.1$ 不是“随机搞破坏”

Chaos Engineering 的核心方法论：
1. **定义“稳态”**——系统的正常行为是什么？（如 API P99 延迟 < $200 \, \text{ms}$，错误率 < $0.1\%$）
2. **假设“某组件故障时稳态仍然成立”**——如果数据库主库宕机，自动故障转移 + 只读副本应保证服务可用
3. **设计实验**——在**可控、可观测、可立即终止**的条件下注入故障
4. **验证或推翻假设**——和对照组（没有注入故障的基线）对比

### $\rm \S \, I.5.2$ 第一个 Chaos 实验

不搞宕机——从最简单的开始：

```bash
# 实验：如果论文管理器 API 的数据库连接断开 30 秒，会发生什么？
# 注入方式：用 iptables 临时阻断到数据库端口的流量
sudo iptables -A OUTPUT -p tcp --dport 5432 -j DROP
sleep 30
sudo iptables -D OUTPUT -p tcp --dport 5432 -j DROP

# 观察：
# - API 返回了什么？（5xx？超时？）
# - 恢复后 API 是否自动重连？
# - 这 30 秒内的请求是丢失了还是重试成功了？
```

不是为了“搞死系统”——是为了发现“系统在部分故障时的真实行为”，然后决定是否修复。

> ⚠️ 演练前先把删除命令记在手上：中途 `Ctrl+C`、崩溃或被 kill 打断时，最后那条 `-D` 不会执行，那条 DROP 规则会留在系统里继续挡流量（用 `sudo iptables -S OUTPUT` 可以确认清没清干净）。优先在测试机或容器里做，别在生产机上第一次试。

## $\rm \S \, I.6$ 关键概念回顾

1. 3-2-1 备份原则的每一项分别防御什么风险？
> 3 份副本防单点故障，2 种介质防同一类存储的共性故障，1 份异地防物理灾难（火灾、水灾）。

2. RPO 和 RTO 分别回答什么问题？
> RPO：最多丢多少数据（决定备份频率）；RTO：最多停多久（决定恢复流程和架构冗余）。

3. Expand-Migrate-Contract 模式为什么比“停机、改表、重启”安全？
> 每一步都可独立回滚——不需要“赌这次变更不出问题”。新老代码和数据在迁移期间共存。

---

## $\rm \S \, I.7$ 应用与辨析

1. “我们每天备份，所以数据安全”——缺失了什么？
> 至少缺失：备份文件是否定期校验（文件完整性）、是否定期恢复演练（内容可用性）、是否有异地备份（物理灾难防护）、是否定义了 RPO/RTO（业务期望）。

2. 数据库迁移工具（如 Alembic/Flyway）解决了什么问题？
> 版本化管理 schema 变更——像 Git 管理代码一样管理数据库结构。每次变更都有 up（执行）和 down（回滚）脚本，可追踪、可复现、可在不同环境（开发/测试/生产）一致应用。注意 down 脚本并不总是自动存在（不少工具和团队只写 up），回滚脚本本身也要演练过才算数。
