# $\rm Chapter \, 3$ 微观优化：分支、展开与 SIMD

> **本章假设你已经会**
>
> 1. 计时纪律：单调钟、预热后多轮取最速、空汇编屏障把结果钉进计时区，见本册 §1.2、§1.3。
> 2. 会用 `gcc -S` 读出循环的真身，认得五种寻址模式与序言尾声，见本册 §2.2。
> 3. 真依赖解不开、名字依赖靠寄存器重命名解开，这是指令级并行的本质，见《计算机系统结构》§4.2、§4.3。
> 4. 分支误预测的 CPI 账：分支频率 × 误预测率 × 误预测代价，见《计算机系统结构》§3.3。
> 5. 一次访存有两个价签（延迟与带宽），工作集大小决定你站在存储金字塔哪一层，见本册 §2.1、§2.4。

第 2 章看的是「数据在哪」，本章看「指令怎么跑」。竞赛生涯里你大概背过一串微优化口诀：分支能省则省、循环要展开、位运算比乘除快。本章的立场是全册心智模型：**性能是测出来的假设-验证循环**，每条口诀先当假设，测量来审判。审判结果有好有坏：有的口诀在这台机器上值 19 倍，有的只值 1.5%，有的根本轮不到你出手。本章五组实验的工作负载统一为 ${N = 2^{20}}$ 个 int32 元素、值域 0～255 均匀（xorshift64* 生成，种子 20261107），每轮对同一数组扫描 ${R = 20}$ 遍，预热 2 轮加计时 7 轮取最速，全部在 WSL2（Ubuntu 24.04，gcc 13.3.0）真跑，CPU 与第 2 章同一台（Intel Core Ultra 7 255H，进程绑到 0 号核），折合拍按本册 §2.4 标定的 2.6 GHz。本章还新增一条测量纪律：**同一进程内把所有版本轮转交错计时**，每轮依次测一遍全部配置再进下一轮，而不是把一个版本连测七轮再换下一个。这条纪律是踩坑换来的：第一版实验按顺序连测，转换循环的 `-O3` 自动向量化版测出 0.698 ns/元素，比 `-O2` 标量版还慢一倍；改成交错后它稳定回到 0.23，前后差异全部来自测量顺序引起的频率漂移，代码一字未改。脚本与完整输出见 `expPE03/result.txt`，正文数字取自其中最后一次正式运行；两次运行间绝对值漂移可达两成，比值稳定，所以结论全部建立在比值上。

## $\rm \S \, 3.1$ 分支预测：最贵的是走错方向

任务很日常：把数组里所有 ${\ge 128}$ 的元素求和。C 的直白写法是一个 if：

```c
long sum_branchy(const int *a, long n) {
    long s = 0;
    for (long i = 0; i < n; i++)
        if (a[i] >= 128) s += a[i];
    return s;
}
```

按 §1.3 的教训，这个函数放在独立编译单元里返回结果由驱动累加，编译器删不掉它。但第一个测量就出了岔子：同样的代码，gcc 默认在 `-O2` 下把它编译成了**没有分支**的代码。这个优化叫 if 转换（if-conversion）：把「条件成立才做」改写成一条**条件传送**（conditional move，x86 指令名 `cmov`），两个值都算出来，按条件挑一个，指令本身不跳转。实测证据：默认旗标下 `if` 版与三目版 `s += (a[i] >= 128) ? a[i] : 0;` 编出的循环体逐条相同，都含 `cmovg`；想研究分支预测本身，必须显式关掉它，单独编译：

```bash
# Shell/WSL，当前目录有 branchy.c；产物 branchy.o，无副作用
# -fno-tree-vectorize 禁自动向量化，-fno-if-conversion 禁 if 转换
gcc -O2 -march=native -fno-tree-vectorize \
    -fno-if-conversion -fno-if-conversion2 -c branchy.c
```

关掉 if 转换后，分支版主循环的真身如下（`objdump -d`，读法口径同本册 §2.2）：

```text
.L2:    movslq (%rdi),%rax     # 取 a[i]，符号扩展成 64 位
        cmp    $0x7f,%eax      # a[i] <= 127 ？
        jle    .Ltail          # 是：跳过加法，被预测的正是这一跳
        add    %rax,%rdx       # 否则：累加进 s
.Ltail: add    $0x4,%rdi       # 指针前进一个 int
        cmp    %rcx,%rdi
        jne    .L2
```

循环体里那条 `jle` 就是全部戏份所在：排序数据下它先连续不跳、再连续跳，一次不错；随机数据下每两个元素就要赌一次，赌错一次冲掉整条流水线（《计算机系统结构》§3.3 的控制冒险）。于是得到四个受测版本：分支版与 cmov 版各配两种数据（原始随机序、升序排序后），同一循环、同一元素集合，唯一变量是分支的可预测性。结果（ns/元素，越低越快）：

| 版本 | 随机序数据 | 排序后数据 |
| --- | --- | --- |
| 分支版 | 6.52 | 0.34 |
| cmov 版 | 0.78 | 0.71 |

三条结论，每条都是一次假设的判决。第一，分支被预测对时它是全场冠军：0.34 对 cmov 的 0.71，快 2.1 倍。原因看得见：排序后数组前半段连续「不取」、后半段连续「取」，分支一次都不走错，循环里每元素只付一次比较加一次不跳的跳转；cmov 却每元素都无条件把加法挂在累加链上，链更长。第二，分支走错时它是灾难：随机序下 6.52，是自己排序版的 19.4 倍。第三，cmov 是保险而不是提速：它的耗时几乎与数据分布无关（0.71 对 0.78），赌的是「两个值都算」的固定成本，换来了「永不走错」。用排序版当无误预测基线，能反推出这台机器上每次误预测的价格：

$$
C_{\text{pen}} = \frac{T_{\text{rand}} - T_{\text{sorted}}}{p_{\text{miss}}} = \frac{6.5217 - 0.3370}{0.5}\,\text{ns} \approx 12.4\,\text{ns}
$$

读法：$T_{\text{rand}}$、$T_{\text{sorted}}$ 是两种数据下的每元素耗时，${p_{\text{miss}} = 0.5}$ 是均匀随机数据的误预测率，商出来的是每次误预测额外付出的时长，约 12.4 ns，折合约 32 拍。这个数比教科书常引的 15～20 拍偏大，多出的部分含 WSL2 虚拟化与前端重取指的账，量级是对的：与《计算机系统结构》§3.3 的 CPI 公式对照，误预测率从 0 涨到 0.5，这段循环每元素多付约 16 拍，正是表中 19.4 倍差距的来源。

白话：分支像岔路口的交警，路牌有规律时他挥手比你思考快；路牌全随机时他每挥错一次，整条流水线排的车队都得掉头。cmov 是不管三七二十一两条路都派一辆车的笨办法，路痴救星，但每单都付双份油钱。

> 本节小结：可预测分支比 cmov 快一倍，不可预测分支比 cmov 慢八倍；cmov 买的是与数据无关的稳定。先问数据有没有规律，再谈要不要分支。

## $\rm \S \, 3.2$ 循环展开：拆的是依赖链

第二个假设来自竞赛圈的常见直觉：「循环要展开，少跳转就快」。先给朴素求和循环量个体温，4 个累加器版本：

```c
long sum_acc4(const int *a, long n) {
    long s0 = 0, s1 = 0, s2 = 0, s3 = 0;
    for (long i = 0; i + 3 < n; i += 4) {
        s0 += a[i]; s1 += a[i + 1];
        s2 += a[i + 2]; s3 += a[i + 3];
    }
    /* 尾巴处理与 s0+s1+s2+s3 合并，略 */
    return s0 + s1 + s2 + s3;
}
```

把累加器个数 $k$ 从 1 扫到 16（16 用 16 个独立命名的标量），实测如下：

| 版本 | ns/元素 | 折合拍 | 相对 $k{=}1$ |
| --- | --- | --- | --- |
| acc1（单累加器） | 0.356 | 0.92 | 1.00× |
| acc2 | 0.230 | 0.60 | 1.55× |
| acc4 | 0.201 | 0.52 | 1.77× |
| acc8s | 0.185 | 0.48 | 1.92× |
| acc16s | 0.193 | 0.50 | 1.84× |

这张表要用两条硬件约束来读。第一条是**真依赖链**（本册 §2.4 的单链追访演示过判据，完整机制见《计算机系统结构》§4.2）：acc1 里 `s += a[i]` 的加法要吃上上一轮的 s，每拍至多消化一个元素，链就是天花板。两版循环体的汇编对比把这件事摆在明面上：

```text
acc1 主循环：                     acc4 主循环（每轮 4 条 load、4 条加法）：
    movslq (%rdi),%rdx                movslq (%rax),%r8
    add    $0x4,%rdi                  add    $0x10,%rax
    add    %rdx,%rax     # 链上加链    add    %r8,%rdx      # 链 1：rdx
    cmp    %rcx,%rdi                  movslq -0xc(%rax),%r8
    jne                               add    %r8,%rdi      # 链 2：rdi
                                      movslq -0x8(%rax),%r8
                                      add    %r8,%rsi      # 链 3：rsi
                                      movslq -0x4(%rax),%r8
                                      add    %r8,%rcx      # 链 4：rcx
                                      cmp    %rax,%r9
                                      jne
```

acc1 只有一条累加链 `rax`，本轮 `add %rdx,%rax` 必须等上轮同一位置的结果；acc4 把 s 拆成 `rdx`、`rdi`、`rsi`、`rcx` 四个互不相干的家伙，四条链在乱序执行引擎（《计算机系统结构》§4.3 的重命名给它撑腰）里并行推进。实测 acc1 落在 0.92 拍，贴住链上限 1 拍（残差在本册 §2.4 标定的时钟漂移带内）；循环开销（指针步进、比较、跳转）与链并行，没有被链放大。第二条约束是取指端的吞吐上限：这台 CPU 每拍能发两条 load，标量求和每元素恰要一条 load，所以无论加多少累加器，每元素 0.5 拍就是地板。两条约束合起来给出下界：

$$
T_k^{\min} = \max\!\left(\frac{L_{\text{add}}}{k},\; w_{\text{load}}\right)
$$

读法：$k$ 条互不依赖的累加链把 1 拍的加法延迟摊薄成 $L_{\text{add}}/k$，${w_{\text{load}} = 0.5}$ 拍/元素是两条 load 端口决定的吞吐地板，瓶颈取较大者。$k{=}1$ 时链说了算（1 拍），${k \ge 4}$ 后端口说了算（0.5 拍），实测 acc4 的 0.52 与 acc8s 的 0.48 拍恰好踩在地板上。acc16s 不再下降，但原因不是直觉里的「寄存器不够」：查汇编，它确有 27 处栈引用（acc4 是 0 处），16 个累加器挤爆了 16 个通用寄存器，部分累加链被赶到栈上；只是此时瓶颈在 load 端口不在链上，溢出恰好没踩到关键路径，代价才只有几个百分点。

所以「循环展开（loop unrolling）」真正的收益不是少跳转，跳转被预测对时近乎免费（§3.1），而是**把一条链拆成 $k$ 条**，给乱序执行引擎喂并行度。它也有代价：代码变长占指令缓存，累加器变多挤占寄存器，而收益在 ${k \ge 4}$ 后归零。顺带一提，等 §3.3 读完你会看到，这个循环连展开都不必手写。

白话：收银台一个队列排到底，是因为找钱的手只有一双、上一单没找完下一单开不了票（依赖链）；开四个窗口（4 个累加器）确实快，但停车场两个入口（load 端口）才是最终瓶颈，开十六个窗口还把员工挤到走廊上办公（溢出），纯属浪费。

> 本节小结：展开的价值在拆依赖链不在省跳转；$k{=}1$ 时链是瓶颈、${k \ge 4}$ 后 load 端口是瓶颈；展开同时倍增累加器，加太多就把值挤回内存。

## $\rm \S \, 3.3$ SIMD：一条指令装八个数

前两节的优化把每元素成本从 7 拍压到 0.5 拍，天花板是「一条指令处理一个数」。AVX2 的 ymm 寄存器宽 256 位，装得下 8 个 int32，一条 `vpaddd` 一拍做完 8 对加法，理论地板 0.125 拍/元素。把同一个求和循环写成五个版本各测一次，这就是本章的主锚点表（加速比分别对 `-O0` 与对 `-O2` 标量版）：

| 版本 | ns/元素 | 折合拍 | vs -O0 | vs -O2 标量 |
| --- | --- | --- | --- | --- |
| 朴素 `-O0` | 2.694 | 7.00 | 1.00× | 0.13× |
| 朴素 `-O2`（自动，未向量化） | 0.349 | 0.91 | 7.72× | 1.00× |
| 手写展开 4 累加器 | 0.195 | 0.51 | 13.79× | 1.79× |
| 朴素 `-O3`（自动向量化） | 0.134 | 0.35 | 20.11× | 2.60× |
| 手写 AVX2 intrinsics | 0.102 | 0.26 | 26.46× | 3.43× |

表里藏着三个发现，每个都先看汇编再下结论。发现一：`-O2` 并没有向量化这个循环，汇编里一条 ymm 指令都没有（gcc 13 的 `-O2` 虽开着自动向量化，用的是「非常保守」的成本模型，对这个归约判定不划算），`-O3` 才肯下手。所以「我开了 -O2 编译器会向量化」是个需要拿汇编验证的假设，不是事实。发现二：`-O3` 自动向量化后的代码比手写版慢三成，原因是语义。源码是 `long s += int a[i]`，C 的语义要求每次加法先把 int 符号扩展成 64 位再加，编译器忠实照办，自动向量化版的向量循环长这样：

```text
.L:     vpmovsxdq (%rax),%ymm1         # a[i..i+3] 符号扩展成 4 个 int64
        vmovdqu  (%rax),%ymm3          # 整块 32 字节（8 个 int32）取回
        add      $0x20,%rax
        vpaddq   %ymm0,%ymm1,%ymm1     # 4 条 64 位通道相加
        vextracti128 $0x1,%ymm3,%xmm0  # 取出高 128 位（后 4 个 int32）
        vpmovsxdq %xmm0,%ymm0          # 同样扩展成 int64
        vpaddq   %ymm1,%ymm0,%ymm0
        cmp      %rcx,%rax
        jne      .L
```

每 8 个元素要付 2 次扩展加 2 次 4 通道加法，真正的 8 通道 `vpaddd` 一次都没出现。发现三：手写版能赢，靠的是源代码之外的知识，值域 0～255、每遍部分和远小于 $2^{31}$，所以敢直接用 32 位通道累加。这不是编译器蠢，是它必须保语义而你签收了额外前提。

手写版本如下，核心内在函数（intrinsics，编译器提供的「一条汇编指令」的函数包装）逐参读法写在注释下方：

```c
#include <immintrin.h>
long sum_simd(const int *a, long n) {
    __m256i v0 = _mm256_setzero_si256();      /* 256 位零向量 */
    /* v1、v2、v3 同样清零：4 条独立链，接住 §3.2 的教训 */
    for (long i = 0; i + 32 <= n; i += 32) {
        v0 = _mm256_add_epi32(v0, _mm256_loadu_si256((const __m256i *)(a + i)));
        /* v1、v2、v3 各吃 a+i+8、a+i+16、a+i+24，略 */
    }
    /* 4 条链合并，storeu 到 8 格 int 数组后标量求和，略 */
}
```

1. `_mm256_loadu_si256(p)`：一个参数，地址；把该地址起 32 字节搬进一个 256 位寄存器。`u` 是 unaligned，不要求地址对齐到 32 字节，代价是对齐账（《计算机系统结构》§7.4）由硬件兜底。
2. `_mm256_add_epi32(x, y)`：两个参数各是 256 位向量，读作 8 格 int32；返回值第 $k$ 格 = 两参数第 $k$ 格之和，8 格互不串门。后缀 `epi32` 声明格子宽度与符号，同一块 256 位还能按 `epi8`、`epi64` 等读法解释，选错后缀就是选错指令。
3. `_mm256_storeu_si256(p, x)`：参数一是目的地址，参数二是源向量，与 load 方向相反，用来在循环收尾把 4 条链合并后的 8 个部分和倒回内存。
4. 横向合并不在向量指令里做：8 个部分和 store 到数组再标量相加，每遍调用只付一次，摊到每元素后为零。

换个负载再验一次：转换循环 `o[i] = a[i] * 3 + 1`，每元素一次 load、一次 store、两次算术。实测（ns/元素）：`-O0` 1.066，`-O2` 自动 0.334（3.2 倍，汇编无 ymm），`-O3` 自动 0.231（4.6 倍，8 通道 ymm），手写 intrinsics 0.212（5.0 倍）。手写与自动这次几乎打平，因为乘加没有溢出语义的余地，编译器能做的手写版没有额外便宜可捡。这组数字背后还压着一个被证伪的假设，值得记一笔：第一次顺序测量时 `-O3` 自动版曾反常地测出 0.698，第一嫌疑人是 4K 别名冲突（两个 4 MiB 的 `malloc` 都经 `mmap` 页对齐，load 与 store 同偏移打架）。验证手法是把输出缓冲平移 64 字节再测，数字纹丝不动（平移后 0.241 对平移前 0.231、平移后 0.250 对平移前 0.212），假设被否决；真凶是测量顺序引起的频率漂移，交错计时后消失。假设-验证循环里被证伪的分支不是浪费，它们把「漂移」这个变量钉死在了协议层。

这个版本顺带量出一张带宽账：每元素搬 8 字节（4 读 4 写），0.212 ns 一元素，折合 37.8 GB/s，工作集 4 MiB 常驻 L3，这已经是第 2 章那张延迟-带宽账单上 L3 一档的吞吐了。

白话：SIMD 是把收银台的扫码枪换成八仓一起过的传送带，东西排得整齐（连续内存、同构运算）它就一拍八个；语义上的小前提（32 位不怕溢出）只有你这个了解数据的人才签得了字。

> 本节小结：SIMD 加速比的来源是一条指令装八个数，-O2 未必向量化、-O3 保语义必加宽、手写 intrinsics 赢在签收额外前提；先看汇编再信任何一个「编译器会帮我」。

## $\rm \S \, 3.4$ 标量替换与寄存器压力：编译器已经做了一半

还有一条竞赛生信仰要审判：「累加用全局变量/内存单元，比局部变量慢」。把它写成可测的对照，两个函数签名完全相同，累加器一个是调用者数组的首元素、一个是先读进寄存器最后写回：

```c
void sum_memacc(int *acc, const int *a, long n) {   /* 每轮迭代读写内存 */
    for (long i = 0; i < n; i++) acc[0] += a[i];
}
void sum_regacc(int *acc, const int *a, long n) {   /* 标量替换的源代码版 */
    long s = acc[0];
    for (long i = 0; i < n; i++) s += a[i];
    acc[0] = (int)s;
}
```

实测：内存版 0.361 ns/元素，寄存器版 0.356，差 1.5%。直觉预测的「慢好几倍」没有出现，汇编揭示了原因。内存版的主循环真身：

```text
.L:     add    (%rsi),%eax     # 取 a[i] 直接加进 eax：链住在寄存器里
        add    $0x4,%rsi
        mov    %eax,(%rdi)     # store acc[0]：每轮迭代照写不误
        cmp    %rdx,%rsi
        jne    .L
```

累加链整个住在寄存器 `eax` 里：下一轮的加法吃的是 `eax` 自己，不等那条 `mov` 回内存再读回来的值。那个内存写只是每次迭代附赠的一笔旁路流量，占掉一个 store 端口而已（store 后同地址再读时，硬件靠存储转发把 `eax` 原值交回，语义正确且不经内存）。也就是说，gcc 在 `-O2` 已经自动做了**标量替换**（scalar replacement，把循环里反复读写的内存单元换成寄存器中的标量）：你写在源代码里的「内存累加器」和寄存器版的差价，只剩每元素一次 store 的端口占用。这条信仰在这台 gcc 13.3 上不值钱，但注意这是实现行为不是语言承诺：`acc` 与 `a` 同为 `int *`，编译器必须假设两者可能重叠，才没有把 store 完全消掉；换编译器或开激进选项，行为可以不同。

寄存器压力则是同一枚硬币的另一面：16 个通用寄存器是硬配额，§3.2 的 acc16s 想同时养 16 条链，汇编里出现 27 处栈读写，被挤出去的值叫**寄存器溢出**（register spilling）。它的教训不在「溢出很慢」，而在优化是有层次的：链（§3.2）、端口（§3.2）、向量宽度（§3.3）、寄存器配额（本节）按顺序检查，越靠前的越值得花力气，源代码层面的微操常常是编译器已经做完的半成品。

白话：你以为自己在教编译器省钱，其实它早把账算完了；你真正能帮它的是签收那些它不敢替你签的前提，比如「这些数不会溢出」「这两个指针不重叠」。

> 本节小结：标量替换编译器已自动做（实测差 1.5%），溢出的代价要先看它是否踩在瓶颈路径上；把力气花在链、端口、向量宽度这些编译器做不了主的层次上。

## $\rm \S \, 3.7$ 本章自测答案

概念回顾答案：

1. ${C_{\text{pen}} = (6.5217 - 0.3370)/0.5 \approx 12.4\,\text{ns}}$，按 2.6 GHz 折合约 32 拍；比常引的 15～20 拍偏大，归因给 WSL2 虚拟化与前端重取指的额外开销（§3.1）。
2. 排序后分支预测全对，分支只付一次比较加一次不跳的跳转；cmov 无条件把加法挂在累加链上，链更长。cmov 买到的是与数据分布无关的耗时（0.71 对 0.78），即「永不走错」的保险（§3.1）。
3. $k{=}1$ 时 ${\max(1,\ 0.5) = 1}$ 拍，实测 0.92 拍贴住链上限；$k{=}4$ 时 ${\max(0.25,\ 0.5) = 0.5}$ 拍，实测 0.52 拍踩在 load 端口地板上，瓶颈已从链换到端口（§3.2）。
4. 汇编显示自动版每 8 元素做两次 `vpmovsxdq` 加两次 4 通道 `vpaddq`：源码 `long s += int a[i]` 的语义要求逐元素符号扩展，编译器必须保语义。手写版签收了「部分和不溢出 int32」这个源代码之外的前提才敢用 32 位通道，便宜的来源是额外知识不是更好的编译器（§3.3）。
5. `add (%rsi),%eax` 表明累加链住在 `eax`，下一轮加法不等内存；`mov %eax,(%rdi)` 是每迭代附赠的旁路 store，因 `acc` 与 `a` 可能重叠无法消去。所以内存累加器在这台上只付 store 端口占用，差价 1.5%（§3.4）。

应用与辨析答案：

1. 它测的是 if 转换之后的两段相同代码（都是 cmov），「提速」来自别的因素或纯属噪声。改法：给 if 版单独编译加 `-fno-if-conversion -fno-if-conversion2`（必要时加 `-fno-tree-vectorize`），并用汇编确认循环里出现条件跳转且无 cmov。数据设计：同一数组的随机序与排序序各测一次，四个数（分支×2 + cmov×2）齐了才能同时读出「预测对的价值」与「cmov 的保险价」（§3.1）。
2. 限定条件至少四个：基线是谁（对 `-O0` 是 26 倍，对 `-O2` 标量只有 3.4 倍）；编译器到了哪一档（`-O2` 未向量化、`-O3` 自动向量化已拿走大半）；负载算术强度与工作集（本章 4 MiB 常驻 L3，换到 DRAM 档就是第 4 章的带宽墙）；语义余地是否存在（有溢出语义余地时自动版被加宽拖慢三成）。缺一条，「快 8 倍」就不是一个可检验的命题（§3.3）。
3. 会变的：`-O3` 自动向量化不再需要加宽，元素本就是 64 位，它与手写版的差距应大幅缩小甚至持平；手写版若继续用 epi32 通道反而要改回 epi64。基本不变的：acc1 到 acc8s 的扫描（瓶颈仍是链与 2 条 load 端口，只是每元素字节翻倍后内存档位可能下移）；分支实验与数据宽度无关。复测脚本把 int 换 long 即可，预测先行、测量审判（§3.2、§3.3）。

**你现在能做什么**：你能在任何一台 x86-64 机器上把同一段循环编译出分支、展开、SIMD 三档形态，用汇编证据确认每档真的存在，再按「预热、取最速、轮转交错」的协议量出它们各自真实的加速比，并识别出哪条口诀在你这台机器上不值钱。下一章镜头拉回数据本身：同样的招数一旦工作集大到缓存装不下，0.26 拍/元素的 SIMD 循环会被带宽墙按在原地，矩阵乘的分块与 AoS/SoA 的摆放方式将成为新的变量。
