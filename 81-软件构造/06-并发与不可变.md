## $\rm \S \, 6.1$ 两只手：归纳论证漏掉的前提

先立任务。论文资料管理器从命令行长成了后端服务：每个请求一个线程，两个请求可能同时调 `add`。**并发**（concurrency）指多个执行流在同一时间段内交叠推进，谁先谁后不由程序写死，由调度器当场决定。**竞态条件**（race condition）指程序的结果取决于执行流之间的相对时序：一种排法结果对，另一种排法结果错。它的反面值得同时立起来：没有竞态的代码，结果只由输入决定，与调度无关。第 2 章到第 5 章的全部正确性论证都默认这一点，只是从没说过。

问题的形状用一条语句说清。`c[0] += 1` 在人眼里是一步，在解释器手里是多条字节码：从列表取出旧值、加一、存回列表。线程切换可以发生在任何两条字节码之间，于是「取旧值」与「存回」之间有一条缝。另一个线程从缝里进来，也取旧值、也存回，两次自增只剩一次。这个现象叫**丢失更新**（lost update），《操作系统》§2.5 用同款实验见过它的机理；那一章还许了愿：加一把 `threading.Lock` 就能堵住，锁怎么用原子指令造出来是《操作系统》§6.3 到 §6.5 的主题。本册站在 ADT 作者的位置把这件事做完：不是会用锁，而是知道什么时候该用锁、什么时候有更便宜的路，以及「线程安全」四个字写进合同时到底承诺了什么。
白话：竞态像两个人同时改同一行共享文档，各自屏幕上都是原文，各自点保存，后保存的把先保存的改动整行覆盖；谁后保存取决于手速，这就是「结果看时序」。


## $\rm \S \, 6.2$ 锚点实验一：丢失更新的实测账

共享计数器是并发世界的果蝇：结构最简单，毛病一个不少。实验口径：$T$ 个线程，每人把同一个计数器自增 $N$ 次，理论终值 ${T \times N}$，实测终值比它少的部分就是被吃掉的更新。两个档位：窄窗口，裸 `c[0] += 1`；宽窗口，在读与写回之间显式插一个 `time.sleep(0)` 让出执行权，把「可能被打断」变成「必然被打断」。宽窗口不是作弊：真实程序的读改写之间可能隔着一次内存分配、一条日志、一次网络调用，缝宽是工程现实，`sleep(0)` 只是把现实里遥远的概率拉近到必现（《操作系统》§2.5 的实验同款）。

```python
def worker_narrow(c, n):
    for _ in range(n):
        c[0] += 1                  # 读、加、写回：相邻几条字节码

def worker_wide(c, n):
    for _ in range(n):
        tmp = c[0]                 # 1. 读
        time.sleep(0)              # 2. 让出执行权：窗口拉宽到必被打断
        c[0] = tmp + 1             # 3. 写回（可能盖掉别人的更新）
```

窄窗口 9 组（$T$ 取 2、4、8，各 3 个种子）全部精确等于理论值。这个结果要诚实地读：CPython 的全局解释器锁（GIL，《操作系统》§2.5 已定义）保证同一时刻至多一个线程在执行字节码，线程切换的粒度是微秒级，踩不进纳秒级的读改写缝。「今天实测不丢」是实现现状，不是语言承诺：换自由线程的解释器、换运行时、或解释器改了切换策略，同样的代码就会丢。把「现在跑不出错」当成「没有竞态」，是并发编程里最贵的错觉。

宽窗口的实测（摘自 `result.txt`，${N = 20000}$，理论终值 ${T \times 20000}$）：

```text
T=2 seed=0 expect=40000 final=20000 lost=20000 (50.00%) time=1.617s
T=2 seed=1 expect=40000 final=20000 lost=20000 (50.00%) time=1.542s
T=2 seed=2 expect=40000 final=20000 lost=20000 (50.00%) time=1.556s
T=4 seed=0 expect=80000 final=20000 lost=60000 (75.00%) time=1.486s
T=4 seed=1 expect=80000 final=20000 lost=60000 (75.00%) time=1.547s
T=4 seed=2 expect=80000 final=20001 lost=59999 (75.00%) time=1.438s
T=8 seed=0 expect=160000 final=20003 lost=139997 (87.50%) time=1.609s
T=8 seed=1 expect=160000 final=20006 lost=139994 (87.50%) time=1.650s
T=8 seed=2 expect=160000 final=20001 lost=139999 (87.50%) time=1.648s
```

两条规律钉在数字上。其一，丢失率恰好是 ${(T-1)/T}$，与 $N$ 无关、与种子无关。账这样算：`sleep(0)` 让出后调度器挑下一个可运行的线程，$T$ 个线程全在同一段循环里，于是近似严格轮转。一轮里 $T$ 个线程依次执行「读到 $v$、让出、写回 ${v+1}$」，每个人读到的是同一个 $v$，写回的是同一个 ${v+1}$：$T$ 次自增净增 1。一轮下来计数器只前进一步，终值约等于 $N$，于是：

$$
\text{丢失率} = 1 - \frac{N}{T \cdot N} = \frac{T-1}{T}
$$
读法：$T$ 是线程数，$N$ 是每线程自增次数，分母 ${T \cdot N}$ 是理论总自增数；${T = 8}$ 时八个更新里只活下来一个。


实测 50.00%、75.00%、87.50% 正是 $\frac{1}{2}$、$\frac{3}{4}$、$\frac{7}{8}$，${T = 8}$ 时八分之七的更新被无声吞掉。其二，终值不再确定：${T = 4}$ 的三个种子给出 20000 也给出 20001。同一个程序、同样的输入，跑两次答案不同，因为答案依赖调度时序。这是竞态条件区别于普通 bug 的指纹：普通 bug 忠实地复现，竞态 bug 看调度的心情。

复现方式（WSL Bash，当前目录为本册实验记录 `expSW06`，输出重定向到 `result.txt`；成功验证是宽窗口各档丢失率与 ${(T-1)/T}$ 吻合、终值都停在 $N$ 附近）：白话：宽窗口不是把 bug 硬造出来，是把生产环境里某天深夜才出现一次的低概率交错搬上实验台变成必现；果蝇好养，毛病不假。



```bash

```

> 本节小结：读改写之间的缝是丢失更新的根源；窄窗口下 GIL 的切换粒度踩不进缝，实测 9/9 精确，但这是实现现状不是语言承诺；宽窗口下丢失率恰为 ${(T-1)/T}$、终值停在 $N$ 附近，且同一程序多种子结果不同，时序依赖是竞态的指纹。

## $\rm \S \, 6.3$ 路线一：锁，把交错钉回串行

**锁**（lock）是一扇一次只放一人通过的门：进门前 `acquire`，拿不到就等；出门 `release`。门内那段代码叫**临界区**（critical section），《操作系统》§6.1 已正式定义：访问共享变量的那段代码。锁怎么用原子指令造出来（自旋、睡眠、futex）是《操作系统》§6.5 的内容，本册站在使用者的位置，只记用法与两笔账：

```python
import threading

def worker(c, n, lock):
    for _ in range(n):
        with lock:                 # 进门
            tmp = c[0]
            time.sleep(0)          # 就算在门里让出，别人也进不来
            c[0] = tmp + 1         # 出门
```

正确性账：锁保证「同一时刻至多一个线程在临界区里」，但「哪些代码算临界区」是程序员申报的。申报漏一处，全部白锁：rep 有四个字段，三个方法的访问都进了门，第四个方法裸奔，竞态照旧。第 4 章说 RI 是实现的私有合同，加了锁之后这份合同多出一条归纳前提「当前线程持锁」，而这条前提没有任何类型系统替你检查，全靠纪律。锁的钱就花在这：把「编译器能查的事」换成了「人不能漏的事」。
白话：锁是一扇一次过一人的门，门本身不认人也不查票，谁该进门、进门干什么全靠每个程序员自己申报；漏报一个入口，整座楼的门禁都是摆设。


性能账：每次进出临界区要付一次加锁解锁的对价，400000 次自增就是 400000 次；临界区越长，后面排队越久，粗锁与细锁的权衡《操作系统》§6.7 专门算过。**原子性**（atomicity）指一个操作要么整体完成、要么整体没发生，其他线程观察不到中间状态。锁的真正价值是它不挑内容：门里放三字节码的自增是原子的，放十个方法的复合操作也是原子的，这笔能力 §6.6 要用。

> 本节小结：锁把临界区内的任意代码段变成原子；代价是两笔，正确性上「申报哪些代码进门」从类型检查降级为纪律，性能上每次进出付对价、门内越长排队越重。

## $\rm \S \, 6.4$ 路线二与路线三：不共享，或共享不可变的

竞态要发生，「共享」和「可变」缺一不可。锁的思路是让写串行；下面两条路线更釜底抽薪：拆掉其中任何一个条件，竞态无处安放。

**不可变对象**（immutable object）指创建之后状态永不改变的对象。Python 的 `str`、`tuple`、`frozenset` 都是；第 4 章 §4.2 提过「不可变类型是最好的 RI：想变都没有入口」。线程安全的账在这里短得漂亮：没有写，就没有读改写之间的缝；一万个线程同时读同一个 tuple，谁也弄不坏谁。不可变对象可以无锁共享，这不是「锁加得好」，是根本没有需要锁的东西。全册比喻在这里正好合缝：抽象屏障是防火墙，不可变是最便宜的防火墙材质，它不隔风（随便读），只隔火（谁也改不了）。失效边界也要钉住：如果共享的是「引用变量本身」，换指向这个动作仍然是写；CPython 里引用赋值接近单条字节码的原子，但这不是跨语言的承诺。不可变方案省心的前提始终是「发布之后无人再改」。

**约束隔离**（thread confinement）指一份数据从生到死只被一个线程碰，别的线程连名字都不知道。不需要不可变，也不需要锁：私有数据没有竞争者。锚点实验二的 snapshot 变体就是它，每线程在自己本地变量上累加，结束时一次性交接：

```python
def worker(i):
    k = 0                  # 本地变量，别的线程看不见
    for _ in range(n):
        k += 1
    slots[i] = k           # 一次性交接：单次整值赋值，不是读-改-写
```

交接那一行值得单独看：跨线程的动作被压缩成一次单值赋值，主线程 `join` 之后才来读。把「持续共享可变状态」换成「私有计算加一次性交接」，是并行程序设计里回报率最高的重构之一。

**消息传递**（message passing）指线程之间不共享可变数据，合作靠发消息：一方把任务或数据放进队列，另一方取走处理。Python 标准库的 `queue.Queue` 是现成的线程安全队列：

```python
def worker(tasks, out):
    k = 0
    while True:
        x = tasks.get()
        if x is None:      # 毒丸：主线程的收工信号
            break
        k += x
    out.put(k)             # 小计作为消息发回
```

`queue.Queue` 值得多看一眼：它自己是线程安全的，内部藏着锁，使用方却一行锁都不用写。白话：不可变是把告示牌刻在石头上，人人可看、无人能改，随便围观；约束隔离是各写各的草稿纸，最后交一次总账；消息传递是传纸条，纸条在谁手里谁才有资格动笔。

这正是 §6.6 要立的原则「把锁藏进 ADT」的现成样板：共享被压缩到队列一处，锁的责任归队列的实现者，使用方只对消息的内容负责。大规模并行世界里「不共享然后通信」与「共享然后加锁」的全面对决，见《性能工程》§6。

> 本节小结：竞态需要共享与可变同时成立；不可变拆「可变」，对象可无锁共享；约束隔离拆「共享」，数据私有、一次性整值交接；消息传递把仅剩的共享点压缩进线程安全队列，锁的责任归队列实现者。

## $\rm \S \, 6.5$ 锚点实验二：四份实现的对账

三条路线加一个对照组，同一任务四份实现：${T = 4}$，每人自增 $N$ 次。nolock 无任何同步；lock 把读改写包进临界区；snapshot 约束隔离，各线程私有累加、槽位交接；queue 消息传递，400000 个「加一」任务进任务队列，四个工人各自累加，小计作为消息发回。两个档位：窄窗口（${N = 100000}$，理论终值 400000）量时间成本；宽窗口（读与写回之间插 `sleep(0)`，${N = 20000}$，理论终值 80000）量正确性。每个变体每档连跑 3 个种子，结果（摘自 `result.txt` 的汇总行）：

```text

nolock    [wide  ] exact 0/3, best time 1.495s
lock      [narrow] exact 3/3, best time 0.067s
lock      [wide  ] exact 3/3, best time 6.078s
snapshot  [narrow] exact 3/3, best time 0.009s
snapshot  [wide  ] exact 3/3, best time 1.442s
queue     [narrow] exact 3/3, best time 1.091s
queue     [wide  ] exact 3/3, best time 1.654s
```

正确性一列先读。窄窗口下四份全对：这正是 §6.2 警告过的危险形态，错误静默、测试全绿，换解释器或换负载就翻车。宽窗口下只有 nolock 0/3（终值停在 20000 附近，恰好丢 ${(T-1)/T = 75\%}$），三条修复路线全部 3/3 精确。lock 版的宽窗口测试比窄窗口狠：`sleep(0)` 插在临界区内部，等于每个持锁者都在门里睡一觉，后面的线程照样进不来。锁的保证与临界区里干什么无关，这一轮把保证钉实了。

成本一列按窄窗口最快时间排序：snapshot 0.009s、nolock 0.034s、lock 0.067s、queue 1.091s。三句话读完。其一，snapshot 比 nolock 还快近 4 倍：不共享省掉的不只是锁，还有一切跨线程的同步流量，数据全程在各线程自己的地盘上。其二，lock 对 nolock 约 2 倍：400000 次进出门的对价，每次纳秒级，积少成多。其三，queue 慢出两个数量级：每个「加一」都要排队、拷贝、取件，消息传递买的是结构清晰，消息粒度越细税越重，所以它适合「事件、任务、命令」这类粗粒度消息，不适合把每次自增都发成消息。

宽窗口的时间另有一笔账：lock 6.078s 对 snapshot 1.442s，约 4.2 倍。差别不在锁的对价，在并行度：snapshot 的四个线程各睡各的，总睡眠量四人平摊；lock 的四个人在门里睡，只能串行，四个线程被重排回一条队。这个 4 倍正好是线程数：锁把临界区变成串行段，Amdahl 定理里并行加速的串行占比 $f$ 就是它，真实多核世界里同一件事的账见《性能工程》§5。还要钉一句：本实验的时间数字不能当加速比读。GIL 让同一时刻至多一个线程执行字节码，这里量的全是同步与协调的开销，不是多核并行收益。
白话：四份实现像四条结账通道，货都送到家（正确性），价格表却差两个数量级；隔离版不但不排队还抄了近道，锁版把四个窗口合并成了一个，消息版每件货都走全套托运手续。


复现方式（WSL Bash，当前目录 `expSW06`，输出追加到同一个 `result.txt`；成功验证是汇总 8 行中除 nolock 的 wide 档外全部 `exact 3/3`）：

```bash

```

> 本节小结：宽窗口下三条修复路线 3/3 精确、无锁对照 0/3；窄窗口成本排序 snapshot < nolock < lock < queue，隔离比不加锁还快，消息传递为结构付两个数量级的税；宽窗口下锁内睡眠把 4 线程重排回串行，4.2 倍的时间差就是并行度被锁吃掉的量。

## $\rm \S \, 6.6$ 把线程安全写进合同

三条路线落回 ADT，是三种不同的合同。不可变 ADT 的合同最硬：「本类型不可变，任何线程可无锁共享」，无条件成立。约束隔离的合同其实是一句调用方义务：「本对象不是线程安全的，你不得把它交给两个线程」；按第 3 章 §3.5 的原则反读，合同里不写明这一点，调用方就有权默认它安全，所以这句义务必须落在文档里。可变共享 ADT 的合同是「本类型线程安全：每个操作原子，调用方无需加锁」。实现上把锁藏进 ADT，每个公开方法进门出门，使用方的代码里一行锁都不出现：

```python
class PaperShelf:
    def __init__(self):
        self._papers = []
        self._lock = threading.Lock()
    def add(self, p):
        with self._lock:
            self._papers.append(p)
```

「每个操作原子」这条合同有一条著名的缝：原子操作拼起来不原子。**检查再行动**（check-then-act）指「先查条件、再依条件行动」的两步模式。调用方写：

```python
if not shelf.has(title):        # 操作一：查
    shelf.add(paper)            # 操作二：行
```

查和行各自原子，中间却有一条缝：另一个线程可以在你查完之后、行动之前把同名论文塞进去，你再 `add` 就重复了。缝在两次操作之间，锁在操作内部，够不着。修法不是让调用方自己加锁（那等于把 ADT 的锁泄进使用方代码，rep 的私有性名存实亡），而是把复合操作升级成 ADT 的一个原子方法：

```python
    def add_if_absent(self, p):
        with self._lock:
            if p not in self._papers:
                self._papers.append(p)
                return True
            return False
```

判断一个线程安全 ADT 的合同够不够用，就看调用方会不会被迫写检查再行动：会，就补一个原子复合方法；复合方式多到补不完，就该换消息传递，让决策序列完整地排队通过。三个方案对调度的态度其实是同一句话的三种回答：要么让交错无害（不可变），要么不交错（隔离与消息传递），要么把必须串行的部分圈出来（锁）。
白话：「每个操作原子」像每扇旋转门都一次只过一人，可「先查有没有票、再买票」是推着行李车过两道门，两道门各自再稳，也拦不住行李在两道门之间被人拿走；修法是把两道门并成一扇。


> 本节小结：线程安全在合同里有三档措辞，不可变=无条件共享、隔离=调用方义务、可变加锁=每操作原子；原子操作的组合仍可能不原子，缝在操作之间，修法是原子复合方法而不是外泄锁；三策略是对「如何对待交错」的三种回答。

## $\rm \S \, 6.9$ 本章自测答案

概念回顾答案：

1. 缺的前提是「操作一次只有一个在执行」，即操作之间不交错。竞态条件的判据是结果依赖执行流之间的相对时序；普通 bug 输入相同则结果相同、忠实地复现，竞态 bug 同样输入跑两次可以不同（来源：§6.1、§6.2）。
2. 窄窗口的 9/9 依赖 CPython GIL 的切换粒度恰好踩不进纳秒级的读改写缝，这是实现现状，解释器版本、运行时、负载一变就翻车，语言并没有承诺过。宽窗口把轮转固定下来：一轮 $T$ 个线程全读到同一个 $v$、全写回 ${v+1}$，$T$ 次自增净增 1，终值停在 $N$ 附近，丢失率 ${1 - N/(T \cdot N) = (T-1)/T}$（来源：§6.2）。
3. 正确性账：「哪些代码算临界区」由程序员申报，漏一处全部白锁，RI 的归纳多了「当前线程持锁」这条无人检查的前提，纪律替代了类型检查。性能账：每次进出付加锁解锁的对价，临界区越长排队越重（来源：§6.3，《操作系统》§6.7）。
4. 不可变拆「可变」：没有写就没有缝，对象可无锁共享；约束隔离拆「共享」：私有数据没有竞争者。snapshot 更快是因为它免掉的不只是锁，还有一切跨线程的同步流量，数据全程留在各线程的地盘上（来源：§6.4、§6.5）。
5. 缝在原子操作之间：查与行各自原子，组合起来仍可被插入，锁在操作内部够不着操作之间的缝。修法是把复合操作升级为 ADT 的原子方法，锁留在实现内部；调用方自己加锁会把 rep 的私有性泄掉，等于签了份把实现细节写进合同的协议（来源：§6.6）。
6. 体现了「把锁藏进 ADT」：线程安全的责任由类型的实现者承担，使用方面对的仍是一份干净的合同，这正是第 4 章「使用方只面对操作」与第 5 章「依赖抽象而非实现」在并发下的延续（来源：§6.4、§6.6）。

应用与辨析答案：

1. 用实验一的两档对照：窄窗口 9/9 精确恰恰演示了「错误静默」，测试全绿与没有竞态是两回事；一万次全对只说明 GIL 的切换粒度在他的负载下没踩进缝。让他补宽窗口实验（读改写之间插 `sleep(0)`），同一份代码立刻 0/3、丢失 ${(T-1)/T}$；再让他明白换自由线程解释器或换语言时窄窗口同样会丢。论证的根子是「实现现状不是语言承诺」（来源：§6.2）。
2. 第一处是 §6.6 的缝：`size()` 与切片之间另一个线程可以 `add`，`top` 返回的 k 与实际切片内容对不上，甚至切片时列表长度已变。第二处更早爆炸：`threading.Lock` 不可重入，`top` 持锁后调用 `size()`，而 `size()` 也要 `with self._lock`，自己等自己，当场死锁。修法：`top` 整体进一次临界区，内部直接用 `self._papers` 与 `len`，不经过公开方法；或改用可重入的 `RLock`，但优先选前者，它把「持锁期间调用了会再抢锁的代码」这类事故从结构上排除（来源：§6.3、§6.6）。
3. (a) 用锁藏进 ADT 的原子计数器，或每线程本地计数加定期合并；粒度是单次加一，消息传递的每条消息税负不划算。(b) 约束隔离：草稿天然是请求线程私有的，结束时一次性整值交接（§6.4 的 snapshot 模式），零锁零竞争。(c) 消息传递：任务队列加结果队列，生产者与工人只碰队列；任务粗粒度，排队税相对任务本身可忽略，换来工人与生产者完全解耦（来源：§6.4、§6.5）。
