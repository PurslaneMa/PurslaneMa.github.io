## $\rm \S \, 6.1$ 三层结构：epoch、batch、step

训练循环是三层嵌套：外层 epoch 把全量训练数据过一遍，中层把数据切成 batch，内层每个 batch 做一次「前向、算损失、清梯度、反向、更新」。迷你框架的十行骨架：

```python
for epoch in range(EPOCHS):              # 第一层：全量数据过一遍
    idx = epoch_perm(epoch)              # 本 epoch 的样本置换（§6.2 讲对齐）
    for s in range(0, len(idx), BS):     # 第二层：切 batch
        j = idx[s:s + BS]
        net.zero_grad()                  # ③ 清旧账（gradW 是 +=，§4.3）
        z = net(Xtr[j])                  # ① 前向
        loss, gz = softmax_ce(z, ytr[j]) # ② 损失层：返回 loss 与 dL/dz
        net.l1.backward(net.a1.backward(net.l2.backward(gz)))    # ④ 反向
        for L in (net.l1, net.l2):       # ⑤ 更新：SGD 就两行
            L.W -= lr * L.gradW
            L.b -= lr * L.gradb
```

这十行的顺序是硬约束：`zero_grad` 必须在 `backward` 之前（`+=` 会累积旧账），`step` 必须在 `backward` 之后（优化器只读梯度、写参数，§5.2）。反向一行从最内层往外读：先算 $\partial L/\partial z$ 进 `l2`，再穿 ReLU，最后进 `l1`。PyTorch 的对应物是 `optimizer.zero_grad()`、`loss.backward()`、`optimizer.step()` 三句，顺序一字不差。

网络与数据：`MLP` 复用 §4.2 的定义，结构 $8\to32\to2$，ReLU 激活，损失用 §5.1 的 `softmax_ce`。MNIST 全量下载与 CPU 全量训练都不现实，本册的口径如实说明：以自造的 2 类高斯数据走全流程，8 维特征、两类中心在 $\pm 0.5\,\mathbf{1}$、各 250 个样本，400 训练、100 测试；流程本身（组批、前向、反向、更新、评估）与 MNIST 上完全一致，只是规模缩小。

## $\rm \S \, 6.2$ 对照实验：迷你框架 vs torch.nn 逐 epoch 对齐

对照的前提是「同结构、同初始化、同超参」，难点在两边是两套独立的世界。三个对齐决定，如实记录：

1. **初始化对齐**：`torch.manual_seed` 与 `np.random.seed` 是两个互不相干的状态机，对不齐。可靠做法是在 numpy 里用 `default_rng(42)` 生成一次 He 初始化（$\mathcal{N}(0,\sqrt{2/f_{\mathrm{in}}})$），把同一组数组拷贝进两边的参数。`torch.manual_seed(0)` 照常声明，但实验不依赖它。
2. **batch 顺序对齐**：每个 epoch 的样本置换用独立种子 `default_rng(123+e)` 预生成，两边共用同一组置换。共享同一个生成器对象是错的：迷你侧先跑 20 个 epoch 会消耗随机状态，torch 侧拿到的就是另一组置换。
3. **数值对齐**：torch 侧全部用 float64（`model.double()`），损失用 `F.cross_entropy`（内部是 log-softmax，与 §5.1 的稳定 softmax 数学等价）。

超参：batch 32、$\mathrm{lr}=0.5$、20 个 epoch。逐 epoch 对照（loss 为该 epoch 各 batch 损失的均值，acc 为测试集准确率）：

| 2 | 0.2174 | 0.2174 | 0 | 0.92 | 0.92 |
| 4 | 0.2096 | 0.2096 | 0 | 0.91 | 0.91 |
| 6 | 0.1997 | 0.1997 | ${2.8\times10^{-17}}$ | 0.91 | 0.91 |
| 8 | 0.1840 | 0.1840 | 0 | 0.91 | 0.91 |
| 10 | 0.1577 | 0.1577 | ${2.8\times10^{-17}}$ | 0.90 | 0.90 |
| 12 | 0.1469 | 0.1469 | ${2.8\times10^{-17}}$ | 0.90 | 0.90 |
| 14 | 0.1519 | 0.1519 | ${2.8\times10^{-17}}$ | 0.90 | 0.90 |

| 20 | 0.1351 | 0.1351 | 0 | 0.91 | 0.91 |

（未列出的偶数 epoch 同样为机器精度级。）20 个 epoch 后四组参数逐数对照，${\max|\Delta w|=6.7\times10^{-16}}$。验证环境：WSL Ubuntu，PyTorch 2.14.1+cpu，float64。

loss 曲线顺带教一件事：它不是单调下降的。epoch 4 的 0.2096 比 epoch 3 的 0.2019 高，epoch 15 的 0.1516 比 epoch 14 的 0.1519 差距更小；SGD 每步沿「一个 batch 的坡」走，batch 之间的抖动写进曲线里，这是随机性的正常代价，不是 bug（第 7 章正式分析 batch 的随机性）。

耗时一列没有放进表里：迷你 0.028 秒、torch 2.57 秒，但这个数字不可比，torch 每步的框架调度开销在小 batch 上占绝对主导，微基准不说明 torch 慢（第 8 章谈真正的性能账）。

> **记账视角**：训练循环本身没有任何算法，它是把 §2 的图、§3 的引擎、§5 的更新式按时序粘起来的胶水。算法都在积木里，胶水只负责「每步按同一顺序拨一次算盘」。

## $\rm \S \, 6.3$ 训练里的三个工程细节

1. **`zero_grad` 为什么每步必须**：真跑一个对照。同一个 epoch 的前三个 batch，正常版与「忘清梯度」版逐步的损失：

   | 步 | 每步清梯度 | 不清梯度 |
   | --- | --- | --- |
   | 1 | 0.9976 | 0.9976 |
   | 2 | 0.5602 | 0.5602 |
   | 3 | 0.6610 | 0.2552 |

   前两步看不出差别（`gradW` 出生时是零，第一轮累积无旧账），第三步开始轨迹分叉：不清梯度时 $\mathrm{l1}$ 的 $|\mathrm{gradW}|$ 累积到 9.69，正常版只有 3.78。旧账混进新梯度，等效于把前几步的梯度全加起来当一步用，方向已经不是这个 batch 的方向，损失可能短期更低（上表正是如此），但那是巧合不是正确。
2. **梯度裁剪一句话**：反向之后、`step` 之前加一句 `if g_norm > clip: g *= clip / g_norm`，把过大的梯度按比例缩回半径 ${\mathrm{clip}}$ 内，防的是 RNN 类网络的反向爆炸（深度学习分册 §7 的梯度消失与爆炸）。
3. **eval 模式为什么存在**：dropout 训练时随机丢单元、eval 时必须关掉；BatchNorm 训练时用当前 batch 的统计量、eval 时改用滑动平均。PyTorch 用 `model.train()` / `model.eval()` 切换这套行为，迷你框架没有这两个层，但「同一份 forward 有两套语义」这件事从现在起要记住，第 9 章存 checkpoint 时它是坑。

## $\rm \S \, 6.4$ 把循环封装成训练器

十行骨架直接散在脚本里没法复用，封装成函数时多出三个决定。其一，返回什么：训练历史（每 epoch 的 loss 与 acc 列表）必须返回，§6.2 的表就是它的产物。其二，评估放哪：每个 epoch 末在测试集上评估一次，评估段要包在 `torch.no_grad()` 里，不建计算图（§3 的账本不用记），省内存也省时间；迷你框架没有 no_grad，因为它的层只在显式调用 `backward` 时才算梯度。其三，随机性归谁：训练集的 shuffle 用训练器内部自己的生成器，测试集永远顺序遍历，评估才可复现。

```python
def train(net, Xtr, ytr, Xte, yte, epochs, lr, bs):
    hist = []
    for e in range(epochs):
        run_one_epoch(net, Xtr, ytr, e, lr, bs)      # §6.1 的中层与内层
        hist.append((loss_all(net, Xte, yte),        # 评估不更新参数
                     acc(net, Xte, yte)))
    return hist
```

这三件事（历史、隔离评估、随机性归属）就是 PyTorch 生态里 `Trainer` 类或 lightning 风格训练器的全部雏形。

## $\rm \S \, 6.6$ 应用与辨析

1. 把 §6.1 骨架里的 `net.zero_grad()` 挪到 `backward` 之后、`step` 之前，训练会发生什么？第 1 步的损失变吗？
2. §6.2 的对照里，若 torch 侧误用 float32，${\max|\Delta w|}$ 会从 ${6.7\times10^{-16}}$ 变成什么量级？（第 8 章有实测，可先估。）
3. batch 大小从 32 改成 400（全量 batch），每 epoch 的 step 数怎么变？这条轨迹与梯度下降法是什么关系？

## $\rm \S \, 6.7$ 本章自测答案

### $\rm \S \, 6.7.1$ 关键概念回顾答案

1. epoch 扫全量、batch 切片、step 走一步；五个动作「清、前向、损失、反向、更新」，顺序硬约束：清在反向前（累积规则）、更新在反向后（优化器读梯度）。（§6.1）
2. 初始化与置换都在 numpy 里生成一次、拷贝进两边；置换按 epoch 独立种子预生成，不用共享的生成器对象。（§6.2）
3. `gradW` 出生时是零数组，头两步没有旧账可混；第三步起 `+=` 把历史梯度全混进来，$|\mathrm{gradW}|$ 从 3.78 涨到 9.69。（§6.3）
4. 反向之后、`step` 之前；判据是梯度范数 ${\|g\|}$ 超过半径 ${\mathrm{clip}}$ 就按比例缩。（§6.3）
5. dropout（关随机丢弃）与 BatchNorm（改用滑动平均统计量）；`no_grad()` 让评估段不建计算图、不记反向的账。（§6.3、§6.4）

### $\rm \S \, 6.7.2$ 应用与辨析答案

1. 清梯度发生在反向之后，等于白清；每步反向仍从零累积？不，反向在清之前执行，累积的是「上上步的旧账」，且第一步损失不变（还没有旧账），从第二步起轨迹错。（§6.1、§6.3）
2. 到 float32 的舍入量级，约 ${10^{-7}}$ 上下；机器精度 ${2.2\times10^{-16}}$ 是 float64 独有的整齐。（§6.2，第 8 章实测 ${7.6\times10^{-7}}$）
3. 每 epoch 从 13 步（${\lceil 400/32\rceil}$）变成 1 步；此时「batch 梯度」就是全量梯度，这条轨迹就是（全批）梯度下降，SGD 退化成 GD。（§6.1）
4. 计算图：评估段也建图，图上的中间量全部留着等 backward，显存随评估次数涨；`no_grad()` 是「本次前向不记账」的开关。（§6.4）
