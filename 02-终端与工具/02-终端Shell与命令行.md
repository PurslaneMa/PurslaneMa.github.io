# $\rm Chapter \, 2$ 终端、Shell 与命令行

> 在上一章你看到了程序从源代码到可执行文件、再到运行中进程的全过程，但那些实验都是靠点击界面或一条简单命令完成的。真实开发中，你需要一个用文字精确描述"运行哪个程序、传什么参数、数据从哪来、结果到哪去"的界面——本章先帮你打开这个界面（终端），再让你安全地驾驶它。

## $\rm \S \, 2.1$ 为什么需要终端

图形界面适合发现功能，但开发工作中大量任务天然以命令形式存在：编译和运行程序、安装依赖、启动服务器、使用 Git、登录远程服务器、查看进程和日志、批量处理文件。OJ 让你只接触"提交代码"这一件事，真实开发中这些步骤你都要亲手做。

终端的核心优势是**准确、可记录、可自动化**：同一条明确命令可以由人执行，也可以原样写进脚本或 CI（Continuous Integration，持续集成——第 21 章）自动执行。GUI 里的点击无法这样记录和复用。

## $\rm \S \, 2.2$ 如何打开终端

先解决最实际的问题：终端窗口从哪来？不同操作系统打开方式不同，但都只需要几秒钟。

### $\rm \S \, 2.2.1$ Windows：PowerShell 与 Windows Terminal

按键盘上的 **Win 键**（带 Windows 标志的键），直接输入 `PowerShell`（Windows 11 输入 `Terminal` 也能搜到 Windows Terminal），看到搜索结果后按回车。一个深蓝色或深色的窗口出现，里面有一行文字：

```text
Windows PowerShell
版权所有 (C) Microsoft Corporation。保留所有权利。

PS C:\Users\你的用户名>
```

这就是终端窗口，`PS C:\Users\你的用户名>` 是提示符（prompt，终端在等你输入时显示的文字，§2.3 详细讲）。

还有两种常见打开方式：

- **Win+R** 打开"运行"对话框，输入 `wt` 回车——打开 **Windows Terminal**（微软现代终端程序，支持多标签页）；如果你的电脑没有 Windows Terminal，输入 `powershell` 回车则直接打开 PowerShell。
- 鼠标**右键点击开始按钮**，菜单里选"终端"（Windows 11）或"Windows PowerShell"（Windows 10）。

PowerShell 和 Windows Terminal 不是一回事：**Windows Terminal 是窗口程序**（负责显示文字、开多个标签页），**PowerShell 是窗口里运行的 Shell**（负责理解你输入的命令）。这个区分正是 §2.7 的主题，现在先不纠结。

### $\rm \S \, 2.2.2$ WSL：开始菜单里的 Ubuntu

如果你已经安装了 WSL（Windows Subsystem for Linux，在 Windows 内运行 Linux 的官方方式，安装方法见[终端进阶](25-终端进阶.md)的 §25.1），打开方式更简单：按 Win 键输入 `Ubuntu` 回车。窗口里出现的是 Linux 风格的提示符：

```text
alice@DESKTOP-XXXX:~$
```

### $\rm \S \, 2.2.3$ Linux 与 macOS

- **Linux 桌面**：按 **Ctrl+Alt+T** 直接打开终端；或者在应用菜单里搜索 "Terminal"。
- **macOS**：按 **Cmd+空格** 唤出 Spotlight 搜索，输入 `Terminal` 回车。

### $\rm \S \, 2.2.4$ 打开之后：你应该看到什么

无论哪种方式，成功标志都一样：一个窗口，里面有一行提示符，末尾光标在闪烁——表示它在等你输入。此时输入 `pwd` 回车（§2.4 会解释），能看到一行输出，就说明终端工作正常。

打不开时先检查：搜索名称拼写是否正确（`PowerShell` 而不是 `power shell`）；Windows 自带 PowerShell，如果 Win 键搜索不到，用 Win+R 输入 `powershell` 试试；WSL 提示没有安装，说明还没装，先去看[终端进阶](25-终端进阶.md)的 §25.1。

## $\rm \S \, 2.3$ 提示符：终端在等你输入

提示符是终端等待输入时显示的那行文字，不同系统长相不同：

```text
PS C:\Users\Alice\projects>          # PowerShell
alice@server:~/projects$             # Bash / Zsh
```

它通常包含当前用户、主机名和当前目录（路径，path——文件在文件系统中的位置描述，第 3 章系统讲）等信息，最后的 `>` 或 `$` 表示"等你输入"。教程里写的 `$ git status`，开头的 `$` 往往只是提示符的示意，**不要把 `$` 一起输入**。

如果提示符以 `#` 结尾，在许多 Unix 文档中表示当前是 root（管理员）权限。不要因为某条命令失败就默认切换 root；先理解失败原因（§2.13）。

## $\rm \S \, 2.4$ 第一条命令：echo、pwd、ls

提示符在等你输入——那输入什么？先学三条最简单的命令，它们足够你建立"终端能用"的信心，并成为后面所有操作的脚手架。

**第一条：`echo`——让终端说句话。** 输入 `echo hello` 回车：

```bash
echo hello
hello
```

`echo` 是打印程序：它把后面给它的文字原样显示出来。这是最简单的一个"程序-参数"结构——`echo` 是程序，`hello` 是参数（argument，传给程序的值）。

**第二条：`pwd`——我在哪。** 输入 `pwd` 回车，终端打印出你当前所在的目录（PowerShell 里对应 `Get-Location`，两者作用相同）：

```bash
pwd
/home/alice
```

**第三条：`ls`——这里有什么。** 输入 `ls` 回车（PowerShell 对应 `Get-ChildItem`），列出当前目录下的文件和文件夹：

```bash
ls
Desktop  Documents  projects  papers.txt
```

如果在 §2.2 打开后立刻做这三件事，你就已经完成了一次完整的"终端体验循环"：输入命令 → Shell 启动程序 → 程序输出结果 → 终端显示。此时如果输入了一个不存在的命令名，比如 `echho`，会得到类似 `command not found` 或 `不是内部或外部命令` 的错误——这引出一个重要机制：Shell 怎么知道 `echo`、`ls` 对应哪个程序？答案是 PATH（§2.9）。

> **练习**：把 `echo`、`pwd`、`ls` 各输入一遍，对照上面的输出。再故意输入一个拼错的命令（如 `echho`），观察错误信息的样子——记住它，后面会经常见到。

## $\rm \S \, 2.5$ 工作目录与 cd：移动

**工作目录（working directory）**就是你现在在文件树中的位置——所有相对路径（relative path，相对于当前位置的路径描述）都从这里出发。就像你在文件管理器里双击打开了一个文件夹，文件管理器就"停在"那个文件夹里；终端也有一个"当前打开的文件夹"，上节的 `pwd` / `Get-Location` 就是问它"你现在停在哪"。

查看当前工作目录，然后切换目录：

```powershell
# PowerShell
Get-Location          # 查看
Set-Location D:\projects
# 常用别名
cd D:\projects        # cd 与 Set-Location 等价
```

```bash
# Bash/Zsh
pwd
cd /home/alice/projects
```

`cd`（change directory，切换目录）成功时通常**没有输出**。不要把"没有输出"理解为没执行——再次输入 `pwd`，或者观察提示符里的目录变化来验证。

常用路径符号：

- `.`：当前目录；
- `..`：上一级目录；
- Windows `C:\`：C 盘根目录；
- Unix `/`：文件系统根目录；
- Unix `~`：当前用户主目录（home directory）的缩写。

```text
./app          当前目录中的 app
../data        上一级目录中的 data
src/main.cpp   当前目录下 src 子目录中的文件
```

Windows 原生路径常用反斜杠 `\`，Unix 用正斜杠 `/`；许多 Windows 开发工具也接受正斜杠，但不要假设所有工具都接受。`cd` 不存在的目录会报错（`找不到路径` / `No such file or directory`），此时先 `pwd` 确认自己在哪，再检查路径拼写——这是最常见的入门错误。

> **练习**：新建一个安全练习目录并进入：`mkdir terminal-lab` 然后 `cd terminal-lab`（PowerShell 的 `mkdir` 也可以直接用），用 `pwd` 确认，用 `cd ..` 回到上一级，再用 `cd terminal-lab` 回来。每一步执行前，先说出你预计当前目录是什么。

## $\rm \S \, 2.6$ 查看文件：cat

目录里放着文件，文件里是什么？`cat`（PowerShell 对应 `Get-Content`）把文件内容打印到终端：

```bash
cat papers.txt
# 逐行打印文件内容
```

```powershell
Get-Content papers.txt
```

先造一个文件来试：`echo` 的输出可以写进文件（`>` 是重定向，把输出从屏幕改道到文件，§2.10 详细讲）：

```bash
echo "line one" > sample.txt
echo "line two" >> sample.txt      # >> 追加而不是覆盖
cat sample.txt
line one
line two
```

注意：文件很大的时候 `cat` 会把内容一次性刷满屏幕（几万行的日志会直接淹没终端）。看大文件要用分页工具（如 `less`，第 7 章工具箱介绍），现在只要知道"`cat` 适合小文件"这条经验规则。

> **练习**：在 `terminal-lab` 目录里创建 `input.txt`，写入两行数字（`echo 42 > input.txt`、`echo 7 >> input.txt`），用 `cat` 查看，再列出目录内容确认文件存在。

## $\rm \S \, 2.7$ Terminal、Shell 与命令：三个层次

你已经亲手敲过 `echo`、`pwd`、`ls`、`cd`、`cat` 这些命令，也看到了提示符。现在把这条链路里的三个层次分清楚——它们经常被混叫，而每次报错，你都要判断"是哪一层出了问题"。

- **终端（Terminal）**：承载文字输入输出的窗口程序。例如 Windows Terminal、VS Code 内置终端、macOS 的 Terminal.app、Linux 的各种终端模拟器。它只负责显示和收集文字。
- **Shell**：在终端里读取你输入的命令、解析语法、启动程序的软件。Windows 常见的是 PowerShell（和传统 `cmd.exe`），Linux 常见 Bash，macOS 默认 Zsh。同一个终端窗口可以运行不同的 Shell。
- **命令行程序**：`git`、`python`、`g++`、`curl` 都是被 Shell 启动的程序；Shell 自己也提供少量内置命令（如 `cd`）。

三者的关系：

```text
你
 ↓ 键盘输入
终端窗口（显示文字、接收输入）
 ↓ 把文字交给
Shell（解析命令、管道、变量等）
 ↓ 创建进程
git / python / g++ / 你的程序
 ↓ 输出
Shell → 终端窗口 → 你
```

这个分层解释了一个常见现象：网上一条 Bash 命令不一定能原样粘贴到 PowerShell——它们是不同的 Shell，命令名、变量语法、引号、管道的处理方式都不同。报错时先分清：是终端的问题、Shell 的语法问题，还是程序本身的问题。

## $\rm \S \, 2.8$ 命令的结构：程序、子命令、选项和参数

你马上会遇到真正的复杂命令，比如 `git log --oneline --max-count 5`。第一次看到会懵：这一串里哪些是程序、哪些是给它的话？拆开看结构：

```text
git log --oneline --max-count 5
```

它可以拆成：

```text
git          程序
log          子命令（subcommand，程序的子功能）
--oneline    选项（option，开关，不带值）
--max-count  带值选项
5            上一个选项的值
```

再看另一个例子：

```text
python script.py input.txt --limit 20
```

- `python` 是解释器程序；
- `script.py` 是位置参数（positional argument，按位置含义确定），告诉解释器运行哪个文件；
- `input.txt` 是脚本自己定义的位置参数；
- `--limit 20` 是脚本定义的选项。

**选项的格式由程序自己决定**，没有强制标准：常见形式有 `-h`、`--help`、`-o output.txt`、`--output=output.txt`。所以见到陌生命令时，先 `--help` 看它自己的约定（§2.13 是完整流程）。

含空格的参数必须加引号，否则会被拆成多个参数：

```text
python script.py "D:\My Data\papers.json"    # 一个参数："D:\My Data\papers.json"
```

引号告诉 Shell"这些字符属于同一个参数"。PowerShell 与 Bash 对单引号、双引号和变量展开的细节不同——基础规则（含空格加引号）两边通用，深层的引号语义放到[终端进阶](25-终端进阶.md)的 §25.5。

> **练习**：编译第 1 章的 `show-args` 程序，分别运行 `show-args one two three`、`show-args "one two" three`，记录每次收到的参数个数和内容，观察引号怎样改变参数分组。

## $\rm \S \, 2.9$ PATH：为什么输入程序名就能运行

输入 `python` 时，Shell 怎么知道去哪里找这个程序？它按照 **PATH** 环境变量（environment variable，进程的环境配置，§2.12 正式讲）列出的目录顺序查找，找到第一个匹配的可执行文件就运行它。

可以把 PATH 想象成一张"寻找程序时依次查看哪些目录"的清单。它**不是** Python 专属的路径，也不是"项目路径"——它管所有命令名的查找。

查看一条命令实际对应哪个文件：

```powershell
Get-Command python
Get-Command git
```

```bash
command -v python
command -v git
```

常见问题：

- 软件装了，但它的目录不在 PATH 里——输入名字找不到；
- PATH 里有多个同名版本，先找到的不是你想要的；
- 修改 PATH 后，旧终端没获得新环境（要重开终端或重新加载配置，见[终端进阶](25-终端进阶.md)的 §25.4）；
- `python` 和 `pip` 实际来自不同的 Python 安装。

排查版本问题时，**同时记录版本号和可执行文件路径**，不要只执行 `--version`——两条命令的输出可能来自不同文件。

### $\rm \S \, 2.9.1$ 为什么当前目录中的程序常写 `./app`

注意 PATH 里通常**不包含当前目录**（安全考虑：避免在陌生目录里输入 `ls` 却意外执行了目录里的同名恶意程序）。所以运行当前目录里的程序要显式写出路径：

```text
./app          # 明确表示"当前目录中的 app"
./app.exe      # PowerShell 中同理
```

`./` 不是装饰，它是在说"从当前目录出发找这个文件"。

> **练习（PATH 排障）**：对 `git`、`python`、`g++` 分别记录：能否被找到、可执行文件完整路径、版本号。如果同一工具有多个版本，记录 PATH 的搜索顺序，**不要删除任何版本**——先弄清哪个在用。

## $\rm \S \, 2.10$ 标准流、重定向与管道

程序与外界交换数据有三个默认通道，合称**标准流**（standard streams）：**标准输入**（stdin，standard input）——默认是键盘；**标准输出**（stdout，standard output）——默认是屏幕；**标准错误**（stderr，standard error）——默认也是屏幕，专用于错误和诊断信息。

Shell 可以重新连接这些流，这叫**重定向（redirection）**：

```text
program > output.txt      # 标准输出写入文件（覆盖已有内容！）
program >> output.txt     # 追加到文件末尾
```

```bash
program < input.txt       # 从文件提供标准输入（Bash 写法）
```

```powershell
Get-Content input.txt | ./program.exe   # PowerShell 给原生程序喂输入的可靠写法
```

**管道（pipe）**把左侧程序的输出接到右侧程序的输入，让程序像积木一样组合：

```text
producer | consumer
```

```bash
ps aux | grep python      # 列出进程，再筛出名字含 python 的行（Bash）
```

```powershell
Get-Process | Where-Object { $_.CPU -gt 10 }   # 筛选 CPU 占用高的进程（PowerShell）
```

两个平台管道的底层思想相同，但 Bash 管道传递文本字节流，PowerShell 管道传递结构化对象（连接原生程序时又会转成文本）——所以同样的管道写法不能两边原样通用。管道中任一阶段都可能失败，复杂命令应先分别运行各段、确认输出，再组合。

**标准错误和标准输出是分开的**，所以 `>` 默认只重定向正常输出，未必捕获错误（不同 Shell 的 stderr 重定向语法不同）。不管用哪种 Shell，你要能回答：只保存正常结果、只保存错误、合并二者、还是屏幕和文件都要？日志收集和 CI 经常依赖这个区别。

> **安全规则**：`>` 会**覆盖**已有文件，执行前确认目标路径，重要文件先备份（用 `>>` 追加或换新文件名）。

> **练习**：运行第 1 章的加法程序——先手动输入，再从 `input.txt` 提供输入（`./sum < input.txt`），把输出保存到 `output.txt`，用 `cat` 验证文件内容。

## $\rm \S \, 2.11$ 退出码和条件执行：程序怎么告诉你成功还是失败

程序运行结束后会给 Shell 一个**退出码（exit code）**：`0` 表示成功，非 `0` 表示某种失败。查看最近一条程序的退出码：

```powershell
$LASTEXITCODE
```

```bash
echo $?
```

退出码只代表**最近一次**相关程序的状态——继续运行其他命令会覆盖它，所以要立即查看。自动化脚本（第 21 章）靠它决定下一步：只有编译成功才运行测试，只有测试成功才部署。反过来，不要写一个打印"失败"却返回 0 的工具——那会骗过所有下游脚本。

Shell 的 `&&`（前一条成功才执行后一条）和 `||`（前一条失败才执行后一条）在 PowerShell 与 Bash 中的兼容情况不同，跨平台说明宁可分开写，不要假设一行通吃。

> **练习**：运行加法程序并正常结束，查看退出码；再故意让它出错（比如输入非数字），确认退出码非 0，并观察错误信息出现在屏幕哪里——这帮你直观感受 stdout 和 stderr 的分流。

## $\rm \S \, 2.12$ 环境变量：进程的"出厂设置"

**环境变量**是操作系统传给进程的一组键值对，进程启动时读入，用来获取配置（如 PATH、编辑器偏好、语言设置）。查看和设置：

```powershell
$env:PATH                                    # 查看（PowerShell）
$env:APP_ENV = 'development'                 # 临时设置（PowerShell）
```

```bash
echo "$PATH"                                 # 查看（Bash；加引号避免被再次分词）
export APP_ENV=development                   # 临时设置（Bash）
```

关键性质：这种设置只影响**当前 Shell 进程**及其之后启动的子进程，关闭终端就消失，也不会传给已经运行的程序。要让设置每次开终端都生效，需要写进 Shell 配置文件（[终端进阶](25-终端进阶.md)的 §25.4 专门讲）。

> **安全规则**：不要把 API Token、密码、私钥写进会提交到 Git 的脚本；命令历史、日志和进程信息也可能泄露敏感参数（`ps` 会显示命令行参数，第 13 章讲）。

## $\rm \S \, 2.13$ 如何安全学习陌生命令

面对从未用过的工具，用固定流程代替"复制粘贴试一下"：

1. 确认工具来源和用途（谁发布的、解决什么问题）；
2. 查看 `tool --help` 或相应帮助；
3. 查看版本和可执行文件路径（§2.9）；
4. 识别子命令、选项、位置参数和默认行为；
5. 先运行只读命令（如 `ls`、`--help`）；
6. 在专门创建的临时目录做最小实验；
7. 修改、覆盖、删除、上传、安装或提权前，再次确认目标；
8. 保存**完整错误信息**，而不是只截最后一行。

危险信号：

- 递归删除或覆盖（`rm -rf` 之类，本教材不会教无上下文使用）；
- 目标路径由未检查的变量或通配符产生；
- 要求管理员/root 权限却不解释原因；
- 从网络下载脚本后直接交给 Shell 执行；
- 把密码、Token、私钥放进命令参数；
- 关闭防火墙、证书检查或系统安全机制来"解决"问题。

> **练习**：选一个你没用过的只读工具，仅通过 `--help` 完成：查看版本、找到一个子命令、让输出更简洁或更详细、记录一次失败命令的退出码。

## $\rm \S \, 2.14$ 常见误区

**"命令没有输出，所以没有执行"**——许多成功命令默认沉默（如 `cd`）。用退出码和预期状态（`pwd`、`ls`）验证，而不是凭输出判断。

**"软件装了，输入名字就一定能运行"**——Shell 还必须通过 PATH 找到它（§2.9）。找不到时先 `Get-Command` / `command -v`。

**"终端就是 Linux"**——Windows 也有终端和 Shell（PowerShell）。终端、操作系统、Shell 是三个不同层次（§2.7）。

**"网上的命令复制下来一定能用"**——它可能针对不同 Shell、操作系统、版本、目录和权限，甚至可能恶意（§2.13）。

**"加管理员权限可以修复所有权限错误"**——管理员权限可能掩盖错误配置并扩大破坏范围。先理解要访问什么资源、正确的所有者是谁。

**"Ctrl+C 会把刚才的操作撤销"**——它只是请求中断当前前台程序，已经写入的文件或发送的请求不会自动回滚。

## $\rm \S \, 2.15$ 关键概念回顾

1. 当前工作目录为什么会影响命令结果？
> 相对路径以当前工作目录为起点解释，同一命令在不同目录下指向不同文件；不确定时先 `pwd` / `Get-Location`。

2. 标准输入、标准输出、标准错误各自适合什么？
> stdin 提供程序输入（键盘或重定向源）；stdout 输出机器要处理的正常结果；stderr 输出给人看的错误和诊断信息。

3. 退出码 0 表示什么？
> 成功。非 0 表示某种失败，自动化脚本据此决定是否继续下一步。

4. 临时设置的环境变量为什么影响不了已经运行的程序？
> 环境变量在进程启动时传入，子进程只继承父进程当时的环境；终端里新设的值不会传给已启动的程序。

5. 输入命令名时，Shell 如何找到对应程序？
> 按 PATH 环境变量列出的目录顺序查找第一个匹配的可执行文件；用 `Get-Command` / `command -v` 查看实际解析结果。

## $\rm \S \, 2.16$ 应用与辨析

6. 终端、Shell 和命令行程序有什么区别？
> 终端是承载文字输入输出的窗口；Shell 是读取、解析命令并启动程序的软件；命令行程序是被 Shell 启动的程序。

7. `tool "a b" c` 通常包含几个参数？
> 两个：`a b`（引号让含空格的文字成为单个参数）和 `c`。

8. `>` 为什么需要谨慎使用？
> 它把标准输出写入文件并**覆盖**已有内容（追加用 `>>`）；执行前确认目标路径，重要文件先备份。

9. 管道连接的是什么？PowerShell 与 Bash 管道有什么基本差异？
> 管道把左侧程序的输出连接到右侧程序的输入；Bash 通常传递文本字节流，PowerShell 传递结构化对象（连接原生程序时涉及文本转换）。

10. 为什么不能把所有 Bash 命令原样粘贴到 PowerShell？
> 它们是不同的 Shell：命令名、变量语法、引号、管道和重定向的语义都不同，原样粘贴可能报错或产生不同行为。

11. 学习陌生 CLI 的安全流程是什么？
> 确认来源和用途 → 查看 `--help` 和版本 → 识别子命令、选项、参数 → 先运行只读命令 → 在临时目录做最小实验 → 破坏性操作前再次确认目标 → 保存完整错误信息。

12. `pwd`、`ls`、`cat`、`echo` 各解决什么问题？
> `pwd` 回答"我在哪"，`ls` 回答"这里有什么"，`cat` 回答"文件里是什么"，`echo` 让程序输出文字（也用于生成小文件）。
