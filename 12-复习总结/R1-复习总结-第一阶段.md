## $\rm \S \, R1.1$ 本章任务

第一阶段教的几乎全是**操作知识**：敲命令、写路径、改权限、设环境变量、装软件。这类知识和 OJ 上的算法题不同——看过一遍、甚至照着敲过一遍，都不算掌握；只有合上正文能独立写出命令、预测输出并解释为什么，才算真正到手。记忆规律决定了单纯“重读”效率很低：一次性线性阅读制造倒摄干扰，24 小时内就会忘掉相当一部分；重读带来的加深很有限，真正强化记忆的是**主动提取**（retrieval）：在不看正文的情况下把知识回忆出来，回忆失败的地方才是你需要回读的缺口。[学习地图与使用方法](../00-学习地图与使用方法.md)建议的每章循环——阅读 → 实验 → 执行前预测 → 故意制造错误 → 不看正文完成检查表——正是对抗遗忘的姿势。本章不教任何新东西，只做四件事：闭卷回忆清单（提取）、核心心智模型复读（组块）、交错练习（对抗“学了后面只会后面”）、易混点对照（澄清）；建议先合上正文完成清单，卡住的题记下来，再做交错练习，最后对照章末“答案与提示”把答错的题回读对应小节。答案全部集中在 R1.6，题目区没有任何答案。建议的节奏：清单做完后把错题标出来，3 天后、1 周后各重做一遍——把提取间隔拉长，记忆才留得住。

## $\rm \S \, R1.3$ 核心心智模型复读

第一阶段建立的心智模型是整套教材的骨架。复习不是背命令，而是把分散的细节挂回这几个模型上；第二阶段（第 10–14 章）会直接在这些模型上继续盖楼。每个模型都配了一个“回到操作”的验证动作，请在你的终端里重放一遍。

### $\rm \S \, R1.3.1$ PATH=地址簿

首次定义于[终端、Shell与命令行](../02-终端与工具/02-终端Shell与命令行.md)的 §2.9：**PATH 是 Shell 寻找程序时依次查看的地址簿**——一张按顺序排列的目录清单。你在终端输入 `python`，Shell 就像翻通讯录一样逐页查找，找到第一个名为 `python` 的可执行文件就运行它，不再继续翻。

落回定义：PATH 是一个环境变量，值是若干目录按顺序排列；Shell 按这个顺序做“名字 → 文件”的查找。地址簿有三个地方会误导你，需要记住边界。第一，地址簿里通常**没有“当前目录”这一页**（安全考虑：防止在陌生目录里输入 `ls` 却执行了目录里的同名恶意程序），所以要显式写 `./app`；第二，地址簿里可能有多个同名程序，找到的是**第一个**，不是“最新”或“最想要”的那个；第三，修改地址簿不会影响已经开场的“进程演出”（R1.3.2）——已运行的进程不会自动获得新 PATH，旧终端要重开或重新加载配置才生效。

排查“命令找不到”和“版本不对”时，这两条命令直接回答“地址簿翻到了哪一页”：

```powershell
Get-Command python | Select-Object Source   # PowerShell：python 实际指向哪个文件
```

```bash
command -v python                           # Bash：同上
```

顺带把“查看地址簿内容”的命令也复习一遍：

```bash
echo "$PATH"            # Bash：加引号避免变量被再次分词
```

```powershell
$env:PATH               # PowerShell：同上
```

**回到操作**：把“命令找不到”的排查做成三步。第一步 `command -v python`（或 `Get-Command python`）——没有任何输出，说明 PATH 里根本没有这个名字；第二步 `echo $PATH`（或 `$env:PATH`）——对照安装目录，确认它在不在列表中；第三步 `python --version` 配合第一步的路径——**同时记录版本号和路径**，因为系统里可能有多个同名安装，你查的“版本”和实际运行的未必是同一个。第 9 章的典型现场：`pip --version` 显示 python 3.9 的 site-packages，而 `python --version` 显示 3.12——`pip` 和 `python` 根本不是同一个安装，用 `python -m pip` 才能保证装进同一个地址簿条目对应的那个 Python。

### $\rm \S \, R1.3.2$ 进程=演出

首次定义于[计算机程序与开发全景](../01-基础观念/01-计算机程序与开发全景.md)的 §1.2.4：**进程像某份程序的一次正在进行的演出**。可执行文件是磁盘上的“剧本”（静态文件），进程是“舞台上正在进行的这场演出”（运行实例）。同一个剧本可以同时开多场演出——一个 `browser.exe` 对应多个浏览器进程；改剧本（编辑源码）或删掉剧本文件，不会影响已经开演的场次——要让新代码生效，必须重新构建并重新启动。

这个模型在第 7 章有了用武之地：`ps`/`top` 是“查看现在有哪些演出、各占多少资源”，`ss`/`lsof` 是“查某场演出占用了哪个端口”。边界：演出比喻不解释进程之间如何共享 CPU、如何被调度、如何互相通信——那是第二阶段第 11 章的内容；现在只需要“可执行文件 ≠ 进程”“修改代码 ≠ 重启生效”这两个结论。

**回到操作**：亲眼验证一次“多场演出”。在终端启动一个持续运行的程序（第 7 章实践三用过的 `python -m http.server 9999`），在另一个终端运行 `ps aux | grep http.server`（PowerShell 用 `Get-Process python`）——你会看到对应进程的 PID 和资源占用；`Ctrl+C` 结束它，源文件一个字节都没少，再启动就是新的一场（新的 PID）。编译和运行也是两个阶段：`g++ main.cpp -o sum` 只是把“剧本”排版成可执行文件，`./sum` 才真正开场；改了代码忘记重新编译就运行，演的还是旧剧本。这还牵出第 1 章的一个区分：`能启动`不等于`功能正确`——进程被创建、没有立即退出，只说明演出开场了；它演的内容对不对、会不会中途崩掉，是另一回事。演出落幕时交还的退出码用 `echo $?`（Bash）或 `$LASTEXITCODE`（PowerShell）查看——它和打印到屏幕的文字是两回事：`return 0` 是“谢幕评分”，`cout << 0` 只是台词。看 `ps aux` 或 `top` 的输出时，重点看四列：PID（进程编号）、%CPU（单核满载 100%，多核可超过 100%）、%MEM（物理内存占比）、RSS（常驻内存，比 VSZ 更接近“实际吃了多少 RAM”）。

### $\rm \S \, R1.3.3$ 标准流与退出码：程序对世界的接口

首次定义于[计算机程序与开发全景](../01-基础观念/01-计算机程序与开发全景.md)的 §1.3.2–§1.3.3，在[终端、Shell与命令行](../02-终端与工具/02-终端Shell与命令行.md)的 §2.10–§2.11 投入使用。每个进程默认拥有三个通道：

| 标准流 | 编号 | 默认连接 | 用途 |
|---|---:|---|---|
| stdin（标准输入） | 0 | 键盘 | 数据送进程序 |
| stdout（标准输出） | 1 | 屏幕 | 正常结果——机器要接着处理的数据 |
| stderr（标准错误） | 2 | 屏幕 | 错误与诊断——给人看的 |

退出码是演出落幕时交给操作系统的“谢幕评分”：0 表示成功，非 0 表示某种失败，自动化脚本靠它决定是否继续下一步。注意退出码只代表**最近一次**相关程序的状态——继续运行其他命令会覆盖它，所以要立即查看。Shell 可以给这些通道“改道”：`>` 把 stdout 写进文件（**覆盖**已有内容）、`>>` 追加、`<` 从文件读入 stdin、`|` 把左边程序的 stdout 接到右边程序的 stdin。

**回到操作**：在临时目录里重放第 2 章的最小例子（Bash，PowerShell 的 `cat` 对应 `Get-Content`）：

```bash
echo "line one" > sample.txt    # stdout 写进文件，覆盖已有内容
echo "line two" >> sample.txt   # 追加到末尾
cat sample.txt                  # 验证：两行都在
```

再把第 1 章实验里的“从文件喂输入”接上：编译好加法程序（`g++ main.cpp -o sum`）后，创建 `input.txt` 写入两个整数，然后运行：

```bash
./sum < input.txt              # stdin 改道：程序从文件读，而不是键盘
./sum < input.txt > output.txt # 输入来自文件，输出写进文件
cat output.txt                 # 验证结果
```

`<` 与 `>` 方向相反：`>` 把输出送进文件，`<` 把文件内容送进程序的 stdin——程序本身一行不改，输入来源就换了。

预期输出是两行文字；如果先 `cat` 再执行第一条 `echo`，文件被覆盖成一行——这就是 `>` 的危险之处。还要记住 stdout 与 stderr 是**两条通道**：程序把错误写进 stderr 时，`>` 默认捕获不到（不同 Shell 的 stderr 重定向语法不同），日志收集和 CI 正依赖这个区别；第 8 章的 `2>&1` 和 `tee`（第 25 章）则是“合并通道”和“同时写文件与屏幕”的常用做法。此外还有条件执行：`&&`（前一条成功才执行后一条）与 `||`（前一条失败才执行后一条）——它们在 PowerShell 与 Bash 中的兼容情况不同，跨平台脚本宁可分开写。

### $\rm \S \, R1.3.4$ 客户端与服务器是角色，端口是分房号

首次定义于[计算机程序与开发全景](../01-基础观念/01-计算机程序与开发全景.md)的 §1.5：客户端发起请求，服务器提供能力——这是**一次交互中的角色**，不绑定物理机器：浏览器和本地后端可以运行在同一台电脑上，一个程序也能同时扮演两种角色（你的后端对浏览器是服务器、对数据库又是客户端）。一台机器跑多个网络服务时，IP 地址大致标识主机，**端口**帮助操作系统把收到的数据交给正确的进程——就像大楼（主机）里每个房间（端口）住着不同的服务：`127.0.0.1:3000` 前端开发服务器、`:8000` 后端 API、`:5432` 数据库。

**回到操作**：把模型变成验证动作。启动后端后，用 `ss -tlnp | grep 8000`（Bash）或 `Get-NetTCPConnection -LocalPort 8000`（PowerShell）确认它确实在监听；再用 `curl -s http://127.0.0.1:8000/`（PowerShell 对应 `Invoke-RestMethod`）发一个请求看响应。如果 8000 被占，先 `lsof -i :8000`（Bash）或查 `OwningProcess`（PowerShell）看占用者是谁——它可能正是你上次没关的旧服务，停掉它比换端口更干净；确认占用者之前不要随机杀进程。curl 的响应第一行是 HTTP 状态行（如 `HTTP/1.1 200 OK`），加 `-i` 会连同响应头一起显示。它能帮你区分两类失败：请求返回了 5xx，说明端口上有进程在监听但内部出错——查代码和日志；连接不上，则回到 R1.3.4 的端口模型，用 `ss`/`lsof` 先确认端口上到底有没有进程在监听。

### $\rm \S \, R1.3.5$ 软件安装的四个层次

首次定义于[软件、运行时、SDK与包管理器](../02-终端与工具/09-软件运行时SDK与包管理器.md)的 §9.3：“安装”不是一个动作，而是四个不同粒度的问题。系统级（apt、winget、brew）管理操作系统软件，需要管理员权限，装完放进系统 PATH；项目级（pip、npm）管理某个语言的第三方库，装进项目目录，不需要管理员；环境级（venv、nvm）隔离不同项目的运行时与依赖版本，靠修改 PATH 让当前 Shell 优先找到隔离环境；容器级（Docker）把整层用户态文件系统一起打包，第 30 章才展开。四层不是互斥的替代品——一个典型项目可能同时用到全部四层。

这个模型解决一类高频问题：“装了为什么不能用”。按层次逐一核对：运行时装了吗（`python --version`）？包装到哪个环境了（`python -m pip` 保证和 `python` 是同一个）？`Get-Command`/`command -v` 指向的到底是哪个可执行文件？PATH 里有没有这个目录？

**回到操作**：把模型套到贯穿项目上（第 9 章 §9.10 的流程）：先在系统级装好运行时（如 `winget install Python.Python.3.12`），再 `cd paper-manager && python -m venv venv` 建项目级隔离环境，激活（Bash 用 `source venv/bin/activate`，PowerShell 用 `venv\Scripts\Activate.ps1`）后 `pip install -r requirements.txt`，最后验证 `python -c "import flask; print(flask.__version__)"`。任一环节失败，都能用 R1.3.1 的 PATH 自查定位：是装错了层次、装错了环境，还是压根没装。还有一个 Windows 搭配经验（第 9 章 §9.3.5）：winget 管系统级基础运行时、Scoop 管日常命令行工具、pip/npm 管项目级库——三者各管一层、互不冲突，比“一个工具全装”更容易排查问题。

再回到第 9 章 §9.6 的 manifest 与 lockfile：打开任意一个真实项目的 `package.json` 与 `package-lock.json`（或 `pyproject.toml` 与 lock 文件），对比两者的字段——manifest 由人维护、声明版本范围（如 `"numpy>=1.24, <2.0"`），lockfile 由工具生成、锁定精确版本和校验和、包含间接依赖。两者都提交 Git，依赖目录（`node_modules/`、`venv/`）用 `.gitignore` 排除。

### $\rm \S \, R1.3.6$ 环境变量：进程的“出厂设置”

首次定义于[计算机程序与开发全景](../01-基础观念/01-计算机程序与开发全景.md)的 §1.3.4，在[终端、Shell与命令行](../02-终端与工具/02-终端Shell与命令行.md)的 §2.12 投入使用：环境变量是进程启动时传入的一组键值对，程序把它当作“出厂设置”——PATH 告诉它去哪找程序，`APP_ENV` 告诉它当前是开发还是生产，`PORT` 告诉它监听哪个端口。出厂设置比喻的边界要记住：设置发生在进程“出生”那一刻，子进程只继承父进程**当时**的设置。

所以两个推论必须成立。第一，在终端里 `export APP_ENV=development`（PowerShell 用 `$env:APP_ENV = 'development'`）只影响当前 Shell 及其之后启动的子进程，关掉终端就消失，不会传给已经运行的程序，也不会让正在运行的程序更新配置；要让每次开终端都带着同样的设置，只能写进 Shell 的配置文件（Bash 的 `~/.bashrc`、PowerShell 的 `$PROFILE`，见 §25.4）。第二，环境变量不是秘密保险箱——它们可能被进程、日志、调试信息或部署平台暴露，不要把密钥放进环境变量后提交进 Git。

**回到操作**：`echo $PATH`（PowerShell 用 `$env:PATH`）查看当前设置；`export APP_ENV=development` 后在同一个终端启动一个会打印该变量的程序——它能读到；换一个新终端再启动，它就看不到了。这就是“出厂设置”影响范围的直观证据。

语法对照放在一起看更清楚（第 25 章 §25.6）：查看环境变量，PowerShell 用 `$env:PATH`、Bash 用 `$PATH`；设置，PowerShell 用 `$env:VAR = 'x'`、Bash 用 `export VAR=x`。写脚本前先确认目标 Shell——把 Bash 的 `export` 原样写进 `.ps1` 会直接报错。

再补一个第 25 章 §25.4 的持久化示例：在 `~/.bashrc` 里写 `export PATH="$HOME/bin:$PATH"` 再 `source ~/.bashrc`——把新目录**追加在原有值前面**，地址簿就优先翻到它；动手前先 `echo $PATH` 记下原值，改错了可以恢复。

### $\rm \S \, R1.3.7$ 库、框架、运行时、SDK、API：按“谁调用谁”分层

首次定义于[计算机程序与开发全景](../01-基础观念/01-计算机程序与开发全景.md)的 §1.4：这五个词都和“使用别人提供的能力”有关，但层次不同，判断标准是**谁调用谁**。库（library）是你要主动调用的可复用实现——`std::sort(values.begin(), values.end())`；框架（framework）规定整体组织方式，在合适的时机调用你的代码（控制反转）——库像你拿起工具干活，框架像一条已经建好的生产线，你把部件放进指定位置；运行时（runtime）为某类程序提供执行环境——Python 解释器、JVM、浏览器里的 JavaScript 引擎；SDK（Software Development Kit）是开发某平台所需的工具集合，通常包含编译器、库、调试器和文档；API（Application Programming Interface）是组件之间“外部怎样使用”的约定，**不等于 HTTP**——C++ 函数签名、操作系统系统调用、浏览器 DOM API 都是 API。

| 概念 | 判断标准 | 本阶段见过的例子 |
|---|---|---|
| 库 library | 你的代码调用它 | `std::sort`、`requests` |
| 框架 framework | 它调用你的代码（控制反转） | 生产线比喻：你放部件，它运行 |
| 运行时 runtime | 执行某类程序的引擎 | Python 解释器、JVM |
| SDK | 开发某平台的工具集合 | Python 安装（解释器 + 标准库 + pip） |
| API | 组件间“外部怎样使用”的约定 | C++ 函数签名、HTTP 接口 |

**回到操作**：遇到一个新名词问两句话。第一句“它解决什么问题”——执行程序（运行时）、开发程序（SDK）、复用代码（库）、被它调用（框架）、约定用法（API）；第二句“谁调用谁”——你的代码调用它，是库；它调用你的代码，是框架。边界：现实中的边界并不绝对，React 官方称自己为库，但配合路由和构建生态会形成框架式体验——分类服务于理解，不是非此即彼的标签。

**本节自查**：不看正文，能独立说出——PATH 的查找顺序与三个边界；可执行文件与进程的关系；三个标准流的编号与用途；`>`/`>>`/`<`/`|` 各自的方向；端口在“主机-进程”之间扮演的角色；软件安装的四层与“装了为什么不能用”的核对顺序；环境变量临时设置的影响范围；判断库与框架的“谁调用谁”标准。说不全的，回读对应小节再继续。

## $\rm \S \, R1.5$ 易混点对照

以下是第一阶段读者最容易混淆或忘记的五处，用同一张表逐项区分；这张表可以抄下来当速查卡：

| 易混对象 | 区别 | 记忆锚点 |
|---|---|---|
| `pwd` / `ls` / `cd` / `cat` | `pwd`（Get-Location）回答“我在哪”；`ls`（Get-ChildItem）回答“这里有什么”；`cd`（Set-Location）移动“我在哪”，成功时无输出；`cat`（Get-Content）回答“文件里是什么” | 位置、内容、移动、读取各司其职；`cd` 成功无输出不代表没执行，用 `pwd` 验证 |
| 绝对路径 / 相对路径 | 绝对路径从根出发（`C:\` 或 `/`），任何位置都指向同一目标；相对路径从当前工作目录出发，同一写法在不同目录指向不同文件 | 项目内用相对路径（整个项目搬走仍有效）；系统固定资源用绝对路径；不确定先 `pwd`/`Get-Location` |
| 环境变量 / Shell 变量 | 环境变量是进程启动时传入的键值对，子进程继承；Bash 里 `VAR=x` 只是当前 Shell 的变量，`export VAR=x` 才进入环境；PowerShell 用 `$env:VAR='x'` | “export 才出门”；临时设置关终端即失，持久化写 `~/.bashrc`/`$PROFILE` |
| PowerShell / Bash | 命令名不同（`Get-ChildItem` 与 `ls` 只是别名关系）、变量语法不同（`$env:PATH` vs `$PATH`）、管道传递对象 vs 文本字节流；Bash 命令不能原样粘贴到 PowerShell | 报错先分三层：终端、Shell、程序；要上服务器的脚本写 Bash（或 Python） |
| 打包 / 压缩 | 打包（tar）把多个文件合并成一个，不减小体积；压缩（gzip）减小数据体积；`.tar.gz`=先打包再压缩；ZIP/7z 一步完成两者 | `.tar.gz` 一条 `tar -xzvf` 解压；`-t` 只查看清单不解压 |

这五处混淆有一个共同根源：把“名字”当成“功能”（`pwd`/`ls`/`cd`/`cat`）、把“起点”当成“全局”（路径）、把“作用域”当成“永久”（变量）、把“一种 Shell”当成“所有 Shell”、把“两个步骤”当成“一步”（打包/压缩）。拿不准时，先回到 R1.3 的模型里定位它属于哪一层、作用域多大、有几个步骤。

### $\rm \S \, R1.6.1$ 闭卷回忆清单答案

1. 终端是承载文字输入输出的窗口程序（Windows Terminal、VS Code 内置终端等）；Shell 是在终端里读取命令、解析语法并启动程序的软件（PowerShell、Bash、Zsh）；命令行程序是被 Shell 启动的程序（`git`、`python`、`g++`）。`echho` 报 “command not found” 是 Shell 层：按 PATH 查找不到名为 `echho` 的可执行文件。见 §2.7、§2.9。

2. PATH 是 Shell 按顺序查找可执行文件的目录清单（地址簿），找到第一个匹配就停止；当前目录通常不在 PATH 中，所以运行当前目录的程序要显式 `./app`；查看解析结果：PowerShell 用 `Get-Command python`，Bash 用 `command -v python`。见 §2.9。

3. stdin（0）默认键盘，stdout（1）默认屏幕，stderr（2）默认屏幕；`>` 把 stdout 覆盖写入文件，`>>` 追加，`<` 从文件读入 stdin，`|` 把左边 stdout 接到右边 stdin；退出码 0=成功，非 0=某种失败。见 §2.10、§2.11。

4. 绝对路径从根目录出发（Windows 盘符根、Unix `/`），相对路径从当前工作目录出发；`~` 是当前用户主目录的 Shell 简写，`.` 是当前目录，`..` 是上一级；隐藏扩展名导致你看到的文件名不是完整名称——“新建文本文档”改名 `data.json` 后实际是 `data.json.txt`，程序按错误的类型处理文件。见 §3.2、§3.4。

5. 所有者 rwx、所属组 r-x、其他用户 r--；`600` = `rw-------`（仅所有者读写）；目录缺 `x` 无法 `cd` 进入、也无法访问其中任何文件——`x` 对目录是“穿门”权限。见 §4.1。

6. 编辑器专注文本编辑（高亮、补全、搜索）；IDE 是集成工作台（编译调用、调试器、项目管理、代码智能）。断点让程序运行到指定行暂停；单步执行逐行推进观察状态；调用栈显示当前执行路径（“我是从哪被调来的”）。gdb 中 `step` 进入当前行调用的函数内部，`next` 执行完当前行（含函数调用）停在下一行。见 §5.1、§5.5。

7. 乱码的根源是“文件用编码 A 保存、你用编码 B 解读”——字节没变，解读方式变了；UTF-8 中 ASCII 字符仍用单字节且编码值一致，纯英文的 UTF-8 与 ASCII 文件字节相同；BOM 是文件开头的不可见字节（UTF-8 的 BOM 为 `EF BB BF`），UTF-8 不需要它，反而会破坏脚本首行和 JSON 解析；`.tar.gz` = 先 tar 打包再 gzip 压缩，`tar -xzvf archive.tar.gz` 一步解压。见 §6.2、§6.4。

8. grep 找行、sed 改行、awk 按列计算、jq 处理 JSON 的嵌套结构；`.*` 是贪婪匹配，默认吃尽可能多的字符（`<.*>` 会从第一个 `<` 吃到最后一个 `>`），在量词后加 `?` 成 `.*?` 非贪婪；注意 GNU grep 的 `-E` 不支持非贪婪，用 rg 或 Python。见 §7.2、§8.2、§8.3。

9. 运行时是执行某类程序的引擎（Python 解释器、Node.js、JVM）；SDK 是开发某平台所需的工具集合（通常含编译器、运行时、库、调试器）；包管理器负责查找、下载、安装、升级和记录包。裸 `pip` 可能属于另一个 Python，`python -m pip install` 保证装进当前 `python` 能 import 的位置。manifest（`package.json`、`pyproject.toml`）由人维护，声明“需要什么、版本范围”；lockfile（`package-lock.json`、`Cargo.lock`）由工具生成，锁定精确版本含间接依赖；两者都提交 Git。见 §9.1、§9.2、§9.6。

10. 临时设置只影响当前 Shell 进程及其之后启动的子进程，关终端即失，不影响已运行的程序；持久化：Bash 写 `~/.bashrc` 再 `source ~/.bashrc`，PowerShell 写 `$PROFILE`；`Ctrl+Z` 挂起程序（可 `fg`/`bg` 恢复），`Ctrl+C` 请求终止程序（已写入的文件或已发送的请求不会自动回滚）。见 §2.12、§25.3、§25.4。

11. glob 的 `*` 匹配任意长度的任意字符（文件名的层面），正则的 `*` 表示“前一个模式出现零次或多次”（文件内容的层面）；`?` 匹配恰好一个任意字符，`[0-9]` 匹配方括号内任意一个字符。两者是两套系统，Shell 的文件通配是 glob，`grep`/`sed` 用的是正则。见 §3.5、§6.6。

12. `ln -s target link` 创建符号链接——一个内容为“目标路径”的小文件，删除目标后链接变成断链（悬空）；`ln target link` 创建硬链接——两个文件名指向同一个 inode，删除任意一个文件名，数据仍通过另一个名字存在；硬链接不能跨文件系统、不能指向目录。见 §3.6。

高频卡点提示：Q1 卡在“终端与 Shell 混为一谈”——报错先分三层；Q4 卡在“以为相对路径是全局的”——不确定先 `pwd`；Q5 卡在“只看文件不看目录”——`x` 对目录是穿门权限，父目录没有就进不去；Q7 卡在“BOM 与编码混淆”——BOM 是文件开头的字节，编码是解读规则；Q9 卡在“pip 与 python 分家”——永远 `python -m pip`。

```bash
#!/bin/bash
set -euo pipefail
DATA_FILE="${1:-papers.txt}"

```

4. 验证完整性：`sha256sum dataset.tar.gz`（PowerShell 用 `Get-FileHash dataset.tar.gz`），与发布方给的 SHA256 值逐字符比对，一致才说明文件完整；看内容清单：`tar -tvf dataset.tar.gz`（zip 用 `unzip -l`）。先看清单再解压，是为了确认里面没有 `../` 路径或绝对路径等恶意条目，并把它解压到临时目录而不是重要目录。见 §6.4、§6.7。

5. `awk '{print $2}' server.log | sort | uniq -c | sort -rn`——awk 取第二列，`sort` 让相同级别相邻，`uniq -c` 计数去重，最后一个 `sort -rn` 按次数降序；预期输出形如 `12 ERROR`。见 §8.2。

6. `-exec` 写法：`find src/ -name '*.cpp' -exec clang-format -i {} \;`（`{}` 是当前文件路径，`\;` 是命令结束符）；`xargs` 写法：`find src/ -name '*.cpp' -print0 | xargs -0 clang-format -i`（`-print0`/`-0` 用 null 分隔，避免文件名含空格出错）。文件少时两者差异不大，文件多时 `xargs` 一次传多个文件名、显著更快。见 §7.2。

7. `Test-Path 'D:\data\papers.json'` 返回 True/False；查看隐藏状态用 `Get-ChildItem -Force 'D:\data\papers.json'`，或 `Get-ChildItem -Hidden` 列出所有隐藏项目。见 §3.2、§3.3。

8. Bash：`tail -f server.log`；PowerShell：`Get-Content server.log -Tail 10 -Wait`。`cat` 会把大文件一次性刷满屏幕淹没终端，所以看大文件用分页工具（`less`）或只取尾部（`tail`）。见 §2.6、§7.2。

**组二**

1. 三条证据：(1) `command -v python`（PowerShell 用 `Get-Command python`）看是否解析到可执行文件、解析到哪个；(2) `echo $PATH`（PowerShell 用 `$env:PATH`）看安装目录是否在 PATH 中；(3) `python --version` 确认版本。最常见两类原因：安装目录不在 PATH 里；安装未完成或装到了另一个用户/另一个环境。见 §2.9、§9.4。

2. 顺序：`ls -l script.sh` 确认文件存在并看权限位与所有者 → `whoami` 确认当前身份 → 对照权限串判断缺哪个 `r/w/x` → 检查父目录的 `x`（可用 `namei -l` 逐级看）→ 确认原因后才考虑提权。你是所有者却缺权限，最常见是缺 `x`，或文件从别处复制带回了过紧的权限。见 §4.1。

3. 最可能的原因：系统里有两个 Python，`pip` 属于 A，`python` 命令启动的是 B——用 A 的 pip 装的包，B 的 `import` 找不到。诊断：`pip --version` 与 `python --version` 对照、`command -v pip` 与 `command -v python` 看路径；修复：`python -m pip install requests`。见 §9.1。

4. Bash：`lsof -i :8080`（或 `ss -tlnp | grep 8080`）；PowerShell：`Get-NetTCPConnection -LocalPort 8080` 取 OwningProcess，再用 `Get-Process -Id <PID>` 查看。停止之前先确认占用者是什么程序、是否应继续运行（比如可能正是你自己上次没关的服务），再决定停止它或换端口。见 §7.4。

5. 原因是文件被保存成了 CRLF（`\r\n`），`\r` 被当成了命令名或解释器路径的一部分。确认：`cat -A script.sh`——行末出现 `^M$` 就是 CRLF（VS Code 右下角也会显示 CRLF）；转换：`dos2unix script.sh`（反向用 `unix2dos`）。见 §3.7、§6.3。

6. 可能是 inode 耗尽——文件系统能创建的文件数量达到上限（大量小文件如 `node_modules` 会占满），即使空间还有余量；用 `df -i` 确认 inode 使用情况。见 §7.4。

7. 两个终端从不同的地方加载环境配置：VS Code 终端继承了 VS Code 本身的环境（包括它配置的 Python 路径），独立的 Windows Terminal 从系统设置加载；差异源头通常是 PATH 的修改方式不同（系统级、用户级、Shell 配置文件）。见 §9.4。

**组三**

1. 统一改名是“改文本”→ sed；按列统计是“算数据”→ awk。JSON 有嵌套结构和多行字符串，按行处理的 sed/awk 会误伤或漏掉，jq 理解 JSON 结构，能正确提取嵌套字段、筛选和变换。见 §8.2。

2. “能编译”=工具链成功生成产物；“能启动”=操作系统成功创建进程且程序没有立即退出；“功能正确”=在明确输入和边界条件下符合需求；“可以交付”=配置、文档、部署、监控和恢复方案齐全。OJ 的 Accepted 大致对应受控环境中的“功能正确”。见 §1.8。

3. 全局安装适合“你作为用户要用的工具”（如 `httpie`、`black`），而不是项目依赖；项目依赖装进 venv/`node_modules/` 实现版本隔离与可复现（manifest + lockfile 记录依赖），换机器或换人时按记录重建即可。见 §9.5。

4. 语言服务做解析和类型检查——在保存时就报告语法错误、类型不匹配、未使用变量等诊断，但不产生可执行文件；链接错误、运行时错误和真正的行为正确性只能在完整构建与运行中暴露。所以“编辑器没报错”只说明通过了语言服务这一层检查。见 §5.3。

5. 先用 `ls *.log`（PowerShell 用 `Get-ChildItem *.log`）确认匹配了哪些文件，再执行删除。通配符一次匹配多个文件，模式写错或当前目录不对时会一次删除大量文件，且删除不可恢复（没有 Git 备份时）；带通配符的删除、覆盖、移动命令，执行前都要先只读验证匹配集合。见 §3.5。

6. 前后端 API 交换用 JSON（所有语言原生支持）；表格数据导入导出用 CSV（Excel 和数据分析库的直接输入）；项目配置用 YAML 或 TOML（人写友好、可注释）。Excel 打开 CSV 会自动转换格式——长数字变科学计数法、前导零被删、日期被“修正”，所以查看原始 CSV 用纯文本编辑器。见 §6.5。

7. 顺序：语言服务扩展是否安装、工作区是否打开了整个项目目录而不是单个文件、编译配置是否正确（如 `compile_commands.json`）——语言服务需要正确的项目配置才能准确分析，且它不产生可执行文件，链接等问题仍要完整构建才能暴露。见 §5.2、§5.3。
