# $\rm Chapter \, 7$ 连接管理与时延：握手、挥手与 TIME_WAIT

前两章把 TCP 的「内容」讲完了：字节流怎么可靠、怎么不堵死网络。还剩「连接」本身：两端从未知到确认彼此、再到好聚好散的全过程。它不只是仪式：握手决定了每一次新连接的固定开销，挥手留下的 TIME_WAIT 决定了高并发短连接服务能不能活，而把一次请求的时延拆开看，你会发现大头往往根本不在传输。本章把这三件事接起来。

> **开始前自检**：本章假设你已经会：
>
> 1. □ 说出 TCP 是「有连接」的字节流、UDP 无连接（§4.2）；
> 2. □ 解释序列号与确认号的累积确认（§5.2）；
> 3. □ 知道 DNS 把域名翻成 IP（计算机速通 §24.1）；
> 4. □ 用 `socket.create_connection` 建过客户端连接（§1.6）。

## $\rm \S \, 7.1$ 三次握手：为什么是三

TCP 建连走三条报文（俗称三次握手）：

1. 客户端发 **SYN**，携带自己的初始序列号 ${x}$；
2. 服务端回 **SYN+ACK**：确认 ${x+1}$，同时带上自己的初始序列号 ${y}$；
3. 客户端回 **ACK**：确认 ${y+1}$。此后双方进入 ESTABLISHED。

为什么两次不够？若只有「请求—应答」，服务端无法确认「客户端能收到我发的任何东西」，而 TCP 承诺双向可靠，必须双向各验证一次「我发你能收」。为什么四次不必？中间两条（服务端的 ACK 与 SYN）方向相同、可以合并，拆开只是慢不换信息。握手报文里还有窗口与 MSS 协商（§5.5 的 rwnd 初值、最大段长），一次握手把传输参数全谈好。连接的本质是**双方初始化并互相确认状态**，不是物理上接了根线。

握手期间服务端同时维护两张队列：**半连接队列**（收到 SYN、还没等到第三条 ACK）与**全连接队列**（三次握手齐、等应用 `accept` 取走）。`accept` 慢不会拖握手（内核替你完成前两条并放进全连接队列），所以「客户端连上了但服务端没反应」往往是应用没及时 `accept`（操作系统分册 §9.3 的队头阻塞在服务器侧的变体），不是网络问题。

SYN 洪水攻击顺带说清：攻击者狂发 SYN 不回第三条，半连接队列被占满、真用户连不进。防御（SYN cookie：把连接状态编码进 SYN+ACK 的序列号里、服务端不再存半开状态）一瞥即可。它正是利用了「连接状态只在双方手里」这一点：队列没了，状态还在密码学承诺里。

## $\rm \S \, 7.2$ 实测：一次握手多少钱

回环上握手只是两次函数调用来回，真实网络里是一个 RTT。实测对比：

```python
import socket, time, statistics
def conn_time(host, port, n=5):
    ts = []
    for _ in range(n):
        t0 = time.perf_counter()
        s = socket.create_connection((host, port), timeout=5)
        ts.append((time.perf_counter() - t0) * 1000); s.close()
    return min(ts), statistics.median(ts)
srv = socket.socket(); srv.bind(('127.0.0.1', 9611)); srv.listen(16)
print('回环:', conn_time('127.0.0.1', 9611))       # srv 需并发 accept，简化版见注
```

本机实测：**回环 connect 最快 0.30 ms、中位 0.62 ms**；而到清华主页（§7.5 实测）的握手是 **13.6 ms**，真实广域网一个 RTT 的量级。数量级结论：握手 ≈ 1 × RTT（第三条 ACK 可以和数据同发，不单独等）。

再看「一次 GET 到底慢在哪」。对 `www.tsinghua.edu.cn` 首页分四段计时（本机实测）：

```text
DNS 47.6 ms | TCP握手 13.6 ms | 请求+首字节 7.5 ms | 合计≈68.7 ms
```

读数出人意料：**DNS 比握手贵 3.5 倍、比服务器处理贵 6 倍**，首屏性能优化里「DNS 预解析」「连接复用」排在前头，就是这两段账决定的（§7.5）。

## $\rm \S \, 7.3$ 四次挥手与 TIME_WAIT：谁先关谁买单

断连比连上啰嗦。TCP 全双工，两个方向要各自关：

1. 主动方发 **FIN**（「我发完了」）；
2. 被动方 **ACK**（「知道了」，但我可能还有数据没发完）；
3. 被动方数据发完，也发 **FIN**；
4. 主动方 **ACK**，随后进入 **TIME_WAIT**，等 ${2 \cdot \mathrm{MSL}}$（报文最大生存时间的两倍，Linux 上合计约 60 秒）才真正释放端口。

中间两条不能合并（ACK 与 FIN 之间可能还隔着数据），所以是四次。关键角色是 TIME_WAIT，它由**主动关闭方**承担，两个理由：最后的 ACK 若丢了，对端会重发 FIN，得有人在岗应答；同时让旧连接的迷路报文在网络里自然死亡，不会串进复用同四元组的新连接。

实测看它的堆积（服务端主动关，本机 Windows）：

```python
import socket, subprocess
srv = socket.socket(); srv.bind(('127.0.0.1', 9613)); srv.listen(64)
for i in range(30):
    c = socket.create_connection(('127.0.0.1', 9613), timeout=2)
    srv.accept()[0].close()          # 服务端主动关 → 服务端侧进 TIME_WAIT
    c.close()
r = subprocess.run(['netstat', '-ano', '-p', 'tcp'], capture_output=True)
tw = [l for l in r.stdout.decode('gbk', errors='replace').splitlines()
      if 'TIME_WAIT' in l and ':9613' in l]
print('TIME_WAIT 条数 =', len(tw))
```

输出：**`TIME_WAIT 条数 = 30`**，30 个短连接，30 条 TIME_WAIT 挂一分钟。线性外推：每秒一千个短连接的服务端，一分钟内要挂约六万条 TIME_WAIT，四元组（源 IP、源端口、目的 IP、目的端口）可能耗尽、端口分配失败。三条工程出路：

1. **谁长谁主动关**：让客户端（连接多、分散）先发 FIN，TIME_WAIT 分散到海量客户端，服务端不背锅，HTTP `Connection: keep-alive` 的默认行为正是如此；
2. **连接复用**（§7.5）：根本不发 FIN，TIME_WAIT 无从产生；
3. **调优端口范围 / `SO_REUSEADDR`**：缓解而非消除。前者扩池子，后者允许新监听套用旧四元组（Linux 另有 `tcp_tw_reuse`，仅出站方向）。

「消灭 TIME_WAIT」不是选项：它是正确性机制，误关会引入旧报文串线，「看到 TIME_WAIT 多」的正解永远是改连接策略，不是删等待。

## $\rm \S \, 7.4$ 时延的组成：一次请求慢在哪

把任意一次「客户端 → 服务器 → 回包」的总时延拆成四段：

1. **传播时延（propagation）**：物理距离 ÷ 光速（光纤中约 ${2 \times 10^{8}\ \mathrm{m/s}}$）。北京到上海往返约 2000 km，光速下限就是 20 ms，**地理决定的地板，谁也优化不掉**；
2. **传输时延（serialization）**：报文长度 ÷ 链路带宽。1500 B 在 1 Gbps 链路上约 0.012 ms，现代带宽下通常可忽略；
3. **排队时延（queueing）**：路由器/交换机缓冲里的等待，拥塞时暴涨，是波动的主要来源（§6 的拥塞就是它）；
4. **处理时延（processing）**：协议栈与应用的计算，含 DNS 查询、握手（§7.2）、TLS（§9）这些「一次性的税」。

工程口诀：**固定成本（DNS + 握手 + TLS）看复用，可变成本（排队）看拥塞，地板（传播）看部署位置**。CDN 的本质就是把第 1 项从「跨洲」压到「同城」；HTTP/3 的 0-RTT 攻的是第 4 项里的握手税（§8.6）。

## $\rm \S \, 7.5$ 连接复用：省的到底是哪笔钱

§7.2 的分解给出了复用的账本。短连接每次请求：DNS（47.6）+ 握手（13.6）+ 处理（7.5）≈ 68.7 ms；keep-alive 长连接：只有处理 7.5 ms，**同一条连接上第二个请求起，省掉的是前两笔共约 61 ms**。再叠一层 TLS（§9 实测另计），复用的收益还要翻倍。

但复用不是免费的：长连接占着服务端一个 fd 与一套缓冲（操作系统分册 §9.5 的 C10K 账），所以实践中按「空闲超时 + 最大请求数」折中（Nginx 默认 75 秒 / 1000 次）。到第 8 章你会看到 HTTP 从 1.0 到 1.1 到 2/3 的演进，半程都在打磨这一笔账。

## $\rm \S \, 7.8$ 本章自测答案

### $\rm \S \, 7.8.1$ 关键概念回顾答案

1. 第一次：客户端证明「我能发」；第二次：服务端证明「我能收也能发」；第三次：客户端证明「我能收你发的」。两次缺最后一验（服务端不知自己能否被收到）；四次中间两条同向可合并，慢而无新信息。（§7.1）
2. 主动关闭方。防两件事：最后的 ACK 丢了要有人应答对端重发的 FIN；旧连接的迷路报文要在网络中寿终，不能串进复用同四元组的新连接。（§7.3）
3. 实验里服务端对每个连接都主动 `close`：每个连接的主动方（服务端）各留一条 TIME_WAIT，30 个连接 30 条，一一对应。（§7.3）
4. 传播时延是地板（光速与距离决定）；排队时延是波动主因（拥塞时暴涨）。（§7.4）
5. 省掉 DNS 与 TCP 握手（加 TLS 的话还有 TLS 握手）这两笔「固定税」，只留处理段。对价：服务端为每条长连接占住 fd 与内存，需要空闲超时与最大请求数约束。（§7.2、§7.5）

### $\rm \S \, 7.8.2$ 应用与辨析答案

1. 诊断：确认 TIME_WAIT 挂在服务端侧（服务端在主动关闭）。处置：① 让客户端先关（改关闭策略/keep-alive 语义）；② 连接复用从根上消灭 FIN；③ 扩源端口范围、`SO_REUSEADDR` 缓解。「治错了病」的是删等待/改内核强行回收 TIME_WAIT，那是把正确性机制当故障清理，旧报文串线风险自担。（§7.3）
2. 同城 ${4 \times 2 = 8\ \mathrm{ms}}$，跨洲 ${4 \times 200 = 800\ \mathrm{ms}}$，同一协议跨洲慢 100 倍。教训：往返次数（round trips）是协议的自有属性，地理只做乘数；高延迟链路上要减少串行往返（合并请求、流水线、连接复用），而不是只压带宽。（§7.4）
3. 1 秒内旧报文可能还没死透（MSL 本义就是报文最大生存时间），四元组立刻复用时，上个连接的迟到数据会被新连接当作有效序列号区间接收，正是 2MSL 防的串线。且对端重发的 FIN 若在 1 秒后才到，已无人应答，对端将卡在 LAST-ACK 反复重试。并发的正解是改连接策略（§7.3 三条出路），不是砍等待时长。（§7.3）
