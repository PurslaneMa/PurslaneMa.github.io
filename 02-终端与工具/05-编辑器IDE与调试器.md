# $\rm Chapter \, 5$ 编辑器、IDE 与调试器

> 你已经能在终端中导航目录、操作文件和编译程序了。但到目前为止，你写代码可能还在用 OJ 页面自带的文本框，或者一个只比记事本多语法高亮的轻量编辑器。真实开发中，花在“理解代码在做什么”和“找出它为什么不是在做你认为它在做的事”上的时间，远超“敲代码”本身。编辑器和调试器就是为这两件事设计的。

> **开始前自检**：本章假设你已经会：
>
> - □ 用 `cd`、`ls`、`cat` 在终端中导航目录和操作文件（§2.5、§2.6）
> - □ 手动编译并运行过一个 C++ 程序（§1.9）
> - □ 知道源码是文本文件、能被编辑器修改（§1.2）
> - □ 制造并读过编译错误信息（§1.9）

## $\rm \S \, 5.1$ 编辑器与 IDE：不是非黑即白

### $\rm \S \, 5.1.1$ 编辑器做一件事：编辑文本

**编辑器**的核心任务是创建和修改文本文件——包括代码、配置、文档和数据。它提供：

- 语法高亮：把关键字、字符串、注释涂上不同颜色，帮助快速扫读；
- 自动缩进和括号匹配：减少格式错误；
- 多文件搜索和替换：在整个项目中找到某个函数的所有调用处；
- 多光标和代码片段：减少重复键入。

你很可能已经在用 VS Code、Sublime Text、Notepad++、Vim 或其他编辑器。它们各有偏好，但共同点是**专注于文本编辑本身**。

### $\rm \S \, 5.1.2$ IDE 是一个集成工作台

**IDE**（Integrated Development Environment，集成开发环境）在编辑器基础上，内置或紧密集成了：

- **编译器/解释器调用**：按一个快捷键构建项目，不需要手动切到终端敲 `g++`；
- **调试器**：设置断点、单步执行、查看变量值，都在同一个窗口内；
- **项目管理**：理解多文件项目结构，知道哪个文件属于哪个目标；
- **代码智能**：跳转到定义、查找所有引用、自动重命名、类型提示；
- **测试运行器**：运行和查看测试结果，点击失败项直接跳到对应代码行。

常见 IDE：Visual Studio（注意不是 VS Code——它们是两个不同的产品）、CLion、Eclipse、IntelliJ IDEA。VS Code 本身是编辑器，但通过安装扩展可以接近 IDE 的体验。

### $\rm \S \, 5.1.3$ 怎么选

| 场景 | 倾向 |
|---|---|
| 单文件 C++ 算法练习 | 编辑器已经足够 |
| 多文件 C++ 项目，需要调试复杂崩溃 | IDE 或配置了调试扩展的编辑器 |
| Python 脚本或数据处理 | 编辑器 + 终端 |
| 大型 Python/Web 项目 | 编辑器（扩展丰富）+ 独立终端工具 |
| 不确定 | 从编辑器开始，缺什么加什么；不必一开始就配齐所有扩展 |

关键不是选“最好的工具”，而是**知道自己当前在用什么，它提供了哪些可以省时间的能力，以及你缺了什么**。

## $\rm \S \, 5.2$ 工作区：你的项目上下文

大多数编辑器和 IDE 都有“工作区”或“项目”的概念。打开一个目录（而不是单个文件）作为工作区后，工具才能理解：

- 这个目录下的文件彼此有什么关系；
- 头文件在哪里、`#include` 应该从哪找；
- 哪些文件是源码、哪些是构建产物或第三方库；
- 全局搜索和重构的范围是什么。

在 VS Code 中，用 `File → Open Folder` 打开项目目录；在终端中也可以用 `code` 命令打开，路径换成你自己的练习目录：

```powershell
# PowerShell 5.1
code D:\practice\demo
```

```bash
# Bash（WSL/Linux/macOS）
code ~/practice/demo
```

> `code` 命令不是 VS Code 默认就有的：先在 VS Code 里执行一次 `Ctrl+Shift+P → "Shell Command: Install 'code' command in PATH"`，之后终端才能调用它。还没有练习目录的话，先在终端创建再打开（例如 Bash 中 `mkdir -p ~/practice/demo`，PowerShell 中 `New-Item -ItemType Directory -Force D:\practice\demo`）。

“只打开一个 `.cpp` 文件”和“打开包含 `CMakeLists.txt`（CMake 的构建配置文件，第 15 章会学）的整个目录”，IDE 能提供的帮助完全不同。如果你抱怨“为什么编辑器不会提示我这个函数在哪定义的”，先检查是否打开了整个项目目录而不是单个文件。

## $\rm \S \, 5.3$ 语言服务：编辑器变聪明

你在编辑器里输入 `std::` 后弹出补全建议，或函数名下出现波浪线——这些都不是编辑器自带的功能，而是**语言服务**（Language Server 或内置语言引擎）在后台分析你的代码。

语言服务通过编译器的前端技术（解析、类型检查）来理解代码，但不产生可执行文件。它提供的典型能力：

- **诊断**：语法错误、类型不匹配、未使用变量——在你编辑时就出现（不必等到编译）；
- **跳转定义**：按住 Ctrl 点击一个函数名，跳到它被定义的位置；
- **查找引用**：右键 → “查找所有引用”，列出项目中所有调用了这个函数的地方；
- **悬停信息**：鼠标悬停在变量上，显示它的类型和声明位置；
- **重命名**：改一个变量名，自动更新项目中所有引用——不是文本替换，而是根据语义理解。

对于 C++，`clangd` 和 Visual Studio 的 IntelliSense 是常见的语言服务实现。你不需要知道它们内部怎么工作，但需要知道：

1. 它们不是魔法——需要正确的编译配置才能准确分析：`compile_commands.json` 是记录每个源文件真实编译命令（宏定义、头文件搜索路径等）的清单，语言服务读它才能按构建时的方式解析代码。该文件由构建系统生成，第 15 章学过 CMake 后自然会得到；现在还没有它时，以编译器实际输出为准；
2. 如果语言服务给出大量红色波浪线而编译却成功了，可能是配置不匹配——以编译器实际输出为准；
3. 如果语言服务完全没有反应，检查是否安装了对应语言的扩展，以及工作区是否正确打开。

## $\rm \S \, 5.4$ 格式化与静态检查：机器帮你统一风格

### $\rm \S \, 5.4.1$ 代码格式化

大括号换不换行、缩进用空格还是 Tab、`if` 后面空几个空格——这些无关程序正确性，但不一致的风格会拖慢阅读速度，并在 Git diff 中制造大量无意义的“修改”。

**格式化工具**自动将代码调整为统一风格：

- C++：`clang-format`
- Python：`black`、`ruff format`
- 前端：`prettier`

最小验证（WSL/Linux/macOS 的 Bash；`clang-format` 随 LLVM/Clang 安装，安装方式见第 9 章）。在任意 C++ 源文件所在目录运行：

```bash
clang-format main.cpp | diff main.cpp -   # 打印格式化前后的差异；无输出表示已符合默认风格
```

`clang-format` 默认只把结果写到标准输出，不改动原文件；确认差异可以接受后，用 `-i` 原地改写：`clang-format -i main.cpp`。想固定团队风格，就在项目根目录放一个 `.clang-format` 配置文件。

大多数编辑器可以配置为“保存文件时自动格式化”。你应该开启这个功能——它消除了关于代码风格的团队讨论，让你把注意力放在逻辑上。

### $\rm \S \, 5.4.2$ 静态检查（Linting）

格式化工具有时也做简单检查，但**静态检查**专门在不运行程序的情况下发现潜在问题：

- 声明了变量但未使用；
- 可能的空指针解引用；
- 数组越界的潜在风险；
- 条件判断中的逻辑冗余；
- Python 中未定义的变量名。

对 C++，编译器警告（`-Wall -Wextra`）本身就是最基础的一层静态检查。对 Python，`ruff` 和 `mypy` 分别负责风格/简单错误和类型检查。

**静态检查在真正编译或运行之前就发现问题**。对单个翻译单元（一个源文件和它包含的头文件），静态检查通常秒级返回；而整项目编译可能数十秒到数分钟。这个差距使它适合挂在保存动作上实时运行，不必每次等一轮完整构建才知道结果。

> **经验规则**：打开编译器的 `-Wall -Wextra`（或对应语言的最严格警告级别），并把警告当作错误来处理。OJ 评测不会因为“你有一个未使用变量”扣分，但真实项目中每一个警告都可能在特定条件下变成 bug。

## $\rm \S \, 5.5$ 调试器：让时间暂停

到目前为止，你排查程序错误可能主要靠：

- 在代码中插 `cout << "here" << endl;`；
- 输出中间变量看值对不对；
- 凭经验和直觉猜哪里出错了。

这些方法在百行以内的算法题中勉强够用。但在千行、万行的项目中，错误可能出现在你从未怀疑的地方，而 `cout` 调试法每次都要重新编译运行。

**调试器**让你在程序运行到某一行时暂停下来，检查所有变量的当前值，然后一行一行地推进，观察状态的变化。

### $\rm \S \, 5.5.1$ 调试的心智模型

```mermaid
flowchart LR
    A["设断点<br/>怀疑出错的位置"] --> B["运行到断点<br/>程序暂停"]
    B --> C["检查变量<br/>是否符合预期？"]
    C -->|符合| D["单步推进<br/>观察状态变化"]
    C -->|不符合| E["你找到了 bug<br/>修正代码"]
    D --> F["在哪一步<br/>状态开始异常？"]
    F -->|找到| E
    F -->|还没| D
```

调试不是“运行→出错→重来”的循环，而是**可控的实验**：每次只改变一个条件（前进一步、更改变量值），观察结果。这比盲目插 `cout` 然后从头重跑高效得多，因为你验证的是假设，而不是靠重跑碰运气。

### $\rm \S \, 5.5.2$ 核心概念

- **断点**（breakpoint）：你标记的“停在这里”的位置。程序运行到这一行时自动暂停，此时程序还没有执行这一行。
- **单步执行**（step）：暂停后可以逐行推进——
  - **Step Over**：执行当前行（包括其中的函数调用），停在下一行。
  - **Step Into**：如果当前行调用了你写的函数，进入函数内部停在第一行；如果是系统库函数，通常跳过。
  - **Step Out**：执行完当前函数的剩余部分，返回调用处。
- **调用栈**（call stack）：显示“我是从哪被调用的”。`main()` 调用了 `parse()`,`parse()` 调用了 `readFile()`，调用栈就像函数调用的面包屑，告诉你当前执行为什么会走到这里。
- **变量观察**（watch）：选中一个变量，每到一个暂停点就显示它的当前值。对于复杂对象，可以展开看每个成员的当前值。

### $\rm \S \, 5.5.3$ 最小例子：gdb 调试 C++ 程序

本节在 WSL/Linux/macOS 的 Bash 中做，需要 `g++` 和 `gdb`（GNU Debugger）。Windows 原生环境默认没有这两个程序：先按第 9 章安装 MinGW-w64，或改用 [5.5.5](#555-windows-调试器补充visual-studio-与-windbg) 中 Visual Studio 的图形调试器；在 WSL 里做本节最省事。

把下面的代码保存为 `sum_array.cpp`，在终端里 `cd` 到它所在的目录，再执行后面的命令。这段程序有 bug：

```cpp
// sum_array.cpp
#include <iostream>

int sum(int* arr, int n) {
    int total = 0;
    for (int i = 0; i <= n; i++) {  // bug: 应该是 i < n
        total += arr[i];
    }
    return total;
}

int main() {
    int data[] = {1, 2, 3, 4, 5};
    int result = sum(data, 5);
    std::cout << result << '\n';
    return 0;
}
```

编译时加上调试信息（`-g` 参数告诉编译器把源码行号、变量名等嵌入可执行文件）：

```bash
g++ -g -std=c++17 -Wall -Wextra sum_array.cpp -o sum_array
```

成功判据：命令没有输出，当前目录出现可执行文件 `sum_array`（`ls -l sum_array` 可见）；若提示 `command not found`，说明编译器不在 PATH 中，先回到第 9 章完成安装。

启动 gdb：

```bash
gdb ./sum_array
```

gdb 启动后，你会看到一个 `(gdb)` 提示符。以下是最常用的几个命令：

```text
 break sum          ← 在 sum 函数入口设断点
 run                ← 运行程序，停在断点处
 print n            ← 查看变量 n 的值
 print arr[5]       ← 访问越界元素——可以看到它是什么
 step               ← 单步执行（进入函数）
 next               ← 单步执行（跳过函数调用）
 continue           ← 继续运行到下一个断点
 backtrace          ← 查看调用栈
 quit               ← 退出
```

运行这个程序并观察 `i` 在最后一次循环时的值，你会直接看到 `i=5` 时访问了 `arr[5]`——一个越界位置。

> **发现 bug 的方式不是靠猜**，而是：设断点→观察变量→单步推进→发现“这里 i 的值不应该等于 n”。你不需要重编译加 `cout` 就能验证假设。

### $\rm \S \, 5.5.4$ 在 VS Code 中使用调试器

命令行 gdb 的手感类似裸终端——功能强大但不如图形界面直观。VS Code 的调试面板让你通过鼠标点击设置断点（代码行号左边点一下出现红点），然后在侧栏看到所有变量和调用栈。

需要两个文件配合：

1. **调试配置**（`launch.json`）：告诉 VS Code 用什么调试器、调试哪个可执行文件；
2. **构建任务**（`tasks.json`）：定义如何编译——因为调试前通常需要先构建。

VS Code 的 C++ 扩展提供了配置向导：打开 `Run and Debug` 面板 → `create a launch.json file` → 选择 `C/C++: g++`，它会生成模板，通常只需调整 `program`（要调试的可执行文件）这一项。

手写时，最小内容如下。在当前项目目录下新建 `.vscode/launch.json`（`launch.json` 是标准 JSON，不能写注释）：

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "g++ 调试 sum_array",
      "type": "cppdbg",
      "request": "launch",
      "program": "${workspaceFolder}/sum_array",
      "args": [],
      "cwd": "${workspaceFolder}",
      "MIMode": "gdb",
      "miDebuggerPath": "gdb",
      "preLaunchTask": "build"
    }
  ]
}
```

两处要按环境改：`program` 指向实际产物（Windows 原生下 MinGW 产出的文件带 `.exe` 后缀），`miDebuggerPath` 填 gdb 的完整路径（示例假定它已在 PATH 中）。`preLaunchTask` 的 `"build"` 必须与 `tasks.json` 中某个任务的 `label` 完全一致——`tasks.json` 的完整写法在 [5.10.3](#5103-tasks把重复命令变成一键操作) 给出，可以先补上那一节再回来；不想配构建任务就删掉 `preLaunchTask` 一行，每次手动编译后再按 `F5`。

成功标志：按 `F5` 后程序在断点处停住，左侧 `VARIABLES` 面板列出当前作用域中变量的值；若提示找不到任务 `build`，说明 `tasks.json` 里还没有这个 `label`。


### $\rm \S \, 5.5.5$ Windows 调试器补充：Visual Studio 与 WinDbg

除 gdb 外，Windows 生态有两个重要的调试器你至少要知道存在：

- **Visual Studio 内置调试器**：如果你安装了 Visual Studio（不是 VS Code），按 F5 即可启动调试。它的图形界面比命令行 gdb 更易上手——鼠标悬停看变量值、拖拽黄色箭头改变执行位置、条件断点（“i==100 时才停”）用右键菜单设置。概念和 gdb 完全相同，只是操作方式不同。
- **WinDbg**：微软的高级调试器，可以调试内核、驱动和 crash dump。日常应用开发中很少直接用，但当你遇到蓝屏死机（BSOD）分析 `.dmp` 文件时会用到它。

### $\rm \S \, 5.5.6$ 不只是调试器：Sanitizer 和内存检查工具

编译器本身也内置了强大的运行时错误检测——比调试器更自动化，不需要手动设断点：

```bash
# g++ 和 clang++ 都支持的 Sanitizer 系列（WSL/Linux/macOS 的 Bash）
g++ -fsanitize=address -g program.cpp -o program    # AddressSanitizer：检测越界、use-after-free、内存泄漏
g++ -fsanitize=undefined -g program.cpp -o program  # UBSan：检测有符号整数溢出、空指针解引用、非法移位
g++ -fsanitize=thread -g program.cpp -o program     # ThreadSanitizer：检测数据竞争
```

UBSan 报告的是**有符号**整数溢出；无符号整数的回绕由标准定义为取模，是合法行为，不会被报告。

编译时加上这些标志，程序运行到出错位置时会自动打印文件名、行号和原因——不需要你手动设断点。前提是程序用 `-g` 编译过，否则输出里只有地址和函数名，没有行号。多数 OJ 沙箱未安装 sanitizer，这组工具主要在本机开发时使用。

**Valgrind**（Linux/WSL）是另一套经典的内存检查工具，不需要用 sanitizer 重新编译就能检测内存泄漏和使用未初始化值：

```bash
valgrind --leak-check=full ./program   # 程序同样要用 -g 编译；否则只有地址和函数名，没有行号
```

输出会告诉你哪一行 `malloc`/`new` 的内存没有被释放，以及哪一行访问了已释放的内存。


### $\rm \S \, 5.5.7$ 不该调试什么

能通过静态检查、类型系统或编译器警告发现的问题，不要用调试器去查——那好比为了找桌面上的一枚硬币而把整张桌子拆开：工具本身没错，只是为这个问题付出的代价不成比例。反过来，涉及复杂状态变化、多线程交互或第三方库调用的问题，静态检查看不到运行中的状态，调试器往往比一百个 `cout` 更快。

## $\rm \S \, 5.6$ 编写最小复现

调试的第一原则不是“打开调试器”，而是**缩小问题范围**。

遇到 bug 时的反射动作：

1. 确认这个 bug 是稳定的还是偶发的——同样输入每次都会触发吗？
2. 去掉与问题无关的代码——如果删除某段逻辑后 bug 仍然存在，那这段逻辑不是原因。
3. 编写一个**最小复现**（minimal reproducible example）：用最少代码、最少依赖、最少输入复现同样的问题。
4. 如果最小复现中 bug 消失了，说明你删掉的那部分有问题或暴露了问题的条件。
5. 如果最小复现中 bug 仍然存在，你现在面对的是一个精确定位的问题，可以针对它设断点。

这个过程本身就经常能让 bug 的原因浮出水面。很多“复杂的 bug”一旦被压缩成最小复现，问题就变得显而易见。

## $\rm \S \, 5.7$ 常见错误：只依赖运行结果，不观察中间状态

你写过这样的调试代码吗：

```cpp
cout << "A" << endl;
// ... 一些代码 ...
cout << "B" << endl;
// ... 更多代码 ...
cout << "value = " << x << endl;
```

这个方法有四个问题：

1. **每次修改都要重新编译**——大型项目编译可能几分钟；
2. **输出信息不系统**——你只看到你主动打印的变量，临时想检查另一个变量就要再加一行、重编译；
3. **修改了程序行为**——`cout` 本身有缓冲和时序影响，对多线程程序更是引入了干扰；
4. **代码中留下垃圾**——调试完后你忘了删除 `cout`，提交到了 Git。

调试器解决了全部四个问题：不需要重编译就能检查任意变量；不会在源码中留下副作用；对多线程程序提供更精确的控制。

## $\rm \S \, 5.8$ 动手实践

### $\rm \S \, 5.8.1$ 实践一：感受语言服务

1. 在 VS Code 中打开一个 C++ 项目目录（可以新建一个练习目录）。
2. 安装 C/C++ 扩展（如果还没有）。
3. 创建一个包含多个函数的 `main.cpp`，刻意留一个未声明的函数调用。
4. 观察：编辑器是否在你编辑时就画出了红色波浪线？悬停在上面显示了什么信息？
5. 尝试 Ctrl+点击一个标准库函数（如 `std::sort`），观察它跳转到哪里。

### $\rm \S \, 5.8.2$ 实践二：gdb 最小调试

使用 [5.5.3](#553-最小例子gdb-调试-c-程序) 的越界数组示例，环境要求与该节相同（WSL/Linux/macOS 的 Bash，或已按第 9 章装好 MinGW-w64）。先 `cd` 到 `sum_array.cpp` 所在目录：

1. 用 `-g` 编译：`g++ -g -std=c++17 -Wall -Wextra sum_array.cpp -o sum_array`。
2. 运行 `gdb ./sum_array`，在 `sum` 函数设置断点（`break sum`）。
3. `run` 到断点后查看 `arr` 和 `n`——`print n` 应显示 `5`。
4. 单步执行循环，观察 `i` 和 `total` 的变化。
5. 当 `i = 5` 时，尝试 `print arr[5]`——观察 gdb 显示了什么值。
6. 把 `i <= n` 改为 `i < n` 后重新编译运行，验证 bug 修复（输出恢复为 `15`）。

### $\rm \S \, 5.8.3$ 实践三：最小复现

1. 沿用 [5.5.3](#553-最小例子gdb-调试-c-程序) 的 `sum_array.cpp`：让 `main` 先读入长度 `n`，再读入 `n` 个整数，但故意把 `n + 1` 传给 `sum`（这一次 bug 在调用者，不在被调函数）。
2. 不要立即看代码找 bug。先通过删代码和简化输入，把程序压缩到 `sum` 加 `main` 十几行的规模。
3. 记录：你删掉了哪些与 bug 无关的部分？压缩后的版本里 bug 还存在吗？
4. 如果存在，在 `sum` 入口设断点，单步观察最后一次循环时 `n`、`i` 和 `arr[i]` 的值。

两个 gdb 实践做完后，清理本节产生的编译产物：

```bash
rm -f sum_array sum_array.exe   # 只删编译产物；源码按需保留
```

## $\rm \S \, 5.9$ vim 生存指南：当你不小心进了“那个黑窗口”

### $\rm \S \, 5.9.1$ vim 是什么，为什么你会遇到它

**vim**（Vi Improved）是一个**终端里的文本编辑器**——默认没有图形菜单和可见的标签栏，操作以键盘为主。它诞生于 1991 年（前身 vi 诞生于 1976 年），设计背景是那个只有键盘、没有图形界面的时代。

你不需要主动去用它。但你**一定会被动遇到它**：

- `git commit` 不带 `-m` 时，Git 打开系统默认编辑器让你写提交信息
- `visudo` 让你在加锁和保存前语法校验的保护下编辑 sudoers（提权配置）；它默认调用 vi 系编辑器，可用 `EDITOR`/`VISUAL` 环境变量换掉（见 [5.9.4](#594-如果你完全不想学-vim)）
- `crontab -e` 编辑定时任务
- SSH 到一台只有命令行的服务器，需要临时改个配置文件——这台机器上只有 vim

> **安全规则**：sudoers 写坏可能让所有用户都无法再 `sudo`。改它要用 `visudo`（它加锁并在写入前校验语法），不要直接用普通编辑器打开 `/etc/sudoers`。

以上场景的共同点：你**不是主动选择**了 vim，而是被某个命令**丢进去**的。如果不认识它，你会对着全屏黑窗口敲什么都没反应，最后只能关掉终端窗口。下面是让你活下来的最小操作——`i` 进入编辑，`Esc` 回到命令模式，`:wq` 保存退出。学完这三个就可以应付 90% 的被动 vim 场景。

### $\rm \S \, 5.9.2$ 模式：为什么敲键盘没反应（vim 最核心的概念）

你熟悉的编辑器（VS Code、记事本、Word）打开后光标闪烁，直接可以打字。vim 不一样——它有两种**模式**，启动时处于**不能直接打字的模式**：

| 模式 | 你看到什么 | 能做什么 |
|------|-----------|---------|
| **普通模式**（Normal） | 光标是方块，底部没有 `--INSERT--` | 移动光标、删除、复制、撤销 |
| **插入模式**（Insert） | 底部显示 `-- INSERT --` | 正常打字 |

vim 启动时处于**普通模式**——这就是为什么你进来后敲键盘没反应。你在普通模式，不是插入模式。

### $\rm \S \, 5.9.3$ 最小生存操作（记住这 7 个就够了）

```text
按 i           → 进入插入模式（现在可以正常打字了）
按 Esc         → 回到普通模式（任何时候不确定就按一次 Esc）
（在普通模式）
  :w           → 保存（write）
  :q           → 退出（quit）
  :wq          → 保存并退出
  :q!          → 不保存强制退出
  dd           → 删除当前行
  u            → 撤销
```

**完整流程示例**：

```bash
git commit           # 打开 vim 编辑提交信息
# 此时在普通模式
按 i                  # 进入插入模式
输入：fix: 修复论文解析的空指针异常
按 Esc                # 回普通模式
输入 :wq              # 保存并退出
```

### $\rm \S \, 5.9.4$ 如果你完全不想学 vim

```bash
# 把默认编辑器改成 nano（更友好的终端编辑器）
export EDITOR=nano
# 写入 .bashrc 永久生效
echo "export EDITOR=nano" >> ~/.bashrc
```

nano 启动后直接可以打字，快捷键在底部显示（`^O` 保存、`^X` 退出——`^` 表示 Ctrl）。不需要模式切换。

> **经验规则**：服务器上至少要学会 vim 的 `i→Esc→:wq` 或换成 nano。`git commit` 进 vim 出不来是每个开发者的必经之路，你不是第一个。

## $\rm \S \, 5.10$ VS Code 进阶：超越“文本编辑器”

VS Code 的以下功能让它成为完整的开发环境，而不只是“好看的文本编辑器 + 终端面板”：

### $\rm \S \, 5.10.1$ 命令面板：键盘驱动一切

`Ctrl+Shift+P`（macOS: `Cmd+Shift+P`）打开命令面板——几乎 VS Code 的所有功能都可以从这里触发，不需要记住快捷键：

```text
Ctrl+Shift+P → "format document"      # 格式化当前文件
Ctrl+Shift+P → "toggle terminal"      # 开关终端面板
Ctrl+Shift+P → "rename symbol"        # 重命名变量/函数（F2 快捷键）
Ctrl+Shift+P → "go to symbol"         # 跳转到当前文件中的函数/类
Ctrl+Shift+P → "reopen closed editor" # 重新打开刚关掉的标签页
```

> **经验规则**：不确定某个操作有没有快捷键时，直接 `Ctrl+Shift+P` 输入关键词搜索——不只找到功能，还会在右侧显示对应的快捷键。

### $\rm \S \, 5.10.2$ 多光标与批量编辑

```text
Alt+Click          → 在点击位置添加一个光标
Ctrl+Alt+↑/↓       → 在上方/下方添加光标
Ctrl+D             → 选中当前单词，再按一次选中下一个相同单词
Ctrl+Shift+L       → 选中文件中所有与当前选中内容相同的文本
Ctrl+Shift+Enter   → 在当前行上方插入空行
```

典型场景：把 20 行中的 `old_variable_name` 全部改成 `new_variable_name`——`Ctrl+Shift+L` → 直接输入新名字，20 行同时修改。

### $\rm \S \, 5.10.3$ Tasks：把重复命令变成一键操作

`.vscode/tasks.json` 定义项目级任务：

```json
{
  "version": "2.0.0",
  "tasks": [
    {
      "label": "build",
      "type": "shell",
      "command": "g++",
      "args": ["-std=c++17", "-Wall", "-g", "main.cpp", "-o", "main"],
      "group": {"kind": "build", "isDefault": true},
      "problemMatcher": ["$gcc"]
    },
    {
      "label": "run tests",
      "type": "shell",
      "command": "python -m pytest tests/ -v",
      "group": {"kind": "test", "isDefault": true}
    }
  ]
}
```

`Ctrl+Shift+B` → 运行默认构建任务。`Ctrl+Shift+P → "Run Test Task"` → 运行测试。

### $\rm \S \, 5.10.4$ Dev Container：把开发环境写进配置

你在[第 30 章 Docker](../08-部署运维/30-Docker基础.md)中会学到容器的细节。但这里先给你看一个 VS Code 独有的能力——把整个开发环境定义为一个 JSON 文件：

`.devcontainer/devcontainer.json`：

```json
{
  "image": "mcr.microsoft.com/devcontainers/cpp:ubuntu-22.04",
  "extensions": ["ms-vscode.cpptools", "twxs.cmake"],
  "postCreateCommand": "sudo apt update && sudo apt install -y cmake libboost-all-dev"
}
```

执行 `Ctrl+Shift+P → "Reopen in Container"` 后，VS Code 拉取镜像、在容器里安装扩展、运行初始化命令，整个项目在一个隔离的 Linux 环境中运行。它有三个前置条件：本机已安装并启动 Docker（第 30 章）、已安装 Dev Containers 扩展（`ms-vscode-remote.remote-containers`）、网络能访问镜像仓库（首次拉取要下载数百 MB）。上面的镜像 tag 只是示例，官方会发布新的 tag，实际使用以官方文档当前的 tag 为准。

三个条件都具备时，新队友第一天加入项目不必在主机上逐个安装编译器和库——环境由这份配置复现。

### $\rm \S \, 5.10.5$ Remote 开发：在服务器上写代码

安装了 Remote-SSH 扩展后：

```text
Ctrl+Shift+P → "Remote-SSH: Connect to Host..."
输入 alice@10.0.0.5
→ VS Code 在服务器上安装一个小型 agent
→ 之后你看到的文件系统、终端、调试器全在服务器端运行
→ 只有 GUI 渲染在你的本地机器上
```

这意味着你可以在 Windows 笔记本上打开 VS Code，编辑和调试运行在远程 Linux 服务器上的代码——完全透明，和本地开发体验一样。

### $\rm \S \, 5.10.6$ 常见插件（按需安装）

VS Code 的强大很大程度上来自插件生态。下面是常见的一批，按当前项目需要挑：

| 插件 | 作用 | 装完就能用的功能 |
|------|------|-----------------|
| **WSL**（`ms-vscode-remote.remote-wsl`） | 在 Windows 上打开 WSL 中的项目 | `code .` 在 WSL 终端中打开 VS Code，一切跑在 Linux 侧 |
| **Remote-SSH**（`ms-vscode-remote.remote-ssh`） | 直接编辑远程服务器上的文件 | `Ctrl+Shift+P → Remote-SSH: Connect`，像本地一样编辑 |
| **GitLens**（`eamodio.gitlens`） | 每行代码显示最后修改者和时间 | 鼠标悬停在任何一行上，看到该行最后由谁、何时修改 |
| **Prettier**（`esbenp.prettier-vscode`） | 前端/JS 项目：保存时自动格式化代码 | 装完在设置中搜 `format on save` 并勾选 |
| **Error Lens**（`usernamehw.errorlens`） | 把错误信息直接显示在代码行尾 | 不用悬停看错误——错误就在你眼前 |
| **Todo Tree**（`gruntfuggly.todo-tree`） | 扫描项目中所有 `TODO`/`FIXME` 注释并汇总 | 侧栏显示所有待办事项列表 |

> **经验规则**：装插件不是越多越好——每个插件都在后台运行，多了会拖慢 VS Code。先装解决你当前问题的，后续按需添加。

### $\rm \S \, 5.10.7$ `settings.json`：VS Code 的配置中枢

VS Code 的所有设置（字体、缩进、格式化、插件行为）都存在一个 JSON 文件中。`Ctrl+Shift+P → "Open Settings (JSON)"` 打开：

```json
{
  "editor.fontSize": 14,
  "editor.fontFamily": "'Cascadia Code', 'Fira Code', Consolas",
  "editor.formatOnSave": true,          // 保存时自动格式化
  "editor.minimap.enabled": false,       // 关掉右侧缩略图——省屏幕空间
  "editor.rulers": [80, 120],            // 在 80 和 120 列画竖线
  "files.autoSave": "onFocusChange",     // 切窗口时自动保存
  "terminal.integrated.defaultProfile.windows": "PowerShell",
  "workbench.colorTheme": "One Dark Pro"
}
```

VS Code 的 `settings.json` 是允许注释的 JSONC（JSON with Comments），所以上面可以写 `//`；标准 JSON 不允许注释，把这些内容复制到别处的 `.json` 文件里解析会报错。

把 `settings.json` 放进 dotfiles（第 25 章 §25.4）——换电脑后一键恢复所有编辑器配置。

## $\rm \S \, 5.11$ 浏览器开发者工具：前端调试的“终端”

你在[第 28 章前端开发](../07-应用开发/28-前端开发.md)中会用到浏览器的 `F12` 开发者工具。但在那之前，这个工具本身就是日常开发的瑞士军刀——不只前端开发者用。

### $\rm \S \, 5.11.1$ 打开方式

- **Edge/Chrome**：`F12` 或 `Ctrl+Shift+I`
- **Firefox**：`F12` 或 `Ctrl+Shift+I`

### $\rm \S \, 5.11.2$ 四个最常用的面板

| 面板 | 快捷键（Edge/Chrome） | 你用它做什么 |
|------|----------------------|-------------|
| **Elements**（元素） | `Ctrl+Shift+C` | 查看页面的 HTML 结构，鼠标悬停看对应元素在页面上的位置和 CSS 样式 |
| **Console**（控制台） | `Ctrl+Shift+J` | 看 JavaScript 错误、手动执行 JS 代码、查看 `console.log` 输出 |
| **Network**（网络） | `Ctrl+Shift+E` | 看本次记录到的请求——URL、状态码、耗时、响应内容（HTTP 与状态码见第 23 章）。后端 API 返回了数据但前端没显示？先看 Network 面板确认请求是否发出、响应是否正常 |
| **Application**（应用） | — | 查看 Cookie、localStorage、IndexedDB——你的登录状态到底存没存？ |

### $\rm \S \, 5.11.3$ Network 面板：后端调试的终极武器

当你的后端 API “好像没收到请求”或“好像返回了但前端没显示”时，Network 面板直接告诉你真相：

```text
打开 F12 → Network 标签 → 刷新页面 →
看到几十行请求：
  papers.json    200   0.3ms   1.2KB    ← 正常
  /api/papers    500   2300ms  0.1KB   ← 500 错误！点进去看 Response 标签
  style.css      200   0.1ms   3.5KB
  logo.png       404   0.2ms   0KB     ← 图片 404——路径拼错了
```

你不需猜测——Network 面板直接告诉你每个请求的方法（GET/POST）、状态码、耗时、请求头和响应内容。这是前端开发者和后端开发者共同的调试入口。

> **经验规则**：遇到“前端说没收到数据，后端说已经发了”的争论时，打开 F12 Network 面板——它就是裁判。

Edge 和 Chrome 使用相同的渲染引擎（Chromium），上面这些面板的用法基本一致；Edge 另有垂直标签页、集锦等浏览器功能，与调试无关，需要时查官方文档即可。

## $\rm \S \, 5.12$ 总结

- **编辑器做文本，IDE 做工作台**。从编辑器开始，缺什么加什么比一开始装全套 IDE 更容易理解每个工具的职责。
- **语言服务在编译前就帮你发现问题**。但它需要正确的项目配置才能准确工作。
- **格式化工具消除风格争议，静态检查在编译前捕获隐患**。两个都“保存时自动运行”。
- **调试器让程序暂停，让你观察状态**——这不是“高手工具”，而是一种比 `cout` 更系统、更少副作用的排查方式。
- **编写最小复现是调试的第一步**。如果在压缩问题的过程中 bug 消失了，你已经找到了关键线索。

## $\rm \S \, 5.15$ 本章自测答案

> 先闭卷作答本章“关键概念回顾”与“应用与辨析”，再核对以下答案。

### $\rm \S \, 5.15.1$ 自测答案 · 关键概念回顾
1. 编辑器专注文本编辑本身（高亮、补全、搜索替换）；IDE 是集成工作台，内置或紧密集成了编译调用、调试器、项目管理和代码智能。
2. 以目录作为工作区后，工具才能理解文件之间的关系、头文件在哪里、哪些是源码哪些是构建产物，语言服务和全局搜索才有正确的范围。
3. 提供诊断、跳转定义、查找引用、悬停信息、重命名；它只做解析和类型检查，不产生可执行文件——链接错误等只能在完整构建中暴露。
4. 格式化统一代码风格，消除 Git diff 里的无意义改动；静态检查在不运行程序的情况下发现潜在问题（未使用变量、空指针风险等）。
5. 断点让程序运行到指定行时暂停；单步执行逐行推进、观察状态变化；调用栈显示“我是从哪被调用的”，帮助理解执行路径。这些能力的前提是编译时加了 `-g`：它把源码行号、变量名等调试信息嵌入可执行文件，调试器才能把运行位置对应到源码行并在断点处查看变量。

### $\rm \S \, 5.15.2$ 自测答案 · 应用与辨析
6. `step` 进入当前行调用的函数内部，停在函数第一行；`next` 执行完当前行（包括其中的函数调用）停在下一行。
7. 调试的第一步是缩小问题范围：去掉无关代码后若 bug 消失，说明删掉的部分才是线索；直接设断点是在尚未定位的问题上盲目尝试。
8. 30 行左右的小程序加一行 `cout` 比启动调试器更快；涉及复杂状态变化、多线程交互或第三方库调用时，调试器不需要重编译、无副作用、更精确。
