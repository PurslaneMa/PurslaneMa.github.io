# $\rm Chapter \, 3$ 内存安全（下）：堆与语言

> **本章假设你已经会**
>

> 4. 四道缓解各防什么，见 §2.4 与 §2.5。本章开头会问一句：这些闸门里，有几道管到了堆？

上一章把栈上的故事讲完了。但凡是生命周期不跟着函数走的数据（链表节点、缓冲区、对象），都住在堆上，而堆没有「函数返回」这个天然的清理节点：内存什么时候不再用，只有程序员自己知道，于是分配器必须自己记账，程序员必须自己喊一声 `free`。本章沿着上一章的目录继续翻页：先看分配器记的是什么账、记在哪（§3.1），再逐个演示堆上的两大主角：释放后再用（§3.2）与重复释放（§3.3，均有实测），然后机制层地看一眼元数据破坏与类型混淆（§3.4）。最后算两笔账：为什么 Rust 和 Go 从语言层就把这一整页目录翻了过去（§3.5），以及公开数据里内存安全漏洞到底占多大比例（§3.6）。全程只演示崩溃与检测，不构造利用。

## $\rm \S \, 3.1$ 堆的记账本：分配器与元数据

先定义对象。堆分配器（heap allocator）是一个库，不是内核服务：`malloc` 与 `free` 在用户态运行，向内核整批申请内存（Linux 上经由 `brk`/`mmap` 系统调用），再零售给程序。它把大块内存切成大小各异的块（chunk）分发；为了知道哪些块在用、哪些空闲、空闲块有多大，它在块里或块旁存放元数据（metadata）。每个块前面有一个固定 8 字节的头部（header），记录本块大小与相邻块占用状态，这就是分配器的记账本。给定期望字节数 $n$，glibc 按

$$
\mathrm{chunk}(n) \;=\; \max\!\left(32,\; \left\lceil \dfrac{n+8}{16} \right\rceil \times 16\right)
$$

确定实际分配的块大小（字节）。读法：先加 8 是头部自己占的份，向上取整到 16 的倍数是为了地址对齐，最小 32 是一个块的下限。这个公式马上会被实测验证两次。

下面实测（Bash / WSL2，Ubuntu 24.04，gcc 13.3.0，glibc 2.39；本章实验全部在此环境完成，工作目录 `expSEC03`）。程序连续申请三个 24 字节的块，并读出第二个块头部的字段：

```c
#include <stdio.h>
#include <stdlib.h>

/* 观测堆块布局：用户指针之间隔了什么 */
int main(void) {
    char *a = malloc(24);
    char *b = malloc(24);
    char *c = malloc(24);
    printf("a=%p\n", (void *)a);
    printf("b=%p (b-a=%ld)\n", (void *)b, (long)(b - a));
    printf("c=%p (c-b=%ld)\n", (void *)c, (long)(c - b));
    /* 只读观察自己块头部的 size 字段（最低位是 PREV_INUSE 标志） */
    unsigned long sz = *((unsigned long *)(b - 8));
    printf("header(b-8)=%#lx  (0x21 = 32 字节块 | PREV_INUSE=1)\n", sz);
    free(b);
    free(a);
    free(c);
    return 0;
}
```

```bash
gcc -O0 -g -o layout layout.c && ./layout
```

```text
a=0x57266c9612a0
b=0x57266c9612c0 (b-a=32)
c=0x57266c9612e0 (c-b=32)
header(b-8)=0x21  (0x21 = 32 字节块 | PREV_INUSE=1)
```

三个读法。第一，相邻用户指针只差 32 字节，而你要的是 24：多出来的 8 字节正是头部，代入公式 $\mathrm{chunk}(24) = \lceil 32/16 \rceil \times 16 = 32$，与实测吻合。第二，头部最低位 `1` 是 `PREV_INUSE` 标志，表示前一个块在用；真正的 `size` 字段是 `0x20`，再次对上公式。为什么标志能塞进 size 字段？块大小既然总是 16 的倍数，二进制表示的最低 4 位永远是 0，分配器把这 4 位拿来当标志位复用：最低位记「前一个块在用」，读账时要按 $\mathrm{size} = \mathrm{field} \mathbin{\&} \mathtt{\sim}15$ 把标志位摘掉。一个字段两份用途，这是记账本越薄越好的典型取舍。第三，也是本章的关键观察：**头部与用户数据紧挨着，中间没有任何硬件隔离**。栈上至少还有 canary 这道闸（§2.4），堆上数据写过头，碾碎的第一样东西就是分配器的账。

`free` 同样在用户数据区里记账。glibc（2.26 起）给小块配了一条线程本地的空闲链表 tcache（thread caching），释放小块时把块本身串上链表：块的前 16 字节被改写成「下一个空闲块的位置」与一个随机标记（2.34 起的 tcache key）。也就是说，释放之后这块内存里立刻多出了分配器的账目，我们下一节直接读给你看。

白话：堆像一个快递柜，`malloc` 是取一个柜格，`free` 是还柜格；柜格门内侧贴着一张登记条（头部），写着这格多大、邻居是否在用，而登记条和你的货物共用同一格空间。

**本节小结**：分配器在用户态用块头记账，实测 `malloc(24)` 实际占 32 字节、头部紧贴数据；释放时账目直接写进刚腾出来的用户区，堆的「数据」与「控制信息」从第一天起就同住一格。

## $\rm \S \, 3.2$ 释放后再用：UAF

现在看目录里的第一个堆条目。释放后再用（use-after-free，UAF）指：`free(p)` 之后继续经 `p` 读写那块内存。定义里的关键是，语言本身不阻止这件事：`free` 只是「喊一声不要了」，指针 `p` 这个变量原封不动，仍然指向那个地址。这样的 `p` 叫悬垂指针（dangling pointer）。读它会发生什么？块的内容没有被清零（清零是白花时间），所以旧数据可能原样还在；一旦这块被复用，读到的就是新住户的数据。下面实测完整走一遍（程序 `uaf.c`，编译 `gcc -O0 -g -o uaf uaf.c`）：

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

/* UAF 演示：free 之后读，值还在；复用之后被覆盖 */
int main(void) {
    /* 先做完所有分配，再打印，避免 stdio 缓冲区夹进来干扰布局观测 */
    char *p = malloc(32);                 /* 第 8 行 */
    char *n = malloc(32);
    memset(p, 'A', 24);
    p[24] = '\0';

    free(n);                              /* 第 13 行：先释放邻居，让链上有个现成节点 */
    free(p);                              /* 第 14 行 */
    unsigned long *w = (unsigned long *)p;
    unsigned long q0 = w[0], q1 = w[1];   /* 第 16 行：free 后立刻读 */
    char *r = malloc(32);                 /* tcache LIFO：大概率原址复用 */
    int reuse = (r == p);
    memset(r, 'B', 24);
    r[24] = '\0';
    char oldbuf[32];
    memcpy(oldbuf, p, 25);                /* 经旧指针 p 读：看新住户写了什么 */

    printf("step1  p=%p n=%p (n-p=%ld)\n", (void *)p, (void *)n, (long)(n - p));
    printf("step2  before free, p content=%s\n", "AAAAAAAAAAAAAAAAAAAAAAAA");
    printf("step3  after free: q0=%016lx q1=%016lx\n", q0, q1);
    printf("step4  r=%p reuse=%s\n", (void *)r, reuse ? "yes" : "no");
    printf("step5  read via old p: %s\n", oldbuf);

    free(r);
    return 0;
}
```

```text
step1  p=0x589a89bab2a0 n=0x589a89bab2d0 (n-p=48)
step2  before free, p content=AAAAAAAAAAAAAAAAAAAAAAAA
step3  after free: q0=0000589f0012297b q1=6068fea413571cd8
step4  r=0x589a89bab2a0 reuse=yes
step5  read via old p: BBBBBBBBBBBBBBBBBBBBBBBB
```

五个读法。第一，$\mathrm{chunk}(32) = 48$，`n-p=48` 又对上 §3.1 的公式。第二，`step3` 证明 free 后内存没有清零，只是被改记了账：`q1` 是随机标记（每次运行都不同，实测三次无一相同），`q0` 看着像乱码，其实是加过混淆的空闲链表指针。glibc 2.32 起，链表指针按 $\mathrm{stored} = \big(\mathrm{addr} \gg 12\big) \oplus \mathrm{next}$ 存放（safe-linking 方案，$\mathrm{addr}$ 是存放位置自身地址，$\oplus$ 是按位异或）；用本行实测值验证：$\mathrm{q0} \oplus (\mathrm{p} \gg 12) = \mathtt{0x589a89bab2d0} = n$，分毫不差，链条上的「下一格」正是先释放的邻居。第三，`step4` 的 `reuse=yes`：tcache 是后进先出，刚还的柜格马上再借，拿到的还是同一格。第四，`step5` 是 UAF 的实锤：经旧指针 `p` 读到的已经是新指针 `r` 写入的 24 个 `B`。同一块内存、两个指针、两个所有者，而语言对此一言不发。第五，把地址拼起来看危害机制：如果旧指针与新指针认定的是**不同类型**（比如旧代码以为里面是存身份的结构，新住户是别的数据），旧代码就会把新数据当旧类型解释，这正是 §3.4 类型混淆的入口，也是 UAF 从「读到脏数据」升级为「控制流劫持」的通道：堆块里若存着函数指针或长度字段，伪造它的成本在复用之后骤降。

这类错误编译器不报、运行时未必崩，是内存安全漏洞里最难靠测试发现的一类。检测工具的思路是给分配器加一道隔离区（quarantine）：`free` 后块先隔离一段时间不参与复用，且在隔离期由影子内存记录「此地已释放」，任何访问当场报警。实测同一程序改用 AddressSanitizer（编译命令 `gcc -O0 -g -fsanitize=address -o uaf_asan uaf.c`）：

```text
==709==ERROR: AddressSanitizer: heap-use-after-free on address 0x503000000040 ...
READ of size 8 at 0x503000000040 thread T0
    #0 ... in main .../expSEC03/uaf.c:16
freed by thread T0 here:
    #1 ... in main .../expSEC03/uaf.c:14
previously allocated by thread T0 here:
    #1 ... in main .../expSEC03/uaf.c:8
SUMMARY: AddressSanitizer: heap-use-after-free .../uaf.c:16 in main
```

（节选）退出码 1。报告把三件事一次说全：第 16 行在读写一块已释放的内存，这块是谁在哪一行分配（第 8 行）、又在哪一行释放（第 14 行）。同一份代码，普通构建下安静地拿到 24 个 `B`，ASan 构建下在第一笔越账上就停机，这正是 §2.4 安全默认值原则在工具链上的样子。

白话：UAF 像退房之后房卡没交：门还开得开，看到的是原房间（可能原样没动），也可能是新住客的行李；ASan 干的事，是让前台在退房后立刻冻结房间、谁刷卡就叫保安。

**本节小结**：`free` 不改指针、不清内存，实测旧指针先读到分配器的账（混淆链表指针与随机标记），原址复用后读到新住户的数据；ASan 用隔离区加影子内存把「安静的错误」变成「当场停机」，代价是运行显著变慢，所以它属于开发期工具而非出厂配置。

## $\rm \S \, 3.3$ 重复释放：double-free 与分配器的自检

第二个条目：重复释放（double free），同一块内存 `free` 两次。危害机制一句话就能说清：空闲链表一个块出现两次，之后的两次 `malloc` 会把同一块内存发给两位客人，两位各自以为自己独占，§3.2 的「同一块内存两个所有者」直接翻倍。分配器对此并非毫无办法：释放小块时写入的随机标记（§3.2 的 `q1`）就是给链表准备的「已退房」贴条，第二次 `free` 同一块时，分配器在链表头上认出这个标记，拒绝入链并中止程序。实测（程序 `dfree.c`，`gcc -O0 -g -o dfree dfree.c`，三次重复行为一致）：

```c
#include <stdlib.h>
#include <stdio.h>

int main(void) {
    char *p = malloc(32);
    printf("p=%p\n", (void *)p);
    free(p);
    free(p);   /* 第二次 free 同一块：分配器报警并中止 */
    printf("unreachable\n");   /* 不应执行到 */
    return 0;
}
```

```text
stderr: free(): double free detected in tcache 2
退出码 134（SIGABRT）；stdout 无任何输出（free 后的 printf 未执行到）
```

三个读法。第一，报错来自 glibc 的自检，退出码 134 与上一章 `stack smashing detected` 的 SIGABRT 同源：都是「库检测到自身一致性被破坏，宁可停机」。第二，报错写在标准错误流，标准输出是空的，所以重定向日志时要分两个流看，只看 stdout 会以为程序正常运行。第三，自检的覆盖面有限：它认的是「块还挂在链表头上」这种最直白的重复，若两次释放之间有其他块入链出链、把标记冲掉，或换用没有此类自检的分配器，程序会继续跑下去，把破坏留给后续。所以这层自检是纵深防御里的一道闸（§1.3），不是免疫声明；它把「最常见路径上的破坏」变成「当场停机」，把其余路径留给工具与语言层。

白话：double-free 像同一间房退了两次押金：前台贴了「已退」的条子，第二次退房时被认出来报警；但条子可能被后来的登记盖住，前台也不是每个柜台都贴条。

**本节小结**：glibc 用随机标记自检最直白的重复释放，实测报错 `double free detected in tcache 2` 并以 134 中止；自检覆盖面有限，靠它兜底不够，得往上加工具（ASan 同样能抓 double free）与语言层保证。

## $\rm \S \, 3.4$ 元数据破坏与类型混淆

把前三节的观察拼起来，就能看懂目录里剩下两个条目为什么长那样。元数据破坏（metadata corruption）指：越界写碾坏的正好是分配器的账（块头、空闲链表指针），于是错误不立刻显形，而是在之后某次 `malloc`/`free` 里被「执行」出来。用 §3.1 的实测布局做一轮纯推演，看「多写几个字节」如何沿着账本传导：

1. 相邻两个 32 字节的块 `a`、`b`（实测布局见 §3.1），`a` 的用户区写满 24 字节后每多写 1 字节，就先压到 `b` 头部的标志位与 size 字段；多写 8 字节正好整格覆盖 `b` 的头部。
2. 覆盖发生后程序照常运行：头部只是一本被动的账，没人翻它就没人发现。
3. 下一次 `free(b)`，分配器读 `b` 的 size 决定挂进哪条空闲链：账被改，块就进了错链，或被伪造的 size 撑出一个不存在的「大块」。
4. 更进一步，释放 `a` 时分配器要按 `PREV_INUSE` 标志决定是否与 `b` 合并；攻击者若把标志与 size 一起伪造，合并动作本身就会按假账改写内存，这就是经典手法围绕「空闲块合并」做文章的原因。
5. glibc 的对策是把假账拦在兑现之前：双向链表一致性检查（报错 `corrupted double-linked list`）与 size 合法性检查（报错 `corrupted size vs. prev_size` 一类），思路与 §3.3 的 tcache key 相同，让伪造过不了自检。

这里只讲机制，不展开构造。堆上的缓冲区溢出（上一章 §2.2 的同款错误换个地皮）之所以比栈版更花哨，正是因为被碾坏的是这本账而不是单个返回地址：账被谁解释、什么时候解释，取决于之后每一次分配与释放，攻击面组合远多于栈，这也是堆利用在历史上自成一门学问的原因。

类型混淆（type confusion）指：程序把类型 A 的对象当类型 B 读写。C 里它常由强制转换或 §3.2 的复用场景促成：释放后原址住进不同类型的新数据，旧指针按旧类型解释新字节。本册不深入其利用形态，只钉两条：其一，类型混淆与 UAF 在堆上常常是同一段内存的两个名字，根因都是「所有权没了，访问还在」；其二，语言层的应对方向一致，要么编译期禁止这种访问（Rust），要么运行期由运行时系统统一掌管对象（带类型信息与生命周期的托管语言），这正是下一节的账。

白话：元数据破坏是改了快递柜的登记条，让分配器下次自己把货物送到错的地方；类型混淆是把 A 格的包裹塞进 B 格，再按 B 格的标签拆包。

**本节小结**：堆溢出碾的是分配器的账，破坏延迟到未来的某次分配释放才兑现，故自检（双向链表检查、tcache key）与语言层保证是仅有的两类系统性缓解；类型混淆与 UAF 同根，解法也同源。

## $\rm \S \, 3.5$ 语言层的免疫账：Rust 与 Go

前三节的一切前提是两个「程序员全权负责」：负责喊 `free`，负责不再用旧指针。Rust 与 Go 从不同角度收走了这两个前提。Rust 的方案是所有权（ownership）系统，核心三条规则：每个值有唯一的所有者变量；赋值与传参默认移动（move），原变量从此失效；可以「借用」（拿引用），但要么多个不可变借用、要么恰好一个可变借用，不可同时；所有者离开作用域时自动释放。用它推一遍本章目录：UAF 需要「free 后旧指针仍可用」，而 Rust 里释放对应所有者离开作用域或值被移动，此后旧变量在**编译期**就被拒绝访问；double free 需要两次释放同一块，唯一所有者只会释放一次，两次释放根本写不出来。实测过的 `uaf.c` 在 Rust 里对应代码无法通过编译，报错 `borrow of moved value`，错误在编译期而不在运行期，这是质变：防护从「发行版默认开的闸门」前移到「代码进不了仓库」。代价同样要记账：借用检查器以严格著称，实现链表、图这类共享结构要换数据结构或引入引用计数，学习成本是社区公认的真实门槛。

Go、Java 一类的方案是垃圾回收（garbage collection，GC）：语言运行时周期性扫描哪些对象仍可达，不可达者统一回收，程序员根本不写 `free`。UAF 在构造上消失：不存在「程序员喊早了」，因为释放时机由可达性而非人的记忆决定；double free 同理无从谈起。代价是另两笔账：内存占用更高（垃圾在回收前一直占着），以及回收带来的时间开销与停顿，所以 GC 语言在对延迟极端敏感或内存极端受限的场景不吃香。

C++ 介于两者之间，值得一笔：智能指针（smart pointer）把释放挂在对象作用域上（RAII，Resource Acquisition Is Initialization），`std::unique_ptr` 移动后旧指针置空，能挡住大部分 UAF 与泄漏。但这是库的纪律而不是语言的保证：裸指针与 `get()` 拿到的指针依然悬垂，引用计数成环照样泄漏，本章的目录在 C++ 里只是被压缩，没有被撕掉。三类方案并排看一眼：

| 方案 | UAF | double-free | 代价 |
| --- | --- | --- | --- |
| C/C++ | 可能 | 可能 | 无运行时开销，全靠人 |
| C++ 智能指针 | 大幅减少 | 基本消除 | 引用计数开销；裸指针仍可绕过 |
| Rust | 编译期拒绝 | 编译期拒绝 | 借用检查的学习与改造成本 |
| Go/Java | 构造上消失 | 构造上消失 | GC 的内存与停顿开销 |

白话：Rust 是房卡注销制度，旧卡在门口就作废，想用旧卡连楼都进不去（编译不过）；GC 是物业统一收房，你根本拿不到「退房」这个权力；C++ 智能指针是给房卡装了个自动注销器，但窗口纸条写的开锁法依然有效。

**本节小结**：UAF 与 double-free 的根因是「释放与访问都由人负责」，Rust 用所有权把它变成编译期错误，GC 语言把它变成运行时的可达性问题，C++ 智能指针是半程方案；免疫不是免费的，各自付出学习成本或运行时开销。

## $\rm \S \, 3.6$ 数据说话：内存安全漏洞的占比

前面三章翻的是目录，这里看目录占整个病志的多大篇幅。三份常被引用的公开数据：微软安全响应中心（MSRC）统计其每年修复的漏洞，约 70% 属于内存安全问题（Matt Miller，BlueHat IL 2019 演讲）；Chrome 团队声明其严重安全漏洞约 70% 是内存安全问题（Google Chromium 项目 Memory Safety 页面，2019 年起口径）；Android 平台安全漏洞中内存安全类占比约 76%（Google Security Blog《Reducing memory safety vulnerabilities》，2019）。注意口径：三者统计年限、漏洞分级与「内存安全」的归类边界不完全相同，数字不能互相精确比较，但量级一致地指向同一结论。这些是行业公开数据，非本册实测。

这份占比就是 §3.5 那笔账的现实分量：一类错误占了漏洞榜的七成，而它恰好是 Rust 与 GC 语言在构造上消除的那类。监管与产业层面随之跟进：美国国家安全局（NSA）2022 年发布指南建议新代码优先选用内存安全语言，网络安全和基础设施安全局（CISA）2023 年联合多国机构呼吁给出内存安全的迁移路线图。回接 §1.6 的成本曲线：迁移有成本，但不迁移的成本写在上面那 70% 里；本章三节实测也说明，即便留在 C/C++，分配器自检、ASan 与四道闸（§2.4、§2.5）仍能把攻击成本显著抬高。下一章离开内存，去看目录里另一大类：Web 应用层的失效方式。

白话：七成病历是同一种病，医学界（语言界）已经发明了让人天然不患此病的体质，剩下的争论只是换体质的手术费谁来付。

**本节小结**：微软约 70%、Chrome 约 70%、Android 约 76% 的公开口径都指向内存安全是漏洞大头；语言层消除＋分配器加固＋检测工具，是压这七成的三条腿。

## $\rm \S \, 3.8$ 应用与辨析

1. 同事说「我们把分配器换成带 double-free 自检的版本，堆漏洞就没了」。用本章实测证据指出这句话错在哪两处，并给出一个更准确的表述。
2. 你接手一个 C 项目，怀疑存在 UAF。比较三种排查手段的适用场景与成本：代码审查盯 `free` 后的指针使用；ASan 构建跑测试；直接换 Rust。哪个先做，为什么？
3. §3.2 的程序若把 `malloc(32)` 改成 `malloc(64)`，`step4` 的 `reuse=yes` 还成立吗？`step3` 读到的前 16 字节含义变吗？依据公式与 tcache 机制推理，不必上机。

## $\rm \S \, 3.9$ 答案

3.7.1：$\mathrm{chunk}(n) = \max(32, \lceil (n+8)/16 \rceil \times 16)$；加 8 是头部占的份，乘 16 取整是对齐，下限 32 是最小块。$\mathrm{chunk}(24)=32$、$\mathrm{chunk}(32)=48$，实测相邻指针差恰为 32 与 48（§3.1、§3.2）。

3.7.2：前 8 字节是 safe-linking 混淆后的空闲链表 next，后 8 字节是随机 tcache key（每次运行不同）。还原式 $\mathrm{next} = \mathrm{q0} \oplus (\mathrm{p} \gg 12)$，实测 $\mathrm{q0} \oplus (\mathrm{p} \gg 12)$ 恰等于先释放的邻居 $n$ 的地址（§3.2）。

3.7.3：报 `free(): double free detected in tcache 2`，SIGABRT，退出码 134；依据是第一次 free 写入链表节点的随机 key，第二次 free 时在链表头被认出。局限：只覆盖「块仍在链表头上」的直白重复，中间隔了其他分配释放、或分配器无此自检时不起作用（§3.3）。

3.7.4：UAF 被第二条（移动后原变量失效）与第四条（所有者离开作用域自动释放且仅释放一次）拒绝；Go 靠 GC 以可达性决定释放，程序员无 `free` 可错。代价：Rust 是借用检查的学习与改造成本，Go 是 GC 的内存占用与停顿（§3.5）。

3.7.5：隔离区（free 后不立刻复用）与影子内存（记录每字节的可访问状态与释放信息）。它让程序变慢且内存变大，性能敏感的出厂产品通常不开，故定位为开发与测试期的门禁（§3.2）。

3.8.1：错处一，自检覆盖面有限，实测它抓的是「块还在链表头上」的直白重复，间隔释放或其他路径可以绕开（§3.3）；错处二，堆漏洞不止 double-free，UAF、元数据破坏、类型混淆（§3.4）都还在，本章实测的 UAF 程序在普通构建下静默复用，自检一声不吭。更准确的说法：带自检的分配器把最常见的一类堆错误变成当场停机，抬高了攻击成本，但没有消除这一页目录。

3.8.2：先上 ASan。代码审查的漏报率取决于人的注意力，UAF 的触发依赖运行路径，盯不出来是常态；换 Rust 是最彻底但成本最高（重写、生态、周期），适合作为长期路线而非第一步。ASan 构建改动小（只加编译选项），实测能当场定位分配、释放与使用三处行号，用它跑现有测试与模糊测试，性价比最高；审查可与其并行，作为 ASan 覆盖不到路径的补充（§3.2、§3.6）。

3.8.3：仍成立。$\mathrm{chunk}(64) = \lceil 72/16 \rceil \times 16 = 80$，仍属小块，走同一条 tcache 链，后进先出的复用顺序不变，故 `r == p`。`step3` 的含义也变：前 16 字节的内容形式相同（混淆 next 与随机 key），但混淆式里的存放位置变成了新的 `p`，还原出的 next 是对应的新邻居；换句话说「读到分配器的账」这一性质不变，账的具体数值随块大小与释放顺序而变（§3.1、§3.2）。

> 你现在能：读出 `malloc(n)` 背后的真实块大小并用实测差值验证分配公式；看到 `double free detected in tcache 2` 与退出码 134 时说出它对应哪层自检；用一个 `-fsanitize=address` 构建把 UAF 从静默错误变成带三处行号的报告；面对新项目，按「分配器自检、ASan、内存安全语言」的顺序给团队列一份成本递增的加固清单。
