# $\rm Chapter \, 4$ UDP 与 TCP：数据报与字节流

上一章 IP 把每个数据报送到了目的主机，但只到主机为止。一台主机上同时跑着浏览器、游戏与聊天软件，IP 头上只写了「哪台机器」，没写「哪个程序收」；何况 IP 尽力而为，丢了不补。传输层要补的正是这两块缺口：把交付推进到进程，并按应用的需要提供「不可靠」与「可靠」两种通道。本章建立 UDP 与 TCP 的语义与取舍，可靠性如何兑现留给第 5 章。

> **开始前自检**：本章假设你已经会：
>
> 1. □ IP 尽力而为：会丢、会乱序、会重复，出错不通知（本册 §3.1）；
> 2. □ 端口号定位「某台机器上的某个程序」（计算机速通 §23.2）；
> 3. □ 回环 127.0.0.1 与最小 socket 收发（本册 §1.5）；
> 4. □ 字节流不保留 send 分段的观察（本册 §1.6）。

## $\rm \S \, 4.1$ 从主机到进程：端口与分用

IP 交付止步于主机，而主机上一刻有几十个进程在收发。传输层接手最后一段：**端口（port）**（计算机速通 §23.2 用过它）是 16 位编号（0–65535），每个收发数据的进程占住一个，0–1023 约定留给公认服务。发送时，多个进程的数据共用一张网卡依次发出，靠头里的端口号标明归属，这叫**复用（multiplexing）**；接收时，内核按「协议与端口」把每个包分回对应进程，这叫**分用（demultiplexing）**。「协议」一栏不可缺少：TCP 与 UDP 的端口各自独立编号，8080 的 TCP 与 8080 的 UDP 是两个互不相干的门牌。

「IP 地址 + 协议 + 端口」三元组于是唯一确定一条通道的一端。本章两个协议的分野，就从这个三元组往后的交付语义开始。

**本节小结**：端口把交付从主机推进到进程——发送侧多进程复用一张网卡，接收侧内核按「协议＋端口」分用；TCP 的 8080 与 UDP 的 8080 是两扇不同的门。

## $\rm \S \, 4.2$ UDP：最小信封

**用户数据报协议（User Datagram Protocol，UDP）**在 IP 之上只加薄薄一层：头部固定 8 字节：源端口、目的端口、长度、校验和；校验和错了整包丢弃，发现而不补救，与 §2.2 的帧校验同一哲学。它的三个语义：

1. **无连接（connectionless）**：不握手、不留状态，拿到对方地址即可发送；
2. 保边界：一次 sendto 对应一个独立的数据报，接收方一次 recvfrom 恰好取走一个，多不退、少不补，第 2 章帧的「边界感」在传输层重现；
3. 不承诺可靠：继承 IP 的尽力而为，丢了不补、乱了不管。

邮政比喻里，UDP 是把写好地址的信封直接投进邮筒：便宜、快，寄丢自理。

**本节小结**：UDP 只在 IP 上加 8 字节头：不握手、保边界、不补救——IP 的语义几乎原样递给应用，省下的开销都变成快。

## $\rm \S \, 4.3$ TCP：字节流与连接

**传输控制协议（Transmission Control Protocol，TCP）**走向另一个极端：头部至少 20 字节，通信前先与对方协商出一组共同状态，这叫**面向连接（connection-oriented）**，协商过程本身在第 7 章。它对上层交付的承诺是**字节流（byte stream）**：

1. 无边界：应用写进去的字节汇成一条连续的流，send 的次数与分段不留任何痕迹（§1.5 已实测：3 次 send、1 次读到全部）；
2. 可靠有序：接收方读到的字节序列与发送方写入的完全一致：丢了的会补，乱序的会排好。

「可靠」是承诺而非天赋：兑现它的序列号、确认与重传是第 5 章的全部内容。本章先认账，这份承诺注定要付时延与流量的代价。

## $\rm \S \, 4.4$ UDP 与 TCP 的取舍：三个维度

对象已分别定义（§4.2、§4.3），比较用三把可测的尺子：

| 维度 | UDP | TCP |
| --- | --- | --- |
| 时延 | 免握手，拿到地址就发 | 先建连接，至少多一次跨网往返 |
| 开销 | 头固定 8 字节，无后续管理流量 | 头至少 20 字节，另有确认与重传的带宽 |
| 语义 | 独立数据报：可丢、可乱序、保边界 | 字节流：可靠、有序、无边界 |

表之外还有第三种可能：组合。TCP 之上应用可以自定义消息边界（§4.5），UDP 之上也可以自建可靠性，第 8 章的 QUIC 正是在 UDP 上重造了一套可靠有序。所以真正的选型问句不是「谁更好」，而是「应用需要哪种语义，愿意付哪种代价」。

## $\rm \S \, 4.5$ 实验：「粘包」的真相

工程黑话「粘包」说：接收方一次 recv 读到了多个消息粘在一起。做实验验证。发送端分 3 次发送、每次间隔 0.2 秒，接收端等字节全部到齐后只读一次（本机 Windows 11、Python 3.12，回环）：

```python
import socket, time
lst = socket.socket(); lst.bind(("127.0.0.1", 0)); lst.listen(1)
a = socket.create_connection(lst.getsockname()[:2]); b, _ = lst.accept()
for c in (b"AAA|", b"BBB|", b"CCC|"):
    b.send(c); time.sleep(0.2)      # 三次发送，间隔 0.2 秒
time.sleep(0.5)                     # 再等 0.5 秒，字节早已全部到齐
print(a.recv(64))                   # 接收方只读一次
```

本机输出：

```text
b'AAA|BBB|CCC|'
```

12 个字节一次到齐，0.2 秒的间隔也没能把它们分开，说明合并不是「发得太快」，而是字节流语义本身：接收缓冲区里只有先后排列的字节，没有承载「哪次 send」的字段（§1.6 的观察 2 在此盖章）。把最后一行换成 `print([a.recv(5) for _ in range(3)])` 再跑，本机输出 `[b'AAA|B', b'BB|CC', b'C|']`：同样的 12 字节被接收方按 5、5、2 重新切块，第一条消息的尾巴粘上了第二条的头。两个方向都试过即可下结论：「粘包」不是故障，而是 TCP 从未承诺过边界的必然结果；定界是应用层自己的活：固定长度、分隔符（§1.5 那个 `|` 就是），或最常见的长度前缀（先说这条有多长）。

## $\rm \S \, 4.6$ 实验：UDP 保边界的对照

同样的三段内容改走 UDP、同样的节奏（三次 sendto 间隔 0.2 秒），接收端用三次 recvfrom 各取一个；随后故意用 4 字节缓冲区去接一个 9 字节的数据报（本机 Windows 11、Python 3.12，回环）：

```python
import socket, time
r = socket.socket(socket.AF_INET, socket.SOCK_DGRAM); r.bind(("127.0.0.1", 0))
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
for c in (b"AAA|", b"BBB|", b"CCC|"):    # 三个独立数据报
    s.sendto(c, r.getsockname()); time.sleep(0.2)
time.sleep(0.5)
print(r.recvfrom(64)[0], r.recvfrom(64)[0], r.recvfrom(64)[0])   # 三次各取一个
s.sendto(b"AAA|BBB|CCC", r.getsockname()); time.sleep(0.2)       # 9 字节数据报
try:
    print("4B 缓冲 ->", r.recvfrom(4)[0])                        # 缓冲区小于数据报
except OSError as e:
    print("4B 缓冲 -> WinError", e.winerror)
```

本机输出：

```text
b'AAA|' b'BBB|' b'CCC|'
4B 缓冲 -> WinError 10040
```

两段读法：

1. 三次 recvfrom 各取走一个数据报：第一个调用只拿到 b'AAA|'，绝不多带，三个数据报各自完好地排队，边界由协议保住；
2. 后半段：Windows 上缓冲区装不下整个数据报就直接抛 WinError 10040，且此后队列已空（实测），剩余 5 字节一去不返；Linux 上同一行代码不报错，返回前 4 字节并静默丢弃其余，平台差异要记住。对照 §4.5：TCP 的 recv(4) 会把剩余字节留在流里下次再读，UDP 的数据报则是原子的，要么整个读到、要么整段损失。

**本节小结**：UDP 的数据报是原子单位，一次 sendto 一条、一次 recvfrom 恰取一条；缓冲区装不下就整条损失——边界白送，可靠自购。

## $\rm \S \, 4.7$ 何时选 UDP，何时选 TCP

落到真实选型，三个代表场景：

1. DNS 查询：一问一答的小报文，免握手省时延；丢了就再问一次，应用层重试比维持一条 TCP 连接便宜：UDP；
2. 游戏与音视频：下一帧永远比迟到的旧帧值钱，重传补回的画面早已错过播放时刻，宁可丢：UDP，常配应用层自己的抗丢编码；
3. 网页、文件传输、邮件：一字节都不能少、顺序不能乱：TCP，让第 5 章的机制把尽力而为补成可靠。

判断句式照旧带条件：这不是「UDP 快所以实时应用都用 UDP」的教条，而是「迟到的可靠交付对这个应用还有没有价值」的判断；一旦价值反转（例如要完整下载录像回放），同类应用也会回到 TCP。

## $\rm \S \, 4.8$ 通往第 5 章：可靠是承诺，不是天赋

本章把传输层的两种语义摆上桌：UDP 是「IP + 端口」的最小信封，TCP 是重写了交付语义的字节流。遗留的问题只有一个：IP 明明会丢、会乱、会重复（§3.1），TCP 凭什么承诺「接收序列与发送一致」？答案藏在头部那至少 20 字节里：给每个字节编号（序列号），让对方逐段签收（确认），缺了号就补发（重传）。这套机关如何对抗丢包、乱序与重复，还顺带管住发送的节奏，就是第 5 章的全部内容。

## $\rm \S \, 4.11$ 本章自测答案

> 先闭卷作答 §4.9 与 §4.10，再核对。

### $\rm \S \, 4.11.1$ 关键概念回顾答案

1. IP 只到主机且尽力而为；传输层用「协议 + 端口」分用到进程；复用在发送侧（多进程共用网卡），分用在接收侧（内核按三元组分发）。（§4.1）
2. 源端口、目的端口、长度、校验和；无连接排除了握手与状态，保边界排除了流式合并，不承诺可靠排除了确认与重传。（§4.2）
3. 无边界、可靠、有序的字节流；代价是建连时延、更大的头部与确认重传流量。（§4.3、§4.4）
4. TCP 不承载 send 分段，接收缓冲区只是连续字节，「消息」是应用层概念；定界用固定长度、分隔符、长度前缀。（§4.5）
5. 恰好一个数据报，多不退、少不补；Windows 抛 WinError 10040 且剩余字节丢弃，Linux 静默返回前若干字节并丢弃其余。（§4.6）

### $\rm \S \, 4.11.2$ 应用与辨析答案

1. 「快」只覆盖时延一维；换 UDP 同时放弃了可靠有序与拥塞控制（后者第 6 章），要完整交付的应用还得在应用层自建重传，总账未必便宜。（§4.4、§4.7）
2. 循环 recv(100)，每次取满 100 字节即一条记录（或用长度前缀自定边界）；UDP 则一次 sendto 一条记录、一次 recvfrom 取一条，边界白送，丢了整条重发。（§4.5、§4.6）
3. 画面走 UDP（迟到的帧没有播放价值）；文字走 TCP（每条都不能丢，几百毫秒的重传延迟可以接受）。（§4.7）

字节流承诺了「可靠有序」，但承诺需要兑现：序列号怎样把乱序排直，确认与重传怎样把丢失补齐，发送太快又靠什么刹车，下一章拆开 TCP 的机关。
