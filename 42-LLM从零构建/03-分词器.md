# $\rm Chapter \, 3$ 分词器：字节级 BPE 从零训练

上一章把原料洗干净了，这一站是切料机：模型的输入不是字符也不是词，而是一串整数编号，把文本翻译成编号、再把编号忠实翻译回来的那台机器就是分词器（tokenizer）。它看起来是整条产线里最不起眼的一段，却决定了几件事的上限：同样的上下文窗口能装多少内容、嵌入矩阵要吃多少参数、模型眼中的「一个字」长什么样。本章把这台机器从零造出来——在 1 MB 真实文本上训练一个字节级 BPE，词表四档可调，压缩率、耗时、往返一致性全部实测。

> **开始前自检**：本章假设你已经会：
>
> 1. □ 字符与字节的区别，UTF-8 里一个常用汉字占 3 个字节（§3.3 全节站在它上面；需要的前提：任意编程入门的编码常识）；
> 2. □ 用 Python 的 Counter 做词频统计（§3.4 训练循环的原材料；需要的前提：会写基础 Python）；
> 3. □ 「贪心」的含义：每步取当前最优、绝不回头（§3.5 的编码过程就是贪心）；
> 4. □ 矩阵乘法的形状规则（第 1 章 §1.1；§3.6 的嵌入参数账 ${V\times d}$ 用）。
>
> 四条都是当场能补的小件，§3.1 有最低限度版本。
>
> 本章实验脚本在 `_lfs_work/exp03`，纯标准库实现，任何能跑 python3 的机器都能复现；训练全程无随机成分，同一语料重跑逐位一致。

## $\rm \S \, 3.1$ 需要的前提

1. **token 与词表**：token 是模型处理文本的最小单位，每个 token 对应词表（vocabulary）里的一个编号；模型实际读写的是编号序列。词表大小记作 $V$。
2. **UTF-8**：互联网主流的字符编码。ASCII 字符占 1 个字节，常用汉字占 3 个字节，emoji 通常 4 个字节。任何字符串都能无损变成字节序列，反之亦然——「无损」二字后面有大用。
3. **贪心法**：每一步都拿当前看起来最好的选择、不回头重考虑。可能错过全局最优，但快、且行为可预测。
4. **词频统计**：数每个元素出现几次。BPE 的每一步都建立在「数得准」上。
5. **正则表达式的基本读法**：知道 `|`（或）、`+`（一串）、`?`（可有可无）三个符号，就够读 §3.5.1 的 pattern——那一节会逐段翻译。

## $\rm \S \, 3.2$ 为什么不是字符级也不是词级

白话：切料有两种天然切法，切得太粗塞不进炉子，切得太细烧火不划算。词和字符就是这两个极端，BPE 是工业上找到的中间档。

词级切法的死穴有三个。第一，未登录词（OOV, out-of-vocabulary）：词表再大也装不下形态变化与新造词，英语一个「tokenizerization」就能让词级系统交白卷。第二，词表爆炸：自然语言的开放词表轻松上百万，嵌入矩阵 ${V\times d}$ 直接失控。第三，低频词学不好：词表里一半的词一年见不了几次面，嵌入向量根本没被训透。

字符级的死穴恰好相反：序列太长。同样一段话，字符数是词数的四五倍，而 Transformer 的注意力账随序列长度平方涨（第 6 章细算）——切得碎，账就爆。顺带一提，同一段中文在字符级是 BPE 级的两三倍长，上下文窗口按 token 计费，切法直接决定窗口的「实际容量」。

给「长」一个量感。本章那份 1 MB 教材语料，词表 512 的 BPE 切出 618,080 个 token，词表 8,192 只切出 276,284 个（§3.6 实测表）——粒度差出一倍多，窗口的实际容量、注意力的平方账、训练算力全都跟着这个倍数走。切料粗细不是风格问题，是产线的第一笔成本账。

字节对编码（Byte Pair Encoding, BPE）的立场：高频组合并成整块（the、tion、常用的「分词」），低频组合一路拆到底。词表可控、没有 OOV、序列长度居中。这条路从数据压缩算法（Gage 1994）走到神经机器翻译（Sennrich et al. 2016），再被 GPT-2 推到字节级（Radford et al. 2019），至今仍是主流。

本节小结：词级死于 OOV 与词表爆炸，字符级死于序列太长，BPE 在两者之间按频率划界——这是整个设计的中心思想。

## $\rm \S \, 3.3$ 字节是底座：256 个初始符号

白话：BPE 需要一套「不可再分」的初始符号。GPT-2 的答案是：不发明字符集，直接用字节的 256 个取值（Radford et al. 2019）。

这个选择的好处是釜底抽薪的。任何文本——中文、英文、emoji、乱码、二进制文件——都是字节序列，而 256 个字节符号能表示一切字节序列，所以**编码永远无损、永远没有 OOV**。上面那串「锟斤拷」也能编码，也能解码，一个字节都不丢。词级方案里「不认识的词怎么办」这个老问题，在字节底座上根本不存在。

「不可再分」也是绝对的：字节底下没有更小的文本单位了，初始符号集不需要任何语言学论证。对比早期方案在「用什么当初始符号」上反复纠结——字母？词根？字符？——字节底座一句话终结讨论。

代价藏在 UTF-8 的变长结构里：一个英文字母 1 个字节起步，一个常用汉字 3 个字节起步。字节是底座不等于字节是终点——中文起步就背着 3 倍的字节负担，能不能把 3 个字节合并成一个「字」token，要看词表大小和语料配比，这笔账 §3.6 用实测数字算。

本节小结：256 个字节符号当初始词表，编码无损、OOV 绝迹；代价是多字节字符要靠后续合并「赚回」效率。

## $\rm \S \, 3.4$ BPE 训练：数相邻对，合并最频对

白话：训练就是一句话——数哪两个符号最常手拉手出现，就给它俩发一张「合并执照」，让它们从此变成一个新符号；发执照的过程重复到词表够大为止。

1. 预分词：先用规则把语料切成「词」状片段（§3.5 讲为什么必须有这一步），统计每个片段的出现次数；
2. 初始化：每个片段变成字节序列，256 个字节值就是初始符号，词表从 256 起步；
3. 循环：数所有片段里**相邻**符号对的出现总频次；把最高频的那对合并成一个新符号，编号接在 256 后面；更新所有片段；
4. 回到第 3 步，直到词表达到目标大小。

复杂度值得一笔。朴素实现每发一张执照就全量重扫一遍语料，$V$ 档词表要扫 $V$ 遍，1 MB 语料、8 千档词表在纯 Python 里能跑到天荒地老。工业做法是增量更新：维护两张表——「符号对 → 总频次」与「符号对 → 包含它的片段清单」；每次合并只碰清单里的片段，把它们拆掉旧对、加上新对，其余片段动都不动。写成伪代码只有几行：

```python
while len(vocab) < V:
    counts = 统计所有片段的相邻符号对        # 按片段频次加权
    pair = argmax(counts)                   # 最频对；平局按编号序固定裁决
    if counts[pair] < 2:
        break                               # 再无可学的结构
    vocab.append(merge(pair))               # 新符号，编号接在 256 之后
    只更新含 pair 的片段                     # 增量：拆旧对、加新对
```

这行循环在说：BPE 训练的全部智慧在两本账上——账记得全（频次），账翻得少（增量）。本章实验用的就是这套增量实现（参考 karpathy/minbpe 的思路），加上另一处提速：在「词频表」上训练而不是在原文上训练，34,247 个不同片段就代表全语料的全部 175,166 次出现——频次加权后，相邻对统计与逐个处理原文完全等价。

实测对账（WSL CPU，纯标准库实现，`_lfs_work/exp03/result.txt`）。语料来自教材站仓库：447 个 `.md` 文件按路径排序、每隔 1 个取 1 个，前 40 个文件拼出恰好 1,000,000 字节，覆盖 11 个一级目录；ASCII 字节占 31.5%，中文字符约 19.6 万个——一份中重英轻的技术教材文本（如实说明：这不是自然网页语料，但对演示 BPE 机制毫无妨碍）。预分词后得到 175,166 个片段、其中不同的 34,247 个。训练从 256 合并到 8,192（7,936 张执照），前 15 张执照的画风如下：

1. 第 1 名频次 18,276，第 2 名频次 13,826——被中文 UTF-8 字节对包揽（语料里中文占大头，最高频的相邻字节自然都在汉字内部）；
2. 第 3 名是「空格＋空格」，频次 9,214——markdown 缩进；
3. 第 14 名是「`\r`＋`\n`」，频次 3,634——Windows 换行符对，语料里的杂质最先被学成 token；
4. 词表尾部的最后三张执照频次只有 6，内容变成「这个＋文件」「可以＋直接」和一段 26 连空格——词表大到一定程度，BPE 开始背词组和排版垃圾；
5. 对照英文侧：英文单词的合并要排到更后面才出现——语料配比直接写进词表构成，谁的字节对多，谁先领执照。

训练耗时也是实测：词表到 512 累计 7.5 秒，到 8,192 累计 92.3 秒（纯 Python、16 核单进程；完整四档表在 §3.6）。训练全程无随机成分，同一语料重跑逐位一致。对照第 1 章的产线比喻：合并执照就是切料规格，领照顺序就是规格优先级——§3.5.2 的编码完全按这个顺序办事。

本节小结：BPE 训练是「数相邻对、合并最频对」的循环；增量更新把复杂度从全量重扫里解放出来；合并日志是语料构成的镜子——中文对、缩进、换行符，什么多它先学什么。

## $\rm \S \, 3.5$ 预分词、编码与特殊 token

白话：机器搭好了，这一节讲它的三个操作细节——切口的规则（预分词）、翻译的顺序（合并序）、以及几个不许碰的保留字（特殊 token）。

### $\rm \S \, 3.5.1$ 预分词正则：切口先定，合并不跨界

为什么不直接在整篇文本上数相邻对？因为 BPE 会无孔不入——跨过空格把「of the」粘成一个 token、跨过换行把两段话缝起来，学出来的都是文本碎片。工业做法是先用一条正则把文本切成「词」状片段，合并只在片段内部进行，切口处永远不越过。

GPT-2 的预分词 pattern（Radford et al. 2019 发布的实现，这里原样给出）：

```text
's|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+
```

逐段读法：

1. `'s|'t|'re|…`：英语缩略形式单独成块，别让撇号被当标点切碎；
2. ` ?\p{L}+`：**一个可选空格加一串字母**——空格粘在词前，这是最关键的一段，下面单独说；
3. ` ?\p{N}+`：可选空格加一串数字（GPT-2 原版不限长度；OpenAI 新一代 cl100k 起改成 `\p{N}{1,3}`，数字最多 3 位一块，见 tiktoken 仓库）；
4. ` ?[^\s\p{L}\p{N}]+`：可选空格加一串标点符号；
5. `\s+(?!\S)|\s+`：空白串，前者保住「词尾的空白」，后者兜底。

空格粘在词前图什么？「 the」整体成为一个预分词单元后，句中的 the 和句首大写的 The 共享同一套子词结构（「he」），空格的代价只付一次；模型看到的每个 token 自带左边界，「这个 token 是不是新词的开头」这类问题就不存在了。代价是词表里每个词都要有一个带空格的双胞胎变体——用词表空间换序列紧凑，划算。

中文的读者要注意：中文没有空格边界，这条正则把一整串连续汉字当成一个「词」片段。所以我们的实测里，最高频的预分词片段根本不是任何词，而是 `'\n'`（10,051 次）、`'.'`（6,297 次）、`'，'`（4,143 次）、`'\r'`（3,155 次）与`'。'`（3,018 次）（`result.txt` 第 2 部分）——在这批技术教材文本里，标点与换行才是最稳定的「词」。BPE 的中文合并，全部发生在这些长片段内部的字节之间。

数字那段有段公案。GPT-2 原版允许任意长的数字连成一块，结果「1234567」这类长数字的切法完全由词频决定、毫无数值语义（本章 §3.7 有实测：`1234567890` 被切成 `12345|6|7|8|90`）。cl100k 起 OpenAI 把数字强制按 1–3 位切开；Llama 2 更激进，逐位切（据 Touvron et al. 2023）——位越细，算术越稳，序列越长，这是一笔公开的取舍。

本实验环境没有 `regex` 包（不支持 `\p{L}` 这类 Unicode 类与占有量词），用标准 `re` 近似：

```python
r"'(?:[sdmt]|ll|ve|re)| ?[^\W\d_]+| ?\d+| ?(?:[^\s\w]|_)+|\s+(?!\S)|\s+"
```

与原版的三点差异，如实声明：近似式里 `[^\W\d_]` 顶替 `\p{L}`，个别非字母的 Unicode 符号（如带圈数字）会被归进字母类；数字段取 `\d+`（同 GPT-2 原版，未做 1–3 位切）；没有占有量词，对病态输入的抗回溯能力弱于生产实现。近似版对 1 MB 语料的覆盖性断言通过（切完拼回去与原文逐字符相等，`result.txt` 第 2 部分）。

### $\rm \S \, 3.5.2$ 编码：按合并序重放

训练完，编码一句话说完：对每个预分词片段的字节序列，反复找出「合并执照编号最小」（也就是最早学到）的相邻对并合并它，直到无对可并。为什么按执照顺序而不是按频率？因为执照顺序是训练时实际发生的合并路径——编码必须重放这条路，训练和推理看到的切法才一致；换成别的优先级，切出来的边界训练时根本没见过。编码的代价是每个片段内平方级的字典查找，1 MB 语料四档编码在实验里只花几秒钟，真正贵的是训练。

实测演示（词表 8,192，`result.txt` 第 6 部分）：

1. `language` 切成 `l | anguage`，两个 token；`Language` 切成 `L | anguage`——大小写一对孪生兄弟，走了两个几乎不相干的 token；
2. `分词器` 切成三个整字 token，每字一个；`Transformer` 切成 `T | ransformer`；
3. `hello world` 切成 `hello | ␣w | or | ld`——注意第二块带着前导空格，§3.5.1 说的「空格粘词前」活体标本。

往返一致性是分词器的生死线：decode(encode(x)) 必须逐字符等于 x。实测在 512/1,024/4,096/8,192 四档词表上，对语料切片、含 emoji 与生僻字的混排句全部 PASS（`result.txt` 第 4 部分）——字节底座的无损性（§3.3）在工程上的兑现。这也是排障时的黄金探针：任何自研分词器，接手第一件事就是跑一轮全量往返断言。

### $\rm \S \, 3.5.3$ 特殊 token：保留字必须走旁路

词表里有少数编号不对应任何文本，它们是协议符号——`<|endoftext|>` 标记文档边界（预训练时用来把多文档缝成一条 token 流），对话模型里的角色标记也是同类。GPT-2 的词表 50,257 就是这么分解的：50,000 次合并＋256 个字节符号＋1 个 `<|endoftext|>`。

关键规矩：特殊 token 不许由普通编码路径碰出来，编码前先把文本按特殊串切开、特殊串直接映射到保留编号。编号放在词表哪头只是惯例——GPT-2 把 `<|endoftext|>` 排在收尾的 50,256，Llama 系把角色符号排在词表开头——重要的是它在词表里占一个固定坑位、且不可由任何文本合并路径生成。实测不设防的后果（`result.txt` 第 5 部分）：把 `第一段结束。<|endoftext|>第二段开始。` 整串直接编码，特殊串被当成字面量碎成 16 个普通 token——协议符号退化成乱码。反过来，若不加甄别就把用户文本里的特殊串放行成编号，用户就能伪造文档边界与角色标记（攻防两个方向都在 §3.8 展开）。

本节小结：切口由正则先定、合并不跨界；空格粘词前是省出来的紧凑；编码按执照顺序贪心重放；特殊 token 走旁路，绝不与普通文本混流。

## $\rm \S \, 3.6$ 词表大小的权衡与工具对照

白话：词表开多大是个三难选择——压缩率想要、嵌入参数嫌贵、低频 token 还学不透。这一节用同一份语料的四档实测把三难摆上桌面。

实测表（`result.txt` 第 3、7 部分；1,000,000 字节同一语料，压缩率＝字节数/token 数）：

| 词表 | 累计耗时（秒） | 压缩率（B/token） | 英文片段 | 中文片段 | 语料总 token |
| --- | --- | --- | --- | --- | --- |
| 512 | 7.5 | 1.618 | 1.268 | 1.824 | 618,080 |
| 1,024 | 11.0 | 2.121 | 1.494 | 2.560 | 471,546 |
| 4,096 | 39.1 | 3.155 | 2.054 | 4.040 | 316,998 |
| 8,192 | 92.3 | 3.619 | 2.305 | 4.721 | 276,284 |

读法：压缩率越大越省——8,192 档下平均每个 token 背 3.619 个字节，512 档只背 1.618 个；「语料总 token」列就是同一份语料训练时的序列长度，直接决定第 5 章训练循环要走的步数。

先看压缩率：词表从 512 到 8,192，同一份语料的 token 数从 61.8 万降到 27.6 万，上下文窗口的「实际内容承载量」翻倍还多——词表越大，每个 token 携带的信息越多，这就是大词表的全部诱惑。本册 nano 模型用的 512 档（第 1 章 §1.6），是「省参数、费序列」的教学配置。现代主流量级在 3.2 万到 25.6 万之间：GPT-2 五万，Llama 2 三万二，Llama 3 十二万八——都是压缩率与参数账反复拉锯后的落点。顺带读一读耗时列：7.5 秒到 92.3 秒，超过线性增长——合并越往后，频次分布越平，每张执照的「性价比」越低，这也是词表不该无限加大的一个信号。

再看代价。嵌入矩阵是 ${V\times d}$ 个参数：512 档时 ${512\times 128=65{,}536}$（第 1 章核对过的数），8,192 档涨到 ${8192\times 128=1{,}048{,}576}$，16 倍。真实模型上这笔账更吓人：GPT-2 small 的词嵌入 ${50257\times 768\approx 3{,}860}$ 万，占其约 1.24 亿总参数的 31.1%；Llama 3 8B 的词嵌入 ${128256\times 4096=525{,}336{,}576}$——正好是第 1 章对账表里那 5.25 亿。输出侧若是未绑定的独立投影，还要再翻一倍；第 4 章会讲的权重绑定（tied embedding）就是让输入嵌入兼任输出投影，直接省下一份 ${V\times d}$——小词表模型尤其爱用。最后是长尾：8,192 档词表尾部的合并频次只有 6（§3.4），这些 token 的嵌入几乎没被训透——词表不是越大越好，低频区是负资产。

中文与英文的悬殊也在这张表里。8,192 档下英文片段 2.305 B/token，中文片段 4.721 B/token——一个汉字 3 字节，折合每字约 0.64 个 token，按字节折算中文反而更「省」；但把词表退回 512，中文片段掉到 1.824 B/token，每字要拆成约 1.65 个 token，多数汉字合不成一个完整 token。同一词表下谁在语料里占大头谁受益——这正是多语模型的词表要按语料配比设计的原因，也是 Llama 3 把词表从上一代的 3.2 万（Llama 2，SentencePiece）一步升到 12.8 万、点名改善多语言压缩效率的动机（据 Touvron et al. 2023；Dubey et al. 2024）。

工具对照（要点版）：

1. tiktoken（OpenAI）：Rust 实现，正则预分词＋BPE，主打推理侧编码速度，GPT-3.5/4 与 Llama 3 系在用（据 tiktoken 仓库）；
2. HF tokenizers：Rust 内核的训推一体库，BPE/WordPiece/Unigram 全家桶，训练自定义分词器的最短路径；
3. SentencePiece（Google）：语言无关，把空格当普通字符（`▁`）处理、无需预分词，解码严格可逆；其 unigram 语言模型路线与 BPE 反着走——先给超大词表，再按似然剪枝（据 Kudo et al. 2018）。unigram 还有一个 BPE 没有的能力：每个切法都有概率，可以随机采样不同切法做数据增强（subword regularization），BPE 只有唯一一条确定性切法。

本节小结：词表三难——压缩率、嵌入参数、长尾学习；四档实测给出量感（512 档 1.618 到 8,192 档 3.619 B/token），中文在小词表下按字拆散、大词表且语料占优时反超英文；工具三家各有地盘。

## $\rm \S \, 3.7$ 分词带来的著名怪事

白话：模型的一些「低级错误」不是脑子的问题，是眼睛的问题——它看到的 world 不是你看到的 world。以下每条都有本章实测背书。

1. **数字不会算术**。实测 `1234567890` 切成 `12345 | 6 | 7 | 8 | 90`，`9.11和9.9谁大` 切成 9 块——数字 token 只是符号，没有大小与进位结构，「9.11 比 9.9 大」这类笑话的根源在此。缓解靠切细：Llama 2 逐位、cl100k 每 1–3 位（据 Touvron et al. 2023；tiktoken 仓库）。
2. **字母数不清**。让模型数「strawberry」里有几个 r 经常翻车，因为它收到的输入里没有字母 r，只有某个含 r 的 token——数字母等于要求它从 token 反推拼写。
3. **大小写是两个世界**。实测 `l | anguage` 对 `L | anguage`，同一个词的大小写版本共享度极低；全大写强调（SCREAMING CASE）在词表里几乎是另一门语言。
4. **空格与排版敏感**。`hello | ␣w | or | ld`——前导空格改变切法；§3.4 里那段 26 连空格甚至拥有自己的 token。多打一个空格，模型看到的输入就变了。
5. **词表里住着死 token**。GPT-2 的词表里藏着一些训练语料几乎从未激活的怪 token，最著名的一个叫 SolidGoldMagikarp（某个 Reddit 用户名），平时沉睡，一旦出现在输入里会诱发奇怪的输出（据 Rumbelow 与 Watkins 2023 年的公开分析）。这是 §3.6 长尾负资产的极端形态：低频 token 不仅学不透，还可能学歪。

这些怪事的共同根源：分词器是模型的「先验感官」，它在预训练前冻结，模型的一切认知都从这套感官里长出来。感官的分辨率，就是认知的分辨率。

本节小结：数字无数值结构、字母不可见、大小写分裂、空格敏感、死 token 沉睡——五件怪事都是 token 边界与词表长尾的产物；理解它们，排障时就先查切分再查模型。

## $\rm \S \, 3.8$ 工程实录

白话：还是老师傅笔记，三段式——现场做法、为什么、出处或载体。

1. **分词器只在采样语料上训练，没人拿 10T 训它**。现场做法：抽几十 GB 量级的代表性样本训词表。为什么：词表只依赖频次排序，几十 GB 足以把排序稳定下来，全量训练多花的机时买不到更好的词表；本章 1 MB 与工业几十 GB 是同一原理的缩放。工业惯例：各家报告只说词表大小与训练语料「的子集」，不铺开细节。
2. **分词器版本冻结，换它等于 checkpoint 作废**。现场做法：tokenizer 与权重同一个版本号发布、同一个仓库存放。为什么：嵌入矩阵按 token 编号索引，编号表一换，全部 embedding 立即错位，模型当场失忆；想换词表只有重训。载体：各开源模型的 tokenizer 配置与权重同 tag 发布（HF 生态惯例）。
3. **特殊 token 的注入与截断双向设防**。现场做法：训练与推理用同一条「显式放行」实现——默认把用户文本中的特殊串当字面量，白名单场景才放行成编号。为什么：不放行时协议符号变乱码（本章实测碎成 16 个 token）；乱放行时用户能伪造文档边界与角色标记，直接操纵上下文结构。载体：主流库（tiktoken、HF tokenizers）都把「特殊串是否生效」做成显式开关。
4. **压缩率的语言不均要先测再上线**。现场做法：选词表前，拿目标语料各语言切片分别算 B/token。为什么：按 token 计费、按 token 算窗口的行业口径下，「同样的内容」在不同语言里的 token 数可以差出一倍（本章 512 档实测：中文每字 1.65 个 token）；用英文语料训的词表去服务中文用户，账单和窗口双双吃亏。据 Dubey et al. 2024，Llama 3 升 12.8 万词表的第一动机就是多语言压缩。
5. **数字切分是算术能力的第一道闸门**。现场做法：数学向的模型在预分词里就把数字切细。为什么：数字 token 无进位结构（§3.7 实测 `12345|6|7|8|90`），块越大越害算术；逐位切（Llama 2，据 Touvron et al. 2023）或 1–3 位切（cl100k）是公开的两档处方。
6. **预分词正则有回溯爆炸的坑**。现场做法：生产正则用占有量词（`?+`、`++`）钉死匹配路径。为什么：普通量词允许引擎回退重试，恶意构造的长数字串、长标点串能把正则打到指数时间——服务进程直接被一条请求挂死；cl100k 的 pattern 里就带着占有量词，Rust 端靠 fancy-regex 支持（据 tiktoken 仓库）。Python `re` 不支持占有量词，自研服务要另想防护。
7. **参考实现认准 minbpe**。现场做法：读 karpathy/minbpe 再动手。为什么：百行级代码把「训练、编码、解码」三件事讲得比任何论文都清楚，本实验的增量训练就是它的工程化版本。
8. **平局裁决必须钉死**。现场做法：频次并列的最高频对，按符号对的编号序取固定一个（本章实现取编号字典序最大者）。为什么：多线程或分布式训练 BPE 时，平局裁决不同步，各机器训出的词表就差一两个合并，tokenizer 文件对不上、整条数据管线返工；「训练要确定性」在分词器上与在模型训练上同等重要。工业惯例：任何公开 tokenizer 的训练实现都固定了平局规则。

本节小结：采样训词表、版本冻结、特殊 token 双向设防、B/token 先测后上线、数字切细、防回溯爆炸——六条都是上线后才知道疼的部位。

## $\rm \S \, 3.9$ 常见错误与证据

这一节按「现象、判据、修法」组织，都是自己人或自己踩过的坑。

1. **词表口径算错**。说好「词表 8,192」，代码却合并了 8,192 次——词表实际 10,448（256 字节＋8,192 合并）。判据：嵌入矩阵形状对不上配置文件时，先查「词表＝256＋合并数（＋特殊 token 数）」这条口径。
2. **编码不按合并序**。训练用一套切法、推理用另一套（比如推理时按频率贪心），同一文本两边切出来的边界不同，模型面对的是训练时没见过的输入。证据：本章 §3.5.2 的规则不是风格建议，是正确性要求。
3. **特殊 token 走了普通编码路径**。实测后果：协议符号碎成 16 个字面量 token。修法：编码前先按特殊串切分，映射走保留编号（§3.5.3）。
4. **拿不同分词器的 token 数横向比价**。同一份语料在我们 512 与 8,192 两档词表下的 token 数是 618,080 对 276,284——差 2.2 倍。跨模型比成本、比「上下文能装几页书」，必须先换算到同一分词器。
5. **用 `errors="ignore"` 静默吞字节**。解码失败悄悄丢字节，往返一致性被破坏还查不出现场。修法：解码用 strict 模式，出错回去查数据源；`result.txt` 第 4 部分的 PASS 就是这么守出来的。
6. **在原文上训练而不是在词频表上训练**。现象：1 MB 语料、8 千档词表，训练一晚跑不完。原因：朴素实现对每次合并在整个原文上重扫，$V$ 遍全文。修法：先预分词＋词频去重，再在「片段 → 频次」表上做增量合并（§3.4）——同样 7,936 次合并，实验里 92.3 秒收工。性能 bug 也是 bug。

本节小结：口径（词表构成）、路径（合并序）、旁路（特殊 token）、可比性（同分词器）、严格性（解码不吞错）——五处翻车点各配一个现场证据。

## $\rm \S \, 3.12$ 本章自测答案

> 先闭卷作答 §3.10 与 §3.11，再核对。

### $\rm \S \, 3.12.1$ 关键概念回顾答案

1. 词级死于 OOV、词表爆炸、低频词学不透；字符级死于序列太长、注意力平方账；BPE 高频成块、低频拆字节，两头兼顾。（§3.2）
2. 256 个字节符号覆盖一切字节流，任何输入都可无损编码；代价是多字节字符（汉字 3 字节）起步负担重，效率要靠训练合并赚回来。（§3.3）
3. 数相邻对频次、合并最频对、重复到目标词表；朴素实现每步全量重扫，增量更新靠「对频次表＋片段倒排」只碰含该对的片段。（§3.4）
4. 「 the」整体成为一个单元：句中句首共享子词结构，空格只付一次代价，每个 token 自带左边界；代价是词表里出现带空格的变体。（§3.5.1）
5. 50,000 次合并＋256 个字节符号＋1 个 `<|endoftext|>`。（§3.5.3）
6. 执照顺序是训练时真实的合并路径，编码重放它才能保证训练与推理切法一致；别的优先级会切出训练时没见过的边界。（§3.5.2）
7. 每个 token 平均携带的字节数，越大越省上下文；实测 8,192 档英文片段 2.305、中文片段 4.721（折合每汉字约 0.64 个 token）。（§3.6）
8. 变贵的是嵌入矩阵 ${V\times d}$、输出侧归一化与（未绑定时的）输出投影；变差的是低频 token 的学习充分度——本章词表尾部合并频次只有 6。（§3.6）
9. 位置只是惯例（GPT-2 在词表尾部、Llama 系在开头）；必须满足的性质是「占用固定编号、且不可由任何文本合并路径生成」——所以要走编码旁路。（§3.5.3）
10. 最高频片段是标点与换行——实测前五名是 `'\n'`、`'.'`、`'，'`、`'\r'`、`'。'`；因为正则把连续汉字整段当一个「词」，中文内部没有预分词边界，最稳定的小片段只剩标点。（§3.5.1）

### $\rm \S \, 3.12.2$ 应用与辨析答案

1. 字符级把文本拉长数倍，注意力按序列长度平方计费，2,048 的窗口实际内容承载量只有 BPE 的几分之一——问题不在模型在切料。实测参照：本章同一份语料，512 与 8,192 两档词表 token 数 618,080 对 276,284，粒度差直接决定窗口容量。（§3.2、§3.6）
2. 生成这种投诉的配置是「词表小，且目标语言不在训练采样里」：本章 512 档的中文片段已经每字拆约 1.65 个 token（1.824 B/token）；而用英文语料训出的词表更狠——GPT-2 的 WebText 几乎没有中文，汉字常按字节拆成 2–3 个 token。修法：把目标语言语料加进训练采样并扩词表——8,192 档中文片段升到 4.721 B/token，每字约 0.64 个 token，按字节折算反超英文；Llama 3 升 12.8 万词表是同一逻辑（据 Dubey et al. 2024）。（§3.6）
3. 错在口径：词表＝256 个字节符号＋合并次数（＋特殊 token）。合并 8,192 次得到 10,448；要 8,192 的词表应合并 ${8192-256=7{,}936}$ 次——本章实验正是 7,936 步。（§3.4、§3.5.3）
4. 若当字面量编码：特殊串碎成普通 token（本章实测 16 个），指令被模型当普通文本复读，不生效但也无害。若不加甄别放行成特殊编号：用户成功注入文档边界或角色标记，后面的「指令」被当成新文档，越权风险。修法：默认字面量、白名单放行，训练与服务两侧同一实现。（§3.5.3、§3.8）
