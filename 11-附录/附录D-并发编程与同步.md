# $\rm Appendix \, D$ 并发编程与同步

> 竞赛中你写的每个程序都是单线程的——从 `main` 开始，一条路走到结束。真实世界中，浏览器同时加载图片和解析 HTML，游戏引擎同时渲染画面和接收手柄输入，服务器同时处理几百个用户的请求。**并发**不是“让程序跑得更快”的魔法——它是让程序同时做多件事的能力。本章从 race condition 出发，建立互斥锁、原子操作、死锁和线程安全的基本直觉。

你应该已经理解进程和线程的区别（[第 11 章](../03-计算机系统/11-操作系统进程与线程.md)），知道 C++ 的基本语法。不假设你写过任何多线程代码。

## $\rm \S \, D.1$ 当两个线程同时访问一个变量

### $\rm \S \, D.1.1$ 一个在 OJ 中永远不会遇到的 Bug

```cpp
#include <thread>
#include <iostream>

int counter = 0;

void increment() {
    for (int i = 0; i < 100000; ++i) {
        ++counter;   // 看起来像一步操作
    }
}

int main() {
    std::thread t1(increment);
    std::thread t2(increment);
    t1.join(); t2.join();
    std::cout << counter << std::endl;  // 期望 200000，实际每次不同
    return 0;
}
```

期望输出 $200000$。实际输出大约 $120000$—$180000$（具体取决于 CPU 和运气）。**每次运行结果不同**。

### $\rm \S \, D.1.2$ `++counter` 不是一步操作

`++counter` 在 CPU 层面至少分解为三步：

```text
1. 从内存读取 counter 的值到寄存器     (LOAD)
2. 寄存器的值 + 1                      (ADD)
3. 把结果写回内存                      (STORE)
```

当两个线程交错执行时：

```text
时间 →
t1: LOAD  counter (读到 42)
t2:                LOAD counter (也读到 42)
t1: ADD   → 43
t2:                ADD   → 43
t1: STORE (写入 43)
t2:                STORE (也写入 43!)
```

两次 `++counter` 只增加了一次——其中一个更新被**覆盖**了。这就是 **race condition**（竞态条件）——程序的正确性依赖于两个线程的精确执行时序，而时序不由你控制。

> **定义**：Race condition（竞态条件）= 程序的结果依赖于多个线程的执行时序，而时序不被你控制——所以同一个程序可能时对时错。本例这种“同一块内存、至少一个是写、又没有任何同步”的具体形式，在 C++ 里另有名字：**data race**（数据竞争），它本身就是未定义行为。Race condition 的范围更大——后面用原子操作消掉了 data race 的程序，照样可能有竞态（辨析见 D.6）。

## $\rm \S \, D.2$ 互斥锁：让一段代码“独占”

### $\rm \S \, D.2.1$ 锁的基本用法

```cpp
#include <mutex>

int counter = 0;
std::mutex mtx;

void increment() {
    for (int i = 0; i < 100000; ++i) {
        mtx.lock();      // 获取锁——如果别人持有，等待
        ++counter;        // 临界区：同一时刻只有一个线程在这里
        mtx.unlock();    // 释放锁
    }
}
// 输出：200000（每次一致）
```

锁保证**互斥**（mutual exclusion）——同一时刻只有一个线程能进入锁保护的区域（临界区，critical section）。`mtx.lock()` 到 `mtx.unlock()` 之间的代码对其他线程不可见——它们会在 `lock()` 处等待，直到当前线程 `unlock()`。

### $\rm \S \, D.2.2$ RAII 锁：不要手动 unlock

```cpp
void increment() {
    for (int i = 0; i < 100000; ++i) {
        std::lock_guard<std::mutex> guard(mtx);  // 构造时 lock
        ++counter;
        // guard 析构时自动 unlock——即使 ++counter 抛出异常
    }
}
```

如果 `++counter` 抛出异常（不太可能，但在其他场景中很常见——比如网络请求、文件写入），手动 `unlock()` 永远不会执行，其他线程永久等待（死锁）。`lock_guard` 利用 RAII（第 15 章讲过）——离开作用域时析构函数自动释放锁，无论怎么离开的（正常返回、异常、提前 return）。

> **经验规则**：不要手动配对 `lock()`/`unlock()`——任何一条提前返回或异常路径漏掉 `unlock()`，其他线程就会永久等待。简单场景用 `std::lock_guard`，需要条件变量、需要中途解锁或跨作用域持有时用 `std::unique_lock`（配对由它自己负责）。

## $\rm \S \, D.3$ 死锁：当两把锁互相等待

### $\rm \S \, D.3.1$ 最简单的死锁

```cpp
std::mutex mtx_a, mtx_b;

void func1() {
    std::lock_guard g1(mtx_a);  // 拿到 A
    std::this_thread::sleep_for(std::chrono::milliseconds(1));
    std::lock_guard g2(mtx_b);  // 等待 B —— 但 B 被 func2 持有
}
void func2() {
    std::lock_guard g2(mtx_b);  // 拿到 B
    std::this_thread::sleep_for(std::chrono::milliseconds(1));
    std::lock_guard g1(mtx_a);  // 等待 A —— 但 A 被 func1 持有
}
// func1 和 func2 同时运行 → 永远互相等待 → 死锁
```

死锁的四个必要条件（全部满足才发生）：
1. **互斥**：资源只能被一个线程持有
2. **持有并等待**：持有锁的同时等待另一个锁
3. **不可抢占**：锁只能由持有者释放
4. **循环等待**：线程 A 等 B 的锁，B 等 A 的锁

**破坏任何一个条件**就能防止死锁。最实用的是破坏条件 4——**尽量让所有线程以相同顺序获取多把锁**。

```cpp
void func1() {
    std::scoped_lock lock(mtx_a, mtx_b);  // C++17：一次锁住多个，内部用避免死锁的算法
    // 或 C++11: std::lock(mtx_a, mtx_b) + std::lock_guard<std::mutex> + std::adopt_lock
    // 注意：`std::lock_guard g1(mtx_a), g2(mtx_b);` 只是依次各锁一把，
    //      并不"同时"——两边顺序不一致时照样死锁，别把它当成 scoped_lock 用
}
```

## $\rm \S \, D.4$ 原子操作：当锁太重时

### $\rm \S \, D.4.1$ 一个简单的计数器不需要锁

```cpp
#include <atomic>

std::atomic<int> counter(0);

void increment() {
    for (int i = 0; i < 100000; ++i) {
        ++counter;  // 原子操作——CPU 保证这是真正的一步
    }
}
// 输出：200000（每次一致；没有上下文切换与锁开销，通常比锁版本快，竞争激烈时优势会缩小）
```

`std::atomic` 保证读-改-写操作在**硬件层面**是原子的——CPU 指令本身（如 x86 的 `LOCK INC`）就是不可分割的。没有锁的开销，没有上下文切换。

### $\rm \S \, D.4.2$ 什么时候用原子，什么时候用锁

| 场景 | 工具 |
|------|------|
| 单个计数器、标志位 | `std::atomic` |
| 多步操作（读→判断→写） | 锁——原子不够，两步之间状态可能变 |
| 复杂数据结构（链表、map） | 锁（或无锁结构——专家话题） |
| 读多写少 | `std::shared_mutex`（读写锁） |

**原子操作不是万能药**——`if (flag.load()) flag.store(false)` 不是原子的整体。从 `load` 到 `store` 之间，其他线程可能已经修改了 `flag`。这种“检查然后操作”的模式需要锁或 `compare_exchange`。

## $\rm \S \, D.5$ 线程安全：你的代码被多线程调用也能正常工作

### $\rm \S \, D.5.1$ 什么会导致线程不安全

- **共享可变状态**（shared mutable state）——如果多个线程访问同一个变量且至少一个是写
- **静态/全局变量**——所有线程共享同一份
- **非线程安全的第三方库**——调用前查文档（如 POSIX 并不要求 `rand()` 线程安全，`strtok()` 用静态缓冲区保存解析位置，两个线程交叉调用会互相破坏）
- **惰性初始化**——两个线程同时检查“是否已初始化”，都以为没有，各自初始化一次

### $\rm \S \, D.5.2$ 不可变性是最强的线程安全

如果一个对象创建后**永远不会被修改**（immutable），任意多个线程同时读取它不需要任何同步——没有写操作，就没有 race condition。前提有两个：对象必须在所有线程开始读之前**构造完成**（安全发布，别一边构造一边把指针递给别的线程）；对象内部也不能有惰性初始化、缓存之类的隐藏写入。

```cpp
const std::vector<Paper> papers = load_papers();  // 只读——线程安全
// 多个线程同时 papers.size(), papers[idx] —— 完全安全
```

这就是为什么函数式编程推崇不可变数据——它从根本上消除了并发 bug 中最常见的一类。

## $\rm \S \, D.6$ happens-before：加锁为什么就够了

D.1 的例子说明没有同步时读写会互相覆盖；D.2 加了锁，程序就对了。但这里跳过了一个更基本的问题：**为什么加了锁之后，线程 1 写的 `counter`，线程 2 一定看得见？**

CPU 有缓存、编译器会重排指令、写操作可能只是进了写缓冲区——从硬件到编译器，每一层都在做“对单线程语义无损但会改变多线程观感”的优化。所以“线程 A 写完，线程 B 立刻读”并不是免费的保证，它是一个需要被建立的**同步关系**。

**happens-before（先行发生）** 就是描述这种关系的约定：如果操作 $A$ happens-before 操作 $B$，那么 $A$ 的结果对 $B$ 可见，且 $A$ 在 $B$ 之前发生。它不是一个时间上的先后，而是一种**保证关系**——两个操作可能在物理时间上重叠，只要没有 happens-before 关系，可见性就没有保证。

`std::mutex` 提供了两条边：线程 1 的 `unlock()` happens-before 线程 2 后续对它同一个 mutex 的 `lock()`，并且同一线程内按程序顺序排列。把这两条接起来就得到完整链条：线程 1 在锁内写的所有东西 → `unlock` → 线程 2 的 `lock` → 线程 2 读到那些东西。

```text
线程 1                                    线程 2
  lock(mtx)                                  ...
  counter = 42      ← 临界区内写            ...
  unlock(mtx)  ─────── happens-before ───→  lock(mtx)
                                            read counter → 一定看到 42
```

**这就是“为什么加锁就够了”**：锁不只是互斥，它还建立了 happens-before 边，免费附带了可见性保证。用锁的程序员不需要理解缓存一致性协议，锁把这件事封装掉了。反过来也成立——一个变量只要始终在锁保护下访问，就不需要它自己是原子的，因为可见性由锁负责（D.4 讲的原子操作解决的是另一个问题：无锁场景下单个操作的不可分割性）。

### $\rm \S \, D.6.1$ acquire / release 的直觉

锁的代价在竞争激烈时很高。当你要传递的是“一小块数据准备好了”这样一个信号，可以用更轻的原子操作建立同样的 happens-before 边：**release** 用于发布，**acquire** 用于接收。

```cpp
#include <atomic>
#include <thread>
#include <iostream>

std::atomic<bool> ready(false);
int data = 0;   // 普通变量：没有原子性，可见性完全靠下面的 release/acquire 建立

void producer() {
    data = 42;                                      // ① 先写数据
    ready.store(true, std::memory_order_release);   // ② 再发布：之前的所有写都对后面配对的 acquire 可见
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) {}   // ③ 等到发布
    std::cout << data << std::endl;                 // ④ 这里一定能看到 42
}

int main() {
    std::thread t1(producer), t2(consumer);
    t1.join(); t2.join();
}
```

预期输出与判据：编译运行 `g++ -std=c++17 -pthread -O2 release_acquire.cpp -o ra && ./ra`，稳定打印 `42`。把 `release`/`acquire` 换成 `relaxed` 之后，这个程序的行为就**不再有保证**——可能打印 42，也可能打印 0，而且可能在不同机器、不同优化等级下表现不同。做一个更直观的观察：把 `data = 42` 移到 `ready.store` 之后（保持 `release`），它会偶发打印 0，因为 release 只保证“它之前”的写可见。

acquire/release 的直觉常被说成“刷新缓存”。这个说法会误导：它暗示存在一个可以把缓存同步过去的动作，而实际机制是**禁止重排加保证可见性**——编译器与 CPU 不允许把 release 之前的访存挪到 release 之后，也不允许把 acquire 之后的访存挪到 acquire 之前，从而保证配对成功时那批写在观察者看来已经完成。它约束的是顺序，不是“把数据搬过去”。理解这一点才能解释一件事：`release` 和 `acquire` 必须**配对使用**在同一个原子变量上，单独用一个不起同步作用。

### $\rm \S \, D.6.2$ relaxed 什么时候可用

`std::memory_order_relaxed` 只保证这个原子操作本身不可分割，不建立任何跨线程的可见性顺序。它适用的条件是：**程序正确性不依赖操作之间的先后可见性**。最典型的是纯计数器和统计量。

```cpp
#include <atomic>
#include <thread>
#include <iostream>
#include <vector>

std::atomic<int> counter(0);

void increment() {
    for (int i = 0; i < 100000; ++i) {
        counter.fetch_add(1, std::memory_order_relaxed);  // 只要原子性，不要顺序
    }
}

int main() {
    std::vector<std::thread> ts;
    for (int i = 0; i < 4; ++i) ts.emplace_back(increment);
    for (auto& t : ts) t.join();
    std::cout << counter.load() << std::endl;   // 400000
}
```

预期输出与判据：编译运行 `g++ -std=c++17 -pthread -O2 -o counter counter.cpp && ./counter`（实测 g++ 9.2.0，多次运行均输出 `400000`）。这里 4 个线程各加 10 万次，无论谁先谁后，总数都与顺序无关——所以不需要顺序，只需要每个 `fetch_add` 不可分割。这个程序换成 `relaxed` 正确，换回 `seq_cst` 也正确，只是后者更慢。

relaxed 失效的场合正好是“需要顺序”的时候：用一个 relaxed 的标志位去发布数据（把上面的 `release` 改成 `relaxed`）就是错的，因为 `data = 42` 可能还没写出去。判断方式很简单——问自己“除了这个变量本身的值，我还需要让别的内存修改同时可见吗”。需要，就必须用 acquire/release 或锁；不需要，relaxed 才安全。

> **经验规则**：不确定就用默认的 `seq_cst` 或直接用锁。relaxed 只在你能明确说出“这里不需要顺序”时使用，而且要在注释里写明理由——否则下一个人只会看到一处可疑的优化。

## $\rm \S \, D.7$ 活锁与饥饿：都在动，但没人前进

死锁（D.3）的特征是所有相关线程都停住了，很容易从“进程没反应、CPU 空闲”看出来。另外两类问题则不会：线程一直在运行、CPU 占用很高，但任务没有进展。

### $\rm \S \, D.7.1$ 活锁

**活锁（livelock）** 指线程没有阻塞，但反复重试同一个动作、每次都因为别人的干扰而失败。经典场景是两个人迎面走：都想给对方让路、同时往同一边移，再同时往另一边移——一直在动，始终过不去。

程序员更常见的形态是**无退避的重试**：两个线程都在“拿锁失败 → 立刻重试”的循环里，每次重试都恰好和对方冲突，于是谁都不成功。诊断信号是 CPU 使用率高、日志里反复出现同样的重试记录、而任务完成数不涨。

与死锁的区别可以这样记：死锁是**没有人在动**（都在等），活锁是**每个人都在动但没有人在前进**。修复方式也不同——死锁靠破坏四个必要条件，活锁靠引入退避（失败后等待一个随机时长再重试，让双方的节奏错开）或引入优先级（让其中一个先走）。随机退避比固定退避更有效，因为固定退避会让两个线程继续保持同步。

### $\rm \S \, D.7.2$ 饥饿与优先级反转

**饥饿（starvation）** 指某个线程长期拿不到资源，而其他线程一直在成功。它和活锁的区别是：活锁里所有人都不成功，饥饿里有人一直成功、只有特定的人一直失败。常见成因是锁的获取不公平（新来的请求总是抢在等待者前面）、线程优先级差异、或任务调度策略偏向短任务。

**优先级反转（priority inversion）** 是饥饿的一个著名特例，值得单独认识，因为它的表现和直觉相反。设想三个线程：高优先级 $H$ 需要一把锁，中优先级 $M$ 不需要锁，低优先级 $L$ 正持有那把锁。

```text
1. L 拿到锁，开始执行
2. H 就绪，需要这把锁 → 阻塞等待 L 释放
3. M 就绪，它不需要锁，抢占了 L（L 优先级最低）
4. L 被 M 挤走，永远跑不完 → 锁一直不释放 → H 一直等
结果：优先级最高的 H 被优先级最低的 L（间接）拖住，而真正在跑的是 M
```

$H$ 的等待时间由 $M$ 决定，与 $M$ 本来毫不相关——这就是“反转”的含义。Mars Pathfinder 探测器在 1997 年就因这个问题反复重启，最终靠远程修改解决了。

避免方式有两类。**优先级继承（priority inheritance）** 让持有锁的 $L$ 临时继承 $H$ 的优先级，于是 $M$ 抢不动它，$L$ 能尽快跑完释放锁。**优先级上限（priority ceiling）** 给锁设一个上限优先级，任何持锁线程立刻提升到该优先级。多数实时操作系统和 `std::mutex` 的实现都支持继承策略；在普通应用代码里更实用的做法是**避免让高优先级任务依赖低优先级任务持有的资源**，或者干脆减少共享资源。

> **经验规则**：高 CPU 占用不等于有进展。观察到“负载高、吞吐不涨、日志反复出现同一动作”时，先怀疑活锁与重试风暴，而不是硬件不够。

## $\rm \S \, D.8$ 取消、超时与结构化并发

前面几节讲的都是线程之间怎么正确共享数据。还有一类问题不涉及数据竞争，却同样会让系统卡死：**一个已经开始的工作没法停下来**。

### $\rm \S \, D.8.1$ 取消必须能传到下游

取消（cancellation）通常来自用户点了“停止”、上游请求断开、或者整体超时。它必须沿调用链一路传下去：

```text
用户点停止 → 请求处理函数 → 后台任务 → 逐段处理循环 → 停止
```

任何一环没把这个信号传下去，链条就断在那里：上层以为已经取消，下层的循环仍在跑、仍在占 CPU、仍在写文件。这就是**资源泄漏**——不是内存没释放那么直白，而是“没人再需要的工作还在消耗资源”。更糟的是它可能仍在产生副作用（继续写数据库、继续发网络请求），与用户的理解不一致。

C++ 没有内建的取消机制，通行做法是传一个**取消标志**（原子布尔量或专门的 stop token），由工作循环在每个可中断点检查：

```cpp
#include <atomic>
#include <thread>
#include <iostream>

int main(int argc, char** argv) {
    bool cancel_arg = (argc > 1);        // 加参数 = 模拟“调用方中途取消”
    std::atomic<bool> stop(false);       // 用原子：会被别的线程改

    std::thread worker([&] {
        for (int i = 0; i < 100 && !stop.load(); ++i) {   // 每轮检查取消标志
            std::cout << "处理第 " << i << " 段\n";
            std::this_thread::sleep_for(std::chrono::milliseconds(10));
        }
    });

    if (cancel_arg) {
        std::this_thread::sleep_for(std::chrono::milliseconds(100));
        stop.store(true);                // 设标志不会立刻结束 worker
    }
    worker.join();
    std::cout << "worker 退出\n";
}
```

预期输出与判据：编译运行 `g++ -std=c++17 -pthread -O2 cancel.cpp -o cancel`。不带参数运行打印到“处理第 99 段”后接“worker 退出”；带任意参数运行（`./cancel x`）在约第 6 段附近停下并接“worker 退出”——实测在约 100 ms 处停止，早一两段或晚一两段都是正常的，误差来自 10 ms 的轮询间隔。

这个例子暴露了两个容易踩的坑。**取消是协作式的**，不是杀死：`stop.store(true)` 只是设了标志，worker 要跑到下一次检查才退出——如果循环体每轮耗时 10 秒，取消就要等 10 秒才生效。所以检查点要放在足够短的间隔上。**`worker.join()` 不能省**：不 join 就退出 `main`，可能在线程还在访问已析构的对象时终止进程——这正好对应 D.5.2 里“安全发布”的反面。

### $\rm \S \, D.8.2$ 超时要逐层设置

超时（timeout）比取消更常见，因为它是自动触发的。它的关键原则是**逐层设置且内层小于外层**。

设想一次请求的预算：客户端等 5 秒，服务端处理预算 3 秒，服务端在一次处理里要查两次数据库，每次查询分别限 1 秒。这个结构是刻意设计的：内层先超时，外层才有时间做补救（重试、降级、返回部分结果、写一条日志）；如果内层没有超时而上层只有超时，那么上层超时时它已经不关心下层在做什么了——那个仍在跑的查询成了泄漏的资源。

反过来，如果各层超时值相等或者外层小于内层，就会出现“外层已经放弃、内层还在干活”的组合。所以每一层都要有超时，且从外到内递减。

### $\rm \S \, D.8.3$ 结构化并发

取消和超时要能正确工作，需要一个前提：**谁负责等谁**有明确的规则。手工 `join` 所有线程、手工传递取消标志，在代码规模上去以后很难保证不漏。**结构化并发（structured concurrency）** 用一条规则取代这些手工约定：**父任务必须等它的所有子任务结束才结束；任何一个子任务失败，所有子任务一起取消**。

```text
       主任务（父）
        ├── 子任务 A ──┐
        ├── 子任务 B ──┤ 父任务结束前，A/B/C 都必须已经有结果
        └── 子任务 C ──┘
   若 B 抛异常 → 取消 A 和 C，把 B 的错误报给父任务
```

这条规则带来三个直接好处：不会出现“父任务返回了但还有后台线程在跑”的泄漏；错误不会因为某个子任务失败而被静默吞掉（父任务必须处理它）；代码的嵌套结构与任务的生存期一致，读代码就能看出谁在等谁。`std::thread` 本身不提供这个保证（`join` 要手动写、异常会绕开它），所以实践中要用 `std::jthread`（C++20，析构时自动请求停止并 join）、`std::async` 的 future（`wait` 时收拢），或者 Python 的 `asyncio.TaskGroup`、Java 的 `StructuredTaskScope` 这类专门设施。

D.8.1 的例子若改成结构化并发的写法，那个 `worker.join()` 就不是“别忘了写”的约定，而是语言机制保证的：作用域结束前必须收拢。

## $\rm \S \, D.9$ 有界队列与背压

前面的问题都出在“协调已经在跑的线程”。还有一类问题出在**生产与消费的速度不一致**：生产者产生数据的速度长期快于消费者处理的速度。

### $\rm \S \, D.9.1$ 无界队列为什么会拖垮系统

直觉的解法是加一个队列解耦两侧——生产者只管入队，消费者慢慢处理。如果这个队列没有容量上限，后果是内存随积压量线性增长，直到 OOM 或系统开始换页而整体变慢。

这里的危险在于**它表现为渐进的性能问题，而不是明确的错误**。系统不会在积压开始时报警，只会越来越慢：队列里的元素本身占内存，队列节点的分配与销毁增加开销，缓存局部性变差，最后 swap 让一切都慢一个量级。等到 OOM 发生时，真正的原因（上游流量超过处理能力）已经被埋在几十层调用栈之下了。

更根本的一点：**积压量是信息系统，用掉它是浪费**。一个正在无限增长的队列说明消费能力不足，这个事实应该尽快反馈给生产端，而不是存起来。

### $\rm \S \, D.9.2$ 有界队列加阻塞就是背压

**背压（back pressure）** 指把“下游忙不过来”这个信号传回上游，让上游慢下来。实现方式就是给队列设上限：队列满时，入队操作阻塞，生产者自然慢到与消费者相同的节奏。内存占用从此有界（上限 $\times$ 元素大小），积压量也不再是一个不可见的数字。

```python
# backpressure.py：有界队列 + 阻塞 = 背压
import queue
import threading
import time

def producer(q, n):
    for i in range(n):
        q.put(i)              # 队列满时这里会阻塞——这就是背压
        print(f"生产 {i}，队列长度 {q.qsize()}")
    q.put(None)               # 结束哨兵

def consumer(q):
    while True:
        item = q.get()
        if item is None:
            break
        time.sleep(0.05)      # 模拟慢处理
        q.task_done()

q = queue.Queue(maxsize=3)    # 上限 3：不允许无限堆积
t1 = threading.Thread(target=producer, args=(q, 6))
t2 = threading.Thread(target=consumer, args=(q,))
t1.start(); t2.start(); t1.join(); t2.join()
```

预期输出与判据（Python 3.12 实测）：

```text
生产 0，队列长度 1
生产 1，队列长度 2
生产 2，队列长度 3
生产 3，队列长度 3
生产 4，队列长度 3
生产 5，队列长度 3
```

关键观察是第四行之后队列长度**稳定在 3 不再增长**：生产者仍然在推进（它没有被永久卡住），但它被迫以消费者的速度推进。把 `maxsize=3` 改成 `maxsize=0`（`queue.Queue` 中 0 表示无界），输出会变成队列长度一路涨到 6——那就是 §D.9.1 描述的形态。这里 `put` 的阻塞是有意的设计选择：它把“消费者跟不上”这个事实变成了生产者的等待时间。

### $\rm \S \, D.9.3$ 阻塞之外的另一种选择：拒绝

满队列时阻塞适用于“可以等、拒绝处理代价更高”的场景（比如本地流水线、内部任务）。对面向外部请求的服务，阻塞有它的问题：阻塞一个请求处理线程意味着占用它，上游的请求可能已经超时离开，于是你花了资源处理一个没人在等的结果。这类场景通常选择**拒绝**：队列满时立刻返回一个“服务繁忙，请稍后重试”的错误。

| 满队列时的策略 | 适用场景 | 代价 |
|---|---|---|
| 阻塞（等有空间再入队） | 内部流水线、可以等 | 占用当前线程；上游可能已超时 |
| 拒绝（立即返回失败） | 面向外部的请求处理 | 请求失败，需要调用方配合重试 |
| 丢弃最旧（覆盖） | 只需要最新状态的场景（如实时监控快照） | 丢失数据，但保住时效性 |

三种策略都需要队列有上限——**上限是前提，策略是选择**。无界队列连选择的余地都没有。

## $\rm \S \, D.10$ 跨层死锁：数据库看不到的那一半

前端、后端到数据库这条链路上，锁不止一种。除了 D.2 讲的程序锁（mutex），数据库内部还有事务持有的**行锁**。这两层锁各自单独都工作得很好，放在一起却会产生**任何一层都检测不到**的死锁。

### $\rm \S \, D.10.1$ 两层锁怎么互相等待

考察两条路径：

```text
路径 1（转账）：BEGIN → 锁住 accounts 第 7 行 → 申请程序锁 payment_lock → ...
路径 2（对账）：拿到程序锁 payment_lock → BEGIN → 锁住 accounts 第 7 行 → ...
```

路径 1 持有行锁、等待程序锁；路径 2 持有程序锁、等待行锁。这是教科书式的循环等待，但**数据库的死锁检测器看不到它**——数据库只知道路径 2 在等行锁，它看不到路径 1 手里的程序锁，因为那是进程内的 mutex，不在数据库的视野里。同样，应用层的超时机制也看不到行锁那一半。结果是两边都以为对方“只是慢”，一直等下去。

问题的根源是**加锁顺序在两层的混合视图里不一致**：路径 1 先数据库后程序，路径 2 先程序后数据库。

### $\rm \S \, D.10.2$ 应对方式

**统一加锁顺序**是最直接的办法：规定“所有事务先取数据库锁，再取程序锁”，或者反过来。只要两条路径遵循同一顺序，就不可能形成跨层循环等待。这条规则需要写成文档并进入评审检查项——它是约定，编译器不会帮你检查。

**缩短事务**降低的是发生概率和影响面。事务持有行锁的时间越长，与程序锁交叉的窗口越大。经验规则是事务里只放数据库操作：把网络调用、文件读写、用户确认、模型推理全部移到事务之外。

```python
# short_txn.py：把网络调用移出事务
import sqlite3, time

def transfer_bad(conn, src, dst, amount):
    cur = conn.cursor()
    cur.execute("BEGIN IMMEDIATE")            # 开始写事务——立刻持有写锁
    cur.execute("SELECT balance FROM accounts WHERE id = ?", (src,))
    balance = cur.fetchone()[0]
    time.sleep(0.5)                           # 模拟一次网络调用（真实场景是调支付网关）
    if balance < amount:
        cur.execute("ROLLBACK")
        return False
    cur.execute("UPDATE accounts SET balance = balance - ? WHERE id = ?", (amount, src))
    cur.execute("UPDATE accounts SET balance = balance + ? WHERE id = ?", (amount, dst))
    conn.commit()
    return True

def transfer_good(conn, src, dst, amount, gateway):
    cur = conn.cursor()
    cur.execute("SELECT balance FROM accounts WHERE id = ?", (src,))
    balance = cur.fetchone()[0]
    if balance < amount:
        return False
    gateway()                                 # 网络调用放在事务之外，锁不再被它拖住
    cur.execute("BEGIN IMMEDIATE")
    cur.execute("UPDATE accounts SET balance = balance - ? WHERE id = ?", (amount, src))
    cur.execute("UPDATE accounts SET balance = balance + ? WHERE id = ?", (amount, dst))
    conn.commit()
    return True
```

预期输出与判据：上面两个函数用同一份内存库跑，都返回 `True` 且余额变化一致（`[(1, 900), (2, 100)]`）——功能相同，差别在于持锁时长：`transfer_bad` 持有行锁约 500 ms，`transfer_good` 只持有到 `commit` 的瞬间。要观察这个差别，把 `time.sleep(0.5)` 放大到几秒，再从另一个连接（第二个 sqlite3 连接，注意 SQLite 的写锁是库级的）尝试写同一批数据：`transfer_bad` 期间会持续被拒绝，`transfer_good` 期间很快就能写进去。

> **经验规则**：事务里不做网络调用、不做文件读写、不等待人工输入。这三件事的耗时都不可控，而它们每多占一毫秒，行锁就多被持有毫秒，跨层死锁与锁等待超时的概率就增加。

**给程序锁设超时**是兜底。既然跨层死锁无法被任何一层的检测器发现，就需要一个“等太久就放弃”的机制。超时后必须**回滚事务再释放程序锁**，并且要能安全重试——否则放弃只是把死锁换成了数据不一致。

## $\rm \S \, D.11$ 并发测试为什么不稳定

把上面的知识用于测试时会撞上一个矛盾：并发 bug 是概率性的，而测试需要确定的结果。

### $\rm \S \, D.11.1$ 两种失效方式

**测试该失败时通过**是最常见的一种。D.1 那个没有同步的计数器就是一个例子：它确实有 bug，但测试可能一直通过。

```cpp
#include <thread>
#include <cassert>
#include <iostream>

int counter = 0;

void increment() {
    for (int i = 0; i < 100000; ++i) ++counter;   // 没有同步
}

int main() {
    std::thread t1(increment), t2(increment);
    t1.join(); t2.join();
    assert(counter == 200000);       // NDEBUG 下被编译掉，测试名存实亡
    std::cout << "passed\n";
}
```

预期输出与判据：`g++ -std=c++17 -pthread -O2 race_test.cpp -o race_rel && ./race_rel` 打印 `passed`（连续运行多次都是）；而 `g++ -std=c++17 -pthread -O0 -UNDEBUG race_test.cpp -o race_dbg && ./race_dbg` 会因断言失败而终止（实测 g++ 9.2.0：`Assertion failed: counter == 200000`，退出码 3）。这个对照同时暴露两个问题：**发布构建里 `assert` 被 `NDEBUG` 编译掉**，条件判断根本没执行；而**即使断言生效，`-O0` 下也只是恰好失败**——换成别的机器、别的核数、别的负载就可能通过。

**测试该通过时失败**就是通常说的 flaky test（不稳定测试）。D.1 的例子里，正确的加锁版本不会有问题；但一个测试如果用了贴近实际负载的并发时序（例如启动 100 个线程、依赖它们都在某个时刻就绪），它就可能因为调度变化而偶发失败。附录 G 的 §G.4 从测试治理角度讲这件事，这里补的是“为什么用 `sleep` 制造并发是错的”。

### $\rm \S \, D.11.2$ 用屏障制造确定性交错

用 `sleep` 来“让对方先跑一会儿”是最常见的反模式：它假定了机器速度，在空闲的开发机上够用的间隔，在 CI 机器上就不够了——于是测试在本地稳定通过、在 CI 上偶发失败。更糟的是它把“需要多少时间”这个与硬件相关的量写进了测试。

正确做法是用**同步原语**（barrier、latch、条件变量）精确指定“谁先谁后”，让交错由代码决定而不是由时间决定。`std::latch`（C++20）可以让 $N$ 个线程都到达某个点后才一起继续；下面用条件变量实现同样的“同时起跑”效果，让 D.1 的 bug 更容易复现：

```cpp
#include <thread>
#include <iostream>

int counter = 0;

void increment() {
    for (int i = 0; i < 100000; ++i) ++counter;   // 没有同步，故意保留 bug
}

int main() {
    std::thread t1(increment), t2(increment);     // 同时起跑
    t1.join(); t2.join();
    if (counter == 200000) { std::cout << "pass\n"; return 0; }
    std::cout << "fail counter=" << counter << "\n";
    return 1;                                    // 用退出码表达失败
}
```

实测结果（g++ 9.2.0）：`-O2` 编译后连续运行 4 次都打印 `pass`；`-O0` 编译后运行 3 次的结果是 `pass`、`fail counter=100000`、`fail counter=136671`——同一个有 bug 的程序，在高优化下掩盖了问题，在低优化下才以约三分之二的概率暴露。

三个让并发测试可靠的要点：

1. **用屏障而不是 sleep。** 想让两个线程同时进入临界区，就用 `std::latch`、`std::barrier` 或条件变量在临界区入口处对齐，而不是 `sleep_for` 一个拍脑袋的时长。
2. **用退出码而不是 `assert`。** 发布构建会去掉 `assert`。用“打印结果 + `return 非零`”表达失败，测试框架和 CI 都能看到（对照附录 G 的测试工具链）。
3. **不要要求 100% 复现，要求“能稳定失败”。** 目标是把复现概率从千分之一提到足够高，配合多次运行（`for i in $(seq 20); do ./race_test || break; done`）就能在 CI 里稳定拦住。追求确定性复现需要专门工具（线程调度器、`-fsanitize=thread`、压力工具），那是另一个话题；先用屏障把概率拉起来，性价比最高。

> **经验规则**：一个并发测试如果在开发机上“总是通过”，它可能不是在验证正确性，只是在验证那台机器的调度恰好没踩到坑。先在低优化等级、多核、带负载的条件下跑一遍，再判断这个测试有没有效。

## $\rm \S \, D.12$ 关键概念回顾

1. Race condition 和 data race 有什么区别？
> Data race 是两个线程同时访问同一内存、至少一个写、无同步——是 C++ 标准中的未定义行为。Race condition 更宽泛——即使没有 data race（用了原子操作），程序的正确性仍可能依赖执行时序。

2. `std::lock_guard` 比手动 `lock()/unlock()` 好在哪里？
> 异常安全——离开作用域时自动 unlock，无论怎么离开的（正常、异常、提前 return）。手动 unlock 在异常路径上极容易被遗漏。

3. 死锁的四个必要条件是什么？最简单的预防方法是什么？活锁、饥饿、死锁三者又有什么区别？
> 死锁的四个必要条件：互斥、持有并等待、不可抢占、循环等待；最简单的方法：所有线程以相同顺序获取多把锁。三者区别：死锁是所有线程都停住、都在等；活锁是线程都在运行但反复重试、始终没有前进（CPU 高、吞吐不涨，靠随机退避或优先级打破）；饥饿是有人一直成功、特定线程长期拿不到资源（靠锁的公平性或调度策略解决）。活锁里没有人成功，饥饿里有人一直成功。

4. 什么时候 `std::atomic` 不够用，必须用锁？
> 多步操作（read-check-write）——如“如果余额 ≥ 100 则扣款”：读余额和写余额之间状态可能被其他线程改变。此时需要锁保护整个操作。

5. happens-before 是什么？为什么“加了锁就一定能看到别的线程写的数据”？
> happens-before 是一种保证关系：若 $A$ happens-before $B$，则 $A$ 的结果对 $B$ 可见且 $A$ 在 $B$ 之前发生。它不是时间先后，物理上重叠的操作只要没有这条边就没有可见性保证。锁提供了两条边——同一线程内按程序顺序，且线程 1 的 `unlock()` happens-before 线程 2 对同一个 mutex 的 `lock()`——接起来就得到“临界区内的写对下一个拿到锁的线程可见”。锁不只互斥，它顺带建立了可见性。

## $\rm \S \, D.13$ 应用与辨析

1. 程序加了锁之后变慢了很多，可能是什么原因？
> 锁的粒度太大（一次锁住了整个处理循环）、锁竞争激烈（很多线程等在同一个锁上）、或锁在循环内部反复 lock/unlock。改进：缩小临界区、用读写锁（读多写少时）、重新设计数据结构减少共享。

2. 如何在设计上避免并发问题，而不是事后加锁？
> 减少共享可变状态——用不可变对象、消息传递（线程间通过队列通信而非共享内存）、每个线程拥有自己的数据副本、在最后合并结果（map-reduce 模式）。

3. 一个服务里，处理线程在事务中调用了一次支付网关，另一个路径先拿程序锁再开事务，运行一段时间后两个路径都卡住，数据库的死锁检测器和应用层超时都没报警。可能的根因是什么？
> 跨层死锁：路径 1 持有行锁等程序锁，路径 2 持有程序锁等行锁，两层各自的检测器都看不到另一半（数据库看不到进程内 mutex，应用层看不到行锁），于是双方都以为“对方只是慢”。应对：统一加锁顺序（都先数据库后程序，或反之）、把网络调用移出事务以缩短持锁时间、并给程序锁设超时作为兜底（超时后必须先回滚事务再释放锁，且要能安全重试）。
