> **本章假设你已经会**
>
> 1. ADT 由操作集合定义类型，rep 是实现私有的存储，使用方只面对操作，见第 4 章 §4.1。

第 4 章结尾留了一个口子：`PaperShelf` 至今只有一个实现，使用方面对的还是这个具体的类。而真实需求从不肯停在一种形状上——论文资料管理器先是按页数排 top-k，下个版本要按发表年份排，再下个版本要导出 markdown 表格；每变一次，你都要么改 `PaperShelf` 本体，要么复制出一个新类。第 3 章说 spec 是合同，可这份合同和实现长在同一个类里，合同想换个签约方，全城的文件都要重签。本章把「操作集合」从实现里拆出来立成正式的接口（§5.1）；用锚点实验一数一数：同一个需求变更，落在继承结构和组合+接口结构上，各要动几处代码、引几个 bug（§5.2）；从这个实验读出「组合优于继承」的账（§5.3）；再把三种最常见的拆法命名归档：模板方法、策略、观察者（§5.4）；用锚点实验二算清「换算法」这件事在两种结构下的成本，以及抽象层本身的运行时税（§5.5）；最后把这章的实验结论对齐到行业黑话 SOLID 里的四条（§5.6）。本章实验全部在 WSL2（Python 3.12.3，内核 6.6.87）上真跑过，脚本与完整输出见本册实验记录 `expSW05/result.txt`，两个脚本合计约 37 秒。

## $\rm \S \, 5.1$ 接口与实现：把操作集合立成正式合同

先立任务。假设 `PaperShelf` 的 top-k 排序依据要从「页数」改成「发表年份」，再往后还会加「引用数」。第 4 章的写法里，排序逻辑和 rep、导出格式一起住在 `PaperShelf` 内部，每种需求变化都要进同一个类动刀。问题的根子不在代码写得差，在于「这台机器提供哪些操作」和「这些操作此刻怎么做」两件事被焊死在了一起。

**接口**（interface）指只声明操作、不携带实现的类型：它规定「有什么方法、参数是什么、行为合同是什么」，把「怎么实现」留给签这份合同的类型。Python 里接口常用**抽象基类**（abstract base class，ABC）表达：

```python
from abc import ABC, abstractmethod

class Rank(ABC):                     # 接口：只声明，不实现
    @abstractmethod
    def key(self, p): ...            # p 是 (title, pages, year) 三元组，返回排序键

class PagesRank(Rank):               # 实现一：页数大的排前面
    def key(self, p):
        return -p[1]

class YearRank(Rank):                # 实现二：年份新的排前面
    def key(self, p):
        return -p[2]
```

`@abstractmethod` 的含义是：任何继承 `Rank` 的类必须给出 `key` 的实现，漏写的类在实例化那一刻报 `TypeError`。注意这道检查落在动态界（第 1 章三界光谱）：Java 把 interface 当一等公民、漏实现在编译期就报错，Python 要等到 `PagesRank()` 那一行才拦。语言不同，接口的检查时机不同，但接口作为合同的地位相同。

使用方只依赖接口：

```python
class Shelf:
    def __init__(self, papers, rank):
        self.papers = list(papers)   # 防御性拷贝，§4.3 的老规矩
        self.rank = rank
    def top(self, k):
        ranked = sorted(self.papers, key=self.rank.key)
        return ranked[:k]
```

`Shelf` 的代码里没有 `PagesRank` 也没有 `YearRank`，只有一个 `rank`：它知道对方「有 key 这个操作」，不知道也不关心对方怎么算。加第三种排序，就是再写一个 `Rank` 的实现，`Shelf` 一行不动。第 4 章说 ADT 的使用方面对操作而非存储，接口把这层关系做成了语言强制：连「有几个实现」都不再是使用方需要知道的事实。

对照全书的心智模型：spec 是合同，抽象屏障是防火墙，接口就好比防火墙上标准化的一排插座。插座规定了形状和电压（操作签名与合同），任何合乎插头的电器（实现）都能插上用，换电器不必砸墙。比喻的失效边界也要说清：插座不保证电器质量，接口只约束签名和合同条款，实现把行为做错（比如 `key` 返回了与合同无关的随机数）接口拦不住，拦它的是第 2 章的测试和第 3 章的替换原则审查。

> 本节小结：接口是只含操作声明与合同、不含实现的类型；使用方依赖接口而非具体实现，实现可以增减替换而不惊动调用方；Python 的 ABC 在实例化时刻检查实现完整性，Java/TS 的 interface 在编译期检查；接口不保证实现质量，行为正确性仍由测试与合同审查兜底。

## $\rm \S \, 5.2$ 锚点实验一：改一处需求，动几处代码

接口值多少钱？空谈没有说服力，实验来算。同一份功能（论文列表的 top-k 加导出），各造两份代码树：**继承版**把排序逻辑写死在每个具体类里（`PagesCsvShelf`、`PagesJsonShelf`、`YearCsvShelf`、`YearJsonShelf`，共用一个 `BaseShelf`），**组合+接口版**把「排序依据」和「导出格式」拆成两个接口（`Rank`、`Exporter`），`Shelf` 持有两个接口引用。两版功能完全等价，先跑 200 组随机数据核对过（0 组不一致）才开演。

然后依次来三个真实感很强的需求变更：

1. R1：所有排序平局时按标题字典序打破（改既有逻辑）；
2. R2：新增「按标题字母序」这个排序依据（加一条轴上的选项）；
3. R3：新增 markdown 表格导出（加另一条轴上的选项）。

统计口径三个：波及文件数、类数、以及「排序依据这同一个决策在代码里被写了几遍」。R1 的实验还模拟了一个常见事故：改逻辑的人只改到了 csv 系的两个文件，漏了 json 系的两个——改漏一处在真实项目里天天发生。实测输出（照抄 `result.txt`）：

```text
继承版: 排序决策共 4 处, 本次改到 2 处 (pages_csv 1 + year_csv 1), 漏 2 处
组合版: 排序决策共 2 处, 集中在 ranking.py 一个文件, 全部改到
继承版同排序不同格式变体 top(5) 不一致: pages 家族 189/200, year 家族 188/200 -> 引入行为分裂 bug 2 处
组合版同排序不同格式变体 top(5) 不一致: pages 家族 0/200, year 家族 0/200

继承版: 新增文件 2, 新增类 2 (AlphaCsvShelf, AlphaJsonShelf); 现在文件 7, 类 7, 排序依据书写位置 6
组合版: 新增文件 0, 新增类 1 (AlphaRank); 现在文件 3, 类 8, 排序依据书写位置 3

继承版: 新增文件 3, 新增类 3 (每种排序都要配一个 md 变体); 现在文件 10, 类 10, 排序依据书写位置 9
组合版: 新增文件 0, 新增类 1 (MdExporter); 现在文件 3, 类 9, 排序依据书写位置 3
```

数字要一条条读。R1 的 189/200 不是四个九的巧合：排序键从 `(-pages)` 变成 `(-pages, title)` 后，含平局的数据里两种实现的 top-5 顺序几乎必然分岔（200 组里只有 11 组恰好没踩到平局边界），csv 变体和 json 变体给同一个用户看两个榜单，异常零个、值不同，第 1 章 §1.3 的静默形态换个马甲又来了。组合版 0/200 的原因更根本：排序决策只写在 `Rank` 一处，两个 exporter 共用同一个 `Rank` 对象，想分裂都找不到第二份可漏的文本。R2 与 R3 合起来看增长率：继承版从 5 个类涨到 10 个，组合版从 7 涨到 9——起步时组合版反而多两个类（两个接口的「空壳」），涨着涨着差距倒转。

实验复现方式（WSL Bash，当前目录为本册实验记录 `expSW05`，脚本会把两份代码树写成真实 `.py` 文件再做真实改写，输出重定向到 `result.txt`，单脚本约 19 秒；成功验证是末段「全程统计」两行与上文数字一致）：

```bash
python3 exp1_ripple.py > result.txt
```

> 本节小结：同一个决策（排序依据）在继承版被抄成「每种排序 × 每种格式」份，改一份漏一份就是实测 189/200 的行为分裂；组合+接口版把决策收敛到一份且与格式正交；新增单轴选项时，继承版沿另一条轴复制类，组合版只加一个实现类、另一个轴零改动。

## $\rm \S \, 5.3$ 组合优于继承：乘法对加法，继承剩下的位置

实验一的账可以写成一行式子。设排序依据有 $M$ 种、导出格式有 $N$ 种：

$$
\text{继承版类数} = M \times N + 1,\qquad \text{组合版类数} = M + N + 3
$$

读法：继承版的每个具体类把两条轴焊在一起，类数按乘法涨，最后那个 1 是 `BaseShelf`；组合版两条轴各出 $M$、$N$ 个实现，3 是两个接口加一个 `Shelf` 壳。$M = N = 3$ 时两边是 10 对 9，$M = N = 10$ 时是 101 对 23，乘法与加法的差距随需求增长拉开。类数还不是最贵的：继承版把同一个排序决策抄了 ${M \times N}$ 份（实测书写位置 4 涨到 9），组合版只写 $M$ 份（2 涨到 3）。**副本数**才是维护成本的真账本：改一处需求动几处代码，动几处代码就漏几处代码，§5.2 的 189/200 就是漏的代价。

「组合」（composition）指一个对象在内部持有另一个对象（的接口引用），把一部分职责委托给它，而不是通过继承把父类的代码整个继承下来。打个比方：继承是与生俱来的血缘，孩子身上带着父母的代码，一辈子改不了姓；组合是插头插座，电器坏了换一个，墙上的插座（使用方）毫无察觉。失效边界：组合引入了一层间接，调用 `self.rank.key` 比直接写排序表达式多一跳，调试时多按一次「跳到定义」；对象之间的关系也不再能靠「is-a」的直觉读出来，得看构造函数把什么装了进来。

那继承还剩什么用？它没有被判死刑，只是被限了适用范围：当子类确实是父类的一种、且要复用的是「骨架结构」而非「可替换的策略」时，继承是对的，§5.4 的模板方法就是它的正经岗位。判断标准借用第 3 章 §3.4 的替换原则：任何子类对象必须能在一切使用父类的场合顶替父类而不惊动调用方。满足这条，继承安全；不满足、只是想「蹭一段代码」，用组合。

> 本节小结：继承把多条变化轴按乘法组合成 ${M \times N}$ 个类、${M \times N}$ 份决策副本，组合按加法长成 ${M + N}$ 个实现加几个固定件；组合的代价是一层间接调用；继承的正当岗位是「is-a 且骨架复用」，判据是替换原则。

## $\rm \S \, 5.4$ 三式：模板方法、策略、观察者

§5.1 到 §5.3 搭出来的东西有个通名：把「变」与「不变」拆开。这一节把三种最常用的拆法命名归档，名字来自 GoF 的《设计模式》一书，行业里直接喊模式名。

**模板方法**（Template Method）：骨架固定在父类，个别步骤留给子类填。论文管理器的导出流程就是这样：取全量排名、拼表头、逐行渲染、拼表尾，流程不变，每行渲染成 csv 还是 markdown 可变：

```python
class TableExporter(ABC):
    def export(self, shelf):                    # 模板方法：骨架写死在父类
        rows = shelf.top(shelf.size())
        body = "\n".join(self.render_row(r) for r in rows)
        return self.header() + "\n" + body
    @abstractmethod
    def render_row(self, row): ...              # 工位留给子类

class MdTableExporter(TableExporter):
    def header(self):
        return "|标题|页数|"
    def render_row(self, row):
        return "|" + row[0] + "|" + str(row[1]) + "|"
```

它是继承的正当用法：子类填的是流水线上的工位，不是替换整条流水线；骨架对子类的约定（先 header 后 body、render_row 不带换行符）靠替换原则守住。

**策略**（Strategy）：把一种可替换的算法封装成接口的一个实现，使用方持有接口引用、在装配时选定。§5.1 的 `Rank`、§5.5 要换的排序算法都是它。判断一个变体该用模板方法还是策略，看变化的粒度：填工位用继承，换整台机器用组合。

**观察者**（Observer）：一个对象状态变化时，自动通知所有订阅它的对象，双方都只依赖一个通知接口。论文库新进一篇论文，统计面板要刷新、缓存要失效、备份要排队，三方都等着这件事，但 `PaperLibrary` 不应该认识它们中的任何一个：

```python
class PaperLibrary:
    def __init__(self):
        self._papers = []
        self._watchers = []
    def subscribe(self, watcher):
        self._watchers.append(watcher)
    def add(self, paper):
        self._papers.append(paper)
        for w in self._watchers:
            w.update(paper)                     # 一处变动，多方得通知
```

不订阅就得轮询：面板每隔几秒问一次「有新论文吗」，问了十次九次空。观察者把「问」倒转成「报」，代价是三条新义务：通知顺序没有承诺（订阅者别依赖谁先谁后）；某个观察者的 `update` 抛异常会打断 `add`（顺序执行里它拦住了后面的订阅者），想隔离就把每次通知包进 try；订阅了不退订，观察者就被库拽着不放，内存里下不来，订阅的生命周期要和观察者的生命周期对齐。

> 本节小结：模板方法用继承固定骨架、子类填工位；策略把可替换算法做成接口实现、装配时选定；观察者把「状态变了」从轮询倒转成广播；三式共用同一个底层动作：把变化轴从不变的主体里拆出去，各自独立演化。

## $\rm \S \, 5.5$ 锚点实验二：策略替换算法的成本对比

设计模式常被批「过度设计」，这一节把代价和收益都换成数字。场景：数据量涨到十万级后，top-k 还在全量排序（${O(n \log n)}$）就浪费了，堆选前 k（《算法与数据结构》册里堆的价格表，${O(n \log k)}$）才是对的。同一个换算法的动作，落在两种结构上成本几何？

成本先行。继承版里选择算法写死在每个具体类的 `top` 中，换成堆要改 4 个文件 4 处；策略版里算法本身是一个 `TopKSelector` 策略（`FullSortSelector` 与 `HeapSelector` 两个实现），换算法只动装配点（构造 `Shelf` 时传入的参数），1 行：

```text
继承版: 算法写死在每个具体类里, 换算法要改 4 个文件 4 处
策略版: 算法是可换的组件, 换算法只动装配点 1 行 (命中 1 处), 类定义零改动
```

改完不能只看它跑没跑：换算法的前提是行为等价（第 3 章 §3.2，等价的判据来自 spec）。实测 500 组含平局随机数据上，`sorted(papers, key=key)[:k]` 与 `heapq.nsmallest(k, papers, key=key)` 的 top-k 完全一致 500/500——Python 文档也承诺 `nsmallest` 等价于排序后切片，这里等于用抽查复核了承诺。

收益端才是重点。抽象不是免费的：`Shelf` 经策略对象间接调用 `key`，比直接函数调用多一层分派。实测 200 万次调用取最快：直接调用 32 ns/次，经策略对象 35 ns/次，间接开销 1.10 倍——纳秒级的税。而换算法本身在 ${n = 100000,\ k = 10}$ 下实测（5 次取最快）：全量排序取前 10 要 54.5 ms，堆选只要 5.6 ms，9.8 倍。两笔账放在一起，结论自己站起来：抽象层的税是纳秒级常数，算法选择的收益是倍数级；策略模式让后者以 1 行装配代码的代价随时发生。《算法与数据结构》册说复杂度是合同、买错价格表就赔性能，这一节补上后半句：策略让换价格表变成一次配置变更而不是一次手术。

```bash
python3 exp2_strategy.py >> result.txt
```

（复现方式同 §5.2：WSL Bash、当前目录 `expSW05`、单脚本约 18 秒；成功验证是 C1 段的「间接开销」在 1.05 到 1.3 倍之间、C2 段的提速在 5 倍以上，具体数值随机器浮动，量级不变。）

边界也要钉住：1.10 倍的税在每次都走的热路径上会积累，把一个每秒千万次的内层循环包上策略接口，税就从「可忽略」变「可测量」；只有一份实现、也看不见第二种需求的代码，先别立接口：接口的回报来自「会变」，为不会变的东西立合同是纯支出。

> 本节小结：继承版换算法 4 文件 4 处，策略版 1 行装配；两种算法实测 500/500 行为等价；分派开销实测 1.10 倍（纳秒级），算法收益实测 9.8 倍（倍数级）；抽象的税在冷路径上可忽略，在热路径与单实现场景下要掂量。

## $\rm \S \, 5.6$ SOLID 精选四条

行业里把这章的原则浓缩成五个字母的 SOLID 口诀，五个里挑四个讲，剩下那条（接口隔离）在小代码库里痛感最弱，遇到「一个巨型接口逼着实现方空实现一堆用不上的方法」时再学不迟。每条都对应本章实验里的一个实测现象，不是悬空的格言。

1. **单一职责原则**（Single Responsibility Principle）：一个类只该有一个被修改的理由。实测对应：R1 变更只动了 `ranking.py`，排序规则这个职责被收进了一个文件，改它不必路过导出格式（§5.2）。
2. **开闭原则**（Open-Closed Principle）：对扩展开放，对修改关闭：加功能靠加新类，不靠改旧类。实测对应：R2 与 R3 组合版各只新增 1 个类、文件数 3 保持不变（§5.2 全程统计）。
3. **里氏替换原则**（Liskov Substitution Principle）：子类型必须能替换父类型。它就是第 3 章 §3.4 替换原则在类型层的名字：`MdExporter` 能顶替 `CsvExporter` 出现在 `Shelf` 里，靠的是两者都守住 `Exporter` 的后置条件。违反它，接口就成了签了没人守的合同。
4. **依赖倒置原则**（Dependency Inversion Principle）：高层模块（`Shelf`）不依赖低层模块（`PagesRank`），双方都依赖抽象（`Rank`）。实测对应：`Shelf` 的构造函数里出现的是 `rank` 这个接口引用，具体类只在装配点露面（§5.1、§5.5）。

四条其实是同一件事的四个投影：把变化轴拆出去，让决策只写一份，让依赖指向抽象。背口诀不如记住实验一的 189/200：原则违背到极处，就是那个数字。

> 本节小结：单一职责收敛修改理由，开闭原则把新增变成加法，里氏替换守住了接口的可信度，依赖倒置让依赖指向抽象；四条都能在本章实验里找到对应的实测数字。

## $\rm \S \, 5.9$ 本章自测答案

概念回顾答案：

1. 接口是 ADT 的「操作集合」正式化：ADT 说使用方只面对操作，单类时代这只是一句纪律，接口把它变成语言强制，使用方代码里根本写不出具体类名，实现增减替换在编译期（Java/TS）或实例化期（Python ABC）被检查（来源：§5.1）。
2. 继承版把排序决策抄进每个「排序 × 格式」具体类，R1 只改到 2 处、漏了 2 处，含平局数据上同族两个变体的 top-5 几乎必然分岔，200 组实测 189 与 188 组不一致。组合版的排序决策只有 `Rank` 一份，csv/json 两个 exporter 共用同一个 `Rank` 对象，不存在可漏的第二份文本，同族分裂在结构上无从发生（来源：§5.2）。
3. 继承版类数 ${M \times N + 1}$，组合版 ${M + N + 3}$；$M$ 是排序依据种数，$N$ 是导出格式种数。副本口径：同一个排序决策在继承版写 ${M \times N}$ 份（实测 4 涨到 9），组合版写 $M$ 份（实测 2 涨到 3）；改需求的成本跟副本数走，漏改概率也跟副本数走（来源：§5.3）。
4. 判据是变化粒度：填骨架上的工位（个别步骤不同、流程相同）用模板方法，动继承、靠子类重写抽象步骤；换整台机器（整个算法可互换）用策略，动组合、接口引用在装配时选定（来源：§5.4）。
5. 税是纳秒级常数：间接调用 35 ns 对直接 32 ns，1.10 倍；收益是倍数级：${n = 100000,\ k = 10}$ 时堆选对全量排序 9.8 倍。每秒千万次的热路径上税会积累成可测量项，那里才需要掂量（来源：§5.5）。
6. 里氏替换是替换原则的类型层命名：子类型对象必须能在一切使用父类型的场合顶替而不惊动调用方（弱前置、强后置）。违反它，接口的「可替换」承诺失效，实现之间不可互换，依赖抽象等于依赖一个空头合同（来源：§5.6，第 3 章 §3.4）。

应用与辨析答案：

1. 不是。`FastShelf` 蹭的不是「is-a 骨架」，是 `PagesRank` 的实现细节，而且它继承的是具体类而非接口，等于把排序决策和容器职责又焊进一个类。建议：`count_ge` 作为 `Shelf` 的普通方法（排序依据来自 `self.rank`），若性能敏感再把「前 k 选择」或「阈值计数」做成策略接口，让计数算法自己成为一条可替换的变化轴（来源：§5.3、§5.4）。
2. 用 189/200（行为分裂）加「组合版新增单轴选项时另一条轴零改动、文件数 3 保持不变」回答：格式轴将来变化，正是开闭原则覆盖的场景，加 `MdExporter` 即可，旧类零修改。顺序反过来时，R3 先发生：继承版先涨 3 个类（5 涨到 8），R2 再涨 2 个（涨到 10）；组合版先加 `MdExporter`（类 7 涨到 8），再加 `AlphaRank`（涨到 9），终态相同，路径上的两个中间态不同（来源：§5.2）。
3. 方案一：`add` 里逐个 try/except 吞掉异常并记录，合同变成「任何单个观察者出错不影响其他观察者、也不影响 add 本身」，代价是观察者连自己的 bug 都不再可见；方案二：照常传播，合同是「观察者失败即入库失败」，调用方要自己兜底。通知顺序不能进接口合同，因为广播的执行细节（订阅表结构、并发与否）是实现私事，写进合同就剥夺了实现自由，这正是第 3 章「没写的就是允许的」用在接口设计上：合同只锁行为承诺，不锁实现选择（来源：§5.4，第 3 章 §3.5）。

**你现在能做什么**：翻出你最近写的一个有 if/elif 分支或布尔开关的类，两分钟内判断这个开关是不是一条被压扁的变化轴；若是，说出把它拆成接口后，哪些现有代码一行都不用动。
