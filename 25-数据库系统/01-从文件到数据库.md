# $\rm Chapter \, 1$ 从文件到数据库：数据多了之后会发生什么

你在 cs 册 §26.1 已经把 SQLite 当黑盒用过：建表、插行、查询，它都接得住。黑盒的另一面是什么？本章从你更熟悉的起点出发——struct 数组加一个文本文件——看数据量和访问人数涨上去之后，这个方案具体死在哪几步；然后给数据库管理系统下一个一句话定义，用一组真实计时验证它值不值这个价，最后诚实划出「一个文件就够了」的边界。

> **开始前自检**：本章假设你已经会：
>
> 1. □ 用数组加文本文件做过「存记录、追加、按编号查找」（竞赛通用；§1.1 从这里出发）；
> 2. □ 跑过 cs 册 §26.1 的第一条 SELECT，把 SQLite 当成「能跑 SQL 的程序」用过；
> 3. □ 知道并发与并行不是一回事，两个进程可以同时在跑（计算机速通 §11.9；§1.2 的第二场事故需要它）；
> 4. □ 知道 CSV、JSON 这类文本格式的长处（计算机速通 §6.5；§1.6 划边界时要用）。

## $\rm \S \, 1.1$ 问题：数据放文件里，你已经会的那一套

竞赛做题时「把数据留到明天」的标准做法只有一步：进程结束前把数组写进文本文件，明天启动再读回来。三个基本操作你现在闭着眼都能写：

1. **装载**：启动时逐行解析（`split` 加类型转换），填进 `vector<Rec>` 或 Python 列表，整个数据集驻留内存；
2. **追加**：新记录以追加模式写到文件尾部，内存数组同步 push；
3. **查找**：按关键字从头到尾扫一遍，命中即返回。

这套方案在竞赛里无懈可击，因为它依赖三个从未说出口的前提：数据几百 KB 以内、只有你一个进程在用、崩了大不了重新生成。本章全部内容，就是看这三个前提各自失效时会发生什么。

## $\rm \S \, 1.2$ 数据多了之后：会发生的四件事

把数据换成一百万行账本，再把第二个同事的程序也指向同一个文件，四件事依次登场：

1. **按键查找变慢且无法加速**。线性扫描是 $O(n)$：一百万行按 id 查一条要约 $14\,\text{ms}$（§1.4 实测），数据涨十倍它跟着涨十倍。竞赛生的第一反应是排序加二分，但「追加写入」与「文件保持有序」是冲突的——每插一条都要重写整个文件，写代价从 $O(1)$ 涨到 $O(n)$；
2. **并发写互相覆盖**。两个进程都在做「读出、改、写回」：A 读到余额 100，B 也读到 100；A 扣 10 写回 90，B 扣 5 写回 95。A 的扣款凭空消失，没有任何报错。这类事故叫**丢失更新（lost update）**，文件系统只保证单次写入不撕裂，不管「读改写」这个序列是否被别人插队（计算机速通 §11.9）；
3. **崩溃撕开文件**。写一半断电，文件尾部留下半条记录，下次启动解析直接抛异常。你可以自己设计「先写副本、校验、再替换」的恢复流程，写到第三版会发现：自己正在重造一个数据库；
4. **没有模式校验**。手一抖把金额写成字符串、把 id 写重复，文件照单全收。错误静默入库，直到三个月后报表对不上才暴露——中途没有任何一道关卡拦它。

第 4 条里「每条记录该长什么样、每个字段是什么类型」，数据库里叫**模式（schema）**。四件事就是四张欠条：查找、并发、崩溃、校验。

## $\rm \S \, 1.3$ DBMS：把四张欠条接下来的那层软件

白话：把这层软件想成一个前台——你要什么数据不用自己冲进仓库翻找，报个需求（查询）就行；仓库怎么分区、怎么防互相踩踏、失火了怎么盘点，都是前台背后的事。

**数据库管理系统（database management system，DBMS）**一句话：插在你的程序和数据文件之间的软件层，你不再直接读写文件，一切访问以查询的形式交给它，它用四样东西兑现四张欠条。

| 欠条 | DBMS 的机制 | 本册哪章拆开 |
| --- | --- | --- |
| 查找慢 | 索引：按键定位而非全扫 | 第 2、3 章 |
| 并发覆盖 | 并发控制：让交错的读改写排队 | 第 6、7 章 |
| 崩溃撕文件 | 日志：崩溃后重放到一致状态 | 第 6、8 章 |
| 无模式校验 | 模式与约束：入库前逐条检查 | 第 4 章 |

cs 册 §27.1 把 SQLite（程序库）与 PostgreSQL（服务进程）分成两类，这里能看清一层：两者兑现的是同一份欠条清单，差别只在兑现代码住在你的进程里还是一个独立服务里——那是工程选择，不是能力分界。

**本节小结**：DBMS 用索引、并发控制、日志、模式约束四样东西，分别兑现查找、并发、崩溃、校验四张欠条；SQLite 与 PostgreSQL 兑现的是同一份清单，差别只是这套机制住在谁的进程里。

## $\rm \S \, 1.4$ 最小实测：SQLite 与账本数组对账

固定条件：$10^6$ 行记录（id、user、amount），随机种子 20261025，Windows 10、Python 3.12.10、NVMe SSD。任务：按 id 做 100 次点查。在空目录把下面代码存为 `bench.py` 运行（`python bench.py`），或整段粘进 REPL：

```python
import sqlite3, time, random
random.seed(20261025); N = 1_000_000
rows = [(i, f"u{i%8}", i/100) for i in range(N)]      # 账本方案：全量驻留内存
con = sqlite3.connect("demo.db")
con.execute("CREATE TABLE t(id INTEGER PRIMARY KEY, user TEXT, amount REAL)")
con.executemany("INSERT INTO t VALUES(?,?,?)", rows); con.commit()
qs = random.sample(range(N), 100); t0 = time.perf_counter()
for q in qs: next(r for r in rows if r[0] == q)        # 每次查询线性扫描
t1 = time.perf_counter()
for q in qs: con.execute("SELECT user FROM t WHERE id=?", (q,)).fetchone()
print(f"数组扫描 {(t1-t0)*1000:.0f} ms | SQLite {(time.perf_counter()-t1)*1000:.1f} ms")
```

```text
数组扫描 1444 ms | SQLite 14.0 ms
```

读法有三条，第三条是故意放在这里的反向证据：

1. $1444$ 对 $14.0$，约 $103$ 倍。数组方案每次查询扫全表，$O(n)$；SQLite 对主键有一套自带的组织结构，按 id 直接定位而不看其他行（这棵树第 2 章拆）。数据再涨十倍，数组线性变慢，SQLite 几乎不动；
2. DBMS 收管理费：同样这 $10^6$ 行，完整实验（同规模、单事务、默认配置）里插入耗时 $17.2\,\text{s}$，磁盘占用从纯文本的 $20.3\,\text{MB}$ 变成 $24.8\,\text{MB}$。写入慢一点、文件大一点，买的是 §1.2 四张欠条的兑现——那 $17.2\,\text{s}$ 花在哪，第 6、8 章给答案；
3. 条件不在按键列上时优势消失。接着 `bench.py` 的会话跑一段全表条件查询（user 等于 `u4`，两种方案都必须看全部行）：

```python
t0 = time.perf_counter()
n = sum(1 for r in rows if r[1] == "u4")               # 数组：全表扫
print(f"数组全扫 {(time.perf_counter()-t0)*1000:.0f} ms, 命中 {n}")
t0 = time.perf_counter()
m = con.execute("SELECT count(*) FROM t WHERE user='u4'").fetchone()[0]
print(f"SQLite 全扫 {(time.perf_counter()-t0)*1000:.0f} ms, 命中 {m}")
```

```text
数组全扫 48 ms, 命中 125000
SQLite 全扫 48 ms, 命中 125000
```

打平。全表扫谁都躲不掉，DBMS 赢的只是「按键直达」这一步；绝对数字随机器与缓存状态浮动，量级关系稳定。

## $\rm \S \, 1.5$ 页与记录：数据库眼中的文件

向刚才的库再问两个数字（同一个 `con` 会话）：

```python
con.execute("PRAGMA page_size").fetchone()    # (4096,)
con.execute("PRAGMA page_count").fetchone()   # (6066,)
```

SQLite 不是把 $24.8\,\text{MB}$ 当字节流随便摆的：它把文件切成固定大小的**页（page）**，行打包成**记录（record）**塞进页里——$10^6$ 行摊进 $6066$ 页，平均每页约 $165$ 行。为什么按页不按行？因为磁盘与 SSD 不按字节卖货：一次 I/O 无论拿 $1$ 字节还是 $4\,\text{KB}$，起步价差不多，批量才划算。这个代价模型是第 2 章的地基；先记住 $6066$ 和 $165$ 这两个数，第 2 章要用它们复核一棵树的高度。

## $\rm \S \, 1.6$ 诚实边界：什么时候一个文件就够了

DBMS 不是每张桌子的默认配置。判断式是三个量的乘积：数据量、并发、可靠性要求。以下三种情形，老老实实用文件更好：

1. 配置、模板、几 MB 内的导出：单用户、整存整取、人眼要读、Git 要 diff——JSON 或 CSV（计算机速通 §6.5）没有对手；
2. 数据可再生：爬一遍就有、跑一遍脚本就重建的内容，崩溃恢复根本没有服务对象；
3. 单进程、能全进内存、只有按键取值：竞赛的排序加二分、或一个 dict，比任何数据库都快且零依赖。

反过来，四张欠条命中任何一张——多用户同时写、断电不能丢、百万行级按键查、字段必须校验——就是 DBMS 的入场券。

## $\rm \S \, 1.9$ 本章自测答案

> 先闭卷作答 §1.7 与 §1.8，再核对。

### $\rm \S \, 1.9.1$ 关键概念回顾答案

1. 查找慢（线性扫描且有序化与追加冲突）、并发互相覆盖（丢失更新）、崩溃撕文件（半条记录）、无模式校验（错误静默入库）。分别由索引、并发控制、日志恢复、模式约束兑现。（§1.2、§1.3）
2. 数组每次查询全扫，$O(n)$；SQLite 按主键经自带结构直接定位，代价几乎与行数无关。数据涨十倍，扫描次数乘十，定位只多常数。（§1.4）
3. 全表条件查询时两者打平：数组 $48\,\text{ms}$ 对 SQLite $48\,\text{ms}$。全表扫谁都躲不掉，DBMS 的优势限定在按键定位与可靠性，不是每个查询都快。（§1.4）
4. 页是 DBMS 读写文件的固定大小单位（本例 $4096$ 字节），记录是打包进页的一行。$6066$ 是总页数，$165$ 是平均每页行数；第 2 章用它们复核 B+ 树高度。（§1.5）
5. 配置文件（数据量小、零并发、人要读）、可再生数据（可靠性无服务对象）、单进程内存查找（并发与数据量都低）。任一场景都同时踩中判断式里的多个量。（§1.6）

### $\rm \S \, 1.9.2$ 应用与辨析答案

1. 一张已爆：按键查询（每次几十毫秒的扫描叠每秒几百次请求，CPU 直接打满）；后端多进程一起跑再爆两张：并发覆盖与模式校验。迁移次序：先把存储换成带主键的 SQLite 表（欠条一、四立即兑现，cs 册 §26.1 的知识直接可用），出现并发写之后再谈事务与连接管理（本册第 6、7 章，cs 册 §27.2）。（§1.2、§1.4）
2. 跳过半条记录保住了程序不崩，但那条记录代表的业务操作丢没丢无法判定——账户可能已经少了一笔钱。真正需要的是日志：每次修改先把意图记录到可靠的地方，崩溃后重放，让操作要么完整发生、要么当没发生（本册第 6、8 章）。（§1.2）
3. 两类 DBMS 兑现同一份欠条清单（cs 册 §27.1）；SQLite 在嵌入式、单机、读多写少的场景就是生产选择——本章实验里它按主键查询比线性扫描快两个数量级。PostgreSQL 的价值在多客户端并发与服务化运维，差别是工程边界，不是玩具与严肃的分界。（§1.3、§1.4）
