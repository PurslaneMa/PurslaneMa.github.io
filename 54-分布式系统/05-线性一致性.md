# $\rm Chapter \, 5$ 线性一致性：一条「成功」能信到什么时候

> **本章假设你已经会**
>
> 1. 失败三件套：消息能丢、能迟到，时钟不可全信，进程随时会死（§1.2）。
> 2. 复制状态机骨架：多机一致被缩小成一条日志的一致，状态由日志重放而来（§3.2）。
> 3. 提交的定义与它的承诺：多数派落盘的写入，换几任 leader 也不会丢（§4.1）。
> 4. Leader 完备性：新 leader 必然继承全部已提交条目（§4.4）。
> 5. 假死复活的旧主为什么危险：它自己不知道已经下课（§4.3）。

第 4 章收尾留了一个悬而未决的问题：写入成功与读到新值之间，隔着一段还没有合同的时间。本章把这份合同写清楚。路线：先看一次「什么都没坏、却读到旧值」的事故，认出我们真正缺的承诺（§5.1）；把承诺写成精确定义，核心动作是把一段乱序的历史排成一条合法队列（§5.2）；用读写历史钉死它与顺序一致性、因果一致性的差别（§5.3）；然后写一个判定器程序，对几段典型历史给出裁决，并实测枚举量随操作数的增长（§5.4）；最后回答工程问题：一次读要怎么走才买得起这份承诺（§5.5），以及 ZooKeeper 与 etcd 在合同细读上差在哪一行（§5.6）。

## $\rm \S \, 5.1$ 问题：什么都没坏，却读到了旧值

场景照旧是 5 台机器的 Raft 集群，日志、提交、持久化全按第 4 章的规则运转。客户端 A 在时刻 $t_1$ 向 leader 写入 x=1，等到了「成功」。时刻 $t_2$，客户端 B 来读 x，请求被负载均衡分到一台 follower，它还差几条日志没抄完，状态机里的 x 还是 0。B 读到了 0。

逐项对账，没有一个人违纪。写入没有丢：它已在多数派磁盘上，符合提交的定义（§4.1）。leader 没有撒谎：它如实报了成功。follower 也没有犯错：抄日志本来就是异步的，落后几个条目是常态。每个部件都清白，事故照样发生，说明缺的不是机制而是合同：到目前为止，系统对「读」没有任何承诺。第 4 章的合同只覆盖写，即「成功」的写入不会丢；它只字未提读操作必须看见什么。

第一个念头是把读全部赶到 leader 上：正主的状态机一定是新的。这个念头有两个洞。其一，leader 不是身份而是事实，§4.3 的老 leader 假死复活说明，一台自以为是正主的机器可能已被多数派换掉，它的状态机停在旧世界，读它照样读到旧值；其二，读全部压到 leader 一台上，写路径还要它操心，负载先把单点压垮，读多写少的负载尤其如此。洞在 §5.5 逐一填上。

我们想要的承诺，最自然的说法是「读到最新的值」，但「最新」两个字必须钉到时刻上：一条写在 $t_1$ 落盘，一条读在 $t_2$ 才开始，只要 $t_1 \le t_2$，读就必须看见写的结果，哪怕读请求被分到一台刚重启的机器。把这句话写严，就是本章的主角：线性一致性（Linearizability）。

白话：第 4 章的合同管「钱不会从账本上消失」，这一章的合同管「你抬头看余额时，看到的必须是此刻账本上真实的数」。前者防丢失，后者防时差。

> 本节小结：写路径的合同已由提交定义兑现，读路径仍是空白；线性一致性就是把「读必须看见此前的写」精确到实时刻度上的那份合同。

## $\rm \S \, 5.2$ 定义：把历史排成一条队

定义需要两个原料。第一个是历史（history）：一段操作记录，每个操作记五样东西，谁发起、读还是写、哪个 key、什么值，外加两个实时刻度，发出时刻与应答时刻。本章用 `W(x=1)[1,2]` 这样的记号：把 x 写成 1，操作从时刻 1 开始、时刻 2 结束；`R(x)=0[3,4]` 表示读 x 返回 0，从时刻 3 开始、时刻 4 结束。每个 key 的初始值约定为 0。

第二个原料是顺序。一段历史只是乱糟糟的操作堆，判定它合不合法，是问：能不能把所有操作排成一条全序（total order），同时满足两条规则？

规则一，实时序（real-time order）：若操作 A 的应答时刻不晚于操作 B 的发出时刻，A 必须排在 B 前面。

$$
A.\mathrm{end} \le B.\mathrm{start} \;\Longrightarrow\; A \prec B
$$

读法：符号 $A \prec B$ 表示全序里 A 排在 B 之前；实时刻度上互不重叠的两个操作有强制的先后，重叠的两个随便排。

规则二，读值合法：每个读在全序里的返回值，等于排在它之前、同一 key 上最近一次写所写的值。

$$
\mathrm{val}(R) \;=\; \mathrm{val}\Big(\max_{\prec}\, \{\, W \;:\; W \prec R,\ \mathrm{key}(W) = \mathrm{key}(R) \,\}\Big)
$$

读法：花括号里收集全序中排在 $R$ 之前、写在同一 key 上的全部写操作，$\max_{\prec}$ 取其中离 $R$ 最近的那一次，读就必须返回它写的值。

两条都满足的历史称为线性一致的。排出来的那条全序，就是这段历史在物理世界里的「真实执行序」；每个操作在全序里的落点叫它的线性化点（linearization point），必须落在这个操作自己的实时刻度区间之内，直观上，操作就发生在那一刻。

白话：把一段历史想成五个窗口同时接客的银行流水，线性一致性问的是：这堆流水能不能假装只来自一个单队列窗口，先来后到不违背表上的时刻，每个读拿到的都是轮到它时账户里真正的数。失效边界也在这：实时重叠的操作没有先后，怎么排都不违规，这正是并发留给系统的自由度。

定义还有一块要交代：没有应答的操作。崩溃或分区里的读写在历史里只有发出时刻、没有应答时刻，它们卡在区间的一端。处理办法是宽限而不是豁免：无应答操作可以排在「发出时刻之后」的任何位置，也可以当作没发生过；唯一不许的是它反过来约束别人。直觉是它没来得及对世界说话，世界就不必等它。本章的判定器只吃全部完成的历史，未完成操作的判定交给完整实现，边界约定与这里相同。

> 本节小结：线性一致性＝存在一条全序，实时序不倒插、读值取同 key 最近写；它把「读见最新」从口号压成了可机械判定的两条规则。

## $\rm \S \, 5.3$ 三个尺度：线性一致、顺序一致、因果一致

一致性模型（consistency model）就是一份份宽严不同的合同，本节把最常用的三份摆在同一张桌上，每份都用历史钉死。顺序一致性（Sequential Consistency）比线性一致松：它只要求存在一条满足规则二的全序，且每个客户端自己的操作在全序里保持发出顺序（程序顺序），但完全不要求实时序，跨客户端的时刻差一概不看。因果一致性（Causal Consistency）更松：只要求有因果关系的操作（同一客户端的程序顺序，加上读与写构成的传递链）在所有副本上顺序一致，没有因果关系的并发操作，各副本可以各排各的。

三段历史，逐段裁决。

1. 跨客户端的时差。`W(x=1)[1,2]` 发出于客户端 A 且在 $t_2$ 前收到成功，客户端 B 在 $t_3 > t_2$ 才发出 `R(x)=0`。规则一钉死写在前，规则二要求读到 1，读到 0 即违法，线性一致说不。顺序一致却说可以：它不看跨客户端的实时刻度，把写排到读之后照样自洽。这段历史就是 §5.1 的事故，也是两份合同的分水岭。
2. 并发读旧值。`R(x)=0[1,4]` 与 `W(x=1)[2,3]`：写开始时读还没结束，实时刻度重叠，规则一不约束先后。读排到写前面，读到初始值 0，完全合法。线性一致从不承诺「并发期间读到新值」，它只管不倒插的时差。
3. 并发写各奔东西。客户端 A 写 x=1、客户端 B 写 x=2，两写并发、无因果链；副本一上先 1 后 2，最终 x=2，副本二上先 2 后 1，最终 x=1。因果一致性放行：两个写没有因果次序，各副本排队自由。顺序一致拒绝：它要求全体机器共用一条全序，两个副本看到的写序不同就自相矛盾。线性一致同样拒绝。

三份合同由此排出宽严：线性一致最强，实时序加统一全序；顺序一致丢掉实时序；因果一致连统一全序也丢掉。合同越严，读路径越贵，§5.5 会把这笔账算出来。

白话：线性一致是全宇宙共用一块表；顺序一致是各人说话算话，但各人的表可以走得不一样；因果一致只保证「你听说的因果不会倒放」，其余随缘。

> 本节小结：三段历史钉死三个尺度：线性一致拒绝 §5.1 的事故，顺序一致允许它但要求统一全序，因果一致连统一全序都不要求；约束越强，读的账单越重。

## $\rm \S \, 5.4$ 判定器实测：合法还是撒谎

文字定义可以直接交给程序。判定器 `lincheck.py` 吃一段历史，用回溯（backtracking）枚举所有满足规则一的候选队列：每一步从「实时序前驱都已就位」的操作里挑一个，读操作当场核对当前各 key 的最近写值，走不通就退一步换路；找到一条合法全序即判合法，全部走死即判非法。核心搜索逻辑二十行：

```python
def bt(depth):
    if depth == n:
        return True                      # 全部操作就位：合法
    for i in range(n):
        if placed[i] or any(not placed[p] for p in preds[i]):
            continue                     # 已排过，或实时序前驱未就位
        kind, key, val = hist[i][1], hist[i][2], hist[i][3]
        if kind == 'r' and lastw.get(key, 0) != val:
            continue                     # 规则二：读值与最近写对不上
        placed[i] = True
        saved = lastw.get(key, 0)
        if kind == 'w':
            lastw[key] = val
        if bt(depth + 1):
            return True
        lastw[key] = saved               # 回溯：撤销这一步，换下一个候选
        placed[i] = False
    return False
```

统计量 nodes 记录访问过的搜索树结点数，它就是枚举量的账。这段代码只处理全部完成的操作，未完成操作按 §5.2 末尾的宽限约定交由完整实现处理。在 Git Bash 里用

```bash
wsl bash -c "cd /mnt/c/Users/20811/Desktop/26Fall/_uni5_work/expDS05 && python3 lincheck.py"
```

即可复现（脚本与完整输出在 `_uni5_work/expDS05/`）；成功标志是五行裁决各占一行，常见失败是 WSL 未启动的连接报错，先进一次 wsl 再跑。五段典型历史的裁决如下。

| 历史 | 判定 | 枚举量 | 一条合法队列 |
| --- | --- | --- | --- |
| H1：`W(x=1)[1,2]`，`R(x)=1[3,4]` | 合法 | 3 | W → R |
| H2：`W(x=1)[1,2]`，`R(x)=0[3,4]` | 非法 | 2 | 无 |
| H3：`R(x)=0[1,4]`，`W(x=1)[2,3]` | 合法 | 3 | R → W |
| H4：`W(x=1)[1,2]`，`W(x=2)[2,3]`，`R(x)=1[2,3]`，`R(x)=2[3,4]` | 合法 | 6 | W1 → R1 → W2 → R2 |
| H5：H4 的第三个操作改成 `R(x)=0` | 非法 | 3 | 无 |

逐条读这张表。H1 是门槛例，写结束后读才开始，读到新值，合法。H2 是 §5.1 的事故本身：写结束与读开始之间有实时刻度空隙，规则一钉死写在前，读到 0 即非法，判定器只探了 2 个结点就定罪，因为写之后的第一个候选位置就无路可走。H3 是最容易被误判的一例：读到旧值，但读写在实时刻度上重叠，读可以合法排在写之前，故合法；线性一致不等于「永远新」，它只管不倒插的时差。H4 专门制造贪心陷阱：按序号顺排 W1、W2 之后，R1 想读的 1 已被覆盖，必须回溯重排成 W1 → R1 → W2 → R2，枚举量 6 比 H1 的 3 翻了一倍，这就是回溯的代价。H5 把 H4 的第三个操作改成读 0，初始值早被 W1 覆盖，怎么排都凑不出，3 个结点定罪。

枚举量会不会失控？两档实验，种子固定，可复现。第一档 `growth_sim.py`（种子 20261104，每个 n 跑 300 段随机历史，读写各半、时刻随机重叠），抽三个规模看账：

| n | 合法比例 | 枚举量中位 | 枚举量最大 |
| --- | --- | --- | --- |
| 4 | 78.7% | 5 | 11 |
| 7 | 63.7% | 8 | 74 |
| 10 | 50.3% | 11 | 6859 |

中位平、尾部炸：中位数从 5 挪到 11，最大值从 11 涨到 6859，差了三个数量级。大多数历史在前几个结点就被非法读判死，痛全在少数深历史里。第二档 `concurrent_sim.py`（种子 20261105，每个 n 跑 200 段全并发历史，所有操作实时刻度互相重叠，规则一完全不起约束）：

| n | 合法比例 | 枚举量中位 | 枚举量均值 | 枚举量最大 |
| --- | --- | --- | --- | --- |
| 4 | 90.5% | 5 | 5.8 | 16 |
| 5 | 93.0% | 6 | 9.5 | 70 |
| 6 | 92.0% | 7 | 22.7 | 326 |
| 7 | 93.0% | 8 | 76.2 | 1957 |
| 8 | 93.0% | 9 | 316.3 | 13700 |
| 9 | 96.5% | 10 | 2400.8 | 82201 |

均值从 5.8 涨到 2400.8，六步每步至少翻倍，最后一步翻了 7.6 倍；最大值从 16 涨到 82201。实时序这条外部证据一旦缺席，判定就退化成在 ${n!}$ 种排列里带剪枝地找合法队列，这正是理论预言的形状：Gibbons 与 Korach 证明了寄存器历史的线性一致性判定是 NP 完全的（Gibbons & Korach, Testing Shared Memories, SIAM J. Computing, 1997）。工程判定器（Jepsen 生态的 Knossos、开源的 porcupine）与我们的玩具是同一套回溯骨架，再叠剪枝、启发式排序与缓存把常数压小；渐近逃不掉，账照算。

白话：判定器像验票员，把乱糟糟的入场顺序反复重排，找出一种既不违背钟表、又不违背账本的排法；找不到，就当场证明系统撒了谎。

> 本节小结：定义可程序化，五段典型历史正反各半全部判对；全并发档枚举量均值六步涨到 2400.8、最大 82201，印证判定的 NP 完全性，工程实现靠剪枝把常数压小。

## $\rm \S \, 5.5$ 读路径三招：多数派、租约、读索引

判定的难是理论家的麻烦，真正的账单在运行时：线性一致要求每次读都踩在实时序上，而分布式系统里没有任何单一部件能看见全局时间。读路径三招，账单从贵到便宜。

第一招，读多数派（quorum read）。读操作不问一台机器，问一个多数派，从各台应答里按 §3.3 的 term 与提交点比较，取已提交的最新值。它是最直白的实时序实现：多数派里必然有最新提交的值（§4.4 的完备性）。账单要具体：5 台机器上，一次读要收齐 3 份应答、逐台比对日志长度与任期，和一次写同一个数量级；读多写少的负载里，这套账很快付不起。

第二招，租约（lease）。leader 上任时给自己发一张有时限的许可证：租约到期前，我独自充当「最新值的权威」，读请求不问别人。租约的合法性锚在时钟上：只要全集群时钟误差有界，租约期内不可能有新 leader 上任，因为新 leader 需要多数派投票，而按时钟账，租约没到期时旧 leader 仍是多数派承认的正主。账单：读退化成一次本地内存操作，快到极致；代价是引入时钟假设。§1.2 说过时钟不可全信，一旦某台机器漂移超过余量，新旧两台机器可能同时认为自己是权威，合同从根上裂开。租约没有消灭风险，只是把「网络会撒谎」的一部分换成了「时钟基本诚实」。

第三招，读索引（ReadIndex）。Raft 论文给的中间档，流程四步：

```mermaid
flowchart LR
    A["读请求到达 leader"] --> B["记下当前 commitIndex"]
    B --> C["向多数派发一轮心跳，确认自己仍是 leader"]
    C --> D["等状态机应用到该 commitIndex"]
    D --> E["读状态机并返回"]
```

心跳那一步防的正是 §4.3 假死复活的旧主：拿不到多数派承认，就拒绝这次读。账单：一轮心跳往返，不写日志、不等新写入，比读多数派便宜（心跳小、不搬数据），比租约贵（多了网络），但不欠时钟任何东西。

| 读路径 | 每次读的账单 | 额外假设 | 风险 |
| --- | --- | --- | --- |
| 读多数派 | 一次多数派往返＋全量数据比对 | 无 | 无，最保守 |
| 租约 | 一次本地内存读 | 时钟误差有界 | 漂移超限则两权威并存 |
| 读索引 | 一轮心跳往返 | 无 | 无，Raft 实现的常用默认 |

白话：读多数派是每买一瓶水都开全体股东大会；租约是给经理一张当日有效的授权书，效力来自墙上那口走时准的钟；读索引是经理每单打电话向股东会确认一句「我还是正主吧」，慢一点，但不用信钟。

> 本节小结：实时序没有免费实现：读多数派付网络，租约付时钟假设，读索引付一轮心跳；三招的差距就是线性一致这份合同的市价。

## $\rm \S \, 5.6$ ZooKeeper 与 etcd：合同要按行读

同一份合同，不同系统卖法不同。ZooKeeper 用自家协议 ZAB 维护日志，思想与 Raft 同族：多数派提交、全局定序；etcd 直接跑 Raft。两者的写路径都线性一致：所有写走 leader、多数派提交、全局编一个序号。差别全在读路径的默认价目上。

| 维度 | ZooKeeper | etcd |
| --- | --- | --- |
| 写入 | 线性一致（走 leader 与多数派） | 线性一致（走 leader 与多数派） |
| 默认读 | 本地副本应答：不保证线性一致，可能读到旧值 | 走读索引路径：线性一致 |
| 换强一致读 | 显式调 sync()，先把本地副本对齐到最新 | 默认即是，无需任何操作 |
| 换便宜读 | 默认就是，无需配置 | 读请求标 serializable=true，退回本地读 |
| 监视（watch） | 有，数据变化即推送 | 有，基于 MVCC 修订号推送 |

读这张表的正确姿势是按行问价，而不是给整库贴标签。「这个系统线性一致吗」问得太粗，正确问法是「哪条路径上的哪些操作线性一致，其余路径给什么」。ZooKeeper 把便宜摆在默认档：读来自本地副本，只保证每个客户端自己的操作不乱序（顺序一致的读），需要强读时调一次 sync() 把副本对齐；etcd 反过来，把强承诺摆在默认档，想省钱要显式声明 serializable=true。两家都没有骗人，只是价目表一个朝里放、一个朝外放。这也是 §5.5 三招的活注脚：ZooKeeper 的默认读相当于跳过全部三招直接读副本，etcd 的默认读走的就是第三招。

按客户端承诺的合同还有一层，叫会话保证（session guarantees），最常用的两条是读己之写（read-your-writes）与单调读（monotonic reads）：前者要求客户端总能看见自己刚写下的值，后者要求客户端的多次读不随着时间倒退。单客户端会话内，ZooKeeper 的 FIFO 序免费给出这两条；跨会话或换连之后，保证要重新买，还是要 sync()。合同读到这一层才算读完：同一份历史，不同客户端看到的可以不是同一家店。

白话：两家店卖同一种「承诺到账」的生意，ZooKeeper 把强承诺放在货架第二层（要开口才拿），etcd 放在收银台上（默认给，想省钱自己说）。买之前读价目表，别背品牌。

> 本节小结：写路径两家都线性一致，读路径默认价目相反：ZooKeeper 默认弱读、sync() 换强读，etcd 默认强读、serializable=true 换弱读；「是否线性一致」要按路径逐条问。

## $\rm \S \, 5.9$ 本章自测答案

1. 规则一：$A.\mathrm{end} \le B.\mathrm{start} \Rightarrow A \prec B$；规则二：读返回全序中同 key 最近一次写所写的值（§5.2）。用 ≤ 时，恰好相接（应答与发出同刻）的操作也被钉成有先后，取的是保守端；用 < 时，相接操作互相自由，一个读恰好与写应答同刻开始就可能合法读到旧值，合同漏了最常见的一种紧邻情形。
2. 合法是因为读 `R(x)=0` 与写 `W(x=1)` 的实时刻度重叠，规则一不约束先后，读可以排在写之前读到初始值 0（§5.3）。最小修改：把读的区间改成 `[3,4]`，让它在写结束之后才开始，规则一钉死写在前，读到 0 同时违反两条规则，正是 H2。
3. W1、W2 顺排后 R1 想读的 1 已被覆盖，唯一出路是把 R1 插到 W2 之前；不回溯的贪心在 W2 就位后无路可走，会把合法历史误判成非法。事故方向的差别：§5.1 是系统真撒谎而合同抓不住（漏报），贪心误判是系统没撒谎却宣布它撒谎（误报）。审一段历史前，先分清你要防的是哪一边（§5.4）。
4. 读多数派：一次多数派往返加数据比对，无额外假设，最保守；租约：一次本地内存读，假设时钟误差有界，漂移超限则新旧两权威并存；读索引：一轮心跳往返，无时钟假设（§5.5）。租约把「读最新值必须问多数派」的网络账换成「时钟基本诚实」的时钟账，风险从失败三件套的「不可靠网络」挪到「不可靠时钟」（§1.2）。
5. ZooKeeper 默认读来自本地副本，只保证每客户端顺序一致，sync() 是换强读的挡把；etcd 默认走读索引、线性一致，serializable=true 是换便宜读的挡把。两家挡把方向相反：一个默认便宜、花钱升级，一个默认昂贵、声明降级（§5.6）。
6. 场景一：读请求标了 serializable=true，退回本地副本读，副本落后时读到旧值，这是 etcd 官方文档明说的语义降级。场景二：应用层把读做在自己的 watch 缓存上，请求根本没到 etcd，缓存滞后多少，读到的事实就旧多少；此时「etcd 线性一致」与「你的系统读到旧值」同时为真，合同只担保到达 etcd 的那次操作（§5.6）。
7. 反例历史：$t_1$ 时旧 leader L 提交 x=1 并照常应答读；$t_2$ 网络分区，多数派选出新 leader 提交 x=2 并向客户端应答成功；$t_3 > t_2$ 时另一客户端读 L，L 对分区毫不知情，返回 x=1。两个时刻：写的应答时刻 $t_2$ 与读的发出时刻 $t_3$，规则一要求写线性化在读之前，读却返回旧值，违反成立（§5.2）。这正是 §4.3 老 leader 假死复活的读路径版本：日志层的机制不会让旧主自动闭嘴，读路径的三招就是为此设的关卡（§4.3、§5.5）。
8. 不存在合法队列。实时序给出 $R(x)=1 \prec R(x)=0$（前者应答时刻 3 不晚于后者发出时刻 3）；初始值为 0，`R(x)=1` 要读到 1 必须排在 `W(x=1)` 之后。于是全序被迫为 W、R1、R0，此时最近写是 W，`R(x)=0` 必须读 1，与它返回 0 矛盾；把 W 排进其他位置都会先卡死 R1 的读值。三条操作、四种排法，全部死路（§5.2、§5.4）。

**你现在能做什么**：给一段带实时刻度的读写历史，你能手排合法队列或用两步证明不存在，并能对任意一条读请求说出它该走三招里的哪一招、付什么账。

到这里，线性一致这份最贵的合同已经写全：定义、判定、市价与两家店的价目表。但复制方案不止 Raft 一种，下一章把 primary-backup 与链式复制拉上同一张桌子，看它们在同样的合同下怎么讨价还价，为什么链式复制的读吞吐能随节点数线性涨，而 Raft 不行。
