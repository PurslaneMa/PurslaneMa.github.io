# $\rm Chapter \, 9$ TLS 与网络安全：加密在哪一层

## $\rm \S \, 9.1$ 加密放哪一层：三个候选的形状

「让线上的人读不到内容」有三种挂锁位置，效果完全不同：

1. **链路层加密**（Wi-Fi 的 WPA3）：一个路由器到你的电脑这段是密文，下一个路由器 onward 又变明文，只护第一跳，咖啡馆邻居读不到，运营商读得到；
2. **传输层加密**（TLS，本章主角）：两端进程之间的全程密文，中间每个路由器只见加密字节。它坐落在 TCP 之上、HTTP 之下，所以叫传输层安全（Transport Layer Security），却实现为应用层的一个库；
3. **应用层端到端**（Signal 协议、数据库字段加密）：连服务器自己都看不到明文，只有对话双方能解，最彻底，但每类应用要专门设计，不能只靠「换端口」获得。

分层的教训在此再次显形：**在哪一层解决，就同时决定了谁能被保护、谁必须可信**。TLS 选择信任两端进程（服务器侧的运维、代码仍是明文的持有者）；要连服务器都不信，就得再往上一层。

**本节小结**：三个挂锁位置护送的距离各不相同，选层本质上是在选「信任谁」；TLS 护两端进程的全程，把「连服务器也不信」的需求留给应用层端到端。

## $\rm \S \, 9.2$ TLS 交付三件事：对应密码学分册的三把锁

一条 TLS 连接建立后，应用拿到的是：

1. **机密性**：线路字节全部是 AES 等对称算法的密文（后续所有 HTTP 头、体都在里面）；
2. **完整性**：每条记录带认证标签（AEAD，密码学分册 §4.4），线路上改一个比特，接收端立刻报错，不会「悄悄篡改」；
3. **身份**：服务器出示由 CA（证书颁发机构）签名的证书，客户端验证签名链后才交出密钥，防的是「隔壁假基站自称银行」。

三件事凑齐才叫安全：只有机密没有完整＝能被篡改的密文；只有前两件没有身份＝和「谁」加密都没搞清（中间人攻击者大笑着转述两边）。握手要解决的难题是：**双方要在明文线路上、当着窃听者的面，商量出只有彼此知道的对称密钥**，密码学分册 §5.3 的 Diffie–Hellman 正是为此而生，TLS 1.3 强制使用它的临时密钥版本（ECDHE），顺带获得前向保密：服务器私钥将来泄露，过去的会话也解不开。

**本节小结**：TLS 交付机密、完整性、身份三件事，缺一件就开一个口子；握手的任务是在窃听者眼皮底下商量出只有双方知道的密钥，ECDHE 顺手把「私钥晚泄露、旧会话也安全」一并送了。

## $\rm \S \, 9.3$ 实测：握手付几个 RTT，套件名怎么读

对 `www.baidu.com` 分两段计时（本机实测）：

```python
import socket, ssl, time
host, port = 'www.baidu.com', 443
t0 = time.perf_counter()
s = socket.create_connection((host, port), timeout=8)
tcp_ms = (time.perf_counter() - t0) * 1000
t0 = time.perf_counter()
with ssl.create_default_context().wrap_socket(s, server_hostname=host) as ts:
    tls_ms = (time.perf_counter() - t0) * 1000
    print(ts.version(), ts.cipher()[0], ts.getpeercert()['notAfter'])
```

输出：

```text
TCP 25.6 ms | TCP+TLS 共 91.2 ms | TLS 增量 65.6 ms
TLSv1.2  ECDHE-RSA-AES128-GCM-SHA256
主体: baidu.com | 签发者: GlobalSign RSA OV SSL CA 2018 | 有效期至: Jan 24 2027
```

两个读数。第一，TLS 1.2 的增量约 **2.6 倍 RTT**：完整握手要 2 个 RTT（ClientHello↔ServerHello+证书、密钥交换↔Finished），再加证书链验证与非对称运算的 CPU 时间。第二，套件名 `ECDHE-RSA-AES128-GCM-SHA256` 是一台压缩机，五个词各管一件事：**ECDHE**＝密钥交换用椭圆曲线 DH（临时密钥，前向保密）；**RSA**＝证书里签名算法（验身份用）；**AES128**＝后续对称加密；**GCM**＝AEAD 模式（加密＋认证一体）；**SHA256**＝伪随机与记录层的哈希。读法：前两段管「开场怎么握手」，后三段管「正片怎么加密」。

## $\rm \S \, 9.4$ 明文对照：不加锁时线上是什么

同一台服务器，先走 80 端口把请求打到线上，再把字节原样打出来（本机实测）：

```python
import socket
s = socket.create_connection(('www.baidu.com', 80), timeout=8)
req = 'GET / HTTP/1.1\r\nHost: www.baidu.com\r\nConnection: close\r\n\r\n'
s.sendall(req.encode())
print(repr(req)); print(repr(s.recv(120)))
```

输出：

```text
b'GET / HTTP/1.1\r\nHost: www.baidu.com\r\nConnection: close\r\n\r\n'   ← 你发的
b'HTTP/1.1 200 OK\r\nAccept-Ranges: bytes\r\nCache-Control: no-cache...' ← 服务器回的
```

URL、Cookie、正文，在线路上就是这个样子，Wireshark 抓包看到的与这里一字不差。同一个 `wrap_socket` 走 443 后，`ts.recv()` 拿回的仍是这样的明文，**加密在套接字接口的下层透明发生**：你喂它明文，它往线上写密文。要在网卡层亲眼看到密文，用 Wireshark 抓 443 端口：应用数据记录以二进制开头（记录类型 `0x17`、版本号、长度），没有任何 ASCII 结构可读，这正是「透明」的代价与收益：应用不感知加密，排障时要记得多一层。

## $\rm \S \, 9.5$ TLS 1.3：把握手砍到 1 个 RTT

1.2 的 2-RTT 是历史包袱（密钥交换与身份验证分了两轮）。1.3（2018 年标准化）把能预计算的都塞进第一条消息：ClientHello 直接带上密钥交换参数，服务器一条回齐「证书 + 密钥交换 + Finished」，1 个 RTT 完成握手。实测对照（本机，两次连接各自的增量）：

```text
baidu (TLSv1.2):     TCP 25.6 | TLS 增量 65.6 ms ≈ 2.6 × RTT
cloudflare (TLSv1.3): TCP 60.0 | TLS 增量 46.3 ms ≈ 0.8 × RTT
```

1.3 的增量压到了约一个 RTT（第二行 TCP 本身更慢是因为到 Cloudflare 的链路更远，增量要和**各自的** RTT 比，不是互相比绝对值）。会话恢复场景还有 **0-RTT**：重连时客户端第一条消息就带应用数据，握手税归零，代价是新攻击面（重放：0-RTT 数据可能被录下重发），所以只允许幂等请求使用。§8.6 的 QUIC 把 TLS 1.3 揉进自己的握手里，「传输握手 + 加密握手」合并成同一次，正是这套账的极限优化。

## $\rm \S \, 9.6$ 信任链：浏览器凭什么点头

身份验证的最后一块拼图是**证书链**。你的电脑里预装着几十家根 CA 的公钥（操作系统与浏览器维护的信任商店）。验证一张服务器证书时：服务器证书 ← 中间 CA 签名 ← 根 CA 签名，逐级用上级公钥验下级签名，链到一张你本来就信任的根证书为止（§9.3 实测里 `baidu.com` ← `GlobalSign` 就是两级的链）。

三个日常推论：自签证书（本站教材站正是）不在信任商店里，浏览器只能让你手动豁免：不是加密弱，是**身份**没人背书；「证书过期」报错拦的是有效期（§9.3 的 `notAfter` 字段），与加密强度无关；证书透明度日志（CT）与 DNS CAA 记录是给 CA 乱签证书上锁的补救。信任链的弱点从来在「签发」这一环（密码学分册 §8.4 的事故目录）。

命令行验链的工具是 `openssl s_client`（WSL2 采集）：

```text
$ echo | openssl s_client -connect www.baidu.com:443 -servername www.baidu.com
subject = C = CN, O = "Beijing Baidu Netcom...", CN = baidu.com
issuer  = C = BE, O = GlobalSign nv-sa, CN = GlobalSign RSA OV SSL CA 2018
Protocol : TLSv1.2    Cipher : ECDHE-RSA-AES128-GCM-SHA256
```

`subject`（证书主人）与 `issuer`（背书人）两行就是链的第一级；加 `-showcerts` 能看完整链条与各级证书正文。排查「浏览器报证书错误」时，先看这两行：主人名字对不对（域名不匹配？）、背书人是谁（企业根？还是意外撞上的拦截）、有效期（§9.3 的 `notAfter`）。三查之后，报错的原因基本就锁定了。

**本节小结**：信任链是从服务器证书逐级验签到本机预装根的一条签名链；自签证书缺的是背书不是加密，证书报错按「名字、背书人、有效期」三查即可定位。

## $\rm \S \, 9.9$ 本章自测答案

### $\rm \S \, 9.9.1$ 关键概念回顾答案

1. 链路层只护单跳（下一段还原明文）；TLS 护两端进程全程，但信任服务器进程本身；应用层端到端连服务器都不可信，代价是逐应用设计。（§9.1）
2. 机密性（对称加密）、完整性（AEAD/MAC）、身份（证书＋签名）。缺身份＝中间人可各自与两端建立合法加密通道、明文转述，加密完好、对象错了。（§9.2）
3. ECDHE＝密钥交换（临时 DH，前向保密）；RSA＝证书签名算法；AES128＝对称密码；GCM＝AEAD 模式；SHA256＝哈希/伪随机。前两段管握手、后三段管正片。（§9.3）
4. 1.2 要 2 个 RTT，1.3 压到 1 个（实测增量 2.6×→0.8× RTT）；0-RTT 的代价是重放风险，只允许幂等请求。（§9.5）
5. 验的是「服务器证书 ← 中间 CA ← 根 CA」逐级签名构成的链，锚点是本机预装的根。自签证书的加密没问题，问题是身份没有公认背书，浏览器只能把决定权交还用户。（§9.6）

### $\rm \S \, 9.9.2$ 应用与辨析答案

1. 企业把自建根 CA 装进你的信任商店，抓包软件用它签一张「假网站证书」，你的浏览器就认了。TLS 的身份验证锚在本地信任库，谁能写信任库谁就能中间人。边界：这只对装了该根的设备成立；没装的外部用户不受影响。这正是「管理设备」与「BYOD 设备」必须区别对待的原因。（§9.6）
2. 0-RTT 数据可能被录制后原样重发，服务器无法区分「客户端刚发的」与「攻击者重放的」；重复扣款恰是非幂等操作。修复：该接口禁用 0-RTT（或应用层加一次性 nonce/幂等键），让重放的数据被业务层拒绝。（§9.5）
3. 看场景：对外公开 API，TLS 已提供传输级机密/完整/双向端点认证，应用签名多数场景冗余；但两处仍要签名：多方系统里 TLS 只护「一段运输」，网关到内部服务若降级 http，签名护住全程；以及需要**不可抵赖**（收货确认这类事后举证）时，TLS 的 MAC 密钥双方共有、无法归责，必须非对称签名。分层决定护送范围，不替代业务语义。（§9.1、§9.2）
