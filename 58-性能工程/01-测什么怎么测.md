# $\rm Chapter \, 1$ 测什么，怎么测

> **本章假设你已经会**
>
> 1. 存储层级是一座从寄存器到内存逐层变慢的金字塔，决定数据离计算单元多远，见《计算机系统结构》§5.1。
> 2. 调度器在几十个就绪进程之间分配时间片，你的程序随时可能被暂停换人，见《操作系统》§3.6。
> 3. 期望与方差是描述「平均多少、抖多大」的最小工具，见《概率论》§2.6。
> 4. 活跃变量分析判定「一个值之后还有没有人读」，没人读的赋值可以删，见《编译原理》§6.3。

性能工程的全册心智模型是一句话：**性能是测出来的假设-验证循环，不是想出来的技巧清单**。这条循环的起点和终点都是测量：起点处，测量告诉你瓶颈在哪；终点处，复测告诉你假设对不对。所以全册第一章不讲任何优化技巧，只讲测量本身。本章干两件事：测什么（延迟、吞吐、资源三张账单），怎么测（让计时数字可信的纪律，以及毁掉数字的五个坑）。然后给两把尺子：Amdahl 与 Gustafson 回答「并行能带来多少加速」，roofline 回答「该往少搬数据还是往榨干算力的方向优化」。本章四个实验全部在 WSL2（Ubuntu 24.04，gcc 13.3，16 逻辑核）上真跑过，脚本与原始输出见本册实验记录 `expPE01/result.txt`，随机种子固定为 20261107，任何人重跑得到同一串数字。下一章起，你手里这些可信的数字才有用武之地。

## $\rm \S \, 1.1$ 性能的三张账单：延迟、吞吐、资源

先定住三个词。延迟（latency）是一个请求从提交到完成经过的墙钟时间（wall-clock time，真实世界的钟走过的时长）；吞吐（throughput）是系统单位时间完成的事件数；资源占用是为此消耗的 CPU、内存、带宽、功耗。三者不是同一维度的数字，也不总是一起变：给单线程服务再加一路并发，吞吐可能翻倍，单请求延迟可能被拉长一截，内存占用直接翻倍。比较前必须固定两件事：说的是哪个指标，量的是谁的哪段动作。

三张账单各有各的用途，缺一张都会误判。只看吞吐，会把「同时接 100 个请求每个等 10 秒」当成好成绩；只看延迟，会忽略服务早就把内存吃光、下一秒就要崩溃；只看资源，会优化一台根本没人抱怨慢的机器。本书后续每一章的实测都会同时报这三张账单里的至少两张。

白话：延迟是「我这单等多久」，吞吐是「全店每小时出多少单」，资源是「为此占了几张桌子和几个厨师」。

> 本节小结：报性能先声明报的是三张账单里的哪一张、量的是谁的哪段动作；只有一个裸数字等于没有口径。

## $\rm \S \, 1.2$ 怎么计时：单调时钟、多轮与最速值

C 里最朴素的计时工具是 `clock_gettime`，Linux/macOS 均可用（Windows 对应 `QueryPerformanceCounter`）：

```c
#include <time.h>

static double now_sec(void) {                 /* 返回当前时刻，单位秒 */
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);     /* 单调时钟：只前进，不回拨 */
    return (double)ts.tv_sec + (double)ts.tv_nsec * 1e-9;
}

/* 用法：t0 = now_sec(); 被测代码; t1 = now_sec(); 差值即耗时 */
```

必须用单调时钟（monotonic clock）而不是墙上时间：后者会被网络对时（NTP）往前调或往回调，两次读数的差可能是负的，时间却真实流逝了。`CLOCK_MONOTONIC` 保证只前进，差的正负才有物理意义。

拿到计时器后，第一条纪律：**同一负载跑多轮，取最速值（minimum）**。理由是一笔不对称账：一次测量得到的时长等于被测工作的真实成本加上噪声贡献，而来自调度抢占、频率波动、中断、缓存的噪声几乎只会把时间加长，不会缩短（你的代码不会因为别人抢了 CPU 反而变快）。既然噪声是单边加项，所有轮次里最快的那一轮就是噪声贡献最小的一轮，它最接近真实成本；平均值则把噪声原样收进来，轮数越多、遇到坏运气越多，均值越偏高。这是 MIT 6.172 课程的口径：对「这段代码本身能跑多快」这个问题，min 是正确的统计量。

这不只是理论。对同一段代码（对 128 MB 的 int 数组求和，访存受限）热身 3 轮后连测 300 轮，实测分布是（`expPE01/result.txt`，exp2）：min 10.80 ms，中位数 13.05 ms，均值 13.16 ms，p90 14.25 ms，p99 15.57 ms，最大 16.65 ms，最大与最速之比 1.54。分布右偏：大多数轮挤在 12～14 ms，右侧拖着一条长尾。如果你只测了一轮，拿到 14.6 ms，你的结论就和拿到 10.8 ms 的另一位差了 35%，而代码一模一样。

min 和分位数（percentile，把实测值从小到大排序后位于某个百分比处的值）各有岗位，不互相取代：

1. **min 回答「这段代码最快能跑多快」**。它是优化的参照值：你改了代码，min 从 10.80 降到 9.9，改进是真的。
2. **中位数与 p99 回答「用户等到的通常是什么、最倒霉时是什么」**。服务上线后的世界里不存在「运气最好的那一轮」，用户永远活在分布里；容量规划和体验保障要看 p99 甚至 p999。

白话：优化看 min，量你的天花板抬高了多少；上线看 p99，量最倒霉的那 1% 用户等到了什么。

> 本节小结：单调钟计时；多轮取最速回答「代码能多快」，分位数回答「用户等到什么」，两个问题用两个统计量。

## $\rm \S \, 1.3$ 坑一：编译器把你测的东西删了

第一坑最阴险：计时器显示 0.000000 s，程序没有任何错。被测代码是对 5 亿个数累加 $i^2$：

```c
uint64_t s = 0;
for (uint64_t i = 0; i < N; i++) {
    s += i * i;                /* 5 亿次乘加 */
}
/* 计时结束，打印 t1 - t0。注意：s 从头到尾没人读 */
```

把这段代码按四种编法各跑 5 轮取最速，实测（exp1）：

| 编法 | 最速耗时 |
| --- | --- |
| `gcc -O0`，结果丢弃 | 1.302 s |
| `gcc -O2`，结果丢弃 | 0.000000 s |
| `gcc -O2`，空汇编屏障钉住结果 | 0.237 s |
| `gcc -O2`，volatile 累加器 | 0.246 s |

0.000000 s 不是机器快到测不出来，是循环整个不存在了。反汇编证实：两次 `clock_gettime` 之间一条循环指令都没有。这是编译器在合法地做它的本职：累加结果 `s` 没有任何可观察的去向，这条赋值「写后无人读」即不活跃，按《编译原理》§6.3 的判据整条删除。本书作者在准备这个实验时还踩到第二形态：把求和包成一个纯函数再在计时区里调用，gcc 把整个计算搬到了两次读时钟之外，计时区里只剩两次系统调用，测出一个不可能的 127 TB/s「带宽」。两形态同根：只要计算结果没有编译器看得见的去向，计算就不必存在。

钉住结果有两个办法：

```c
s += i * i;
__asm__ volatile("" : : "r"(s) : "memory");   /* 空汇编：声明"我使用了 s" */
```

空汇编屏障（barrier）自己什么也不做，但它声明「寄存器里的 s 被我用了，且内存可能被动过」，编译器于是必须把 s 真的算出来。另一个办法是把 s 声明为 volatile，强制每轮迭代读写内存。实测里 volatile 只比屏障慢 4%（0.246 s 对 0.237 s），但这不代表它无害：volatile 禁止向量化、强制访存，你测到的已经是「加了 volatile 的那段代码」而不是原代码，它应当留给出多线程场景（第 5 章再见面），不是基准测试的默认手段。

白话：基准测试和编译器在打同一场仗：你想测「干了多少活」，编译器的职责恰恰是「少干活」。测不出来的时候，先怀疑活儿根本没干。

> 本节小结：结果没有可观察去向，计算就不存在；先用屏障把结果钉进计时区，再谈秒数。

## $\rm \S \, 1.4$ 坑二与坑三：冷缓存与抖动

第二坑：第一次访问的数据不在缓存里。对同一个 4 MB 的 int 数组（能整个装进这台机器的 L3）求和，两种测法各跑 6 轮取最速（exp4）：

| 测法 | 最速耗时 | 折算带宽 |
| --- | --- | --- |
| 连续 6 轮（warm，数组常驻缓存） | 0.22 ms | 19.3 GB/s |
| 每轮前先扫一遍 256 MB 把缓存挤空（cold） | 0.49 ms | 8.6 GB/s |

2.2 倍的差距全部来自「数据在不在缓存」，代码一个字没改。而且 warm 组内部也有台阶：第 1 轮 0.66 ms，之后一路降到 0.22 ms，预热的不只是数据缓存，还有 TLB 与硬件预取器的「手感」。对照实验里那个 128 MB 的数组（远大于 L3）怎么测都得去内存拿数据，最速 12.35 ms、带宽 10.9 GB/s，冷热两法差距就小得多。这里有一条必须养成的习惯：报数字时同时报工作集大小与缓存大小的相对关系，读者才能知道你站在《计算机系统结构》§5.1 那座金字塔的哪一层上。预热纪律相应地是：先空跑几轮再开始计时；如果你的被测对象本来就是「第一次访问」（比如服务的冷启动），那它就是被测行为本身，单独测它，别混进稳态数字里。

第三坑：抖动（jitter，同一段代码各轮次耗时的随机波动）。§1.2 那 300 轮里，同一份代码的耗时从 10.80 ms 漂到 16.65 ms。来源都是环境级噪声：调度器把 CPU 换给别的进程（见《操作系统》§3.6）、CPU 频率迁移、TLB 与页错误、邻居进程抢内存带宽。直方图右偏，p99 比中位数高 19%，长尾正是这些偶发事件的形状。对策是一条组合拳：固定环境（测前关掉无关负载、有条件就绑核），多轮取 min 当参照值，同时报出分布让读者知道 min 离中位数有多远。想用「多测几轮再取平均」来压抖动是方向性错误：平均只会把噪声收进来，压不住它。

白话：缓存像工位桌面，用过的资料摊在桌上，第二轮自然快；但调度器随时可能喊隔壁同事来坐你的工位，哪一轮都可能被拖长，min 就是「整个下午没人来打扰」的那一轮。

> 本节小结：先预热再计时并报工作集大小；抖动靠「固定环境、多轮取 min、报分布」对付，平均压不住噪声。

## $\rm \S \, 1.5$ 坑四与坑五：过拟合基准与统计口径

第四坑：被测方学会了考卷。基准测试（benchmark，为测量而构造的标准化负载）是出给程序和硬件的一份考卷，而缓存预取器、分支预测器、编译器都会「背题」。循环访问 stride 恒为 1 的数组，预取器学会节奏后速度虚高，真实负载的访存杂乱无章时立刻现原形；基准永远喂同一个输入，分支预测器练到近乎全对，换真实数据就跌回去。对策：轮换多种输入形状、保留真实负载的采样片段、对「恰好在这几个测试点上有效的优化」保持怀疑，那不是优化，是背诵。

第五坑：统计口径不严谨，即数字本身没带着能解读它的信息。一份可信的实测报告至少包含：环境（CPU 型号、核数、频率策略、内存与系统版本）、轮数、选用的统计量（min 还是中位数）、分布或至少分位数、复现所需的脚本与种子。缺了这些，「平均快 30%」可能只是 p99 的长尾被裁掉了，与典型路径毫无关系。五个坑合起来是一张排查表：

| 坑 | 典型症状 | 对策 |
| --- | --- | --- |
| 编译器删代码 | 计时为 0 或异常快 | 屏障钉住结果，必要时看汇编 |
| 冷缓存 | 第一轮或冷测慢数倍 | 预热后计时，报工作集与缓存的关系 |
| 抖动 | 单轮波动超过两成 | 固定环境、多轮取 min、报分布 |
| 过拟合基准 | 优化只在基准上灵 | 多形状输入、真实负载片段 |
| 统计不严谨 | 只报一次或只报平均 | 报环境、轮数、统计量、分布与种子 |

白话：五个坑其实是同一句话的五次翻译：你计时器里走过的秒数，并不全部来自你想测的那份工作。

> 本节小结：数字离开「环境＋轮数＋统计量＋分布」这四件行李就不可信；优化只有在换过考卷后仍然成立时才算数。

## $\rm \S \, 1.6$ Amdahl：串行部分是加速比的天花板

测量回答「现在多快」，还差一把尺子回答「最优能多快」，否则你不知道离终点还有多远。第一把尺子来自把程序拆成两段：设总工作量归一化为 1，其中**本质上串行**（谁也替不了谁，按单机时间）的占 $f$，**可以并行**的占 $1-f$，$0 \le f \le 1$。$p$ 个工人瓜分并行段，每人只干它的 $p$ 分之一：

$$
\begin{aligned}
T_p &= f + \frac{1-f}{p} \\
S_p &= \frac{T_1}{T_p} = \frac{1}{f + \dfrac{1-f}{p}}
\end{aligned}
$$

读法：$T_p$ 是 $p$ 台机器跑完全部工作的总时间，串行段 $f$ 一分不减，并行段被摊薄 $p$ 倍；$S_p$ 叫加速比（speedup），分子 $T_1 = f + (1-f) = 1$ 是单机时间，分母是 $p$ 机时间。对 $S_p$ 取 $p \to \infty$ 的极限：

$$
\lim_{p\to\infty} S_p = \frac{1}{f}
$$

读法：并行段被摊到接近零，剩下串行段 $f$ 独自决定底线，加速比再怎么加机器也压不过 $1/f$。$f=0.3$ 时天花板 3.33 倍，给 128 核也只能摸到 3.27 倍。这就是 Amdahl 定律：**先砍串行，再谈加核**。

公式本身可以验证。用模拟把「$p$ 台机器瓜分并行段」这件事真的算出来（exp3，numpy，种子 20261107，每个点重复 200 轮取 min，与真机计时同口径），理想情形下实测与理论逐点相等：

| $p$ | 实测加速比 | Amdahl 理论 | 偏差 |
| --- | --- | --- | --- |
| 2 | 1.538 | 1.538 | +0.00% |
| 8 | 2.581 | 2.581 | +0.00% |
| 32 | 3.107 | 3.107 | +0.00% |
| 128 | 3.274 | 3.274 | +0.00% |

这是精确的账，不是经验拟合。给每个线程加 5% 的随机抖动再跑，最大偏差只有 5.1%（出现在 $p=2$），而且 $p \ge 16$ 后偏差全部转负：并行段要等最慢的那个线程完工（§1.7 会算这笔 max 的账），机器越多，「最倒霉的那个」越倒霉。

白话：十个人装修一套房，刷墙可以一人一间，图纸却只有一张，人人得轮流看。图纸就是 $f$，人再多，看图纸的时间一分不少。

> 本节小结：$S_p = \dfrac{1}{f + (1-f)/p}$，天花板 $1/f$；想加速先砍串行段，加核是并行段的事。

## $\rm \S \, 1.7$ Gustafson：换一个口径，天花板会移动

Amdahl 有个著名推论「并行化不划算」，但它隐含了一个口径选择：**活是固定的**（地图就是这张，跑完就收工）。工程里常见的是另一个口径：机器变多，问题也跟着变大（渲染更高的分辨率、训练更多的轮次、搜索更大的图）。把口径换成「在 $p$ 台机器上实测：串行 $f$、并行 $1-f$，两者之和归一为 1」，这份被扩大了的工作若交给单机做，并行部分要放大 $p$ 倍，单机时间为 $f + p(1-f)$。于是：

$$
\begin{aligned}
S_G &= \frac{f + p(1-f)}{f + (1-f)} = f + p(1-f) = p - f(p-1)
\end{aligned}
$$

读法：分母 $f+(1-f)=1$ 是 $p$ 机实测时间（已经归一），分子是同样这份扩大的活单机的耗时；$S_G$ 就是 Gustafson 加速比。它没有 $1/f$ 的天花板：$f=0.3$、$p=128$ 时 $S_G = 0.3 + 128 \times 0.7 = 89.9$，随 $p$ 线性增长，斜率 $1-f$。

模拟同样能验证它（exp3，5% 抖动，每个点 200 轮取 min）：

| $p$ | 实测加速比 | Gustafson 理论 | 偏差 |
| --- | --- | --- | --- |
| 8 | 5.907 | 5.900 | +0.12% |
| 32 | 21.883 | 22.700 | −3.60% |
| 128 | 85.151 | 89.900 | −5.28% |

偏差的方向值得读：实测系统性低于理论，因为并行段的墙钟时间由最慢线程决定，$p$ 个抖动样本取 max，机器越多离「全员平均」越远；而 $p=1$ 那一行反而高出理论约 12%，那是「200 轮取 min 抓住了运气最好的一轮」，正是 §1.2 里 min 逻辑在模拟中的回声。max 拖后腿、min 抢先跑，两个方向都对得上号，公式才算真被理解了。

两条定律不矛盾，它们回答不同的问题。Amdahl 答「这堆固定的活，加机器值不值」，Gustafson 答「机器多了，敢接多大的活」。拿到任何一个「并行加速 XX 倍」的宣称，第一件事是问清它站在哪个口径上。

白话：Amdahl 问「同样的房子，人多快多少」；Gustafson 问「人多了，敢接多大的楼盘」。两问都有用，但不能混着答。

> 本节小结：$S_G = f + p(1-f)$，无天花板但口径是「规模随机器扩张」；两律是同一块串行石头的两种问法。

## $\rm \S \, 1.8$ roofline：一张图定优化方向

并行给不了加速时，剩下的方向只有两个：少搬数据，或算得更满。判断该往哪边使劲，用算术强度（arithmetic intensity）：

$$
I = \frac{\text{总运算次数}}{\text{总搬运字节数}}
$$

读法：每搬运一个字节，能换来多少次运算，单位 FLOP/字节（FLOP 指一次浮点运算，整数运算同口径折算）。roofline 模型说，一段代码的可达性能被两条资源封顶：

$$
P \le \min(P_{\text{max}},\ I \times B)
$$

读法：$P_{\text{max}}$ 是芯片每秒能完成的运算上限，$B$ 是每秒能搬运的字节上限；强度低时 $I \times B$ 先顶到屋檐，此时芯片的算力单元大面积闲置，这叫访存受限（memory-bound），优化方向是少搬数据；强度高过临界值 $P_{\text{max}}/B$ 后才算力受限（compute-bound），方向才是榨干算力单元。分界点 $P_{\text{max}}/B$ 叫机器平衡点。

本章的两个实验恰好是这根杆子的两个端点。§1.4 的求和循环每 4 字节数据只做 1 次加法，$I = 0.25$ FLOP/字节，远低于任何机器平衡点，所以它被带宽按在地上：实测 10.9 GB/s 的内存带宽决定了它 12.35 ms 的最速值，抠指令毫无用处。§1.3 的 $s \mathrel{+}= i \times i$ 循环的输入 $i$ 全程住在寄存器里，搬运量约等于零，强度视为无穷大，只受算力封顶：实测 5 亿次迭代 0.237 s，约每秒 21 亿次迭代。《42-LLM 从零构建》§6.3 在同一台 CPU 上测过完整的两端：$1024^3$ 矩阵乘跑到 80.2 GFLOPS，逐元素加只有 1.0 GFLOPS，83 倍差距全部来自搬运；GPU 上平衡点更高，这个差距更狠。

roofline 的失效边界要事先声明：它只看算力与带宽两条资源，不看延迟与依赖链，一个线程的访存请求在途时 CPU 在干等，这笔延迟账 roofline 记不到（第 2 章用 pointer chasing 补上）；它给的是上界而不是承诺，实际能不能贴住屋顶取决于实现。用它选优化方向，足够了。

白话：roofline 是屋顶，你的算法是一根杆子：强度不够高，杆子再硬也只能贴着「带宽」那面矮屋檐爬，顶不到「算力」那面高的。

> 本节小结：先算强度再选方向：低于平衡点，省搬运；高于平衡点，才值得抠计算。

## $\rm \S \, 1.9$ 关键概念回顾

1. 为什么「多轮取最速」是对「代码本身速度」的正确统计量？它为什么不能用来回答「用户感知延迟」？
2. 空汇编屏障与 volatile 都能救回被删掉的循环，两者分别向编译器传达了什么？为什么说 volatile 不是基准测试的默认手段？
3. 写出 Amdahl 加速比公式及其极限；$f=0.4$ 时，64 核的理论加速比上限是多少？
4. 同一个 $f=0.3$ 的程序，Amdahl 口径下 128 核只值 3.27 倍，Gustafson 口径下值 89.9 倍。两个数字都不错，差别出在哪？
5. 计算本章求和循环的算术强度，并说明为什么对它做指令级优化没有回报。

## $\rm \S \, 1.10$ 应用与辨析

1. 排障：同事写的基准计时恒为 0.000000 s，程序本身不报错。按顺序列出你的排查步骤，并说明每一步排除的是五个坑里的哪一个。
2. 辨析：某服务中位数延迟 30 ms、p99 为 200 ms，同学的报告写着「平均 45 ms，很快」。这份报告缺了什么？用本章的口径补齐它。
3. 假设-验证循环的完整走一遍：$f=0.1$ 的程序在 16 核上实测加速比 4.2，Amdahl 理论值 6.4。提出两个可测量的假设（各指向不同的坑），并为每个假设设计一次复测。

## $\rm \S \, 1.11$ 本章自测答案

概念回顾答案：

1. 噪声（调度、频率、中断、缓存）几乎只会加时长不会缩短，min 是噪声贡献最小的一轮，最接近真实成本（§1.2）。用户感知是分布的整体，不存在「运气最好的一轮」，用户活在 p99 里（§1.2）。
2. 屏障向编译器声明「这个结果被使用了，内存可能被动过」，计算必须真的发生；volatile 强制每次读写内存并禁取向量化，测的是改过的代码（§1.3）。
3. $S_p = \dfrac{1}{f+(1-f)/p}$，极限 $1/f$；$f=0.4$ 时上限 2.5 倍（§1.6）。
4. Amdahl 固定问题规模，并行段摊薄后串行段 $f$ 成了底线；Gustafson 让规模随机器扩张，单机耗时按 $p$ 倍放大，串行占比被稀释（§1.6、§1.7）。
5. 每 4 字节 1 次加法，$I=0.25$ FLOP/字节，远低于平衡点，访存受限，瓶颈在带宽不在指令（§1.8）。

应用与辨析答案：

1. 顺序：先怀疑编译器删代码（看反汇编、加屏障，坑一）；确认计算真实发生后查预热（是否第一轮、工作集多大，坑二）；再看多轮分布（抖动多大，坑三）；换输入形状复测（是否过拟合，坑四）；最后补齐环境与统计口径（坑五）。全程对应 §1.3 至 §1.5。
2. 缺口径与分布。平均 45 ms 掩盖了双峰：多数人 30 ms，1% 的人 200 ms。应报中位数、p99、样本量与测量时长，并区分负载来源；若 200 ms 集中在特定请求类型，还得按类型拆开（§1.2、§1.5）。
3. 假设一：串行段被低估（$f$ 实际大于 0.1），复测：单独计时段间同步开销，重新标定 $f$；假设二：并行段自身没扩展好（内存带宽饱和或负载不均），复测：换更小的可装入缓存的问题规模，看加速比是否回到理论线；两个假设指向完全不同的修法，这正是「假设-验证」的意义（§1.4、§1.6）。

**你现在能做什么**：拿到任何一个「快了 X%」的宣称，你都能追问环境、轮数、统计量与分布，并亲手用一个空汇编屏障验证被测的计算真的发生了。下一章我们钻进机器内部，回答本章留下的那笔账：为什么求和循环怎么写都只有 10.9 GB/s？答案藏在「延迟」与「带宽」的区别里，也就是内存层级真正的运转方式。
