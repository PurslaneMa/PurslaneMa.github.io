# $\rm Chapter \, 9$ I/O 模型：从阻塞到 epoll

前八章的资源都能「算」，唯独 I/O 要「等」：磁盘寻道毫秒级、网络往返几十毫秒，CPU 在这段时间能跑几百万条指令。程序等 I/O 时线程处于什么状态、一份 CPU 怎么同时看住成百上千个「可能就绪」的连接，这是操作系统与网络服务器交界处的最后一个主题。把本章读完，第 10 章就能用操作系统的眼睛通读全书。

> 2. □ 知道文件描述符是「进程打开的 I/O 资源」的编号（§1.4 与计算机速通 §12.1）；
> 3. □ 用 socket 写过收发（计算机网络分册 §1.6 的回环实验）；

## $\rm \S \, 9.1$ 等 I/O 时，线程在干什么

`recv()` 在数据未到时的行为不是「原地转圈」：内核把线程状态置为睡眠、从 CPU 上撤下、挂到该 socket 的等待队列上（§3.1 的阻塞态）；数据到达时内核唤醒它、重新排队上 CPU。所以**阻塞的代价不是 CPU 空转，是「这一份执行流被冻结」**，单线程程序冻结意味着整个程序对任何其他连接都无响应。要害问题从「等不等」变成：**谁替程序看着一堆 fd、等其中任何一个就绪？**

**本节小结**：阻塞的线程睡在内核等待队列上，不烧 CPU、但整条执行流冻结；本章剩下的篇幅全在回答这一节末尾抛出的问题——怎么让一个执行流同时看住一大堆「可能就绪」的 fd。

## $\rm \S \, 9.2$ 五种 I/O 模型一张表

以「等数据 + 拷数据」两段为坐标（POSIX 传统口径）：

| 模型 | 等数据阶段 | 拷数据阶段 | 一句话 |
| --- | --- | --- | --- |
| 阻塞 I/O | 睡眠等 | 同步拷 | 默认形态；单线程被一个 fd 冻结 |
| 非阻塞 I/O | 忙轮询（EWOULDBLOCK） | 同步拷 | 不冻结但烧 CPU；只适合「顺手看一眼」 |
| I/O 多路复用 | select/poll/epoll 替你等**一批** fd | 同步拷 | 一个线程看住全部连接，就绪再动 |
| 信号驱动 I/O | 内核发 SIGIO 通知 | 同步拷 | 通知粒度糙，少用 |
| 异步 I/O（AIO） | 内核全包 | 内核拷完再通知 | 真异步；Linux 原生 AIO 生态弱，io_uring 在补 |

前四种的共同点：数据搬运仍由用户线程自己做，它们只解决「等」的问题。异步 I/O 连搬都代劳。Python 的 `asyncio` 属于第三种（事件循环 + 多路复用），不是第五种，它把「等」事件化了，搬数据仍是协程恢复后自己做。

**本节小结**：五种模型的坐标是「等数据谁负责、拷数据谁负责」：前四种只改革「等」，第五种连搬都包了；给任何框架定位（比如 asyncio）就用这两栏去查。下一节用实测看「只改革等」能换来什么。

## $\rm \S \, 9.3$ 实验：队头阻塞 vs 就绪驱动

同一到达模式跑两种服务器（WSL2、内核 6.6.87、Python 3.10）：客户端 A 在 ${t=0}$ 连接但 ${t=0.6}$ 才发数据；客户端 B 在 ${t=0.1}$ 连接、${t=0.3}$ 就把数据递到。完整脚本 12 行可复现：

```python
import socket, selectors, threading, time
# 阻塞式：accept A 后 recv(A) 冻结，B 的数据躺在内核缓冲区无人读，直到 0.6s A 发言。
# 多路复用：srv 与全部 conn 注册进 selectors（Linux 上即 epoll），
#          循环 sel.select(timeout=0.5) 只返回就绪 fd，逐个 accept/recv/回显。
# （完整双场景脚本见文末注；此处为主干）
sel = selectors.DefaultSelector()
while served < 2:
    for key, _ in sel.select(timeout=0.5):
        if key.fileobj is srv:
            conn, _ = srv.accept(); conn.setblocking(False)
            sel.register(conn, selectors.EVENT_READ)
        else:
            data = key.fileobj.recv(16)   # 就绪才被叫到，recv 不阻塞
            ...
```

本机实测输出（时间取自脚本内 `perf_counter`）：

```text
── 阻塞式（单线程）──
  t= 0.0s accept A，recv 阻塞中…
  t= 0.6s A 的数据 A 到手（B 的早在 0.3s 就到了，但没人 accept 它）
  t= 0.6s B 的数据 B 这才被读到
── selectors/epoll（单线程）──
  t= 0.3s 服务到 B
  t= 0.6s 服务到 A
```

读数有三条。第一，阻塞式里 B 的数据 0.3 秒就到了，却排队到 0.6 秒，**队头阻塞（head-of-line blocking）**：排在前面的 A 冻结了整条服务线，B 的延迟与自己的行为无关。第二，epoll 版同一个线程、按「谁就绪服务谁」：B 在 0.3 秒当场完成。单线程没有变快，变的是**等待的组织方式**。第三，A 在两种版本里都在 0.6 秒被服务：多路复用不会让任何一个连接更快，它只保证「谁也不堵谁」，慢客户端的代价由它自己承担，不再外溢给别人。

> 复现要点：客户端线程里用 `sleep` 控制连接与发送时刻（A：0.0 连接、0.6 发送；B：0.1 连接、0.3 发送），两种服务器各跑一轮；阻塞版先 `accept` A 再 `recv`（随后才轮到 B），复用版把 `srv` 与每个新连接都 `sel.register` 进事件循环。日志行由脚本内 `perf_counter` 相对起点打印。
> 两次运行的到达模式完全一致（A：0.0 连接、0.6 发送；B：0.1 连接、0.3 发送），所以时间差全部归因于服务器侧的等待组织方式，而不是客户端行为。
> 阻塞式的那一轮里，`accept` B 的动作发生在 `recv(A)` 返回之后，这正是「队头」二字的现场：B 的处理被排在 A 的后面，哪怕 B 早已就绪。

## $\rm \S \, 9.4$ select、poll、epoll 的账

三者都属「多路复用」，差别在「等一批 fd」的实现。白话：好比等一屋子人举手报到——select/poll 每轮都把全屋花名册重新抄一遍、挨个问「是你就绪吗」，epoll 把花名册挂在内核里只登记一次，每轮直接取已经举手的名单：

1. **select**：每次调用把整个 fd 集合从用户态拷进内核，内核逐个检查，返回后用户再逐个遍历，两次 ${O(n)}$，且 fd 数量有上限（典型 1024）。连接多而活跃少时，绝大多数检查是白做；
2. **poll**：去掉 1024 上限，链表组织，但每次全量拷贝、全量扫描的账没变；
3. **epoll**：把「注册」和「等待」拆开：`epoll_ctl` 注册一次（内核红黑树常驻），`epoll_wait` 只取**就绪链表**。返回的每个 fd 都需要处理，扫描成本 ${O(\text{活跃数})}$ 而非 ${O(\text{总连接数})}$。

三模型对账一张表：

| | select | poll | epoll |
| --- | --- | --- | --- |
| fd 上限 | 1024（FD_SETSIZE） | 无硬上限 | 无硬上限 |
| 注册成本 | 每次调用全量拷入 | 每次调用全量拷入 | `epoll_ctl` 一次，内核常驻 |
| 每轮等待成本 | ${O(	ext{总数})}$ | ${O(	ext{总数})}$ | ${O(	ext{就绪数})}$ |
| 返回后找就绪 | 逐个遍历位图 | 逐个遍历结构体 | 就绪链表直接给出 |
| 跨平台 | POSIX 通用 | POSIX 通用 | Linux 专属（BSD/macOS 为 kqueue，Windows 为 IOCP） |

数量级感受：一万个连接、一百个活跃：select 每轮检查一万次，epoll 每轮拿一百个。这就是 C10K 问题（1999 年 Dan Kegel 提出的「万级并发连接怎么撑」）在系统调用层面的答案。epoll 还有 `EPOLLET` 边缘触发与 `EPOLLLT` 水平触发之分：前者只在状态翻转时提醒一次、要求一次把数据读完，后者只要还有数据就反复提醒。Nginx 用边缘触发配非阻塞 fd，把「读干净」的责任放到应用侧。

多线程版本还有一个经典坑：**惊群（thundering herd）**：多个 worker 线程都阻塞在等待同一个监听 fd 上，连接到来时全员被唤醒、只有一个抢到 `accept`，其余白白折腾一轮上下文切换。解法有二：`EPOLLONESHOT` 让一个事件只唤醒一个 worker；或内核侧直接用 `SO_REUSEPORT` 让每个 worker 各持一个监听 socket、内核做哈希分发，Nginx 1.9+ 两个都用了。

**本节小结**：三者的账差在「每轮等待的成本」：select/poll 每轮全量拷贝加全量扫描（${O(\text{总数})}$），epoll 注册一次常驻内核、每轮只拿就绪链表（${O(\text{就绪数})}$）；在这个差之上再叠 ET/LT 两种通知粒度与惊群治理，就是全部工程细节。

## $\rm \S \, 9.5$ 每连接一线程 vs 事件循环

| | 每连接一线程 | 单线程事件循环（epoll） |
| --- | --- | --- |
| 编程模型 | 顺序阻塞，最好写 | 回调/协程，状态要自己管 |
| 万级连接 | 线程栈内存与切换开销先顶不住 | 一个线程看住全部 |
| 用满多核 | 天然并行 | 一核一个事件循环（Nginx/Redis 的 worker 模型） |
| 适合的负载 | 连接少、单连接计算重 | 连接多、每个连接轻 |

工程地图：Nginx、Redis、Node.js 是事件循环的代表；Go 把 epoll 藏进 runtime 的网络轮询器，让程序员照旧写「阻塞式」代码、阻塞只是 goroutine 让出（§3.6 的视角）；Python asyncio 用协程把回调拍平成顺序代码。多核的标准形态是「每核一个 worker、各跑一个事件循环」，Redis 6.0 的 I/O 线程与 Nginx 的 `worker_processes auto` 都是这个形状：核内事件循环、核间进程分片，惊群问题随之消解。

选型经验回到老问题，即**等待的组织方式**：连接数 × 单连接负载决定线程模型还是事件循环。压测时记住两条公平纪律：客户端与服务器同机回环会把「网络等待」缩成微秒级，量不出真实 I/O 模型差距；对比必须在同一负载形状（连接数、活跃比、请求大小）下做，否则测的是负载差不是模型差（计算机速通 §32 的方法论在这里同样成立）。

> **竞赛生迁移提示**：OJ 里「开满线程池暴力算」管用，是因为那里没有**等待**，人人都在烧 CPU，线程越多核越满越好。真实服务的负载是「一万个人各等你 30 毫秒」，CPU 大部分时间闲着、执行流全冻在等待上。把「加线程」的直觉换成「等 I/O 的占了多少执行流」这一个问题，选型就不会跑偏。

## $\rm \S \, 9.8$ 本章自测答案

### $\rm \S \, 9.8.1$ 关键概念回顾答案

1. 睡眠态：从 CPU 撤下、挂到该 fd 的等待队列，数据到达时被内核唤醒重新排队。真正代价不是 CPU 空转（CPU 让给别人了），而是这份执行流被冻结：单线程程序意味着对所有其他连接无响应。（§9.1）
2. 前四种（阻塞、非阻塞、多路复用、信号驱动），它们只改变「等」的方式，数据从内核缓冲区到用户缓冲区的拷贝都由用户线程触发；异步 I/O 连拷贝都由内核代劳、完成后才通知。（§9.2）
3. 单线程服务线被 A 冻结在 `recv(A)` 上，既不会再 `accept` B，更不会读 B。B 的数据 0.3 秒到达后只能躺在内核缓冲区排队，直到 0.6 秒 A 发言解冻服务线。这是队头阻塞：后面的人被前面的人堵住，与 B 自身无关。（§9.3）
4. select/poll 每轮 ${O(\text{注册总数})}$（全量拷入 + 全量扫描）；epoll 每轮 ${O(\text{就绪数})}$（就绪链表直达）。一万连接一百活跃时是一万对一百的差。（§9.4）
5. 边缘触发只在「无→有」翻转时提醒一次；若不一次读完（read 到 EAGAIN），剩余数据不会再有通知，连接就饿死了。非阻塞 fd 是「读到 EAGAIN」这个终止条件的前提：阻塞 fd 在最后一次 read 不足时会冻结事件循环。（§9.4）

### $\rm \S \, 9.8.2$ 应用与辨析答案

1. 路线一：改事件循环（asyncio/Netty 类），前提是单连接逻辑轻、能接受回调或协程改造；路线二：保留线程模型但限流 + 池化（线程数 = 核数量级，连接排队），前提是真正并行的是计算而非连接数本身。`sys` 高多半在大量线程切换上，两条路线都以「减少执行流数量」为纲。（§9.5）
2. asyncio 是 I/O 多路复用（第三种）上的协程封装：等待由事件循环 + epoll 代办，数据拷贝由恢复后的协程自己做。协程解决的是多路复用编程模型里「回调地狱」的问题：把就绪后的续写拍平成顺序代码，不改变 I/O 模型本身。（§9.2、§9.5）
3. 错误前提：epoll 的「就绪」语义只对 socket/管道这类真会阻塞的对象有意义；普通文件读通常立即可读（页缓存未命中也只是慢，不产生「未就绪」状态），监听常规文件 fd 得不到有效事件，epoll 对其退化为 poll 语义甚至直接不可用。大文件提速的正道是 `readahead`/mmap/`io_uring`，不是 epoll。（§9.4）
