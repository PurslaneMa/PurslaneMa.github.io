## $\rm \S \, 27.1$ SQLite vs PostgreSQL：文件数据库 vs 服务数据库

### $\rm \S \, 27.1.1$ SQLite：零配置但单机

SQLite 不需要安装服务器——它就是一个 C 库，程序编译时链接它。数据库是一个文件（如 `papers.db`），你的程序直接用文件路径打开。

**适合**：移动 App（iOS/Android 都内置 SQLite）、桌面软件（VS Code 用 SQLite 存设置）、单机数据分析、原型开发。

**不适合**：多个进程同时写同一个数据库（SQLite 只支持一个写者）、需要细粒度权限控制、需要通过网络访问。

### $\rm \S \, 27.1.2$ PostgreSQL：独立服务进程

PostgreSQL（通常叫 Postgres）是一个**客户端-服务器数据库管理系统**。它作为后台服务进程运行（和[日常系统管理：软件、用户、服务与日志](../03-计算机系统/13-系统服务日志与软件安装.md)中学过的 systemd 服务是同一个模型），监听某个端口（默认 5432），等待客户端连接。

```bash
# 安装并启动 Postgres
sudo apt install postgresql           # Ubuntu/Debian
sudo systemctl enable --now postgresql  # 开机自启 + 立即启动
systemctl status postgresql           # 确认正在运行
```

### $\rm \S \, 27.1.3$ 什么时候该从 SQLite 迁移到 Postgres

| 情况 | SQLite | Postgres |
|---|---|---|
| 单用户、单机 | ✅ | ✅（重了些） |
| 多人同时写 | ❌（一次一个写者） | ✅ |
| 需要用户权限隔离 | ❌ | ✅ |
| 数据量 > 几百 GB | 可能 | ✅ |
| 生产 Web 应用 | 小流量、单写者可以；并发写与权限控制受限 | ✅ |
| 需要 JSON/全文搜索/地理空间等高级功能 | 有限 | ✅ |

## $\rm \S \, 27.2$ 连接数据库：客户端、驱动与连接字符串

### $\rm \S \, 27.2.1$ 三种连接方式

1. **命令行客户端**：`psql`（Postgres）、`sqlite3`（SQLite）——人在终端中手动执行 SQL。
2. **图形客户端**：**DBeaver**（dbeaver.io，免费开源）、**TablePlus**（tableplus.com，macOS/Windows）、**pgAdmin**（Postgres 官方 Web GUI）、**DataGrip**（JetBrains 出品，付费）。这些让你浏览表结构、可视化查询结果、导出数据。
3. **应用程序**：你的 Python/C++ 代码通过**数据库驱动**连接。

### $\rm \S \, 27.2.2$ 连接字符串

无论哪种方式，连接到数据库都需要一组参数——**连接字符串**把它们编码成一个 URI 格式：

```text
postgresql://alice:<密码>@db.example.com:5432/paperdb
             ↑      ↑              ↑               ↑    ↑
             用户名 密码（不写明文）  主机            端口  数据库名

sqlite:///home/alice/projects/papers.db
         ↑
         本地文件路径（SQLite 不需要用户名密码主机）
```

**密码不能出现在源码中**——用环境变量（回顾[日常系统管理：软件、用户、服务与日志](../03-计算机系统/13-系统服务日志与软件安装.md)中的配置管理）：

```python
import os
DATABASE_URL = os.environ["DATABASE_URL"]  # 从环境变量读取，不在代码中写密码
```

## $\rm \S \, 27.3$ 数据库迁移：让表结构随代码演进

### $\rm \S \, 27.3.1$ 问题

你的第一版 `papers` 表只有 `title`、`year`、`citations`。第二版你想加入 `abstract` 字段和 `doi` 字段。你怎么更新生产数据库中已有的表结构？

手动 `ALTER TABLE papers ADD COLUMN abstract TEXT` 的问题：你的队友不知道你加了这个字段（他们本地的表结构还是旧的）；你不知道这个字段在三个月前是第几次迁移加的；回滚时你不知道怎么撤销。

### $\rm \S \, 27.3.2$ 迁移工具

**迁移**（migration）是“一次对数据库结构的变更，记录在一个带编号的脚本中”：

```sql
-- 001_create_papers.sql
CREATE TABLE papers (id SERIAL PRIMARY KEY, title TEXT, year INT);

-- 002_add_abstract.sql
ALTER TABLE papers ADD COLUMN abstract TEXT;
ALTER TABLE papers ADD COLUMN doi TEXT UNIQUE;

-- 003_add_tags.sql
CREATE TABLE tags (...);
```

迁移脚本按顺序编号，**只向前追加、不修改已经共享的迁移**（还没人执行过的本地草稿可以改；一旦推送，别人可能已经执行过，改它会让各环境的迁移历史分叉）。每个开发者本地跑同样的迁移序列，生产环境也跑同样的序列——数据库结构在各环境中一致的前提，是同一套编号没有被改动过。

Python 生态中 **Alembic**（配合 SQLAlchemy）是最常用迁移工具。Node.js 有 **Knex.js** migrations。Go 有 **golang-migrate**。

## $\rm \S \, 27.4$ 并发写入：MVCC、死锁与丢更新

第 26 章讲过 `BEGIN`/`COMMIT` 和隔离级别表。但“两个事务同时跑会发生什么”在表里只写了现象（脏读、不可重复读），没解释现象从哪来。真实故障——死锁报错、更新丢失、数据库文件越跑越大——都出在这一层。

### $\rm \S \, 27.4.1$ MVCC：读为什么不必等写

回忆第 26 章 §26.5.6 的隔离级别表：如果读操作要等写操作提交才能执行，那么任何隔离级别都会退化成一串串行执行，并发能力无从谈起。数据库要同时做到“读到一致的数据”和“读不阻塞写”，靠的是**多版本并发控制**（Multi-Version Concurrency Control，MVCC）。

它的机制可以用一句话概括：**每一行保留多个版本，事务读的是自己开始时刻的那个版本，而不是“当前最新的值”**。写入时不原地覆盖旧值，而是产生一个新版本；事务拿到的是一份**快照**（snapshot），快照在事务开始（或第一条读语句执行）时确定，之后无论别的事务提交了多少修改，这个事务看到的都还是那份快照。

SQLite 在 WAL（Write-Ahead Logging，预写式日志）模式下也能观察到这个行为——下面的脚本让一个读事务跨越一次写入提交：

```python
import sqlite3, threading, time

conn = sqlite3.connect('mvcc.db')
conn.execute('PRAGMA journal_mode=WAL')          # 打开 WAL：允许读写并发
conn.executescript('CREATE TABLE papers(id INTEGER PRIMARY KEY, citations INT);'
                   'INSERT INTO papers VALUES(1,100);')
conn.commit(); conn.close()

def reader():
    r = sqlite3.connect('mvcc.db', isolation_level=None)
    r.execute('BEGIN')
    v1 = r.execute('SELECT citations FROM papers WHERE id=1').fetchone()[0]
    print(f'  读者在事务开始后读到 citations={v1}')
    time.sleep(1.5)                              # 让写者在中间提交
    v2 = r.execute('SELECT citations FROM papers WHERE id=1').fetchone()[0]
    print(f'  读者在同一事务里再读 citations={v2}  -> 快照没变（可重复读）')
    r.execute('COMMIT'); r.close()

def writer():
    time.sleep(0.4)
    w = sqlite3.connect('mvcc.db', timeout=5, isolation_level=None)
    w.execute('BEGIN IMMEDIATE')
    w.execute('UPDATE papers SET citations=200 WHERE id=1')
    w.commit(); w.close()
    print('  写者在 t=0.4s 提交 citations=200（没有被读者阻塞）')

t1 = threading.Thread(target=reader); t2 = threading.Thread(target=writer)
t1.start(); t2.start(); t1.join(); t2.join()
print('  最终值:', sqlite3.connect('mvcc.db').execute(
    'SELECT citations FROM papers WHERE id=1').fetchone()[0])
```

实测输出：

```text
  读者在事务开始后读到 citations=100
  写者在 t=0.4s 提交 citations=200（没有被读者阻塞）
  读者在同一事务里再读 citations=100  -> 快照没变（可重复读）
  最终值: 200
```

三种现象同时出现，正好是 MVCC 的三条推论。**读不阻塞写**：写者在读者还在事务里时提交成功，没有被等待。**读到的是一致快照**：读者两次读同一行得到 100，尽管数据库里已经是 200——这不是“读到了错误数据”，而是隔离级别承诺的行为，第 26 章表里“不可重复读 = ❌”的 REPEATABLE READ 就是这样实现的。**最终值是新值**：快照只约束读，事务提交后的新事务看到 200。

MVCC 也解释了开发中两个常见疑问。第一个是“为什么我明明在另一个连接里改了数据，这个查询还是旧值”——你大概率处在某个未提交的长事务里，看到的是它的快照，`COMMIT` 或重开连接就会更新。第二个更实际：**为什么长事务会让数据库膨胀**。因为 MVCC 不能立刻删掉旧版本——只要还有一个事务的快照可能需要它，那个版本就必须留着。一个开着不提交的事务会阻止清理，让表文件和索引持续增长（Postgres 里叫“表膨胀”，要靠 `VACUUM` 回收，但它也清不掉仍被快照引用的版本）。

> **经验规则**：应用里的事务要短——只包住真正需要原子性的那几条语句，不要在事务中间做网络请求、等用户输入或跑耗时计算。一个常见事故是“事务里调用第三方 API，对方超时 30 秒”，这 30 秒内数据库不能回收任何版本，高写入表会迅速膨胀。同时要注意：长连接上开着事务忘记提交，比短事务更隐蔽。

### $\rm \S \, 27.4.2$ 死锁：加了锁，然后互相等

有了锁和事务，就必然出现一种局面：事务 A 持有第 1 行的锁、等第 2 行；事务 B 持有第 2 行的锁、等第 1 行。两者都在等对方释放，谁也不会先动——这就是**死锁**（deadlock）。数据库的做法是主动打破僵局：检测到等待环后，杀掉其中一个事务并回滚它，让另一个继续。

用 SQLite 观察一次写入冲突的实际报错。SQLite 一个数据库同时只有一个写者，所以两个事务同时尝试写，后到的那个会失败：

```python
import sqlite3, threading, time

def holder(delay):
    c = sqlite3.connect('papers.db', timeout=0.5)
    c.execute('BEGIN IMMEDIATE')       # 立刻申请写锁
    print('A: BEGIN IMMEDIATE 成功，持有写锁')
    time.sleep(delay)
    c.execute('UPDATE papers SET citations = citations + 1 WHERE id = 1')
    c.commit(); c.close()
    print('A: 提交并释放写锁')

def waiter():
    time.sleep(0.5)                    # 确保 A 已拿到锁
    c = sqlite3.connect('papers.db', timeout=0.5)
    try:
        c.execute('BEGIN IMMEDIATE')   # 抢同一把锁 -> 等 0.5s 后放弃
        print('B: BEGIN IMMEDIATE 成功')
        c.commit()
    except sqlite3.OperationalError as e:
        print(f'B: sqlite3.OperationalError: {e}')
    finally:
        c.close()

t1 = threading.Thread(target=holder, args=(3.0,)); t2 = threading.Thread(target=waiter)
t1.start(); t2.start(); t1.join(); t2.join()
```

前置：当前目录下有一个 `papers.db`，其中 `papers` 表有 `id` 与 `citations` 列（第 26 章实践一的库即可）。实测输出：

```text
A: BEGIN IMMEDIATE 成功，持有写锁
B: sqlite3.OperationalError: database is locked
A: 提交并释放写锁
```

`database is locked` 就是 SQLite 版本的“我拿不到锁”。它在 SQLite 里是**超时后报错**（`timeout=0.5` 表示等 0.5 秒就放弃），而不是像 Postgres 那样报 `deadlock detected`——原因是 SQLite 锁粒度是整库、只有一个写者，构不成环，只是单纯的等待超时。Postgres 允许多个写者分别锁不同行，才可能出现真正的环路，报错文本是：

```text
ERROR:  deadlock detected
DETAIL:  Process 12345 waits for ShareLock on transaction 67890; blocked by process 54321.
HINT:  See server log for query details.
```

Postgres 会自动杀掉其中一个事务（被杀的收到上面这条错误，另一个正常提交）。

应对方式有三条，按优先级排列。**统一加锁顺序**：约定所有代码都按主键升序更新行（比如先更新 `id` 小的论文再更新 `id` 大的），环就不可能形成——这需要真去改代码，不是配置。**缩短事务**：事务越短、持锁时间越短，交集越少。**应用层重试**：把失败的事务当作可重试操作——捕获死锁错误后等一小段随机时间重新执行整个事务。这条必须配随机延迟，否则两个事务会同步重试、再次撞在一起：

```python
import random, time
for attempt in range(5):
    try:
        do_transaction()                   # 整个事务重来，不是重发某一条语句
        break
    except DeadlockError:                  # 各驱动的异常类不同（psycopg 是 errors.DeadlockDetected）
        time.sleep(random.uniform(0, 0.1 * (2 ** attempt)))   # 指数退避 + 随机抖动
```

重试的前提是**事务里没有不可重放的副作用**——如果事务中途已经发过邮件、调过支付接口，重试会让它们执行两次。有副作用时要把副作用移出事务，或配合幂等键（第 29 章 §29.7）。

> **安全提醒**：排查锁问题时不要用“先杀掉可疑连接”这种手段——在 Postgres 里 `pg_terminate_backend` 会直接中断业务事务，可能让应用看到连接错误。正确顺序是先看锁等待关系（Postgres 查 `pg_locks` 与 `pg_stat_activity`），找出持锁最久的那条 `query` 和它的 `state`，再决定是等、是改代码还是提升超时。

### $\rm \S \, 27.4.3$ 丢掉更新：读-改-写之间的空隙

事务解决了“要么全做要么全不做”，但不解决另一个问题：两个事务各自**读**到了同一个旧值，然后各自**写**回自己的新值，后写的那个覆盖前一个——前一次更新就消失了。这叫**丢掉更新**（lost update）。

反例用两个线程模拟两个请求同时给同一篇论文的引用数 +1：

```python
import sqlite3, threading, time

def naive(name):
    c = sqlite3.connect('lost.db', timeout=5)
    v = c.execute('SELECT citations FROM papers WHERE id=1').fetchone()[0]  # 读
    time.sleep(0.3)                                                        # 模拟处理耗时
    c.execute('UPDATE papers SET citations=? WHERE id=1', (v + 1,))        # 用旧值写回
    c.commit(); c.close()
    print(f'  {name} 读到的 citations={v}，写回 {v+1}')

c = sqlite3.connect('lost.db')
c.executescript('CREATE TABLE papers(id INTEGER PRIMARY KEY, citations INT);'
                'INSERT INTO papers VALUES(1,100);')
c.commit(); c.close()
ts = [threading.Thread(target=naive, args=(n,)) for n in ('A', 'B')]
for t in ts: t.start()
for t in ts: t.join()
print('  最终 citations =', sqlite3.connect('lost.db').execute(
    'SELECT citations FROM papers WHERE id=1').fetchone()[0], '（期望 102，实际丢了 1 次更新）')
```

实测输出：

```text
  B 读到的 citations=100，写回 101
  A 读到的 citations=100，写回 101
  最终 citations = 101 （期望 102，实际丢了 1 次更新）
```

两个请求都读到 100、都写回 101，两次自增变成一次。注意这里用的 `citations = ?` 是**基于读到的值**计算新值，空隙就出在“读”和“写”之间——填掉空隙有两种思路。

**悲观锁**（pessimistic locking）：在读到写之间一直持有锁，让别人进不来。Postgres 用 `SELECT ... FOR UPDATE` 明确锁住行，SQLite 用 `BEGIN IMMEDIATE` 事务一开始就取写锁：

```sql
BEGIN IMMEDIATE;                            -- SQLite：立刻取写锁（Postgres 用 BEGIN; 后接 SELECT ... FOR UPDATE）
    SELECT citations FROM papers WHERE id = 1;   -- Postgres 写 FOR UPDATE 时这一行被锁住
    -- 应用层算出 v+1
    UPDATE papers SET citations = ? WHERE id = 1;
COMMIT;
```

把上面反例的读写都包进 `BEGIN IMMEDIATE`，结果就对了（实测）：

```text
  A 读到 100 写回 101
  B 读到 101 写回 102
  最终 citations = 102 (期望 102)
```

第二个事务必须等第一个提交才能读，因此它读到的是 101 而不是 100。代价也直接：**等锁**。热点行的写请求会被串行化，如果事务很长（比如中间调了外部 API），等待时间会累积成超时。

**乐观锁**（optimistic locking）：不预先加锁，而是靠一个**版本号列**在提交时检查“我读到的这行没被人动过”。写法是给表加 `version INT`，更新时把读到的版本号写进 `WHERE`，然后检查影响行数：

```sql
UPDATE papers SET citations = ?, version = version + 1
WHERE id = 1 AND version = ?;    -- 最后一个 ? 是读到的版本号
-- 应用层检查 rowcount：0 表示有人先改了，需要重读重试；1 表示成功
```

实测（两个线程，冲突方自动重试）：

```text
  A 第 1 次尝试成功：102 -> 103 (version 0 -> 1)
  B 第 1 次尝试冲突（version 已变），重读重试
  B 第 2 次尝试成功：103 -> 104 (version 1 -> 2)
```

乐观锁不占锁、不阻塞别人，冲突时由应用层重试——适合冲突概率低的场景（读多写少、按用户各自的数据）。冲突率高时重试会变多，反而不如悲观锁稳定。选择依据是**冲突概率**和**持锁时长**，不是“哪个更先进”：同一行被高频并发修改就用悲观锁，偶尔撞一下就用乐观锁。

> **竞赛生迁移提示**：这两个模型和你熟悉的**CAS**（compare-and-swap，比较并交换）是同一个思想——乐观锁的 `WHERE version = ?` 就是一次数据库层面的 CAS，`rowcount = 0` 等价于 CAS 失败。悲观锁则相当于先取互斥量再操作。区别在于失败后怎么办：CPU 上的 CAS 通常立刻重试，数据库上的冲突重试要退避并考虑重试成本。

## $\rm \S \, 27.5$ 索引进阶：复合索引与覆盖索引

第 26 章讲过单列索引和 `EXPLAIN QUERY PLAN`。真实查询的条件往往不止一列，这时问题变成“该建几个索引、列的先后顺序有没有关系”。

### $\rm \S \, 27.5.1$ 复合索引与最左前缀

**复合索引**（composite index）是在多列上建的一个索引。它的结构决定了它只能被“从左往右”地用——这个性质叫**最左前缀**（leftmost prefix）。

原因是索引的排序方式：`INDEX(tag, year)` 先按 `tag` 排序，`tag` 相同的行内部再按 `year` 排序。这就像一本先按作者姓氏、再按出版年排序的书目——找“某作者的某年出版的书”可以直接翻到位置，找“某作者的所有书”也可以，但找“某年出版的所有书”就没法用这个顺序，因为同一个年份散落在每位作者下面。

在 SQLite 里实测（`papers` 表 5 万行，已建 `CREATE INDEX idx_tag_year ON papers(tag, year)`）：

```python
def plan(sql, params=()):
    return [r[3] for r in c.execute('EXPLAIN QUERY PLAN ' + sql, params)]

plan('SELECT * FROM papers WHERE tag=? AND year=?', ('cnn', 2020))
plan('SELECT * FROM papers WHERE tag=?', ('cnn',))
plan('SELECT * FROM papers WHERE year=?', (2020,))
```

实测输出：

```text
1) WHERE tag=? AND year=?  -> ['SEARCH papers USING INDEX idx_tag_year (tag=? AND year=?)']
2) WHERE tag=?             -> ['SEARCH papers USING INDEX idx_tag_year (tag=?)']
3) WHERE year=?            -> ['SEARCH papers USING INDEX idx_tag_year (ANY(tag) AND year=?)']
```

前两条符合预期：两列都能用上索引，只按 `tag` 也能用（走索引的左前缀 `tag` 部分）。第三条是需要注意的地方——SQLite 的优化器做了一个叫**跳跃扫描**（skip-scan）的动作：`ANY(tag)` 表示它把 `tag` 的每个不同取值都试一遍，在每个取值内部用 `year` 定位。它确实用了这个索引，但代价等于“枚举所有 tag 值”——索引能提供的缩减效果大打折扣（实测中 `tag+year` 的查询约 1.7 ms，只按 `year` 要 10.4 ms，而只按 `tag` 是 28.1 ms，差异来自返回行数不同，关键是两者的执行路径完全不同）。其他数据库不一定做这个优化：MySQL 在无法使用最左前缀时直接就放弃这个索引了。所以**不能依赖跳跃扫描**，正确做法是按查询模式建索引或把列顺序调整为最常用的前缀。

一条实用规则：**把选择性高（不同取值多）的列放在前面，把范围查询的列放在最后**。索引里出现 `>`、`<`、`BETWEEN`、`LIKE 'x%'` 之后，右边的列就用不上索引定位了——`INDEX(tag, year)` 上 `WHERE tag=? AND year>2020` 可用（`year` 在最后一列做范围），但 `INDEX(year, tag)` 上同样的查询只能用到 `year`。实验方法是固定的：写好查询后跑一次 `EXPLAIN QUERY PLAN`，看输出的括号里列出了哪些列，那就是实际用上的部分。

### $\rm \S \, 27.5.2$ 覆盖索引：不回表

普通索引只存索引列，查到匹配的行后要拿着行号回到主表取其它列——这一步叫**回表**（table lookup）。如果查询需要的列恰好都在索引里，数据库就可以完全绕过主表，这个索引叫**覆盖索引**（covering index）。

SQLite 会在查询计划里明确告诉你它用了覆盖索引（实测）：

```text
SELECT id,tag,year FROM papers WHERE tag=? AND year=?    -> ['SEARCH papers USING COVERING INDEX idx_tag_year (tag=? AND year=?)']
SELECT tag,year    FROM papers WHERE tag=? AND year=?    -> ['SEARCH papers USING COVERING INDEX idx_tag_year (tag=? AND year=?)']
SELECT tag,year,title FROM papers WHERE tag=? AND year=? AND citations>?  -> ['SEARCH papers USING INDEX idx_tag_year (tag=? AND year=?)']
```

前两条输出里有 `COVERING`——因为 SQLite 的表默认以 `rowid` 为键，普通索引里隐式带着 `rowid`，而这里的 `id` 就是 `rowid`，所以 `id, tag, year` 全都囊括在索引内。第三条没有 `COVERING`：`title` 不在索引里，必须回表。

代价上，回表确实更贵（实测覆盖索引查询约 0.78 ms，回表的约 1.16 ms，数据在内存缓存中），但更要紧的是它的**放大效应**：回表是逐行随机访问主表，当结果行数很多或数据不在缓存里时，代价会大幅上升。

建立覆盖索引的做法是把查询里 `SELECT`（以及 `WHERE`/`ORDER BY`）用到的列都放进 `INCLUDE` 部分（Postgres 语法）或直接放进列列表（SQLite/MySQL 的写法）：

```sql
-- Postgres：索引列用于查找，INCLUDE 里的是"搭便车"的列，不参与排序但可直接读取
CREATE INDEX idx_papers_tag_year ON papers(tag, year) INCLUDE (title);
```

覆盖索引的代价是索引本身更大、写入时要维护更多内容。它不是“更高级的索引”，只是在“某条固定查询被调用得足够频繁、且它需要的列很少”时才划算。判断方式仍然是看执行计划里有没有出现覆盖的标记，以及测量真实耗时——不要凭感觉加宽索引。

## $\rm \S \, 27.6$ 分页：`OFFSET` 与游标

列表接口几乎都要分页。最直观的写法是 `LIMIT ? OFFSET ?`，但它在**深分页**（翻到很后面）时表现很差，而且会漏数据。这条在 §27.5 的索引讨论之后看会更清楚，因为原因和索引直接相关。

### $\rm \S \, 27.6.1$ `OFFSET` 的两个问题

**代价问题**：`OFFSET 10000` 不是“跳到第 10000 行”，而是“先取出符合条件的前 10000 行，再把它们丢掉，然后取接下来的行”。工作量随 `OFFSET` 线性增长——第 1 页和第 500 页的开销差了 500 倍。在 SQLite 上实测：

```text
OFFSET 0      : 0.292 ms
OFFSET 1000   : 0.274 ms
OFFSET 10000  : 0.549 ms
OFFSET 49000  : 1.048 ms
```

在几万行的小表上差别还只是毫秒级，但这段代价是 $\mathcal{O}(\text{offset})$ 的——数据涨到千万行时，越往后翻越慢，而“翻到最后一页”恰恰是最容易超时的请求。

**正确性问题**：`OFFSET` 分页假设“两次查询之间数据没有变化”。若你在第 1 页和第 2 页之间有人**删除**了一行（在你已看过的部分），第 2 页会整体前移一格，有一行你永远看不到；若有人**插入**了新行，第 2 页会重复上一页末尾的行。这叫**翻页漂移**——它不是并发 bug，而是分页方式本身的缺陷：`OFFSET` 表达的是“跳过前 N 行”，而不是“接着上次的位置”。

### $\rm \S \, 27.6.2$ 游标分页：记住位置而不是数数

**游标分页**（cursor pagination，也叫 keyset pagination）换一个思路：不数“跳过多少行”，而是记住**上一页最后一行的排序键值**，下一页从这个值之后继续取。

```sql
-- 第 1 页
SELECT id, title FROM papers ORDER BY id LIMIT 20;
-- 第 2 页：用上一页最后一行的 id 作为游标（这里假设是 20）
SELECT id, title FROM papers WHERE id > 20 ORDER BY id LIMIT 20;
```

这个写法让索引真正发挥作用——`WHERE id > 20 ORDER BY id` 直接在 B-tree 上定位到起点，取 20 行就停。实测代价几乎不随位置变化：

```text
id > 1      : 0.330 ms
id > 30000  : 0.269 ms
id > 49900  : 0.243 ms
```

对比 §27.6.1 里 `OFFSET 49000` 的 1.048 ms（而两个查询返回的行数相同），而且 keyset 的耗时不会随页数增长。

它同时消除了漂移：`id > 20` 是在“当前数据”上定位的，中间插入或删除了别的行也不影响这一页的起止边界——除非被删的正是那条游标行本身，此时用它的 `id` 依然能正确定位（`id > 20` 不依赖第 20 行还存在）。

代价是要接受三个约束。第一，**只能顺序前进**，不能直接跳到第 N 页——所以它适合“加载更多”和无限滚动，不适合“跳转到第 500 页”的界面需求。第二，**排序键必须唯一且稳定**，通常用主键；如果按 `citations DESC` 排，值相同的行顺序不确定，翻页会错乱，需要加主键作为第二排序键（`ORDER BY citations DESC, id DESC`，游标写成两者组合 `WHERE (citations, id) < (?, ?)`）。第三，游标要编码后交给客户端（把排序键值序列化成字符串，如在 URL 里），客户端要把这个不透明字符串原样传回。

> **经验规则**：内部工具、后台管理这类页数少、允许漂移的列表用 `LIMIT/OFFSET` 就够了，代码更简单；给用户翻的公开列表、日志流、消息流这类可能很深且数据持续变化的场景，用游标分页。两者不必二选一——同一个应用里不同接口可以各用各的。

## $\rm \S \, 27.7$ NoSQL：一类问题族，不是一种数据库

“用不用 NoSQL”这个问法本身就有问题——它把一组解决不同问题的数据库当成了一个替代品。**NoSQL**（Not Only SQL）是一组数据模型和查询方式都不同于关系数据库的系统，它们之间差异极大，共同点只是“不用 SQL 作为主要接口”（部分系统后来也提供了 SQL 接口）。

| 类型 | 数据模型 | 它擅长的问题 | 代表 |
|---|---|---|---|
| 键值（key-value） | 键 → 一个值（不透明） | 缓存、会话、计数器——按 key 直接取，不需要复杂查询 | Redis、Memcached |
| 文档（document） | 一组文档（通常是 JSON），字段可嵌套、可变化 | 结构不固定或经常演进的数据、一次读出整块文档 | MongoDB、CouchDB |
| 列族（wide-column） | 行有大量稀疏列，按列族组织 | 海量写入、按时间或分区键扫描（时序、事件） | Cassandra、HBase |
| 图（graph） | 节点 + 边，边是一等公民 | 多跳关系查询（社交关系、推荐路径、权限图） | Neo4j |

每种类型都对应一个关系数据库做起来别扭的场景。文档存储省掉了“先设计 schema 再迁移”的流程，适合字段经常变的内容；图数据库把多跳关系变成一次遍历，而 SQL 里要写多层 `JOIN` 或递归 CTE；键值存储的单键读写延迟低，适合做缓存。

**什么时候不该用 NoSQL**，这才是更需要判断的部分。需要跨多条记录做**事务性修改**（转账、扣库存）时，多数 NoSQL 的多文档事务能力比关系数据库弱或更晚才补齐，而关系数据库的 `BEGIN`/`COMMIT` 直接解决了它。需要**任意组合的临时查询**（产品经理说“帮我按这个条件筛一下”）时，SQL 的 WHERE/JOIN/GROUP BY 组合自由，而 NoSQL 的查询能力往往受限于它预设的访问模式——可能要预先建好每种查询对应的索引，或额外引入一套分析系统。数据**关系复杂且需要一致性约束**（外键、唯一约束）时，关系数据库的约束能替你在数据库层兜住错误（见 §27.8），NoSQL 常把这类正确性责任推回应用代码。

还有一类常见误用是把 NoSQL 当“因为关系数据库太慢”的解决方案。性能问题的来源通常是索引缺失、查询写法或数据量增长后的表设计（§27.5、§27.6 讲的就是这些），换成另一种数据库往往只是把同一个问题换个地方暴露。合理的迁移理由是**数据模型不匹配**——比如字段结构天然是嵌套文档、或访问模式确实是按 key 取整块——而不是“它听起来更快”。

现实中的系统多数是混用的：关系数据库保存需要事务和约束的核心数据，Redis 做缓存和会话，搜索引擎做全文检索，各自负责它擅长的那一类问题。选型问题不是“关系还是 NoSQL”，而是“这份数据要用什么方式被读写”。

## $\rm \S \, 27.8$ 约束该放在哪一层

一个具体问题：注册接口要保证邮箱不重复。你可以在应用层写“先 `SELECT` 查一下有没有，没有就 `INSERT`”。这个写法在**单请求**下工作正常，在并发下不成立。

两个注册请求几乎同时到达时，时序可能是：请求 1 查询“不存在”，请求 2 查询“不存在”，请求 1 插入成功，请求 2 插入成功——数据库里出现了两条相同邮箱。应用层检查读到的状态在它执行的那一刻是对的，但它的结论在插入时已经过期了。这不是“检查写得不对”，而是**“检查后用”这个模式在并发下天然有窗口**（和 §27.4.3 的丢更新是同一个结构）。

修法不是把检查写得更小心，而是把约束放到**数据库**里，让数据库在写入那一刻原子地判断：

```sql
CREATE TABLE users (
    id    INTEGER PRIMARY KEY,
    email TEXT UNIQUE,                                    -- 唯一约束
    year  INT CHECK (year >= 1900 AND year <= 2100)       -- CHECK 约束
);
```

`UNIQUE` 的作用是：插入或更新时若该列已有相同值，语句直接失败并报错（SQLite 报 `UNIQUE constraint failed: users.email`，Postgres 报 `duplicate key value violates unique constraint`）。数据库在同一个事务、同一次写入里完成判断，并发请求中后到的那个必然失败——应用层捕获这个错误，返回“邮箱已注册”即可。这与[后端与 API](29-后端与API.md) §29.7 的幂等键用的是同一个机制：唯一约束让重复写入变成一个可检测的确定结果。

用 SQLite 实测并发下的差别。应用层检查在交错执行时给出错误结论，唯一约束在插入那一刻拦住第二个：

```python
c.execute("INSERT INTO papers VALUES('10.1/x')")     # 请求 1 插入成功
try:
    c.execute("INSERT INTO papers VALUES('10.1/x')")  # 请求 2
except sqlite3.IntegrityError as e:
    print('被数据库拦下:', e)
```

实测输出：

```text
请求 1 执行: SELECT ... WHERE doi=10.1/x  -> 没查到，准备插入
请求 2 执行: SELECT ... WHERE doi=10.1/x  -> 没查到，准备插入
请求 1 执行: INSERT -> 成功
请求 2 执行: INSERT -> 被数据库拦下: UNIQUE constraint failed: papers.doi
最终行数: 1 —— 重复数据没有写进去
```

**CHECK** 约束管的是同一行内的取值合法性：`CHECK (year >= 1900 AND year <= 2100)` 让不可能的值在写入时就被拒绝，而不是等到某天报表算错才发现。实测：

```text
CHECK 拦截: CHECK constraint failed: year >= 1900 AND year <= 2100
```

`CHECK` 和 `UNIQUE` 的关系可以这样理解：两者都是数据库层的**断言**，区别在 `UNIQUE` 是跨行判断（这一列的值在整个表里是否已存在），`CHECK` 是单行判断（这一行的这些列取值是否合法）。它们和 `NOT NULL`、`PRIMARY KEY`、`FOREIGN KEY` 一起构成数据库的完整性约束。

实践上有一条清晰的分工：**能用约束表达的正确性规则就交给数据库**，应用层只负责把数据库的错误翻译成用户能懂的消息。应用层的检查可以作为“快速失败 + 友好提示”保留（先查一次，重复就直接返回 409，省一次写入失败），但**不能作为唯一防线**——真正保证不重复的是那个 `UNIQUE`。反过来，检查里包含业务规则（比如“同一用户 24 小时内最多发 10 篇”）时，约束难以表达，这类就只能留在应用层，并接受它需要额外的并发处理（如事务里加锁）。

## $\rm \S \, 27.9$ 备份与恢复：不是“复制文件就行”

### $\rm \S \, 27.9.1$ SQLite 的简单备份

```bash
# SQLite：.backup 走在线备份 API，写入进行中也能安全完成
sqlite3 papers.db ".backup papers_backup.db"

# 直接复制 .db 文件才必须停写——复制到一半的数据库可能损坏
# 或导出为 SQL 文本
sqlite3 papers.db .dump > backup.sql
```

### $\rm \S \, 27.9.2$ PostgreSQL 的逻辑备份

```bash
# 导出整个数据库为 SQL 文本
pg_dump paperdb > backup.sql

# 导出为自定义格式（可压缩、可并行恢复）
pg_dump -Fc paperdb > backup.dump

# 恢复：先让目标库回到干净状态（plain 格式会重放建表与数据，库里有残留会报主键冲突）
# dropdb 会删除目标库——先确认它就是你要覆盖的那个库
dropdb paperdb && createdb paperdb
psql paperdb < backup.sql

# 自定义格式可以原地清理旧对象后恢复
pg_restore -d paperdb --clean --if-exists backup.dump
```

### $\rm \S \, 27.9.3$ 备份不是“存了就安全”

- **备份需要定期测试恢复**。一个从未被恢复过的备份可能已经是损坏的——你只是不知道而已。
- **开发/测试/生产数据库必须分开**。不要用生产数据做开发测试（脱敏后可以）。
- **备份文件包含所有数据**——备份文件的权限应设为 `600`（只有所有者可读写），不要放在可通过 Web 访问的目录下。

## $\rm \S \, 27.10$ 常见故障排查

### $\rm \S \, 27.10.1$ “连接被拒绝”

```bash
psql -h db.example.com -U alice paperdb
# psql: error: connection to server at "db.example.com", port 5432 failed: Connection refused
```

排查步骤（回顾[域名、HTTPS、代理与排障](../04-网络/24-域名HTTPS代理与排障.md)中的分层排障框架）：
1. Postgres 服务是否在运行？`systemctl status postgresql`
2. 是否监听正确的端口？`ss -tlnp | grep 5432`
3. 是否只监听了本机？Postgres 默认 `listen_addresses = 'localhost'`（`postgresql.conf`），只接受本机连接。要让外部连上，需要同时改两处：在 `postgresql.conf` 中放开监听地址，并在 `pg_hba.conf` 中为来源网段配置认证规则；改完 `sudo systemctl reload postgresql` 生效。
4. 防火墙是否拦截？`sudo ufw status`

### $\rm \S \, 27.10.2$ “权限不足”

```bash
# psql: error: FATAL: role "alice" does not exist
```

Postgres 的用户系统和操作系统用户是分开的。创建 Postgres 用户（口令不要写进脚本或命令历史——先建角色，再用 `psql` 的 `\password` 交互输入，它不回显、只发送加密后的口令）：

```sql
CREATE USER alice;                              -- 只建角色，不设明文口令
\password alice                                 -- 提示两次输入，不回显
GRANT CONNECT ON DATABASE paperdb TO alice;     -- 按需授权；这里演示最小的一步
GRANT SELECT ON ALL TABLES IN SCHEMA public TO alice;   -- 只读场景：只给 SELECT
```

需要更多权限时再逐项 `GRANT`（`INSERT`/`UPDATE` 等），不要图省事直接给超级用户。相关配置与 Secret 管理见[日常系统管理：软件、用户、服务与日志](../03-计算机系统/13-系统服务日志与软件安装.md)。

### $\rm \S \, 27.10.3$ “表不存在”

可能的原因：连接到了错误的数据库（`\c paperdb` 切换数据库）；表名拼写错误（Postgres 把未加引号的表名转为小写）；或者迁移脚本还没执行。

## $\rm \S \, 27.11$ 动手实践

前三个实践都在 WSL/Ubuntu（有 `sudo` 与 `systemctl`）里做；Windows 原生环境请用 Postgres 官网安装器，把 `systemctl` 换成第 13 章 §13.1.4 的 Windows 服务命令。动手前确认两件事：`psql --version` 有输出、`sudo systemctl status postgresql` 显示 `active (running)`。实践四、五只用 Python 标准库的 `sqlite3`，任何平台都能做，只需要一个新建的空目录。

### $\rm \S \, 27.11.1$ 实践一：从 SQLite 迁移到 Postgres

前置：第 26 章实践留下的 `papers.db`（`sqlite3 papers.db ".tables"` 能看到 `papers`）；Python 环境里装好驱动 `pip install "psycopg[binary]"`（第 9 章 §9.1 的 pip；导入名是 `psycopg`）。

### $\rm \S \, 27.11.2$ 实践二：模拟备份恢复

### $\rm \S \, 27.11.3$ 实践三：排查连接问题

前置：Postgres 正在运行（`systemctl status postgresql` 为 `active`），你知道正确的端口（5432）和一个用户名（如 `alice`）。

1. 用错误端口连接：`psql -h localhost -p 5433 -U alice paperdb`。预期输出：`connection to server at "localhost", port 5433 failed: Connection refused`——在 TCP 层就被拒绝，根本走不到认证。
2. 用不存在的用户名连接：`psql -U nosuchuser paperdb`。预期输出：`FATAL: role "nosuchuser" does not exist`——TCP 通了，是认证层失败。
3. 用[域名、HTTPS、代理与排障](../04-网络/24-域名HTTPS代理与排障.md)中的分层排查框架，从 TCP 层 → 用户认证层分别测试（`ss -tlnp | grep 5432` → `psql`），对照第 1、2 步的报错差异说明问题出在哪一层。
4. 清理：本实践不产生文件；若为测试改过 `pg_hba.conf`，改回并 `sudo systemctl reload postgresql`。

### $\rm \S \, 27.11.4$ 实践四：观察快照、锁冲突与丢更新

前置：Python 3（标准库自带 `sqlite3`，不需要 `sqlite3` 命令行）。在一个新目录中创建练习库：

```python
import sqlite3
c = sqlite3.connect('papers.db')
c.executescript('CREATE TABLE papers(id INTEGER PRIMARY KEY, citations INT);'
                'INSERT INTO papers VALUES(1, 100);')
c.commit(); c.close()
```

1. 运行 §27.4.1 的 MVCC 脚本（把 `mvcc.db` 换成上面建的 `papers.db`，并先 `PRAGMA journal_mode=WAL`）。预期输出：读者在事务内两次读都得到 `100`，写者在同一时间提交成功，最终值为 `200`——快照读与读写并发同时成立。
2. 把同一个脚本里的 `BEGIN` 换成 `BEGIN IMMEDIATE`（读写都加锁），再跑一次。预期输出：读者会**阻塞**到写者提交之后，读取的最终值变成 `200`——这就是悲观锁用等待换一致性的代价。
3. 运行 §27.4.2 的锁冲突脚本（需要 `papers` 表有 `id`、`citations` 两列，上面已建好）。预期输出：`B: sqlite3.OperationalError: database is locked`，而 A 正常提交。把 `timeout=0.5` 调大（如 `5.0`）再跑，预期 B 不再报错而是等待后成功——这说明该错误是“等待超时”而不是“永久失败”。
4. 运行 §27.4.3 的丢更新反例，预期最终 `citations = 101`（而不是 102）；然后把读写包进 `BEGIN IMMEDIATE`，预期变成 `102`；再换成版本号列的乐观锁写法，预期输出里出现一次“冲突（version 已变），重读重试”后成功。
5. 清理：本实践只有本地 `.db` 文件，确认不需要后删除即可。

### $\rm \S \, 27.11.5$ 实践五：用执行计划和计时验证索引与分页

前置：Python 3。灌入一批数据以便观察（5 万行在普通笔记本上只需一两秒）：

```python
import sqlite3, random
c = sqlite3.connect('idx.db')
c.executescript('CREATE TABLE papers(id INTEGER PRIMARY KEY, tag TEXT, year INT, citations INT, title TEXT);')
c.execute('CREATE INDEX idx_tag_year ON papers(tag, year)')     # 复合索引 (tag, year)
random.seed(1)
rows = [(random.choice(['transformer','cnn','rnn','gan','rl']), random.randint(2010, 2025),
         random.randint(0, 5000), 'p%d' % i) for i in range(50000)]
c.executemany('INSERT INTO papers(tag,year,citations,title) VALUES (?,?,?,?)', rows)
c.commit(); c.execute('ANALYZE'); c.commit()
```

1. 对 §27.5.1 的三条查询分别执行 `EXPLAIN QUERY PLAN`。预期输出：`WHERE tag=? AND year=?` 得到 `SEARCH ... USING INDEX idx_tag_year (tag=? AND year=?)`；`WHERE tag=?` 得到 `（tag=?）`；`WHERE year=?` 得到 `（ANY(tag) AND year=?）`——第三条出现 `ANY(...)` 就是跳跃扫描。
2. 对同三条查询计时（各跑 200 次取平均）。预期输出：三者耗时明显不同；对照上一步的计划，说明“用了索引”和“用足了索引”是两件事。
3. 比较覆盖索引：对 `SELECT tag, year FROM papers WHERE tag=? AND year=?` 和 `SELECT tag, year, title FROM papers WHERE tag=? AND year=?` 执行 `EXPLAIN QUERY PLAN`。预期输出：前者含 `COVERING INDEX`，后者只有 `INDEX`（`title` 不在索引里，必须回表）。
4. 比较分页代价：对 `SELECT * FROM papers ORDER BY id LIMIT 20 OFFSET ?` 依次用 `0`、`1000`、`10000`、`49000` 计时，再对 `SELECT * FROM papers WHERE id > ? ORDER BY id LIMIT 20` 用 `1`、`30000`、`49900` 计时。预期输出：前者的耗时随 `OFFSET` 上升，后者几乎不变。
5. 清理：删除 `idx.db`（或在练习库里 `DROP INDEX idx_tag_year`）；确认无其他文件产生。

## $\rm \S \, 27.12$ 总结

- SQLite 是嵌入式文件数据库——零配置、单机、不适合并发写入。Postgres 是客户端-服务器数据库——独立服务进程、多用户、细粒度权限。
- 连接数据库需要驱动（代码层面）和连接字符串（包含主机、端口、用户名、密码、数据库名）。
- 数据库迁移是“按编号顺序管理表结构变更”：只向前追加、不改已共享的脚本。
- 备份必须定期测试恢复。开发/测试/生产数据库必须分离。
- MVCC 让读不阻塞写：每行保留多个版本，事务读自己开始时刻的快照。代价是长事务会阻止旧版本回收，让表持续膨胀。
- 死锁是等待环，数据库会杀掉其中一个事务；应对靠统一加锁顺序、缩短事务、应用层带随机退避的重试。
- 读-改-写之间的空隙会丢更新；悲观锁（`BEGIN IMMEDIATE` / `SELECT ... FOR UPDATE`）靠持锁消除，乐观锁靠版本号列 + 检查影响行数，冲突时重读重试。
- 复合索引只能用最左前缀；覆盖索引让查询所需的列都在索引里，避免回表。都靠 `EXPLAIN QUERY PLAN` 验证。
- `LIMIT/OFFSET` 的代价随页深线性增长还会翻页漂移；游标分页（`WHERE id > ?`）稳定且代价不随位置变化，代价是不能跳页。
- NoSQL 是一组数据模型不同、擅长场景不同的数据库；数据模型不匹配才是迁移理由，不是“听起来更快”。
- 唯一约束与 CHECK 把正确性规则放到数据库层，这是并发下应用层“先查后写”失效后唯一可靠的防线。

## $\rm \S \, 27.15$ 本章自测答案

> 先闭卷作答本章“关键概念回顾”与“应用与辨析”，再核对以下答案。

### $\rm \S \, 27.15.1$ 自测答案 · 关键概念回顾
1. SQLite 是嵌入式文件数据库——程序直接读写 `.db` 文件，无独立服务进程。PostgreSQL 是客户端-服务器数据库——作为 systemd 管理的独立服务进程运行，客户端通过网络连接。连接字符串包含主机、端口、用户名、密码、数据库名；其中密码（以及特定环境下的用户名）不应硬编码在源码里，应从环境变量或密钥管理器读取。
2. 每行保留多个版本，事务读的是自己开始时刻确定的快照，所以读取不需要等待写入提交；同时写者产生新版本而不覆盖旧值，也不需要等待读者。反过来，旧版本只有在没有任何事务的快照可能引用它时才能被回收——一个长期不提交的事务会阻止回收，表与索引因此持续增长（Postgres 需要 `VACUUM`，但也清不掉仍被快照引用的版本）。
3. 因为两个请求都读到同一个旧值、再各自写回，后写的覆盖了前一个（丢掉更新）。悲观锁在“读”和“写”之间一直持有锁（SQLite 用 `BEGIN IMMEDIATE`，Postgres 用 `SELECT ... FOR UPDATE`），让第二个事务必须等第一个提交后才能读；乐观锁不改锁策略，而是给行加版本号，更新时用 `WHERE ... AND version = ?` 并在应用层检查影响行数，为 0 说明有人先改了，重读重试。
4. 列的顺序决定排序方式，索引先按 `tag` 排、相同 `tag` 内再按 `year` 排。`WHERE tag=? AND year=?` 两列都能用于定位；`WHERE tag=?` 能用左前缀 `tag`；`WHERE year=?` 无法用最左前缀（SQLite 会退化成跳跃扫描 `ANY(tag)`，其它数据库可能直接放弃该索引）。覆盖索引省掉的是**回表**：查询所需的列都在索引里时，数据库不必再拿着行号回主表取其它列。
5. 好在两点：代价从 $\mathcal{O}(\text{offset})$ 变成常数（`WHERE id > ?` 直接在索引上定位起点，实测 `id > 49900` 与 `id > 1` 耗时相当，而 `OFFSET 49000` 明显更慢），且不会因为中间行的插入删除而翻页漂移。代价是不能跳到任意页（只能顺序前进）、排序键必须唯一稳定（否则相同排序值的行顺序不定，需要加主键作次级排序键），且游标要对客户端做编码后原样回传。迁移工具解决的是表结构变更的“有序、可溯源、可复现”：所有环境的结构从同一套按编号排列的脚本生成，不会出现“我本地有这个字段但生产没有”。

### $\rm \S \, 27.15.2$ 自测答案 · 应用与辨析
6. Postgres 的用户系统和操作系统用户独立——需要在 Postgres 内部用 `CREATE USER` 创建角色，并 `GRANT` 相应权限。
7. 迁移脚本按编号顺序执行。如果两人各自创建了 `003_xxx.sql`，合并时会冲突——需要手动协调编号，确保所有环境的迁移序列一致。备份必须实际演练，是因为备份文件可能损坏（存储静默损坏）、可能不完整（备份开始时刻未处理完的事务不在其中），恢复流程本身也可能有误——只有真正恢复一次并验证数据可用，才能确认这个备份有效；从未被恢复过的备份不能当作保障。
8. 因为“检查后用”之间存在窗口：两个请求都查到“不存在”，然后都插入成功，检查的结论在插入时已经过期。修法是把规则放进数据库，给邮箱列加 `UNIQUE` 约束，让数据库在写入那一刻原子判断；应用层捕获唯一约束冲突（`IntegrityError` / `duplicate key`）后返回“邮箱已注册”。应用层的预检查可以作为快速失败保留，但不能作为唯一防线。涉及第三方支付时，事务里的副作用不能随事务重试而执行两次——要把支付调用移出事务，或配合幂等键（第 29 章 §29.7），并把失败重试与“响应丢失后的重发”都纳入同一套幂等设计。
