# $\rm Chapter \, 4$ 认证性：MAC 与 AEAD

第 2 章末尾的位翻转攻击留下结论：加密保证「偷看不见」，不保证「没被改」。本章补上第二根柱子，认证性：先看一种连加密都骗不过的攻击（重放），再定义消息认证码与其安全模型，把第 3 章埋的长度扩展坑用 HMAC 填上，然后给出把保密与认证一次做对的 AEAD（AES-GCM），最后是贯穿全册的工程命门：nonce 纪律。

> **开始前自检**：本章假设你已经会：
>
> 1. □ 哈希三性质与长度扩展攻击（本册第 3 章；§4.2 的 HMAC 正是它的解药）；
> 2. □ CTR 模式与密钥流（本册第 2 章；§4.4 的灾难发生在它身上）；
> 3. □ 两密异或的论证：同一密钥流下密文异或等于明文异或（本册第 1 章；§4.4 原样复现）；
> 4. □ CBC 位翻转攻击（本册第 2 章；§4.1 说明它属于哪一档攻击模型）。

## $\rm \S \, 4.1$ 问题：偷看不见，不等于没被改

Bob 收到 Alice 的加密转账指令并成功解密。这一刻他确认了什么？密钥没泄漏、密文没被第 1 章意义上的「破译」。他没确认什么？这段密文是不是 Alice 发的那一条。第 2 章的位翻转攻击里，攻击者改一位 IV 就改了指令的金额位，解密全程毫无异常，保密性对完整性只字未提。

还有更隐蔽的一类：**重放攻击（replay attack）**。指令「向甲付一万元」连同合法密文被攻击者原样复制，在 Alice 发出之后、Bob 处理完之前再发一遍，密文与任何校验都原封不动，账却被扣了两次。篡改是「改内容」，重放是「动时序」。三类攻击与三种需求正好一一对应，这张对应表是全书的骨架：

| 攻击 | 受害的需求 | 对应工具 |
| --- | --- | --- |
| 窃听 | 保密性 | 分组密码＋工作模式（第 2 章） |
| 篡改 | 完整性 | 哈希（第 3 章）→ 本章的 MAC |
| 重放 | 新鲜性 | 序号、时刻、会话绑定（本章 §4.4 起） |

篡改与重放合起来指向同一个缺口：Bob 需要确认「这条消息确实出自 Alice，且内容与时刻都是她认可的」。这个需求叫**认证性（authenticity）**。至于新鲜性的实现，两种朴素做法各有各的坑：序号方案要回答「乱序到达的报文算不算重放」，时间戳方案要回答「双方时钟差半秒算谁错」，第 8 章 TLS 用「每方向独立递增的序号进 AEAD」一次解决，这里先记住问题本身。

## $\rm \S \, 4.2$ MAC：共享密钥盖的章

**消息认证码（message authentication code，MAC）**是对称世界里的答案：双方共享密钥 $k$，发送方计算标签 $t = \text{MAC}_k(m)$ 连同消息发出；接收方用同一密钥重算并比对，一致才收货。两件配套的事一次说清。其一，MAC 不提供保密：标签只是消息的「章」，消息本身该加密还得加密，两者是并行的需求。其二，验证流程里比对要「重算后整串比较」，而新鲜性不在 MAC 的管辖内，重放的报文标签完全合法，所以序号与时刻必须由协议另行绑定（§4.4 与第 8 章都有实例）。

注意钥匙的对称性带来的边界：能验证标签的人恰恰就是能伪造标签的人，共享密钥的一方全体既能「盖章」也能「仿章」，所以 MAC 证明的是「出自共享这把密钥的某一方」，证明不了「出自 Alice 本人」；把认证推广到陌生人可验证，是第 6 章数字签名的任务。

MAC 的安全模型叫 **EUF-CMA（existential unforgeability under chosen-message attack）**：攻击者可以选择任意消息并看到它们的合法标签，然后要求为一条**没问过的**消息伪造标签，做不到才算安全。模型名里的「存在性（existential）」值得停一下：攻击者可以挑**任何一条**新消息来伪造，包括毫无意义的一条，哪怕伪造成功的对象再无价值、概率再低，方案就算破。这与直觉里「伪造有意义的转账指令才算攻击」相反：模型把标准拉到最苛刻，工程上的安全感才不靠「攻击者觉得没意思」。它与第 1 章 CPA 的关系一目了然：选择明文攻击者「能要密文」，EUF-CMA 攻击者「能要标签」，模型难度同步升档。

把哈希和密钥组合成 MAC，第一直觉 $H(k \| m)$ 已在第 3 章翻车（长度扩展）。与第 3 章的对照可以先压缩成一句：哈希验证完整性靠「指纹经可信渠道发布」，MAC 靠「密钥经保密渠道共享」，认证的根基从公开的数学搬到了共享的秘密，正因如此它才能顶住主动替换。标准解是 **HMAC（Hash-based MAC）**：

$$
\text{HMAC}_k(m) = H\big((k \oplus \text{opad}) \,\|\, H((k \oplus \text{ipad}) \| m)\big)
$$

还有一条配密钥的纪律要先立好：**加密与认证用两把独立密钥**。一把密钥服务两个用途，任何一处实现的交互都可能把加密侧的内部状态泄漏给认证侧（反之亦然），两把独立密钥把风险隔开。工程形态是从一把主密钥派生出多把子密钥（密钥派生，第 8 章 TLS 的 HKDF 就是干这个的），本节先记住「一用途一把钥匙」。

HMAC 的标准库实现一行可得（`python`，观察两点：消息改一位、标签全变，雪崩效应；标签截短展示只是习惯，安全长度见 §4.3）：

```python
import hmac, hashlib
k = b"shared-key"                                   # 双方共享的密钥
t1 = hmac.new(k, b"TRANSFER 0100", hashlib.sha256).hexdigest()[:16]
t2 = hmac.new(k, b"TRANSFER 0101", hashlib.sha256).hexdigest()[:16]
print(t1, t2, t1 != t2)                             # ab3c0e458968d1c8 4c36e478e2e8485e True
```

HMAC 的输出长度继承所用的哈希：SHA-256 给出 $256$ 位标签，抗伪造强度即 $2^{256}$ 级，MAC 侧不碰生日界，因为攻击者必须为**指定的新消息**伪造，落回单点逆像而非碰撞。

两个常数 $\text{ipad} = \texttt{0x36}$、$\text{opad} = \texttt{0x5C}$（各重复到块长）的由来正是长度扩展的病根：内层哈希的输出没有被当作链条终点，而是被外层完整地重新哈希了一遍，攻击者拿到最终标签后，外层哈希让他无法从中继续滚动；密钥先与常数异或再进哈希，也避免了「密钥直接拼接在消息前」的暴露面。密钥长度的处理也有约定：比块长长的密钥先哈希压短，比块长短的补零到块长，无论哪种，进入两层哈希的密钥形状都规整一致。读 HMAC 不必背常数，记住结构：内外两层哈希把密钥彻底包住，消息想再挂后缀已无链条可续。

## $\rm \S \, 4.3$ AEAD：一次做对两件事

有了 MAC，理论上可以给任何加密方案手工补认证，但组合顺序有对错之分。**Encrypt-then-MAC（EtM）**：先加密得 $C$，再用独立密钥对 $C$ 算标签 $t$，接收方**先验标签、后解密**。它对的理由：认证层完整覆盖密文，任何篡改在解密发生前就被拒之门外，解密器永远不处理「没过安检」的输入。反过来 **MAC-then-Encrypt** 先认证明文再整体加密，接收方必须先解密才能验签，解密器被迫处理攻击者投喂的伪造密文，TLS 1.0 时代的 Lucky13 攻击就是靠「填充对错」与「MAC 对错」的耗时差异把明文一位一位抠出来的（加密后认证＝先开门再安检，这个词序本身就是漏洞）。

工程上不手工拼装，用**认证加密（authenticated encryption，AE）**原语，带附加数据的版本叫 **AEAD（AE with associated data）**：一个接口同时输出保密与认证。以 GCM 为例的调用形态是：

1. 加密：输入密钥、nonce、明文与附加数据，输出密文与标签 $(C, t)$；
2. 解密：输入同一组参数，**先校验标签**，通过才输出明文，失败则一个字节都不给；
3. 附加数据（如包头）不加密但参与认证，被改了同样过不了校验，因为它「不需要保密」不等于「可以随便改」。

第 8 章会看到 TLS 1.3 把整条握手 transcript 的哈希当附加数据喂给 AEAD，「握手过程本身也被认证了」，这是 AAD 用法的高级形态，此处只留个名字。

本册的主角是 **AES-GCM（Galois/Counter Mode）**：加密层就是第 2 章的 CTR 模式；认证层 GHASH 在 GF$(2^{128})$ 上对密文与附加数据做多项式求值，再与加密层混合出标签。读法层面记住三点：它把保密与认证合成一次校验，错误不再区分「填充错」与「校验错」，位翻转攻击在标签一步全数拦下；标签校验失败时**绝不能**输出任何部分明文；它的安全性完全押在一个前提上，就是下一节。标签可以截短使用，但代价要算清：$t$ 位标签的伪造概率是 $2^{-t}$，截到 $32$ 位意味着伪造四次试一次，敏感场景别省这几字节。组合顺序的对错也并成一表收尾：

| 组合方式 | 验签时机 | 风险 |
| --- | --- | --- |
| Encrypt-then-MAC | 解密前 | 无已知硬伤，现代默认 |
| MAC-then-Encrypt | 解密后 | 解密器直面伪造密文，Lucky13 |
| AEAD（GCM） | 单次校验 | nonce 重用（§4.4） |

表里 AEAD 与 EtM 并非竞争关系：GCM 可以读成把 EtM 制度化进一个原语，加密层与认证层共享参数、校验时序由接口强制，调用者想犯「先解密后验证」的顺序错误都没有入口。HMAC 家族至今仍在 TLS 1.3 的密钥派生与证书校验里服役，AEAD 则接管了记录层。

## $\rm \S \, 4.4$ nonce 纪律：一条约束，全线崩塌或全线安全

GCM 的加密层是 CTR，密钥流由 $(\text{key}, \text{nonce})$ 唯一决定。GCM 的标准 nonce 是 $96$ 位（$12$ 字节）。这个尺寸与「计数器还是随机」强相关：计数器方案天然不重用，随意用满；随机方案则撞上第 3 章的生日界，$96$ 位空间里随机取约 $2^{32}$ 个 nonce，重用概率就过半，所以 NIST 的指引是同一密钥下随机 nonce 只准加密约 $2^{32}$ 条消息，想多加密就得换计数器或换密钥。生日攻击在这里不是理论威胁，是写进标准的配额。

> **竞赛连接**：$2^{32}$ 这个数就是 §3.2 生日表的直接读法，$2^{96}$ 值域、抽 $2^{32}$ 个点、期望碰撞对数 $m(m-1)/2^{n+1} \approx 0.5$；出题人换了个马甲，考的还是抽屉原理。同一密钥下 nonce 重用一次，两条消息共享同一段密钥流，第 1 章的两密论证原样生效：

```python
ks = bytes([0xA3, 0x1F, 0xD0, 0x5C, 0x90, 0xAE, 0x37, 0x62])  # 同 key 同 nonce → 同一段密钥流
m1, m2 = b"PAY 0100", b"PAY 9900"
c1 = bytes(a ^ b for a, b in zip(m1, ks))    # 截获的密文 1，明文已知
c2 = bytes(a ^ b for a, b in zip(m2, ks))    # 截获的密文 2，明文未知
x = bytes(p ^ q for p, q in zip(c1, c2))
print(x.hex())                               # 0000000009080000，即 M1^M2
print(bytes(p ^ q for p, q in zip(x, m1)))   # b'PAY 9900'：明文 2 完整恢复
```

密文异或 `0000000009080000`：前四位金额相同（异或为零），第 $5$ 位差 `09`（`1` 对 `9`）、第 $6$ 位差 `08`（`0` 对 `9`），差异的位置和大小全裸露，用已知的第一段即可完整恢复第二段。更糟的是 GCM 的认证层：nonce 重用还会泄漏 GHASH 内部的认证子密钥，攻击者随后可伪造标签，保密与认证一起阵亡。既然后果是全线的，纪律也得是全线的，写成清单：

1. **来源二选一**：计数器或高质量随机数，写进设计文档，不用「随手想个办法」；
2. **按方向独立**：双向通话各自维护自己的 nonce 序列，避免两侧撞号；
3. **计数器要持久化**：进程重启归零是重用的高发区，计数器落盘或重启即换密钥；
4. **密钥轮换联动**：换密钥时 nonce 空间重新起算，两者同步管理。

清单之外还有半条命门：nonce 靠随机数生成时，随机数本身的熵不足同样致命，「随机」如果出自一个可预测的进程，攻击者直接猜下一发 nonce，纪律形同虚设。生成器的质量与 nonce 的管理是同一条命门的里外两面。

还须与第 2 章的 IV 划清界限：IV 的约束只是「别固定」（固定则重复泄漏），偶尔重复只损失统计形状；nonce 的约束是「同一密钥下绝不重复」，偶尔重复损失的是整条安全性，名字不同，约束强度差一个量级。这条纪律在第 7 章的 ECDSA 重用、第 10 章的 WEP 破案里会以不同面目反复出现。**随机数与计数器的管理是密码工程的命门**：算法再强，救不了一个会重用的 nonce；第 10 章的审计问句「每个一次性量的来源与生命周期是什么」，就是这条纪律的收口形态。

## $\rm \S \, 4.5$ 关键概念回顾

1. 重放攻击篡改的是什么？为什么「密文与校验全部合法」的报文仍是攻击？
2. MAC 的密钥对称性给「认证」划了什么边界？EUF-CMA 模型里攻击者能做什么、不许做什么？
3. HMAC 的双层结构堵住了长度扩展的哪一步？两个填充常数的实际作用是什么？

## $\rm \S \, 4.6$ 应用与辨析

1. 系统用 AES-CBC 加密请求，MAC 用另一把密钥只覆盖明文（MAC-then-Encrypt 变体）。攻击者构造乱填充的密文提交，指出系统反馈的哪类信息构成解密预言机。
2. 团队决定「nonce 用计数器，进程每次重启归零，密钥三个月一换」。指出重用窗口在哪，给出最小修改方案。
3. 对比三句话，指出哪句对、哪句错并改对：甲说「加密了所以没人能改」；乙说「加了 MAC 所以内容出自 Alice 本人」；丙说「GCM 一次校验通过，可同时确认保密与完整」。

## $\rm \S \, 4.7$ 本章自测答案

> 先闭卷作答上面两节，再核对。

### $\rm \S \, 4.7.1$ 关键概念回顾答案

1. 篡改的是时序而非内容：原样重发合法报文，加密与校验全部通过。缺的部件是「新鲜性」，报文要绑定序号、时刻或会话，旧报文作废。（§4.1）
2. 边界：验证者＝伪造者，MAC 只证明「出自共享密钥的某一方」，证明不了具体个人。EUF-CMA：攻击者可任选消息获取合法标签，不许为任何未问过的消息伪造出可通过校验的标签。（§4.2）
3. 内层输出被外层整体重新哈希，链条终点不再是可续滚的中间态；常数把密钥与消息在两层里隔开，密钥不再直接拼接暴露。（§4.2）
4. 先验标签保证解密器只处理过安检的输入，篡改在解密前被拒；MAC-then-Encrypt 必须先解密才能验证，解密器被迫直面伪造密文，处理差异（耗时、报错）泄漏成预言机。（§4.3）
5. 同时破坏保密（密钥流重用，两密论证）与认证（GHASH 认证子密钥泄漏，可伪造标签）。来源两类：计数器或高质量随机数，保证使用周期内不重复。（§4.4）

### $\rm \S \, 4.7.2$ 应用与辨析答案

1. 「填充是否合法」的报错（或耗时差）就是预言机：攻击者逐字节翻转密文块，按报错差异判断解密出的填充是否正确，Lucky13 抠明文用的正是这个差异面。改法：合并成 AEAD 的一次校验，两类错误不可区分。（§4.3）
2. 重用窗口在「计数器归零到密钥更换」之间：重启后 nonce 从零重走，与前一时段重叠。最小修改：计数器持久化到磁盘（重启接着数），或重启即换密钥；两案都保证 $(\text{key}, \text{nonce})$ 二元组不重复。（§4.4）
3. 甲错：加密只给保密，CBC 位翻转可改内容不被察觉。乙错：MAC 的密钥双方共有，只能证明「出自共享密钥的一方」，Alice 自己无法向第三方自证。丙对：AEAD 一次校验同时覆盖保密与完整性（前提是 nonce 不重用）。（§4.1、§4.2、§4.3）
