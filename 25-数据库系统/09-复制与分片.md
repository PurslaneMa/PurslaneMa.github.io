# $\rm Chapter \, 9$ 走向分布式：复制、分片与一致性权衡

单机的账到第 8 章全部结清。但一台机器有天花板：磁盘会满、主机会挂、一个机房会停电。数据库走出单机有两条路：**复制**（同一份数据的多份拷贝）与**分片**（不同数据的多份切片），各自引入新的账：复制要回答「几份拷贝不一致怎么办」，分片要回答「数据按什么切才不歪」。本章用两个可复现的模拟把这些账摆上桌，最后给一致性谱系一张总图。它是第 7 章隔离级别的「跨机房放大版」。

> **开始前自检**：本章假设你已经会：
>
> 1. □ 解释隔离级别在「安全与吞吐」间的取舍（§7.4 的旋钮思想）；
> 2. □ 说明 WAL 日志里记录了「改了什么」（§6.4、§8.3，复制搬的就是它）；
> 3. □ 知道 B+ 树按键有序、范围查询走叶链（§2.4，分片的范围切法依赖它）；
> 4. □ 知道分布式「主从」「容灾」的日常说法（计算机速通 §31.2 部署形态；本章给机制版）。

## $\rm \S \, 9.1$ 复制：同一份数据，几份拷贝

复制的动机是三个愿望：**可用**（一台挂了还有备份）、**读扩容**（读请求分给多台）、**低延迟**（各地读者就近读）。做法的核心是把主库的变更（§8 的 WAL 段落正是现成的变更流）搬到从库重放。主从角色再各推一步就是两种高可用形态：

1. **主从（含故障切换）**：从库平时只读；主库挂了，把某个从库提升为新主（要处理「旧主回来了」的脑裂：旧主的数据比新主旧，还带着旧写）；
2. **多主（multi-master）**：几台都接受写、互相复制。写可用性最高，但两个主同时改同一行时冲突要业务裁决（谁赢？合并？报错？），一致性谱系上只能落在弱端。

```mermaid
flowchart LR
    C[客户端] -->|写| P[(主库)]
    P -->|异步搬 WAL 段| S1[(从库1)]
    P -->|异步搬 WAL 段| S2[(从库2)]
    C -->|读| S1
    C -->|读| S2
```按「主库等多深」分三档：

1. **异步复制**：主库提交即返回，从库后台追。快，但存在**延迟窗口**：窗口内主从不一致；
2. **同步复制**：主库等至少一个从库确认才返回。慢（每次写多一趟跨机往返，计算机网络分册 §7.4 的传播时延是地板），但窗口闭合；
3. **半同步**：等至少一个从库、超时降级异步，是工程折中，MySQL 生态的常用档。

**本节小结**：复制就是把 §8 的 WAL 段落搬去从库重放，换可用、读扩容、低延迟三个愿望；同步深度是主旋钮——异步快但留延迟窗口、同步窗口闭合但每笔写吃跨机往返、半同步是动态折中。

## $\rm \S \, 9.2$ 模拟一：延迟窗口里的超卖

异步复制的代价用线程模拟（复现核心 12 行）：

```python
import threading, time
primary, replica = {'stock': 1}, {'stock': 1}
def replicate_later():
    time.sleep(0.3)                    # 复制延迟 300ms
    replica['stock'] = primary['stock']
threading.Thread(target=replicate_later).start()
primary['stock'] -= 1                  # A 在主库买走最后一件
b_sees = replica['stock'] > 0          # B 的查询被路由到从库
```

本机实测输出：

```text
A 下单后主库 stock=0；B 立即查从库看到有货=True（若 B 也下单→超卖）
0.5s 后从库追平 stock=0。一致了，但窗口内的错已经可能犯下
```

300 毫秒的窗口在真实系统里是毫秒到秒级（跨机房更糟），「读从库省压力」与「读到旧值」是同一枚硬币。三类标准解药，各有代价：

1. **读己之写（read-your-writes）**：写后一小段时间内强制读主库（会话粘主），应用层最常用；
2. **单调读**：同一用户的读固定路由到同一从库，防「时间倒流」（上一秒看到新值、下一秒换到更旧的从库又看到旧值）；
3. **同步/半同步**：把窗口关掉。写延迟直接上一个台阶，且从库跨机房时每笔写都吃 RTT。

选哪副药由业务定：商品展示页读旧半秒无所谓（纯读走从库）；下单链路必须读主（§7.4 的「读-判-写」在这里再罚一次）。

> **与操作系统分册的接口**：延迟窗口的本质是「两本账异步收敛」，与 §8.5 的文件系统日志、§7.4 的库级锁同属「一致性代价」家族，只是尺度从页/库放大到了机房。同理，从库追赶用的正是操作系统分册 §9.5 的「等待组织」思想：主库不等、从库自取，异步化换吞吐。

**本节小结**：延迟窗口里「读从库省压力」与「读到旧值」是同一枚硬币的两面；三副解药各牺牲一样东西——读己之写牺牲写后扩容、单调读牺牲路由自由、同步档牺牲写延迟，按业务丢不丢得起配药。

## $\rm \S \, 9.3$ 分片：不同数据，各归各片

复制的每台机器都有全量数据，写容量没扩。**分片（sharding）**按某个键把行拆到不同机器：哈希分片（键散列取模）打散均匀、范围分片（按键区间）对范围查询友好（§2.4 的叶链在每片内仍成立）。100 万键、16 片的负载模拟（固定种子 2026）：

```text
均匀 key: 最重分片 62903 / 最轻 61687（比值 1.02）    ← 哈希尽职
倾斜 key（80% 流量是同一把 vip key）: 最重 812225 / 最轻 12337（比值 65.8）
```

两条读数讲清分片的两种病：**哈希分片摊得开「均匀的 key」，摊不开「同一把 key」**：`vip:42` 不管怎么散列都落同一片，80% 流量压死一台（热 key 问题，解法在 key 之外：本地缓存、加随机后缀拆子键）；范围分片则怕「时间单调键」：按时间追加的数据永远落在最后一片（写热点），插入类业务因此偏好哈希或「时间取模」预混。

| | 哈希分片 | 范围分片 |
| --- | --- | --- |
| 均匀性 | 好（key 均匀时 1.02 倍差） | 差（时间键全落一片） |
| 范围查询 | 要广播全部片 | 片内叶链直走 |
| 加片 | 取模全变（一致性哈希缓解） | 裂一片即可（邻居借数据） |
| 适用 | KV、点查为主的负载 | 时序、按区间扫描的负载 |

分片还有一张隐形单：**跨片事务**。§6 的原子性在单机靠 WAL 一条日志保证；两个片上的两行要同生共死，就要两阶段提交（2PC）：先问各片「能提交吗」，再下「提交」令，跨机往返 ×2、任一环节挂掉要等超时裁决。工程上因此有一条强烈偏好：**分片键选业务主路径**（订单按 user_id 切，则「单用户下单」永远单片内事务），跨片一致性交给异步补偿。分片数变更的痛同理：取模从 16 改 32 片几乎全部 key 要搬家，一致性哈希（节点加减只动邻居的数据）就是为此发明。

**本节小结**：哈希摊得开均匀 key、摊不开同一把热 key；范围对扫描友好、怕时间单调键写热点；跨片事务要 2PC 两条往返——所以分片键选业务主路径，让事务尽量死在单片内，跨片一致性留给异步补偿。

## $\rm \S \, 9.4$ 一致性谱系：CAP 的精确读法

跨机之后，「一致性」从二值变成光谱（对照 §7.4 的隔离级别：同一个词、两层含义，面试常考的混淆点）：

1. **强一致（线性一致）**：任何读都看到最新写。代价＝同步等待，跨机房 RTT 进每次操作；
2. **读己之写 / 单调读 / 因果一致**：三个逐级放宽的用户级保证（§9.2 的三副药各对应一条），是大多数业务真正的需求层；
3. **最终一致**：停写之后，各份拷贝会收敛到相同值，这是异步复制的底线承诺。**「最终」没有时间上界**，超卖窗口正是它的价。

BASE 是最终一致的另一个名字（Basically Available / Soft state / Eventually consistent），与 ACID（§6.2）对着排。记住它们描述的是**两种合法的工程立场**，不是对错：ACID 押「一致性优先」，BASE 押「可用性优先」，各自适配不同业务。

CAP 在这个谱系里的精确读法：网络**分区（P）**发生时（机房间断网不是如果、是什么时候），你只能在 **C（拒绝部分请求保一致）** 与 **A（继续响应、容忍不一致）** 里挑，不是三选二的选择题，是「P 必然发生时 C 与 A 二选一」的被迫题。实践里没人真做「CA 系统」：单机的 SQLite 倒是天然 CP 无 P（不联网就没有分区），这也是嵌入式与分布式数据库的分水岭。

把两张表放在一起收拢本章的「谱系感」：

| 层 | 旋钮 | 两端 |
| --- | --- | --- |
| 单机隔离（§7） | 隔离级别 | 并发吞吐 ↔ 读异常 |
| 复制（§9.1） | 同步程度 | 写延迟 ↔ 主从窗口 |
| 分片（§9.3） | 分片键/策略 | 点查效率 ↔ 范围查询 |
| 跨机一致（§9.4） | CAP 取舍 | 一致性 ↔ 可用性 |

四行全是同一道题的四个尺寸：**要什么、肯放弃什么**，这是数据库工程的全部决策语法。

## $\rm \S \, 9.7$ 本章自测答案

### $\rm \S \, 9.7.1$ 关键概念回顾答案

1. 可用（容灾）、读扩容（读分摊）、低延迟（就近读）。变更流＝WAL 日志段落（§8 的现成产物），从库重放即可。（§9.1）
2. 异步：快、有延迟窗口；同步：窗口闭合、每次写多一趟跨机往返；半同步：平时同步、从库故障时降级异步，是速度与安全的动态折中。（§9.1）
3. 读己之写牺牲「写后读的扩容」（要粘主库）；单调读牺牲「从库选择的自由」（固定路由）；同步档牺牲写延迟。没有免费药，只有按业务配药。（§9.2）
4. 盲区一：同一把热 key（散列值唯一），解法是缓存或子键拆分；盲区二：改分片数时取模全变（全量搬家），解法是一致性哈希。（§9.3）
5. 分区发生时，C（拒绝请求保一致）与 A（响应但容忍旧值）二选一。CA 需要「无分区」，单机或不联网才成立，分布式系统 P 不可放弃，故 CA 是伪命题；SQLite 是「单机 CP」的特例。（§9.4）

### $\rm \S \, 9.7.2$ 应用与辨析答案

1. bug 一（发帖后看不到自己的帖）＝违反读己之写：写进了主库、读到了旧从库。修复：发帖后的会话窗口内读主库，或客户端本地回显。bug 二（再刷又看到）说明不是丢数据，是异步复制在窗口内追平。这正是「最终一致」的正常行为，用户感知的 bug 其实是路由策略的 bug。（§9.2）
2. 按用户查：哈希定片、片内 B+ 树走索引，一次网络跳转即可。按时间全平台统计：要么广播到 16 片各自聚合再归并（代价：放大 16 倍查询、归并层做二次聚合），要么另建按时间分片的汇总表（代价：双写与同步）。分片键定了之后，「另一个维度的查询」都要付代价。这是分片设计的第一问：按哪个维度查得最多。（§9.3）
3. ① 哪些读可以接受旧值、旧多少（决定读写分离比例与粘主规则）；② 半同步降级到异步的窗口里，业务是否容忍（超卖类不可容忍就要纯同步）；③ 从库故障切换时的提升流程演练过吗（旧主回巢的脑裂问题）。（§9.1、§9.2、§9.4）
