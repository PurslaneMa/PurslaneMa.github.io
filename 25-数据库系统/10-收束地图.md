## $\rm \S \, 10.1$ 选型：三把刻度尺

「用 SQLite 还是 MySQL/PostgreSQL」不是品味题，是三把刻度尺量出来的：

1. **写并发**：SQLite 库级单写（§7.3）：单写者或低频写直接够用；多写者高并发必须行级锁的服务器型；
2. **访问形态**：嵌入式（库即文件、进程内调用、零运维）vs 客户端-服务器（网络连接、独立进程、可远程多端访问）。手机 App、桌面软件、边缘节点是前者的主场；
3. **分布式需求**：要读扩容/容灾/分片（第 9 章的任何一愿）就别让 SQLite 硬上，它的分布式故事不在本册范围。

两张脸对照着记：

| | SQLite | MySQL/PostgreSQL |
| --- | --- | --- |
| 形态 | 库＝一个文件，进程内调用 | 服务进程＋网络连接 |
| 运维 | 零（备份＝拷文件） | 进程、账号、监控、备份策略 |
| 写并发 | 库级单写 | 行级锁、多写者 |
| 类型 | INTEGER/TEXT/…（动态亲和） | 严格模式、丰富类型与扩展 |
| 分布式 | 无（本册不表） | 复制/分片生态成熟 |

一把务实的尺：**先 SQLite，撞到具体刻度再换**。它的上限（单机读并发极高、写串行但每条极快、备份＝拷文件）覆盖了绝大多数应用的整个生命周期；「以后要换」的迁移成本也被 SQL 标准压在可控范围。反向的浪费更常见：起手就上三节点 MySQL 集群，结果三年也没写满一台，§9 的每个机制都是要人盯的，运维复杂度白付。

## $\rm \S \, 10.2$ 连接池：一次排队论的实战

服务器型数据库的每个连接在服务端占内存与 fd（操作系统分册 §9.5 的账），不能无限开；但连接建立要付握手税（计算机网络分册 §7.2 的实测：TCP+鉴权几十毫秒），也不能每请求新建。连接池＝预建 N 条反复复用。池大小的账用模拟跑出来（20 个并发请求、每个占用 50 ms，固定种子；复现核心 8 行）：

```python
pool = queue.Queue()
for _ in range(N): pool.put(1)
def worker():
    t0 = time.perf_counter(); pool.get()          # 等连接
    waits.append((time.perf_counter()-t0)*1000)
    time.sleep(0.05)                              # 模拟查询
    pool.put(1)
```

本机实测：

```text
池= 1: 平均等待 484.0 ms | 最大等待 962.3 ms | 总耗时 1019 ms
池= 4: 平均等待 100.1 ms | 最大等待 200.8 ms | 总耗时  255 ms
池=20: 平均等待   0.0 ms | 最大等待   0.0 ms | 总耗时   55 ms
```

（复现要点：20 个线程同时 `pool.get()`，占用用 `sleep(0.05)` 模拟；等待时间从「发起 get」量到「拿到连接」。）

三条读数就是 sizing 的全部直觉：池太小，请求排队（等待时间≈(并发/池-1)×占用时长）；池够大，等待归零；**再大无益**：20 个连接对 20 个请求总耗时 55 ms（＝单个占用时长），开到 50 条也只是让数据库白扛 30 条空闲连接。> **排队论的影子**：池=1 的 484 ms 平均等待不是巧合：20 个请求串行过一条连接，第 k 个的等待 ≈ ${50(k-1)}$ ms，平均恰是 ${50 	imes 9.5 = 475}$ ms（实测 484，差值是调度杂项）。池=4 时每条连接上排 5 个，平均等待 ${50 	imes 2 = 100}$ ms——与实测 100.1 几乎重合。公式 ${	ext{平均等待} pprox 	ext{占用} 	imes (	ext{每池排队数}-1)/2}$ 给你估算任意池大小的能力，不用每次跑模拟。

经验公式由此而来：先按「单次占用 × 排队上限」估上限，再压到数据库与内存能扛的总量——池 ≈ 并发请求数的上限，再按数据库能扛的总量封顶；「连接池打满」的告警本质是排队（§10.2 的第一行读数），处理方向是加池或缩短单次占用——后者往往更便宜（§5 的索引账）。
还有一个反直觉的读数值得记：池从 1 到 4，总耗时只降了 4 倍（1019→255 ms）；池从 4 到 20，也只降了约 5 倍（255→55 ms）——收益都是线性的，但**等待时间的感受是非线性的**（962 ms 对 200 ms 对 0 ms）：用户体感由「等待」而非「总耗时」决定，这解释了为什么池通常比「够用」多配一两档。

## $\rm \S \, 10.3$ 慢查询治理：一个作战流程

生产上「数据库慢了」的标准作战序列，每步都有本册的章可回：

1. **抓现场**：开慢查询日志（先看有没有现成的，多数事故的 TOP 1 在日志里躺了一周）（如 SQLite 的 `EXPLAIN` 手动、服务器型的 slow log 阈值 1 秒），拿到最贵的 TOP 3 语句，先抓大头，不猜；
2. **读计划**：对每条跑 `EXPLAIN QUERY PLAN`（服务器型的等价命令同构），按 §5.7 三问（SCAN 大表？TEMP B-TREE？驱动顺序？）定位等价律缺失；
3. **配药**：缺索引建索引（§3 的三笔账验收）、语义级浪费改写（§5.5 的深分页类）、统计过期跑 `ANALYZE`（§5.6）；
4. **防复发**：把 EXPLAIN 断言进 CI（计划里不许出现对大表的 SCAN）、给查询上超时、慢日志周报。

第 4 步是「治理」与「救火」的分界：让计划回归可见，比人肉记「上次哪条慢了」可靠得多。

## $\rm \S \, 10.8$ 本章自测答案

### $\rm \S \, 10.8.1$ 关键概念回顾答案

1. 写并发（库级 vs 行级锁）、访问形态（嵌入式 vs 客户端-服务器）、分布式需求。底气：绝大多数应用到不了它的刻度线；边界：多写者高并发与第 9 章的三愿一出现就必须换。（§10.1）
2. 池=1 纯排队（等待≈占用×队列位置）；池=4 接近满载复用（少量排队）；池=20 等待归零、总耗时＝单次占用。打满告警＝排队发生：加池或缩占用时长，先看哪个便宜。（§10.2）
3. 防复发一步（EXPLAIN 断言进 CI、超时、周报）——它把知识从「上次那个人记得」变成「系统记得」。（§10.3）
4. wal 涨：查长事务、清 checkpoint 水位线（§8.4）；机器热：分片热 key 缓存/子键拆分或范围热点预混（§9.3）。（§10.4）
5. 20 个请求串行过 1 条连接，第 ${k}$ 个等待 ${50(k-1)}$ ms，平均 ${50 	imes 9.5 = 475}$ ms——实测 484，差 9 ms 是线程调度与锁竞争的杂项。公式给的量级判断足够选型，精确值才需要模拟。（§10.2）

### $\rm \S \, 10.8.2$ 应用与辨析答案

1. 桌面软件：SQLite——嵌入式零运维、库即文件、单写者无压力（三把尺全部不触线，第 1 章实验里 103 倍的查询差已经说明它不是玩具）。社团网站：SQLite 也够（日 PV 千级、写极稀）——若预期多人并发写管理后台，起步 PostgreSQL 单机也行，但别上集群。秒杀：服务器型＋行级锁或干脆把库存扣减挪进 Redis 原子操作、异步落库——单机 SQLite 的库级锁与单点是刻度尺上第一项就撞死的。（§10.1、§9.2）
2. 发现（慢日志/告警）→ 取 TOP 3（输入：语句；输出：清单）→ 逐条 EXPLAIN（输入：语句；输出：计划）→ 按三问定位（输出：等价律缺失类型）→ 配药（索引/改写/统计）→ 验收（耗时对比）→ 防复发（CI 断言＋超时）。时间轴上每步的产物都是下一步的输入，与操作系统分册 §10.2 的四步定位同构。（§10.3、§10.4）

3. WAL 的 PRAGMA 属于引擎私有语法，迁移时删除——PostgreSQL 自身就是 WAL 架构（§8.5 跨库视角），无需开关；「粘主库」是路由层逻辑、与具体库无关，保留即可，但要在新库上重新验证半同步档位的窗口行为（§9.1 三档的参数名不同）。迁移真正要重算的是这三处依赖引擎细节的账：锁粒度变了（库级→行级，§7.3 的 busy 重试可放宽）、类型亲和变了（动态→严格，数据要清洗）、EXPLAIN 语法变了（CI 断言要重写）。（§7.3、§8.5、§10.3）
