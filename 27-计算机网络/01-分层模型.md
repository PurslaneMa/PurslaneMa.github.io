# $\rm Chapter \, 1$ 分层：两台机器之间的信使系统

本章从一个最小场景出发：两台机器之间没有任何共享记忆，只有一条能传信号的线路，却要「可靠地把字节送过去」。直接动手会撞上四个搅在一起的问题；分层的全部内容就是把它们拆开，拆成五层，每层只回答一类问题，层与层之间靠服务衔接。

> **开始前自检**：本章假设你已经会：
>
> 1. □ IP 地址与端口号怎样定位「某台机器上的某个程序」（计算机速通 §23.1、§23.2）；
> 2. □ 客户端与服务器：先发起连接的是客户端，守在端口旁等连接的是服务器（计算机速通 §23.2）；
> 3. □ 用 curl 发过 HTTP 请求，见过请求行与状态码（计算机速通 §23.3、§23.4）；
> 4. □ 会用 Python 标准库写小脚本：函数、for 循环、元组（计算机速通 §17）。

## $\rm \S \, 1.1$ 问题：一根网线上的四件事

最朴素的方案：A、B 两台机器用一根网线直连，A 把文件变成字节写进线路，B 原样读回。真动手会撞上四个问题，它们同时发生、彼此纠缠：

1. 寻址（addressing）：线路上不止 A、B 两台机器（第三台也插了进来）时，这些字节是发给谁的？机器需要名字；
2. 误码（bit error）：电信号会失真，一位翻转，文件就悄悄损坏，即错误要能被发现，最好还能补救；
3. 快慢不匹配：A 是服务器、B 是旧设备，A 灌得快、B 吃不下，缓冲区迟早溢出，即要有机制管节奏；
4. 共享线路：多台机器共用一条线，同时说话信号会撞在一起，即要有人裁决谁先发。

把这四件事写进同一个发送循环，改其中任何一件都要重读全部逻辑，与竞赛代码把读入、判定、输出全塞进 main 里没法改是同一种痛。分层要拆的正是这团纠缠。

## $\rm \S \, 1.2$ 分层：每层只回答一类问题

**分层（layering）**把「可靠地把字节送过去」拆成一组纵向叠放的层：每层只解决一类问题，并遵守两条纪律。

1. 对上提供服务：给上层一个稳定的接口（interface），上层只管调用，不问内部实现；
2. 对下使用服务：把字节交给下一层去传，不重造下层已有的能力。

两条纪律买到的是「整层可替换」：以太网换成 Wi-Fi，上面的程序一行不改；传输层从 TCP 换成别的协议，应用只需换个接口调用。两台机器的同名层各自对话，靠事先约定的格式与流程，这种约定就是协议（protocol），一对同名层合称对等层。

信使系统类比：作家把写好的信交给出版社，出版社装封交给邮局，邮局装包交给承运人，每一段只认识下一段的交接窗口，收信端对称地一层层拆还。比喻落地就是那两条纪律：交接窗口即接口，事先约定的封皮格式即协议。

**本节小结**：分层＝每层只答一类问题；接口让上层不问实现，协议让对等层说同一种话，两者合起来买到「整层可替换」。

## $\rm \S \, 1.3$ 五层模型：逐层一句话职责

本书采用教科书常用的五层口径（工程讨论里还有更细的 OSI 七层划分，本书不展开）。逐层一句话职责：

| 层 | 一句话职责 | 代表协议 |
| --- | --- | --- |
| 5 应用层 | 把字节变成语义 | HTTP、DNS |
| 4 传输层 | 在两台机器的进程之间建立通道，管顺序与快慢 | TCP、UDP |
| 3 网络层 | 跨过多条链路，把数据从源头送到目的地 | IP |
| 2 链路层 | 在相邻两台机器之间把帧投递到位 | 以太网、Wi-Fi |
| 1 物理层 | 把比特变成电信号、光信号或无线电波 | 网线与射频规范 |

拿这五层回收 §1.1 的四个问题：寻址被网络层认领（IP 地址），误码与共享线路被链路层认领（第 2 章），快慢与「进程到进程」被传输层认领（第 4–7 章）。四个纠缠的问题拆到三层，每层只剩一个主题。

## $\rm \S \, 1.4$ 封装：信纸、信封与邮包

**封装（encapsulation）**是层间交接的具体形态：应用数据下行时，每层在它前面加一段头部（header），写上本层需要的说明；接收端每层只拆自己的头部，把内容上交。类比：信纸（应用数据）套上信封（传输层头部，写「哪个端口收」），装进邮包（网络层头部，写「哪台机器收」），再贴上运单（链路层头尾，写「下一站是谁、校验和多少」），邮局读不到信纸，承运人读不到地址。

用真实尺寸走一遍，一条 100 字节的应用消息：

1. 传输层加 20 字节 TCP 头，变成 120 字节交给网络层；
2. 网络层加 20 字节 IP 头，变成 140 字节交给链路层；
3. 链路层加 18 字节头尾（第 2 章细讲），变成 158 字节的帧，加上 8 字节前导在线上占 166 字节。

应用净荷只剩 ${100/166 \approx 60\%}$。比喻的失效边界：真实信封全程不换，而链路层的运单每一跳都要撕掉重写（第 2、3 章）；「套娃」也不会无限加深，层数固定为五，消息再大也只加厚最外面几层。

## $\rm \S \, 1.5$ 实验：本机回环上的最小 TCP 收发

**回环（loopback）**地址 127.0.0.1 的流量不出网卡，内核在本机内直接递回，不插网线也能走完一次真实的封装链。**套接字（socket）**是传输层递给应用层的接口：§1.2 说的「对上提供服务」，在 Python 里就是它。两端放在同一进程里（回环允许这样做），先连接，再分 3 次发送、只读 1 次。在任意目录保存为 `exp.py`，用 `python exp.py` 运行；端口填 0 表示由内核分配空闲端口，无权限问题：

```python
import socket
lst = socket.socket(); lst.bind(("127.0.0.1", 0)); lst.listen(1)
a = socket.create_connection(lst.getsockname()[:2])    # 一端
b, _ = lst.accept()                                    # 另一端
for chunk in (b"AAAA|", b"BBBB|", b"CCCC|"):           # 发送方分 3 次写
    b.send(chunk)
print(a.recv(64))                                      # 接收方只读一次
a.close(); b.close(); lst.close()
```

本机（Windows 11、Python 3.12）连续多次运行输出一致：

```text
b'AAAA|BBBB|CCCC|'
```

发送方调了 3 次 send，接收方 1 次 recv 就拿到全部 15 个字节。

**本节小结**：回环让完整封装链不出网卡走完一遍；套接字是传输层递给应用的接口——递上来的是字节流，分段的细节全被收走，下一节把这层「收走」钉死。

## $\rm \S \, 1.6$ 读实验：应用层看不见下层

三个观察把「看不见下层」钉死：

1. recv 返回的是「此刻可读的字节」，不是「一次 send 的量」：把 `recv(64)` 改成 `recv(5)`（本机实测），15 个字节按 5 字节一块返回 `b'AAAA|'`、`b'BBBB|'`、`b'CCCC|'`，同一次发送被接收方重新切了三刀；
2. 分段不留痕：把两次写之间隔 0.1 秒、写完再读（本机实测），一次 recv 仍拿到全部 15 字节，send 的次数与边界在字节流里没有载体；
3. 代码里没有任何一行知道这 15 字节走了哪层封装：回环上它没出网卡，换两台真机要过交换机甚至路由器，recv 的调用者无法区分。传输层递上来的只有「字节流到达」这一件事。

这正是 §1.2 两条纪律的另一面：上层不能依赖下层的内部行为（send 怎么分段、路上经过几跳），也因此下层可以整层替换。字节流语义的完整展开在第 4 章。

## $\rm \S \, 1.7$ 分层的代价

分层不是免费的，两笔账摆在明面上。

1. 头部开销：§1.4 的 100 字节消息为约定付了 ${66\%}$ 的税；即便是撑满 1500 字节上限的大消息，线上开销也约有 ${4\%}$。小包高频的应用（DNS、游戏）为此精打细算，这是协议设计的常识约束。
2. 跨层信息丢失：每层只见接口给出的抽象。TCP 重传一段数据时不知道应用层「这是重试请求」；链路层不知道帧里装的是网页还是口令，无法对重要流量优先处理；应用层看不到无线链路正在抖动，只能感到「变慢了」。工程上存在跨层设计（无线协议把信号质量上报给上层调度），但每做一次跨层勾兑，就消耗一分「整层可替换」的自由，这是权衡，不是谁对谁错。

**本节小结**：分层收两笔税——头部开销（100 字节小消息约 ${60\%}$、满载约 ${4\%}$）与跨层信息丢失；税买到的是整层可替换。

后面各章介绍协议时，都会标出它站在这笔权衡的哪一边。

## $\rm \S \, 1.8$ 回到 curl：把调试工具对准层

计算机速通第 23 章用 curl 调试过 HTTP，现在可以按层给那批工具归位：

1. `curl -v` 展示请求行、状态码与头部，应用层视角（计算机速通 §23.4）；
2. `curl -w` 的时间分解中，DNS、TCP、TLS 三段各对应一次跨层交接：查域名是应用层到应用层，建连接是传输层握手，TLS 是叠在传输层上的加密层（第 9 章）；
3. tcpdump 抓到的是链路层的帧（计算机速通 §23.2.7），下一章的主角。

从此排障有了坐标系：`curl -w` 显示建连慢而首字节快，去查传输层与路由，而不是改 HTTP 参数。本章给出「在哪一层」，接下来五章逐层填进「查什么」。

## $\rm \S \, 1.11$ 本章自测答案

> 先闭卷作答 §1.9 与 §1.10，再核对。

### $\rm \S \, 1.11.1$ 关键概念回顾答案

1. 寻址、误码、快慢不匹配、共享线路；网络层认领寻址，链路层认领误码与共享线路，传输层认领快慢与进程到进程。（§1.1、§1.3）
2. 「对上提供服务」排除上层伸手进下层内部改状态；「对下使用服务」排除每层重造寻址、重传这类下层能力，即两条合起来保证整层可替换。（§1.2）
3. 100 → 120（加 TCP 头 20）→ 140（加 IP 头 20）→ 158（加链路层头尾 18）→ 线上 166（加前导 8）；净荷占比 ${100/166 \approx 60\%}$。（§1.4）
4. 由「此刻接收缓冲区可读多少」决定；send 的次数与边界不写进字节流，接收方按自己的节奏读，栈里没有承载边界的字段。（§1.6）
5. 例：链路层知道无线信号变差，传输层不知道，接口只传「帧送达或丢弃」，不传信道质量；强行上报需要专门的跨层接口，破坏可替换性。（§1.7）

### $\rm \S \, 1.11.2$ 应用与辨析答案

1. 收益是整层可替换（以太网换 Wi-Fi 不改应用）；数字是 100 字节消息净荷只占约 ${60\%}$、满 MTU 消息开销约 ${4\%}$，税存在但有限，且换来了上述自由。（§1.4、§1.7）
2. 传输层与应用层可见（TCP 有确认机制，第 5 章）；链路层与网络层不可见，它们只保证本跳与本层交付，「端到端收到」是传输层语义。（§1.3）
3. 「对上提供服务」：物理层与链路层换了实现，接口不变；「对下使用服务」：TCP 只调用链路层服务，不关心底下是谁，即整层替换因此对上层透明。（§1.2）
