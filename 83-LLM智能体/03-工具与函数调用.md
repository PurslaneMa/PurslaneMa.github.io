第 1 章立起循环时，工具协议只有最简形态：一个工具、一个参数、报错回填一层保护；第 2 章管住了上下文的生长。本章回到行动这一拍本身。真系统里工具有几十个、参数有十来个，模型一次把调用写对不再是理所当然；工具本身也会超时失联，而且有些错装不上报警器。本章回答四个问题：怎么把工具说明书写清楚，让模型一次写对（§3.2）；写错了怎么兜底，工具坏了怎么重试（§3.3）；互不依赖的调用怎么一起发（§3.4）；这些约定怎么从一家的私规变成公共标准（§3.5）。

## $\rm \S \, 3.1$ 问题：协议只保证形状，不保证质量

§1.4 的协议有三拍：解析、执行、回填。它保证的是形状：只要模型吐出的文本能解析成一次调用，执行器就跑、观察就回填。拿论文资料管理器的任务对照：「查 2021 到 2024 年引用数超过 500 的论文」，同一个协议下有三种彼此不同的翻车方式。

1. 模型把年份写成字符串 `"2021"` 而不是数字 `2021`。执行器一查类型不对，拒绝执行，报错回填。这是**看得见的失败**：上下文里多了一条报错，下一轮模型有机会改。
2. 模型把起止年份填反了。两个参数都是合法整数，校验无话可说，工具照常执行，返回「命中 0 条」。这是**静默错误**（silent error）：每一步协议都走了，错误却不在任何报错里，反馈通道对它失明。
3. 论文库服务超时。参数全对，错在工具那一侧。这不是模型的问题，但任务照样卡住，而且重试还有讲究，乱重试会把故障中的服务压得更死。

三类失败对应三个新问题：第一类靠报错质量与重试兜底，第二类只能靠事前预防，第三类靠有策略的重试。事前预防的那份「事前材料」就是本章的第一个主角：工具 schema。真系统里调用失败是常态而非意外，《AI工程》§37.5 把重试副作用与预算失控并列为 agent 可靠性的头号坑；本章把这三类失败逐一拆开，各配一件工具。

白话：第 1 章的协议像一条传送带，保证包裹能上去也能下来；但它不保证包裹里装的东西是对的，也不保证传送带自己不断电。

> 本节小结：协议保证形状不保证质量；失败分三类，参数错被拦（可见，可反馈修复）、参数错没被拦（静默，重试失明）、工具侧故障（与模型无关，重试有讲究）；三类的对策分别是报错回填、事前 schema、有策略的重试。

## $\rm \S \, 3.2$ schema 设计：给手的说明书

定义（工具 schema，tool schema）：随提示发给模型的结构化工具说明，写明工具名、每个参数的名字、类型、取值范围，以及哪些参数必填。最常见的载体是 JSON Schema。论文任务的检索工具写成这样：

```json
{
  "name": "search_papers",
  "description": "按关键词检索论文库，返回题录与引用数",
  "parameters": {
    "type": "object",
    "properties": {
      "query":       { "type": "string",  "description": "检索关键词" },
      "year_from":   { "type": "integer", "description": "起始年份（含）" },
      "year_to":     { "type": "integer", "description": "结束年份（含）" },
      "max_results": { "type": "integer", "description": "最多返回条数，默认 10" },
      "field":       { "type": "string",  "enum": ["cs", "math", "physics"] }
    },
    "required": ["query", "year_from", "year_to"]
  }
}
```

`enum` 是枚举（enum）：把取值收拢在一个封闭清单里。这份说明在《软件构造》§3.1 的框架里就是一份合同：`required` 加类型标注是前置条件（调用前必须满足什么），`description` 与返回约定是后置条件（执行后承诺给什么）。真实模型的工具列表每轮请求都随上下文重发（《AI工程》§37.1.2 给了实际 API 格式），所以 schema 不是写一次就完的静态文件，它住在每轮的上下文里，写得又臭又长也在烧 §2.1 那笔词元账。

schema 为什么会影响模型的调用质量？对模型来说 schema 就是上下文里的一段文本，它照着这段文本填参数。参数名叫 `q` 还是叫 `query`，模型猜错槽位的概率不同；文本里没写类型，模型就不知道该发数字还是字符串；没标必填，模型就不知道哪几个不能省。本章实验把伪 LLM 建成一个噪声读取器：三类缺陷信道，各有一个出错率，出错率由 schema 的写法决定。三个信道是：歧义信道（填错槽位）、类型信道（类型发错）、必填信道（漏发参数）。四个变体各自只弄坏一件事：

| 变体 | 相对 V0 改了什么 | 歧义信道 | 类型信道 | 必填信道 |
| :--- | :--- | :--- | :--- | :--- |
| V0 规范 | 无（基线） | 0.02 | 0.04 | 0.02 |
| V1 歧义名 | 参数名换成短名 q / y1 / y2 / n / f | 0.22 | 0.04 | 0.02 |
| V2 无类型 | 删掉全部类型标注 | 0.02 | 0.22 | 0.02 |
| V3 不标必填 | 删掉 required 与可选说明 | 0.02 | 0.04 | 0.18 |

这些出错率是合成标定，不是对真实 LLM 的实测，这和第 1 章 §1.3 的声明同一个精神。歧义信道的事件对半分：一半把 `y1` 与 `y2` 的值换位（类型合法，校验放行，静默错误），一半把 `query` 与 `max_results` 的值换位（类型冲突，被校验拦下）。收到具体报错后，对应信道的出错率打四折，模拟「报错指出了改哪里」的反馈修复。任务：一个任务里对 `search_papers` 发 6 次调用（6 个不同主题的检索意图），轮数预算 8（只有 2 轮富余给重试），每个条件 400 个任务。四个指标：首发通过率（第一次尝试就通过校验的比例）、完成率（8 轮内 6 次调用全部通过校验的任务占比）、正确完成率（参数一个没错的完成）、静默错误率（通过校验但参数有错的调用占比）。

| 变体 | 首发通过率 | 完成率 | 正确完成率 | 静默错误率 | 平均轮数 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| V0 规范 | 93.2% | 99.5% | 95.0% | 0.8% | 6.41 |
| V1 歧义名 | 84.2% | 92.5% | 48.2% | 10.7% | 6.91 |
| V2 无类型 | 75.8% | 78.0% | 74.8% | 0.6% | 7.26 |
| V3 不标必填 | 80.1% | 88.0% | 82.5% | 1.0% | 7.11 |

读这张表分四步。

1. 首发通过率逐级下跌，且能对上解析预测：一次调用被拦的概率是三个信道至少一个出事，V0 为 $1-0.99\times 0.96\times 0.98\approx 6.9\%$，通过率约 93.1%，实测 93.2%；V2 的类型信道抬到 0.22，首发跌到 75.8%。schema 每坏一条信道，每十次调用就多一两次返工。
2. 完成率的差距是轮数税。校验错误可见、报错回填后重试大多能救回，但每救一次烧一轮，预算只有 8 轮：V2 平均 7.26 轮，富余耗尽，完成率掉到 78.0%。V0 平均 6.41 轮，99.5% 完成。schema 差不直接杀死任务，它让任务在预算下窒息。
3. 正确完成率才是判决书。V1 完成率 92.5% 看着能用，正确完成率却腰斩到 48.2%。歧义信道 0.22 的一半是类型合法的年份换位，即每次调用约 11% 概率静默装反，六次独立调用全对的概率是

$$
(1-0.11)^{6}=0.89^{6}\approx 49.7\%
$$

实测 48.2% 略低于预测，差的一截来自少数任务没在预算内跑完。重试对静默错误完全失明：报错永远不出现，反馈通道里没有它的任何信息，模型把「命中 0 条」当成正常结果咽下去。
4. V1 与 V2 的对照是本节的题眼。V2 完成率低（78.0%）但正确率高（74.8%），错误可见，重试兜得住；V1 完成率高（92.5%）但正确率垫底（48.2%），错误不可见。两个变体在两张指标上优劣互换，说明「完成」和「正确」是两个指标，选 schema 时先问一句：我的错误可见吗。

白话：schema 是给装配工的说明书。含糊的说明书有两种坑：零件装不上，看得见，返工就是了；零件装反了机器照样转，直到烧了才发现。后者才要命，而防它的唯一办法是把说明书写清楚，不是事后检修。

> 本节小结：schema 用名字、类型、枚举、必填标注把工具说明写成合同；实测上它一头压首发通过率（93.2% 对 75.8%），一头压静默错误（V1 歧义名让正确完成率腰斩到 48.2%，$0.89^{6}$ 的连乘）；校验拦得住类型错，拦不住语义错，报错回填救得了前者救不了后者。

## $\rm \S \, 3.3$ 错误处理与重试：反馈的第二用途

§1.4 把解析失败的报错回填，让一次格式抖动自愈。现在把这件事推广成完整的错误处理。错误有两个来源，各自有不同的处理路线。

模型侧：参数写错被校验拦下。处理方式是报错回填加重试，而报错的**质量**决定修复速度。V2 的高频报错是「参数 year_from 类型不符，应为 int」：它指名道姓说改哪个参数、改成什么类型，模型照着改就行；如果只回填一句「invalid arguments」，模型只能整个重猜。实验一里，收到具体报错后对应信道的出错率打四折，这个四折就是报错质量的价格。

工具侧：参数全对，工具自己出了故障。失败也分谱系（《分布式系统》§1.2–§1.3 专门讲这件事）：超时、连接断开这类**瞬态故障**（transient failure）过一会儿就好，重试有意义；参数非法、资源不存在这类错误重发一万次也是同样结果，重试纯烧钱。对瞬态故障，重试还有一个容易被忽略的代价：被重试的调用如果已经有副作用，重发就是再执行一遍。定义幂等（idempotency）：同一调用执行多次与执行一次效果相同。查询天然幂等，重试无害；「给这篇论文打标签」不幂等，重试会在标签表里插两行。重试不幂等的调用前，先想想《AI工程》§37.5.2 讲的重复副作用。

对瞬态故障，重试的**时机**有讲究。定义指数退避（exponential backoff）：第 $k$ 次失败后等待 $2^{k-1}$ 个时间片再试，累计等待

$$
\sum_{k=1}^{n}2^{k-1}=2^{n}-1
$$

读法：$n$ 次失败后总共干等了 $2^{n}-1$ 片。为什么要等？瞬态故障常常不是孤立的：服务过载时，这一秒挂、下一秒多半还挂，失败在时间上扎堆，一段失败期像一个故障窗。立即重试的几次尝试全挤在窗内，退避把尝试摊到窗外的概率更大。这听起来像推理，实验二直接量它。

任务：顺序完成 5 次工具调用，每次尝试占 1 个时间片，总预算 40 片，每次调用的尝试上限 6 次，超限或超时即任务失败。两种故障体制：iid 体制下每次尝试独立地以 0.4 的概率失败；bursty 体制模拟一台过载的服务，在正常与故障两态间切换（每片 0.05 概率掉进故障、0.15 概率恢复，故障窗平均约 6.7 片，正常态尝试仍有 0.1 瞬态失败率）。三种策略：不重试、立即重试（下一片就试）、指数退避（等 $2^{k-1}$ 片，封顶 8）。每个组合 1000 次试验。

| 体制 | 策略 | 完成率 | 成功任务平均用时 | 平均尝试次数 |
| :--- | :--- | :--- | :--- | :--- |
| iid | 不重试 | 7.5% | 5.0 片 | 5.0 |
| iid | 立即重试 | 97.6% | 8.2 片 | 8.2 |
| iid | 指数退避 | 97.3% | 10.5 片 | 8.1 |
| bursty | 不重试 | 43.2% | 5.0 片 | 5.0 |
| bursty | 立即重试 | 87.0% | 6.0 片 | 6.0 |
| bursty | 指数退避 | 97.9% | 7.9 片 | 6.3 |

读这张表分三步。

1. iid 体制：重试是雪中送炭，时机无关紧要。不重试完成率 7.5%，与解析预测 $0.6^{5}\approx 7.8\%$ 吻合；两种重试都抬到 97% 上下，与 $(1-0.4^{6})^{5}\approx 98.0\%$ 吻合（6 次尝试全败的概率是 $0.4^{6}\approx 0.41\%$）。故障既然逐次独立，等不等都一样，退避只是白等：平均用时 10.5 片对 8.2 片。
2. bursty 体制：立即重试掉到 87.0%。机理在窗上：任务约 6 片做完，撞上故障窗的概率约 $1-0.95^{6}\approx 26\%$；撞上后立即重试的剩余尝试全挤在窗内，而窗平均 6.7 片比尝试上限 6 次还长，常常烧光上限仍全败。退避的 97.9% 靠的也是窗：失败后等 $1+2+4=7$ 片再试，正好跨出平均长度的窗，第 4 次尝试大概率已恢复正常。
3. 结论不在「退避永远更好」：iid 下立即重试更快且同样可靠。结论是重试策略要匹配故障的时间结构；结构未知时，退避是稳妥的默认，它顺带不把故障中的服务打得更死，也给了对端喘息恢复的时间。

白话：电梯检修时，连按十次按钮和等一分钟再按，效果天差地别；灯泡接触不良时，再按十次和等一分钟效果一样。重试策略对不对，取决于你面对的是检修中的电梯还是接触不良的灯泡。

> 竞赛生迁移提示：竞赛里你写过「失败就再来一次直到成功」的死循环重试，比如拒绝采样。那里重试不要钱也没有服务端；工程里每次重试都是一次计费调用，故障中的服务还会被重试风暴压得更死。所以工程重试三件套缺一不可：预算上限、退避间隔、幂等检查。

> 本节小结：错误处理按来源分两路，模型侧靠高质量报错回填加重试，工具侧先分瞬态还是永久再决定重试；指数退避第 $k$ 次失败后等 $2^{k-1}$ 片、累计 $2^{n}-1$ 片；实测在独立故障下退避只是白等（10.5 对 8.2 片），在故障窗体制下立即重试被窗吃掉（87.0% 对 97.9%），策略要匹配故障的时间相关性。

## $\rm \S \, 3.4$ 并行工具调用：独立的事一起做

到现在为止每轮只发一个调用。定义并行工具调用（parallel tool calling）：一轮模型输出里同时给出多个调用，执行器并发派发，每个调用各得一条观察、分别回填。能不能并行的判据只有一条：调用 B 的参数需不需要调用 A 的观察。需要就是依赖，必须串行；不需要就互为独立，可以同波。

实验一的检索任务是现成的例子：6 个主题的检索互不依赖，串行要 6 轮，并行一轮发 6 个、一轮回填 6 条观察。若任务还要「下载命中的论文再写摘要」，下载依赖检索结果、摘要依赖下载，那是三层依赖，至少 3 轮。轮数的下限由依赖层数决定，不由事件数决定；模型调用次数从线性于事件数降为线性于依赖层数，这就是并行省的钱。省的还是 §2.1 的账：任务累计输入随轮数大致按平方涨，轮数压下去，累计开销跟着平方级往下掉。

回填的形状也变了。第 1 章的消息列表每轮加 1 条 assistant 加 1 条 tool，$L_{t}=1+2t$；并行时一轮回填 $k$ 条 tool，公式推广为

$$
L_{t}=1+(k+1)\,t
$$

$k=1$ 就退回第 1 章的形状。对账时数一数 tool 消息条数与并行调用数是否一致，是检查「每个调用都拿到了观察」的快速办法。

两笔新代价要记。其一，部分失败：一波 6 个里 2 个超时，其余 4 个照常成功，失败者按 §3.3 的路线单独重试，不要因为 2 个失败把 4 个成功的观察也扔掉。其二，并行放大了故障的暴露面：一波 5 个调用，单发成功率 90% 时全过的概率只有 $0.9^{5}\approx 59\%$，波越大越要有心理准备。

白话：寄五封信不必跑五趟邮局，一个袋子拎走；但先查地址再寄信，这两步怎么也并不了。并行省的是趟数，依赖决定哪些事必须分趟。

> 本节小结：并行工具调用把互不依赖的调用排进同一轮，轮数下限由依赖层数决定；回填公式推广为 $L_{t}=1+(k+1)t$；代价是部分失败的处理与故障暴露面的放大。

## $\rm \S \, 3.5$ MCP 思想：把 M×N 变成 M+N

前几节的约定（schema 怎么写、报错怎么回填、结果怎么给）如果每个 agent 应用和每个工具提供方之间都要单独谈一遍，就有一笔组合账：M 个应用、N 个工具，最多 M×N 份接入胶水代码，每份都可能写得不一样。模型上下文协议（Model Context Protocol，MCP）是 2024 年底由 Anthropic 提出并开源的行业标准，把这笔账砍成 M+N：工具方把工具包装成 server，用本章 §3.2 形状的 schema 声明自己；agent 方实现一次 client，去发现 server 声明了哪些工具、转发调用、把结果按协议回填。工具作者写一次 server，所有支持协议的 agent 都能用；agent 作者接一次 client，所有 server 都能用。

协议的形状你已经在本章见过：声明 schema、发调用、回结果，就是解析-执行-回填三拍的跨进程版本，只是执行这一拍从同一个 Python 进程里的函数调用，变成了可能隔着一台机器的消息。类比插座国标：插头形状统一之后，电器厂和电网各管各的那一半，谁也不用迁就谁。

也要说清边界。协议统一解决的是「怎么接」，不解决「接什么」：server 递来的 schema 若是 V1 那种歧义名，标准插座上照样装反（§3.2）；工具若不幂等，协议再标准，重试照样出重复副作用（§3.3）。另外工具执行是 agent 的攻击面，真正动手前该想沙箱与最小权限，本册第 7 章展开，系统侧的隔离机制见《计算机安全》§6。

白话：MCP 是给工具世界定插座标准。标准出来前，每个电器配一种插孔，全世界都是转接头；标准出来后，电器厂管插头、电网管插孔，中间那一层谁都不用再写。

> 本节小结：MCP 把 M×N 份私有接入砍成 M+N，靠的是把本章的 schema 声明、调用、回填约定成跨进程的公共协议；协议统一不自动解决 schema 质量与幂等，接入的口子宽了，对第 7 章的安全要求也水涨船高。

## $\rm \S \, 3.6$ 常见错误与证据式排查

错误一：说明书用散文写，不标类型与必填。症状是首发通过率低、重试烧预算，就是 V2 与 V3 的实测（首发 75.8% 与 80.1%，平均轮数 7.26 与 7.11）。排查方法：把被拒调用按报错文本分桶统计，桶里「类型不符」占大头就补类型标注，「缺少必填」占大头就补 required，对桶下药。

错误二：报错回填是一句含混的「出错了」。模型只能整个重猜，修复率低。排查方法：对照实验一的做法，报错文本里给出参数名与期望类型（「参数 year_from 类型不符，应为 int」），统计修复率有没有抬升，没有就继续改报错措辞。

错误三：重试不分类、无上限、无退避。对参数非法这类永久错误重试是烧钱，对瞬态故障无间隔重试是打风。排查方法：给重试记录两个数，尝试次数（是否顶到上限）与前后两次报错是否相同（相同说明模型没改参数，立即停）；幂等性没把握的调用先查 §3.3。

错误四：有依赖的调用误并行。把「下载论文」和「检索论文」放进同一波，下载用的还是旧参数，拿到的是上一轮就过期的结果。排查方法：画出调用的依赖层，检查同一波里是否有调用吃了别家上一波才产出的观察；回填后数 tool 消息条数是否等于波内调用数（§3.4 的对账）。

错误五：只防可见错，不防静默错。校验器拦得住类型错，拦不住「区间填反」这类语义错，V1 的正确完成率 48.2% 就是漏网之鱼堆出来的。排查方法：对关键调用加结果合理性检查（检索返回 0 条就告警），或用第二次独立调用交叉验证；校验通过不等于结果正确，这两句话要分开记。

> 本节小结：五个坑五套检查，报错分桶下药、报错文本带参数名、尝试计数加报错比对、依赖图加 tool 条数对账、结果合理性告警；共同的源头是「完成」与「正确」要分开测。

## $\rm \S \, 3.7$ 动手实践：十分钟手摇 schema 校验

前置条件：装了 python3 的终端（WSL 或 Linux/macOS 均可）；在用户主目录新建练习目录，不碰已有文件。

```bash
mkdir -p ~/ea03-practice && cd ~/ea03-practice
```

读法：新建目录 `ea03-practice` 并进入；`-p` 让目录已存在时不报错。把下面 13 行存成该目录下的 `validate.py`（对象：新建文件），运行 `python3 validate.py`。

```python
def validate(a):
    for k, t in {'query': str, 'year_from': int, 'year_to': int}.items():
        if k not in a:
            return '缺少必填参数 %s' % k
        if type(a[k]) is not t:
            return '参数 %s 类型不符，应为 %s' % (k, t.__name__)
    return '校验通过'

calls = [
    {'query': 'attention', 'year_from': 2021, 'year_to': 2024},    # 规范调用
    {'query': 'attention', 'year_from': '2021', 'year_to': 2024},  # 年份写成字符串
    {'query': 'attention', 'year_to': 2024},                       # 漏了 year_from
    {'query': 'attention', 'year_from': 2024, 'year_to': 2021},    # 区间反了，类型全对
]
for c in calls:
    print(validate(c))
```

成功验证：输出四行，第一行 `校验通过`，第二行 `参数 year_from 类型不符，应为 int`，第三行 `缺少必填参数 year_from`，第四行又是 `校验通过`。第四行就是静默错误的最小化身：类型全对、必填全在，校验器对「区间填反」无话可说，而真正执行时这个调用会返回 0 条结果。这正是 §3.2 里校验（可见错误）与语义（静默错误）的分界线。常见失败：若第二行没有报错，多半是测试数据里的 `'2021'` 手滑写成了 `2021`；想看报错被拦下之后怎么自愈，把第二行改成 `int('2021')` 再跑一遍，观察「报错指出了改哪里」之后一行代码就能修复，这就是 §3.3 报错质量的价格。

> 本节小结：13 行校验器复现四类调用的命运，前三类各有报错、第四类校验放行；第四行「校验通过」是本节要带走的那句话，通过校验不等于结果正确。

## $\rm \S \, 3.10$ 本章自测答案

概念回顾答案：

1. 工具名、每个参数的名字与类型、取值范围（枚举）、必填与可选的划分（§3.2）。合同语言下，required 加类型标注是前置条件，声明调用前必须满足什么；description 与返回格式约定是后置条件，声明执行后承诺给什么（§3.2）。
2. 分界在错误是否进入反馈通道：可见错误被校验拦下，报错回填，下一轮模型有信息可改；静默错误类型合法、绕过校验，报错不出现，重试机制看不到它（§3.2）。V1 的静默错误率 10.7%，六次独立调用全对的概率是 $0.89^{6}\approx 49.7\%$，实测正确完成率 48.2%（§3.2）。
3. 第 $k$ 次失败后等 $2^{k-1}$ 片，累计 $2^{n}-1$ 片（§3.3）。iid 体制下两种重试完成率同为 97% 上下，退避白等，用时 10.5 片对 8.2 片；bursty 体制下立即重试 87.0%、退避 97.9%，机理是故障窗平均 6.7 片，立即重试的尝试挤在窗内烧光上限，退避的 $1+2+4=7$ 片跨出了窗（§3.3）。
4. 判据是数据依赖：调用 B 的参数需不需要调用 A 的观察，不需要才可同波（§3.4）。一波 $k$ 个调用时每轮回填 1 条 assistant 加 $k$ 条 tool，$L_{t}=1+(k+1)\,t$；$k=1$ 退回第 1 章公式（§3.4）。

应用与辨析答案：

1. 检查一：翻重试日志，比对前后报错文本。一字不变说明模型没有收到可行动的信息，或者压根没改参数，无脑重试没有出路（§3.6 错误二、错误三）。检查二：给错误分类，判断是模型侧参数错还是工具侧永久错误。参数非法类错误重发一万次也是同样结果，应停止重试、改为修报错质量或修参数生成（§3.3）。
2. 完成率四个变体都升：预算富余从 2 轮变 6 轮，重试空间更大，V2 升幅最大，它靠重试吃饭，78.0% 会明显回升；正确完成率几乎不动。正确与否由静默错误与任务本身可解性决定，预算救的是没跑完的任务，救不了装反的参数（§3.2）；V1 至多因任务跑完而小幅回升，48.2% 的主坑不变。
3. 不成立，至少不完整。完成率只统计「校验都过了」，V1 的高完成率里藏着 10.7% 的静默错误，正确完成率 48.2% 远低于 V2 的 74.8%（§3.2）。两个变体在两张指标上优劣互换，恰恰说明选指标前要先问「我的错误可见吗」；只报完成率的评测会漏掉整个静默通道。
