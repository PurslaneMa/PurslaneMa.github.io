# $\rm Chapter \, 8$ 应用层：DNS、HTTP 的演进与 HTTP/3

传输层给了你「进程到进程的字节管道」，剩下的问题是应用怎么用它：名字怎么变成地址（DNS），请求-响应怎么在管道上排班（HTTP 的三代演进）。本章的主线只有一个：**每一次演进都在砍第 7 章实测出来的那几笔固定税**，你会看到 DNS 缓存把 58.9 ms 砍到 0.4 ms，keep-alive 把 10 次请求的 155 ms 握手税砍掉，HTTP/2 再砍排队，HTTP/3 连握手本身都要免单。

> **开始前自检**：本章假设你已经会：
>
> 1. □ 把一次请求的时延拆成 DNS / 握手 / 处理三段（§7.2 的实测数字会被反复引用）；
> 2. □ 用浏览器开发者工具看过请求列表（计算机速通 §23.2）；
> 3. □ 知道 HTTP 报文 = 请求行/状态行 + 头部 + 体（计算机速通 §23.3）；
> 4. □ 知道 TCP 字节流不保留消息边界（§4.4）。

## $\rm \S \, 8.1$ DNS：分层的通讯录

域名到 IP 的翻译不是查一张表，而是**逐层问路**：根服务器（`.edu` 归谁管？）→ 顶级域服务器（`tsinghua.edu` 归谁管？）→ 权威服务器（`www.tsinghua.edu.cn` 是多少？）。你的系统默认不自己跑全程，而是问**递归解析器**（ISP 或 `223.5.5.5` 这类公共 DNS），它替你迭代问完三层、把答案带回来并缓存。

分层的好处是每一层只需回答「下一层在哪」：根只认得十几台 TLD 服务器的地址，`.cn` 的服务器只认得 `cn` 域下的权威。**全球通讯录没有任何一台机器存得下，但每台都只需要存自己那一层**。这与 IP 路由的「最长前缀匹配」（§3.4）是同一个设计哲学：分层 + 逐级委托。

真实的解析记录长这样（WSL2 下 `dig` 采集，解析器为 `1.1.1.1`）：

```text
;; Query time: 4 msec ;; SERVER: 1.1.1.1#53(UDP)
www.tsinghua.edu.cn.   7137   IN   A    101.6.15.66

www.baidu.com.          673   IN   CNAME  www.a.shifen.com.
www.a.shifen.com.       399   IN   A      182.61.200.110
www.a.shifen.com.       399   IN   A      182.61.200.108
```

三样东西值得读：① 每行答案自带剩余 TTL（7137 秒，这条记录刚被刷新过缓存；399 秒，快过期了）；② `baidu.com` 的答案不是 IP 而是 **CNAME**（别名）：真名是 `www.a.shifen.com`，解析器要再多问一轮拿 A 记录，别名链在 DNS 里是常态；③ 一条名字可以对应多个 A 记录，客户端随机挑一个，DNS 顺手就做了最朴素的负载均衡。查询走 UDP 53 端口、4 ms 是热缓存的速度，与 §8.2 的 0.4 ms 同类（本地系统缓存比网络解析器还近一层）。

## $\rm \S \, 8.2$ 实测：缓存砍掉的那一笔

DNS 的答案带 TTL（生存时间），解析器按 TTL 缓存。实测（本机，`socket.gethostbyname` 走系统解析器）：

```python
import socket, time
def resolve(h):
    t0 = time.perf_counter(); socket.gethostbyname(h)
    return (time.perf_counter() - t0) * 1000
print('tsinghua 冷:', resolve('www.tsinghua.edu.cn'))   # 58.9
print('tsinghua 热:', resolve('www.tsinghua.edu.cn'))   # 0.4
```

本机输出：

```text
tsinghua 冷: 58.9 ms
tsinghua 热: 0.4 ms
```

**147 倍**。这正是 §7.2 那次请求里 DNS 占 47.6 ms 大头的原因：冷查询要走一次完整的递归迭代。工程含义：浏览器「DNS 预解析」（提前触发查询，把冷账算在用户点链接之前）、本地缓存、以及应用侧的长 TTL，都是围绕这一笔的优化。代价与谎言：TTL 内的答案不会更新，改了 DNS 记录要等旧 TTL 过期才全球生效，所以「计划切流量」前要提前把 TTL 调低。

## $\rm \S \, 8.3$ HTTP/1.0 → 1.1：先省握手税

HTTP/1.0 每个请求一条连接：DNS + 三次握手 + 请求 + 四次挥手，用完即弃。1.1 的默认 **keep-alive** 让连接活下来服务后续请求。实测 10 次 GET（本机对清华主页，取两轮较优）：

```python
import http.client, time
def run(n, keepalive):
    t0 = time.perf_counter(); conn = None
    for i in range(n):
        if conn is None:
            conn = http.client.HTTPConnection(host, 80, timeout=8)
        conn.request('GET', '/', headers={'Connection': 'keep-alive' if keepalive else 'close'})
        conn.getresponse().read()
        if not keepalive: conn.close(); conn = None
    return (time.perf_counter() - t0) * 1000
```

输出：**keep-alive 42 ms 对每次新建 197 ms，10 个请求省 155 ms**（平均每个 15.5 ms，恰是 §7.2 实测的握手 13.6 ms 加挥手开销的量级）。1.1 还顺手加了 Host 头（一台 IP 多个网站的基础）与 chunked 分块传输，但主线就是这条：**连接复用，省固定税**。

1.1 的另外两个配套件也值得点名：**Host 头**让一条 IP 上可以住多个网站（请求头里的 `Host: www.tsinghua.edu.cn` 就是「找这家」，服务器按名字选内容，这是 CDN 与虚拟主机的地基）；**chunked 传输**让服务器不必预先算好响应大小就能开始发送（边生成边分块）。

复用的遗留问题：1.1 的 keep-alive 是**串行**的，同一条连接上第 2 个请求必须等第 1 个响应发完（响应要按序）。浏览器只好开 4–8 条并行连接硬拼带宽，又把 TIME_WAIT 压力还给了服务端（§7.3 的账）。

## $\rm \S \, 8.4$ 报文边界：HTTP 怎么在字节流上切消息

§4.4 的结论在这里兑现：TCP 只给字节流，HTTP 必须自己声明「一条消息到哪结束」，接收方才知道「请求齐了、可以处理了」。三种收尾方式：

1. **`Content-Length: N`**：体正好 N 字节，数完即止，最常见，也是 keep-alive 能工作的前提（不知道边界就没法在同一条流上认出下一条消息）；
2. **`Transfer-Encoding: chunked`**：不知道总长时边发边切块，每块前置十六进制长度，零长块收尾，动态生成的页面靠它；
3. **读到连接关闭**：1.0 的兜底，服务器发完就挥手，接收方「流断了=消息完了」。它天然与 keep-alive 互斥，也解释了 1.0 为什么必须一物一连接。

一个把三者串起来的实验回忆：§4.4 里三次 `send` 被一次 `recv` 合并，接收方看到的只是字节流，「消息」完全是应用层用这些约定切出来的。实战排障里「响应体被截断」「下一请求解析报错」，八成是这三种方式的实现出了岔子（如 `Content-Length` 与实际长度不符）。

## $\rm \S \, 8.5$ HTTP/2：一条连接上的多车道

2015 年的 HTTP/2 把「并行」做进协议：一条 TCP 连接里开任意多条**流（stream）**，每个流独立编号、交错发送，头部用 HPACK 压缩（每次请求几十字节起的重复头被压成几个字节）。图景：1.1 是单车道公路加宽成 4 条连接，2.0 是一条路上画了多条车道。

但 2.0 有个内置矛盾：多车道跑在**一条 TCP 字节流**上，而 TCP 保证的是「字节按序到达」，任何一段丢包，内核就得停下等重传，**所有车道一起堵**（TCP 层队头阻塞，与 §4.4 的流内阻塞同根，发生在更下面一层）。丢包率 2% 的无线网络上，HTTP/2 实测可能比开多条 1.1 连接还慢，这不是实现缺陷，而是「多路复用叠在单字节流上」的结构性代价。

## $\rm \S \, 8.6$ HTTP/3 与 QUIC：换地基

HTTP/3（2022 年标准化）的答案是把地基从 TCP 换成 **QUIC**，即在 UDP 上重新实现连接、可靠性与安全性（§9 会看到 TLS 1.3 被揉进握手里）。三笔收益：

1. **握手合并**：TCP 握手 + TLS 握手原本要 2–3 个 RTT，QUIC 一并谈完，首次连接 1 RTT、会话恢复 **0-RTT**（第一个包就带数据），§7.2 的 13.6 ms 握手税在恢复场景直接归零；
2. **流之间真正独立**：QUIC 在自己的层里按流管理序，丢包只堵所在流，其他流照跑，TCP 队头阻塞结构性消失；
3. **连接迁移**：连接标识与四元组解耦，手机从 Wi-Fi 切 4G 不用重连（连接号还在，路换了）。

代价：UDP 在部分网络设备上被限速或封锁（QUIC 失败要回落 TCP）；内核没有 UDP 加速路径那么成熟，CPU 开销靠用户态实现硬扛。演进没有终点，只有取舍：**1.1 省握手、2.0 省排队、3.0 连握手都想免**。每一代都在对着第 7 章那张时延账单划线。

## $\rm \S \, 8.9$ 本章自测答案

### $\rm \S \, 8.9.1$ 关键概念回顾答案

1. 根回答「`.cn` 的服务器在哪」，TLD 服务器回答「`example.cn` 的权威在哪」，权威回答「`www.example.cn` 的 IP」。递归解析器替客户端跑完整个迭代链并把答案按 TTL 缓存。（§8.1）
2. 冷查询要完整递归迭代（58.9 ms），热查询命中本地缓存（0.4 ms）。TTL 决定答案能被缓存多久，它同时是性能机制（少问上级）与一致性代价（改记录要等过期）。（§8.2）
3. 155 ms ≈ 10 次（DNS 已热后的）TCP 握手加挥手开销，每请求约 15.5 ms。串行限制：同一连接上响应必须按请求顺序完成，后请求被前请求的慢响应堵住，浏览器被迫开多条并行连接对冲。（§8.3）
4. HTTP/2 的队头阻塞在 TCP 层：所有流复用一条字节流，内核的按序交付让任一段丢包卡住全部流。HTTP/3 的 QUIC 在传输层内按流独立管理序，丢包只影响所在流。（§8.4、§8.5）
5. TCP 连接由四元组（源/目的 IP+端口）标识，换网即换 IP、四元组作废；QUIC 用独立的连接标识认人，与地址解耦，地址变了连接还在。（§8.5）

### $\rm \S \, 8.9.2$ 应用与辨析答案

1. 迁移前 1–2 天把 TTL 调到 60 秒以下并等旧 TTL 过期（全球缓存里只剩短 TTL 记录）；切换时改权威记录为新 IP；观察流量迁移完成后可把 TTL 调回。若跳过第一步，旧的长 TTL 记录会在各处缓存里钉住旧 IP 数小时。（§8.2）
2. 解释一：内网丢包率升高时 TCP 层队头阻塞放大，所有流被偶发丢包拖住（验证：抓包看重传统计与流完成时间的相关性；对照多条 1.1 连接）。解释二：网关 CPU 打满，QUIC/H2 的用户态实现比内核 TCP 贵（验证：CPU profile 是否落在协议解析路径）。（§8.4、§8.5）
3. 错误一：QUIC 在 UDP 上**重新实现了**可靠性与按序（流内），跑在上面的 HTTP/3 拿到的仍是可靠语义；错误二：UDP「不可靠」指的是它不替应用保证交付，不是数据会被随机篡改，校验与加密 QUIC 自己带（TLS 1.3 内置）。（§8.5）
