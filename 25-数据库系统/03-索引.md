# $\rm Chapter \, 3$ 索引：用空间和写放大换查找

第 2 章结尾点了一句影子成本：每多一棵二级树，写入就多改一棵。本章把这本账算全——先用一百万行的 sqlite3 实验把三笔账（查询、空间、写入）的数字摆上桌，再回到结构解释数字从哪来：回表为什么按次收费、三棵树的叶子各存什么、覆盖索引怎么把回表整项买断、联合索引的页序为什么让一半查询失效；最后用 `EXPLAIN QUERY PLAN` 把索引失效清单逐条过堂。那份计划文本是优化器选择过程留下的脚印——它怎么选，第 5 章拆。

> **开始前自检**：本章假设你已经会：
>
> 1. □ 记得 B+ 树的两条结构规则与树高公式 $h=\lceil\log_{d}N\rceil$（§2.4）；
> 2. □ 知道聚簇索引与二级索引的叶子各放什么、「回表」发生在哪一步（§2.6）；
> 3. □ 接受「磁盘算法按页访问次数记账」的代价模型（§2.1）；
> 4. □ 会用 Python 的 sqlite3 模块建表、插行、跑 SELECT（cs 册 §26.1；本章实验全程用它）。

## $\rm \S \, 3.1$ 先看账本：三笔账

固定条件沿用 §1.4 的口径：$10^6$ 行（id、user、amount），user 取一千种值，随机种子 20261025，SQLite 3.49.1。同一张表 t 三次变身——裸表、加单列索引 idx_user、加覆盖索引 idx_user_amount——三笔账如下（查询出自 §3.6 的输出块，空间与写入出自同一实验的补测）：

1. **查询账**：同一条「按 user 求和」各跑 $100$ 次，$71.17\,\text{ms/次} \to 5.54\,\text{ms/次} \to 0.23\,\text{ms/次}$：单列索引快约 $13$ 倍，覆盖索引再快约 $24$ 倍；
2. **空间账**：表本体 $22.1\,\text{MB}$；idx_user 追加 $13.0\,\text{MB}$，idx_user_amount 追加 $22.0\,\text{MB}$——两棵二级树合计 $35\,\text{MB}$，比表本体还多六成；
3. **写入账**：裸表插入 $10^6$ 行 $1.2\,\text{s}$；预建这两棵二级树后，同样的插入 $39.3\,\text{s}$，慢 $32$ 倍。这种「一次逻辑写入、多棵结构跟着改」的效应叫**写放大（write amplification）**。

三笔账连起来读：索引不是无条件的优化，而是把查询省下的钱记到空间与写入的账上。读多写少的表可以大方建，写密集的表每棵树都要过堂——判断依据是表的读写比，不是「索引总是好的」。§3.2 到 §3.5 解释查询账里那几十倍的来源，§3.6 把写入账拆到可操作。

## $\rm \S \, 3.2$ 回表：二级索引的第二次下探

§2.6 交代过结构：二级索引的叶子放「键值加 rowid」。也就是说，二级树只回答「哪些行的 rowid 满足条件」，而查询要的 amount 不在它的叶子里——每个命中 rowid 都要回聚簇树再下探一次，才能取回整行。把一次二级树探针记作 $p$，一次回表下探记作 $b$，命中 $k$ 行的查询代价是：

$$
T = p + k \cdot b
$$

§3.6 的数字代进去：$k=1000$，覆盖索引把 $k \cdot b$ 整项消掉后，$5.54\,\text{ms}$ 掉到 $0.23\,\text{ms}$——差额摊到每次回表约 $5.3\,\text{µs}$，这还是页已在内存缓存里的价格；冷缓存下每次下探都是一次真实 I/O，起步价是 §2.1 的 $0.1\,\text{ms}$。所以「走了索引」不等于「快了」：决定索引值不值的是命中行数占总行数的比例，数据库叫**选择率（selectivity）**。选择率一高，$k \cdot b$ 就盖过 $p$；命中多到一定程度，优化器干脆放弃索引直接全扫——它怎么算这笔账是第 5 章的事。

**本节小结**：二级索引只圈出 rowid，取整行要按命中数逐次回表，代价是 $T = p + k \cdot b$；索引值不值由选择率说了算，命中多到一定程度优化器宁可全扫。

## $\rm \S \, 3.3$ 三份副本：一行数据住几棵树

表只有一份，空间账却翻了倍——因为每个索引都是一份按键重排的完整誊抄。三棵 B+ 树的叶子内容与各自能直接回答的问题：

| 树 | 叶子内容 | 能直接回答 |
| --- | --- | --- |
| 聚簇树（表本体） | 整行：id、user、amount | 按 id 点查、全表扫 |
| idx_user | user 加 rowid | 「哪些行 user 等于某值」，取 amount 仍需回表 |
| idx_user_amount | user 加 amount 加 rowid | 连 user 带 amount 一次取齐，不必回表 |

空间账由此有了结构解释：键选多宽，誊抄就多厚——idx_user_amount 的叶子键比 idx_user 宽约一倍（amount 占 $8$ 字节），贵出的 $9.0\,\text{MB}$ 就是这份宽度。cs 册 §26.5 给过索引的接口与「查得快不是免费的」提醒，现在这句话有了精确含义：索引本体不是几张目录卡，而是一整本按新键序重排的薄书。

## $\rm \S \, 3.4$ 覆盖索引：把回表整项买断

白话：把查询要的列全部搬进目录卡片，卡片本身就写全了答案，用不着再回正本翻一次。

上表第三行有个名字：查询要的每一列都住在某棵二级树的叶子里时，这棵树对这条查询就是**覆盖索引（covering index）**。cs 册 §27.5.2 教过「不回表」的判断接口，结构原因现在补齐：二级索引的叶子本来就带 rowid（§2.6），把查询要的列并进键后，rowid 把主键免费补齐，要的每个字段都在叶内顺读可达——公式里的 $b$ 从「一次随机下探」降为「叶链上多扫几字节」。

代价与收益都已在 §3.1 的账上：收益是 $5.54 \to 0.23\,\text{ms/次}$ 的约 $24$ 倍；代价是键变宽、树变大（$13.0 \to 22.0\,\text{MB}$），写放大再上一层。所以覆盖索引的正确用法是为高频查询定制：挑出最常一起出场的那几列并进键，而不是把所有列都塞进去——后者等于把整张表再誊一遍，空间账直接翻倍。

## $\rm \S \, 3.5$ 联合索引与最左前缀：页序的解释

idx_user_amount 其实已经是**联合索引（composite index）**：键是二元组 ${(a, b)}$（这里 $a$ 是 user、$b$ 是 amount），叶页按字典序摆放：

$$
(a_1, b_1) \le (a_2, b_2) \iff a_1 < a_2 \ \lor\ \big(a_1 = a_2 \land b_1 \le b_2\big)
$$

整棵树先按 $a$ 分段，段内按 $b$ 有序。cs 册 §27.5.1 给过「只能从左往右用」的规则与书目类比，为什么，页序三句话说清：

1. **查 $a$**：$a$ 的取值把叶子切成连续段，等值条件直接落到段边界——可用；
2. **只查 $b$**：$b$ 只在段内有序，全局看 $b$ 的每个取值散布在所有 $a$ 段里，没有任何连续页段能圈出它们——索引失效，只剩全扫；
3. **$a$ 等值后接 $b$ 范围**：先落段，段内 $b$ 有序，范围条件照样能用——这正是**最左前缀（leftmost prefix）**的全部内容：从排序第一维起，不跳维、不倒序地用。

$9$ 个键的迷你页序（$a$ 取 ${1,2,3}$）：${(1,1)}$ ${(1,3)}$ ${(1,5)}$ ${(2,1)}$ ${(2,2)}$ ${(2,5)}$ ${(3,2)}$ ${(3,4)}$ ${(3,5)}$。查 $b=5$：命中落在第 $3$、$6$、$9$ 位，横跨全部三个段，不扫全列无法保证不漏；查 $a=2$ 且 $b \ge 2$：先落中段，从 ${(2,2)}$ 顺读两格收工。

**本节小结**：联合索引的页按字典序先 $a$ 后 $b$ 摆放，所以条件必须从最左维起、不跳维地用；只查 $b$ 的命中散布在所有 $a$ 段里，没有连续页段可圈，索引只能弃用。

## $\rm \S \, 3.6$ 实验：三种查询的耗时与计划

在空目录把下面代码存为 `idx_exp.py` 运行（`python idx_exp.py`），复现 §3.1 的查询账与三份计划文本：

```python
import sqlite3, time, random; random.seed(20261025); N = 1_000_000
rows = [(i, f"u{random.randrange(1000):03d}", round(random.uniform(0, 1000), 2)) for i in range(N)]
con = sqlite3.connect("idx.db")
con.execute("CREATE TABLE t(id INTEGER PRIMARY KEY, user TEXT, amount REAL)")
con.executemany("INSERT INTO t VALUES(?,?,?)", rows); con.commit()
qs = [f"u{v:03d}" for v in random.sample(range(1000), 100)]
Q = "SELECT sum(amount) FROM t WHERE user=?"
for name, ddl in [("无索引", None), ("单列", "CREATE INDEX idx_user ON t(user)"), ("覆盖", "CREATE INDEX idx_user_amount ON t(user, amount)")]:
    if ddl: con.execute(ddl)
    t0 = time.perf_counter()
    for q in qs: con.execute(Q, (q,)).fetchone()
    print(f"{name}: {(time.perf_counter()-t0)*10:.2f} ms/次 |", con.execute("EXPLAIN QUERY PLAN " + Q, ("u500",)).fetchone()[3])
```

```text
无索引: 71.17 ms/次 | SCAN t
单列: 5.54 ms/次 | SEARCH t USING INDEX idx_user (user=?)
覆盖: 0.23 ms/次 | SEARCH t USING COVERING INDEX idx_user_amount (user=?)
```

读数四条（绝对数字随机器与缓存状态浮动，量级关系稳定）：

1. 计划文本就是优化器的选择书：`SCAN t` 是顺着聚簇树把全部叶页过一遍，`SEARCH … USING INDEX` 是按 §2.4 的树高下探——同一句 SQL，三份计划；
2. 单列索引的 $5.54\,\text{ms}$ 里，计划文本看不见 $k \cdot b$：计划只说「怎么找行」，不说「每行取回来多贵」——回表是藏在 SEARCH 字样后面的暗账；
3. 覆盖索引一行直接印出 `COVERING` 字样，§3.4 的结构判断在计划文本里可查可验；
4. 空间账与写入账在同一实验里补测：插入 $10^6$ 行裸表 $1.2\,\text{s}$，预建两棵二级树 $39.3\,\text{s}$；反过来先导完数再建索引，两棵树各花 $0.62\,\text{s}$ 与 $1.10\,\text{s}$，合计 $2.9\,\text{s}$——差出 $13$ 倍。批量排序建树远比逐行维护树便宜，**先导数、后建索引**因此是写密集场景的标准次序；空间账用 `PRAGMA page_count` 前后相减即可复核（$5392 \to 8574 \to 13952$ 页）。

## $\rm \S \, 3.7$ 索引失效清单：EXPLAIN 逐条实证

接着 §3.6 的会话，把基线与六种写法逐一过堂：

```python
cases = [("基线", "SELECT * FROM t WHERE user='u500'"),
         ("函数", "SELECT * FROM t WHERE lower(user)='u500'"),
         ("前导通配符", "SELECT * FROM t WHERE user LIKE '%500'"),
         ("前缀通配符", "SELECT * FROM t WHERE user LIKE 'u5%'"),
         ("隐式转换", "SELECT * FROM t WHERE user=500"),
         ("范围改写", "SELECT * FROM t WHERE user >= 'u5' AND user < 'u6'"),
         ("OR 半边", "SELECT * FROM t WHERE user='u500' OR amount>999")]
for name, s in cases:
    print(f"{name} ->", con.execute("EXPLAIN QUERY PLAN " + s).fetchone()[3])
```

```text
基线 -> SEARCH t USING COVERING INDEX idx_user_amount (user=?)
函数 -> SCAN t
前导通配符 -> SCAN t
前缀通配符 -> SCAN t
隐式转换 -> SEARCH t USING COVERING INDEX idx_user_amount (user=?)
范围改写 -> SEARCH t USING COVERING INDEX idx_user_amount (user>? AND user<?)
OR 半边 -> SCAN t
```

1. **函数包列**（`lower(user)`）→ `SCAN t`。树按 user 的原值排序，`lower(user)` 是一批树里没有的新值，定位无从谈起。方向反过来（函数包在常量一侧），或把表达式本身建成索引，才能救；
2. **前导通配符**（`LIKE '%500'`）→ `SCAN t`。字典序从第一个字符比起，`%` 开头等于拒绝告知起点；
3. **前缀通配符**（`LIKE 'u5%'`）竟然也 `SCAN t`：默认的 LIKE 不分大小写，BINARY 序的索引给不出「既快又不漏」的不区分大小写范围——列声明成 `COLLATE NOCASE` 或打开 `case_sensitive_like` 才走索引。失效与否系于排序规则，不系于「前缀」二字；
4. **隐式转换**（`user=500`）没有失效：仍是 `SEARCH`。SQLite 的类型亲和性把数字字面量先转成文本再比较，树照用。同一条在 MySQL 上会让字符列的索引失效——隐式转换策略是各引擎自己的约定，失效清单不能跨引擎背诵；
5. **OR 半边无索引**（user 有索引、amount 没有）→ `SCAN t`：索引只能圈出半边行集，另一半仍要全扫再合并，直接全扫反而便宜；
6. 两条对照组：基线 `SELECT *` 意外走了 `COVERING INDEX`——idx_user_amount 恰好包含 t 的全部列（user、amount 加 rowid 即 id）；范围改写 `user >= 'u5' AND user < 'u6'` 精确落进 `(user>? AND user<?)`，连续区间正对 BINARY 序的段边界。

失效自检的动作从此固定：任何「加了索引却没变快」的查询，第一步 `EXPLAIN QUERY PLAN`，看 SEARCH 还是 SCAN、括号里点名了哪些列——cs 册 §27.5.1 的方法论，本章把每条失效背后的结构原因补齐了。

## $\rm \S \, 3.10$ 本章自测答案

> 先闭卷作答 §3.8 与 §3.9，再核对。

### $\rm \S \, 3.10.1$ 关键概念回顾答案

1. 查询账（$71.17 \to 5.54 \to 0.23\,\text{ms/次}$）、空间账（$22.1\,\text{MB}$ 加 $13.0$ 加 $22.0$）、写入账（$1.2\,\text{s}$ 对 $39.3\,\text{s}$）。读写比决定哪笔账主导：读多写少时查询收益盖过写放大，写密集时每棵树都是净负担。（§3.1）
2. $T = p + k \cdot b$：差额约 $5.3\,\text{ms}$ 是 $k=1000$ 次回表的单价（每次约 $5.3\,\text{µs}$，缓存命中价）。选择率决定 $k$：越高回表项越重，高过阈值优化器弃索引改全扫。（§3.2、§3.6）
3. 聚簇叶放整行；idx_user 叶放 user 加 rowid；idx_user_amount 叶放 user 加 amount 加 rowid。翻倍来自「每个索引都是按键重排的完整誊抄」——键多宽、誊抄多厚。（§3.3）
4. 按字典序：先 $a$ 分段、段内 $b$ 有序。只查 $b$ 时命中散布于所有 $a$ 段，无连续页段可定位；$a$ 等值落段后段内 $b$ 有序，范围可用。规则：从第一维起、不跳维地用。（§3.5）
5. 隐式转换（类型亲和性把 $500$ 转成文本再比较，树照用）与范围改写（连续区间正对 BINARY 序的段边界）。共同点：失效与否是引擎约定与排序规则的事，不是查询写法一条清单管天下。（§3.7）

### $\rm \S \, 3.10.2$ 应用与辨析答案

1. 三笔账都可能翻车：选择率低则索引帮不上查询（§3.2）、每个索引一份誊抄吃空间（§3.3）、写放大最高实测 $32$ 倍（§3.1）。加之前看两个数字：这条查询的选择率与这张表的读写比。（§3.1、§3.2）
2. 建覆盖索引 (user, amount)：查询账 $71.17 \to 0.23\,\text{ms/次}$，比裸表约 $310$ 倍，比单列索引再快约 $24$ 倍（省掉 $1000$ 次回表）；代价是键更宽（空间账 $+22.0\,\text{MB}$）、写放大再上一层。（§3.4、§3.6）
3. 改写把「不区分大小写的模式匹配」换成「区分大小写的连续区间」，恰好落进 BINARY 序的段边界（计划文本 `(user>? AND user<?)` 即证）。绕开的是前缀通配符因大小写不敏感而失效那条；前提是业务语义接受区分大小写、列按 BINARY 规则排序。（§3.7）
