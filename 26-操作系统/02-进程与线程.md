# $\rm Chapter \, 2$ 进程与线程：fork、exec 与调度实体

上一章把进程立为三抽象之一：内核记账的「演出」。本章翻开这本账：一个进程在内核里由哪些字段构成；它怎样被复制（fork）又被替换（exec）；退出之后谁来收尸（wait、僵尸与孤儿）；以及当两个执行流共享同一套地址空间时，会发生什么——线程，和一场你能亲手跑出来的数据竞态。

> 1. □ 三个抽象、系统调用与 fd 表（本书 §1.2、§1.3）；
> 2. □ 「进程 = 演出」与时间片切换的说法（计算机速通 §11.2、§11.5）；
> 3. □ 在 cs 册 §11.3 见过线程与数据竞争的名字（本章将实测它）；
> 4. □ 会用 Python 跑脚本并用 `subprocess` 执行外部命令（§1.3 刚练过）。

## $\rm \S \, 2.1$ 进程的账本：内核里的字段清单

内核为每个进程维护一份记录，教科书称为**进程控制块（process control block，PCB）**；Linux 的实现叫 `task_struct`，名字不必记，字段清单值得记：

| 字段 | 存什么 | 上一章的落点 |
| --- | --- | --- |
| PID 与父进程指针 | 身份与家谱 | §1.3 实验里的 8260 与 42940 |
| 地址空间（页表指针） | 这场演出的整套布景 | §1.2 的虚拟内存抽象 |
| 打开文件表（fd 数组） | 已打开文件的槽位 | §1.3 里从 3 起编的 fd |
| 寄存器现场 | 程序计数器、栈指针、通用寄存器 | 时间片切走前存、切回时装（计算机速通 §11.2） |
| 状态与退出码 | 就绪、运行、睡眠，或已退出 | §2.4 的僵尸进程 |

两点先说清楚。其一，寄存器现场是调度切换的存根：CPU 只有一套寄存器，时间片到了就把当前进程的现场整份存进 PCB，换下一位上场——这就是「演出暂停再续演」的机制落点。其二，父进程指针是 §2.4 僵尸与孤儿故事的伏笔：每个进程都有父亲，父亲对子进程负有一项到期义务——收尸。

## $\rm \S \, 2.2$ fork：一次调用、两个返回值

复制一个进程是 Unix 的老手艺。`fork` 是 Linux/Unix 的系统调用（Windows 没有，本节输出在 WSL2 的 Linux 6.6.87 内核下采集）：

```python
import os
pid = os.fork()          # 复制当前进程，之后的代码父子各跑一份
if pid == 0:
    print("child: fork() returned 0, my pid is", os.getpid(), flush=True)
    os.execv("/bin/echo", ["echo", "child: after execv, echo runs with same pid"])
else:
    print("parent: fork() returned", pid, flush=True)
    _, status = os.waitpid(pid, 0)
    print("parent: wait got exit code", os.waitstatus_to_exitcode(status), flush=True)
```

```text
parent: fork() returned 552
child: fork() returned 0, my pid is 552
child: after execv, echo runs with same pid
parent: wait got exit code 0
```

`fork()` 被调用一次，却返回了两个值：父进程拿到子进程的 PID（552），子进程拿到 0。机制就在 PCB 上——内核把父进程的账本整份复印给子进程：同样的地址空间、同样的 fd 表、寄存器现场停在同一个返回点，唯一的差别是账本上「fork 的返回值」一格，一边填 0 一边填新 PID。哪边先打印由调度决定，这次是父进程抢先。

复制的代价要按需收。地址空间如果真的一页一页复制，fork 一个占 2 GB 的进程就要先搬 2 GB；实际做的是**写时复制（copy-on-write，COW）**：父子先共用同一批只读内存页，谁先写入谁触发复制。cs 册 §11.5.4 用 `/proc` 实测过 `VmSize` 与 `VmRSS` 的分离，那就是 COW 的现场证据，此处不再重做。Windows 走的是另一条路：`CreateProcess` 创建时就指定要运行的程序，复制与替换捏成一步，没有「先克隆再决定」的窗口——这个差别在下一节变成 fork + exec 两步设计的存在理由。

## $\rm \S \, 2.3$ exec 家族与 shell 的 fork + exec 模型

`execv` 的语义是：进程不变（PID、fd 表原样保留），地址空间里的代码与数据整个换掉——同一间剧场换了正在上演的剧目。它是一个家族（`execv`、`execl`、`execvp` 等），差别只在参数排法：`v` 收参数数组，`l` 收逐个列出，带 `p` 的版本会翻 PATH 地址簿找程序。§2.2 代码里子进程调用 `execv` 后，打印行换成了 `/bin/echo` 的输出而 PID 未变。用 strace 抓 Python 的 `subprocess`（`strace -f` 会连同子进程一起追踪，输出在 WSL2 采集）：

```text
[pid   645] execve("/usr/bin/python3", ["/usr/bin/python3", "-c", "pass"], ...) = 0
```

`[pid 645]` 就是 subprocess 新建的那个子进程：被复制出来后用 `execve` 换成了目标程序。shell 运行一条命令用的正是同一套模型：

```mermaid
flowchart LR
    A["shell: fork 出子进程"] --> B["子进程: execv 换成 ls"]
    B --> C["ls 运行、退出"]
    C --> D["shell: waitpid 收退出码"]
```

fork 与 exec 拆成两步不是历史包袱。cs 册 §12.1 讲过「重定向就是改 fd 指向」，现在补上时机：改在 fork 之后、exec 之前——子进程趁自己还是 shell 的副本时把 fd 1 指到目标文件，exec 换身不换 fd 表，于是 `ls` 浑然不觉地把清单写进了文件。没有这个两步之间的窗口，shell 就得让 `ls` 自己去理解几百种重定向参数；`CreateProcess` 的一步式创建没有这个天然窗口，只能靠额外的参数结构把同样信息塞进去。

## $\rm \S \, 2.4$ wait 与收尸：僵尸与孤儿

子进程退出后，PCB 不会立刻消失：退出码是留给父亲的遗产，父亲用 `waitpid` 来领，内核才销毁账本。父亲还没来领的已死进程就是**僵尸进程（zombie process）**——在 WSL2 下实测，子进程退出、父进程故意不收：

```text
    PID    PPID STAT COMMAND
    483     469 Z+   python3
```

STAT 列的 `Z` 就是僵尸。它不占 CPU、不占内存页，只剩 PCB 里的一条退出记录；`kill` 对它无效——它已经死了，唯一的归宿是父进程 `wait`，或父进程自己也退出、把它托付出去。日常排障里看到成片 `Z`，结论几乎总是「某个父进程在泄漏 wait」。

Python 的 `subprocess` 在父进程这一侧替你做了 wait（Windows 10，Python 3.12.10 实测）：

```python
import subprocess, sys
r = subprocess.run([sys.executable, "-c", "raise SystemExit(3)"])
print("returncode:", r.returncode)
```

```text
returncode: 3
```

`r.returncode` 就是子进程的退出码；你拿到它的那一刻，收尸已经完成，所以用 subprocess 的人从不需要操心僵尸。反过来，若父亲死在儿子前面，儿子就成了**孤儿进程（orphan process）**：内核不会让它没人管，而是把它过继给祖先进程（WSL2 下实测，收养者是这个会话里 PID 363 的系统进程；标准 Linux 服务器上通常是 1 号进程）：

```text
orphan: parent gone, my getppid() is now 363
```

关键事实只有一条：`getppid()` 变了。孤儿可以继续跑，僵尸不再跑，两者都由内核兜底，区别只在「死没死透」。

## $\rm \S \, 2.5$ 线程：共享地址空间的进程

**线程（thread）**是共享同一地址空间与打开文件表、但各自持有一份寄存器现场与栈的执行流。按 PCB 的视角：两个线程就是两份记录共享同一张页表——剧场只有一套，台上并排站着两位演员。cs 册 §11.3 用 C++ 见过它的名字，这里用 Python 实测一个真竞态。两个线程各自把同一个计数器增 $10^5$ 次，账面应为 $2\times10^5$：

```python
import threading, time
counter = 0
def burn():
    global counter
    for _ in range(100000):
        tmp = counter          # 1. 读
        time.sleep(0)          # 2. 让出 GIL：放大读与写之间的竞态窗口
        counter = tmp + 1      # 3. 写回
ts = [threading.Thread(target=burn) for _ in range(2)]
for t in ts: t.start()
for t in ts: t.join()
print("expect 200000, got", counter)
```

本机（Windows 10，Python 3.12.10）连跑 5 次的真实结果：100057、100000、100520、100000、100637——全部远小于 200000。丢失更新的账很好算：线程 1 读到 5、还没写回 6 时，线程 2 也读到 5 并写回 6，线程 1 随后把自己的 6 盖上去——两次自增只剩一次。`time.sleep(0)` 在每轮读与写之间强制让出执行权，把「可能被打断」变成「必然被打断」，于是结果稳定地丢掉约一半。这里要诚实补一句：不加 `sleep(0)` 的裸 `counter += 1` 在本机跑 8 次全是 200000，因为 CPython 的全局解释器锁（Global Interpreter Lock，GIL）使得微秒级的线程切换踩不进纳秒级的读改写窗口——这是当前解释器的实现现状，不是语言承诺；换了自由线程的版本或其他运行时，裸写同样会丢。竞态的本质不在「跑出过错误值」，而在「语言不保证读改写不可分割」。给计数器加一把 `threading.Lock` 后，本机实测 3 次全部精确等于 200000；锁的机制是第 6 章的主题。

## $\rm \S \, 2.6$ 进程还是线程：同一维度的比较

选型先定维度。比较对象是「并发的执行单元选谁」，共同维度有四个：创建成本、隔离性、共享数据的代价、通信方式。

| 维度 | 进程 | 线程 |
| --- | --- | --- |
| 地址空间 | 各自独立（COW 起步） | 共享同一套 |
| 创建成本 | 高：复制 PCB、建页表 | 低：补一份栈与寄存器现场 |
| 崩溃隔离 | 一个崩不连坐 | 一个段错误带走整个进程 |
| 共享数据 | 要经进程间通信（管道、套接字、文件） | 直接读写共享变量，但要自己上锁 |

何时选谁，可以落成两条经验规则。选进程：需要故障隔离（浏览器给每个标签页一个进程，OJ 评测机把提交代码扔进独立进程——崩了不伤判题机），或需要绕开 GIL 做 CPU 并行。选线程：任务间本来就共享大量状态、以 I/O 等待为主、创建销毁频繁。两者都不是免费的：进程贵在隔离的成本，线程贵在共享的纪律。

## $\rm \S \, 2.9$ 本章自测答案

> 先闭卷作答 §2.7 与 §2.8，再核对。

### $\rm \S \, 2.9.1$ 关键概念回顾答案

1. PID 与父指针、地址空间（页表指针）、打开文件表、寄存器现场、状态与退出码。寄存器现场必须进账本：CPU 只有一套寄存器，时间片切换时全靠 PCB 存下「演到哪一句」，换人再装回。（§2.1）
2. 内核复印父进程的 PCB，父子从同一返回点继续，仅返回值一格不同：父得子 PID、子得 0。COW 让父子先共用只读页，谁先写谁复制，成本从「整个地址空间」降到「实际写过的页」。（§2.2）
3. PID、fd 表等账本内容不变，地址空间的代码与数据整个换掉。fork 与 exec 之间的窗口被 shell 用来改 fd 指向完成重定向——子进程换身后带着被调好的 fd 去运行新程序。（§2.3）
4. 僵尸：子已退出而父未 wait，退出码无人领取；孤儿：父先死，子被内核过继给祖先进程。僵尸已经死了，没有可执行的实体，kill 发出的信号无人接收，只能靠父进程 wait 或父进程退出转交。（§2.4）
5. 读、改、写三步之间被切换打断，另一线程的写覆盖了本线程的写回。裸写在本机不出错只是 CPython 当前实现恰好保护了纳秒级窗口，语言并未承诺读改写不可分割；锁才是把承诺补上的机制。（§2.5）

### $\rm \S \, 2.9.2$ 应用与辨析答案

1. 缺了对象与机制的对应：Linux 的 fork + exec 是两步、有 COW 兜底；Windows 的 CreateProcess 一步到位、创建即指定程序，两条路线各自完整，不能拿「少一步」推断「慢」。（§2.2、§2.3）
2. 先找父进程让它补 wait（或注册 `SIGCHLD` 处理）；短期内可让父进程退出，把僵尸托付给祖先进程收走；根治是改用 subprocess 这类替你 wait 的接口。僵尸本身杀不得也杀不死，处置对象是父进程的 wait 义务。（§2.4）
3. 199998 恰是丢更新的证据：两次自增被覆盖丢了两次。竞态的定义是「结果依赖于执行交错」，不是「结果一定错得离谱」；恰好在窗口外完成全部读改写时结果也会正确，这才使它难复现、难排查。（§2.5）
