# $\rm Chapter \, 1$ 像素与图像

图形学的最终交付物永远是同一种东西：一个二维数组。无论中间经过多少矩阵和着色公式，屏幕上出现的都是一张由小格子组成的图。所以整套书从「这个数组长什么样」开始：它如何存储、每个数代表什么、直接对它做算术会在哪里吃亏。这些问题看着平凡，但第 2 章的光栅化要决定「往哪个格子写什么颜色」，第 4 章的光照要在写之前算颜色，本章建立的词汇与陷阱后面每一章都在用。

> **开始前自检**：本章假设你已经会：
>
> 1. □ 二维数组按行优先存储、下标从 0 开始（C++ 基础；§1.1 与 §1.3 的实践直接使用）；
> 2. □ 字节与二进制：8 位恰好能表示 256 个不同的值（本站计算机系统分册；§1.3 的量化建立在其上）；
> 3. □ 加权平均与凸组合（高中数学；§1.4 的 alpha 合成是加权平均的直接应用）；
> 4. □ 幂函数 $y=x^a$ 的增减性（高中数学；§1.5 的 gamma 曲线就是幂函数）；

## $\rm \S \, 1.1$ 屏幕上的「图」在内存里是什么

把任何图片放大到足够倍数，会看到整齐的小方格，每个格子一种颜色。这不是放大算法的失真，而是图像的本相：**光栅图像（raster image）**就是**像素（pixel）**的二维数组。把屏幕想成一张巨大的方格纸，「一张图」就是每个格子该填什么颜色的完整说明书。比喻的边界也要说清：方格纸的格子有实体边界，像素没有——§1.5 末尾会给出更准确的像素观。

两个描述数组规模的词。**分辨率（resolution）**是横竖各有多少像素：$1920\times1080$ 共 $2073600$ 个像素；**纵横比（aspect ratio）**是横竖像素数之比，$1920/1080=16/9$，它决定画面是宽银幕还是竖屏。

内存开销可以手算：每像素红绿蓝三通道、每通道 1 字节，共 3 字节，$2073600\times3=6220800$ 字节，约 $5.93\ \mathrm{MiB}$。图像处理程序吃内存，根源就是「像素数 × 通道数 × 每通道字节数」这个乘积随分辨率平方级增长。

两个工程约定提前说定。其一，图像文件几乎都把第 0 行放在**最上面**，y 轴向下；而 OpenGL 的帧缓冲把第 0 行放在最下面——没有对错，但读写代码前先问一句「原点在哪」。其二，一个像素记录的不是「一小方块的颜色的平均」这种带面积的东西，而是连续图像**在这一个采样点上的取值**：格子之间的内容根本没有被记录。像素是采样样本，不是有面积的小方块——第 2 章问「几何覆盖了哪些采样点」时，这个观点会成为主角。

**本节小结**：图像是像素的二维数组，分辨率与纵横比说它的规模；像素是采样点上的取值，不是有面积的小方块。

## $\rm \S \, 1.2$ RGB 与加色混合

方格纸的每个格子要填「一种颜色」，颜色得先变成数字。人眼视网膜上有三类视锥细胞，分别对红、绿、蓝三个波段最敏感；只要三个数分别刺激这三类细胞，大脑就会「看到」想要的颜色的近似。这就是 **RGB（Red, Green, Blue）**：每个像素三个数、每个数一个通道的强度。

两个数值例子先建立手感。橙色记作 ${(255,165,0)}$：红通道拉满、绿通道过半、蓝通道为零；灰色 ${(128,128,128)}$：三通道相等。三通道等量时显灰这条性质，本章后面还会用到。

屏幕与颜料的混合规则相反，这件事值得单独强调。屏幕自己发光：红光加绿光得黄 ${(255,255,0)}$，越加越亮，这是**加色混合（additive mixing）**。颜料吸收光：越混越暗，美术课的红黄蓝三原色属于**减色混合（subtractive mixing）**。写图形学代码时你永远在加色那一边，用颜料直觉去猜混色结果几乎必错。

> **易混点**：屏幕上红+绿=黄，与颜料「红+黄=橙」不是同一套规则。加色混合的原色是红绿蓝，减色混合用的是青品黄，两套原色与两套混色表不可互相套用。

## $\rm \S \, 1.3$ 量化与存储：手写一个 PPM

物理亮度是连续量，一个通道却只有 256 个整数。把连续值四舍五入到最近的整数级，这个动作叫**量化（quantization）**，最多差半级的误差叫**量化误差（quantization error）**。平时它不可见，但在平缓的渐变区，相邻级之间的跳变会连成肉眼可见的条带（色带）。把每通道从 8 位浮点化到 16 或 32 位、允许数值远超 0 到 1 的图像叫 **HDR（High Dynamic Range）**，渲染管线的中间结果常用它，显示之前再压回 8 位。

文件格式只讲最简单的一种：**PPM（Portable PixMap）**。它是纯文本，结构是头三行加数据：第一行 `P3`，第二行宽和高，第三行每通道最大值，之后按行给出每个像素的三个整数。下面的脚本先写一幅宽 4、高 6 的竖直灰度渐变，再读回来逐值验证：

```python
W, H = 4, 6
rows = [round(255*y/(H-1)) for y in range(H)]      # 0,51,102,153,204,255
with open("grad.ppm", "w") as f:
    f.write(f"P3\n{W} {H}\n255\n")
    for y in range(H):
        for x in range(W):
            f.write(f"{rows[y]} {rows[y]} {rows[y]}\n")

data = open("grad.ppm").read().split()
assert data[:4] == ["P3", "4", "6", "255"]
px = [int(v) for v in data[4:]]
assert len(px) == W*H*3 and px[:3] == [0,0,0] and px[-3:] == [255,255,255]
print("readback ok, rows:", px[::W*3])
```

运行后打印 `readback ok, rows: [0, 51, 102, 153, 204, 255]`：设计值与读回值逐行一致。把第二行的 `4, 6` 与写数据时用的 `W, H` 故意改得不一致再跑，读回端会立刻断言失败——文件头里的宽高就是读方的「地图」，地图错了数据再对也读不出原图。

**本节小结**：量化把连续亮度压进 256 级，代价是渐变区的色带；PPM 用三行头加逐像素整数，头上的宽高是读方解释数据的地图。

## $\rm \S \, 1.4$ Alpha 与合成

界面弹窗、游戏特效都要求「半透明的图叠在另一张图上」。做法是给每个像素加第四个数 $\alpha$：0 表示全透明，1 表示不透明，带它的图像叫 RGBA。两层图像怎么合成，由 **over 算子**规定。白话：over 干的事就是按不透明度掺和——前景出多少由 $\alpha_f$ 定，剩下的份额全给背景：

$$
C=\alpha_f C_f+\left(1-\alpha_f\right) C_b
$$

逐符号读：$C_f$ 是前景像素的三通道颜色，$C_b$ 是背景的三通道颜色，$\alpha_f$ 是前景的不透明度，结果 $C$ 是合成后的三通道颜色。它就是一次加权平均：前景以 $\alpha_f$ 的权重、背景以 $1-\alpha_f$ 的权重。

手算一格。前景红 ${(255,0,0)}$、$\alpha_f=0.25$，背景白 ${(255,255,255)}$：

$$
\begin{aligned}
R &= 0.25\times255+0.75\times255=255 \\
G &= 0.25\times0+0.75\times255=191.25
\end{aligned}
$$

B 通道与 G 相同，四舍五入存回 8 位得 ${(255,191,191)}$——白底上蒙一层四分之一透明的红，得到浅粉。多层叠加时从最底下一层起逐层套用 over 即可，这个算子满足结合律，先合哪两层不影响最终结果。

**本节小结**：over 算子把半透明合成压成一次加权平均，多层叠加逐层套用、先后顺序不影响结果。

## $\rm \S \, 1.5$ gamma 与 sRGB

把两盏灯的物理亮度加倍，屏幕上的像素值并不加倍：像素值与物理亮度不成正比。原因是人眼对暗部的相对变化更敏感——若把 256 个级数按亮度均匀分掉，大量级数会浪费在人眼根本分不出差别的地方。所以显示器实际采用的传递函数在暗部塞了更多码值：主流标准是 **sRGB（standard RGB）**，曲线近似幂函数，像素值约等于物理亮度的 $1/2.2$ 次幂。你在代码里操作的 0 到 255，几乎从来不是线性亮度本身。

直接拿 sRGB 码值做算术会出错。对几个颜色对分别算「直接平均码值」与「先转线性亮度、平均、再转回码值」：

| 颜色对 | 直接平均码值 | 线性平均再转回 |
| --- | --- | --- |
| ${(0,255)}$ | $128$ | $188$ |
| ${(30,225)}$ | $128$ | $166$ |
| ${(64,192)}$ | $128$ | $146$ |
| ${(10,90)}$ | $50$ | $65$ |

等权混合黑与白，直接平均得 128，而亮度意义上的中点对应码值约 188——直接平均的中间调**偏暗**。验证只需两个转换函数：

```python
def s2l(c):                        # 码值 0..255 -> 线性亮度 0..1
    c /= 255
    return c/12.92 if c <= 0.04045 else ((c+0.055)/1.055)**2.4
def l2s(v):                        # 线性亮度 -> 码值
    s = 12.92*v if v <= 0.0031308 else 1.055*v**(1/2.4) - 0.055
    return round(s*255)
print(l2s((s2l(0) + s2l(255))/2))  # 188
print(l2s((s2l(30) + s2l(225))/2)) # 166
```

下面这个小部件把两种平均并排放着——拖动混合比例，看中间调差多少：

结论是一条工程纪律：混合、平均、光照这类运算都在**线性工作空间**进行，输出的最后一步才转回 sRGB。第 4 章的光照公式默认线性空间，原因就在这里。回头再补一句 §1.1 留下的话：既然像素只是采样点上的取值，「方格纸」的格子并没有实体边界——放大后看到的方块，是缩放算法在样本之间插值补出来的。

## $\rm \S \, 1.8$ 本章自测答案

> 先闭卷作答上面两节，再核对。

### $\rm \S \, 1.8.1$ 关键概念回顾答案

1. 像素记录的是连续图像在单个采样点上的取值，格子之间没有被记录的内容；它没有面积。「方格纸」失效在格子边界上——放大后看到的方块是插值算法补出来的，不是数据自带的。（§1.1、§1.5）
2. 人眼有三类视锥细胞，三个数足以分别刺激它们。${(255,255,0)}$ 是黄色；屏幕自发光，红光加绿光属于加色混合。（§1.2）
3. 上界是每通道半级，即 0.5。平缓渐变区最容易显形——相邻级的跳变连成色带。（§1.3）
4. $C=\alpha_f C_f+(1-\alpha_f)C_b$。$\alpha_f=0$ 时结果就是背景，前景完全透明；$\alpha_f=1$ 时结果就是前景，背景被完全遮住。（§1.4）
5. sRGB 码值相对线性亮度是非线性的，暗部被过度加权，等权平均的中间调比亮度意义上的中点更暗（黑与白平均得 128，线性正确值约 188）。正确流程：先转线性亮度，平均，再转回 sRGB。（§1.5）

### $\rm \S \, 1.8.2$ 应用与辨析答案

1. R：$0.5\times0+0.5\times200=100$；G：$0.5\times0+0.5\times120=60$；B：$0.5\times0+0.5\times40=20$。结果 ${(100,60,20)}$。（§1.4）
2. 平均是线性运算，应在线性亮度上做；直接平均 sRGB 码值会把中间调压暗（上表），整图缩小时每像素都是多次平均，偏暗累积成整体发灰发暗。修法：每像素先转线性，平均后再转回 sRGB 写出。（§1.5）
3. 读方按头部的「宽 6 高 4」切分数据：总像素数仍是 24，断言可能不报错，但每「行」6 个像素横跨了真实数据的两行，图像内容错位、颜色串行。宽高是读方解释数据的地图，错地图比错数据更隐蔽。（§1.3）
