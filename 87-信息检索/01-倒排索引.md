全册的心智模型在本章立起来：检索是在几十亿文档里回答「哪些文档与这句话相关」，而要排序就得先有分数，所以全册做的事情是把相关性变成可排序的分数。分数要一个文档一个文档地算，前提是先把候选从几十亿里捞出来。捞 candidates 这一层的整套 machinery，就是信息检索的底层：索引怎么建、查询怎么跑、存储怎么压。它是后面七章每一页都要踩的地板。

本章只讲这块地板：倒排索引（inverted index）。按顺序回答四个问题：搜索引擎为什么不扫全库（§1.1、§1.2）；索引怎么从一份文档流里长出来（§1.3）；两个查询词的记录表如何在远小于表长的时间内求交集（§1.4）；一条倒排记录怎么从 4 字节压到 1 字节（§1.6）。§1.5 把全部声称的数字真跑一遍。读完本章你能对一份自己的文档集合，说清索引每一字节花在哪、查询每一步花在哪。

## $\rm \S \, 1.1$ 任务：在几十亿文档里回答「谁含有这个词」

最朴素的找法人人都会：拿着查询词，把每个文档从头到尾扫一遍，扫到就记下文档号。这套做法的正确性无可指摘，毛病在账上。设文档集合共有 $D$ 个文档、平均长度 $L$ 个词，一次扫描要读的字符总量是 ${\Theta(D \cdot L)}$。在你自己的笔记本上扫一万篇摘要毫无压力；网页搜索的语料是几千亿个文档，查询响应却要求在几百毫秒内给出，两条数字之间差着十几个数量级，靠更快的 CPU 补不回来。账的形状不对：每次查询都付全款，而全款与查询本身毫无关系。查「注意力机制」和查「量子纠缠」，扫的字符一样多。

出路是把付钱的时机挪走。书末的索引页已经示范过这件事：出版社在装订前花一趟功夫，把每个术语出现在哪些页码列成一张排好序的表；读者翻书时不再通读，直接查表翻页。检索引擎做的是同一件事，只是把「装订前」换成了「建库时」，把「页码」换成了「文档号」。代价一次性付出，此后每次查询只碰与查询词有关的条目，账从「每次查询 $\Theta(DL)$」变成「每次查询正比于答案涉及的记录数」。全册后面所有的排序打分都建立在这笔账被改写之后。

先把三个名词钉死，本章乃至全册都在它们上面走：

1. 文档（document）：检索的基本单位，可以是一篇论文、一个网页、一条聊天记录。给它一个从 0 开始的文档号（doc id）。
2. 词例（token）：文档里每一次实际出现的词。「猫追猫」里有三个词例。
3. 词项（term）：词典里的条目，索引的键。「猫追猫」整理成词项后只有「猫」和「追」两个，每个词项名下挂着含有它的文档号清单。

词例从文本里切出来的过程叫分词。英文靠空格与规范化（大小写、词根），中文没有空格可倚仗，需要专门的分词器；本套教材《LLM 从零构建》§3.2 至 §3.5 讲过 BPE 分词器的全套账，本章不重复，只约定：进入索引之前，每个文档已经是一串词例。此外每个词项在写进词典前通常还要做归一化（大小写折叠、单复数归并），让「Cat」和「cats」落到同一条词项上，本章实验里词表已经是干净的，不涉及这一步。

## $\rm \S \, 1.2$ 词项-文档矩阵：对但太贵的第一答案

把「哪个文档含有哪个词项」整个写下来，最直接的形状是一张矩阵。词项-文档矩阵（term-document incidence matrix）$M$ 的每一行是一个词项，每一列是一个文档：

$$
M[t,d]=
\begin{cases}
1, & \text{文档 } d \text{ 含有词项 } t \\
0, & \text{否则}
\end{cases}
$$

读法：$t$ 是词项编号，$d$ 是文档编号，$M[t,d]$ 记录「第 $t$ 个词项是否出现在第 $d$ 个文档里」。有了它，布尔查询变成行运算：查「$t_1$ AND $t_2$」就是取出两行做按位与，结果行里为 1 的列就是答案文档。这个表示完全正确，毛病在两笔账上，而且两笔都是固定支出。

第一笔是存储。矩阵要为每个格子留位置，字节数被 ${N \cdot V}$ 钉死（$N$ 是文档数，$V$ 是词表大小）。而真实的文档集合里这张矩阵极度稀疏：一篇几千词的文档只会碰到几十万词表里的一小片，绝大多数格子在全部生命周期里都是 0，却一直占着位置。语料翻一倍、词表长一倍，即使内容一点没变多，这张矩阵的租金也翻两番。第二笔是查询。要枚举「词项 $t$ 出现在哪些文档」，哪怕它只出现在 3 个文档里，也得把长度 $N$ 的整行扫完才能找齐那 3 个 1。存储为 0 付钱，查询为 0 扫描，两张账单上全是「没有的东西」。

这个处境你在图论里见过。邻接矩阵同样把空间钉死在「顶点数的平方」，同样让稀疏图把预算花在根本不存在的边上，而邻接表的立场是只记账发生的事：每个顶点名下挂一条链，链上只有它真正指向的邻居（§5.2）。把这套立场搬到检索上，就得到本章的主角。

> 本节小结：词项-文档矩阵把布尔查询变成行运算，但存储与查询两笔账都为 0 付费；稀疏性决定了该换邻接表式的表示。

## $\rm \S \, 1.3$ 倒排索引：只记账发生的事

倒排索引（inverted index）就是检索版的邻接表，两大件：

1. 词典（dictionary）：全部词项的名单，每个词项挂一个指针，指向它的记录表。词典本身用哈希表或排序数组实现，做到「报出词项，一步定位」。
2. 倒排记录表（posting list）：每个词项一条，按文档号升序存放所有含有该词项的文档号，每条记录叫一个倒排记录（posting）。

「倒排」这个词是对矩阵视角说的：矩阵按文档组织内容（一列是一个文档的词表），索引按词项组织内容（一行缩成一条记录表）。查询「$t_1$ AND $t_2$」从「矩阵两行按位与」变成「两条有序记录表求交集」，§1.4 专门讲怎么求得快。矩阵里那片 0 的汪洋，在倒排索引里根本不存在：词项没出现，就没有记录，一个字节都不付。

小语料上的构建只要一趟扫描。词例流按文档顺序喂进来，词典用哈希表挂着，每条记录表只管追加：

```python
inv = {}
for d, toks in enumerate(docs):      # docs: 每文档一个词例列表, 已按文档号升序
    for w in toks:
        lst = inv.setdefault(w, [])  # 词典里没有这个词项就立一条
        if lst[-1:] != [d]:          # 同一文档内同一词项只记一次
            lst.append(d)            # d 递增, 记录表天然有序
```

整个构建是 ${\Theta(T)}$，$T$ 是全库词例总数，§1.5 会实测这笔账。记录表的升序是白捡的：文档号本来就按扫描顺序递增，追加即有序。这个升序不是小事，§1.4 的跳表和 §1.6 的 delta 压缩全都踩在它上面。

几百万文档起，哈希词典和整片记录表在内存里同时长到装不下，构建策略换挡成基于排序的构建：把语料切成块，每块独立地扫出「词项，文档号」对、排序、落盘；全部块落完再做多路归并，同一词项的记录散在各块里，归并时按词项收拢，拼成的正是完整记录表。代价从「一张放进内存的大表」变成「可以流式处理的有序对」，存储挪到磁盘，内存只需容纳当前块。这套「分块、排序、归并」的骨架正是 MapReduce 的原型：map 阶段对每个词例输出「词项， 文档号」，reduce 阶段收到某词项名下的全部文档号，顺序拼接就是记录表，洗牌阶段的排序把最贵的一步免费完成了（《分布式系统》§2.2）。本册实验规模小，用哈希直建即可，但账要会算：块越大排序越省归并，块越小内存越省，取舍在 §1.5 的口径之外，属于真实建库时才需要操心的事。

> 竞赛生迁移提示：这张结构与图算法里的前向星如出一辙：词典就是 head 数组，记录表就是按链串起来的边表。你在 OJ 上写过一万遍的「桶＋链」，就是搜索引擎几千亿文档的存储骨架。

> 本节小结：倒排索引＝词典＋按文档号升序的记录表；小语料一趟扫描 $\Theta(T)$ 直建，大语料分块排序再归并，升序免费带来跳表与压缩的全部红利。

## $\rm \S \, 1.4$ 跳表指针：查询时的投机

有了倒排索引，布尔查询的核心动作是「两条升序记录表求交集」。双指针合并你已经写过无数遍：两根指针分别指着两条表的当前记录，小的前进，相等就收进答案：

```python
def merge_and(l1, l2):
    i = j = 0
    out = []
    while i < len(l1) and j < len(l2):
        if l1[i] == l2[j]:
            out.append(l1[i]); i += 1; j += 1
        elif l1[i] < l2[j]:
            i += 1
        else:
            j += 1
    return out
```

代价是 ${\Theta(p_1 + p_2)}$，$p_1$、$p_2$ 是两条表的长度。真实查询里这个界经常被一侧单独拉爆：查「the AND entanglement」，"the" 名下挂着几乎全库的文档，"entanglement" 只挂几百条；合并却要把 the 的整条表陪走一遍，走完 ${10^{9}}$ 条才确认 300 条答案。大头花在了长表上，而长表的大多数记录与答案毫无关系。

跳表指针（skip pointer）是给长表装的「快进键」：在记录表里每隔固定条数预埋一个指针，指向表中前方某个位置的文档号，间隔通常取 $\sqrt{p}$（$p$ 是表长）。合并时长表的指针不再是只会加一的老实人，它多会一招：当自己落后于对面指针时，先看前方的跳点——

$$
\text{若 } l_1[i] < l_2[j] \text{ 且 } l_1[i + s] \le l_2[j], \text{ 则 } i \mathrel{\mathrel{+}=} s \text{（一次越过 } s \text{ 条记录）}
$$

读法：$s$ 是跳步间隔，$l_1[i+s]$ 是 $i$ 前方下一个跳点处的文档号。条件写得很吝啬：跳过去必须仍不超过 $l_2[j]$ 才允许跳。这不是保守，是正确性所系：两条表求的是交集，跳过任何「可能等于 $l_2[j]$ 的记录」都会漏答案；只有确认「这一整段连碰面的资格都没有」时，跳步才是白赚的。指针在跳点之间照常一格一格走，所以答案一个不漏，而运气好时一次跳步替掉几百次「加一、比较、加一」。

收益不是白拿的，它有两层前提，恰好构成适用条件清单：

1. 两条表的密度差要够大。短表的文档号间隔越远，长表的跳点才越有机会整段整段地跃过无人区；两条表一样密时，长表几乎每条记录都紧挨着对面指针，跳步条件极少满足，指针退化为普通合并。§1.5 用同一份语料把「零收益」与「大收益」两种情形都量了出来。
2. 索引要基本静态。跳点指向的是「插入新记录后就会漂移」的位置；文档集合频繁增删时，维护跳点的开销会吃掉它省下的查询时间。搜索引擎的索引按批重建，正适合装跳表。

> 本节小结：双指针合并 ${\Theta(p_1+p_2)}$，长表陪短表走全程；跳表指针按 $\sqrt{p}$ 预埋快进键，「跳过去仍不超过对面」才跳，收益取决于两表密度差，静态索引才划算。

全库 ${87.8\%}$ 的 gap（${145239}$ 条）不足 ${128}$，一个字节就装下；高频词的 delta 每条恒定 1 字节，是定长的四分之一，低频词 gap 变大，红利随密度衰减。程序另做了两道独立对账：跳表合并与朴素合并的交集逐条相等（三对全过）；delta＋VBYTE 随机抽 ${50}$ 个词项编码后再解码，逐条复原原表。压缩没有改变索引回答了什么，只改变了回答的成本。

白话：这一节做的事还是拿数据对口供。定理说矩阵被 ${N \cdot V}$ 钉死，实测空格子占 ${98\%}$、倒排存储是它的十分之一；定理说跳步收益看密度差，实测同一份语料上从 ${0\%}$ 到 ${78\%}$ 全谱出现；定理说 gap 比文档号小，实测 ${87.8\%}$ 的 gap 一字节装下。

> 本节小结：${2000}$ 文档合成语料实测，矩阵 ${10^{7}}$ 字节对倒排 ${1.01 \times 10^{6}}$ 字节；跳表节省随两表密度差从 ${0\%}$ 到 ${78.2\%}$；delta＋VBYTE 把记录压到定长的 ${28.0\%}$。

## $\rm \S \, 1.6$ 压缩：delta 与 VBYTE

记录表按文档号升序，这条免费的红利在存储侧还有一笔没收：表里相邻记录挨得极近，用 4 字节定长存每个文档号，等于用能表示四十亿的位数去记一个多半不超过几千的间隔。压缩分两步把这笔浪费收走。

第一步是 delta 编码（delta encoding）：把每条记录改存它与前一条的差。设记录表为 ${d_1 < d_2 < \cdots < d_p}$，改存

$$
g_1=d_1,\qquad g_i=d_i-d_{i-1}\ (\forall\, i\ge 2)
$$

读法：$g_i$ 是第 $i$ 条记录的间隔（gap），首记录没有前驱，原样存文档号本身。解码时从 $g_1$ 出发逐条累加 ${\sum g_k}$ 即复原 $d_i$——升序保证每个 gap 非负，这是记录表必须有序的第二个理由。高频词的记录在文档号轴上几乎一个挨一个，$g_i$ 多半是 1、2、3 这种小整数；§1.5 实测全库 ${87.8\%}$ 的 gap 小于 ${128}$。

第二步是 VBYTE（variable byte，可变字节编码）：让小整数真的少占字节。把整数 $x$ 的二进制从低位起每 ${7}$ 位切一组，每组装进一个字节，字节的高位当「续读标记」——为 1 表示后面还有组，为 0 表示这是最后一个字节。例：文档号 ${8243}$ 分解为 ${64 \cdot 128 + 51}$，编成两个字节 ${\texttt{0xC0}}$、${\texttt{0x33}}$：首字节高位 1、载荷 ${64}$，表示「后面还有」；次字节高位 0、载荷 ${51}$，表示「到此为止」。解码器逐字节读，遇到高位 0 就收工，复原 ${64 \cdot 128 + 51 = 8243}$。小于 ${128}$ 的数一个字节完成，最大到 ${2^{28}}$ 也只花 4 个字节，与定长持平。这套编码是「按字节对齐」的变长码，位级变长码（如 $\gamma$ 编码）还能再省，但对齐换来的解码速度让 VBYTE 成了工程首选，本册停在字节级。

两步合起来，§1.5 实测记录表从定长 ${661628}$ 字节压到 ${185575}$ 字节，${28.0\%}$。压缩的代价要如实入账：查询时每条记录要先解码才能参与合并，CPU 多付一道；这笔交换合不合算取决于瓶颈在哪——按《数据库系统》§2.1 的代价模型，磁盘按页计费，索引从磁盘读入时省下的传输与缓存占用通常远超解码的 CPU 开销，真实搜索引擎几乎无一例外压缩存储；但若索引常驻内存、查询又以短表为主，解码开销开始变得可见。压缩不是无条件的改进，它是「存储瓶颈换计算开销」的一笔兑换。

> 本节小结：delta 把「文档号」换成「间隔」，升序保证间隔非负；VBYTE 按 7 位一组变长存放，小数省字节；两者叠加实测压到定长的 ${28.0\%}$，代价是查询时的解码 CPU。

## $\rm \S \, 1.7$ 代价账与通往排序

把本章的能力与缺口并成一表：

| 维度 | 本章到达的位置 |
| --- | --- |
| 构建 | 一趟扫描 ${\Theta(T)}$，大语料分块排序归并 |
| 存储 | 只记非零项，delta＋VBYTE 后约 ${0.33}$ 字节每词例 |
| 查询 | 布尔查询毫秒级返回「含有全部词项」的文档集合 |

第三行藏着本章没碰的缺口：布尔查询的返回是一个无序集合。「the AND entropy」可能命中 ${10^{6}}$ 个文档，用户屏幕上只有十条位置，谁排第一？「含有」不等于「相关」——一篇文档提一句熵和一篇通篇讨论熵的论文，在布尔账上是同一个 1。给每个「文档， 查询」对算出一个可排序的相关性分数，需要的原料（词在一篇文档里出现了几次、这个词在多少文档里出现过）恰好都躺在倒排索引旁边。下一章就在这套骨架上加一台计分器：TF-IDF 与向量空间模型。

## $\rm \S \, 1.10$ 本章自测答案

概念回顾答案：

1. 词典（词项到记录表的定位）与倒排记录表（词项名下按文档号升序的文档号清单）。依赖升序的机制两个：双指针合并靠两边同时前进求交集；delta 压缩靠升序保证间隔非负、可复原（§1.3、§1.6）。
2. 矩阵存储被 ${N \cdot V}$ 钉死、查询要为 0 扫整行。倒排的立场是只记账发生的事：没出现的词项一个字节不付（存储）；记录表里只有真正含有的文档，直取即得（查询）（§1.2、§1.3）。
3. 依赖哈希表「平均一次算术定位键」的合同，让每个词例都能 ${O(1)}$ 找到自己的记录表。装不下时换挡成分块排序＋多路归并：每块独立排序落盘，归并时同词项记录收拢成表（§1.3）。
4. 交集要求两条表都枚举完各自的候选，跳过任何仍可能等于对面当前值的记录会直接漏答案；条件保证被跳过的整段与交集无缘，跳步才不亏正确性（§1.4）。
5. 语料对一（两表都密，短表均间隔约 ${8}$）零收益，${0}$ 次跳步；语料对二（短表均间隔约 ${200}$）节省 ${78.2\%}$，间隔差约 ${25}$ 倍。结论：短表间隔显著超过跳点跨度（即两表密度差大）时才值得装跳表（§1.5）。
6. delta 把「绝对文档号」换成「与前一条的间隔」，从记录里移走的是文档号的高位信息。解码时靠逐条累加补回：${d_i=\sum_{k \le i} g_k}$；有序性保证间隔非负，否则累加无法复原（§1.6）。

应用与辨析答案：

1. 两种方案解的是不同形状的问题。一万篇规模上 SQLite 的 B＋树索引足够，标签与年份都是结构化字段，数据库按行过滤的账已经够快；自建倒排的钱花在全文词项级检索上，对「标签」这种受控词表是杀鸡用牛刀。涨到一千万篇，全文查询（摘要内容搜索）成为主要负载时倒排才值回票价，而标签/年份过滤仍该留在数据库侧——工程答案是两边分工，不是二选一（§1.1、《数据库系统》§3）。
2. 对的一半：间隔小意味着跳点密，单次跳步覆盖小但机会多，实测语料对二那样的稀疏短表上确实省步数。错的一半：实测合成对显示跳步只在短表间隔超过跳点跨度时才开火，间隔从 $\sqrt{p}$ 压到 ${8}$ 不会让等密度查询（语料对一）多出任何一次跳步。两个代价：跳点本身占存储，间隔 ${8}$ 时跳点数涨约 ${56}$ 倍（对 $\sqrt{p}$ 间隔）；每一步都要多查一次跳点表，未开火的跳步全是白付的查询开销（§1.4、§1.5）。
3. VBYTE 直存在文档号本身很小或表极短时几乎不亏（每条最多 2 字节对 delta 的 1 字节）；亏得最狠的是高频词的反面——低频词：文档号大（直存 2 字节）而间隔同样大（delta 也要 2 字节），直存没有把「相邻记录挨得近」变现。全库尺度：直存 ${319941}$ 字节对 delta ${185575}$ 字节，多付约 ${73\%}$，即放弃约五分之二的压缩空间（§1.5、§1.6）。
