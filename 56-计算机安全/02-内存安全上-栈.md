## $\rm \S \, 2.1$ 函数调用在栈上留下了什么

先看机制账。任何 C 程序都是一串函数调用，函数 A 调用 B，B 执行完必须回到 A 里「调用的下一条指令」处继续。问题在于：CPU 只有一个指令指针，B 执行时这个指针在 B 内部，那「回到哪里」这件事记在哪？答案是栈（stack）：进程地址空间里一段专门的内存，由两个寄存器管理，`rsp` 指向栈顶，栈向低地址生长。执行 `call` 指令时，CPU 自动把返回地址（return address，即调用指令的下一条指令地址）压入栈顶；执行 `ret` 指令时，CPU 从栈顶弹出那个值，直接跳过去。注意这个「直接」：`ret` 对目标不做任何检查，这是本章全部故事的支点。

一个函数从进入到返回，在栈上占用的一段连续区域叫栈帧（stack frame）。以 x86-64 的通行安排为例，从高地址到低地址依次是：返回地址、调用方的帧指针（进入时 `push rbp` 保存）、本函数的局部变量。换句话说，**返回地址就躺在局部变量的楼上，中间只隔固定几十个字节**。这句朴素的话是 §2.2 一切推演的前提，我们先用实验把它钉死。

下面的程序只做观测：函数 `show` 里声明两个局部数组，然后用 `__builtin_frame_address(0)`（gcc 内建，取当前函数帧指针的地址）和 `__builtin_return_address(0)`（取返回地址槽的地址与当前值）把布局打印出来，不写任何越界数据。

```bash
# Bash / WSL，当前目录 expSEC02
gcc -O0 -fno-stack-protector -o layout_nsp layout.c
./layout_nsp        # 观察 buf、tag 与返回地址槽的相对位置；跑两次对比绝对地址
```

实测输出（两次运行）：

```text
--- layout_nsp run1 ---                    --- layout_nsp run2 ---
buf       @ 0x7ffe9dcd35d0                 buf       @ 0x7fff46309140
tag       @ 0x7ffe9dcd35c8 (tag-buf=-8)    tag       @ 0x7fff46309138 (tag-buf=-8)
frame     @ 0x7ffe9dcd35f0 (saved rbp 槽)  frame     @ 0x7fff46309160 (saved rbp 槽)
ret slot  @ 0x7ffe9dcd35f8 (frame+8)       ret slot  @ 0x7fff46309168 (frame+8)
canary槽  @ 0x7ffe9dcd35e8 (frame-8)       canary槽  @ 0x7fff46309158 (frame-8)
```

三个读法。第一，`frame+8` 正是返回地址槽，当前值 `0x5bfe2e163247` 指向 `main` 内，`ret` 一执行 CPU 就会去那里取指令。第二，`buf` 在 `frame-0x20`，所以从这个构建的 `buf` 到返回地址槽的距离是 `0x28`，即 40 字节：`buf` 多写 40 个字节，第 41 到 48 字节就正好落在返回地址上。第三，两次运行的绝对地址不一样，这不是抖动，是 §2.5 要讲的地址空间布局随机化在起作用，此处先按下。

```text
高地址 ┌────────────────────────────┐
       │   调用方（main）的栈帧        │
       ├────────────────────────────┤
       │   返回地址                   │ ← frame+8，ret 之后 CPU 跳到这里
       ├────────────────────────────┤
       │   saved rbp（调用方帧指针）   │ ← frame
       ├────────────────────────────┤
       │   canary（protector 构建才有）│ ← frame-8
       ├────────────────────────────┤
       │   buf[16]                   │ ← frame-0x20
       │   tag[8]                    │ ← frame-0x28
       └────────────────────────────┘
低地址（栈向低处生长，更高的新帧画在上面）
```

白话：栈帧像一摞从下往上叠的便签，每张便签的右上角贴着一张「办完事回哪儿」的回执（返回地址），回执就压在你写的草稿（局部变量）正上方，中间没有隔板。

**本节小结**：`call` 压栈、`ret` 弹栈跳转且不做检查；返回地址与局部变量同帧而居，实测相距仅几十字节，这条「物理事实」是溢出能够劫持控制流的全部地形。

## $\rm \S \, 2.2$ 一次越界写如何变成控制流劫持

有了地形，缺的只是一个不检查边界的写。C 语言的数组没有长度信息，`fread`、`memcpy`、`strcpy` 这类函数按你给的大小照单全收，写多大规模完全由调用者负责。于是下面这条代码在「`buf` 只有 16 字节」和「一次读 512 字节」并存时，就是一个漏洞：多出来的字节会沿着栈向高地址蔓延，依次碾过 `buf` 之后的每个槽位。向缓冲区写入超出其容量的数据，就叫缓冲区溢出（buffer overflow）；发生在栈帧里的叫栈缓冲区溢出。

溢出能到哪、碾过什么，取决于这个构建里 `buf` 到返回地址槽的实际距离。我们用第二个程序实测它：`vuln_segv.c` 与实验程序相同地声明 `char buf[16]` 并用 `fread` 读入，但把观测量放在全局区（栈外），并在返回前后把关键槽位的值打印出来；另装一个 SIGSEGV 处理器，崩溃瞬间打印内核报告的故障信息。观测代码不影响被观测的布局逻辑。

```bash
# Bash / WSL
gcc -O0 -fno-stack-protector -o v_segv vuln_segv.c
python3 -c "open('payloadA.bin','wb').write(b'A'*512)"   # 512 个 'A'
./v_segv payloadA.bin
```

第一步，量距离。输出第一行是 `距离=200 字节`：在这个构建里，`buf` 之后要写 200 字节才够到返回地址槽（与 §2.1 的 40 不同，因为该函数里还有别的局部对象；距离随构建而变，思路不变）。512 个 `A` 远远越过它，于是读回的槽位值变成了这样：

```text
read 512 bytes; after fread: saved_rbp=0x4141414141414141 ret_slot=0x4141414141414141
[SIGSEGV] si_code=128 (SI_KERNEL) si_addr=(nil) RIP=0x5cdc9ffcb461
```

`0x41` 正是字符 `A` 的编码：保存的帧指针和返回地址槽，全被输入数据替换成了 `0x4141414141414141`。但程序没有死在「跳到 0x4141414141414141」上，内核报告的是 `si_code=128`（SI_KERNEL，内核态异常）且故障地址为空。原因在地址格式本身：x86-64 规定 64 位地址中高 16 位必须是低 48 位的符号扩展，这种地址称为规范地址（canonical address），`0x4141414141414141` 不满足，CPU 在尝试取下一条指令时触发的是通用保护异常而非缺页。程序死于「不知道该去哪」。

把目标换成一个合法但无映射的地址，观测会干净得多。构造 216 字节的输入：前 200 个 `A` 精确填满 `buf` 到返回地址槽之间的区域（顺带把 saved rbp 也填成 `A`），随后的 8 字节是小端序的 `0x000000000041414141`，正好落进返回地址槽。

```bash
python3 -c "
import struct
open('payload4.bin','wb').write(b'A'*200 + struct.pack('<Q',0x41414141) + b'B'*8)"
./v_segv payload4.bin
```

这份 216 字节的输入，每一字节落在哪，全部有实测读回值作证：

```text
字节偏移      内容                  落点（v_segv 构建，实测距离 200）
0..199      'A' × 200            从 buf[0] 起一路向上，正好填到返回地址槽正下方
其中 192..199（含在上面）           落在 saved rbp 槽，读回 0x4141414141414141
200..207    0x000000000041414141  落在返回地址槽，读回 0x41414141
208..215    'B' × 8              落在调用方帧内，本次观测未用到
```

```text
read 216 bytes; after fread: saved_rbp=0x4141414141414141 ret_slot=0x41414141
[SIGSEGV] si_code=1 (SEGV_MAPERR) si_addr=0x41414141 RIP=0x41414141
```

逐行读这份输出，这是全章最关键的三行。`ret_slot=0x41414141`：读回的槽位值确认我们写的地址确实落在那里。`RIP=0x41414141`：崩溃瞬间，指令指针的值就是我们写进去的那个值，CPU 已经真的去 `0x41414141` 取指令了。`si_addr=0x41414141`、`si_code=1`（SEGV_MAPERR，访问未映射内存）：内核确认这是一次访问不存在地址的缺页。三个数字互相印证，结论只有一个：**函数返回后指令指针的值，完全由我们写入的数据决定**。控制流被输入接管，这就是「失控」的机制定义。`ret` 不检查目标，而目标的来源是栈上的数据，数据可写，于是跳转目标可写。

顺带把崩溃词汇表补齐。内核在程序访问不该访问的内存时发送 SIGSEGV 信号，术语叫段错误（segmentation fault）；shell 显示 `Segmentation fault`，退出码 139 是「128 加信号编号 11」的约定。若程序被 SIGABRT（编号 6）终止，退出码则是 134，§2.4 会见到。

白话：返回地址是 CPU 的一张「回程票」，票就插在你桌上的文件堆最上层；谁能往文件堆里塞纸，谁就能换掉这张票，而检票口（`ret`）从不验票，只认票面。

**本节小结**：C 不检查数组边界，一次越界写沿栈向上碾过 saved rbp 与返回地址；实测读回槽位值、故障地址与 RIP 三者一致，证明返回后指令指针完全由输入数据决定。本章的机制讲解到此为止，只演示了崩溃，没有构造任何利用。

## $\rm \S \, 2.3$ 两代利用思想：注入与复用

崩溃本身只损失可用性，攻击者要的是机密性与完整性：让程序「返回」到能干活的地方。历史上形成两代思路，本节只讲思想，不写任何可操作的构造细节。

第一代是注入。既然跳转目标任意，就把一段机器码连同 payload 一起写进 `buf`，再把返回地址改成 `buf` 自己的地址：函数一返回，CPU 开始「执行」这份输入数据。这段机器码的典型功能是启动一个 shell，故得名 shellcode。它在 §2.1 的地形上是自洽的：地址可预测（老系统不开随机化），栈上内容可写。

第二代回应的是防御：现代系统默认栈页不可执行（§2.4 的 NX），放进栈的机器码读得出来、执行不了。二代思路换了目标：不再注入新代码，而是复用程序和库里**已经存在**的指令。可执行内存里到处是以 `ret` 结尾的短指令序列（行话叫 gadget），把它们用栈上的「假返回地址链」串起来，就能拼出任意逻辑。这叫返回导向编程（Return-Oriented Programming，ROP），思想层面一句话说完：攻击面从「写什么代码」变成「怎么排列已有代码的地址」，而后者用的还是 §2.2 那个被接管了的返回地址。本册到此止步，不再深入。

白话：一代是往你家门口塞一张写着指令的纸条，指望你照着念；NX 相当于规定「门口的纸条一律不许念出声」；二代不塞纸条了，改把你家里现成的每句话拆成词，重新排列成新的命令。

**本节小结**：注入利用「栈可执行」，ROP 利用「代码可复用」；防御与利用的每一次换防，都发生在「某个默认假设被颠倒」的地方，这正是下一节的主题。

## $\rm \S \, 2.4$ 编译期缓解：canary 与 NX

先装第一道闸：金丝雀（stack canary）。名称源自矿工笼里的金丝雀，毒气来了它先死。机制分三步：函数入口处，编译器插入代码，把一个每次运行都不同的随机值写进 canary 槽（实测位置 `frame-8`，正好横在局部变量与 saved rbp 之间）；函数返回前，把槽里的值与备份比对；不一致就调用 `__stack_chk_fail`，进程立即被 abort。任何溢出想从 `buf` 摸到返回地址，必经 canary 槽，从而必然打碎它。

glibc 的实现惯例有两点值得知道：canary 取自内核在进程启动时提供的随机字节（AT_RANDOM 辅助向量），每个进程都不同；最低字节固定为 `0x00`，这样基于字符串的读写函数一碰到它就停，整块 canary 不会被字符串操作带出去或续写过去。盲猜一次成功的概率是

$$
P_{\text{一次猜对}} = 2^{-64}
$$

读法：canary 是 64 位随机数，不带任何信息泄露硬猜，期望要试 ${2^{63}}$ 次，而猜错一次进程当场死亡，连试的机会都攒不下来。它的绕过思路因此只有一句话：先利用另一个信息泄露漏洞把 canary 读出来。

实测它。用同一份 216 字节 payload 跑四个构建，两两只差一个开关：

```bash
gcc -O0 -fno-stack-protector              -o v_nsp    vuln.c   # canary 关
gcc -O0 -fstack-protector-strong          -o v_sp     vuln.c   # canary 开
gcc -O0 -fno-stack-protector     -z execstack -o v_nsp_nx vuln.c # canary 关，栈可执行
gcc -O0 -fstack-protector-strong -z execstack -o v_sp_nx vuln.c # canary 开，栈可执行
for t in v_nsp v_nsp_nx v_sp v_sp_nx; do ./$t payload4.bin; echo "exit=$?"; done
```

| 构建     | canary | 栈可执行 | 读入 216 字节后的行为                    | 退出码 |
| -------- | ------ | -------- | ---------------------------------------- | ------ |
| v_nsp    | 关     | 否       | 段错误，返回地址被接管                   | 139    |
| v_nsp_nx | 关     | 是       | 段错误，返回地址被接管                   | 139    |
| v_sp     | 开     | 否       | `*** stack smashing detected ***` 后中止 | 134    |
| v_sp_nx  | 开     | 是       | 同上                                     | 134    |

两行读法。开 canary 的两个构建，崩溃信息从 `Segmentation fault` 换成了 `stack smashing detected`，退出码从 139（SIGSEGV）变成 134（SIGABRT），而且崩溃发生在打印完 `read 216 bytes...` 之后、`ret` 执行之前：比对逻辑拦在了跳转之前，控制流根本没被接管。canary 不阻止溢出发生，阻止的是溢出**变现**。

第二道闸：不可执行栈。分页系统给每个内存页记权限位（读、写、执行），NX（No-eXecute）就是把栈页的执行位去掉，让「栈上的字节被当代码取指」这件事在硬件层直接缺页拒绝。它践行的是 §1.3 的安全默认值与最小权限：数据页凭什么需要被执行？实测对比两份只有链接开关差异的程序，各自打印自己 `/proc/self/maps` 里栈那一行的权限位：

```text
默认(-z执行位不动):  7fffc0a20000-7fffc0a41000 rw-p ... [stack]
-z execstack:        7ffc6e5dc000-7ffc6e5fd000 rwxp ... [stack]
```

`rw-p` 是可读写、不可执行；`rwxp` 把执行位还给了栈，这正是 shellcode 时代的老默认。注意一个诚实的观察：本次实验里，`v_nsp_nx` 与 `v_nsp` 的崩溃行为完全相同（都退出 139）。因为我们的 payload 里只有字母没有代码，NX 挡不住「跳到坏地址」这种崩溃，它挡的是 §2.3 第一代「在栈上执行注入代码」这下一步。每道缓解各管一段，没有一道管全部，这就是 §1.3 纵深防御的理由。

白话：canary 是压在重要文件上的一张复写纸，谁动过文件堆，回来一对就露馅；NX 是把「草稿区」和「演讲台」分开，草稿写得再像讲稿也不许上台念。

**本节小结**：canary 以「返回前比对」拦下溢出变现（实测退出码 139 变 134，拦截发生在 `ret` 之前）；NX 以页权限位掐断注入执行（实测栈页 `rw-p` 对 `rwxp`）；两者都是编译/链接期一个开关的成本。

## $\rm \S \, 2.5$ 运行期缓解：ASLR 与 CFI

canary 与 NX 都没回答一个问题：§2.2 的命中 payload 之所以命中，是因为返回地址槽的位置可以算出来、目标地址可以预先写死。如果连「栈在内存的哪个位置」每次运行都不一样呢？地址空间布局随机化（Address Space Layout Randomization，ASLR）就是这么做的：内核在每次启动进程时，给栈、堆、共享库等区域各自加上随机偏移。实测最直接：

```bash
./layout_nsp | grep 'buf'    # 0x7fffcf56f1c0
./layout_nsp | grep 'buf'    # 0x7ffead64de70
setarch $(uname -m) -R ./layout_nsp | grep 'buf'   # 0x7fffffffe0c0
setarch $(uname -m) -R ./layout_nsp | grep 'buf'   # 0x7fffffffe0c0
```

正常情况下两次运行地址毫无关系；`setarch -R` 关闭随机化后，两次运行分毫不差。这就是 §2.1 留下的那个悬念的答案。随机化把「写死一个目标地址」变成了「猜」，猜中的概率由熵（随机化的位数）决定：

$$
P_{\text{一次猜中}} = 2^{-n}, \qquad \mathbb{E}[\text{尝试次数}] = 2^{\,n-1}
$$

读法：若某区域基址有 $n$ 位随机，一次瞎猜命中的概率是 ${2^{-n}}$，平均要试 ${2^{n-1}}$ 次；$n$ 取 20 就是百万级，取 30 就是十亿级。$n$ 的具体数值随内核配置与平台不同（这是一条经验规则而非定数），所以别背数字，记住「位数每加一，难度翻一倍」。ASLR 的绕过思路也只有一句话：泄露。只要任何一个漏洞能把一个运行时地址读出来，整张布局地图就定标了，随机性从猜测问题退化成偏移计算问题。

最后一道闸管的是更普遍的口子。栈溢出劫持的是 `ret`，但现代程序里还有大量函数指针、虚表跳转等间接跳转，每一个都是 §2.2 逻辑的变体。控制流完整性（Control-Flow Integrity，CFI）的思路是：编译期记录每个间接跳转的合法目标集合，运行期跳之前先校验，不在集合内就中止。它相当于把「检票」从 `ret` 一处推广到所有门口。绕过思路一句话：攻击者可以不碰控制流，只篡改数据（改一个标志位、一个指针指向的对象），或者干脆在合法集合内挑目标。

至此四道闸齐了，值得并排看一眼它们各自贯彻的原则与代价：canary 与 NX 是编译期一个开关（安全默认值，成本近零，发行版默认开启），ASLR 是内核加载策略（纵深防御，把确定性变概率），CFI 是全程序插桩（最小权限的指令级版本，开销最大）。没有一道是「关掉就沦陷、开了就免疫」，它们叠加起来抬的是同一根成本曲线，见 §1.6。

白话：ASLR 是每天给全城街道随机改名，让你手里的旧地图作废；CFI 是在每个路口都设检票员，不再只查回程票一张。

**本节小结**：ASLR 把「算出地址」变「猜出地址」（实测关随机化后地址分毫不差），CFI 把「只查返回」变「处处查跳转」；四道缓解各堵一段、互为备份，代价从近零到可观不等。

2. §2.2 的两次实验里，纯 `A` 填充与命中 payload 触发的 SIGSEGV 有何不同（`si_code` 与 `si_addr` 各是什么）？为什么不同？
3. canary 为什么把最低字节设为 `0x00`？这个设计防的是哪一类泄漏路径？
4. 本次实验中 NX 开与关不影响崩溃行为，为什么它仍然必要？它精确挡住的是 §2.3 里的哪一步？
5. ASLR 与 canary 都让「猜」变难，但猜的对象不同。各是什么？

## $\rm \S \, 2.7$ 应用与辨析

1. 同学声称「我写的 C 程序有溢出漏洞，但每次运行崩溃地址都一模一样，所以 ASLR 在我们实验室的服务器上没开」。设计一个两分钟的验证方案（提示：§2.5 的 `setarch -R` 可以双向用），并说明如果 ASLR 确实关闭，最可能的两个原因是什么。
2. 比较 canary 与 CFI：两者都在「跳转/返回前」做检查。从保护对象、插入位置、开销、绕过面四个维度列表对比，并回答：为什么有了 CFI 不少系统仍保留 canary？
3. 同事写了一段 C 代码：`void f(const char *s){ char buf[8]; strcpy(buf, s); }`，编译命令是 `gcc -O2 -fstack-protector-strong`。若 `s` 指向 100 字节字符串，程序会发生什么（崩溃类型与预期退出码）？这层保护防住了什么、没防住什么？若把编译命令换成 `-O2` 且发行版默认开 `-fstack-protector-strong`，答案变吗？

## $\rm \S \, 2.8$ 答案

2.6.1：从高到低：返回地址（`frame+8`）、saved rbp（`frame`）、canary 槽（`frame-8`，protector 构建才有）、局部变量（如 `buf` 在 `frame-0x20`）。§2.1 实测距离 40 字节（§2.2 的另一构建为 200）；距离由该函数的局部对象总大小与编译器布局决定，随构建而变，但「返回地址必在局部变量楼上、只隔固定间隔」不变（§2.1、§2.2）。

2.6.2：纯 `A` 使返回地址槽为 `0x4141414141414141`，不是规范地址，CPU 取指触发通用保护异常，内核报 `si_code=128`（SI_KERNEL）、`si_addr` 为空；命中 payload 的槽值 `0x41414141` 是合法但未映射的地址，CPU 真去取指，触发缺页，`si_code=1`（SEGV_MAPERR）、`si_addr=RIP=0x41414141`。差别不在攻击强度而在目标地址的合法性（§2.2）。

2.6.3：防止 canary 被 `strcpy`、`fread` 这类按 `0x00` 截止或按字节续写的操作整块带出：读操作碰到 `0x00` 会停，写操作越不过它，于是「字符串型漏洞」既偷不到完整 canary，也容易先碰碎它。防的是信息泄露路径，不是溢出本身（§2.4）。

2.6.4：本次 payload 只有字母数据，没有任何代码，崩溃来自「跳到坏地址」，与栈可不可执行无关。NX 挡的是 §2.3 第一代：把机器码写进 `buf` 并让返回地址指过去。没有 NX，那一步是通的（实测 `-z execstack` 下栈页权限变 `rwxp`）；有 NX，栈上数据无法被执行单元取指。缓解各管一段，所以需要纵深防御（§2.3、§2.4）。

2.6.5：canary 让攻击者猜「槽里的 64 位随机值」，一次比对定生死，盲猜期望 ${2^{63}}$ 次；ASLR 让攻击者猜「整片区域的位置」，熵位数 $n$ 决定期望 ${2^{n-1}}$ 次。前者护单个函数的返回路径，后者护全进程的地址地图；泄露类漏洞对两者的破解方式也不同：读 canary 是点，读一个运行时地址则定标全图（§2.4、§2.5）。

2.7.1：方案：同一程序连跑五次记录崩溃地址或局部变量地址（`./vuln; for i in 1 2 3 4 5; do ./layout_nsp | grep buf; done`），再用 `setarch $(uname -m) -R ./layout_nsp` 对照。若普通运行地址恒定且与 `-R` 下完全一致，ASLR 确实未生效。两个最可能原因：程序编译时带了禁用选项（如链接 `-no-pie` 且系统对栈随机化被 `setarch`/`sysctl` 关闭），或该服务器内核启动参数禁用了随机化。验证前者看编译命令，后者看 `cat /proc/sys/kernel/randomize_va_space` 是否为 0（§2.5）。

2.7.2：保护对象：canary 只护「本函数的返回路径」，CFI 护所有间接跳转的合法目标集合。插入位置：canary 在函数入口/出口，CFI 在每个间接跳转前。开销：canary 两条指令级，CFI 需要全程序分析加逐点校验，开销高一个量级。绕过面：canary 怕信息泄露（读出值即可），CFI 怕面向数据的攻击与合法集合内的坏目标。保留 canary 的理由：它对最常见的溢出路径性价比极高，而 CFI 覆盖的间接跳转攻击往往还需要先有另一个漏洞配合；纵深防御允许多道闸叠加而非互相替代（§2.4、§2.5）。

2.7.3：`strcpy` 会向 `buf[8]` 写约 100 字节，溢出碾过 canary 槽与返回地址；`-fstack-protector-strong` 覆盖含数组（或局部变量取址）的函数，`f` 在保护范围内，故返回前比对失败，`stack smashing detected`，进程 SIGABRT，退出码 134。防住的是：控制流不被这次溢出接管。没防住的：溢出本身照常发生，canary 之后的槽位（包括 saved rbp 以外的数据）已被污染，若函数在返回前还有依赖这些数据的逻辑，损害照样发生。发行版默认即是该选项时，换 `-O2` 答案不变，因为保护来自默认开启的 canary 而非优化级别（§2.4）。

> 你现在能：用 `__builtin_frame_address` 与 `/proc/self/maps` 亲手读出一个进程的栈帧布局与页权限位；看到 `Segmentation fault` 与退出码 139、`stack smashing detected` 与 134 时，说出它们各自对应哪一道缓解的哪一步；面对一个新系统，用四道闸的「各防什么、绕过靠什么」清单快速评估它的内存安全姿态。
