# $\rm Chapter \, 1$ 计算机、程序与开发全景

> 本章回答一个看似简单、实际上贯穿整套手册的问题：你写下的一份代码，怎样变成计算机正在运行的程序，又怎样成为别人可以使用的软件？

作为算法竞赛选手，你已经写过数百个程序，也对编译错误和运行结果不陌生。但 OJ 平台替你隐藏了大量中间环节：文件保存在哪里、编译器（compiler）接受哪些参数、一个 `main.cpp` 怎样变成可以运行的程序、输入输出如何连接到测试数据、退出码（exit code）和资源占用如何被收集。这些环节在竞赛中不需要关心，但在真实开发中每天都要面对——选编译选项、管文件位置、判断启动失败的原因，都只能自己来。下一章[终端、Shell与命令行](../02-终端与工具/02-终端Shell与命令行.md)将打开终端，让你亲手向 Shell 描述这些指令。

> **开始前自检**：本章假设你已经会：
>
> - □ 用 C++ 写过从标准输入读取、向标准输出写出的程序
> - □ 理解变量、函数、数组、指针、递归与常见复杂度
> - □ 在 OJ 上提交过代码并见过编译/运行结果

## $\rm \S \, 1.1$ 本章假设与目标

先说清楚这一章站在哪儿。你写 C++ 写得不短了，变量、函数、数组、指针、递归、复杂度都熟，题也可能刷过几百道。但你一直在一个被包装好的环境里干活：打开编辑器、把代码粘进去、点提交，过一会儿回来看 Accepted 或一堆报错。

这个环境替你做了太多事——保存文件、挑编译器、传编译参数、创建进程、准备输入、限制时间和内存、收输出、比对答案。你只负责中间那几十行。真实开发里这些步骤没人代劳：编译参数得自己定，文件放哪得自己安排，程序起不来也得自己查。

学完本章并做完实践，你应该能：

- 把源代码（source code）、可执行文件（executable）、程序、进程（process）这四个词分开用；
- 讲出编译、链接、加载、运行的大致先后；
- 说清参数、标准输入、标准输出、标准错误、退出码各自管什么；
- 分清库、框架、运行时、SDK、API 和服务；
- 画出一个前后端应用从用户点击到数据库走过的路；
- 记住“能编译”“能启动”“功能对”“能交付”是四件不同的事。

## $\rm \S \, 1.2$ 从一道 OJ 题看程序生命周期

考虑熟悉的 C++ 程序：

```cpp
#include <iostream>

int main() {
    long long a, b;
    std::cin >> a >> b;
    std::cout << a + b << '\n';
    return 0;
}
```

你看到的是一段文本。CPU 并不能直接执行 `std::cin` 或 `a + b` 这些字符。一次提交背后大致是这样一个流程：

```text
源代码文本
   ↓ 编译器进行预处理、编译和汇编
目标文件
   ↓ 链接器连接运行库等依赖
可执行文件
   ↓ 操作系统加载
进程
   ↓ 读取输入、计算、写出结果、结束
退出码 + 标准输出 + 资源使用数据
   ↓ 评测器比较输出并检查限制
评测结果
```

不同编译器和平台的实现细节会不同，但这张图足以作为初始模型。

### $\rm \S \, 1.2.1$ 源代码是文本文件

源代码首先是按照某种字符编码保存的字节序列。`.cpp` 扩展名帮助编辑器、构建工具和人识别用途，但文件内容本身仍是文本。

下面几项互不相同：

- 文件名：`main.cpp`
- 文件路径：`D:\projects\sum\main.cpp` 或 `/home/alice/projects/sum/main.cpp`
- 文件内容：C++ 源代码
- 字符编码：通常 UTF-8
- 换行格式：Windows 常见 CRLF，Linux 常见 LF

扩展名不是魔法。把 `photo.jpg` 改名为 `photo.cpp` 不会把图片转换为 C++。

### $\rm \S \, 1.2.2$ 编译不是“运行”

编译器读你的源代码，检查语法和类型，再把它换成更贴近机器执行的东西。你平时敲的 `g++ main.cpp -o main` 看着是一步，其实里面串了四件事：

1. **预处理**：展开 `#include`、`#define` 和条件编译。
2. **编译**：把处理过的 C++ 变成汇编或中间形式。
3. **汇编**：生成目标文件。
4. **链接**：把多个目标文件和用到的库合成最终程序。

四步都过了，你才拿到可执行文件。所以“编译通过”这四个字含金量比想象中低——它只说明工具链吐出了一个产物。至于这个产物能不能在这台机器上启动、运行时依赖齐不齐、输入输出符不符合要求、有没有越界和竞态、逻辑对不对、安不安全，它一概没保证。

### $\rm \S \, 1.2.3$ 链接解决“名字对应哪段实现”

一个项目往往有多个源文件：

```text
src/
├── main.cpp
├── parser.cpp
└── search.cpp
```

`main.cpp` 可能调用 `search.cpp` 中实现的函数。每个文件可以分别编译成目标文件，链接器再把函数引用和实际实现对应起来，并连接标准库或其他库。

报错也分阶段，先看清它落在哪一步，比埋头改代码有用得多：

- **编译错误**：语法、类型或声明写错了。
- **链接错误**：声明找得到，实现找不到；或者同一份实现出现了两次。
- **运行时错误**：程序已经跑起来，执行中途出事。
- **逻辑错误**：程序正常结束，结果却是错的。

看到报错时，先判断处于哪个阶段，比直接修改代码有效。

### $\rm \S \, 1.2.4$ 可执行文件不是进程

可执行文件是磁盘上的静态文件。双击或在终端运行它时，操作系统创建一个**进程**：分配进程标识符，建立虚拟地址空间，加载代码和动态库，准备栈、堆、环境变量和标准流，然后从入口开始执行。

同一个可执行文件可以同时启动多个进程：

```text
磁盘上的 browser.exe
       ├── 浏览器进程 A
       ├── 浏览器进程 B
       └── 浏览器进程 C
```

文件是持久的程序载体，进程是某次正在运行的实例。修改或删除源代码一般不会立即改变已经启动的进程；要让新代码生效，通常需要重新构建并重启程序。

## $\rm \S \, 1.3$ 程序如何接收输入并给出结果

### $\rm \S \, 1.3.1$ 命令行参数

你以后写的工具，多半不是“跑起来再问用户要数据”，而是“启动那一刻就把活儿交代清楚”——`grep -i error app.log` 就是这样。启动瞬间传进去的这些信息，叫命令行参数。

```cpp
#include <iostream>

int main(int argc, char* argv[]) {
    std::cout << "argc = " << argc << '\n';
    for (int i = 0; i < argc; ++i) {
        std::cout << i << ": " << argv[i] << '\n';
    }
}
```

假设程序名为 `show-args`：

```text
show-args papers.txt --limit 10
```

Shell 会把它解析为若干参数。通常 `argv[0]` 是程序自身名称，其余依次是 `papers.txt`、`--limit` 和 `10`。

空格默认用于分隔参数。如果参数本身包含空格，需要按当前 Shell 的规则加引号：

```text
show-args "my papers.txt" --limit 10
```

不要以为整条命令就是传给程序的一个字符串。通常是 Shell 先解析命令，再以参数列表启动程序。

### $\rm \S \, 1.3.2$ 标准输入、标准输出和标准错误

进程启动时通常拥有三个标准流：

| 标准流 | 常见编号 | C++ 对应 | 用途 |
|---|---:|---|---|
| standard input | 0 | `std::cin` | 输入数据 |
| standard output | 1 | `std::cout` | 正常结果 |
| standard error | 2 | `std::cerr` | 错误、诊断、日志 |

在 OJ 中，标准输入常连接到测试数据文件，标准输出被评测器捕获。开发工具中，输出也可以来自键盘、文件、另一个程序或网络。

为什么需要把正常结果和错误分开？假设程序输出 JSON 给另一个程序处理，如果调试日志也混进标准输出，JSON 就会损坏。更好的约定是：机器需要继续处理的结果写 stdout，人类诊断信息写 stderr。

### $\rm \S \, 1.3.3$ 退出码

程序结束时会向操作系统返回一个整数状态。约定上：

- `0` 表示成功；
- 非 `0` 表示某种失败。

退出码不是打印到屏幕的文字。以下两件事不同：

```cpp
std::cout << 1; // 输出字符 1
return 0;       // 以成功状态结束
```

脚本、构建工具和 CI 通常依赖退出码决定是否继续。一个检测到错误却仍返回 0 的程序，会误导自动化系统。

### $\rm \S \, 1.3.4$ 环境变量

环境变量是一组在进程启动时传入的名称和值，例如：

```text
PATH=...
APP_ENV=development
PORT=8080
```

它们常用于告诉程序去哪里找可执行文件、当前处于什么环境、监听哪个端口。环境变量不是天然安全的秘密保险箱：它们可能被进程、日志、调试信息或部署平台暴露。

子进程通常继承父进程的环境。你在某个终端临时设置的变量，通常只影响该终端和之后由它启动的程序，不会神奇地修改已经运行的其他程序。

## $\rm \S \, 1.4$ 库、框架、运行时、SDK 和 API

写代码写到某个阶段，你一定会想借别人的力：想发 HTTP 请求，不想自己实现 TCP；想显示界面，不想自己写渲染；想跑 Python，不想自己写解释器。这时候一堆词冒出来——库、框架、运行时、SDK、API，招聘要求里还老爱把它们并列着写。

它们确实都在说“用别人提供的能力”，但站的位置不一样。先看需求，再一个个认名字。

### $\rm \S \, 1.4.1$ 库

最直接的一种借力叫**库**（library）：别人把一组功能写好放在那儿，你主动挑着调用。

```cpp
std::sort(values.begin(), values.end());
```

C++ 标准库提供容器、算法、字符串和输入输出等能力。第三方库可能提供图像处理、网络协议或机器学习功能。

库可以是：

- 只需包含源码或头文件的形式；
- 编译后静态链接进可执行文件；
- 运行时加载的动态库，例如 Windows 的 DLL 或 Linux 的 `.so`。

### $\rm \S \, 1.4.2$ 框架

**框架**（framework）反过来：整体怎么组织、什么时机该发生什么，由它定；你的代码只按约定填进组件或回调，剩下的交给它在合适的时候调用。这个“你不再决定自己什么时候被执行”的转折，叫控制反转（inversion of control）。

和库的差别说到底是主动权在谁手里。用库时你握着方向盘，一个用完接着挑下一个；用框架时你站上了它的生产线，把自己的零件放到指定工位——什么时候被送上工位，不由你定。

现实中的边界并不绝对。React 官方称自己为库，但配合路由和构建生态时，也会形成框架式开发体验。

### $\rm \S \, 1.4.3$ 运行时

再往下一层是**运行时**（runtime）：程序不会凭空跑起来，得有个环境替它兜底——加载代码、管内存、把语言指令变成机器动作，顺带提供一批现成能力。同一个程序换个运行时，能用的东西可能完全不同：

- 浏览器能够执行网页中的 JavaScript，并提供 DOM、网络等 Web API；
- Node.js 在浏览器之外执行 JavaScript，并提供文件、进程等 API；
- Python 解释器执行 Python 程序；
- JVM 执行 Java 字节码；
- .NET Runtime 执行相应中间代码。

同一种语言在不同运行时中可用的能力可能不同。浏览器 JavaScript 不能默认直接读取任意本地文件，Node.js 则有文件系统 API。

### $\rm \S \, 1.4.4$ SDK

要“运行”某个程序，和要“开发”某个程序，需要的家当不一样。**SDK**（Software Development Kit，软件开发工具包）是后者的整套装备：编译器、库、命令行工具、调试器、模板、文档，按平台配齐。

安装“能运行某程序的运行时”和安装“能开发该程序的 SDK”不一定相同。例如某些平台允许只安装较小的运行环境来运行软件，而开发者需要完整 SDK。

### $\rm \S \, 1.4.5$ API

API 是 Application Programming Interface，即应用程序编程接口。它描述一个软件组件允许其他代码怎样使用它。

API 不等于 HTTP。以下都是 API：

- C++ 函数的参数和返回值；
- 操作系统打开文件的系统调用；
- 浏览器提供的 DOM API；
- 一个服务器暴露的 HTTP 接口；
- 数据库驱动提供的查询方法。

接口关心“外部怎样使用”，实现关心“内部怎样完成”。稳定接口可以让实现演进而不迫使所有调用者一起重写。

## $\rm \S \, 1.5$ 客户端、服务器与服务

### $\rm \S \, 1.5.1$ 角色而不是固定机器

客户端发起请求，服务器接收请求并提供某种能力。这描述的是一次交互中的角色，不一定对应两台物理机器。

在自己的电脑上运行后端并用浏览器访问时：

- 浏览器是客户端；
- 本地后端进程是服务器；
- 两者可能运行在同一台机器上；
- 通信仍可经过操作系统的网络栈。

一个程序也可以同时扮演两种角色：你的后端接收浏览器请求时是服务器；它请求数据库或第三方 API 时又是客户端。

### $\rm \S \, 1.5.2$ 服务是什么

“服务”常指持续运行、等待请求或事件的程序，例如：

- Web API 服务；
- 数据库服务；
- SSH 服务；
- 文件同步服务；
- 操作系统的后台服务。

服务通常需要考虑启动、停止、重启、日志、权限、配置、健康检查和异常恢复。把程序放到后台运行不等于已经可靠地部署为服务。

### $\rm \S \, 1.5.3$ 端口

一台机器可以运行多个网络服务。IP 地址大致标识主机，端口帮助操作系统把收到的数据交给正确进程。

```text
127.0.0.1:3000  → 前端开发服务器
127.0.0.1:8000  → 后端 API
127.0.0.1:5432  → PostgreSQL
```

“端口被占用”表示已有进程绑定了目标地址和端口。解决方法是识别占用者、判断它是否应继续运行，再决定停止它或换端口；不要看到端口冲突就随机杀进程。

## $\rm \S \, 1.6$ 一个全栈应用的最小地图

以论文资料管理器为例：

```text
用户
 │ 点击、输入
 ▼
浏览器前端（HTML/CSS/JavaScript）
 │ HTTP + JSON
 ▼
后端 API（例如 Python）
 │ SQL
 ▼
数据库（例如 SQLite——详见第 26 章）
```

更真实的部署还可能包含：

```text
域名 → DNS → HTTPS → 反向代理 → 后端服务 → 数据库
                              ├→ 日志
                              └→ 文件/对象存储
```

每一层解决不同问题：

- **前端**：展示信息并处理用户交互。
- **HTTP API**：约定前后端怎样交换数据。
- **后端**：执行权限检查、业务规则和数据处理。
- **数据库**：持久保存结构化数据并支持查询。
- **反向代理**：接收公网请求，处理 TLS、路由或静态文件。
- **系统服务管理器**：让后端在开机后启动、失败后按策略恢复并保存日志。

“全栈”不是指一个人记住所有框架 API，而是能理解请求如何跨层流动，出现错误时知道应该在哪一层找证据。

## $\rm \S \, 1.7$ 开发环境、测试环境与生产环境

### $\rm \S \, 1.7.1$ 开发环境

开发者修改和调试代码的环境。它常开启详细错误、自动重载和调试工具，使用测试数据。

### $\rm \S \, 1.7.2$ 测试或预发布环境

用于自动测试、集成验证或发布前检查。配置应尽量接近生产，但不得使用真实敏感数据进行随意测试。

### $\rm \S \, 1.7.3$ 生产环境

真实用户使用的环境。生产环境强调稳定、安全、监控、备份和可恢复性，通常不会暴露详细调试页面。

环境之间的差异应由明确配置管理，而不是靠开发者临时修改源码。数据库、密钥和外部服务也应隔离。

## $\rm \S \, 1.8$ 从“写出代码”到“交付软件”

一个真实修改通常经历：

1. 理解需求和现有代码。
2. 建立或更新本地开发环境。
3. 在 Git 分支中修改源码。
4. 运行格式化、静态检查和测试。
5. 构建可部署产物。
6. 提交并推送到 GitHub。
7. 创建 Pull Request，接受代码评审。
8. CI 在干净环境中重复检查。
9. 合并并部署到目标环境。
10. 观察日志、指标和用户反馈，必要时回滚。

因此以下判断必须分开：

| 层次 | 说明 |
|---|---|
| 能编译/构建 | 工具成功生成产物 |
| 能启动 | 操作系统成功创建进程，程序没有立即退出 |
| 功能正确 | 在明确输入和边界情况下符合需求 |
| 质量合格 | 可读、可测试、性能和安全满足要求 |
| 可以交付 | 配置、文档、部署、监控和恢复方案齐全 |

OJ 的 Accepted 主要对应一个受控环境中的功能正确。软件开发还要处理输入不可控、长期运行、多人协作、升级兼容和故障恢复。

## $\rm \S \, 1.9$ 第一个动手实验：手工走完生命周期

### $\rm \S \, 1.9.1$ 打开终端

Windows：按 `Win` 键，输入 `PowerShell` 或 `wt`（Windows Terminal），回车。Linux：`Ctrl+Alt+T`。macOS：`Cmd+Space`，输入 `Terminal`。

看到闪烁光标和提示符（如 `PS C:\Users\你的用户名>` 或 `$`）——这就是终端，你可以在这里输入命令。

### $\rm \S \, 1.9.2$ 准备目录与文件

在终端中逐行输入以下命令（`#` 及之后是注释，不需要输入）：

```powershell
# PowerShell
mkdir lab01
cd lab01
@"
#include <iostream>
int main() { long long a, b; std::cin >> a >> b; std::cout << a + b << '\n'; return 0; }
"@ | Out-File -Encoding UTF8 main.cpp
```

```bash
# Bash / WSL / Linux / macOS
mkdir lab01 && cd lab01
cat > main.cpp << 'EOF'
#include <iostream>
int main() { long long a, b; std::cin >> a >> b; std::cout << a + b << '\n'; return 0; }
EOF
```

## $\rm \S \, 1.12$ 总结

**源代码、可执行文件、进程和软件是四层不同的东西**。

- **源代码**是文本。扩展名只是约定，编译不是“运行”。
- **可执行文件**是磁盘上的静态产物。编译成功只说明工具链接受了语法，不说明程序正确。
- **进程**是操作系统为某次运行创建的实例。同一个可执行文件可以同时对应多个进程。
- 程序通过**命令行参数、标准流和环境变量**与外界交换信息。退出码告诉调用者成败，标准输出给机器，标准错误给人。
- **库、框架、运行时、SDK、API**都涉及“使用别人提供的能力”，但层次不同：库被你调用，框架调用你，运行时提供执行环境，SDK 是开发工具集合，API 定义组件之间的使用约定。
- 客户端和服务器是**一次交互中的角色**，不是固定机器。端口帮助系统把网络数据交给正确的进程。
- **能编译、能启动、功能正确、质量合格、可以交付**是五道不同的门槛。OJ 的 Accepted 近似功能正确，真实软件还需要长期维护、多人协作和故障恢复。

你手中现在有了一张从代码到交付的全景图。下一章[终端、Shell与命令行](../02-终端与工具/02-终端Shell与命令行.md)的问题是：**在上面所有实验中，你都通过敲键盘、看文字来操作程序——承载这些文字的界面是什么？它怎样理解你输入的命令，找到你要运行的程序，并把结果还给你？**

这就是终端和 Shell 要解决的问题。

### 自测答案 · 关键概念回顾
1. CPU 只能执行机器指令，`.cpp` 只是文本；必须经编译器（预处理、编译、汇编）转换为目标文件、链接器连接依赖后生成可执行文件才能运行。
2. 库是被你的代码主动调用的可复用实现；框架规定整体组织并在合适时机调用你的代码（控制反转）；运行时为某类程序提供执行环境和基础服务；SDK 是开发某平台所需的工具集合；API 是组件之间”外部怎样使用”的约定。
3. 不必。它们是交互中的角色：同一台机器上的浏览器（客户端）和本地后端（服务器）可以共存，一个程序也能同时扮演两种角色。

### 自测答案 · 应用与辨析
4. 编译错误发生在单个源文件的语法、类型检查阶段；链接错误发生在把目标文件和库连接成可执行文件时——声明存在但找不到实现，或同一实现出现多次。
5. 可执行文件是磁盘上的静态文件；进程是操作系统为一次运行创建的实例，拥有 PID、虚拟地址空间和标准流；同一个可执行文件可以同时对应多个进程。
6. 标准输出供机器继续处理（如 JSON 数据），标准错误供人类查看诊断信息；混在一起会污染数据，分开后可以分别重定向和过滤。
7. 打印是把字符写入标准输出流；返回 1 是进程结束时交给操作系统的状态码（0 成功、非 0 失败），脚本和 CI 依靠它决定是否继续。
8. 开发环境开启详细错误、自动重载、使用测试数据，且没有监控、备份和恢复方案；生产环境要求稳定、安全、可监控、可备份、可恢复，两者的配置必须明确隔离。
9. 能启动只说明操作系统成功创建了进程；可以交付还要求功能正确、质量合格（可读、可测、安全）以及配置、文档、部署、监控和恢复方案齐全。
10. 浏览器前端 → HTTP/JSON → 后端 API → SQL → 数据库；真实部署还会经过域名、DNS、HTTPS、反向代理和日志等层次。
