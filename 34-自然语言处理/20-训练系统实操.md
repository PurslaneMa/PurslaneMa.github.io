## $\rm \S \, 20.1$ 需要的前提

1. 梯度与 `.grad`：`loss.backward()` 把损失对每个参数的偏导算出来、累加到对应参数的 `.grad` 属性上；不清零就继续往上加，这个「默认累加」行为正是 §20.5 梯度累积的地基。
2. 数据并行与 AllReduce（§11.5）：数据并行是「每卡完整模型、各吃各的数据」，AllReduce 是「大家加总、总账抄给所有人」的通信原语；本章要证的是「平均后的梯度恰好等于全局大批量的梯度」这条恒等式。
3. ZeRO 三 Stage（§11.5.3）：依次切优化器状态、梯度、参数，切得最深的那档就是 FSDP 做的事；本章 §20.4 从显存与通信两头把这笔账算细。
4. 全局 batch 的组成式（PDF 第 165 页）：global batch = 每卡 batch × 卡数 × 梯度累积步数。本章所有数字锚都从它出发。

## $\rm \S \, 20.2$ accelerate 起手式：一条命令派生 N 个进程

### $\rm \S \, 20.2.1$ 多进程是什么样子

白话：accelerate 要解决的问题，是「单卡脚本」与「多卡程序」之间隔着一整套分布式样板代码，它替你把样板写好，你只改三行。

课件把春季学期的 `LLM-inclass5` 示例用 HuggingFace accelerate 重写了一遍（PDF 第 159 页），运行方式只有一条命令的变化：

```bash
accelerate launch train.py [args]
```

它做的事是：每张 GPU 派生一个独立的 Python 进程（PDF 第 160 页）。2 卡跑一次，`nvidia-smi` 里能看到两个进程，各有一个完整的解释器。每个进程有自己的编号 rank（0 和 1），accelerate 通过 `accelerator.is_main_process` 与 `accelerator.process_index` 把它们区分开。

判断「哪个进程执行哪段代码」的标准写法（PDF 第 161 页，示例 `SimpleQ`）：

```python
if args.report_to == "wandb" and accelerator.is_main_process:
    wandb.init(project="llm26_inclass5_multigpu", config=vars(args))

accelerator.wait_for_everyone()
if accelerator.is_main_process:
    print("\nafter wandb-init debug print1 (main)")

print("\nafter wandb-init debug print2", "[rank:]", accelerator.process_index)
accelerator.wait_for_everyone()
```

2 卡运行的实际输出（PDF 第 162 页）是三行：`print1` 出现 1 次（只有主进程进那个分支），`print2` 出现 2 次（每个进程各打一条，rank 1 的先到、rank 0 的后到，顺序不保证）。这就是多进程训练的阅读方式：**没被条件挡住的每一行代码，每个进程都会执行一遍**；想只打一份日志，就得用 `is_main_process` 拦。

`wait_for_everyone()` 是一个栅栏（barrier）：先到的进程在这里停住，等最慢的进程到齐再一起往下走。课件留的 `SimpleQ` 问的就是它的含义——没有这个栅栏，rank 1 可能在 rank 0 还没初始化 wandb 时就抢跑了，后面的集体通信会因为「有人没到」而挂住或报错（语义详见 HuggingFace accelerate 文档的 deferring execution 一节）。

### $\rm \S \, 20.2.2$ 调试的代价

多进程调试有个新手坑：在其中一个进程里下断点，别的进程正在栅栏处等它，等太久就把等待方超时报错。课件给的缓解手段是放大分布式超时（PDF 第 163 页）：

```python
os.environ["TORCH_DISTRIBUTED_TIMEOUT"] = "9600"
```

白话：大家一起等你查 bug，但等待有耐心上限，这个环境变量就是把耐心从默认值调到 9600 秒。

小结：accelerate 的多卡程序 = 单卡脚本 + `launch` 派生进程 + 栅栏对齐 + 主进程判定，输出要按「每进程各打一遍」来读。

### $\rm \S \, 20.2.3$ prepare 把四个对象都包了一遍

accelerate 的核心 API 是 `accelerator.prepare`，把训练循环里的四样东西各包一层（PDF 第 167 页）：

```python
model, optimizer, dataloader, scheduler = accelerator.prepare(
    model, optimizer, dataloader, scheduler
)
if accelerator.is_main_process:
    print(type(model), type(optimizer), type(dataloader), type(scheduler))
```

打印出来的四个类型说明了包了什么：

1. `model` 变成 `torch.nn.parallel.distributed.DistributedDataParallel`（或配 FSDP 时是 `FullyShardedDataParallel`）——分布式行为挂在模型上；
2. `optimizer` 变成 `accelerate.optimizer.AcceleratedOptimizer`——`step()` 被拦截，只在允许同步的时机真正更新（§20.5 会用到）；
3. `dataloader` 变成 `accelerate.data_loader.DataLoaderShard`——数据被切成每进程一份，各卡不重叠；
4. `scheduler` 变成 `accelerate.scheduler.AcceleratedScheduler`——学习率调度按「优化器真实步数」走，配套代码里 `total_steps = len(dataloader) // args.gradient_accumulation_steps * args.num_train_epochs` 也按累积后的步数计。

白话：prepare 就像给四个零件各套了一层「分布式外壳」，你的训练循环代码一行不用改，外壳在暗处替你切数据、同步梯度、拦更新。课件在这页标了「Important! Let's study this later」——下面两节就来拆这层外壳。

小结：prepare 的本质是包装（wrap），训练循环表面没变，暗处多了切分、同步与拦截三件事。

## $\rm \S \, 20.3$ DDP：显存账与梯度恒等式

### $\rm \S \, 20.3.1$ 为什么每张卡的显存一模一样

现象（PDF 第 164 页）：2 卡 DDP 跑起来，`nvidia-smi` 里两张卡的显存占用精确相等。这不是巧合，是 DDP 设计使然，课件给了三层原因。

白话先给直觉：DDP 是「人人背全套、各做各的题」，负担当然一样重。

1. 完全相同的模型副本（identical replicas）：GPU 0 拿一份完整模型，GPU 1 拿一份一模一样的完整副本。参数、层结构、优化器配置全同，基础显存自然逐字节相同。
2. 等大的每卡 batch（equal batch sizes）：全局 batch 被均分成每卡一份，两卡同时处理形状完全相同的张量，前向激活的显存也相同。组成式即 §20.1 的 global = per-gpu × 卡数 × 累积步数。数字锚：2 卡 × 每卡 16 × 累积 4 步 = 128，即全局有效 batch 是 128。
3. 同步优化（synchronized optimization，选读）：反向时框架做 all-reduce 把各卡梯度平均，之后每一步各卡的权重、梯度、优化器状态（如 Adam 的动量缓冲）都被镜像得完全一致，显存占用自然全程锁死在一起（PDF 第 166 页）。

课件顺带给了反例：什么时候显存会不相等——用老式 DP（主卡聚合损失与输出，显存独大，见 §20.3.3）或流水线并行（各卡摊的层不同，每层显存不同）。这两个反例反过来确认了「DDP 显存对称」来自「完整复制 + 等量数据」。

显存到底多大？课件 debug 输出里打印过两个权重（PDF 第 169 页）：`q_proj` 形状 ${[1536, 1536]}$、FFN 的 `down_proj` 形状 ${[1536, 8960]}$。按每参数的字节数真算一笔账（1 MB 按 $2^{20}$ 字节）：

| 每卡要存的东西 | 每参数字节数 | q_proj（2 359 296 个参数） | down_proj（13 762 560 个参数） |
| --- | --- | --- | --- |
| bf16 参数 | 2 | 4.5 MB | 26.25 MB |
| bf16 梯度 | 2 | 4.5 MB | 26.25 MB |
| fp32 主权重（混合精度） | 4 | 9.0 MB | 52.5 MB |
| AdamW 一阶矩＋二阶矩（fp32） | 8 | 18.0 MB | 105.0 MB |

读表：混合精度 + AdamW 训练下每个参数摊约 16 字节，仅这两个矩阵每卡就要背约 246 MB，而且 DDP 下这个数字是**每张卡各来一份**。这也是 §11.6 那把「7B 模型 FP32 约 28 GB」尺子的完整版：7B 参数按 16 字节摊开就是约 112 GB，单卡必然装不下，这才引出 §20.4 的切分。

小结：DDP 显存对称是因为「模型完整复制 × 等量数据 × 全程镜像」，代价是每卡都背全款。

### $\rm \S \, 20.3.2$ 多卡反向传播恒等式：平均梯度 = 全局 batch 梯度

DDP 每步真正发生的数学只有一件事，本节把它证全。白话：要说明「8 张卡各算一小份再平均」与「一张卡吃下全部数据算一遍」在梯度意义上逐位等价，多卡训练才没有偷偷换掉优化问题。

设定记号：$N$ 张卡，全局 batch $\mathcal{B}$ 被切成 $N$ 份 $\mathcal{B}_1,\dots,\mathcal{B}_N$，每份 $b$ 个样本（等 batch），且两两不交、并起来恰是 $\mathcal{B}$。$\ell_i$ 记样本 $i$ 的损失，$\theta$ 记参数。全局损失与第 $n$ 卡的本地损失都取「按样本平均」：

$$
L(\mathcal{B})=\frac{1}{Nb}\sum_{i\in\mathcal{B}}\ell_i
\qquad
L_n=\frac{1}{b}\sum_{i\in\mathcal{B}_n}\ell_i
$$

第 $n$ 卡本地反向得到 $\nabla_\theta L_n$；DDP 的 all-reduce 把各卡梯度取平均，每卡最终拿到 $\frac{1}{N}\sum_{n=1}^{N}\nabla_\theta L_n$。逐项展开这个平均：

$$
\begin{aligned}
\frac{1}{N}\sum_{n=1}^{N}\nabla_\theta L_n
&=\frac{1}{N}\sum_{n=1}^{N}\left(\frac{1}{b}\sum_{i\in\mathcal{B}_n}\nabla_\theta\ell_i\right)\\
&=\frac{1}{Nb}\sum_{n=1}^{N}\sum_{i\in\mathcal{B}_n}\nabla_\theta\ell_i\\
&=\frac{1}{Nb}\sum_{i\in\mathcal{B}}\nabla_\theta\ell_i\\
&=\nabla_\theta L(\mathcal{B})
\end{aligned}
$$

读法：第一步代入 $L_n$ 的定义；第二步把常数重新组合，$\frac{1}{N}\cdot\frac{1}{b}=\frac{1}{Nb}$，提到双求和外面；第三步是关键——各卡的数据两两不交、并起来就是 $\mathcal{B}$，所以「对卡求和再对样本求和」可以拼成「直接对全局 batch 求和」；第四步认出这正是全局损失的梯度。

结论就是多卡反向传播恒等式：

$$
\frac{1}{N}\sum_{n=1}^{N}\nabla_\theta L_n=\nabla_\theta L(\mathcal{B})
$$

一句话：all-reduce 平均后的梯度，与把全部 ${Nb}$ 个样本堆在一张卡上算出的梯度逐位相同。它成立靠三个前提，每一个都对应 DDP 的一条工程纪律：

1. 每卡等 batch（$b$ 相同）：若不等，简单平均会把小 batch 卡的样本权重高估，需要按样本数加权平均才回到恒等式；DDP 的数据切分默认均分，正是在保这条。
2. 损失按样本取平均（mean 而非 sum）：写成 sum 的损失，梯度会大 $b$ 倍，等效于偷偷放大学习率。
3. 各卡权重完全一致：§20.3.1 的完整复制保证每步起点相同、all-reduce 后更新也相同，下一步起点仍一致，恒等式每一步都在场。

小结：DDP 没有改变优化问题，它只是把一个大 batch 的求和拆到 $N$ 张卡上并行做、再用通信把结果拼回来。

### $\rm \S \, 20.3.3$ DP 与 DDP：线程与进程的分野

PyTorch 官方明确建议从老式 `DataParallel`（DP）迁到 `DistributedDataParallel`（DDP），理由集中在两点（PDF 第 184–185 页，出自 PyTorch DDP 系列教程 theory 篇）。

白话：DP 是「一个老板娘带一群学徒」，DDP 是「一群独立厨师对暗号」。

1. 绕开 GIL：DP 是单进程多线程，Python 的全局解释器锁（Global Interpreter Lock，GIL）让多个线程抢同一个解释器，Python 层面根本不是真并行（课件注：Python 3.13 之前不是真正的 multi-thread）。DDP 每卡一个进程、各有各的解释器，彻底绕开。这与深度学习框架分册 §9.5 把 all-reduce 挂进反向传播的读法互补：那里讲通信怎么藏，这里讲进程怎么派。
2. 通信结构：DP 是 master-slave 架构，数据每步从主卡 scatter 出去、结果再 gather 回主卡，主卡是必然瓶颈，也是显存独大的元凶（§20.3.1 的反例）。DDP 用 AllReduce（实践中是 NVIDIA 的 NCCL 库）在所有卡之间同时同步梯度，没有中心节点，还能跨机器扩展。

小结：DP 输在「线程假并行 + 中心瓶颈」，DDP 用「进程真并行 + 无中心 all-reduce」双杀。

### $\rm \S \, 20.3.4$ reducer：通信怎么藏进反向（选读）

DDP 的实现细节（PDF 第 178–181 页，官方 notes 与 reducer 源码）值得知道一句，因为它解释了「恒等式在哪一刻生效」：DDP 在反向传播时给每个参数挂一个 autograd 钩子（hook，§20.6 专讲），某参数的梯度一算完，就把它归进一个桶（bucket）异步发起 all-reduce，通信与剩余层的反向计算重叠进行。官方 notes 的原话是：梯度同步通信发生在反向传播期间、与反向计算重叠；当 `backward()` 返回时，`param.grad` 里装的已经是同步后的梯度张量（docs.pytorch.org 的 DDP notes）。

白话：不是「先算完所有梯度再开会对账」，而是每算完一桶就对一桶的账，等反向走完，账已经对齐了。这也回答了 §20.3.2 恒等式的落地时机：`backward()` 返回的那一刻。

小结：DDP 的通信不占额外关卡，它藏在反向传播内部，靠钩子按桶流水。

## $\rm \S \, 20.4$ FSDP：切参数存，通信换内存

DDP 把模型整个复制到每张卡，模型大到单卡放不下时这条路就断了。FSDP（以及 DeepSpeed，两者 accelerate 都能调，PDF 第 182 页）的思路是 §11.5.3 讲过的 sharding：参数、梯度、优化器状态都切开，每卡只存一份分片。

看懂它最直接的办法是看 debug 输出。课件在训练循环里插了打印两卡上第一层 `q_proj` 与 `down_proj` 形状的代码（PDF 第 168 页），DDP 与 FSDP 的输出对比（PDF 第 169 页）：

```text
DDP   rank 0  qproj: [1536, 1536]   ffn: [1536, 8960]   device: 0
DDP   rank 1  qproj: [1536, 1536]   ffn: [1536, 8960]   device: 1
FSDP  rank 0  qproj: [2359296]      ffn: [0]            device: 0
FSDP  rank 1  qproj: [0]            ffn: [13762560]     device: 1
```

两处信息：其一，DDP 两卡形状完全相同，验证「完整复制」；FSDP 打出来的形状对不上二维矩阵，是展平的一维、甚至是 ${[0]}$——参数被按 FSDP 单元切分并平铺存储，打印时刻该卡没有持有（或未收齐）那个单元的分片就是 ${[0]}$。课件在此处明确标注 deep understanding of FSDP is not required，机制细节以 PyTorch FSDP 官方文档为准。其二，课件留的算术：$1536\times1536=2\,359\,296$、$1536\times8960=13\,762\,560$，正好对上 debug 输出里的两个一维长度——切分单元是按层走的，q_proj 与 down_proj 分属不同单元，两张卡轮到持有的单元不同。

运行时的账是这样的（PDF 第 183 页）：8 卡 FSDP 实际在做「模型 sharding 到 8 张卡 + 8 路数据并行」，每卡处理不同的 batch；forward 和 backward 时通过 all-gather 临时把当前层的完整参数收齐，用完即丢，只留自己那份分片。白话：图书馆的参考书平时一人管一册，谁要用整本就临时把大家手里的页凑齐，翻完立刻散伙。

这笔记账的关键是「通信换内存」双向都不免费：

1. 显存侧：每卡只存 ${1/N}$ 的模型状态，大模型放得下了；
2. 通信侧：每个单元前向多一次 all-gather、反向再一次 all-gather、梯度还要 reduce-scatter 收回去，通信量明显上涨；
3. 所以课件结论是 sharding 一般会明显减慢训练，它只负责「放得进」，加速主要还是靠数据并行（§20.3.2 的恒等式照常生效）；TP 能加速是因为多卡同时在跑同一个模型的不同切面，FSDP 与 DeepSpeed 都不支持 TP（§11.5.4 已讲，这里补上机制原因），要 TP 得走 Megatron-LM。

小结：FSDP 把 §20.3.1 那张「每卡全款」的表按卡数除下去，代价是每层多付几轮通信的利息。

## $\rm \S \, 20.5$ 梯度累积：小显存攒出大 batch

### $\rm \S \, 20.5.1$ 朴素版：PyTorch 手写

白话：显存装不下 128 个样本，那就一次喂 32 个，但每 4 次才更新一次参数——只要梯度攒对了，优化器看到的东西和一次喂 128 个完全一样。

先看纯 PyTorch 写法（PDF 第 187 页）：

```python
model.train()
optimizer.zero_grad()          # 注意：只在循环外（或每次更新后）清一次

for step, (inputs, labels) in enumerate(dataloader):
    outputs = model(inputs)
    loss = criterion(outputs, labels)
    loss = loss / accumulation_steps   # 关键：把每份 loss 除以累积步数
    loss.backward()                    # 梯度默认累加到 .grad 上

    if (step + 1) % accumulation_steps == 0:   # 每 K 步才更新一次
        optimizer.step()
        optimizer.zero_grad()
```

两个要点：一是别每步 `zero_grad()`（课件原话 Don't zero_grad every step!），清了就把前几个 micro-batch 攒的梯度洗掉了；二是 loss 要先除以累积步数 $K$，为什么，下一小节证。

### $\rm \S \, 20.5.2$ 数学：累积 K 个 micro-batch = 大 batch 梯度（全证）

要证：对 $K$ 个 micro-batch 分别 backward、把梯度加起来，再（在 all-reduce 处）平均，结果与「一整份大 batch 一次算出」的梯度恒等。

设定：把 §20.3.2 里第 $n$ 卡的份数 $\mathcal{B}_n$（$b$ 个样本）再切成 $K$ 个 micro-batch $\mathcal{B}_{n,0},\dots,\mathcal{B}_{n,K-1}$，每个 $b$ 个样本、两两不交、并起来是 $\mathcal{B}_n$。单个 micro-batch 的损失 $L_{n,k}=\frac{1}{b}\sum_{i\in\mathcal{B}_{n,k}}\ell_i$。

先看不缩放会发生什么。对每个 micro-batch 直接 `backward()`，PyTorch 把梯度累加进 `.grad`，$K$ 步之后手里是求和：

$$
\sum_{k=0}^{K-1}\nabla_\theta L_{n,k}
=\frac{1}{b}\sum_{k=0}^{K-1}\sum_{i\in\mathcal{B}_{n,k}}\nabla_\theta\ell_i
=\frac{1}{b}\sum_{i\in\mathcal{B}_n}\nabla_\theta\ell_i
=K\,\nabla_\theta L(\mathcal{B}_n)
$$

读法：第二步又是「micro-batch 两两不交、并起来是 $\mathcal{B}_n$」的拼和；结果是想要的梯度的 $K$ 倍——等效学习率被放大 $K$ 倍，训练直接跑偏。所以每个 micro-batch 的 loss 先除以 $K$（上面代码里的 loss 缩放），累积完后：

$$
\sum_{k=0}^{K-1}\nabla_\theta\frac{L_{n,k}}{K}
=\frac{1}{Kb}\sum_{i\in\mathcal{B}_n}\nabla_\theta\ell_i
=\nabla_\theta L(\mathcal{B}_n)
$$

即「累积 $K$ 个缩放后 micro-batch 的梯度」与「整份 $\mathcal{B}_n$ 一次算出」恒等。再叠加 §20.3.2 的 all-reduce 恒等式，全局就有：

$$
\frac{1}{N}\sum_{n=1}^{N}\sum_{k=0}^{K-1}\nabla_\theta\frac{L_{n,k}}{K}
=\nabla_\theta L(\mathcal{B})
\qquad
|\mathcal{B}|=N\cdot K\cdot b
$$

数字锚：2 卡 × 每卡 16 × 累积 4 步 = 128，与单卡一次吃 128 个样本的梯度逐位相同；换来的代价是前后向各跑 4 遍（时间换显存）。

### $\rm \S \, 20.5.3$ accelerate 版与 sync_gradients 时机

DDP 场景下梯度累积还有第二重收益（PDF 第 188 页）：all-reduce 是慢操作，攒 $K$ 个 micro-batch 才通信一次，通信开销直接降到 ${1/K}$。accelerate 把这套时机管理包进了上下文管理器：

```python
for epoch in range(args.num_train_epochs):
    for batch in dataloader:
        with accelerator.accumulate(optimizer):
            outputs = model(**batch)
            loss = outputs.loss
            accelerator.backward(loss)
            optimizer.step()          # 被包装的 optimizer 拦截
            scheduler.step()
            optimizer.zero_grad()

        if accelerator.sync_gradients:  # 只在优化器真正更新的那一步为 True
            completed_steps += 1
```

表面看每步都在 `step()`，实际上 AcceleratedOptimizer 拦截了调用：前 $K-1$ 个 micro-batch 只攒梯度，`step()` 是空操作；第 $K$ 个 micro-batch 处理完，`sync_gradients` 变为 True，这一步才真正执行 all-reduce、参数更新与清零（累积步数在 prepare 阶段告知 accelerate，见 §20.2.3 的 `AcceleratedOptimizer`）。循环外想数「优化器真走了几步」，也要用 `sync_gradients` 做闸门——课件正是这么写的。

小结：梯度累积的数学只有一句「和要先除以 $K$ 才是平均」，工程上则是「攒梯度、晚更新、少通信」三件事在同一根闸门上对齐。

## $\rm \S \, 20.6$ PyTorch hooks：不改模型代码的观测探针

### $\rm \S \, 20.6.1$ hook 解决什么问题

白话：想看（或想动）网络中间某一层的输出，但又不想把模型代码抄一份出来改——hook 就是挂在一个模块上的「哨兵」，每次前向（或反向）路过它，哨兵先执行你给的函数。

PyTorch hooks 的正式说法（PDF 第 172 页）：hook 是挂到张量或 `torch.nn.Module` 对象上的自定义函数，在前向或反向经过时被调用，可用来监视、修改或记录计算图的中间量，服务于可视化、调试等。课件先问了个反面对照题（PDF 第 173–174 页）：不用 hook，想给某个中间层的激活加噪声（某种 dropout），怎么办？答案是只能拷贝整份模型文件（比如 inclass 例子里 `modeling_llama.py` 那种上千行的文件）改它的 forward——不优雅。hook 让你在外部挂一个函数就办成同一件事。

### $\rm \S \, 20.6.2$ 一个完整可跑的例子

课件的原例（PDF 第 175–177 页，`hooktry.py`）在一个三层小网上挂前向钩子，把中间层输出当场清零：

```python
import torch
import torch.nn as nn

class DNN(nn.Module):
    def __init__(self):
        super().__init__()
        self.l1 = nn.Linear(2, 2)
        self.tanh = nn.Tanh()              # 钩子将挂在它上面
        self.l2 = nn.Linear(2, 2, bias=False)

    def forward(self, x):
        x = self.l1(x)
        x = self.tanh(x)
        return self.l2(x)

model = DNN()
x = torch.randn(1, 2)
print("before hook\n", model(x))           # 钩子还没挂：正常输出

feats = {}
def hook_func(module, inp, out):           # 前向钩子的三参数签名
    feats["feat_ori"] = out.detach().clone()   # 先留底： detach 出图再克隆
    out[:] = out * 0                            # 再当场把该层输出清零

model.tanh.register_forward_hook(hook_func)
print("after hook\n", model(x))            # 挂上之后再前向一次
print("after hook original output:", feats["feat_ori"])
```

课件给出的真实运行输出是：

```text
before hook
  tensor([[0.1726, 0.3461]], grad_fn=<MmBackward0>)
after hook
  tensor([[0., 0.]], grad_fn=<MmBackward0>)
after hook original output: tensor([[-0.5545, -0.0105]])
```

三行输出对应三次提问（课件练习：哪些输出是零？feat_ori 会是零吗？），逐个读：

1. before hook 非零：钩子注册之前的那次 `model(x)` 不受影响，哨兵还没上岗。
2. after hook 是全零：钩子在 `tanh` 输出后当场清零，下一层 `l2` 是无偏置线性层，零输入过线性只得零。
3. feat_ori 非零：它在钩子函数里先于清零被 `detach().clone()` 留了底——`clone()` 是复制一份独立张量，之后的 `out[:] = out * 0` 是原地修改，动不了已克隆的那份。这就是「先留底、再动手」的标准次序。

把 `out[:] = out * 0` 换成 `out + 噪声`，同一个骨架就是「给中间层加噪声」的探针；这也是 DDP 的实现根基——§20.3.4 的 reducer 正是把梯度同步挂成反向钩子，通信才得以藏在 backward 里（课件从 DDP 文档过渡到本节时问的 Hmm...What is a hook? 就埋在这里）。

反向钩子一句版：`register_full_backward_hook` 给的函数拿到 `grad_input` 与 `grad_output`，用来检查或修改梯度，机制与前向对称。

### $\rm \S \, 20.6.3$ 代价与边界

哨兵不是免费的：hook 函数在每次前向都执行，改输出就是在改计算本身（本例中梯度流经被清零的层，反传也会跟着变）；探针忘了卸载（返回的 handle 调 `.remove()`），会一直挂着拖慢并污染后续实验。课件留的 I-homework 是把钩子挂到 Llama 模型的某个操作上试一遍。

小结：hook 是「不改模型代码的观测探针」，读中间量、改中间量、以及框架自己挂通信，用的是同一套机制。

## $\rm \S \, 20.7$ Wandb 与 Gradio：把实验看住、把模型摸到

多卡训练一跑几小时，看不到曲线等于盲飞。课件的做法是 Weights & Biases（wandb，网页端实验监控，PDF 第 189–190 页）：`wandb.init(project=..., config=vars(args))` 把全部超参上报，训练中的 loss 与学习率曲线在网页上实时可看。两个与本章机制直接相关的细节：

1. `wandb.init` 必须放在 `is_main_process` 分支里（§20.2.1 的代码）：多进程各 init 一次会把同一次实验上报成多份。
2. init 之后紧跟 `wait_for_everyone()`：保证非主进程不会抢在实验建档前跑散。

训练完的交付端是 Gradio（PDF 第 192–193 页）：inclass5 用 Gradio 起一个网页聊天界面，直接和微调后的模型对话。课件给了对照组：问「Are you LLM?」，基模型给的是一段续写（从「如果你是 LLM 可以申请牛津奖学金」顺下去的补白，它在补全文本而不是回答问题），微调后的模型才给出像「回答」的应答。白话：微调前它是接龙的笔，微调后才是对话的人——训练系统的效果，最后就在这一个界面上验收。另有一个工程提醒（PDF 第 191 页）：`train.py` 与 `chat.py` 必须共用同一个 `format_chat` 模板，训练时喂什么格式、聊天时就该是什么格式，错位等于白训。

小结：Wandb 管训练中的可观测，Gradio 管训练后的可触摸，两者都以「主进程/共用模板」这类多进程纪律为前提。

## $\rm \S \, 20.11$ 本章自测答案

> 先闭卷作答 §20.9 与 §20.10，再核对。

### $\rm \S \, 20.11.1$ 关键概念回顾答案

1. 每个进程都执行一遍；`print1` 在 `is_main_process` 分支里出现 1 次，`print2` 没有条件挡、出现 2 次。（§20.2.1）
2. 栅栏（barrier），先到的进程等最慢的进程到齐再继续；没有它，rank 1 可能在 rank 0 完成 wandb 初始化前抢跑，后续集体通信挂住或报错。（§20.2.1）
3. model 包成 DDP（或 FSDP），optimizer 包成 AcceleratedOptimizer，dataloader 包成 DataLoaderShard，scheduler 包成 AcceleratedScheduler；拦截 `step()` 的是被包装的 optimizer。（§20.2.3）
4. 完全相同的模型副本、等大的每卡 batch、同步优化全程镜像；global = 2 卡 × 每卡 16 × 累积 4 = 128。（§20.3.1）
5. all-reduce 平均后的梯度等于全局 batch 损失的梯度；前提是每卡等 batch、损失按样本取平均、各卡权重一致。sum 会让梯度大 $b$ 倍，等效偷偷放大学习率。（§20.3.2）
6. DP 是单进程多线程（GIL 争抢、假并行）加 master-slave 的 scatter/gather（主卡瓶颈）；DDP 是每卡一进程（各有解释器）加无中心的 NCCL all-reduce。（§20.3.3）
7. 反向传播期间，靠参数上的 autograd 钩子按桶异步发起、与反向计算重叠；`backward()` 返回时 `.grad` 已是同步后的平均梯度。（§20.3.4）
8. 参数被按 FSDP 单元切分并展平成一维存储，打印时刻未持有（或未收齐）的单元就是 ${[0]}$；8 卡 FSDP = 模型 sharding 到 8 卡 + 8 路数据并行。（§20.4）
9. 累积 $K$ 个 micro-batch 的梯度是求和，等于目标平均的 $K$ 倍，除以 $K$ 才回到平均；`sync_gradients` 为 True 时才真正 all-reduce、更新参数并清零，前 $K-1$ 步的 `step()` 是空操作。（§20.5）
10. 签名是 `hook_func(module, inp, out)`；feat_ori 非零因为它在清零之前被 `detach().clone()` 留底，after hook 全零是因为 tanh 输出被原地清零、`l2` 无偏置。（§20.6.2）

### $\rm \S \, 20.11.2$ 应用与辨析答案

1. 梯度被放大 $b$ 倍，等效学习率放大 $b$ 倍，训练可能发散；恒等式的「损失按样本平均」前提被破坏——DDP 不检查这一点，代码照跑，错在数学。（§20.3.2）
2. 数学上两案等价（都凑出全局 128，恒等式都成立）；通信上前者 all-reduce 仍每优化器步一次但卡间数据切得更碎、每卡激活显存更小，后者把通信频率降到原来的 $1/2$，用时间换显存。卡数加倍还受限于你有没有 4 张卡。（§20.5.2）
3. sharding 不加速：FSDP/DeepSpeed 不支持 TP，切分只是把模型状态摊开存储，每层前向反向还要多付 all-gather 与 reduce-scatter 的通信，一般明显减慢；8 卡 FSDP 的加速全部来自 8 路数据并行。（§20.4）
4. 留底拿到的是清零后的张量，feat_ori 变全零；after hook 仍全零（清零照样生效）；before hook 不受影响（钩子未挂）。次序决定「留的是动手前还是动手后的快照」。（§20.6.2）
