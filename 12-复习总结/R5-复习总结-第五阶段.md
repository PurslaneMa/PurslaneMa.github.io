## $\rm \S \, R5.3$ 核心心智模型复读

下面六个锚点概念在本阶段反复出现，而且都在第 26 章之前就建立过。复习时把新学的细节挂到这些旧锚点上，比单独背命令记得牢——每个锚点标注首次定义的章节，忘了就回读那一章。这六个锚点也是第 46 章贯穿项目的骨架：从命令行工具到可部署应用，每一步都挂在它们上面。

### $\rm \S \, R5.3.1$ 表-行-列：数据的最小组织单位

首次定义于[第 26 章](../07-应用开发/26-SQL从零开始.md)（§26.1）：一张表就是一个二维网格，每一行是一条记录，每一列是一个字段——和 C++ 的 `struct Paper` 是同一个思想，区别只是数据在磁盘上、由数据库引擎管理读写与查询。表上的两根柱子是主键（`PRIMARY KEY`，每一行的唯一标识，像 `std::unordered_map` 的 key）和外键（`REFERENCES`，保证关联列的值一定存在于被引用的表中）——第 26 章的多表设计全靠它们撑起来。这个模型贯穿本阶段：第 26 章的一切查询（筛选、聚合、JOIN）都是在“行”和“列”上做变换；第 27 章的迁移、备份、权限操作的对象也是表和行；第 29 章后端把 `SELECT` 的结果序列化成 JSON 数组——数组元素对应行，对象字段对应列。边界：表是逻辑组织，磁盘上的物理布局（B-tree、页）由引擎决定，你不需要也不应该手动控制。也正是因为引擎擅长在整张表上批量工作，第 26.5.5 节的 N+1 反模式才成立：循环里逐行查标签要 1001 次查询，改成一个 JOIN 让数据库一次搞定。

### $\rm \S \, R5.3.2$ 请求-响应：浏览器、后端、数据库的通用语言

请求-响应模型首次定义于[第 23 章](../04-网络/23-网络基础到HTTP.md)：客户端发请求，服务器回响应。第 28 章的 `fetch` 和你熟悉的 `curl` 做的是同一件事——发 HTTP GET 请求、拿 JSON——区别只在运行位置（浏览器 vs 终端）和结果去向（更新 DOM vs 打印到终端）（§28.3.3）。第 29 章把请求-响应完整走了一遍：路由匹配 → 参数校验 → 业务逻辑 → 序列化 → 错误处理（§29.1），并用 HTTP 方法（GET/POST/PUT/DELETE）和状态码（200/400/404/429/500）给这个模型补充语义。边界：HTTP 本身无状态——服务器不记得你是谁，JWT 和 Session 是在应用层“伪造”的记忆（§29.4）；浏览器同源策略限制 `fetch` 只能访问同源、或服务器通过 CORS 明确允许的跨域地址（§28.3.3）。第 29.5 节的中间件是这条管道上的安检站——日志、认证、CORS 各自只做一件事，串在请求进入处理函数之前和响应离开之后，避免在每个处理函数里重复同样的代码。把这段模型首尾接起来，就是论文管理器的完整请求链：浏览器 `fetch` → 反向代理（Nginx/Caddy）→ Flask 路由 → PostgreSQL——每一跳都是一个请求-响应，出问题时沿这条链逐层排查（§32.3）。

### $\rm \S \, R5.3.3$ 前端/后端分工：谁负责“把数据变成页面”

分工的边界在[第 28 章](../07-应用开发/28-前端开发.md)（§28.1.1）划清：浏览器做两件事——获取资源（通过 HTTP 下载 HTML/CSS/JS/JSON）和渲染页面（把 DOM 变成像素）；后端（[第 29 章](../07-应用开发/29-后端与API.md) §29.1）做另一件事——接收请求、查数据库、把结果序列化成 JSON 返回。前端和后端之间只通过 HTTP 请求与 JSON 响应对话，谁也不直接碰对方的内部状态——这是理解全栈协作的基础。第 28.4 节的组件化（React/Vue/Svelte 的“数据驱动视图”）处理前端内部的复杂度，第 29.3 节的 REST 约定处理两端之间的接口约定。边界：接口一旦定下来，改字段就是破坏性变更——第 29.10 节用 URL 路径版本（`/api/v1/papers`、`/api/v2/papers`）让新旧约定共存：删字段要升版本，加字段不用。

### $\rm \S \, R5.3.4$ 进程、端口与服务：一切“运行中”的东西

“进程是某份程序的一次正在进行的演出”首次定义于[第 1 章](../01-基础观念/01-计算机程序与开发全景.md) §1.2.4，第 11 章把它接到调度、信号与进程树上。第 27 章的 PostgreSQL 就是一场常驻演出——由 systemd 管理、监听 5432 端口的服务进程（§27.1.2）；第 29 章的后端是另一场——不读 `std::cin` 而读 HTTP 请求、不写 `std::cout` 而写 HTTP 响应（§29.1）。端口是演出的“入口编号”：`-p 8000:8000` 把宿主机 8000 入口接到容器内 8000 入口（§30.3.2），反向代理（首次定义于[第 24 章](../04-网络/24-域名HTTPS代理与排障.md)）再把公网请求转发到这些入口。第 29.8 节把第 11 章的 SIGTERM 知识接上了后端：`docker stop` 发 SIGTERM，后端先停收新请求、排空在途请求、再关数据库退出；超过默认 10 秒会补发 SIGKILL 强杀。谁负责“启动、重启、记日志”这件事也有两个时代：第 13 章的 systemd（`systemctl` 管理系统服务）和第 30 章的 Docker Compose（`docker compose` 管理容器）——它们解决同一类编排问题，只是管的对象不同。边界：容器与宿主机共享内核，不是完整虚拟机（§30.1.1）——“在我电脑上能跑”不等于“在服务器上一定没问题”。排查“连不上”时，第 27.5 节的检查顺序（服务在跑吗 → 监听端口对吗 → 防火墙拦吗）与第 32.3 节的五问（现象/时间/范围/变化/哪一层）是同一条证据链，只是粗细不同。

### $\rm \S \, R5.3.5$ 镜像、容器与数据卷：类、对象与对象外的持久化

“镜像=只读模板、容器=运行实例”首次定义于[第 30 章](../08-部署运维/30-Docker基础.md)（§30.2），类比沿用第 15 章的类与对象：镜像像类定义（只读），容器像 `new` 出来的对象（在镜像之上加一层可写层）。同一个镜像能启动多个容器，容器之间互不影响。关键边界在可写层的寿命：`docker rm` 删容器时，可写层连同里面的修改一起消失——所以数据库文件必须放数据卷（volume）里，卷独立于容器生命周期（§30.2；§30.5 的 Compose 里 `pgdata` 就是这样一个命名卷）。Compose 用服务名（`db`、`backend`）互相引用，容器内直接写服务名，不用关心容器 IP。Compose 的 `depends_on` 只保证依赖容器先启动，不保证它“就绪”（比如数据库进程起来了但还没接受连接）——[第 31 章](../08-部署运维/31-部署容器与云服务.md)应用与辨析里的解法是 `healthcheck` + `condition: service_healthy`。

### $\rm \S \, R5.3.6$ 日志与健康检查：部署后不靠“等用户报 bug”

日志作为排障证据首次定义于[第 13 章](../03-计算机系统/13-系统服务日志与软件安装.md)。第 30 章把它带到容器世界：`docker logs <container>`、`docker compose logs -f`（§30.3.1、§30.5）。第 32 章给出“好日志”的标准：毫秒级时间戳、级别、唯一请求 ID、做了什么、结果和耗时（§32.2.1）——没有请求 ID 的日志无法把错误关联到具体请求。健康检查（health check）是部署后的第一个自动化防线：后端提供一个 `/health` 端点（[第 31 章](../08-部署运维/31-部署容器与云服务.md) §31.5），Uptime Kuma 这类监控工具定期从外部探测，服务挂了立刻告警，而不是等用户凌晨三点来报告——它和你本地 `curl /health` 的区别是 24 小时在跑、挂了自动通知你。边界：日志是离散事件，回答“发生了什么”；系统整体健康度要看指标（QPS、P95/P99、错误率），只看日志会漏掉“慢慢变慢”这类趋势。健康状态可以直接从 `docker ps` 的 STATUS 列看到（如 `Up 2 minutes (healthy)`）——第 31 章实践二就是加一个 `/health` 端点并观察这一列。

### $\rm \S \, R5.3.7$ 声明式思考：说“要什么”，而不是“怎么做”

SQL 是声明式的——[编程语言范式概览](../06-编程语言/16-编程语言范式概览.md)介绍过这个范式，[第 26 章](../07-应用开发/26-SQL从零开始.md)（§26.1.5）正式使用：你写 `SELECT ... WHERE ... ORDER BY ...` 描述“要什么”，数据库的查询优化器决定“怎么做”——走哪个索引、用哪种 JOIN 算法。这和 C++ 里手写 `for` 循环逐行判断是两种思维：命令式每一步都自己指定，声明式把执行细节交给引擎。这个模型贯穿本阶段：第 26 章用 `EXPLAIN QUERY PLAN` 观察优化器的决定（SCAN 还是 SEARCH）；第 29 章后端只负责把查询意图翻译成 SQL 交给数据库。边界：声明式把“怎么做”交给引擎，不等于不能影响它——建索引、看执行计划，就是你在和优化器沟通。

## $\rm \S \, R5.5$ 易混点对照

本阶段最容易被混淆或忘记的五个点，逐对列出区别与记忆锚点。容易混的原因各不相同：有的是层级不同但名字相近（数据库/表/索引），有的是动作不同但可以挂在同一个 URL 上（GET/POST/DELETE 靠 HTTP 方法区分），有的是“一个在浏览器、一个在服务器”（前端渲染 vs 后端序列化），有的是“一个在宿主机、一个在容器里”（镜像/容器/卷）。对照表之外只有一条判断方法：先问“这个对象活在哪个层、解决什么问题”，再比较。

| 易混对象 | 区别 | 记忆锚点 |
|---|---|---|
| 数据库 / 表 / 索引 | 数据库是持久存储系统（SQLite 是一个文件，Postgres 是一个服务进程）；表是其中按行-列组织数据的地方；索引是数据库额外维护的加速查询的结构（B-tree），不属于表本身。建了索引不代表查询一定用它——`EXPLAIN QUERY PLAN` 输出 `SCAN` 就是没走索引 | 数据库=书架，表=一本书，索引=书末的目录。目录让“按年份找”变快，但每写一行书、目录也要更新——所以索引不是越多越好 |
| GET / POST / DELETE | GET 读取资源（不改变服务器状态）；POST 创建新资源（每执行一次就多一条数据）；DELETE 删除资源。GET/PUT/DELETE 幂等——执行一次和十次副作用相同；POST 不幂等 | GET 是问路，POST 是下单，DELETE 是撕票。重发问路和撕票都安全，重复下单会重复扣款——POST 需要幂等键 |
| 前端渲染 vs 后端渲染 | 前端（浏览器）拿到 JSON 后用 JavaScript 生成 DOM——渲染发生在有 DOM 的地方；后端只把查询结果序列化成 JSON 返回，不生成页面 | 谁在拼 HTML，谁就是渲染者。后端负责“把数据变成格式”，前端负责“把格式变成画面”——这也是 API 版本管理（§29.10）存在的原因：前端只能按后端给的字段解析 |
| 镜像 / 容器 / 数据卷 | 镜像是只读模板（类定义），容器是镜像的运行实例加可写层（对象），数据卷是独立于容器生命周期的存储。删容器丢可写层，卷里的数据还在 | 镜像=母盘，容器=刻出来的碟，数据卷=碟外的笔记本。碟可以扔，笔记本上的记录还在——数据库文件必须放卷里 |
| SQL 注入 / XSS | 都是“把不可信的数据当代码执行”，但注入点不同：SQL 注入把用户输入拼进 SQL 语句、在数据库里执行；XSS 把用户输入插进 HTML/DOM、在其他用户的浏览器里执行。防御分别是参数化查询与 HTML 转义 | 一个骗数据库，一个骗浏览器；共同对策是“数据与代码严格分离”——用户输入永远是数据，不是代码 |

### $\rm \S \, R5.6.1$ 闭卷回忆清单答案

1. （[第 26 章](../07-应用开发/26-SQL从零开始.md) §26.1.4）

```sql
INSERT INTO papers (title, year) VALUES ('BERT', 2019);
SELECT title, year FROM papers WHERE year >= 2019;
UPDATE papers SET citations = 130000 WHERE id = 1;
DELETE FROM papers WHERE id = 4;
```

`UPDATE` / `DELETE` 永久修改数据且没有撤销（除非包在事务里），执行前先把语句中的 `UPDATE`/`DELETE` 换成 `SELECT *` 跑一遍，确认 `WHERE` 选中的正是要改或删的行。在 sqlite3 交互里逐条执行：INSERT 后 SELECT 能看到新行，UPDATE 后 SELECT 确认修改，DELETE 后 SELECT 确认行消失。

2. （[第 26 章](../07-应用开发/26-SQL从零开始.md) §26.2.1）SQL 里 `NULL = NULL` 的结果是 `NULL`（既不是 TRUE 也不是 FALSE），所以 `venue = NULL` 永远匹配不到任何行；判断空值必须写 `WHERE venue IS NULL`（或 `IS NOT NULL`）。

3. （[第 26 章](../07-应用开发/26-SQL从零开始.md) §26.3.2–26.3.3）三张表：`papers`（论文实体）、`tags`（标签实体）、`paper_tags`（关联表，只有 `paper_id` 和 `tag_id` 两个外键，联合主键保证同一对不重复）。查询用 JOIN：

```sql
SELECT p.title FROM papers p
JOIN paper_tags pt ON p.id = pt.paper_id
JOIN tags t ON pt.tag_id = t.id
WHERE t.name = 'transformer';
```

4. （[第 27 章](../07-应用开发/27-数据库基础.md) §27.1–27.2）SQLite 是嵌入式文件数据库：程序直接读写 `.db` 文件，没有独立服务进程，只支持一个写者——适合移动 App、单机分析和原型；PostgreSQL 是客户端-服务器数据库：独立服务进程（systemd 管理）监听 5432 端口，多用户、细粒度权限——适合多人并发写和生产 Web 应用。连接字符串包含协议、主机、端口、用户名、密码、数据库名；密码不从源码读取，从环境变量注入。连接方式有三类：命令行客户端（`psql`、`sqlite3`）、图形客户端（DBeaver、pgAdmin）、应用代码里的数据库驱动。

5. （[第 27 章](../07-应用开发/27-数据库基础.md) §27.3–27.4）迁移解决“表结构变更无法同步、无法追溯、无法回滚”：手动 `ALTER TABLE` 只有执行者本地知道，队友和生产环境的结构就分叉了。规则：迁移脚本按编号顺序执行、永远向前追加、不修改已有迁移，所有环境跑同一序列，结构一致可复现。备份必须定期演练恢复——一个从未被恢复过的备份可能是损坏的，只是你还没发现。

6. （[第 28 章](../07-应用开发/28-前端开发.md) §28.1–28.3）HTML 描述结构（页面上有什么），CSS 描述外观（长什么样），JavaScript 描述行为（用户操作时怎么响应）。DOM 是浏览器解析 HTML 后在内存中构建的节点树——HTML 源码是文本，DOM 是它的结构化表示，JavaScript 通过遍历和修改 DOM 动态改变页面。操作 DOM 的三件套：查找元素（`getElementById`、`querySelectorAll`）、修改内容与样式（`textContent`、`style`）、响应事件（`addEventListener`）。最小验证：双击 index.html 打开页面，按 F12 在 Console 里执行 `document.getElementById('paper-list').children.length`，能看到渲染出的条目数。

7. （[第 29 章](../07-应用开发/29-后端与API.md) §29.1）路由匹配（URL → 处理函数）、参数校验（非法输入返回 400 而不是 500）、业务逻辑（查询数据库、计算）、序列化（对象 → JSON）、错误处理（数据库挂了返回 503 而不是崩溃）。错误处理还要区分“用户的错”和“服务器的错”：参数非法是 400，服务器内部问题才是 500/503——前者重试无用，后者值得重试（呼应 §29.7 的重试纪律）。

8. （[第 29 章](../07-应用开发/29-后端与API.md) §29.3、§29.7）GET 读取、POST 创建、PUT 完整更新、DELETE 删除。POST 不幂等——每发一次就多创建一条数据；PUT/DELETE 天然幂等，重发多少次副作用相同。幂等键：客户端为一次业务动作生成 UUID 随请求发送，服务器以它为主键，第一次处理并保存结果，同一个 key 再来直接返回第一次的结果——重复的 POST 不会产生第二行数据。客户端配合重试的纪律（§29.7）：超时和 5xx 值得重试，按指数退避（1s、2s、4s）；4xx 不重试——请求本身有错，重一万次结果一样，唯一的例外是 429。

9. （[第 30 章](../08-部署运维/30-Docker基础.md) §30.2、§30.3.2）镜像是只读模板（类定义），容器是镜像的运行实例加一层可写层（对象），数据卷独立于容器生命周期、用于持久化（删容器不删卷）。`-p 8000:8000` 左边是宿主机端口、右边是容器内端口——访问宿主机 8000 会转发到容器内 8000。验证方法：`docker ps` 的 PORTS 列会显示 `0.0.0.0:8000->8000/tcp`。

10. （[第 31 章](../08-部署运维/31-部署容器与云服务.md) §31.1–31.2）四样东西：有公网 IP 的服务器、域名（DNS 把域名解析到 IP）、HTTPS 证书、反向代理（接收公网请求转发给容器内应用）。Caddy 默认自动获取并续期 Let's Encrypt 证书，Nginx 需要手动用 Certbot 完成这一步。上线方式也有两种：手动部署（`git clone` + `docker compose up -d`）适合学习和个人项目，每步都透明可控；CI/CD 在测试通过后自动拉取、构建、部署（§31.3），适合团队和频繁更新。域名生效的验证：`nslookup papers.example.com`（或 `dig`）应返回服务器 IP——这一步在分层排障里属于 DNS 层。

11. （[第 32 章](../08-部署运维/32-安全可观测性与故障排查.md) §32.1）至少答出四种：① SQL 注入 → 永远参数化查询、不拼接用户输入；② XSS → 永远不把用户输入直接插入 HTML（React/Vue 默认转义）；③ 敏感数据泄露 → 密钥不进源码、不进 Git 历史，泄露后立即在服务端轮换；④ 认证与授权缺陷 → 每个资源操作都检查当前用户是否有权限，不能只在前端隐藏按钮；⑤ 依赖漏洞 → 定期 `pip-audit` / `npm audit` 扫描并升级。密钥分两级管理：项目级用 `.env` 和 GitHub Secrets（跟着项目走但不进 Git），个人级（你的 GitHub Token、数据库密码）放 Bitwarden/1Password 这类密码管理器，而不是明文笔记。

12. （[第 32 章](../08-部署运维/32-安全可观测性与故障排查.md) §32.2–32.3）日志回答“发生了什么”（离散事件，要有时间戳、请求 ID、结果和耗时）；指标回答“系统整体怎么样了”（QPS、P50/P95/P99 延迟、错误率）；链路追踪回答“一个请求走了哪些路、瓶颈在哪一步”。排障顺序：现象 → 时间范围 → 影响范围 → 最近有什么变化 → 按层排除（DNS → TCP → TLS → HTTP → 应用 → 数据库），每层用对应命令收集证据。修好后写一份五问复盘（发生了什么 / 第一信号 / 根因 / 修复 / 防复发）——下一次类似故障就不用从头排查（§32.3.3）。

### $\rm \S \, R5.6.2$ 交错练习答案

第一组：

1. （[第 26 章](../07-应用开发/26-SQL从零开始.md) §26.2.2）

```sql
SELECT title, year FROM papers
WHERE year >= 2020
ORDER BY citations DESC
LIMIT 5;
```

在 sqlite3 里执行后应返回恰好 5 行，第一行是引用数最高的论文。

2. （[第 30 章](../08-部署运维/30-Docker基础.md) §30.4）

```dockerfile
FROM python:3.12-slim
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]
```

先复制依赖列表、再 `RUN pip install`、最后复制源码——只要 `requirements.txt` 没变，`pip install` 这一层会被 Docker 层缓存命中，不必每次构建都重新下载依赖。注意 `EXPOSE 8000` 只是文档（声明容器监听哪个端口），真正让宿主机能访问靠的是 `-p` 端口映射。构建运行：

```bash
docker build -t paper-api .
docker run -p 8000:8000 paper-api
```

成功标志：`curl http://localhost:8000/api/papers` 返回 JSON；`docker ps` 能看到运行中的容器，`docker logs <容器>` 能看后端输出。

3. （[第 28 章](../07-应用开发/28-前端开发.md) §28.3.3）

```javascript
async function loadPapers() {
    const res = await fetch('/api/papers');
    const papers = await res.json();
    const list = document.getElementById('paper-list');
    papers.forEach(p => {
        const li = document.createElement('li');
        li.textContent = `${p.title} (${p.year})`;
        list.appendChild(li);
    });
}
loadPapers();
```

浏览器禁止 `fetch` 在 `file://` 协议下工作（同源策略的一部分），必须通过 HTTP 访问：先 `python -m http.server 8080` 再打开 `http://localhost:8080`。`fetch` 和 `curl` 是同一件事——发 HTTP GET、拿 JSON。渲染时还要处理三种状态：加载中、成功、错误（提示加重试按钮）——这是第 28 章实践三的内容。

4. （[第 26 章](../07-应用开发/26-SQL从零开始.md) §26.4）

```sql
BEGIN TRANSACTION;
UPDATE papers SET citations = citations + 100 WHERE venue = 'NeurIPS';
ROLLBACK;
```

`ROLLBACK` 撤销本次事务内的所有修改，`COMMIT` 才让它们生效。中途断电或报错时，数据库保证事务内的操作要么全部生效、要么全部撤销（原子性）——不会出现“引用数加了但审计日志没写”这种一半生效的状态。

第二组：

1. （[第 31 章](../08-部署运维/31-部署容器与云服务.md) §31.9；[第 28 章](../07-应用开发/28-前端开发.md) §28.3.3）本地开发时 Vite 代理把 `/api/*` 转发到后端，浏览器看来是同源请求，不触发跨域检查；生产部署后浏览器直接向另一个源发请求，被同源策略拦截。修复：后端加 CORS 响应头，或让反向代理把前端和后端统一到同一域名下（Nginx 的 `location /` 与 `location /api/` 都 `proxy_pass` 到本地端口）。

2. （[第 27 章](../07-应用开发/27-数据库基础.md) §27.3）手动 `ALTER TABLE` 只有执行者本地知道，队友本地和生产环境的结构会分叉，且无法追溯、无法回滚。用迁移：写一个编号脚本（如 `002_add_abstract.sql`）：

```sql
ALTER TABLE papers ADD COLUMN abstract TEXT;
```

所有环境按编号顺序执行同一序列，结构一致。成熟的迁移工具（Python 的 Alembic、Node 的 Knex.js）管理的就是这套编号脚本，你手写的 `001_xxx.sql` 是它的最小形态。

3. （[第 29 章](../07-应用开发/29-后端与API.md) §29.4.2）不能。JWT 的 payload 只是 Base64 编码（可解码读取），不是加密；它的安全来自签名（防篡改），不来自加密（防读取）。密码等敏感信息永远不放 JWT。

4. （[第 27 章](../07-应用开发/27-数据库基础.md) §27.4.2）

```bash
pg_dump paperdb > backup.sql        # 备份（导出为 SQL 文本）
psql paperdb < backup.sql           # 恢复
```

恢复必须在演练中验证：备份文件可能损坏、权限错误或格式不兼容，只有实际恢复一次才能确认备份有效——“从未恢复过的备份等于没有备份”。演练的验证方法：恢复后 `SELECT COUNT(*) FROM papers` 应回到备份时的行数。

5. （[第 31 章](../08-部署运维/31-部署容器与云服务.md) §31.2.1–31.2.2）

```nginx
server {
    listen 80;
    server_name papers.example.com;
    location /api/ {
        proxy_pass http://localhost:8000;
    }
}
```

Caddy 版本用 `handle_path /api/* { reverse_proxy localhost:8000 }` 表达同样转发，并且自动完成 HTTPS（自动获取并续期 Let's Encrypt 证书）——Nginx 需要手动用 Certbot。

第三组：

1. （[第 32 章](../08-部署运维/32-安全可观测性与故障排查.md) §32.3.2）① 服务是否在运行：`docker ps`（或 `systemctl status`）；② 后端日志有无错误：`docker compose logs backend`；③ 反向代理配置的 `proxy_pass` 地址是否正确（容器端口是否变了、容器 IP 是否换了）；④ 数据库是否可连：`psql` 连接后 `SELECT COUNT(*) FROM papers`。按 TCP → HTTP → 应用 → 数据库逐层排除，不要先猜结论再找证据。

2. （[第 29 章](../07-应用开发/29-后端与API.md) §29.9）固定窗口的边界漏洞：第 59 秒用光当前窗口的 60 次额度，第 61 秒进入新窗口又满血 60 次，两个窗口的额度在 2 秒内叠加成 120 次。改滑动窗口（统计最近 60 秒内的实际请求数）或令牌桶（恒定速率补充令牌 + 桶容量允许短时突发），被拒的请求返回 429 和 `Retry-After` 头。

3. （[第 29 章](../07-应用开发/29-后端与API.md) §29.8）收到 SIGTERM 后：停止接受新请求（返回 503）→ 等待在途请求完成（排空，设超时上限）→ 关闭数据库连接（提交或回滚未完成的事务）→ 进程退出。不能无限等：`docker stop` 发完 SIGTERM 默认等 10 秒就补发 SIGKILL 强杀——排空时间必须小于调用方的耐心。生产环境用 gunicorn 这类 WSGI 服务器时，排空逻辑由它内置（如 `--graceful-timeout`），原理和上面“标志位 + 在途请求跑完”相同。

4. （[第 26 章](../07-应用开发/26-SQL从零开始.md) §26.5）`SCAN` = 全表扫描（$\mathcal{O}(n)$），没有使用索引。对 `WHERE year = 2020` 这类筛选建索引：

```sql
CREATE INDEX idx_papers_year ON papers(year);
```

再 `EXPLAIN QUERY PLAN` 同一查询应变为 `SEARCH`（$\mathcal{O}(\log n)$）。注意边界：表很小、或筛选命中的行比例很高时，优化器可能仍选 SCAN 而且更快——用 `EXPLAIN ANALYZE` 看实际执行计划和耗时，而不是只看有没有索引。另外 `LIKE '%xxx'`（前导通配符）这类写法无法使用普通索引——精确匹配 `=` 才能稳定走索引（第 26 章应用与辨析）。
