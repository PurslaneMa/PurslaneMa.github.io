# $\rm Chapter \, 8$ TLS 1.3 解剖：把积木装成协议

前七章的零件齐了：AES-GCM 提供带认证的加密（本册第 4 章），ECDHE 协商共享秘密（第 5、7 章），签名与证书绑定身份（第 6 章），哈希与 HKDF 把材料派生成密钥（第 3 章）。但浏览器每天打开 HTTPS 时，这些零件以什么顺序、在哪些消息里、防住哪些攻击运转，是一个独立的设计问题，协议设计的问题不在算法，而在次序与组合。本章解剖 TLS 1.3：逐条消息读握手、看密钥怎么派生、讲清前向保密，最后把整条握手按第 1 章的攻击模型逐项对账。

> **开始前自检**：本章假设你已经会：
>
> 1. □ AEAD（AES-GCM）的接口与 nonce 纪律（本册第 4 章；§8.2 起所有加密消息都用它）；
> 2. □ ECDH 流程与共享点的 $x$ 坐标如何取用（本册第 5、7 章；§8.3 的输入）；
> 3. □ 签名验签与证书链（本册第 6 章；§8.2 的 `CertificateVerify`）；
> 4. □ 哈希作为「定长指纹」的性质（本册第 3 章；§8.2–§8.3 的握手上下文）；
> 5. □ 攻击模型：从被动窃听到主动篡改、中间人（本册第 1 章；§8.4 逐条对账）。

## $\rm \S \, 8.1$ 问题：零件与协议之间差什么

给浏览器与服务器各发一份第 4、6、7 章的算法清单，它们仍然通不了话。零件之上至少缺三样东西。其一，**次序**：必须先验证对面的身份、再交付应用数据；验证本身又要靠已协商的加密保护，鸡生蛋问题需要精确切分。其二，**派生**：ECDH 给出的是一个点/一个大整数，AES-GCM 需要的是定长密钥，还要客户端与服务器各用各的、且与握手绑定。其三，**绑定**：每条消息都要被「钉」在整场对话上，否则早期的明文消息（如 `ClientHello`）可以被攻击者替换或降级。TLS 1.3 的握手就是这三件事的答案。

给三个缺口挂号：次序在 §8.2，派生与前向保密在 §8.3，恢复与对账在 §8.4。

先按第 1 章的攻击模型预演读者即将看到的每条消息：窃听者能读到什么（参数与证书，本就该公开），篡改者改什么会露馅（签名与 MAC 处爆），冒充者缺什么（CA 链与私钥）。带着这三问读下一节。次序的秘密藏在消息的排列里，现在进握手。

读法约定：下文所有反引号内的名字都是 TLS 的消息字段名，出现顺序即真实顺序。

## $\rm \S \, 8.2$ 握手逐消息读法

完整握手五步（`{}` 起的从该条起已被 AEAD 加密）：

```text
ClientHello            →  密钥分享 + 参数清单（明文）
ServerHello            ←  选定参数 + 密钥分享（明文）
{ EncryptedExtensions  ←  附加参数
  Certificate          ←  证书链
  CertificateVerify    ←  对握手上下文的签名
  Finished             ←  对握手上下文的 MAC  }（ServerHello 之后即加密）
{ Finished             →  客户端对握手上下文的 MAC }
```

| 消息 | 方向 | 内容 | 加密与否 |
| --- | --- | --- | --- |
| `ClientHello` | $\to$ | ECDHE 密钥分享、套件清单、随机数 | 明文 |
| `ServerHello` | $\leftarrow$ | 选定套件、密钥分享 | 明文 |
| `EncryptedExtensions` | $\leftarrow$ | 其余参数 | 加密 |
| `Certificate` | $\leftarrow$ | 证书链 | 加密 |
| `CertificateVerify` | $\leftarrow$ | 对握手上下文的签名 | 加密 |
| `Finished` | $\leftarrow\to$ | 对握手上下文的 HMAC | 加密 |

先看五条消息各装了什么，再逐条读它们解决什么。

> **易混点**：`CertificateVerify` 签的是握手上下文，不是证书本身；`Finished` 用 HMAC 而非签名。前者证明「证书的主人同意这场握手」，后者证明「双方看到同一份握手」且通道已经可用。`ClientHello` 携带 ECDHE 密钥分享（本册第 7 章的 $aG$）与支持的密码套件清单，第一条消息就发密钥材料，握手从两轮往返压到一轮。`ServerHello` 选定一个套件并给出 $bG$，此刻双方已能算出 ECDH 共享秘密，立刻派生出「握手流量密钥」，把后续全部消息关进 AES-GCM。`Certificate` 交出证书链（第 6 章）。`CertificateVerify` 是关键设计：服务器不是孤立地签「我的公钥」，而是签**到此刻为止全部握手消息的哈希**：证书与这场具体对话绑定，第 5 章那种「把 `ClientHello` 的参数换成弱选项」的降级攻击，会因为哈希对不上而在验签处失败。`Finished` 双方各发一次：对同一份握手上下文的 HMAC，收到的那个值对不上，说明双方看到的对话不一致，握手立刻作废，它同时是「加密通道确实通了」的测试。两条 Hello 里的 32 字节随机数也随握手哈希一起被签名与 MAC 覆盖，「新鲜性」由此进入每一份计算。

整套五步只花一次往返：客户端发出自己的 `Finished` 时即可开始发应用数据，比 TLS 1.2 少一整轮。还有一处与直觉不符的设计值得点破：整条握手认证的是**服务器**，客户端默认匿名，浏览器的身份（账号、Cookie）在 TLS 建成之后由应用层登录完成，客户端证书只在企业内网等少数场景出现。

**本节小结**：五条消息各管一件事——两条 Hello 换出共享秘密，`Certificate`/`CertificateVerify` 把身份钉进这场对话，`Finished` 确认双方看到同一份握手；从 `ServerHello` 起全部加密，一次往返即建成通道。钥匙是怎么从那个共享秘密造出来的，下一节细看。

## $\rm \S \, 8.3$ 密钥导出与前向保密

ECDH 共享秘密是一个点坐标，离 AES-GCM 要用的密钥还差两步。第一步 HKDF-Extract 把任意长度的输入材料「浓缩」成定长的伪随机密钥；第二步 Expand 用不同的标签（label）从它派生出多把互相独立的密钥。用 SHA-256 实跑（输入材料用 RFC 5869 的测试向量演示结构）：

```python
import hashlib, hmac
prk = hmac.new(b"tls13 derived", b"\x0b" * 22, hashlib.sha256).digest()
def expand(prk, info):
    t = b""; out = b""
    for i in range(1, 3):
        t = hmac.new(prk, t + info + bytes([i]), hashlib.sha256).digest()
        out += t
    return out[:32]
print(expand(prk, b"tls13 c ap traffic").hex()[:32])  # 14cb18abb385ea7148e1b172074812a5
print(expand(prk, b"tls13 s ap traffic").hex()[:32])  # 3e43d9d201f37458bc649bfa35114a37
```

同一个 `prk`，标签不同，导出的客户端密钥与服务器密钥完全不同（第 3 章哈希的雪崩效应保证这点）；握手流量密钥与应用流量密钥同理分开，各自作废互不牵连。Extract 与 Expand 分成两步也是纪律：Extract 负责「把不均匀的材料变均匀」，Expand 负责「从均匀材料批量造钥匙」，职责分开，任何一步出问题都能单独定位。

> **经验规则**：0-RTT 的取舍口诀，重放无妨才上 0-RTT；拿不准就当它不防重放，退回普通 1-RTT。

这套流程的深层收益是**前向保密（forward secrecy）**：会话密钥来自**临时（ephemeral）** ECDH，私钥 ${a,b}$ 在握手结束即丢弃，从不落盘、从不上线。日后服务器长期私钥即便泄露，攻击者翻旧流量也一无所获：旧会话密钥只活在 $(a,b)$ 里，而它们已经不存在了。反面教材是 TLS 1.2 时代的静态 RSA 密钥交换：客户端直接用服务器证书里的公钥加密预主密钥，历史流量全程可被录下，只要日后拿到那把私钥，把历史密文逐条解开即可。前向保密把「密钥泄露」的伤害半径从「过去全部流量」缩到「未来会话」，这正是第 1 章攻击模型里「事后泄露长期密钥」这一档的正面回应。

握手建成通道后，每条应用数据在记录层（record layer）进出 AES-GCM：每个方向规定一个静态 IV，记录的 nonce 由它与单调递增的序列号异或得到，第 4 章「nonce 绝不复用」的纪律在这里被协议结构而非运气满足；序列号同时作为 AEAD 的附加认证数据进标签，乱序、删除与重排立刻在校验处现形。TLS 没有发明新密码学，只是把纪律固化成了状态机。

整条密钥路线图收拢成四级：

1. ECDH 共享秘密（点坐标的一个分量）；
2. HKDF-Extract：浓缩成定长的伪随机密钥；
3. HKDF-Expand 按标签分岔：握手流量密钥与应用流量密钥，客户端/服务器各一套；
4. 每条记录：AEAD 密钥配序列号派生的 nonce，逐条加密认证。

会话密钥的完整生命周期也只在内存里：不落盘、不进日志、不随备份走，前向保密不只靠 ECDHE 的临时性，也靠这份「无处可查」的洁癖。

**本节小结**：本节走完密钥的四段旅程——ECDH 出秘密、Extract 浓缩、Expand 按标签分岔、逐条记录加密；临时私钥用完即焚换来前向保密，nonce 唯一性则由 IV 异或序列号的结构保证。通道修好了，接下来看断线怎么便宜地重连、以及整条握手对攻击模型的对账。

## $\rm \S \, 8.4$ 会话恢复、0-RTT 与攻击模型对账

重连时不必重跑全套 ECDH：TLS 1.3 用预共享密钥（PSK）恢复会话，甚至允许客户端在第一个飞行里就捎上应用数据（0-RTT）。代价要说破：0-RTT 数据没有握手提供的防重放保护，攻击者录下这条早期请求原样重发，服务器可能当真（对「下单」「转账」类请求危险），所以 0-RTT 只用于幂等请求。另补一句恢复模式的结构：新会话密钥由 PSK 与新鲜的 ECDH 共同派生，前向保密得以保留；若省掉 ECDH 只用纯 PSK，这一层就没了，TLS 1.3 把两种模式都留给不同场景自选。会话票据由服务器的票据加密密钥保护，这把钥匙自身也要轮换，恢复会话的前向保密半径跟着它的轮换周期走。这是「性能换安全余量」的典型交易。

按第 1 章的攻击强度阶梯给整条握手对账：

| 攻击（强度递增） | 挡住它的机制与消息 |
| --- | --- |
| 被动窃听 | `ServerHello` 后全部 AEAD 加密（第 4 章）；ECDH 共享秘密从未上线（第 5、7 章） |
| 主动篡改/降级 | AEAD 标签逐条认证；`CertificateVerify` 与 `Finished` 把每条消息钉进握手哈希 |
| 中间人冒充 | 证书链验到根证书（第 6 章），签名覆盖握手上下文，调包即失败 |
| 长期密钥事后泄露 | 临时 ECDH 的前向保密：旧会话密钥已随 $(a,b)$ 消失 |

四个台阶各有专属机制，缺一阶整条协议就退回上一章的裸零件。这正是「安全性相对攻击模型而言」（本册第 1 章）在工程里的样子。反过来读这张表同样成立：任何一条机制被关掉（为兼容老设备而降级），对应档位的攻击立刻复活，协议的安全性等于链条上最弱的一环。

> **易混点**：前向保密防的是「长期密钥事后泄露」，不防「今天被窃听」；设备中马这类主动攻破发生时，会话密钥就在内存里，任何保密机制都救不回当场的那次对话。
>
> 另一个常被混用的词是「后量子」：它指「能抗量子计算机的算法」，不是「量子加密」。

**本节小结**：恢复用 PSK 省一轮 ECDH，0-RTT 再省一轮但放弃防重放，只敢装幂等请求；对账表的四个攻击台阶各有专属机制，关掉任何一环对应攻击立刻复活——安全等于最弱一环，这是本章收束时最该带走的一句话。

## $\rm \S \, 8.5$ 关键概念回顾

1. 零件清单到可用协议，缺的「次序、派生、绑定」三件事分别由握手的哪个设计承担？
2. `CertificateVerify` 为什么签的是握手上下文哈希而不是证书本身？它挡住第 5 章的哪类攻击？
3. HKDF 的 Extract 与 Expand 各干什么？为什么客户端与服务器密钥要分开派生？
4. 前向保密防的是哪一档攻击？静态 RSA 密钥交换为什么没有它？
5. 0-RTT 省了什么、丢了什么？什么样的请求才敢放进 0-RTT？

## $\rm \S \, 8.6$ 应用与辨析

1. 同学说：「HTTPS 用的 AES-GCM 里 nonce 是随机数，说明 nonce 纪律（第 4 章）在 TLS 里靠运气。」指出错在哪。
2. 攻击者录下一次完整握手与 0-RTT 请求「向我的账户充值 1 元」，一周后原样重放。哪些机制会拦住它？0-RTT 呢？
3. 某老服务器仍开静态 RSA 密钥交换。解释为什么「今天部署的 HSM（Hardware Security Module，硬件安全模块）硬件保护私钥」并不能挽回过去流量的保密性。

## $\rm \S \, 8.7$ 本章自测答案

> 先闭卷作答上面两节，再核对。

### $\rm \S \, 8.7.1$ 关键概念回顾答案

1. 次序由「`ServerHello` 即派生握手密钥、其后消息全部加密」的切分承担，密钥分离的完整说法是「阶段 × 方向」各一把钥匙；派生由 HKDF 的标签化 Expand 承担；绑定由 `CertificateVerify` 与 `Finished` 对握手哈希签名/MAC 承担。（§8.2、§8.3）
2. 孤立签证书只证明「证书是真的」，不证明「这场对话用的是它」；签握手上下文把身份与参数、密钥分享钉在一起，参数被替换则哈希变、验签败，挡住的是篡改与降级式中间人。（§8.2）
3. Extract 把不均匀的输入材料浓缩成均匀伪随机密钥；Expand 用不同标签从同一密钥派生多把独立密钥。分开是密钥分离纪律：一把泄露或被误用不波及其他方向/阶段。（§8.3）
4. 防的是「事后获得服务器长期私钥」这一档。静态 RSA 交换把秘密直接用长期公钥加密进历史流量，私钥到手即可回溯解密；ECDHE 的秘密依赖已销毁的临时私钥。（§8.3）
5. 省掉一轮往返（应用数据随第一飞行发出）；丢掉防重放。只有重放无害的幂等请求（如查询）才可放入。（§8.4）

### $\rm \S \, 8.7.2$ 应用与辨析答案

1. 错在机制：TLS 1.3 的 AEAD nonce 由「静态写方向 IV」与「序列号」异或派生，序列号严格递增，每次连接重置并换 IV，nonce 唯一性由协议结构保证，不靠随机数运气。（§8.2、§8.3）
2. 重放整场握手会被拦：握手有随机数与（若服务器验证）会话票据时效， Finished 的 MAC 也覆盖时间性上下文。0-RTT 应用数据本身没有防重放保护。这正是 §8.4 的警告，幂等性才是真正的防线。（§8.4）
3. HSM 只保护私钥「从今天起」不被读出；历史流量里的预主密钥是当时用该私钥解密的，攻击者早已录下密文，一旦（以任何方式）用出私钥即可回溯解开全部旧流量，前向保密的缺席不能用硬件追认。（§8.3）
