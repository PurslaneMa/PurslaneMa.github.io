# $\rm Chapter \, 7$ 死锁：四个条件与机械化破解

上一章结尾说过：锁一多，就有人同时拿两把。两个线程各持一把锁、都在等对方手里那把，谁也不会放，谁也等不到，这就是死锁（deadlock）。它不像竞态那样「算错但能跑完」，而是整组线程永久卡死；线上事故里最难复盘的一类，因为现场毫无输出，日志停在半句话上。本章把这种死法机器化：先在实验里亲手造一场，再拆出它成立的四个必要条件，即破掉任意一条，死锁就不可能发生。

> **开始前自检**：本章假设你已经会：
>
> 1. □ 写出「读-改-写」竞态的缝，知道锁的职责是把缝焊死（§6.1）；
> 2. □ 解释「同时持有多把锁」是把程序送进本章领地的那一步（§6.7 末段）；
> 3. □ 知道线程共享所在进程的地址空间（§2.6）；
> 4. □ 知道数据库的「事务」是把多条写打包的边界（计算机速通 §26.5）。

## $\rm \S \, 7.1$ 死锁的现场：亲手造一场

两个线程、两把锁，各自先拿一把、睡一小会保证对方也拿到了，再去抢对方那把：

```python
import threading, time
lock_a, lock_b = threading.Lock(), threading.Lock()
deadlocked = threading.Event()

def t1():
    with lock_a:
        time.sleep(0.05)                    # 保证两把锁都已被拿住
        if not lock_b.acquire(timeout=2):
            deadlocked.set()                # 2 秒拿不到 = 死锁现场

def t2():
    with lock_b:
        time.sleep(0.05)
        if not lock_a.acquire(timeout=2):
            deadlocked.set()

th1, th2 = threading.Thread(target=t1), threading.Thread(target=t2)
t0 = time.perf_counter()
th1.start(); th2.start(); th1.join(); th2.join()
print(f"死锁发生: {deadlocked.is_set()}，耗时 {time.perf_counter()-t0:.2f}s")
```

本机（Windows / Python 3.12.10）输出：

```text
死锁发生: True，耗时 2.06s
```

如果没有 `timeout=2`，这两个线程会永远卡在 `acquire` 上。这就是生产事故的形态：线程池里两个工人互等，外部请求源源不断进来排在他们后面，服务「活着但不响应」。`timeout` 只是让我们能观察到卡死并退出，不是解药。

**本节小结**：两个线程交叉持锁即死锁，现场特征是「活着但不响应」；下一节把这种死法拆成四个可检验的必要条件。

## $\rm \S \, 7.2$ 四个必要条件：缺一不死

死锁要成立，以下四个条件必须**同时**成立（ Coffman 条件）。逐条定义：

1. **互斥（mutual exclusion）**：资源一次只能被一个执行流持有。两把锁满足；只读的共享数据不满足，它人人可同时用，争不起来；
2. **持有并等待（hold and wait）**：执行流持有至少一个资源，同时还在等别的。§7.1 的两个线程都在「拿着一把、等另一把」；
3. **不可剥夺（no preemption）**：资源只能由持有者自愿释放，别人抢不走。Python 的锁没有「强制撬锁」的接口；
4. **循环等待（circular wait）**：存在一条环，$T_1$ 等 $T_2$ 手里的资源，$T_2$ 又等 $T_1$ 的。环可以更长：三个线程首尾相接同样死。

「必要条件」给了一个机械化结论：**破掉任意一条，死锁在逻辑上就不可能发生**。四种破解姿势正是对着四条来的。

**本节小结**：互斥、持有并等待、不可剥夺、循环等待，四者缺一不死；破解不必四条全破，破掉任意一条就够。

## $\rm \S \, 7.3$ 破解姿势：对着条件逐条开火

1. **锁排序，即破循环等待**。约定全程序「任何时刻要拿多把锁，一律按固定顺序（如锁地址或编号）获取」。环需要「有人逆序拿」，全员同序则无人逆序，环不成立。§7.1 的两个函数改成都先拿 A 再拿 B：

   ```python
   def t1s():
       for lk in (lock_a, lock_b): lk.acquire()
       for lk in (lock_a, lock_b): lk.release()
   def t2s():   # 同序，不再各持一把
       for lk in (lock_a, lock_b): lk.acquire()
       for lk in (lock_a, lock_b): lk.release()
   ```

   实测同一场景（本机）：

   ```text
   锁排序后耗时 0.0012s，无卡顿
   ```

   从 2.06 秒的互等到 1.2 毫秒干净跑完。这是工程里首选的姿势：不花运行时代价，只花纪律成本，即所有拿锁代码遵守同一全序；
2. **try-lock 回退，即破持有并等待**。拿第二把锁改用 `acquire(timeout=…)` 或 `try_acquire`，拿不到就**释放已持有的**、退避后重来。等待不再「持有着等」，条件 2 破。代价是回退重试的白做功与实现复杂度，常用于无法统一排序的存量代码；
3. **一次性申请，即破持有并等待的另一刀**。开头的自检框若不成立就先补：需要几把锁，在最外层一次全部拿齐再进临界区，绝不「先拿一把再要一把」。银行转账典型：`transfer(A, B)` 一开始就同时锁 A、B，锁不齐就都不锁。简单粗暴，代价是锁的持有时间变长、并发度下降；
4. **超时与恢复，给不可剥夺开实用后门**。条件 3 在语言层面破不掉（没有强制撬锁接口），但可以配看门狗：检测到线程持锁超时，杀掉整个事务或进程重启。数据库的「死锁检测 + 回滚一方」就是这条路（§7.4）。

四条里没有一条叫「加更多锁」，锁越多，排序与审计的负担越重。经验规则回到 §6.7：先粗后细，出现争用再拆，拆时立刻补排序约定。

**本节小结**：锁排序破循环等待、最便宜所以是首选；try-lock 回退与一次性申请破持有并等待；超时恢复是给不可剥夺开的实用后门。

## $\rm \S \, 7.4$ 数据库里的死锁：SQLite 为什么死不了

数据库事务天然是「持有并等待」的重灾区：事务 1 改表 X 想改表 Y，事务 2 改 Y 想改 X，教科书式的死锁现场。但拿 SQLite 实测会发现它**根本走不到那一步**：

```python
import sqlite3
conn1 = sqlite3.connect('dl2.db', timeout=0.3, isolation_level=None)
conn2 = sqlite3.connect('dl2.db', timeout=0.3, isolation_level=None)
conn1.execute('CREATE TABLE x(a INT)')
conn1.execute('BEGIN'); conn1.execute('INSERT INTO x VALUES (1)')  # c1 拿到写锁
try:
    conn2.execute('INSERT INTO x VALUES (2)')                      # c2 的第一条写就被挡
except sqlite3.OperationalError as e:
    print(f'c2 第一条写即被挡: {e}')
conn1.execute('COMMIT')                                            # 写锁释放
conn2.execute('INSERT INTO x VALUES (2)')
print('c1 提交后 c2 写入成功', conn1.execute('SELECT a FROM x').fetchall())
```

本机输出：

```text
c2 第一条写即被挡: database is locked（等了 0.38s）
c1 提交后 c2 写入成功 [(1,), (2,)]
```

关键在 `database is locked` 出现的位置：不是在「交叉持锁」的深水区，而是**第二个连接的第一条写语句**。SQLite 的写锁粒度是整个数据库文件，同一时刻只允许一个写事务存在，别人的写请求在门口就收到 `SQLITE_BUSY`。条件 1（互斥）成立，但「两个写事务各自持有一部分再互相等」的格局根本排不出来：粗到极致的锁，用并发度换取了「这一类死锁在结构上不可能」。代价则是写吞吐的上限，这也是大型业务库不学它的原因。

PostgreSQL 与 MySQL/InnoDB 走另一头：锁粒度细到行，两个事务各改几行时真的可以交叉持锁，死锁因此真实存在。它们的对策是**检测与恢复**：等待图里发现环，主动回滚代价小的那个事务并报错（`SQLITE_BUSY` 的对应物是 `40P01 deadlock_detected`）。应用侧的正确姿势是：把死锁当可重试错误，收到后随机退避几百毫秒重跑整个事务。

**本节小结**：锁粒度决定死锁是否存在——SQLite 粗到结构上死不了锁、代价是写吞吐；行级锁的数据库真会死锁，靠检测与回滚兜底。

## $\rm \S \, 7.5$ 预防、避免与检测：三种 stance 的取舍

1. **预防（prevention）**：设计期就破坏四条件之一，锁排序、一次性申请。零运行时代价，是并发代码的默认纪律；
2. **避免（avoidance）**：运行期每次分配前判断「分配后还可能出现安全序列吗」（银行家算法是教科书代表）。要预先声明最大需求，实际系统几乎不用，真实负载没人能提前报准「我最多要多少锁」；
3. **检测与恢复（detection & recovery）**：放手让它发生，定期查等待环，发现就回滚一方。数据库用这条路；线程程序里对应「看门狗 + 事务重试」。

选型经验：并发结构自己写 → 预防（排序）；并发结构由数据库管 → 吃它的检测与重试语义，应用只做退避重跑。

## $\rm \S \, 7.8$ 本章自测答案

### $\rm \S \, 7.8.1$ 关键概念回顾答案

1. 互斥、持有并等待、不可剥夺、循环等待。必要条件的含义是四者同时成立死锁才可能，所以破坏任意一条，死锁在逻辑上被排除，无需运行时检测。（§7.2）
2. 循环等待。要求全程序存在一把「锁的全序」：任何代码要同时拿多把锁时，都按这一顺序获取。环需要至少一处逆序，全员同序则逆序不存在。（§7.3）
3. 都破「持有并等待」。try-lock 回退的代价是失败后的白做功与重试逻辑复杂度，但锁持有时间不变；一次性申请实现最简单，但把所有锁的持有时间拉长到整个临界区，并发度下降。（§7.3）
4. SQLite 写锁粒度是整个数据库文件，同一时刻只允许一个写事务，第二个写事务在第一条写语句处即被挡（实测 `database is locked`），「各持一部分再互等」的格局排不出来。代价是写并发度：写吞吐被单事务串行化锁死。（§7.4）
5. 数据库有现成的事务边界可回滚，检测到环后回滚一方、另一方继续，损失可控且可自动重试；裸线程没有「回滚线程」的语义，杀线程的清理代价高，所以只能预防优先。（§7.5）

### $\rm \S \, 7.8.2$ 应用与辨析答案

1. 先抓两个线程的栈（`py-spy dump` 或 `faulthandler`），确认双方各停在哪个 `acquire`；再列出各自已持有的锁，画出「线程 → 等待的锁 → 持有者」的有向边，找环。环在即证实；然后按 §7.3 补排序或改 try-lock。（§7.1、§7.2）
2. 两种设计：① 给每把锁发全局唯一编号（如创建时从同一个原子计数器取号），约定「按编号升序获取」；② 按业务对象排序，转账锁两个账户时按账户 ID 升序，多表事务按表名字典序。共同点是排序键必须全局可比且稳定。（§7.3）
3. 实验里两个线程等了 2 秒（timeout 上限）依然谁都没拿到，死锁不是「等得久」，是「永远等不到」：对方释放锁的前提是它能拿到你手里的锁，而它正被你堵着。调大超时只是把「确认死锁」的判决推迟，不改变结局。（§7.1）
