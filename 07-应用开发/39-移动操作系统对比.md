# $\rm Chapter \, 39$ 移动操作系统：iOS 与 Android 的本质区别

> 你手机上一个 App 有 iOS 版和 Android 版，它们看起来一模一样，但背后的代码是两套完全不同的程序——用不同的语言写、在不同的系统上跑、通过不同的商店分发。一个 iOS App 的安装包不能直接装到 Android 上，反着也不行。这不是因为"苹果和 Google 打架"，而是两套操作系统从内核、到应用框架、到安全模型，有着根本性的不同。

## $\rm \S \, 39.1$ 内核与底层架构

### $\rm \S \, 39.1.1$ 两个操作系统，两个内核

[操作系统、进程与线程](../03-计算机系统/09-操作系统进程与线程.md)中你知道了操作系统内核管理硬件、调度进程、处理系统调用。移动操作系统的内核：

- **Android** 内核基于 **Linux**。和你的服务器上跑的 Linux 是同一个内核——同样的进程调度器（CFS）、同样的内存管理（分页 + swap）、同样的文件系统（ext4/f2fs）。Android 在 Linux 之上加了自己的应用框架和运行时。
- **iOS** 内核是 **XNU**（X is Not Unix），和 macOS 是同一个内核。XNU 是 Mach 微内核 + FreeBSD 内核组件的混合体。iOS 和 macOS 共享内核和大量底层框架，但 UI 层分开。

为什么 Android 选 Linux？2005 年 Google 收购 Android 时，Linux 已经有成熟的驱动生态、内存管理和网络栈——直接借用可以省下几百万行代码和维护成本。为什么苹果用 XNU？XNU 是苹果从 NeXT 继承的（1997 年收购），已经深度集成到苹果的所有操作系统产品线中。

### $\rm \S \, 39.1.2$ 运行时环境

- **Android** 的应用主要用 **Java/Kotlin** 编写，编译为 Dalvik 字节码（`.dex`），在 **ART**（Android Runtime）上运行。ART 在应用安装时把字节码**预先编译为机器码**（AOT，Ahead-of-Time），启动快、不占用 CPU 做 JIT。这和 Java 在服务器上"先解释后 JIT 编译"的模式不同。
- **iOS** 的应用用 **Swift / Objective-C** 编写，编译为**原生 ARM 机器码**。没有中间字节码层、没有虚拟机——和 C++ 程序的编译和执行一样直接。这意味着 iOS App 通常启动更快、内存占用更小，但代价是每代 CPU 架构升级时 App 需要重新编译。

### $\rm \S \, 39.1.3$ HAL：硬件适配层

Android 通过 **HAL**（Hardware Abstraction Layer，硬件抽象层）来屏蔽不同手机厂商的硬件差异——GPS 芯片、摄像头传感器、指纹识别器。HAL 定义了统一接口：`getCurrentLocation()`、`capture()`。每个硬件厂商实现自己的 HAL 驱动。三星手机的摄像头 HAL 和 Google Pixel 的摄像头 HAL 是两套代码，但上层应用调用的是同一个 API。

iOS 没有这个需求——苹果自己设计芯片（A 系列、M 系列）、控制所有传感器选型、自己写所有驱动。这给了苹果更深入的硬件-软件整合优势（同样的硬件跑 iOS 比 Android 更省电，因为驱动被深度优化），但也意味着你不可能在非苹果设备上合法运行 iOS。

## $\rm \S \, 39.2$ 应用沙盒与权限模型

### $\rm \S \, 39.2.1$ 每个 App 都是囚犯

两个系统都使用了**沙盒**（sandbox）机制——每个 App 运行在自己的文件系统区域内，不能访问其他 App 的数据。其底层实现在[文件系统与权限](../02-终端与工具/03-文件系统路径与权限.md)的用户/组权限之上叠加了一层：即使两个 App 以同一用户身份运行，它们也看不到彼此的文件。

- **iOS 沙盒**更严格：每个 App 有自己的 `Documents/`、`Library/`、`tmp/` 目录，App 之间无法直接访问对方的文件。要共享数据必须通过系统提供的"分享扩展"（Share Extension）或 App Group（同一开发者的 App 间共享容器）。
- **Android 沙盒**在 Linux 用户隔离基础上实现：每个 App 分配一个独立的 Linux UID。从[操作系统、进程与线程](../03-计算机系统/09-操作系统进程与线程.md)的角度看，`ps` 输出中每个 App 进程都有自己的 UID——和服务器上为每个服务创建独立账户是同一个原理。

### $\rm \S \, 39.2.2$ 权限申请

你一定见过这种弹窗："XXX 想访问你的相册"——这就是系统权限申请的 UI。底层机制：

| | iOS | Android |
|---|---|---|
| 权限请求时机 | App 首次访问时弹窗，只能拒绝或允许 | 安装时声明所有需要的权限（manifest），运行时逐个弹窗 |
| 权限粒度 | 粗：相册、相机、位置、麦克风 | 细：精确位置 vs 粗略位置、前台 vs 后台 |
| 拒绝后 | App 必须处理被拒绝的情况（iOS 强制） | App 可能崩溃或行为异常（取决于开发者写没写处理逻辑） |

### $\rm \S \, 39.2.3$ 后台执行限制

在[操作系统、进程与线程](../03-计算机系统/09-操作系统进程与线程.md)中你学过时间片、前台/后台。移动操作系统对"后台"的定义远比桌面严格——为了节省电量：

- **iOS 后台极度受限**：App 进入后台后只有几秒的宽限期来完成收尾工作，之后被**冻结**——不再消耗 CPU、不再执行代码。只有特定场景（音频播放、导航、VoIP 通话）可以通过特殊 API 申请后台运行。这就是为什么 iOS 设备电池续航通常优于同容量 Android 设备——后台 App 几乎不耗电。
- **Android 后台较宽松**：App 可以申请后台 Service。理论上你可以写一个永不停止的后台进程持续运行——尽管现代 Android（8+）会在检测到异常耗电时强制终止。所以同一个即时通讯 App 在 Android 上推送更即时、iOS 上稍延迟——iOS 用统一推送通道（APNs），不需要 App 自己在后台跑。

## $\rm \S \, 39.3$ 应用分发

### $\rm \S \, 39.3.1$ App Store vs 开放生态

- **iOS**：唯一的应用商店是 **App Store**。所有 App 必须经过苹果的人工+自动审查（审核代码质量、内容合规、隐私政策、收费模式）。这防止了恶意软件，但也意味着苹果可以拒绝任何不符合其政策的应用。
- **Android**：**Google Play** 是主力商店，但不是唯一渠道。用户可以安装第三方商店（如三星 Galaxy Store、华为应用市场），也可以直接下载 `.apk` 文件手动安装（"侧载" sideloading）。这给了用户更多自由，但也让恶意软件更容易传播——Google Play Protect 扫描已安装 App，但覆盖率和 iOS 的审查不可比。

### $\rm \S \, 39.3.2$ 编译目标

iOS App 编译为 ARM64 机器码（`.ipa`）。Android App 编译为 DEX 字节码 + 可选的原生库（`.apk` / `.aab`）。一个 Android App 可以有多个架构版本（ARM64、ARM32、x86_64），Google Play 会自动匹配用户的设备架构。

## $\rm \S \, 39.4$ 跨平台开发：一次写，多端跑

既然 iOS 和 Android 是两套完全不同的系统，怎么有人能用一套代码同时发布两个平台？

| 框架 | 语言 | 原理 | 原生体验程度 |
|---|---|---|---|
| **React Native**（Meta） | JavaScript | JS 代码通过"桥"调用原生 UI 组件 | 中——UI 是原生的，但桥有性能开销 |
| **Flutter**（Google） | Dart | 完全自绘——Skia 引擎直接画像素，不调用原生 UI 组件 | 高——渲染性能和原生几乎无差 |
| **Kotlin Multiplatform**（JetBrains） | Kotlin | 业务逻辑共享，UI 层各自原生写 | 原生——UI 层还是各自平台代码 |
| **SwiftUI + shared Swift** | Swift | 实验性——Swift 在非苹果平台上的支持有限 | N/A |

**Flutter 的"自绘"选择**：React Native 通过桥接调用 iOS 的 `UITextField` 或 Android 的 `EditText` 来显示输入框。Flutter 不用——它在屏幕上直接画一个输入框，包括光标、文字渲染、键盘弹出动画全部自己实现。代价是 Flutter App 的安装包更大（Skia 引擎就几十 MB），好处是 UI 在所有平台上像素一致。

## $\rm \S \, 39.5$ 动手实践

### 实践一：查看 Android 进程隔离

如果你有一台 Android 手机，启用开发者选项后：

```bash
adb shell                     # Android Debug Bridge
ps -A | grep com.             # 每个 App 包名对应一个进程
ls -l /data/data/             # 每个 App 的私有数据目录（UID 隔离）
```

### 实践二：对比 App 权限

在 iOS（设置→隐私）和 Android（设置→应用→权限管理）中分别查看同一个 App（如微信或 Chrome）在两个系统上申请的权限列表。观察哪些权限一致、哪些不同。

### 实践三：Flutter 体验

```bash
flutter create hello_mobile
cd hello_mobile
flutter run        # 在连接的手机或模拟器上运行
```

修改 `lib/main.dart` 中的文字，保存后 App 自动热重载——不需要重新编译安装。

## $\rm \S \, 39.6$ 总结

- Android 内核是 Linux，iOS 内核是 XNU（和 macOS 共享）。Android 用 HAL 适配不同硬件，iOS 自己控制全栈。
- 两个系统都用沙盒隔离 App。iOS 后台严格冻结，Android 后台相对宽松——这是电池续航差异的主因。
- iOS 只有 App Store 分发，Android 支持侧载和第三方商店。
- 跨平台框架中，Flutter（自绘）和 React Native（原生桥接）是主流选择。

## $\rm \S \, 39.7$ 关键概念回顾

1. Android 和 iOS 分别使用什么操作系统内核？
> Android 使用 Linux 内核；iOS 使用 XNU（Mach + FreeBSD 组件，和 macOS 共享）。

2. iOS 和 Android 的 App 沙盒机制分别依赖什么底层技术？
> iOS 的沙盒是独立于用户权限的文件系统隔离（每个 App 私有的 Documents/Library/tmp）；Android 的沙盒基于 Linux UID 隔离（每个 App 分配一个独立 Linux 用户 ID）。

3. Flutter 和 React Native 在 UI 实现上的核心差异是什么？
> React Native 通过桥接调用原生 UI 组件（iOS UIKit、Android Views）；Flutter 完全自绘——Skia 引擎直接画像素，不调用系统 UI 组件。

## $\rm \S \, 39.8$ 应用与辨析

4. 为什么同一个即时通讯 App 在 Android 上消息推送更即时但在 iOS 上可能有延迟？
> iOS 后台极度受限——App 进入后台后被冻结，无法维持长连接。推送通过统一的 APNs 通道，增加了转发延迟。Android 允许后台 Service 维持长连接，但代价是更耗电。

5. iOS App 的 `.ipa` 文件和 Android App 的 `.apk` 文件在结构上有什么区别？为什么不能直接互换？
> `.ipa` 是 ARM64 原生机器码（编译后的 Swift/Obj-C），直接运行在 CPU 上。`.apk` 包含 DEX 字节码 + 可选的原生库，由 ART Runtime 执行。不同的指令集、不同的系统 API、不同的文件格式——完全没有互换性。
