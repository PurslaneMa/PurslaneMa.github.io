# $\rm Chapter \, 31$ 部署与云服务器

> 你的论文管理器在 Docker Compose 中完美运行——前端 `localhost:5173`、后端 `localhost:8000`、数据库 `localhost:5432`。但只有你电脑上能访问。这一章让它出现在公网上——任何人都能通过浏览器打开你的应用。

> **开始前自检**：本章假设你已经会：□ 会打包并运行容器（第 30 章）；
> □ 理解反向代理、域名与 HTTPS（第 24 章）；
> □ 会把服务跑在服务器/云主机上。

## $\rm \S \, 31.1$ 从 localhost 到公网

### $\rm \S \, 31.1.1$ 你需要什么

最小部署需要：
1. **一台有公网 IP 的服务器**（云服务器/VPS）——你的应用跑在上面。
2. **一个域名**（可选但强烈建议）——用户输入 `papers.example.com` 而不是 `142.250.80.46`。
3. **HTTPS 证书**——浏览器地址栏的锁图标，加密通信。
4. **反向代理**——接收公网请求，转发给 Docker 容器内的应用。

### $\rm \S \, 31.1.2$ 云服务商

| 服务商 | 特点 |
|---|---|
| **AWS**（aws.amazon.com） | 最全面——EC2(虚拟机)、RDS(托管数据库)、ECS(托管容器)、Lambda(无服务器) |
| **Google Cloud**（cloud.google.com） | GKE——托管 Kubernetes（容器编排平台，超出本书范围）、BigQuery(数据分析) |
| **Azure**（azure.microsoft.com） | 微软生态、企业集成 |
| **DigitalOcean**（digitalocean.com） | 简单、价格透明、教程质量高 |
| **Vercel**（vercel.com） | 前端+Serverless——`git push` 自动部署（不适合后端+数据库的完整应用） |
| **Railway**（railway.app） | 类似 Vercel 但支持后端+数据库 |
| **Fly.io**（fly.io） | 全球分布——Docker 镜像自动部署到多个大洲的近用户边缘节点 |

对于个人项目和学习，DigitalOcean 或 Railway 的简单性和定价透明度优于 AWS 的功能广度。

## $\rm \S \, 31.2$ 反向代理：Nginx vs Caddy

在[域名、HTTPS、代理与排障](../04-网络/24-域名HTTPS代理与排障.md)中你见过反向代理的概念。部署时的实际选择：

### $\rm \S \, 31.2.1$ Nginx：经典方案

```nginx
# /etc/nginx/sites-available/paper-manager
server {
    listen 80;
    server_name papers.example.com;

    location / {
        proxy_pass http://localhost:5173;   # 前端
    }
    location /api/ {
        proxy_pass http://localhost:8000;   # 后端
    }
}
```

Nginx 不做自动 HTTPS——你需要手动安装 Certbot 获取和续期 Let's Encrypt 证书：

```bash
sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d papers.example.com
```

### $\rm \S \, 31.2.2$ Caddy：自动 HTTPS

Caddy 默认自动获取和续期 Let's Encrypt 证书——不需要额外配置：

```text
# Caddyfile
papers.example.com {
    reverse_proxy localhost:5173
    handle_path /api/* {
        reverse_proxy localhost:8000
    }
}
```

一行就启用了 HTTPS。对于个人项目，Caddy 的简洁性让它成为比 Nginx 更好的默认选择。

## $\rm \S \, 31.3$ 部署流水线

### $\rm \S \, 31.3.1$ 手动部署（适合学习和小项目）

```bash
# 在服务器上
git clone https://github.com/you/paper-manager.git
cd paper-manager
docker compose up -d

# 配置 Caddy 反向代理
# 验证域名 + HTTPS
```

手动部署简单、透明——出问题你知道每一步在做什么。缺点是每次更新需要 SSH 登录、`git pull`、`docker compose up -d`。

### $\rm \S \, 31.3.2$ CI/CD 自动部署（适合团队和频繁更新）

在[依赖、构建、测试与 CI](../05-开发工作流/21-依赖构建测试与CI.md)中你见过 CI 的概念。CD（持续部署）在 CI 通过后自动把代码部署到服务器：

```yaml
# .github/workflows/deploy.yml
deploy:
  needs: [test, build]    # 测试和构建通过后才部署
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - name: Deploy via SSH
      uses: appleboy/ssh-action@v1
      with:
        host: ${{ secrets.SERVER_HOST }}
        username: deploy
        key: ${{ secrets.SSH_PRIVATE_KEY }}
        script: |
          cd /opt/paper-manager
          git pull
          docker compose up -d --build
```

每次 `git push` 到 main 分支 → GitHub Actions 自动拉取、构建、部署。你不需要手动登录服务器。

## $\rm \S \, 31.4$ 环境隔离

[日常系统管理：软件、用户、服务与日志](../03-计算机系统/13-系统服务日志与软件安装.md)中强调过开发/测试/生产环境必须分离。在部署场景中具体化为：

| 环境 | 数据库 | 配置 | 谁访问 |
|---|---|---|---|
| **开发** | SQLite 本地文件 | debug=True、详细日志 | 只有你 |
| **测试/预发布** | Postgres（独立实例） | 接近生产配置 | 你和队友 |
| **生产** | Postgres（托管或专用实例）+ 自动备份 | debug=False、最小日志、监控告警 | 用户 |

用环境变量或 `.env` 文件切换配置——不要在生产服务器上手动改代码中的数据库连接字符串。

## $\rm \S \, 31.5$ 基础监控与健康检查

部署后不是"等用户报 bug"：

1. **健康检查**：定期 `curl http://localhost:8000/health`（需要你写一个 `/health` 端点），确认服务存活。
2. **日志**：`docker compose logs -f` 或配置日志驱动（如 journald、Elastic Stack）。
3. **资源监控**：`docker stats` 查看每个容器的 CPU/内存。服务器层面用 `htop`、`df -h`。
4. **告警**：使用 **Uptime Kuma**（github.com/louislam/uptime-kuma，自托管免费）或 **Better Stack**（betterstack.com，SaaS）做可用性监控——服务挂了立刻通知你。

## $\rm \S \, 31.6$ 动手实践

### 实践一：部署到云服务器

1. 在 DigitalOcean/Railway/AWS 上创建一台最低配服务器（~$5/月）。
2. 安装 Docker + Caddy。
3. 用 `git clone` + `docker compose up -d` 部署论文管理器。
4. 配置域名和 HTTPS。
5. 用手机（不同网络）访问你的域名——确认公网可访问。

### 实践二：添加健康检查

1. 在后端中添加 `/health` 端点（返回 `{"status": "ok"}`）。
2. 在 Compose 中配置 `healthcheck`。
3. 用 `docker ps` 确认健康状态。

### 实践三：模拟更新部署

1. 修改前端代码（如改标题）。
2. SSH 登录服务器，`git pull`，`docker compose up -d --build`。
3. 刷新页面——确认更新生效。

## $\rm \S \, 31.7$ 总结

- 部署 = 公网服务器 + 域名 + HTTPS + 反向代理 + Docker Compose。
- Nginx 经典；Caddy 自动 HTTPS 默认更简单。
- CI/CD 在测试通过后自动部署——不需要手动 SSH。
- 环境隔离：开发用 SQLite，生产用 Postgres（不同实例）。
- 部署后必须监控——健康检查 + 日志 + 资源 + 告警。

## $\rm \S \, 31.10$ 本章自测答案

> 先闭卷作答本章"关键概念回顾"与"应用与辨析"，再核对以下答案。

### 自测答案 · 关键概念回顾
1. 有公网 IP 的服务器、域名（DNS→IP）、HTTPS 证书（TLS 加密）、反向代理（接收公网请求并转发给容器内应用）。
2. Nginx 需要手动配置 HTTPS（Certbot），Caddy 默认自动获取和续期 Let's Encrypt 证书。对于个人和小团队项目，Caddy 的默认行为更省事。
3. CI（持续集成）在推送后自动构建和测试。CD（持续部署）在 CI 通过后自动把产物部署到服务器。CI 保证质量，CD 保证速度。

### 自测答案 · 应用与辨析
4. 不能。`depends_on` 只等待容器启动（进程存在），不等待数据库服务真正接受连接。应用需要内置重试逻辑（如等待 PostgreSQL 的 `pg_isready`）或使用 `healthcheck` + `condition: service_healthy`（Compose v3.4+）。
5. `docker compose up` 依赖于你保持 SSH 连接。使用 `docker compose up -d`（后台）+ systemd service 或托管容器服务保证进程在退出终端后持续运行、崩溃后自动重启。
6. 本地开发时 Vite 代理将 API 请求转发到后端，绕过 CORS 检查。生产部署时浏览器直接向不同源发请求——需要在后端添加 CORS 头，或让反向代理把前后端统一到同一域名下。
