## $\rm \S \, 5.1$ 先修计时器：主线程的墙钟在满载时说谎

第一个实验还没开始就翻车了。第一版计时沿用第 1 章的套路：主线程在「起跑线屏障」（barrier，所有线程到齐才放行的集合点）后读钟，等所有线程在终点屏障会合再读一次，差值当并行区耗时。p=16 动态分块一跑，测出 0.624 ms 扫完 256 MiB，折合 400.7 GB/s，超过这台机器 DRAM 的物理上限三倍多。数字物理上不可能，说明测的不是那段工作。

排查分三步，每步一个证据。第一步验时钟本身：让程序睡 10 ms 再计时，重复 1000 次，最短一次 10.082 ms，从不少于 10 ms；自旋计时与跨核迁移读钟同样干净（`expPE05/result_clockcheck.txt`）。第二步验跨核一致性：16 个线程钉在 16 个 vCPU 上同步读钟，与主线程读数的最大偏差 0.449 ms，属于屏障唤醒的正常延迟（`result_clocksane.txt`），跨核时钟一致，不是时钟说谎。第三步给每个线程发一块表：干活线程各自在起跑线后与终点前自己读钟，同一轮里 7 个干活线程自报 6.9～7.9 ms，主线程的墙钟却只有 0.811 ms（`result_sanity16.txt`）。矛盾坐实在主线程身上：16 个 worker 占满全部 16 个 vCPU 时，没有绑核的主线程被调度器推迟了几毫秒才读到起点，墙钟窗口错过了整个干活时段；同一份记录还显示 9 个线程领到 0 块任务，vCPU 偶发停摆几毫秒也是真实存在的。

修法是把表发到亲历者手里：并行区时长取全体 worker 的 ${\max(\text{终点}) - \min(\text{起点})}$，主线程退出计时、也退出屏障，只负责创建与回收：

```c
static void *worker(void *arg) {
    long id = (long)arg;
    pin_to((int)id);                     /* 线程 t 钉到 vCPU t */
    pthread_barrier_wait(&bar);          /* 起跑线：屏障只属于 worker */
    double ts = now_sec();
    /* …… 干活 …… */
    t_end[id] = now_sec();
    t_start[id] = ts;
    pthread_barrier_wait(&bar);
    return NULL;
}
/* 主线程：pthread_create 全部、pthread_join 全部，
   并行区时长 = max(t_end[]) - min(t_start[])，自己不碰钟 */
```

第 1 章的纪律没有错，它只是带了一个单线程语境下的隐含前提：计时线程自己就是干活的人。并行区里计时的人如果不干活，他就可能挤不进现场。这一条连同 §1.3 的坑，构成多线程基准的两条新增纪律。

白话：让场外记分员掐表，全场座位坐满时他自己挤不进场，等挤进去比赛都结束了；改成场上运动员每人一块表，取最早开跑和最晚冲线，谁也没法漏计时。

> 本节小结：满载时主线程会被饿几毫秒，墙钟窗口可以完全错过并行区；并行区计时必须由 worker 自己读钟，取 max(终点) 减 min(起点)。

## $\rm \S \, 5.2$ 加速比曲线：16 核买不来 16 倍，带宽先到顶

计时器修好，正式开测。任务是对 256 MiB 的 int32 数组求和（`curve.c`，每次运行核对总和与单线程参考值逐位一致），线程数 ${p \in \{1, 2, 4, 8, 16\}}$，两种分法：**静态分块**（static partitioning，开跑前把数组连续等切成 $p$ 份，一人一份锁死）与**动态分块**（dynamic partitioning，切成 4 MiB 的小块，谁干完自己那份就用一次原子加法领下一块）。两个内核只差一个取任务的循环：

```c
/* 静态：份额锁死 */
long lo = id * N / P, hi = (id + 1) * N / P;
for (long i = lo; i < hi; i++) s += arr[i];

/* 动态：干完就领，DCHUNK = 1M 元素 = 4 MiB */
for (;;) {
    long c = atomic_fetch_add(&next_chunk, DCHUNK);  /* 原子领块 */
    if (c >= N) break;
    long hi = (c + DCHUNK < N) ? c + DCHUNK : N;
    for (long i = c; i < hi; i++) s += arr[i];
}
```

先把账推了再跑。求和每 4 字节只做 1 次加法，算术强度 0.25 FLOP/字节，是 §1.8 里最典型的访存受限负载；单线程扫 256 MiB 实测 43.68 ms，折合 5.7 GB/s，远低于这台机器内存系统卖得出的带宽。按 §2.5 的账，单线程慢不是因为内存贵，是因为一个核的在途行数有限，缺口的延迟只能干等。所以并发的第一笔红利不是「算得快」，是**多个核用各自在途窗口合买带宽**。实测（FORMAL RUN 2，7 轮轮转取 min）：

| $p$ | 静态 ms | 加速比 | GB/s | 动态 ms | 加速比 | GB/s |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 43.68 | 1.00 | 5.7 | 40.40 | 1.08 | 6.2 |
| 2 | 24.62 | 1.77 | 10.2 | 21.05 | 2.08 | 11.9 |
| 4 | 9.61 | 4.55 | 26.0 | 9.41 | 4.64 | 26.6 |
| 8 | 7.00 | 6.24 | 35.7 | 6.53 | 6.69 | 38.3 |
| 16 | 5.83 | 7.49 | 42.9 | 4.98 | 8.78 | 50.2 |

曲线的形状用带宽一眼读完。程序里没有任何串行段（每个字节都可并行），Amdahl 的名义天花板是 16 倍；实测静态档 7.49 倍就趴下了，因为带宽先到顶。把这件事写成不等式：设单线程实测带宽 $B_1$、并行饱和后买到的上限 $B_{\max}$，则并行段耗时被搬运量除以带宽封底：

$$
S_p \;\le\; \frac{B_{\max}}{B_1}
$$

读法：分子是并行区能买到的最大带宽，分母是单线程买到的带宽；这个程序没有串行段，加速比就是「带宽买到了多少倍」，${50.2/5.7 = 8.8}$ 倍，动态档实测 8.78 倍贴住这条线，静态档 7.49 倍还差一截。静态档差的这截来自负载不均：`cpuspeed` 给 16 个 vCPU 各派一个线程单线程扫同一个数组，快慢差 1.46 倍（最快 14.27 ms，最慢 20.87 ms），而且**慢的编号跨运行不稳定**（前一次试跑 cpu 6 慢 47%，这次 cpu 6 反而最快，慢的换成了 cpu 12 和 cpu 9）。我们原本的假设是 P 核与 E 核的固定拓扑，被两次运行直接证伪；剩下的解释是宿主调度与频率的临时状态，虚拟机之下无法从 Linux 侧看穿。但结论不依赖解释：静态等分把等量的活绑给指定编号的 vCPU，撞上慢核就只能等它；动态领块按完成度发货，自动绕开慢核。这就是 p=16 处动态比静态快 17%（4.98 对 5.83 ms）的来源。另外记两笔口径账：其一，加速比在 p=4 到 8 之间拐弯（4.55 到 6.24），带宽从 26 GB/s 爬到 35.7 GB/s 后增速放缓，墙的位置在 40～50 GB/s 一带；其二，正式运行前两次试跑（`result_curve.txt`、`result_curve_run2.txt`）里静态档 p=8 到 16 几乎走平（5.09 到 5.15 倍），这次却从 6.24 爬到 7.49，绝对值与拐点细节轮间会漂，「拐点在 4～8、p=16 动态恒优于静态、墙在几十 GB/s」这三个判断次次成立。

两个小数字也值得记：p=1 时动态 1.08 倍略高于静态，64 次原子领块的开销在 40 ms 面前不可见，两档在单线程下同价；p=2 处静态 1.77 倍已经低于动态 2.08 倍，慢 vCPU 的伤害从两个线程起就进场了。

白话：单线程是个推手车的搬运工，一次只端得动几个托盘（在途行），一车货要等好久；16 个人一起推，走廊的吞吐先挤爆，货梯成了新瓶颈。

## $\rm \S \, 5.3$ 负载不均：总时长钉死在最慢的人身上

§5.2 的活是均匀的，现实里干活常常不均匀。`sched.c` 把同一数组改成 16 条条纹，每条 4M 元素，条纹 0 与条纹 8 是重条纹：每元素做 17 次 xorshift，轻条纹只做 1 次。把一个条纹的工作量记作 1 单位，轻条纹 1 单位、重条纹 17 单位，全数组共 ${2 \times 17 + 14 = 48}$ 单位。静态等分 p=8 时，线程 0 拿到条纹 0、1 共 18 单位，线程 4 同理 18 单位，其余六人各 2 单位：最重的人拿的是均摊值（6 单位）的 3 倍。同步点语义下总时长由最慢者决定：

$$
T_p \approx \frac{\max_i W_i}{\bar{r}}
$$

读法：$W_i$ 是第 $i$ 人分到的活，$\bar{r}$ 是单人平均速率；分子取 max 而不是平均，这就是「水桶装水看最短的板」。用动态档标定 $\bar{r}$：均摊 6 单位对应 18.4 ms，单人速率约 0.33 单位/ms，线程 0 的 18 单位要 55 ms 上下，与静态实测 51.9 ms 咬合（差在拖尾者最后独享机器，跑得比平均快）。三种调度策略的对照（`sched.c`，5 轮取 min，各模式总和逐位核对）：

| $p$ | 静态 ms | 动态定长 ms | Guided ms | 动态/静态 | Guided/静态 |
| --- | --- | --- | --- | --- | --- |
| 8 | 51.9 | 18.4 | 46.9 | 2.82× | 1.11× |
| 16 | 48.2 | 13.3 | 23.4 | 3.62× | 2.06× |

动态定长块（64K 元素）把 p=8 的差距拉开 2.82 倍，p=16 拉开 3.62 倍，都远低于理想值（p=8 应为 ${48/6 = 8}$ 倍），因为剩下的瓶颈换成了带宽与 xorshift 的吞吐，负载不均的账已经还清。Guided（guided scheduling，块尺寸从大往小缩，每轮领「剩余量除以 $2p$」但有下限）在这里几乎没用：p=8 的第一块是 ${64\text{M}/16 = 4\text{M}}$ 元素，恰好等于一整条重条纹，谁领到第一块谁就成了 17 单位的拖尾者，测出 1.11 倍的安慰奖；p=16 首块减半才好看到 2.06 倍。Guided 的适用条件由此划清：它救的是成本随下标缓变的循环（比如三角形矩阵，后半段活越来越少，大块在前正合适）；重活扎堆在开头时，第一批大块正好砸在重活上。

这三种策略不是 C 程序员的手写专利，它们就是 OpenMP（Open Multi-Processing，编译制导的共享内存并行标准）`schedule` 子句的三个选项。OpenMP 的思想是「循环切块分给线程池，运行时细节交给编译器」：

```c
#pragma omp parallel for reduction(+:s) schedule(dynamic, 65536)
for (long i = 0; i < N; i++) s += elem(i);
/* schedule(static)：编译期等分；schedule(dynamic, k)：干完领 k 个；
   schedule(guided)：块从大到小。上面两个手写循环就是前两者的展开 */
```

白话：装礼物，静态是开工前把筐均分到每人脚边，动态是干完一筐去台子上再领一筐，guided 是筐越到后面越浅。活儿匀，静态最省心；活儿不匀，只有「再领一筐」能救场。

> 本节小结：同步点语义下 $T_p$ 由 $\max_i W_i$ 决定，静态等分在 9 倍不均下实测慢 2.82 倍；Guided 的大块开局会撞上扎堆的重活，选块策略前先看工作量随下标的分布。

## $\rm \S \, 5.4$ 锁的代价账：次数 × 单价，外加两个陷阱

分完活要对总账：所有线程往一个共享累加器里加自己的部分和。不加会怎样，`lockcost.c` 的 bare 档给出了实物证据：每 64K 元素攒一个局部和，然后裸写 `acc += s`，不加任何同步，8 线程实测 8.43 ms，总和错误（表里 ok 列 NO）。这叫竞争条件（race condition，结果取决于线程交错顺序的错误）：两次「读、加、写」交错执行时后写者覆盖前写者，更新凭空丢失。裸写还比正确方案慢：这些写全落在同一条缓存行上，每笔都要跨核抢行所有权（§4.5 的账，原子 RMW 从不打折，这里连裸写也不打折）。

正确方案三档，唯一的变量是「多久同步一次、用什么同步」（p=8，3 轮轮转取 min，`-fno-tree-vectorize` 编译）：

```c
/* merge：各攒各的，结束前每线程锁一次（共 8 次） */
for (long i = lo; i < hi; i++) s_local += arr[i];
pthread_mutex_lock(&mtx);  acc += s_local;  pthread_mutex_unlock(&mtx);

/* mutex-G：每攒 G 个元素锁一次 */
for (long c = lo; c < hi; c += G) { ...局部和 s...;
    pthread_mutex_lock(&mtx);  acc += s;  pthread_mutex_unlock(&mtx); }

/* atomic-G：每攒 G 个元素做一次原子读改写（read-modify-write，RMW） */
atomic_fetch_add((_Atomic long long *)&acc, s);
```

互斥锁（mutex，同一时刻只许一个线程进入的锁）保护的那段代码叫临界区（critical section）。实测全表：

| 配置 | 同步次数 | min ms | 总和正确 |
| --- | --- | --- | --- |
| serial（单线程基线） | 0 | 40.91 | 是 |
| bare 64K（无同步） | 0 | 8.43 | 否 |
| merge（每线程 1 次） | 8 | 6.27 | 是 |
| mutex G=1K | 65536 | 10.44 | 是 |
| mutex G=64K | 1024 | 5.69 | 是 |
| mutex G=4M | 16 | 5.89 | 是 |
| atomic G=1 | 64M | 909.24 | 是 |
| atomic G=1K | 65536 | 6.65 | 是 |
| atomic G=64K / 4M | 1024 / 16 | 6.11 / 6.06 | 是 |

这笔账能对得很齐。把并行档的近似成本写成 ${T_p \approx T_{\text{work}} + n_{\text{sync}} \times c_{\text{sync}}}$，读法：干活时间加上同步次数乘单次同步价。mutex 档用 G=1K 与 G=4M 两点回归：${(10.44 - 5.89)/(65536 - 16) \approx 69\,\text{ns}}$ 每次带锁归并，G=64K 的预测落点 5.96 与实测 5.69 在 3 轮取 min 的噪声内吻合。merge 档只有 8 次锁，6.27 ms 几乎就是 8 线程无同步扫数的价（对照 §5.2 静态 p=8 的 7.00 ms，同一次运行内自洽）。atomic 档两头极端：G=1 时 64M 笔 RMW 打在同一条缓存行上，909.24 ms 折合每笔 14.2 ns，整个程序被这条行串行化；G 提到 1K 之后边际价掉到约 9 ns，因为 RMW 的行所有权等待能与周围访存的在途延迟重叠（§4.1 在途账的回声）。粒度判据一句话：**每次同步至少要摊到几千元素的活，才不算白交钱**。

最后把两个陷阱原样存档，它们都是全册心智模型的现场教材。陷阱 A（死代码）：第一版 serial 档把求和攒在局部变量里没人使用，gcc -O2 把整个循环删了，测出 0.06 ms，靠 ok 列 NO 与 acc=0 抓住（§1.3 坑一的多线程还魂），修法是把结果写进共享的 acc。陷阱 B（代码生成不一致）：修好死代码后 serial 测得 49.79 ms 对 merge 的 4.74 ms，10.5 倍差距虚高，objdump 显示 merge 的内层有 `vpmovsxdq` 的 ymm 向量化而 serial 是标量，比的根本不是锁而是 SIMD；终版给 lockcost 统一加 `-fno-tree-vectorize` 全档标量化，serial 40.91 对 merge 6.27 的 6.5 倍才干净，且与 §5.2 同一运行的 p=1、p=8 数字互相咬合。

顺带把 bare 的账补全：它与 merge 的内核逐字相同，只差同步方式，1024 笔无同步写比 8 次带锁归并多花 2.16 ms，平均每笔约 2 μs，比带锁归并贵一个数量级以上——§4.5 那句「伪共享的账单爱在同步原语上冒头」在裸写上同样成立，量级存账，单价不抠。

白话：对账有两种，每人记自己的流水最后交一次总表（merge），或者每动一笔都排队签字（mutex/atomic）；签字一次 69 纳秒，签字 6400 万次就是一整个程序的寿命。

> 本节小结：同步成本 = 次数 × 单价，mutex 单价实测约 69 ns、同线 RMW 满价 14.2 ns；merge 几乎免费，粒度撑到几千元素以上同步价就藏进访存等待；死代码与代码生成不一致是本实验路上真实的两颗雷。

## $\rm \S \, 5.5$ 实测 Amdahl：两堵墙取更矮的一堵

§1.6 的 Amdahl 定律还没在这台机器上实测过。`amdahl.c` 人造了一个串行段：worker 0 独跑一条 xorshift 依赖链，第 $i$ 步的输入是第 $i-1$ 步的输出，数学上无法并行；随后全体线程并行扫同一个 256 MiB 数组。串行时长 $S$ 与并行段单独耗时 $P_1$ 各自实测，总时间与加速比 ${S_p = T_1/T_p}$ 随 $p$ 实测（5 轮取 min）：

| $p$ | 实测加速比 | Amdahl 理论 | | $p$ | 实测加速比 | Amdahl 理论 |
| --- | --- | --- | --- | --- | --- | --- |
| 2 | 2.12 | 1.87 | | 2 | 1.78 | 1.66 |
| 4 | 3.40 | 3.29 | | 4 | 2.50 | 2.47 |
| 8 | 4.57 | 5.31 | | 8 | 2.77 | 3.27 |
| 16 | 4.71 | 7.67 | | 16 | 2.84 | 3.90 |

左半表是 ${S = 3.44\,\text{ms}}$、${T_1 = 47.47\,\text{ms}}$（名义 ${f = 0.072}$，Amdahl 天花板 13.8 倍）；右半表是 ${S = 12.69\,\text{ms}}$、${T_1 = 61.31\,\text{ms}}$（${f = 0.207}$，天花板 4.83 倍）。两个方向都值得停一下。左半表 p=4 之前实测**高于**理论：并行段单独实测从 44.04 ms 收缩到 10.54 ms，是 4.18 倍的超线性（superlinear scaling，多于 $p$ 倍的加速），来源还是 §5.2 那笔账，单线程的在途窗口买不满带宽，小 $p$ 阶段每个线程都在帮全程序买带宽。右半表 p=4 处两墙几乎重合（2.50 对 2.47），此后实测掉到理论之下。缺口的来源一目了然：左半表并行段最终只扩到 6.64 倍（44.04 收缩到 6.63 ms），带宽墙接替串行墙成了挡路者。把两堵墙写成一个下界：

$$
T_\infty \;=\; S \;+\; P_1 \cdot \frac{B_1}{B_{\max}}
$$

读法：$S$ 是串行段一分不减的部分，$P_1$ 是并行段单线程耗时，$B_1/B_{\max}$ 是带宽扩张倍数的倒数，两项相加是核数无穷时并行段的时间下限，天花板即 $T_1/T_\infty$。代入左半表（$B_1$ 由本表 $P_1$ 反推 5.8 GB/s，$B_{\max}$ 借同一次正式运行 §5.2 静态档的 42.9 GB/s）：${T_\infty = 3.44 + 44.04 \times 5.8/42.9 = 9.41\,\text{ms}}$，天花板 5.05 倍，实测 4.71 倍达到两墙界的 93%；右半表 ${T_\infty = 18.66\,\text{ms}}$，天花板 3.29 倍，实测 2.84 倍达到 86%。顺带一提，两个表的并行段增量都恰好是 ${256/42.9 \approx 5.97\,\text{ms}}$，正是 256 MiB 按饱和带宽折算的搬运下限，账目自洽。所以预测并行收益需要两个数：串行段多长（Amdahl 墙），并行段的带宽能扩张多少（带宽墙），实测曲线永远贴着两堵墙中更矮的那堵。

白话：图纸上十个人一天完工，但材料库门口一次只放行六辆车；人头再翻倍，工期卡在车库门口。

> 本节小结：实测加速比 = min(Amdahl 墙, 带宽墙)；小 $p$ 处并行段超线性（实测可高于名义 $f$ 的理论），大 $p$ 处带宽墙接管，两个天花板合成式 ${T_\infty = S + P_1 B_1/B_{\max}}$ 在本机两档 $f$ 上分别解释 93% 与 86% 的实测点。

## $\rm \S \, 5.8$ 本章自测答案

概念回顾答案：

1. 16 个 worker 占满 vCPU 时主线程被宿主调度推迟毫秒级，墙钟窗口错过干活时段（§5.1）。clockcheck 排除时钟本身走错（睡 10 ms 的实测从不短于 10 ms），clocksane 排除跨核读数不一致（16 核同步读钟偏差至多 0.449 ms）。
2. ${S_p \le B_{\max}/B_1}$（§5.2）。本机 ${B_1 = 5.7}$ GB/s（单线程静态档）、$B_{\max}$ 约 43～50 GB/s（p=16 静态/动态），封顶 7.5～8.8 倍，实测静态 7.49、动态 8.78 倍。
3. 同步点语义下总时长由最慢者决定，${\max_i W_i = 18}$ 单位对完美均摊 6 单位，比值 3（§5.3）。实测低于 3 倍（2.82）是因为其余线程干完后拖尾者独享机器，末段跑得比平均快。
4. ${(10.44 - 5.89)/(65536 - 16) \approx 69\,\text{ns}}$ 每次带锁归并（§5.4）。G=1K 时 64K 笔 RMW 的行所有权等待可与访存在途延迟重叠，边际价约 9 ns，收不到满价；满价 14.2 ns 只在 G=1（除同步无事可做）时全部兑现。
5. $S$ 是串行段耗时，$P_1$ 是并行段单线程耗时，$B_1$、$B_{\max}$ 是单线程与饱和并行的带宽，$T_\infty$ 是核数无穷时的下限（§5.5）。实测高于名义 $f$ 理论，是因为并行段自身超线性（单线程在途窗口买不满带宽），Amdahl 的理论假设并行段恰好缩 $p$ 倍。

应用与辨析答案：

1. 质疑一：计时方法，24 倍超过这台机器任何已知的并行上界（§5.1 的 400 GB/s 教训），复测：要求对方打印计时方法，把表发给 worker 重测。质疑二：基线被弱化，单线程档可能被编译器删循环或用了解释级写法（§5.4 陷阱 A），复测：核对单线程档总和正确性与汇编里有无循环。质疑三：工作集作弊，16 线程档可能落在缓存里而单线程档从 DRAM 起（§1.4 冷缓存坑），复测：报工作集与 L3 的比值，换一个远超 L3 的规模重跑。
2. 临界区撑到整个循环等于串行化整个程序，8 线程退化为 1 线程加 7 个观众，时间回到 serial 档的 40.91 ms（§5.4）。正确的判据是次数乘单价：单次 mutex 归并约 69 ns，只要每次同步摊到几千元素以上（本例 G≥1K），同步价就藏进访存等待，merge 与 mutex G≥64K 的实测（6.27 对 5.69～5.89）说明「少」与「粗」之间最优解在中间。
3. 8 条重条纹共 ${8 \times 17 + 8 = 144}$ 单位，p=8 静态等分每人 2 条纹：线程 0 到 3 各拿 ${17 + 1 = 18}$ 单位，其余各 2 单位，$\max_i W_i$ 仍是 18，与 §5.3 原版（2 条重条纹、同为 18 单位）几乎不变，静态时间比不动；动态定长本来就按完成度发货，144 单位比 48 单位的绝对时间涨 3 倍但比值不变。两档都不敏感时说明瓶颈已从负载不均换成带宽，验证手段是把条纹宽度调小让不均更碎，看动态档是否重新拉开差距（§5.3）。

**你现在能做什么**：拿到任何一段想并行的循环，你能先问三件事——活匀不匀（决定静态还是动态）、总账怎么对（决定锁的粒度与种类）、并行段自己能扩张多少倍（决定别拿 Amdahl 单墙当预算），然后设计对照实验，让每一步改动都被 worker 手里的表审判。
