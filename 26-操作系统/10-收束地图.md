## $\rm \S \, 10.1$ 一张总图：程序 = 一组被内核记账的资源

把九章的概念按「内核记的账」重新摆一遍：

| 账本 | 记的是什么 | 对应机制 | 出问题的样子 |
| --- | --- | --- | --- |
| 进程表 | 谁在运行、谁在等什么（§2.1） | PID、状态机、等待队列 | 卡死不响应（§7 的互等） |
| 页表 | 每个进程的假地址怎么映射（§4.3） | 多级页表、TLB | 缺页风暴、抖动（§5.5） |
| 锁与 futex | 谁持有、谁在门外排队（§6.5） | CAS、内核等待队列 | 争用烧自旋、死锁（§7） |
| inode 与目录表 | 名字与数据块的对账（§8.3） | 链接数、块位图、日志 | 空间泄漏、悬空引用（§8.5） |
| fd 就绪表 | 哪些 I/O 可以动了（§9.4） | epoll 就绪链表 | 队头阻塞、惊群（§9.3–9.4） |

一句收束：**操作系统就是五本账的记账员；调优与排障，就是核对哪本账出了错**。

## $\rm \S \, 10.2$ 程序慢了：四步定位顺序

按「代价从大到小、检查从粗到细」排一个固定顺序，每步都有内核侧的观测点：

1. **CPU 慢**：先看使用率与 R 状态。CPU 满载且大量进程处于 R（运行态），才是计算瓶颈；否则别急着优化算法。观测：`/proc/stat` 两次采样、`top` 的 load 对比核数；
2. **内存慢**：CPU 不满但系统吞吐上不去，查缺页。major fault（要走磁盘）暴涨即内存不足在硬扛；再狠一点是 §5.5 的抖动：CPU 花在换页上。观测：`vmstat` 的 `si/so` 列、`/proc/vmstat` 的 `pgmajfault`；
3. **I/O 慢**：内存没问题、等待集中在读写，查块设备利用与队列深度。观测：`iostat -x` 的 `%util` 与 `await`（计算机速通 §10.2 的磁盘量级感在此兑现）；
4. **锁慢**：前三步都健康、线程大量睡眠且 wake 后立刻又睡，基本是争用。观测：`perf lock`、Python 侧 `py-spy top` 的热点是否落在 `acquire`。

每一步的判定标准都写成「读数 + 阈值方向」，不是「感觉不对」：

| 步 | 判「有问题」的读数 | 判「健康」的读数 |
| --- | --- | --- |
| 1 CPU | 使用率持续 > 90% 且 R 进程数 ≈ 核数 | load < 核数 × 0.7 |
| 2 内存 | si/so 持续 > 0、major fault 每秒上涨 | si/so = 0 |
| 3 I/O | %util > 90% 或 await 超设备正常值数倍 | await 在毫秒级常态 |
| 4 锁 | 栈热点聚在 acquire、ctx switch 激增 | 无锁等待堆积 |

一个能直接跑的三件套（WSL2、内核 6.6.87 采集）：

```python
import time, subprocess
def cpu():                      # /proc/stat 首行：各项累加 jiffies
    vals = list(map(int, open('/proc/stat').readline().split()[1:]))
    return sum(vals), vals[3] + vals[4]        # 总量, 空闲
a1, i1 = cpu(); time.sleep(1); a2, i2 = cpu()
print(f'CPU {100*(1-(i2-i1)/(a2-a1)):.1f}%')
print('loadavg:', open('/proc/loadavg').read().split()[:3])
print('R 进程:', sum(1 for l in subprocess.run(['ps','-eo','stat='],
      capture_output=True, text=True).stdout.split() if l.startswith('R')))
```

本机实测（空载）：

```text
CPU 1.1%
loadavg: ['0.49', '0.28', '0.11']
R 进程: 1
```

读法示范：CPU 1.1% 说明「慢」不在计算；load 0.49 远低于核数说明也不缺 CPU；R 进程只有 1 个（就是采样自己），三行输出把第 1 步直接判掉，排查往内存/I/O 方向走。这就是「先粗后细」：每一步都用观测证据开路，不凭感觉换代码。

同一个「服务变慢了」，三种典型慢法在四步里的落点完全不同：

| 慢法 | 第 1 步判据 | 第 2 步判据 | 第 3 步判据 | 最终落点 |
| --- | --- | --- | --- | --- |
| CPU 密集（新加了个 O(n²) 统计） | CPU ≈ 100%、R 一片 | si/so = 0 | iowait 低 | 第 1 步即命中，回代码做 profiling |
| 内存不足（数据集涨过内存） | CPU 中低、load 高但 R 少 | si/so 持续、major fault 涨 | 磁盘忙的是 swap 区 | 第 2 步命中，回到 §5.5 抖动 |
| 日志刷盘（每次请求多一次 fsync） | CPU 低、R 极少 | 缺页正常 | %util 近百、await 高 | 第 3 步命中，查写入模式与 §8.6 的日志档位 |
| 锁争用（热点数据一把粗锁） | CPU 中低但「跑不满」 | si/so = 0 | iowait 低 | 前三步全健康才轮到第 4 步：抓栈见 `acquire`，按 §6.7 拆锁 |

三行的观测在每种慢法里读数组合都不同：**定位不是「跑很多工具」，是「同一组读数的组合判型」**。注意第四行锁慢法的判据是「前三步全部健康」：它没有自己专属的计数器，只能靠排除法显形，这也是它排在最后的原因。

**本节小结**：四步是「CPU → 内存 → I/O → 锁」的固定筛网，每步只认读数不认感觉；同一种「慢」在不同步上留下不同的读数组合，前三步全健康才轮到靠排除法定罪的锁。

## $\rm \S \, 10.3$ 程序卡了、程序炸了：两个快速判例

**卡（不响应）**：先分「死了还是等了」。`ps` 看 STAT：`D`（不可中断睡眠，多半在等 I/O 或换页，§5.3）、`S`（可中断睡眠，等锁/等网络）、`Z`（僵尸，§2.4）、`R` 正常。线程全 `S` 且栈底都在 `acquire` → 回 §7.2 画等待环；单线程 `D` 态不退 → 存储/内存压力方向。工具：`py-spy dump`（Python）、`gdb -p`（C/C++）。

一个真实判例形状：进程 `ps` 显示 `D` 十几秒不退、`kill -9` 都无效：不是进程蛮横，是它陷在不可中断的系统调用里（常见于 NFS 失联或磁盘故障），信号要等它返回用户态才能送达。此时排查对象不是进程，是它脚下的存储路径。顺手的例行检查还有一条：`ps aux | awk '$8 ~ /Z/'` 数僵尸，大批 `Z` 说明父进程没 `wait`（§2.4），泄漏的是进程表条目。

**炸（崩溃/被杀）**：`Segmentation fault` 是页表账没对上，写了没映射或只读的页（§4.2 的保护位）；`Killed` 无core多半是 OOM：内核的内存账付不起，挑大头进程杀掉保机器（观测：`dmesg | grep -i oom`）。竞赛直觉「越界=RE」在原理层就是这条：地址翻译的拒绝。

**本节小结**：卡与炸各有一张速查表——卡先分「死了还是等了」，看 STAT 字段分流到存储路径、等待环或僵尸清理；炸先问「谁没对上账」，段错误归页表、OOM kill 归内存账。两条都直接接回前九章的原理章。

## $\rm \S \, 10.4$ 三条通往其他分册的接口

1. **数据库分册**：它的 WAL 与本书 §8.5 的文件系统日志是同一个思想（先记日志再动账）；它的 B+ 树站在 §8.1「按页读写」的地基上；它的锁与 §7.4 的库级/行级粒度直接对话，连接池打满、慢查询拖垮整机这类事故，账本横跨两册（fd 就绪账 × 锁账），要两边对着读；
   
2. **计算机网络分册**：epoll 是网络服务器的地基（§9.5 的 C10K）；连接的「等」与 TIME_WAIT 的账最终都要落到本书的 fd 与等待队列上；
3. **计算机速通册**：Ch10–13 的工具层（`top`、`ps`、`free`、`ss`、日志）在这九章里全部拿到了原理层的解释。常用的几行输出到账本的对照：

| 工具输出 | 读的是哪本账 | 原理出处 |
| --- | --- | --- |
| `top` 的 RES/SWAP | 页表与驻留集 | §4.5、§5.3 |
| `top` 的 S 列（R/S/D/Z） | 进程状态机 | §3.1、§2.4 |

**本节小结**：三条接口的方向是「本书在中间」：数据库的 WAL 与 B+ 树踩在 §8 的日志与页读写上，网络服务器踩在 §9 的 fd 与等待队列上，速通册的工具行输出都能折算回某一本账——事故横跨分册时，账本也横跨。

## $\rm \S \, 10.8$ 本章自测答案

### $\rm \S \, 10.8.1$ 关键概念回顾答案

1. 进程表（§2，卡死/互等）、页表（§4–5，缺页风暴/抖动）、锁账（§6–7，争用/死锁）、inode 与目录（§8，泄漏/悬空）、fd 就绪（§9，队头阻塞/惊群）。（§10.1）
2. 依据是「检查成本与覆盖面」：CPU 一眼可判（三件套两行）且排除后方向立刻收窄；锁的判定最贵（要抓栈、画等待图），放在前面三步都健康之后才值得做。粗的先筛，细的后查。（§10.2）
3. 都在睡眠，但 D 不可中断，连信号都叫不醒，多半卡在 I/O 或换页（§5.3）；S 可被信号唤醒，常见于等锁/等网络（§9.1）。前者查存储与内存，后者查代码里的等待关系。（§10.3）
4. 段错误是页表账，访问了未映射或权限不符的地址，翻译被拒（§4.2）；OOM kill 是内存账，物理页与交换空间付不起，内核按记账选牺牲者（观测在 `dmesg` 的 oom 记录）。（§10.3）

### $\rm \S \, 10.8.2$ 应用与辨析答案

1. ① `/proc/stat` 两采样 + load 对核数：CPU 高且 R 多 → 计算瓶颈，转 profiling；② `vmstat 1`：`si/so` 持续非零或 major fault 涨 → 内存压力，查泄漏与缓存；③ `iostat -x 1`：`%util` 近百或 `await` 飙 → 存储瓶颈，查日志刷盘与 fsync；④ 前三步健康则 `py-spy dump`/`perf lock` 抓锁，栈聚在 `acquire` 即争用，按 §7.3 拆锁排序。（§10.2）
2. 漏了两层：free 只算「未分配」，内核拿大量内存做页缓存（可回收但不白给）；抖动的判据不是 free 余量，是**换页活动**，`si/so` 与 major fault 才是「正在硬扛」的直接证据。（§5.5、§10.2）
3. epoll 优化的是「等待的组织」（fd 就绪账），不是任何一个连接的数据通路速度：§9.3 实验里 A 在两种模型下都是 0.6 秒被服务。放到定位顺序里：它属于第 4 步「等待与锁」的范畴，若瓶颈测出来在第 1–3 步（CPU/内存/I/O），换 epoll 无解。（§9.3、§10.2）
