# $\rm Chapter \, 12$ 推理服务：KV cache、连续批处理与投机解码

出货窗口。训练花的是一次性的钱，服务花的是每一天的钱——一个模型上线后，单位质量的服务成本由这一章的四件套决定：KV cache 管显存、连续批处理管调度、量化管压缩、投机解码管延迟。它们共同回答一个反直觉的问题：为什么解码看起来要每 token 读一遍全部权重，多开几个请求却几乎不增加成本？

> **开始前自检**：本章假设你已经会：
>
> 1. □ 算术强度与访存受限/算力受限的判定（第 6 章）；
> 2. □ GQA 用共享 KV 头省显存的机制（第 4 章）；
> 3. □ 推理每 token 约 ${2N}$ FLOPs 的账（第 1 章）；
> 4. □ 自回归解码：前文作为条件逐 token 生成（第 5 章）。

## $\rm \S \, 12.1$ 需要的前提

1. **机器平衡点**：GPU 每秒能算的 FLOPs 与每秒能读的字节之比约为每字节两三百次乘加（第 6 章）。一段代码的「算术强度」（每读一字节做几次运算）低于它，就在等显存；高于它，才算力拉满。
2. **prefill 与 decode**：处理用户输入的整段 prompt 叫 prefill（一次前向算完所有位置），逐 token 生成回答叫 decode（每步一个 token）。两阶段的性能形态完全不同，是本章一切调度的根源。
3. **白话开场**：训练是把书读厚（算力换能力），服务是把书读薄（显存换并发）。这一章的每个组件都是一次「同样多的答案、更少的显存/时间」的搬运术。

## $\rm \S \, 12.2$ 两阶段推理：为什么 decode 慢、prefill 快

decode 每步生成一个 token，计算量约 ${2N}$ FLOPs——但它必须把全部 ${2N}$ 字节（bf16）权重从显存读一遍。算术强度约 1 FLOP/字节，远低于机器平衡点：**decode 是访存受限的**，GPU 的算力单元大面积闲置。H100 上读 16 GB（8B 模型 bf16）按 3.35 TB/s 算约 5 ms，这就是 8B 模型单请求解码速度的天花板量级，与算力无关。

prefill 相反：整段 prompt 的所有位置并行计算，矩阵乘成大块，算术强度轻松过平衡点，是算力受限——所以首 token 延迟与 prompt 长度成正比、与「能不能并行」有关。一个 prompt 2000 token 的 prefill 在 8B 模型上是 ${2N\times 2000\approx 3.2\times 10^{13}}$ FLOPs，约 0.1 s 量级（按 40% MFU）——比解码 2000 个 token（约 10 s）快两个数量级。

这组不对称直接推出两条工程结论：第一，**prompt 越长，首字越慢**，但整体 prefill 从来不是大头；第二，decode 每步都要读全部权重，读一次只产一个 token——**多带几个请求一起解码，权重读取摊薄，吞吐近乎白送**。这就是 batching 的物理学基础。

本节小结：prefill 算力受限、decode 访存受限；decode 的成本在「读权重」，于是并发几乎免费、延迟由显存带宽决定。

## $\rm \S \, 12.3$ KV cache：把历史记住

### $\rm \S \, 12.3.1$ 为什么必须有它

没有缓存的自回归解码，每生成一个 token 都要对「全部历史」重算一遍各层的 K、V（注意力键值）——生成第 $t$ 个 token 的代价是 ${O(t)}$，整段生成的代价是 ${O(L^2)}$。观察：历史 token 的 K、V 根本不会变（它们只依赖各自之前的内容），算一次存起来即可。这份缓存就是 KV cache，代价是把解码的空间复杂度变成随上下文线性增长。

### $\rm \S \, 12.3.2$ 显存账：GQA 的 4 倍红利

每个 token、每一层要缓存的字节数（bf16）：

$$
\text{每 token 每层} = 2\ (\text{K 与 V}) \times n_{kv} \times d_{head} \times 2\ \text{字节}
$$

实测对账（`_lfs_work/exp12/result.txt`，Llama-3-8B 配置，32 层、${d_{head}=128}$、8K 上下文）：

1. **MHA（32 个 KV 头）**：每 token 每层 16384 B，全层 512 KB/token；一条 8K 序列 4.00 GB。
2. **GQA（8 个 KV 头）**：每 token 每层 4096 B，全层 128 KB/token；同上下文 1.00 GB。

GQA 把 KV 头从 32 砍到 8，服务显存直接除以 4——第 4 章那个「省 KV 头」的结构决定，在这里兑现成并发能力：80 GB 的卡减去 16 GB 权重与激活，能同时驻留的 8K 序列从十几条变成几十条。

### $\rm \S \, 12.3.3$ cache 带来的新问题

KV cache 把显存变成了稀缺调度资源：每条请求的缓存随生成增长、长度事先未知，多个请求的缓存怎么摆、怎么回收，成了推理系统的核心问题——$\S 12.5$ 的分页就是为它而生的。

本节小结：KV cache 用 ${O(L)}$ 显存把解码从 ${O(L^2)}$ 计算里救出来；账是「2×KV头×头维×2字节×层数」，GQA 直接四倍红利。

## $\rm \S \, 12.4$ 连续批处理：调度粒度从「请求」改成「步」

最朴素的 batching 把一批请求凑一起、整批进出：同一批里有人 50 token 就完了、有人 500 token 还在写，短请求的位置只能空转，batch 里的算力在等最长的那个。Orca（Yu et al. 2022）提出的方案叫**连续批处理（continuous batching，迭代级调度）**：每完成一个解码步就盘点——谁生成完了立刻出队、腾出的位置立刻让新请求入队，batch 永远保持满员。吞吐提升的量级是数倍（据 vLLM 论文对静态方案的对比）。

两个衍生问题：其一，新请求的长 prefill 插进来会卡住整个 batch 一步（prefill 比 decode 慢两个量级），工程解法是 **chunked prefill**——把长 prompt 切成小块分几步吃进去，与 decode 步混排；其二，更激进的架构把 prefill 与 decode 拆到不同的机器池（PD 分离，据 DistServe，Zhong et al. 2024），各自按自己的瓶颈配硬件——prefill 池要算力、decode 池要带宽。

本节小结：调度粒度从「整批请求」细到「单步 token」，空转消失；长 prefill 的插队与饥饿用切块与分离处理。

## $\rm \S \, 12.5$ PagedAttention：给 KV cache 上分页

显存碎片有两个来源：请求还没来就按最大长度预留（内部碎片），以及相邻请求的缓存大小各异、空闲块对不上（外部碎片）。vLLM 的 PagedAttention（Kwon et al. 2023）把操作系统管内存的老办法搬了过来：把每条序列的 KV cache 切成固定大小的块（约 16 token 一块），逻辑连续、物理离散，按需分配、随生成随长。论文口径下 KV 显存浪费从六到八成压到 4% 以下——同样的显存立刻多驻留几倍的并发序列，这就是 vLLM 吞吐神话的主体。

操作系统分册的「分页」在这里逐字复用：页表、按需分配、写时复制（多请求共享同一 prefix 时 KV 块直接共享）。这也是本册与系统学部那几册最漂亮的一次会师——大模型推理的最后一公里，用的是 1960 年代的内存管理智慧。

本节小结：KV cache 的碎片靠分页治：固定块、逻辑连续物理离散、按需增长，浪费从七八成压到 4% 以下。

## $\rm \S \, 12.6$ 量化：把权重压到 4 比特

第 1 章说过推理显存按 2 字节/参数起步。压到 1 字节（int8）是热身，压到半字节（int4）才是主菜：8B 模型从 16 GB 到约 4.5 GB（含缩放元数据）。代价是精度，控制代价的手段是**分组缩放**：把权重每 128 个一组，每组记录自己的最大绝对值作 scale，量化误差不再被整张矩阵的离群值绑架。实测（`exp12/result.txt`，4096×4096 随机权重，对称 int4）：

1. 分组 128：相对 Frobenius 误差 0.1173；
2. 整矩阵单 scale：误差 0.2176——差近一倍，因为少数离群值把公共 scale 撑大，多数正常值被压没。

进阶：AWQ（Lin et al. 2024）按激活分布挑「重要通道」给更高精度保护；GPTQ（Frantar et al. 2023）逐列量化并用二阶信息补偿误差。KV cache 本身也能压到 fp8——它的显存占比随并发与上下文增长，长上下文服务里比压权重更划算。

本节小结：int4 加分组缩放把推理显存除以 4、误差约一成；离群值是量化唯一的天敌，分组、AWQ、GPTQ 全是围着它转的招。

## $\rm \S \, 12.7$ 投机解码：用小模型给大模型代笔

decode 是访存受限——每步读一遍权重只产一个 token，带宽严重浪费。投机解码（Leviathan et al. 2023；Chen et al. 2023）的思路：让一个便宜的小草稿模型连写 $\gamma$ 个候选 token，再用大模型**一次前向并行验证**这 $\gamma{+}1$ 个位置（大模型本来就要读一遍权重，顺手把 $\gamma{+}1$ 个位置的 logits 全算出来，几乎不加时间），接受通过的、在第一个被拒处修正。

**接受的规则要保证结果分布不变**。设大模型分布 $p$、草稿分布 $q$，对草稿给的 token $x$：以概率 ${\min(1,\,p(x)/q(x))}$ 接受；若拒绝，从**残差分布** ${\mathrm{norm}(\max(p-q,\,0))}$ 里重采一个修正 token。证明只要一行：每个位置产出 $x$ 的总概率是

$$
q(x)\min\!\Big(1,\frac{p(x)}{q(x)}\Big) + \max\big(p(x)-q(x),\,0\big) = \min(p,q) + \max(p-q,0) = p(x)
$$

读法：草稿给得准的部分照单全收，给不准的部分被残差分布矫正——最终输出与大模型自己采样的分布逐点相同，**不损质量，只省时间**。

省多少？设单 token 接受率 $\alpha$（草稿与大模型分布的接近程度），每轮循环期望产出的 token 数是

$$
\mathbb{E}[\text{接受}] = \sum_{i=0}^{\gamma} \alpha^i = \frac{1-\alpha^{\gamma+1}}{1-\alpha}
$$

推导：前 $i$ 个全接受的概率是 $\alpha^i$，第 $\gamma{+}1$ 个位置（验证步白送的那个）必产出一个 token，逐项求和即几何级数。实测对账（`exp12/result.txt`，$\gamma=4$，蒙特卡洛十万次）：

| $\alpha$ | 公式值 | 蒙特卡洛 |
| --- | --- | --- |
| 0.6 | 2.306 | 2.316 |
| 0.8 | 3.362 | 3.363 |
| 0.9 | 4.095 | 4.095 |

白话：草稿越像大模型（$\alpha$ 越高），每读一遍权重能白捡的 token 越多；$\alpha=0.8$ 时每轮 3.4 个，近似三倍加速。$\alpha$ 的经验带在 0.7–0.9（工业惯例），来自「同源小模型 + 蒸馏」或「同模型提前退出」等草稿构造。

一条边界要说破：投机解码只在**访存受限**（小 batch）时是白捡——batch 一大、算力被验证吃满，就退化成纯亏。所以它是「单请求低延迟」的武器，不是吞吐武器。

本节小结：草稿代笔、大模型并行验证，残差采样保证分布逐点不变；期望收益是几何级数 ${(1-\alpha^{\gamma+1})/(1-\alpha)}$，只在访存受限时兑现。

## $\rm \S \, 12.8$ 服务指标与成本账

1. **TTFT**（time to first token，首字延迟）：由排队 + prefill 时间决定，交互产品的命门——用户对「等第一个字」比对「每个字快慢」敏感得多。
2. **TPOT**（time per output token，逐字延迟）：decode 步长，决定打字机流畅感；受 batch 大小与显存带宽支配。
3. **吞吐**（tokens/s/GPU）：平台的成本指标，与上面两条天然拉扯——batch 越大吞吐越高、TPOT 越差。SLO 管理就是把 TTFT、TPOT 各设上限，在夹缝里最大化吞吐。
4. **成本换算**：一切最后落到每百万 token 的钱。GPU 租金刚性成本 ÷ 有效吞吐，再乘利用率折损；这也是第 1 章「训练预算 vs 推理摊销」的账闭环的地方——过度训练的小模型在这里把训练多花的钱赚回来。

本节小结：TTFT 管「等得久不久」、TPOT 管「流不流畅」、吞吐管「一 token 几文钱」；三者由 batch 大小与调度统一权衡。

## $\rm \S \, 12.9$ 工程实录：出货窗口的师傅账

1. **prefix cache 吃重复前缀**。大量请求共享同一长 system prompt（agent 类产品尤其明显），把公共前缀的 KV 块存成可复用（Radix 树管理，据 SGLang），prefill 直接跳过命中部分——TTFT 掉一个量级的案例很常见。上线前统计前缀命中率，低于两成说明 prompt 模板该收敛了。
2. **CUDA graph 消启动开销**。decode 单步的计算被几百个小 kernel 切碎，每次 launch 的固定开销在小 batch 时占比惊人；把整步录成 CUDA graph 重放，小 batch TPOT 能省两三成（工业惯例）。
3. **块大小不是越小越好**。分页块 16 token 是经验值：块小碎片少但元数据与访存碎，块大省元数据但内部碎片涨；改之前先量自己产品的平均生成长度分布。
4. **量化选型看场景**。W4A16（权重 int4、激活 bf16）省显存省带宽，单请求延迟最友好；W8A8（SmoothQuant 路线）算力受限场景更快但省得少。KV cache 长上下文优先压 fp8。选型前跑一遍目标模型的真实输出对比（困惑度 + 人工抽查），离群值敏感的模型（MoE 常见）int4 会伤分。
5. **投机解码的接受率要监控**。上线后 $\alpha$ 会随流量分布漂（用户问的领域变了，草稿模型不熟），加速比跟着掉；把「每轮接受长度」做成看板指标，跌破阈值自动回退普通解码。
6. **灰度与回滚**。模型更新与推理框架更新分开灰度：先切 5% 流量看 TTFT/TPOT/业务指标，出问题秒级回滚到旧权重（旧权重常驻显存或就近缓存）。权重文件巨大，「加载 8 GB 再启动」的冷启动本身就是事故源——热备与预热是上线清单的固定项。

本节小结：出货窗口的账本页码——prefix 命中率、CUDA graph、块大小、量化选型、接受率、灰度回滚，六项全部进看板与上线清单。

## $\rm \S \, 12.10$ 常见错误与证据

1. **拿 prefill 的优化思路治 decode**（或反之）。prefill 是算力受限，堆算子优化有回报；decode 是访存受限，同样的优化收益趋零。判据：先算算术强度再选优化方向（第 6 章的判定流程原样适用）。
2. **KV 账漏乘层数或用错 KV 头数**。把 8K 上下文算成 32 MB（漏乘 32 层）或者忘了 GQA 是 8 不是 32 头，容量规划直接错 4–32 倍。判据：拿 §12.3.2 的公式逐项代数，再用「128 KB/token」这个锚核对。
3. **大批量下开投机解码**。batch 已把算力喂饱，验证 ${\gamma{+}1}$ 个位置就是真金白银的计算量，期望加速变成负数。判据：先看 GPU 利用率——访存受限才开。
4. **整矩阵单 scale 上 int4**。实测误差 0.2176 对分组 0.1173，翻倍损失；某些层（跟 MoE 专家或 embedding 相关）离群更凶，会更差。判据：量化后必须跑困惑度回归，逐层对比权重量化前后的范数。
5. **把吞吐当延迟汇报**。「我们单卡 3000 tokens/s」若是大 batch 吞吐，跟用户体感的 TPOT 毫无关系。判据：汇报时 TTFT、TPOT、吞吐三个数分开给，并附 batch 大小。

## $\rm \S \, 12.12$ 应用与辨析

1. 一个 8B 模型服务要扛 100 路并发 8K 上下文。算一算：bf16 权重 + GQA KV cache 需要多少显存？一张 80 GB 卡行不行、两张呢？给出优化顺序。
2. 产品经理要求「首字延迟减半且吞吐不降」。指出这个要求与哪个物理量冲突，并给两个工程上的折中方案。
3. 有同事建议「把投机解码的 $\gamma$ 从 4 加到 16，加速再翻番」。分析这个提议在 $\alpha=0.8$ 和 $\alpha=0.3$ 下各自的期望收益变化，说明为什么 $\gamma$ 不是越大越好。
4. 长上下文（128K）服务上线后显存爆了。按本章的四件套（KV 账、分页、量化、调度）各给一条可立刻执行的缓解动作，并排出先后。

## $\rm \S \, 12.13$ 本章自测答案

> 先闭卷作答 §12.11 与 §12.12，再核对。

### $\rm \S \, 12.13.1$ 关键概念回顾答案

1. prefill 整段并行处理 prompt（大矩阵乘、算术强度高、算力受限）；decode 逐 token 生成（每步读全部权重只产一个 token、算术强度约 1 FLOP/B、访存受限）。（§12.2）
2. decode 的成本瓶颈是把权重从显存读出来；多个请求共享同一次权重读取，摊薄后每请求的边际显存带宽成本大幅下降，算力本来就闲着。（§12.2）
3. 每 token 每层 ${2\times n_{kv}\times d_{head}\times 2}$ 字节；实测 MHA 512 KB/token、8K 共 4.00 GB，GQA 128 KB/token、共 1.00 GB；GQA 省 4 倍。（§12.3.2）
4. 静态按批进出、短请求空转；连续批处理按步调度、满员滚动。chunked prefill 治长 prompt 插队卡批；PD 分离让 prefill 与 decode 各按瓶颈配硬件。（§12.4）
5. KV cache 切成固定小块（约 16 token），逻辑连续、物理离散、按需分配；预留式碎片消失，浪费从六到八成降到 4% 以下。（§12.5）
6. 离群值撑大公共 scale、把正常值压没；分组让每组有自己的 scale。实测分组 0.1173、单 scale 0.2176。（§12.6）
7. 接受概率 ${\min(1,p/q)}$、拒绝从 ${\mathrm{norm}(\max(p-q,0))}$ 重采；${q\min(1,p/q)+\max(p-q,0)=p}$，分布逐点不变。期望 ${\sum_{i=0}^{\gamma}\alpha^i=(1-\alpha^{\gamma+1})/(1-\alpha)}$。（§12.7）
8. TTFT＝排队+prefill；TPOT＝decode 步长（batch 与带宽）；吞吐与二者拉扯由 batch 权衡。投机解码在算力受限（大 batch）时失效。（§12.8、§12.7）

### $\rm \S \, 12.13.2$ 应用与辨析答案

1. 权重 bf16 16.1 GB；KV 每 token 128 KB，100 路 × 8K × 128 KB ${\approx}$ 102.4 GB——合计约 118 GB，单张 80 GB 不行，两张勉强（还剩激活与余量）。优化顺序：先 KV fp8（KV 减半到 51 GB，单卡仍不够）；再 int4 权重（16→4.5 GB，两张卡轻松、单卡仍差 KV）；根治要么上第三张卡、要么把并发分片到多实例。（§12.3、§12.6）
2. 冲突在 decode 的访存带宽：TTFT 减半主要靠 prefill 加速，吞吐不降要求 batch 不减，而 batch 变大 TPOT 变差、单步变慢反过来拖长整体生成时间。折中一：prefix cache 削 prefill 量（对长公共前缀场景等效减半 TTFT）；折中二：chunked prefill 把 prefill 拌进 decode 步，首字稍延后但 batch 满员，TTFT 与吞吐各让半步。（§12.4、§12.9）
3. $\alpha=0.8$：$\gamma=4$ 期望 3.36，$\gamma=16$ 期望 ${ (1-0.8^{17})/0.2\approx 4.92 }$——收益 +46%，但每轮验证的计算量随 $\gamma$ 线性涨、且被拒时已生成部分全部作废重采，边际回报递减明显；$\alpha=0.3$：$\gamma=4$ 期望 1.43，$\gamma=16$ 期望约 1.43——几乎不变（几何级数尾部 $\alpha^{17}$ 可忽略），纯增加验证开销与缓存。所以 $\gamma$ 加大只在 $\alpha$ 高时有边际收益，且有作废浪费，工程上 4–8 是常见带。（§12.7）
4. 先后：一，立即查调度上限（最大并发与最大上下文配置），砍超限请求、开请求准入——止血；二，KV 量化的 fp8（显存立即减半）；三，开分页确认（若还没用 vLLM 类运行时，这一步是主修复）；四，结构性的：换 GQA/加 KV 头共享或上下文并行（动模型，最后做）。（§12.3–§12.6）
