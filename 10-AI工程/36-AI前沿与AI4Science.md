## $\rm \S \, 36.1$ AI for Science：当 AI 遇到科学

### $\rm \S \, 36.1.1$ AlphaFold：五十年难题的终结

**蛋白质折叠问题**的难度：一个蛋白质是一串氨基酸序列（如“ALYVCF...”），在细胞内它会自动折叠成一个精确的三维形状——这个形状决定了蛋白质的功能。如果你知道氨基酸序列，你能预测它的三维形状吗？这个问题困扰了生物学家五十年——理论上可能的折叠方式是一个天文数字（Levinthal 悖论）。

2020 年，DeepMind 的 **AlphaFold 2** 在 CASP14（蛋白质结构预测竞赛）中给出了令整个结构生物学界震惊的结果——在多数目标上达到接近实验方法（X 射线晶体学、冷冻电镜）的精度，而单个结构只需分钟级计算，不是数月的实验。

AlphaFold 不是“又是一篇 AI 论文”——它改变了生物学家的工作流程。在此之前，确定一个蛋白质的结构需要数月到数年的实验室工作和数百万美元。现在你输入一个氨基酸序列，AlphaFold 在几分钟内给出三维结构。

### $\rm \S \, 36.1.2$ AI for Science 的范式

传统的科学研究流程是：观察现象 → 提出假设 → 设计实验 → 收集数据 → 验证假设 → 修正理论 → 重复。这个循环中“设计实验”和“收集数据”通常是最昂贵的一步。

AI 可以做三件事来加速这个循环：
1. **替代昂贵的实验**：AlphaFold 用计算替代了 X 射线晶体学。
2. **从已有数据中发现人类看不见的模式**：GraphCast（Google DeepMind）用 AI 做全球天气预报——传统数值天气预报需要超级计算机跑几个小时，AI 模型在一分钟内给出预报，在多数变量和预报时效上精度相当甚至更好（具体取决于评估指标与区域）。
3. **提出新的假设**：GNoME（Google DeepMind）用 AI 预测了 220 万种新的晶体结构（材料科学），相当于 800 年的实验工作量。

### $\rm \S \, 36.1.3$ AI for Science 谱系

| 领域 | 代表系统 | 解决什么问题 |
|---|---|---|
| **结构生物学** | AlphaFold 3、RoseTTAFold | 蛋白质/DNA/小分子复合物结构预测 |
| **药物发现** | AlphaFold + 分子对接、DiffDock | 虚拟筛选候选药物、预测药物-靶点结合方式 |

## $\rm \S \, 36.2$ AI Agent：不只是“我问你答”

### $\rm \S \, 36.2.1$ 什么是 Agent

你在[AI 工程概览](33-AI工程概览.md)中见过的“对话式辅助”是 L1——你问一句、AI 答一句。“Agent”是 L3——你给 AI 一个**目标**，AI 自己规划步骤、选择工具、执行操作、观察结果、修正计划，直到完成目标。

一个 Agent 的核心循环：

```text
任务 → 推理（我该做什么？）→ 行动（执行命令/调 API）→ 观察（看看结果是什么）→ 推理（下一步做什么？）→ ... → 完成
```

它在结构上类似你在[操作系统、进程与线程](../03-计算机系统/11-操作系统进程与线程.md) §11.4 学过的信号处理循环——“事件到达 → 响应 → 回到等待”；区别是 Agent 的“事件”来自工具返回的环境反馈而不是操作系统信号，而且下一步做什么要由它自己推理决定，信号处理函数只是被动响应。

### $\rm \S \, 36.2.2$ Agent 的关键组件

| 组件 | 职责 | 例子 |
|---|---|---|
| **LLM**（大语言模型） | 推理和规划 | Claude、GPT |
| **工具**（Tools） | 与外部世界交互 | 搜索网页、运行代码、读写文件、调 API |
| **记忆**（Memory） | 跨轮次保留上下文 | 对话历史、向量数据库中的长期记忆 |
| **规划**（Planning） | 分解复杂任务 | “先搜索相关论文→再写代码→再运行测试→再修复” |

### $\rm \S \, 36.2.3$ RAG：检索增强生成

**RAG**（Retrieval Augmented Generation，检索增强生成）是当前最广泛使用的 Agent 模式之一。它解决的核心问题：LLM 的知识截止于训练日期，且无法访问你的私有数据。

RAG 的流程很简单：

1. 用户提问：“论文管理器后端用的是哪个数据库？”
2. 系统把问题转换为搜索查询，从你的项目文档/代码库中检索最相关的片段。
3. 系统把检索到的片段和原始问题一起发给 LLM：“根据以下资料回答：{资料}。问题：{问题}”
4. LLM 基于资料给出准确答案——而不是瞎编。

这和你在[数据库基础](../07-应用开发/27-数据库基础.md)中学过的“索引加速查询”是同一个思路：不遍历所有数据（不把所有文档塞进 LLM 的上下文），而是先检索出相关部分，只给 LLM 看这些。

### $\rm \S \, 36.2.4$ Chunking：文档该切多大

检索的单位不是“一篇文档”而是**块（chunk）**。整个文件太大——一篇 30 页的手册塞进上下文既贵又会让模型漏掉细节；一句话太小——单独一句话常常丢了它说的到底是哪个对象。切分策略决定了检索的上限：**块里没有的信息，再好的模型也检索不出来**。

两种基本切法各有代价：

```python
# chunking.py：同一份文档的两种切法
docs = """# 论文管理器
## 数据层
论文数据存放在 SQLite 的 papers 表中，字段包括 title、year、authors。
标签是多对多关系，通过 paper_tags 中间表维护。

## 后端
后端用 FastAPI 暴露 REST 接口，/papers 支持按 year 和 tag 筛选。
所有写操作都要走事务，避免标签写了一半。

## 部署
服务用 systemd 管理，日志通过 journalctl -u paper-api 查看。
"""

def fixed_chunks(text, size=80, overlap=20):
    out, i = [], 0
    while i < len(text):
        out.append(text[i:i + size])
        i += size - overlap          # 重叠：相邻块共享 overlap 个字符
    return out

def structural_chunks(text):
    """按 Markdown 小节切，每个块自带所属章节标题。"""
    out, section = [], ""
    for line in text.split("\n"):
        if line.startswith("#"):
            section = line.strip("# ").strip()
            continue
        if line.strip():
            out.append(f"[{section}] {line.strip()}")
    return out

print("=== 固定长度 + 重叠 ===")
for c in fixed_chunks(docs):
    print(repr(c))
print(f"块数: {len(fixed_chunks(docs))}")

print("\n=== 按结构切 ===")
for c in structural_chunks(docs):
    print(repr(c))
print(f"块数: {len(structural_chunks(docs))}")
```

实测输出（Python 3.12，节选）：

```text
=== 固定长度 + 重叠 ===
'# 论文管理器\n## 数据层\n论文数据存放在 SQLite 的 papers 表中，字段包括 title、year、authors。\n标签是多对多关系，通过 p'
'thors。\n标签是多对多关系，通过 paper_tags 中间表维护。\n\n## 后端\n后端用 FastAPI 暴露 REST 接口，/papers 支持按 y'
'EST 接口，/papers 支持按 year 和 tag 筛选。\n所有写操作都要走事务，避免标签写了一半。\n\n## 部署\n服务用 systemd 管理，日志通'
'署\n服务用 systemd 管理，日志通过 journalctl -u paper-api 查看。\n'
块数: 4

=== 按结构切 ===
'[数据层] 论文数据存放在 SQLite 的 papers 表中，字段包括 title、year、authors。'
'[数据层] 标签是多对多关系，通过 paper_tags 中间表维护。'
'[后端] 后端用 FastAPI 暴露 REST 接口，/papers 支持按 year 和 tag 筛选。'
'[后端] 所有写操作都要走事务，避免标签写了一半。'
'[部署] 服务用 systemd 管理，日志通过 journalctl -u paper-api 查看。'
块数: 5
```

固定长度切法按字符数硬切，代价从输出里看得很清楚：第二块以 `thors。` 开头、第四块以 `署` 开头——**一个词和一个字被从中间截断**，这一块单独拿出来语义是残缺的。这也是为什么需要**重叠窗口（overlap）**：相邻块共享一段文字，让“跨边界的那句话”至少完整地出现在其中一块里。重叠的代价是存储和检索结果里出现重复内容，通常取块长的 $10\%$ 到 $20\%$。

按结构切（Markdown 标题、代码函数边界、HTML 段落）通常更好，因为切点落在作者本来划定的语义边界上，每个块也自带所属章节名。它失效的场合是内容没有结构可依——日志、聊天记录、扫描件 OCR 结果。实践中常见组合是：先按结构切，结构块仍然过长时再在块内用固定长度加重叠细分。

### $\rm \S \, 36.2.5$ 召回率与精确率：检索的两个方向

检索给出 $k$ 个块，质量有两个独立的度量方向：**召回率（recall）** 关心“该找的有没有找到”，**精确率（precision）** 关心“找来的有多少是有用的”。这两个指标会互相拉扯——多给几个块提高召回率，同时拉低精确率。要度量它们，需要一份**标注集**：对每个问题人工标出“答案在哪个 chunk”。

```python
# retrieve_eval.py：用“答案在哪个 chunk”的标注集度量检索质量
CHUNKS = {
    "c1": "论文数据存放在 SQLite 的 papers 表中",
    "c2": "标签是多对多关系，通过 paper_tags 中间表维护",
    "c3": "后端用 FastAPI 暴露 REST 接口",
    "c4": "服务用 systemd 管理，日志通过 journalctl 查看",
    "c5": "部署脚本把镜像推到 registry 后重启服务",
}

EVAL_SET = [                       # 每个问题标出真正含答案的 chunk（gold）
    {"q": "论文存在哪张表？",     "gold": {"c1"}},
    {"q": "标签怎么写进数据库？", "gold": {"c2"}},
    {"q": "怎么查服务日志？",     "gold": {"c4"}},
    {"q": "接口用什么框架写的？", "gold": {"c3"}},
]

def fake_retriever(q, k):
    """教学替身：真实实现是向量检索或 BM25。这里用固定表模拟，故意排错第 4 题。"""
    table = {
        "论文存在哪张表？":     ["c1", "c2", "c3"],
        "标签怎么写进数据库？": ["c2", "c1", "c5"],
        "怎么查服务日志？":     ["c4", "c5", "c3"],
        "接口用什么框架写的？": ["c5", "c3", "c4"],      # 正确答案排在第 2 位
    }
    return table[q][:k]

def evaluate(k):
    hit, prec, rr = 0, 0.0, 0.0
    for item in EVAL_SET:
        got = fake_retriever(item["q"], k)
        hits = [c for c in got if c in item["gold"]]
        hit += 1 if hits else 0
        prec += len(hits) / k
        rr += (1 / (1 + got.index(hits[0])) if hits else 0)     # 首个命中的倒序排名
    n = len(EVAL_SET)
    return hit / n, prec / n, rr / n

print(f"{'k':>2}  {'命中率(recall@k)':>16}  {'精确率(precision@k)':>18}  {'MRR':>6}")
for k in (1, 2, 3):
    h, p, m = evaluate(k)
    print(f"{k:>2}  {h:>16.2f}  {p:>18.2f}  {m:>6.2f}")
```

实测输出（Python 3.12）：

```text
 k     命中率(recall@k)    精确率(precision@k)     MRR
 1              0.75                0.75    0.75
 2              1.00                0.50    0.88
 3              1.00                0.33    0.88
```

$k=1$ 时命中率 $0.75$（第 4 题没命中），$k=2$ 时升到 $1.00$，代价是精确率从 $0.75$ 掉到 $0.50$。这里多出的一个指标 **MRR（Mean Reciprocal Rank，平均倒数排名）** 度量“正确答案排在第几位”——它同时惩罚“没找到”和“找到但排在很后面”，因为排在后面的块更容易被模型的注意力忽略（对照第 33 章 §33.3.6 的中间遗忘）。检索质量评测的完整做法和要求与第 33 章 §33.6.2 的模型评测一致：标注集要覆盖真实问题分布、要包含历史失败案例、要进版本控制。

### $\rm \S \, 36.2.6$ Rerank：为什么先粗排再精排

标注集里第 4 题的现象很典型：正确答案在，但排在第二位。检索的排序决定了模型看到什么顺序，而**粗排和精排适合用不同的方法**。

粗排（召回阶段）面对的是全库上百万个块，必须快——向量相似度或 BM25 这类能在几十毫秒内扫完全库的方法，代价是判断精度有限，它擅长把“大致相关”的几十个候选捞出来。精排（rerank）只面对这几十个候选，可以用慢很多但准很多的方法逐个打分，例如一个交叉编码器（cross-encoder）把“问题 + 候选块”拼在一起送进模型判断相关性。

```python
# rerank.py：先粗排取 20 个候选，再精排取前 3 个
def coarse_retrieve(q, k=20):
    """教学替身：真实实现是向量检索。返回 20 个候选，顺序不完美。"""
    return [f"候选{i}" for i in range(1, k + 1)]

def rerank(q, candidates, top_n=3):
    """教学替身：真实实现是一次模型调用，对每个 (问题, 候选) 对给出相关性分数。"""
    scores = {c: (10 if c == "候选9" else 1) for c in candidates}   # 真正相关的排在第 9
    return sorted(candidates, key=lambda c: -scores[c])[:top_n]

candidates = coarse_retrieve("论文表的主键是什么？")
print("粗排结果（前 5）：", candidates[:5])
print("精排结果（前 3）：", rerank("论文表的主键是什么？", candidates))
```

预期输出与判据：粗排给出的前 5 个候选里不含 `候选9`，而精排后 `候选9` 排到了第一——这就是 rerank 的价值：把粗排埋没在候选列表深处的好结果提到前面。实证方式是关掉 rerank 再跑一遍同一份标注集，比较 MRR；如果指标没有提升，说明你的粗排已经够好，加 rerank 只是多付一次模型调用的钱和延迟。

### $\rm \S \, 36.2.7$ 向量库存的是 embedding，不是你的知识

`chromadb`、`pgvector`、Pinecone 这类**向量数据库（vector database）** 的常见误解是把它当成“知识库”。它存的实际是 embedding——每个块对应一个定长的数字向量加上少量元数据。原文通常还要存在别处（文件、对象存储、数据库），向量库只负责“按语义找相似块”。

三个直接后果：

**换 embedding 模型等于全部重建索引。** 向量空间是特定模型定义出来的——A 模型算出的向量和 B 模型算出的向量在同一个空间里没有可比性，放在一起算距离毫无意义。换嵌入模型、甚至同一模型换版本，旧向量都必须全部重算重新写入。对一个有 10 万块的知识库，这意味着一次完整的重嵌入和重索引；所以嵌入模型的选择要提前想清楚，且迁移脚本要提前准备好。

**元数据过滤（metadata filtering）是检索的一部分，不是事后清理。** 每个块要连同它的来源、部门、密级、更新时间一起存进去，检索时按这些字段先缩小范围。

**权限过滤必须在检索层做。** 常见错误是先按相似度取前 $k$ 个，再从结果里剔除用户无权看的内容。这时名额已经被无权内容占掉了：

```python
# permission_filter.py：先检索后过滤 → 用户什么也拿不到
CHUNKS = [
    {"id": "c1", "text": "论文表 papers 的字段与索引",           "acl": {"public"}},
    {"id": "c2", "text": "论文表结构：内部审计字段仅实验室可见", "acl": {"lab"}},
    {"id": "c3", "text": "论文表结构：草稿字段仅实验室可见",     "acl": {"lab"}},
    {"id": "c4", "text": "论文表结构：实验记录字段仅实验室可见", "acl": {"lab"}},
]

def score(q, text):
    return sum(1 for ch in set(q) if ch in text)

def retrieve_bad(q, acl, k=2):
    top = sorted(CHUNKS, key=lambda d: -score(q, d["text"]))[:k]   # 先取前 k
    return [d for d in top if d["acl"] & acl]                      # 后过滤

def retrieve_good(q, acl, k=2):
    visible = [d for d in CHUNKS if d["acl"] & acl]                # 先过滤
    return sorted(visible, key=lambda d: -score(q, d["text"]))[:k] # 后取前 k

q, viewer = "论文表结构", {"public"}
print("先检索后过滤 →", [d["id"] for d in retrieve_bad(q, viewer)], "（0 条）")
print("先过滤后检索 →", [d["id"] for d in retrieve_good(q, viewer)], "（拿到唯一可见的那条）")
```

实测输出（Python 3.12）：

```text
先检索后过滤 → [] （0 条，用户什么也拿不到）
先过滤后检索 → ['c1'] （拿到了唯一可见的那条）
```

这里演示的是**功能损失**：相似度最高的三条恰好都是私有的，过滤后什么都不剩，用户看到“没有相关资料”。更严重的是**越权泄露**——如果那条私有内容真的被放进上下文，模型会把它当资料复述给无权的人，而这条内容已经进了模型供应商的日志。所以权限条件要和向量检索一起下推（`acl ∩ user_acl ≠ ∅` 作为查询条件），而不是在应用层对结果做减法。

### $\rm \S \, 36.2.8$ 幻觉不能只靠 prompt 消除

在 system prompt 里写“只根据资料回答，不要编造”，能减少编造，但不能消除。原因是机制性的：**模型没有事实校验能力**——它生成的是“在这个上下文里最像合理答案的文本”，判断一句话是否为真需要外部事实来源，而模型自身不具备独立于生成过程的核验通道。当检索没命中时，资料里没有答案，模型面对的是“要么说不知道、要么编一个”的选择，而训练目标倾向于后者。

可用的手段要组合起来，每一层堵一个洞：

- **检索**管住“模型依据什么说话”。资料里没有的信息，至少不再被模型当作已知。
- **引用溯源（citation）**要求模型对每句话标出来自哪个块，并在代码侧校验“引用的块确实被检索进了上下文”。它把“模型说的某句话”变成“可核对到具体原文的某句话”，人工抽检因此变得可行。
- **输出校验**用程序检查事实性约束：数字是否出现在引用的块里、时间是否与资料一致、是否出现了资料之外的人名。能自动发现的问题就不必靠人读。
- **拒答**给模型一条不编造的出路，并在检索分数低于阈值时由代码强制拒答，而不是指望模型自觉。

这些手段的取舍在“降低幻觉”和“提高覆盖率”之间：拒答越多，答错越少，但用户问十次有六次得到“我不知道”也等于不可用。这个取舍可以用一份标注集量化：

```python
# hallu.py：拒答阈值决定“少答”与“答错”的取舍
SAMPLES = [   # (问题, 检索是否命中, 模型在有资料时的行为)
    ("论文表有几列",     True,  "answered_correct"),
    ("谁的引用最高",     True,  "answered_correct"),
    ("上周新增了几篇",   False, "answered_wrong"),   # 检索没命中，模型硬答
    ("部署在哪台机器",   False, "answered_wrong"),
    ("标签表主键是什么", True,  "answered_correct"),
    ("明天会下雨吗",     False, "refused"),
    ("哪个作者最活跃",   False, "refused"),
    ("论文表怎么建索引", True,  "answered_wrong"),   # 检索命中了，答案仍写错
]

def report(refuse_when_no_hit):
    refused = wrong = correct = 0
    for q, has_hit, behavior in SAMPLES:
        if not has_hit and refuse_when_no_hit:
            refused += 1
            continue
        if behavior == "answered_correct":
            correct += 1
        else:
            wrong += 1
    total = len(SAMPLES)
    print(f"  覆盖（回答率）: {(correct + wrong) / total:.0%}   "
          f"答对 {correct} / 答错 {wrong} / 拒答 {refused}")
    print(f"  错误回答占全部回答的比例: {wrong / (correct + wrong):.0%}")

print("策略 A：检索没命中就让模型直接答（覆盖优先）")
report(refuse_when_no_hit=False)
print("策略 B：检索没命中就拒答（准确优先）")
report(refuse_when_no_hit=True)
```

实测输出（Python 3.12）：

```text
策略 A：检索没命中就让模型直接答（覆盖优先）
  覆盖（回答率）: 100%   答对 3 / 答错 5 / 拒答 0
  错误回答占全部回答的比例: 62%
策略 B：检索没命中就拒答（准确优先）
  覆盖（回答率）: 50%   答对 3 / 答错 1 / 拒答 4
  错误回答占全部回答的比例: 25%
```

两份结果放在一起能读出两件事。拒答把覆盖率从 $100\%$ 砍到 $50\%$，换来错误率从 $62\%$ 降到 $25\%$——这是真实的取舍，不存在“既全对又全答”的旋钮。更关键的是策略 B 里**仍有一条错误回答**：它来自“检索命中了、模型仍然写错”那一类，说明检索加拒答并不能覆盖全部幻觉来源，输出校验那一层不能省。阈值取多少取决于业务：医疗、法律场景宁可少答，代码补全场景宁可多答让人自己判断。

> **经验规则**：先度量再调阈值。用标注集把“答对 / 答错 / 拒答”三类数出来，再决定拒答阈值——直接凭感觉把阈值调高，只会得到“看起来更安全”而实际更难用的系统。

## $\rm \S \, 36.3$ Agent 框架一览

这些框架把 §36.2.3 到 §36.2.8 里那些需要自己搭的零件（切分、嵌入、检索、rerank、引用）预先实现好了：

| 框架 | 语言 | 特点 |
|---|---|---|
| **LangChain**（langchain.com） | Python/JS | 最早的 LLM Agent 框架，工具链最全但抽象过多 |
| **LlamaIndex**（llamaindex.ai） | Python | 专注 RAG——数据连接器、索引、查询引擎 |
| **CrewAI**（crewai.com） | Python | 多 Agent 协作——定义不同角色的 Agent 协同完成复杂任务 |
| **AutoGen**（微软） | Python | 多 Agent 对话框架，支持人在回路 |
| **DSPy**（斯坦福） | Python | 编程式优化 prompt 和 pipeline——替代手工调 prompt |
| **Anthropic Tool Use** | API | 原生 function calling——让 Claude 决定何时调用你的函数 |

它们降低的是搭出原型的成本，不改变上面那些机制与取舍——框架替你选了默认的切分长度和 rerank 开关，而检索质量仍然由这些选择决定。

## $\rm \S \, 36.4$ 模型微调与部署

### $\rm \S \, 36.4.1$ 什么时候该微调

**不需要微调的场景**（RAG 就够了）：
- 让模型基于你的私有文档回答事实性问题
- 让模型遵循特定的输出风格（prompt 工程可以搞定）
- 知识类任务（模型本身的能力已经够用）

**需要微调的场景**：
- 你需要模型学会一种新的行为模式（如“用 JSON schema X 输出”且 prompt 工程始终不稳定）
- 领域高度专业化（如医疗影像报告生成、古代汉语翻译）
- 需要极低推理成本（微调一个 7B 模型替代 GPT-4 处理大量简单任务）

### $\rm \S \, 36.4.2$ 微调方法速览

| 方法 | 修改什么 | 成本 |
|---|---|---|
| **全参数微调**（Full Fine-tuning） | 所有参数 | 高（7B 模型用 Adam 混合精度微调通常要 80 GB 级显存——权重、梯度、优化器状态都要驻留显存） |
| **LoRA**（Low-Rank Adaptation） | 附加小矩阵，冻结原权重 | 低（7B 模型可在 < $24 \, \text{GB}$ 显存上微调） |
| **QLoRA** | LoRA + 4-bit 量化 | 极低（7B 模型可在 < $12 \, \text{GB}$ 显存上微调） |
| **指令微调**（Instruction Tuning） | 在“指令-回复”格式数据上训练 | 让模型更擅长遵循指令 |
| **RLHF**（人类反馈强化学习） | 用人类偏好训练奖励模型 + PPO | ChatGPT 的核心——让输出“更符合人类偏好” |

### $\rm \S \, 36.4.3$ 部署方案

| 方案 | 适用场景 | 延迟 | 成本 |
|---|---|---|---|
| **Hugging Face Inference Endpoints** | 快速原型，不想管基础设施 | 低 | 中 |
| **vLLM**（github.com/vllm-project/vllm） | 高吞吐推理，PagedAttention | 极低 | 自托管 |
| **Ollama**（ollama.com） | 本地运行开源模型，一键启动 | 取决于硬件 | 免费（自己出硬件） |
| **Replicate**（replicate.com） | 按调用计费，不需要 GPU 机器 | 中 | 低-中 |
| **Together AI / Fireworks / Groq** | 高速推理 API 提供商 | 极低 | 中 |

对于个人项目，Ollama 一行命令就能在本地跑 Llama/Qwen：

```bash
ollama run llama3.2        # 下载并启动 Llama
ollama run qwen2.5:7b      # 中文支持更好的选择
```

这些命令会把数 GB 的模型权重下载到本地。权重不是 Ollama 提供的：Llama 系列受 Meta 社区许可约束，Qwen 多为 Apache-2.0——用于商用或再分发前先查模型卡上的许可证。

## $\rm \S \, 36.5$ 动手实践

### $\rm \S \, 36.5.1$ 实践一：搭建最简 RAG

起始目录与前置条件：任意空目录（建议专门建一个实验目录），Python 3.9+；只需 `pip install chromadb`——它自带的默认嵌入函数会在首次添加文档时下载一个几十 MB 的小模型，需要网络，但不需要 GPU。

```python
# pip install chromadb
import chromadb

# 1. 创建向量数据库（存储你的文档的"意义向量"）
client = chromadb.Client()
collection = client.create_collection("papers")

# 2. 添加文档
papers = [
    "Attention Is All You Need 提出了 Transformer 架构",
    "BERT 使用双向 Transformer 做预训练",
    "GPT 系列是自回归语言模型",
]
collection.add(
    documents=papers,
    ids=[f"doc_{i}" for i in range(len(papers))]
)

# 3. 查询——不是关键词匹配，是语义匹配
results = collection.query(query_texts=["哪个模型用了 Transformer？"], n_results=2)
print(results["documents"])
# → ["Attention Is All You Need 提出了 Transformer 架构", "BERT 使用双向 Transformer 做预训练"]
```

预期输出与判据：打印出以这两段文档开头的嵌套列表，顺序可能随嵌入模型版本变化——关键是两段结果都与 Transformer 有关，说明这是语义检索而不是关键词匹配（查询词里没有“BERT”，它却被检索出来）。首次运行最慢（要下载嵌入模型），之后明显变快。

结束与清理：`chromadb.Client()` 的数据在内存里，进程退出即释放，不需要清理；想持久化时改用 `PersistentClient(path=...)`（第 37 章 §37.2.2 会复用这套接口）。删除脚本即可结束本实践。

### $\rm \S \, 36.5.2$ 实践二：用 Ollama 跑本地模型

起始目录与前置条件：已安装 Ollama（ollama.com，一个本地服务加命令行客户端）；给 1.5b 模型预留约 1–2 GB 磁盘；有 GPU 会自动加速，CPU 也能跑但更慢。

```bash
ollama run qwen2.5:1.5b     # 最小，适合 CPU
# 在交互界面中测试中文理解和代码生成
```

预期输出与判据：进入 `>>>` 交互提示符，输入“用一句话解释什么是 Transformer”，得到通顺的中文回答即成功（小模型答错细节是正常的）。若提示模型不存在，先 `ollama pull qwen2.5:1.5b`。

结束与清理：输入 `/bye` 退出（Ctrl+D 也可以）；不再需要该模型时用 `ollama rm qwen2.5:1.5b` 释放磁盘，`ollama list` 可以查看已下载的权重。

### $\rm \S \, 36.5.3$ 实践三：观察 Agent 循环

起始目录与前置条件：Claude Code 在论文管理器项目根目录（含 `src/`），工作区干净（`git status` 无未提交改动）。

1. 在 Claude Code 中提一个需要多步骤的任务，如“找出 src/ 下所有包含 TODO 的文件，统计每个文件的 TODO 数量，输出为 Markdown 表格”。
2. 观察 Agent 的每一步：它先 `grep` 搜索 → 看结果 → 决定是否还需要更多信息 → 生成输出。
3. 刻意让第一步失败（如把路径写成不存在的 `srcc/` 再问），观察 Agent 如何修正。

预期输出与判据：最终表格里每个文件的 TODO 数可用 `grep -c TODO <文件>` 复核；第 3 步中它能报告路径不存在并改用搜索或向你确认，而不是硬编造数字。

结束与清理：`git status` 检查它是否写了临时文件，按需删除；不要让 Agent 提交或推送代码。

## $\rm \S \, 36.6$ 总结

- AI for Science 用计算替代昂贵实验。AlphaFold 是最著名的成功案例，但天气预报、材料设计、药物发现都在发生类似的革命。
- Agent = LLM + 工具 + 记忆 + 规划。它能自主完成多步骤任务而不需要每步都让人干预。
- RAG 让 LLM 能访问你的私有知识库——检索相关文档 → 基于文档回答。不需要微调。检索质量由切分策略决定：块里没有的信息检索不出来；重叠窗口让跨边界的内容至少完整出现在一块里。
- 召回率和精确率是两个互相拉扯的方向，要用“答案在哪个 chunk”的标注集度量；先粗排取候选、再精排提准确率，是两者兼顾的常规做法。
- 向量库存的是 embedding 而不是你的知识：换嵌入模型必须重建全部索引；元数据与权限过滤必须在检索层下推，否则要么漏召回要么越权泄露。
- 幻觉不能靠 prompt 消除——模型没有事实校验能力。检索、引用溯源、输出校验、拒答要组合使用，并明确“降低幻觉”与“提高覆盖率”之间的取舍。
- 微调是当 prompt 工程和 RAG 都不够时才考虑的下一步。LoRA/QLoRA 让微调在消费级 GPU 上可行。

## $\rm \S \, 36.9$ 本章自测答案

> 先闭卷作答本章“关键概念回顾”与“应用与辨析”，再核对以下答案。

### $\rm \S \, 36.9.1$ 自测答案 · 关键概念回顾
1. 从氨基酸序列预测蛋白质的三维折叠结构。在此之前需要数月到数年的实验室工作，AlphaFold 用分钟级计算达到同等精度。
2. Chat 是你问一句、AI 答一句的单轮交互。Agent 是 AI 自主规划步骤、选择工具、执行操作、观察结果、修正计划，直到完成目标的循环过程。
3. LLM 无法访问训练数据之外的知识（私有文档、最新信息）。RAG 在回答问题前先从知识库中检索相关文档，给 LLM 提供上下文基础，防止编造。
4. 固定长度硬切会把词和句子从中间截断，使单块语义残缺；重叠窗口让跨边界的那句话至少完整出现在相邻两块中的一块里。代价是存储冗余、检索结果里出现重复内容，通常取块长的 10%–20%。
5. 向量库存的是 embedding（定长向量加少量元数据），原文通常在别处；它只负责按语义找相似块。向量空间由特定嵌入模型定义，不同模型（甚至同模型不同版本）的向量不可比，换模型必须把全部数据重新嵌入并重建索引——10 万块的知识库就是一次完整的重嵌入工程。

### $\rm \S \, 36.9.2$ 自测答案 · 应用与辨析
6. RAG 适合：基于私有文档回答事实问题、知识频繁更新。微调适合：需要学习新行为模式（特定输出格式）、高度专业化领域、需要降低推理成本。如果一个任务用 RAG + prompt 工程就能稳定完成，不要微调。
7. 工具是 Agent 与外部世界交互的接口（搜索网页、运行代码、读写文件）。不把全部信息放进 prompt 的原因是上下文窗口有限、信息过载导致模型遗漏关键细节、部分信息需要实时获取。
8. “先取前 5 条再过滤”把名额浪费在了无权内容上：相似度最高的几条恰好是私有内容时，过滤后剩下的可见内容可能为零或很少，用户看到“没有相关资料”——这是功能损失；如果不过滤而直接把内容交给模型，就成了越权泄露。改法是把权限条件下推到检索层：先按 `acl ∩ user_acl ≠ ∅` 等元数据条件缩小可见集合，再在可见集合内排序取前 $k$ 个。
