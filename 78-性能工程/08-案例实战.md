## $\rm \S \, 8.1$ 任务与基线：每次查询十万个点

最近邻查询是常见的真实负载：推荐系统找相似用户、地图找最近站点、向量数据库找相似嵌入，底层都是它。任务定义：平面上给定点集 $P$，对每个查询点 $q$ 返回 $P$ 中与 $q$ 欧氏距离最近的点的编号。批量场景下同一个点集要应答成千上万次查询，所以「预处理一次、查询反复用」的方案值得考虑，预处理成本可以摊薄。

基线 V0 不做任何预处理，每个查询把十万个点全扫一遍：

```c
static unsigned nn(float x, float y){
    unsigned bi = 0;  float bd = FLT_MAX;
    for (int i = 0; i < N; i++){
        float dx = x - px[i], dy = y - py[i];
        float d = dx*dx + dy*dy;          /* 不开方，比平方就够了 */
        if (d < bd){ bd = d; bi = i; }
    }
    return bi;
}
```

对账单由所有版本共用的批处理骨架打出：跑完整个查询集，把最近点编号累加成整数和、距离平方累加成双精度和，各版本打印的这两个值必须逐字一致：

```c
static void run_batch(void){
    unsigned long long s = 0;  double ds = 0.0;
    for (int j = 0; j < Q; j++){
        unsigned i = nn(qx[j], qy[j]);
        float dx = qx[j] - px[i], dy = qy[j] - py[i];
        s += i;
        ds += (double)dx*dx + (double)dy*dy;   /* 双精度累加，放大差异 */
    }
    g_cksum = s;  g_distsum = ds;
}
```

计时之外的部分保持简单：点坐标与查询坐标都是 $[0,1)^2$ 上的均匀随机数，来自种子 20261107 的 xorshift32 发生器；距离用 float 计算（与真实负载的内存流量一致），对账和用 double 累加以放大版本间的任何分歧。

实测 123948 ns/查询。内层循环每次迭代做 2 次加载、2 次减法、2 次乘法、1 次加法、1 次比较，用 `objdump` 看过生成代码：全是 `movss/subss/comiss` 一类的标量指令，gcc -O2 没有把它向量化（找最小值的下标归约不在 -O2 的廉价向量化模型里），所以 1.24 ns/次评估就是标量流水线的真实单价，折合约 4 拍一次迭代。距离只比平方不开方，省掉的是每次评估一次 `sqrt`；这是数据结构课的老技巧，但它只省常数，救不了 $O(n)$。

白话：V0 像在全校学生名单里挨个问「你离操场最近吗」，问完十万人才能毕业一个查询。查询一多，这条路按人头收费，贵得线性增长。

> 本节小结：基线每查询 123948 ns、十万次距离评估、单价 1.24 ns/评估；口径与对账先行，后面每一轮都跟这两个数比。

## $\rm \S \, 8.2$ 第一轮：换算法，从十万次评估到 23 次

第一轮的瓶颈假设一句话就能说清：每次查询都付 $O(n)$，而空间局部性白送了便宜货没人拿。假设改成：把点集按空间组织成 k-d 树（k-d tree），每个查询只访一小块空间，评估次数从 $n$ 掉到对数量级。

建树规则：每层选一个中位点当节点，按该层指定的轴（第 0 层按 $x$、第 1 层按 $y$，交替）把剩下的点分成两半，小于分点的进左子树、大于的进右子树，递归到每侧只剩一个点。十万个点的树深约 ${\lceil \log_2 100000\rceil = 17}$ 层。查询走标准流程：每到一站先算该站点到自己点距离、顺手更新当前最优，再算查询点在分裂超平面的哪一侧，先走近的那枝，回来时按判据决定要不要走远枝。判据是整个算法的心脏，推导只有一步：设查询点 $q$ 在分裂值 $s$ 左侧，远子树（右侧）里随便哪个点 $p$ 都满足 $x_p \ge s$，于是

$$
\lVert q-p\rVert^2=(x_q-x_p)^2+(y_q-y_p)^2\ \ge\ (s-x_q)^2 .
$$

读法：左边是 $q$ 到远子树内任何一点的真实距离平方，右边是 $q$ 到分裂超平面的距离平方；$p$ 再怎么挑也跨不过这道墙。所以只要右边的墙距不小于当前最优值 $d_{\min}^2$，整枝远子树一个点都不用碰。

V1 的实现用指针版节点：每节点存坐标、原始编号、左右孩子指针，对齐后 32 B，孩子是指针。建树与查询的核心代码如下（轴按深度交替，中位点即节点本身）：

```c
static Node *build_rec(int *idx, int lo, int hi, int depth){
    if (lo >= hi) return NULL;
    qsort(idx + lo, hi - lo, sizeof(int), (depth & 1) ? cmpy : cmpx);
    int mid = (lo + hi) / 2;
    Node *n = &pool[pool_n++];
    n->x = px[idx[mid]];  n->y = py[idx[mid]];  n->idx = idx[mid];
    n->l = build_rec(idx, lo, mid, depth + 1);        /* 左半：坐标 <= 分裂值 */
    n->r = build_rec(idx, mid + 1, hi, depth + 1);    /* 右半：坐标 ≥ 分裂值 */
    return n;
}

static void search(const Node *n, float x, float y, int depth){
    float dx = x - n->x, dy = y - n->y;
    float d = dx*dx + dy*dy;
    if (d < best){ best = d; bi = n->idx; }
    float diff = (depth & 1) ? (y - n->y) : (x - n->x);
    const Node *nearc = diff < 0.0f ? n->l : n->r;    /* 近枝先走 */
    const Node *farc  = diff < 0.0f ? n->r : n->l;
    if (nearc) search(nearc, x, y, depth + 1);
    if (diff*diff < best && farc) search(farc, x, y, depth + 1);
}
```

实测 222.19 ns/查询，对 V0 加速 558 倍；建树 0.092 s。计数诊断给出关键证据：每个查询平均只访问 23 个节点、做 23 次距离评估。评估次数之比是 ${100000/23 \approx 4348}$ 倍，但端到端只有 558 倍，缺口的账这么平：

$$
\frac{T_{\text{V0}}}{T_{\text{V1}}}
=\frac{100000}{23}\times\frac{1.24\ \text{ns}}{9.66\ \text{ns}}
\approx 4348\times 0.128\approx 558 .
$$

读法：加速比等于「评估次数之比」乘以「单次成本之比」。V0 的一次评估 1.24 ns，V1 的一次节点访问 9.66 ns，贵了 7.8 倍。为什么树的访问这么贵？因为它是依赖链：下一个访问哪个孩子，取决于上一次比较的结果（§3.2），处理器既不能提前取孩子节点，也不能把 23 站摊到多个端口上；每一站还各带一次方向分支。

顺带把摊销算清：建树 0.092 s，V0 每查询 123.9 µs，两相相除约 742。也就是说查询量超过约 742 个，k-d 树开始净赚；本章 5000 个查询远远过了回本点。

白话：k-d 树像把全校学生按宿舍楼、楼层逐级分组，找最近的人先去本人所在楼层，找不到合适的再考虑隔壁，十万人里问二十几个人就够了；但每问一站都要「先想想该去哪」，这一想，比名单上直接念一个名字贵好几倍。

> 本节小结：换算法立竿见影，评估次数从 100000 掉到 23，端到端 558 倍；大头进账后，单次 9.66 ns 的节点访问成了新的瓶颈。

## $\rm \S \, 8.3$ 第二轮：布局紧凑化，第一个被证伪的假设

看着 9.66 ns/访问，下一个假设顺理成章：V1 的节点 32 字节（两个坐标加编号加两个指针，对齐后 32 B），孩子指针指得到处都是；如果换成 16 字节的紧凑节点、指针换成数组下标、整棵树装进一个连续数组，每次访问触碰的缓存行减半，节点访问应该明显变快。这一轮只改数据表示，算法一行不动（原编号挪进一个旁落数组，只在更新最优时读一次）。

复测结果：245.21 ns/查询，比 V1 慢 10.4%。六遍全部更慢，慢幅 4.2%～16.1%。假设被证伪，而且不是噪声。

为什么字节减半反而更慢？先摆能确认的事实：每个查询只有 23 次访问、10.0 次最优更新；预热之后整棵树常驻缓存（V1 的节点池 3.2 MB、V2 的 1.6 MB，都远小于 24 MB 的 L3），所以「省一半缓存行」省的是本来就几乎免费的东西。至于那 10.4% 的倒扣，有两个候选机制：旁落数组让每次最优更新多碰一条别的缓存行；以及递归建树天然按先序摆放，父节点和左孩子在内存里本来就挨着，32 B 与 16 B 在这条访问路径上没有实质差别。两个机制哪个占多少，现有仪器拆不开：本机 WSL 内核没带 perf（§7.4 记录过），缓存事件计数做不了。照实记录：证伪给了「此路不通」的结论，未必附赠「为什么不通」。

处置：回退到 V1 的表示。这个结果与 §4.4 的口径互相印证：AoS、SoA、紧凑化这类布局手段只在访存真是瓶颈时才收钱，这里瓶颈是依赖链，不是字节。

白话：把名单从大字报抄成小字报，省的是纸，不是问话的次数；学生本来就在同一间教室里，字再小也快不了。

> 本节小结：32 B 压到 16 B，六遍全慢 4.2%～16.1%，假设证伪回退；缓存全热时，布局优化没有瓶颈可省。

## $\rm \S \, 8.4$ 第三轮：桶叶，把贵的访问换成便宜的扫描

第二轮的教训指明了方向：省字节没用，要省的是「昂贵的节点访问」本身。新的瓶颈假设：每次节点访问 9.66 ns 里，大头是取孩子、算方向、分支这一套固定开销；如果把树变矮、让每个叶节点管一段连续的点，就能用几次廉价的连续评估顶掉一次昂贵的访问。

改动（V3）：叶节点不再是单点，而是一段最多 32 个点的连续区间；建树递归到区间长度不大于 32 就停，并把点物理重排，让每棵子树的点在数组里真正连成一片。重排这一步不可省：区间连续指的是内存连续，排序必须在点的存储本体上做，查询时的顺序扫描才成立。树从十万个节点缩到 8191 个（4096 个叶），深度从 17 层降到约 12 层，内部节点 20 B。叶扫描的代码就是一段朴素的循环：

```c
if (n->l < 0){                        /* 叶：顺序扫 [lo, hi) 一整片 */
    for (int i = n->lo; i < n->hi; i++){
        float dx = x - ppx[i], dy = y - ppy[i];
        float d = dx*dx + dy*dy;
        if (d < best){ best = d; bi = pid[i]; }   /* pid 映射回原始编号 */
    }
    return;
}
```

查询逻辑不变：碰到叶就在区间上顺序扫一遍。

实测 197.88 ns/查询，对 V2 加速 1.24 倍，累计 626 倍；建树反而降到 0.078 s（排序层数变少）。计数诊断：每查询访问 14 个节点、36 次距离评估。账能拼上：沿用 V1 实测的节点单价 9.66 ns，则连续评估的单价是 ${(197.88-14\times 9.66)/36\approx 1.74\ \text{ns}}$，与 V0 的 1.24 ns 同量级，只贵了叶内那次范围判断。9 次昂贵的节点访问换成 13 次便宜的连续评估，净赚约四分之一。

白话：原来二十几个中层干部逐个请示，现在改成三个片区各配一份花名册，请示次数少了，翻名册本身几乎不花钱。

> 本节小结：桶叶用 8191 个节点顶替十万个，每查询 14 次访问加 36 次连续评估，197.88 ns，累计 626 倍；贵的东西换便宜的，才是缓存层面的正路。

## $\rm \S \, 8.5$ 第四、五轮：两个微优化，一死一生

第四轮假设：递归查询的调用开销（保护现场、跳转、返回）在 197.88 ns 里应该占一块，换成显式栈的迭代版能再省一截。改动只有一件事：递归改栈，访问顺序一字不动，远枝带平面距离进栈、出栈时复检剪枝。复测 221.82 ns，比 V3 慢 12.1%，六遍全部更慢，慢幅 6.3%～13.0%。证伪得干脆：树深只有十几层，`call/ret` 这类分支预测器闭着眼都能猜对（§3.1），递归几乎不花钱；栈版反而每次访问多一组进出栈的读写。回退。

第五轮假设：9.66 ns 的访问单价接近 L2 与 L3 的延迟量级（§2.4），剩下的是访存延迟，软件预取（software prefetch）能盖住一块。改动：进入内部节点时预取两个孩子节点，进叶时预取点区间第一行。复测 195.14 ns，六遍里五遍更快（快 0.9%～5.8%）、一遍更慢 2.0%。这次活了下来，但只算边界收益：幅度与轮间漂移同量级，与 §4.3 那次干脆的证伪对照着看正好是一对案例，流式扫描里预取全无必要，依赖链遍历里预取只能盖住远枝那一小段，因为近枝的地址马上就要用，预取来不及，远枝则要等整棵近子树走完才轮到，预取的礼物在路上就被挤掉了一半。保留 V5，正文明确标注收益量级。

白话：把逐级请示改成写字条传阅是画蛇添足，因为请示本身根本不慢；提前把隔壁片区的花名册抱过来倒有点用，只是省下的那几步路，走十趟才省出一趟。

> 本节小结：显式栈六遍全慢 6.3%～13.0%，证伪回退；预取六遍五遍快 0.9%～5.8%，保留但标注为边界收益。

## $\rm \S \, 8.6$ 总账：一张表、一次翻车、一个结构

五轮循环走完，全表如下（ns/查询，取自 `result.txt` 第 1 遍；比值只在同一次运行内比较）：

| 版本 | 单一改动 | ns/查询 | 对上一版 | 累计加速 |
| --- | --- | --- | --- | --- |
| V0 | 无（暴力扫描） | 123948.2 | — | 1× |
| V1 | 建 k-d 树 | 222.19 | 558× | 558× |
| V2 | 节点 32B→16B 连续数组 | 245.21 | 0.90× | 证伪，回退 |
| V3 | 桶叶（32 点连续区间） | 197.88 | 1.24× | 626× |
| V4 | 递归改显式栈 | 221.82 | 0.89× | 证伪，回退 |
| V5 | 软件预取 | 195.14 | 1.01× | 635× |

三个数字值得单独念一遍。其一，558 倍贡献了 635 倍里的约 88%：整个战役最大的单笔进账来自换算法，后面四轮合起来只再乘了 1.14，这正是 §1.6 的 Amdahl 逻辑在微观上的样子，最大的瓶颈先吃，剩下的每一口都小。其二，五轮里两轮证伪、一轮边界，弯路不是学费而是产出：每个被证伪的假设都把「还剩什么慢」的候选名单划掉一行，第五轮的假设之所以值得试，恰恰因为前四轮把别的嫌疑人排除了。其三，绝对值跨遍漂移（V0 六遍从 123285 到 134261 ns，幅度约 9%），但结论的方向在六遍里纹丝不动：V2 对 V1 六遍全慢（4.2%～16.1%），V4 对 V3 六遍全慢（6.3%～13.0%），V5 对 V3 五快一慢。同一遍内的比值可信、跨遍的绝对值只配看量级，§4.1 立的规矩在真实战役里第三次兑现。

最后照实记一次翻车。V3 首版把节点数组开成 ${N/16+16\approx 6266}$ 个，而叶节点最少装 16 个点，节点总数最坏可到约 12500 个：数组越界，越界的写把点数据踩坏。抓住它的不是计时，是对账单：距离平方之和打印成 `NaN`，编号之和对不上。按 §7.5 的顺序，这批数字在修好之前根本没有资格进任何表格。修正上界为 $N/8+64$ 后六版对账逐字一致，本章所有数字都出自修正后的构建。先测对再测快，这一章自己是第一个受益者。

白话：这场仗的账本翻到底，第一页写着「换个问法」，后面四页写的是「这条路不通」「那条也省省吧」「这里还能抠一点」；赢大头的从来不是某次聪明的小改动，而是第一步就不按人头收费。

> 本节小结：635 倍的 88% 来自第一轮换算法；两轮证伪划掉了候选瓶颈；一次越界被对账单当场抓获，数据先于速度。

## $\rm \S \, 8.7$ 全册收束：循环本身就是方法

回望七章，每章都在这条循环上走过至少一圈：

1. §1 定口径：测什么、怎么测、五个坑怎么躲，没有口径的快慢是空话。
2. §2 机器视图：汇编、调用约定、内存层级，给「慢」找到物理上的记账单位。
3. §3 微观优化：分支、展开、SIMD、寄存器，在依赖链上抠拍数。
4. §4 缓存友好：循环序、分块、布局、伪共享，让每次访存都物有所值；也留下了本章同款的证伪案例。
5. §5、§6 并行：加速比的两堵墙（串行份额与带宽）和消息传递的记账法。
6. §7 仪器：剖析器告诉你慢在哪，sanitizer 告诉你对不对。

本章把七件兵器连成纪律，并且展示了这条纪律最重要的一条性质：它对失败免疫。假设被证伪时，损失只是一次改动的工时，而收获是一条被证据钉死的排他结论；假设被证实时，进账直接落到表格里。跑完五轮，你手里不只是 635 倍的程序，还有一张「每一纳秒花在哪、哪条路不通」的地图。下一章（本册复习总结）不引入新知识，专门帮你把这张地图收进长期记忆。

白话：七章学的是兵器谱，本章练的是打法；打法只有一条，先量、再猜、只改一处、重测、记账，猜错了认，猜对了赚，两头都不亏。

> 本节小结：全册一个模型，假设-验证循环；它允许失败、消化失败、并把失败变成下一轮假设的依据。

## $\rm \S \, 8.10$ 本章自测答案

概念回顾答案：

1. 端到端加速比 $=$ 评估次数之比 $\times$ 单次成本之比。实测：次数比 ${100000/23\approx 4348}$，单价比 ${1.24/9.66\approx 0.128}$，乘积约 558，与直接相除的 558 吻合。次数比来自换算法（k-d 树），单价比的倒扣来自依赖链化的访问模式。（§8.2）
2. 远子树的任何点 $p$ 与查询点 $q$ 被分裂超平面隔开，$q$ 在近侧，故 $\lVert q-p\rVert^2\ge(s-x_q)^2$（墙距的平方）。若 $(s-x_q)^2\ge d_{\min}^2$，则远子树里不存在能打败当前最优的点，整枝跳过。推导只用到「远子树全部点在墙的另一侧」这一条建树保证。（§8.2）
3. 没省到：访问全在缓存命中后进行（两版树都远小于 24 MB L3），省字节省的是免费的东西；先序建树让父子本就相邻，16 B 节点没有减少实际触碰的行数。反而多付出：10.0 次/查询的最优更新要碰旁落编号数组的缓存行。结果六遍全慢 4.2%～16.1%。两个候选机制的主次，本机没有 perf 拆不开，照实存档。（§8.3）
4. 桶叶把「每点一个节点」换成「每 32 点一片连续区间」，每查询从 23 次昂贵访问变成 14 次访问加 36 次廉价连续评估。核算：${14\times 9.66+36\times 1.74\approx 197.9\ \text{ns}}$，其中 9.66 ns 是 V1 实测的节点单价，1.74 ns 是由 V3 实测总值反推的连续评估单价，与 V0 的 1.24 ns 同量级。（§8.4）
5. 递归深度只有十几层，`call/ret` 被分支预测器完美处理，几乎零开销；栈版每次节点访问额外多一组进出栈的读写，还要出栈时复检剪枝。六遍全慢 6.3%～13.0%。「调用开销占大头」这个假设对深递归或大栈帧才成立，这里两者都不占。（§8.5）

应用与辨析答案：

1. 交 V0。回本点约 742 个查询（建树 0.092 s 除以 V0 单次 123.9 µs）；10 个查询连零头都不够，预处理纯亏。判断的普适式：预处理成本除以（旧方案单次成本减新方案单次成本）。（§8.2）
2. 大概率明显变大。二维的 23 次访问依赖「墙能有效挡住远枝」这一几何事实；维度升高时，查询点到各分裂超平面的墙距普遍变小、能剪的枝变少（维数灾难的直观表现），访问节点数向 $n$ 逼近。其中「墙距变小、剪枝变弱」是几何事实，但本章未做三维实测，具体数字属经验外推，引用时应注明。正确做法是先跑基线再下结论，本章的流程原样适用。（§8.2、§8.3）
3. 四样证据：环境（机器、内核、绑核、编译选项），排除「硬件不同」；口径（计时协议、多轮取 min、查询集与点集是否同分布同规模），排除「拿好测的输入自肥」；比值是否在同一次运行内取得，排除「跨运行漂移凑出来的倍数」；对账与正确性验证（剪枝写错常常是漏解而不是报错），排除「用错误的答案换速度」。（§1.2、§1.5、§7.5）
