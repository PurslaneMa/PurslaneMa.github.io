## $\rm \S \, 4.1$ 声明式：一句 SQL，无数种算法

本章的贯穿查询就一句：数一数 a 表每行的 bcode 在 b 表里能不能找到——

```sql
SELECT count(*) FROM a JOIN b ON a.bcode = b.code;
```

命令式的写法你闭眼能写：外层循环 a 的每一行，内层循环 b 找 code 相等者，命中就计数。循环怎么嵌、先扫谁、要不要先排序或建哈希表——都得你定，选错就是 §4.5 实测的 $46.2\,\text{s}$ 对 $6.3\,\text{ms}$。SQL 把这些全丢给了数据库：它只描述结果集「是什么」，不描述「怎么算出来」，这门语言叫声明式（declarative）。cs 册 §26.2 用这个词形容过 SQL，本章补上它成立的机制：数据库内部先把这句话翻译成一个代数表达式，再对这个表达式自由改写、挑最便宜的执行方案——说「要什么」与算「怎么算」能解耦，靠的是中间那层关系代数。

## $\rm \S \, 4.2$ 五算子最小集：关系的代数

白话：关系代数就是给「挑行、挑列、拼表」这些操作各发一个数学符号——符号之间有交换律、结合律这类定律，数据库才能像化简算式一样改写你的查询。

**关系代数（relational algebra）**把表看成集合：行无重复、无顺序；算子吃进关系、吐出关系，于是可以任意组合。最小集是五个算子，另有一个纯记号便利的改名。设 P 有三行 `('db',2019)`、`('db',2020)`、`('ml',2020)`（列 tag、year），Q 有一行 `('db',2019)`，逐个走一遍：

| 算子 | 记号与读法 | 在 P（或 Q）上的结果 |
| --- | --- | --- |
| 选择（selection） | $\sigma_{\text{tag}=\text{db}}(P)$：按条件挑行 | 留下前两行，`('ml',2020)` 出局 |
| 投影（projection） | $\pi_{\text{year}}(P)$：挑列并按集合去重 | $2019$、$2020$ 两行 |
| 并（union） | $P \cup Q$：行集合相加 | 仍是 P 的三行，重复行只留一份 |
| 差（difference） | $P - Q$：在 P 不在 Q | 后两行 |
| 笛卡尔积（Cartesian product） | $P \times Q$：两两全配对 | $3 \times 1 = 3$ 行，每行贴上 Q 的行 |
| 改名（rename） | $\rho_{S}(P)$：整个关系换名 | 内容不变，以便同一表在表达式里出场两次 |

五个集合算子里你早已熟悉四个，唯一的异类是 $\times$：它把两边所有行两两配对，行数是 $|P| \times |Q|$。一个陈述级事实：σ、π、∪、−、× 这五个足以表达 SQL 的全部查询能力。所以优化器面对的不是任意程序，而是一个每步都可交换、可结合、可下推的代数表达式——这就是 §4.1 说的「改写自由」的来源。

## $\rm \S \, 4.3$ 连接：笛卡尔积加一次选择

跨表查询要的不是全配对，而是「匹配上的行」。给这个最常见的组合起个名字——**连接（join）**，记作 $\bowtie$，定义为一层语法糖：

$$
R \bowtie_{\theta} S \;=\; \sigma_{\theta}(R \times S)
$$

先做积，再用条件 $\theta$（连接条件，通常是两边键相等）把不匹配的行全部扔掉。最小例：R 有 `('u1','c9')` 与 `('u2','c3')` 两行，S 有 `('c9','甲')`、`('c9','乙')`、`('c7','丙')` 三行；$R \times S$ 共 $6$ 行，按「R 第二列等于 S 第一列」选择后剩 2 行——u1 连到甲与乙，u2 一无所获（内连接语义，即 cs 册 §26.3.3 的 INNER JOIN；LEFT JOIN 是在此之上再补回左表落空的行）。

定义里藏着本章剩余全部内容的动机：$|R| \times |S|$ 的积瞬间膨胀，而 $\theta$ 又几乎总把绝大部分行扔掉。三种连接算法（§4.4）的全部差别，就是「不真把积造出来」的三种办法。

## $\rm \S \, 4.4$ 三种算法：不把积造出来

设外表 $M$ 行、内表 $N$ 行，b 表摊在约 $10^3$ 个页上（§2.1 的记账单位回来了）：

1. **嵌套循环连接（nested loop join）**：外表每取一行，内表找一遍匹配。无索引时内表被完整重扫 $M$ 遍，行访问 $M \times N$——外表 $10^4$ 行配内表 $10^5$ 行就是 $10^9$ 次，§4.5 实测 $46.2\,\text{s}$；按页推进、内表整页缓存能把页访问从 $M$ 乘 $10^3$ 压到 $B_M \times 10^3$，但 $M \times N$ 次比较一次也省不掉。内表连接列上有索引时，每次探测从全扫降为一次树探（§2.4 的个位数页），总量降到 $M$ 次探针；
2. **排序归并连接（sort-merge join）**：两边先按连接键排序（$O(M \log M + N \log N)$），再两头同步推进、线性归并——键序对齐后各走一遍。适合连接列本来就有序（索引扫出来的就是序）、或结果反正要按键排序的场合；
3. **哈希连接（hash join）**：先把一侧按连接键建成哈希表（竞赛生秒懂：`unordered_map`），再扫另一侧逐行探测，$O(M + N)$，等值连接专用；代价是建表那侧要装得进内存，装不下就分块重扫。

三者适用条件互斥得干净：通用但怕无索引的是嵌套循环，要序的是归并，要内存的是哈希。SQLite 不实现哈希连接，它的替代品你马上会见到：查询时自动造一棵临时索引顶上（§4.5 的第三份计划）。

**本节小结**：三种算法都在绕开「先造出 $|R| \times |S|$ 的积再扔」——嵌套循环靠索引把内表全扫换成探针，归并靠键序一次对齐，哈希靠等值直接寻址；选哪个取决于索引、序与内存哪个现成。

## $\rm \S \, 4.5$ 实验：SEARCH 与 SCAN 之间差 7000 倍

在空目录运行（数据：a 表 $10^4$ 行、b 表 $10^5$ 行，随机种子 20261025）：

```python
import sqlite3, time, random; random.seed(20261025)
keys = random.sample(range(10**9), 100_000)
b = [(i, f"c{keys[i]:09d}") for i in range(100_000)]
a = [(i, b[random.randrange(100_000)][1], round(random.uniform(0, 100), 2)) for i in range(10_000)]
con = sqlite3.connect("join.db")
con.execute("CREATE TABLE b(id INTEGER PRIMARY KEY, code TEXT)")
con.execute("CREATE TABLE a(id INTEGER PRIMARY KEY, bcode TEXT, val REAL)")
con.executemany("INSERT INTO b VALUES(?,?)", b); con.executemany("INSERT INTO a VALUES(?,?,?)", a)
con.commit(); Q = "SELECT count(*) FROM a JOIN b ON a.bcode = b.code"
con.execute("PRAGMA automatic_index=OFF")
print("计划:", [r[3] for r in con.execute("EXPLAIN QUERY PLAN " + Q)])
t0 = time.perf_counter(); print(f"无索引: {con.execute(Q).fetchone()[0]} 行, {time.perf_counter()-t0:.1f}s")
```

```text
计划: ['SCAN a', 'SCAN b']
无索引: 10000 行, 46.2s
```

接着同一会话跑三步对照——建真索引、删掉后让 SQLite 默认配置自选：

```python
t0 = time.perf_counter(); con.execute("CREATE INDEX i_code ON b(code)")
print(f"建索引耗时: {time.perf_counter()-t0:.2f}s")
print("有索引计划:", [r[3] for r in con.execute("EXPLAIN QUERY PLAN " + Q)])
t0 = time.perf_counter(); print(f"有索引: {con.execute(Q).fetchone()[0]} 行, {(time.perf_counter()-t0)*1000:.1f} ms")
con.execute("DROP INDEX i_code"); con.execute("PRAGMA automatic_index=ON")
print("默认配置计划:", [r[3] for r in con.execute("EXPLAIN QUERY PLAN " + Q)])
t0 = time.perf_counter(); print(f"自动临时索引: {con.execute(Q).fetchone()[0]} 行, {(time.perf_counter()-t0)*1000:.1f} ms")
```

```text
建索引耗时: 0.10s
有索引计划: ['SCAN a', 'SEARCH b USING COVERING INDEX i_code (code=?)']
有索引: 10000 行, 6.3 ms
默认配置计划: ['SCAN a', 'SEARCH b USING AUTOMATIC COVERING INDEX (code=?)']
自动临时索引: 10000 行, 127.6 ms
```

读数四条（绝对数字随机器浮动，倍数关系稳定）：

1. 裸计划 SCAN a 配 SCAN b：外表每行重启内表 $10^5$ 行全扫，$10^9$ 次行访问对上 §4.4 的账，$46.2\,\text{s}$；
2. 给 `b(code)` 建一棵索引只花 $0.10\,\text{s}$，内表每行从全扫降为一次 SEARCH，$46.2\,\text{s} \to 6.3\,\text{ms}$，约 $7000$ 倍——比 §3.6 单表过滤的 $13$ 倍再涨约 $560$ 倍，因为省下的不是一遍扫描，而是「每行一遍全扫」。计划里 `COVERING` 字样是因为 `count(*)` 只要键列本身，§3.4 的判据原样适用；
3. 连索引都懒得建时，默认配置的 SQLite 看出 b(code) 该有索引，查询时自己造一棵临时索引（计划里 `AUTOMATIC` 字样），$127.6\,\text{ms}$——比真索引慢约 $20$ 倍（每次查询重造一遍），比裸扫快约 $360$ 倍。§4.4 说的「哈希连接的替代品」就是它；
4. 这三份计划就是 §4.1 的承诺在兑现：同一句 SQL，三种执行方案，数据库自己挑。挑错的代价不是百分之几十，是四个数量级。

手写对拍验证算法本身的差距（同一会话，取 a 的前 $1000$ 行、b 的前 $10^4$ 行）：

```python
a_s, b_s = a[:1000], b[:10_000]
t0 = time.perf_counter()
n_nl = sum(1 for x in a_s for y in b_s if x[1] == y[1])
print(f"嵌套循环: {n_nl} 对, {time.perf_counter()-t0:.2f}s")
t0 = time.perf_counter()
A = sorted(a_s, key=lambda r: r[1]); B = sorted(b_s, key=lambda r: r[1])
i = j = n_sm = 0
while i < len(A) and j < len(B):
    if A[i][1] == B[j][1]: n_sm += 1; i += 1
    elif A[i][1] < B[j][1]: i += 1
    else: j += 1
print(f"排序归并: {n_sm} 对, {(time.perf_counter()-t0)*1000:.0f} ms")
```

```text
嵌套循环: 92 对, 0.41s
排序归并: 92 对, 9 ms
```

读数两条：

1. 手写嵌套循环 $10^7$ 次比较用 $0.41\,\text{s}$，速率约 $2.4\times10^7$ 次每秒；按它推算 $10^4 \times 10^5$ 的 $10^9$ 次要约 $41\,\text{s}$——与 SQLite 裸嵌套循环的 $46.2\,\text{s}$ 同量级（它多一层通用执行器的开销）。两种实现殊途同归：$O(MN)$ 在千万行级就开始不可用；
2. 排序归并 $9\,\text{ms}$，约 $46$ 倍——排序的 $O(n \log n)$ 一次付清，归并线性，两边越大差距越宽。两种手写算法都对出 $92$ 对，正确性顺手互证。

## $\rm \S \, 4.6$ 连接顺序：优化器存在的原因

两张表的连接只有一种分法，三张表有先连谁再连谁的讲究，$n$ 张表共 ${n!}$ 种顺序（`math.factorial` 实算）：

| 表数 $n$ | 2 | 3 | 4 | 5 | 8 | 10 |
| --- | --- | --- | --- | --- | --- | --- |
| 连接顺序数 ${n!}$ | 2 | 6 | 24 | 120 | 40320 | 3628800 |

一张 10 表的报表查询有 360 万种连接顺序，而顺序之间的代价差就是 §4.5 那 $7000$ 倍的量级——全枚举不可行，每种都试更不可行。数据库的答案是把「选顺序」本身也当成优化对象：用动态规划自底向上合并、用代价估算剪枝，把指数压成可控的搜索（System R 的思路，陈述级），代价是可能错过全局最优。每一步的代价分数从哪来——树高、页数、选择率怎么进公式——是第 5 章的全部内容。

## $\rm \S \, 4.9$ 本章自测答案

> 先闭卷作答 §4.7 与 §4.8，再核对。

### $\rm \S \, 4.9.1$ 关键概念回顾答案

1. 数据库把 SQL 翻译成关系代数表达式，再利用算子的交换、结合、下推性质自由改写并挑选执行方案。关系代数是「要什么」与「怎么算」之间那层可推导的中间语言。（§4.1、§4.2）
2. $R \bowtie_{\theta} S = \sigma_{\theta}(R \times S)$。积是 $|R| \times |S|$ 的瞬间膨胀而 $\theta$ 几乎全扔，算法的意义就是不做无用配对：嵌套循环靠索引把内表全扫换成探针，归并靠序一次对齐，哈希靠等值直接寻址。（§4.3、§4.4）
3. 嵌套循环：外表每行探内表，无索引 $M \times N$ 次行访问、有索引降为 $M$ 次探针，通用；排序归并：两边排序后线性归并，$O(M \log M + N \log N)$，要序；哈希：小表建表大表探测，$O(M+N)$，等值专用且要内存。SQLite 用查询时自动建的临时索引承担哈希的角色。（§4.4）
4. 三份计划同源于一句 SQL：SCAN a 配 SCAN b 的裸嵌套循环（$10^9$ 次行访问）；AUTOMATIC 临时索引（每次查询重造，付一次建索引钱）；持久索引加 SEARCH（建一次用无数次）。（§4.5）
5. $n$ 张表 ${n!}$ 种顺序，10 表即 $3628800$ 种，顺序间代价差可达数量级。优化器用动态规划加代价估算剪枝，把指数搜索压成多项式，可能错过全局最优。（§4.6）

### $\rm \S \, 4.9.2$ 应用与辨析答案

1. 内表那一侧。嵌套循环的代价是「外表每行探一次内表」：内表连接列有索引，$M$ 次全扫变 $M$ 次探针，收益是数量级的（§4.5 的 $7000$ 倍）；外表一侧的索引只影响扫描外表的启动顺序，外表本来就要整表过一遍，收益是常数的。（§4.4、§4.5）
2. 先排除哈希连接：它要求建表侧整个装进内存，装不下要么分块重扫要么退回归并。排序归并可用，前提是愿意付两边排序的代价（$O(n \log n)$，或连接列上已有索引提供现成的序）；嵌套循环加内表索引也可行，但 $8000$ 万行的外表乘树探，代价取决于外表行数与缓存命中。（§4.4）
3. 它扛住的：连接算法选择（§4.5 里自动临时索引救了无索引的连接）、连接顺序在表数不大时的搜索（§4.6）。它扛不住的：连接列上有没有持久索引——临时索引每次重造，比真索引慢约 $20$ 倍；以及表数变大后搜索空间本身失控。设计者给的原料（索引、键序）仍是数量级差距的来源。（§4.5、§4.6）
