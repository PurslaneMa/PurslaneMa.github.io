# $\rm Chapter \, 8$ 设备与精度：GPU 与混合精度

前七章的世界只有一个设备（CPU）和一种精度（float64）。真实训练把这两个假设同时打破：矩阵乘法搬到 GPU 上，数值从 float64 压到 float32 甚至 float16。本章前半回答「这件事在 PyTorch 里怎么写」：怎么选设备、张量往哪搬、混合精度两件套（autocast 与 GradScaler）各写哪一行、dtype 怎么选；后半打开盖子，把设备抽象的内部约定与精度数字的账算清。两者连起来，你既能写出可迁移到 GPU 的训练脚本，也能判断「跑不对是代码错了还是精度不够」。

## $\rm \S \, 8.1$ 选设备与搬张量：一份代码两台机器

要解决的问题：同一份训练代码要在 CPU 与 GPU 上都能跑，不能写死设备名。习惯写法是先问一句有没有卡：

```python
import torch
device = 'cuda' if torch.cuda.is_available() else 'cpu'   # 有卡用卡，无卡退回 CPU
print(torch.cuda.is_available(), device)
```

本机（无 GPU）真跑得：

```text
False cpu
```

往后所有张量都得跟 `device` 走，`.to(device)` 作用在**三处**：模型（`model.to(device)`，搬一次，参数与缓冲一起搬，等价于 `model.cuda()`）、每个 batch 的数据（`xb, yb = xb.to(device), yb.to(device)`，写在循环里）、损失函数里的权重张量（`nn.CrossEntropyLoss(weight=w).to(device)`，`weight` 也是张量，忘了搬同样报错）。

| 写法 | 说明 |
| --- | --- |
| `device = 'cuda' if torch.cuda.is_available() else 'cpu'` | 一份代码自适应有无 GPU |
| `model.to(device)` | 搬模型参数，只做一次 |
| `xb.to(device)` | 搬一个 batch 的数据，每步都做 |
| `torch.cuda.memory_allocated()` | 当前进程已占用的显存字节数，打印它看显存涨 |
| `with torch.no_grad():` | 评估段不建图，省显存也更快（§6.2） |

显存不够时按顺序试三招：其一，调小 batch，显存大头是反向要留的激活，随 batch 近似线性涨；其二，评估段加 `with torch.no_grad():`，中间量算完即丢、不建图；其三，分块，把长序列或大图切成小块依次前向，推理尤其常用。`memory_allocated()` 只是已占用量，要读硬件上限用 `torch.cuda.get_device_properties(0).total_memory`。

## $\rm \S \, 8.2$ 混合精度两件套：autocast 与 GradScaler

要解决的问题：省显存、提速度，又不把梯度算坏。混合精度（mixed precision）的做法是前向反向用 16 位跑、参数主拷贝与更新保持 float32。PyTorch 把它拆成两个开关，标准片段如下：

```python
scaler = torch.amp.GradScaler(device)            # 只对有卡的情况有意义
for xb, yb in loader:
    xb, yb = xb.to(device), yb.to(device)
    opt.zero_grad()
    with torch.autocast(device_type='cuda', dtype=torch.bfloat16):
        loss = criterion(model(xb), yb)          # 框内的算子自动降到 bf16
    scaler.scale(loss).backward()                # ① 先把 loss 放大再反向
    scaler.step(opt)                             # ② 更新前在内部除回缩放
    scaler.update()                              # ③ 按本步是否溢出调缩放因子
```

两个开关各管一段：

1. `torch.autocast` 管「哪些算子用 16 位跑」：框内的矩阵乘、卷积等走 bf16，归约、归一化、损失等保 float32，选哪些由框架查表决定，不必逐层指定。
2. `GradScaler` 管「16 位算出的梯度怎么活着送到更新」，即 §8.5 的 loss scaling：`scale` 把 loss 乘上缩放因子 ${S}$，梯度跟着放大 ${S}$ 倍躲过下溢；`step` 在 float32 里除回 ${S}$ 再更新；`update` 发现这一步出现 inf 或 nan 就跳过、调小 ${S}$。

| 写法 | 说明 |
| --- | --- |
| `torch.autocast(device_type='cuda', dtype=torch.bfloat16)` | 框内算子自动选 16 位 |
| `GradScaler(device)` | 创建缩放器，记录当前缩放因子 |
| `scaler.scale(loss).backward()` | 放大 loss 再反向，梯度不下溢 |
| `scaler.step(opt)` / `scaler.update()` | 除回缩放后更新，再调整因子 |

用 bfloat16 时不需要 `GradScaler`：它的动态范围与 float32 相同，不会下溢（§8.5）。本机无 GPU，把 `device_type='cuda'` 换成 `'cpu'` 就能原样跑通这两件套，autocast 照样把算子降到 bf16：

```python
with torch.autocast(device_type='cpu', dtype=torch.bfloat16):
    out = nn.Linear(4, 2)(torch.randn(3, 4))
print(out.dtype)
```

```text
torch.bfloat16
```

## $\rm \S \, 8.3$ dtype 怎么选：默认 float32

要解决的问题：float32、bfloat16、float16 三个名字摆在一起，训练该挑哪个。口诀三条：

1. 训练默认 `float32`：绝大多数网络的起点，也是参数主拷贝该保持的精度；
2. 想省显存、提速度就用 `bfloat16`，它保范围（指数与 float32 一样宽），小梯度不下溢，不需要额外开关；
3. `float16` 保精度（尾数比 bfloat16 长），但范围窄、要配 `GradScaler` 护航，只在明确有收益时用。

| 场景 | 选 | 理由 |
| --- | --- | --- |
| 一般训练、调试 | float32 | 稳定，无需额外开关 |
| 大模型、深网络提速 | bfloat16 | 范围与 float32 相同，免缩放 |
| 追求尾数精度 | float16 + GradScaler | 尾数长但范围窄，需护航 |

口诀落到一句话：默认 float32；bfloat16 保范围、float16 保精度但要配缩放。为什么是「范围」与「精度」的取舍，交给 §8.5 的位分配表。

## $\rm \S \, 8.4$ 打开盖子：设备抽象与搬运的账

不打开盖子，你会缺一块判断力：会写 `.to(device)`，却说不清跨设备运算为什么直接报错、搬运为什么是最贵的操作之一。迷你框架加设备只差一个字段：`Tensor` 增加 `device` 属性（本机 CPU 上用 `'cpu'` 与 `'cpu:0'` 模拟两台「设备」，只是标签，不真搬迁），再约定一条规则：参与同一运算的张量必须同设备，否则抛错。`.to(device)` 是唯一允许的搬迁入口：

```python
class Tensor:
    def __init__(self, data, device='cpu'):
        self.data = np.asarray(data, dtype=np.float64)
        self.device = device                 # 设备标签，本机不真搬迁
    def to(self, device):
        return Tensor(self.data, device)     # 搬运 = 换标签发新对象

t = Tensor(W, device='cpu:0')
t2 = t.to('cpu')                             # 搬运完成
t + w                                        # 设备不同 → RuntimeError
```

`__add__` 里加一行 `assert self.device == other.device` 就把规则变成代码。这条规则在 torch 内部叫设备分派（device dispatch）：每个算子收到张量后先查 `device` 字段，再决定调用 CPU 内核还是 CUDA 内核。迷你框架的「设备」只是标签，torch 的设备背后是两套完整的算子实现，`torch.add` 一个名字、两套代码，接口与实现就此分层。跨设备运算直接报错不是 torch 小气，是设计：`RuntimeError: Tensor on device meta is not on the expected device cpu!`（真跑捕获，用 torch 的 meta 设备在 CPU 机器上演示同类报错）。

报错比隐式搬运好，因为搬运是最贵的操作之一。同样是规格口径：A100 显存带宽约 2039 GB/s，而主机到显卡的 PCIe 4.0 只有约 32 GB/s，差 60 倍。这是「数据与计算同地」的数字注脚：一个 batch 搬进显存只要毫秒，但每个 step 都搬一遍就把 GPU 喂不饱，正确做法是整个数据集（或分块）常驻显存、整份模型常驻显存，搬运只发生在训练开始与结束时。

## $\rm \S \, 8.5$ 打开盖子：精度预算：从 float32 到 float16

不打开盖子，你会缺一块判断力：知道要开混合精度，却说不清省下的字节花在哪、付的误差有多大、什么时候会从「差一点」变成「差很多」。先把 float32 相对 float64 的账算一遍。同一 MLP（$8\to32\to2$）、同一数据（§6.2 的高斯数据）、同一种子、20 epoch，torch 只换 dtype。本机 CPU 实测：

| 指标 | float64 | float32 | 倍率 |
| --- | --- | --- | --- |
| 20 epoch 耗时 | 0.134 s | 0.088 s | 1.52 |
| 参数字节数 | 2832 B | 1416 B | 2.0 |
| 最终 loss | 0.132959 | 0.132959 | 相同 |
| 测试 acc | 0.90 | 0.90 | 相同 |
| 与 float64 参数最大差 | （基准） | ${7.6\times10^{-7}}$ | |

验证环境：WSL Ubuntu，PyTorch 2.14.1+cpu。三个读数：内存精确减半（尾数从 52 位缩到 23 位，字节数减半）；训练 20 epoch 后 float32 的参数与 float64 偏离 ${7.6\times10^{-7}}$ 量级，恰好是 float32 的机器精度（${\approx1.2\times10^{-7}}$）累积的样子，loss 与 acc 纹丝不动；CPU 上 32 位还快了 1.5 倍。GPU 上差距更大：A100 的规格口径是 fp32 矩阵算力约 19.5 TFLOPS、fp64 约 9.7 TFLOPS，张量核心（Tensor Core）对半精度还要再快一个量级，本机无 GPU，这些数字是规格书口径而非实测。

这个论证有个边界要划清：float32 买得起的是「每一步差一点」，不是「误差无界累积」。上面的 ${7.6\times10^{-7}}$ 是 20 epoch 的账；epoch 拉长，偏离会缓慢增长，但 SGD 每步都被「当前 batch 的噪声」重新洗牌，舍入误差不系统叠加，最终稳在与梯度噪声同量级的位置。真正怕低精度的是另一处：下面 float16 的小梯度被抹零，那是「差一点」与「差很多」的分界线。

float16 的格式是 1 位符号、5 位指数、10 位尾数，最小正规数 ${6.1\times10^{-5}}$，最小非正规数 ${2^{-24}\approx5.96\times10^{-8}}$。用 numpy 真跑一组表示实验：

| 值 | float16 表示 | 相对误差 |
| --- | --- | --- |
| ${10^{-4}}$ | ${1.000\times10^{-4}}$ | ${1.7\times10^{-4}}$ |
| ${10^{-5}}$ | ${1.001\times10^{-5}}$ | ${1.4\times10^{-3}}$ |
| ${10^{-6}}$ | ${1.013\times10^{-6}}$ | ${1.3\times10^{-2}}$ |
| ${10^{-7}}$ | ${1.192\times10^{-7}}$ | ${1.9\times10^{-1}}$ |
| ${10^{-8}}$ | 0 | 1.0 |

梯度更新 ${w\gets w-\mathrm{lr}\cdot g}$ 在 ${\mathrm{lr}=10^{-3}}$、${g=10^{-5}}$ 时更新量只有 ${10^{-8}}$：float32 里是 ${1.000\times10^{-8}}$，float16 里直接是 0。loss scaling（损失缩放）是针对它的手术：把损失乘一个大数 ${S}$（如 ${2^{10}}$），反向传播的梯度全体跟着乘 ${S}$，${10^{-8}}$ 的更新量变成 ${10^{-5}}$，落回 float16 的可表示区；优化器更新前再除回 ${S}$（在 float32 里做）。同一组数字验证：直接算更新，float16 得 0；先乘 ${2^{10}}$ 再在高精度除回，得 ${1.001\times10^{-8}}$，与真值同量级。

下溢实验的完整版放进表里：初值 ${w=10^{-3}}$、${\mathrm{lr}=10^{-3}}$、${g=10^{-5}}$，连走一万步（验证环境 NumPy 2.5.4）：

| 实现 | 单步更新量 | 一万步后的 ${w}$ |
| --- | --- | --- |
| float32 | ${1.000\times10^{-8}}$ | ${8.999\times10^{-4}}$ |
| float16 | 0 | ${1.0004\times10^{-3}}$ |

float16 的参数在起点附近纹丝不动：不是学得慢，是压根没学。这类 bug 在真实训练里的长相是「某些层的参数一万步零变化」，数值下溢要排在怀疑名单前列。

混合精度的格式取舍在指数与尾数之间：

| 格式 | 位分配 | 最大值 | 最小正规数 | 有效十进制位 |
| --- | --- | --- | --- | --- |
| FP16 | 5 指数 + 10 尾数 | 65504 | ${6.1\times10^{-5}}$ | 约 3.3 |
| BF16 | 8 指数 + 7 尾数 | ${\approx3.4\times10^{38}}$ | ${1.2\times10^{-38}}$ | 约 2.9 |

真跑对照（torch bfloat16）：${10^{-8}}$ 在 BF16 里表示为 ${1.001\times10^{-8}}$，活着；在 FP16 里是 0。反过来，65504 在 BF16 里被舍成 65536，尾数粗的代价。BF16 的动态范围与 float32 相同，梯度再小也不下溢，所以不需要 loss scaling；FP16 尾数长、算得准，但要配 GradScaler 护航。表里还有一行值得单看：FP16 的最大值只有 65504，前向激活一旦超过它就溢出成 inf，损失再一平均就是 nan；BF16 的上限 ${3.4\times10^{38}}$ 与 float32 一致，从根上没有这个问题。至此 §8.2 两件套的分工也就落地了：autocast 管「哪些算子用 16 位跑」，GradScaler 管「16 位算出的梯度怎么活着送到更新」，两个开关各管一段、缺一不可。

## $\rm \S \, 8.6$ 常见错误与报错翻译

| 症状 | 原因 | 怎么改 |
| --- | --- | --- |
| 报错 `RuntimeError: ... is not on the expected device ...` | 数据搬到了 GPU、模型还在 CPU（或反过来） | 两处都搬：`xb = xb.to(device)` 与 `model.to(device)`（§8.1） |
| 某些层的参数一万步零变化 | float16 下溢，小梯度被抹成 0（§8.5） | 换 bfloat16，或给 float16 配 `GradScaler`（§8.2） |
| loss 变 `nan` | 两种常见来源：float16 前向激活超过 65504 溢出成 inf；学习率过大导致发散 | 换 bfloat16 或检查激活幅度；先把 lr 调小（§6.5） |

## $\rm \S \, 8.8$ 应用与辨析

1. `X = X.to('cuda')` 之后直接 `model(X)`，若模型还在 CPU 上会发生什么？正确的两行怎么写？
2. §8.5 中 float32 参数偏离 float64 约 ${7.6\times10^{-7}}$：训练 200 epoch 这个数字会一直涨吗？涨到什么量级会开始影响 loss？（提示：SGD 的噪声水平。）
3. 把 §8.5 的 ${g=10^{-5}}$ 换成 ${g=10^{-6}}$，float16 的更新量是多少？相对误差多大？（用表外推再核对。）
4. 一个网络的梯度范数长期在 ${10^{-9}}$ 量级（梯度消失），FP16 加 loss scaling 救得了它吗？loss scaling 放大的是什么、救不了什么？
5. BF16 的有效十进制位约 2.9，为什么训练损失曲线看不出它比 FP16 差？

## $\rm \S \, 8.9$ 本章自测答案

### $\rm \S \, 8.9.1$ 关键概念回顾答案

1. 有卡自动用卡、无卡退回 CPU，同一份代码两台机器都能跑；三处是模型、每个 batch 的数据、损失里的权重张量。（§8.1）
2. autocast 管「哪些算子用 16 位跑」，GradScaler 管「梯度怎么活着送到更新」（loss scaling）；bfloat16 动态范围与 float32 相同、不下溢，无需缩放。（§8.2、§8.5）
3. 省一半内存与近一半时间；付出 ${10^{-7}}$ 量级的参数偏离，量级由 float32 机器精度 ${1.2\times10^{-7}}$ 决定。（§8.5）
4. ${2^{-24}\approx5.96\times10^{-8}}$；${10^{-8}}$ 比它还小，表示为 0，更新被完全抹掉；三步是前向损失乘 ${S}$、反向梯度放大 ${S}$ 倍、更新前在 float32 里除回。（§8.5）
5. FP16 保尾数（精度）、BF16 保指数（范围）；噪声以下的舍入可以接受（SGD 的 batch 噪声更大，把舍入误差盖住），下溢线以下的抹零必须救。（§8.5）

### $\rm \S \, 8.9.2$ 应用与辨析答案

1. 报 `RuntimeError`（设备不匹配）；`X = X.to('cuda')` 与 `model.to('cuda')` 两行都要，数据与计算同地。（§8.1）
2. 不会无限涨：偏差稳定在 float32 舍入与 SGD 噪声的平衡点，${10^{-7}}$ 到 ${10^{-6}}$ 量级；要影响 loss 得超过梯度噪声本身，这台实验的噪声远大于此。（§8.5）
3. 更量 ${10^{-7}}$，float16 表成 ${1.19\times10^{-7}}$，相对误差约 19%（表中 ${10^{-7}}$ 一行）；仍是「没归零但已经不准」。（§8.5）
4. 救不了梯度消失本身：scaling 放大的是「梯度表示」的下溢，把 ${10^{-9}}$ 搬进可表示区，但反向穿过网络时逐层衰减的结构没变；救了存储、救不了传播。（§8.5）
5. 损失曲线的分辨率由 SGD 噪声决定（batch 间抖动，§7.5 的振荡），${10^{-2}}$ 量级的抖动完全盖住 ${10^{-2.9}}$ 与 ${10^{-3.3}}$ 尾数之差。（§8.5）
