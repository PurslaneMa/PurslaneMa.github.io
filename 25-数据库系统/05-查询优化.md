# $\rm Chapter \, 5$ 查询优化器：代价估算与执行计划

第 4 章末尾留了一个悬念：连接顺序是 ${n!}$ 级的爆炸，谁来选？答案是查询优化器。SQL 是声明式语言，你只说「要什么」，它替你挑「怎么算」。本章看它怎么挑：先讲它手里的三件等价变换工具与一本代价账，再用三组真实实验看清它的能与不能，包括它亲手选出一个更慢计划的那一刻。

> **开始前自检**：本章假设你已经会：
>
> 1. □ 读 `EXPLAIN QUERY PLAN` 的 SCAN 与 SEARCH 行（§3.4）；
> 2. □ 算三种连接算法各自的页数账（§4.4）；
> 3. □ 说明覆盖索引为什么不回表（§3.5）；
> 4. □ 知道 B+ 树按主键有序、范围查询走叶链（§2.4）。

## $\rm \S \, 5.1$ 优化器在优化什么

同一个查询，等价的执行方案有无穷多：先过滤再连接、还是先连接再过滤；用哪个索引、还是全表扫；表 A 驱动 B、还是 B 驱动 A。方案间耗时差几个数量级（§4.4 实测过 7000 倍），而逐个试跑等于不优化。优化器的做法是：**对每棵候选计划树估算代价，选最便宜的那棵**，不执行、只估算——像打车软件派单：不真派车试跑一圈，凭路况数据估出哪条路线最快就派谁。估算的依据是三件东西：等价变换律（生成候选）、统计信息（估行数）、代价公式（把行数折算成页访问）。

## $\rm \S \, 5.2$ 等价律：三件最值钱的变换

关系代数的等价律很多，工程里最值钱的三条：

1. **选择下推（predicate pushdown）**：先过滤再连接，几乎总比先连接再过滤便宜，因为过滤掉一半行，连接的工作量直接减半。公式一句话：${\sigma_{p}(A \Join B) = \sigma_{p}(A) \Join B}$（当 ${p}$ 只涉及 A 的列时）；
2. **投影下推**：只把后面用到的列带进连接，行更窄、每页装更多，与覆盖索引（§3.5）是同一笔账的两面；
3. **连接交换律与顺序**：${A \Join B = B \Join A}$，但驱动方不同代价迥异（§4.4 的嵌套循环里，外层每行都要扫内层），而多表连接时顺序组合是 ${n!}$，优化器要在这里做剪枝搜索而不是穷举。

**本节小结**：这三件变换负责「生成等价候选」——下推砍掉无关的行与列，交换律换驱动方；候选里谁最便宜，由下一节的统计信息与代价公式裁定。

## $\rm \S \, 5.3$ 统计信息：估行数靠什么

代价公式的核心输入是「这一步出来多少行」。优化器不扫表数行（那等于执行了），它看**统计信息**：每张表的行数、每列的不同值个数（NDV）、最值与分布直方图。SQLite 里 `ANALYZE` 命令采集这些统计存进 `sqlite_stat1` 表，`EXPLAIN QUERY PLAN` 的选择随之可能改变。

没有统计时的默认假设值得知道：均匀分布、选择性按 ${1/\text{NDV}}$ 估。倾斜数据下这套假设会错得很远。95% 的行都是同一个值的列，按均匀假设估出的行数可能差两个数量级，§5.6 的实验会给出实证。

看一眼真实的统计表（§5.6 的库执行 `ANALYZE` 后，逐字采集）：

```text
sqlite> SELECT * FROM sqlite_stat1;
events|idx_kind|200000 10000
sqlite> SELECT COUNT(DISTINCT kind) FROM events;
20
```

读数惊人：kind 的真实不同值只有 20，统计表却记成 10000，因为 SQLite 的 ANALYZE 对大表做的是近似采样，遇到 95% 行集中在一个值的极端倾斜，集中度被严重低估（以为平均每个值约 20 行，实际 kind=1 有 19 万行）。两个数字就是优化器的全部「市场情报」：总行数与近似的 NDV；没有直方图（PostgreSQL 的 pg_stats 有分布信息），情报粗到这个程度，估算跟着粗，§5.6 里 125 ms 对 5 ms 的悬殊，根子在这行统计上。生产库定期 ANALYZE（尤其大批量导入后）喂的就是这张表，喂完仍要拿真实查询验收，因为「统计准了」也只是把估算的方差调小。
顺带一提 `PRAGMA analysis_limit=N`（如 1000）能让 ANALYZE 只采样 N 行快速完成。大表上「统计略粗但新鲜」往往胜过「极准但从不更新」。

## $\rm \S \, 5.4$ 实测一：下推这件事，优化器已经代劳了

先验证一件好事：手写「先连接后过滤」与「先过滤后连接」，优化器是不是给出同样的计划？20 万订单 × 5000 用户、无二级索引（复现：建表插入，种子 20261025）：

```python
import sqlite3, time
Q1 = '''SELECT o.id FROM orders o JOIN users u ON o.user_id=u.id
        WHERE u.tier=9 AND o.amount>400'''
Q2 = '''SELECT o.id FROM (SELECT * FROM orders WHERE amount>400) o
        JOIN users u ON o.user_id=u.id WHERE u.tier=9'''
for name, q in [('先连接后过滤', Q1), ('先过滤后连接', Q2)]:
    plan = [p[3] for p in conn.execute('EXPLAIN QUERY PLAN '+q)]
    t0 = time.perf_counter(); conn.execute(q).fetchall()
    print(name, f'{(time.perf_counter()-t0)*1000:.0f} ms', plan)
```

本机输出：

```text
先连接后过滤: 17 ms ['SCAN o', 'SEARCH u USING INTEGER PRIMARY KEY (rowid=?)']
先过滤后连接: 21 ms ['SCAN o', 'SEARCH u USING INTEGER PRIMARY KEY (rowid=?)']
```

两行计划**逐字相同**：SQLite 已经把 `tier=9` 下推到连接之前（对 users 按主键逐个 SEARCH 就是过滤后的探测）。教训双向：一，别为「性能」手写嵌套子查询做下推，现代优化器比你先想到；二，也别因此认为「怎么写都一样」，优化器只会等价变换，不会替你改变语义。下一组实验就是它帮不了你的地方。

## $\rm \S \, 5.5$ 实测二：深分页，改写语义才逃出生天

第 20 万页附近取 10 行，两种写法**不等价但同样正确**（同一结果集），实测（同库三轮取最优）：

```text
OFFSET 深翻页:        9.64 ms ['SCAN orders']
锚点法（WHERE id>=…）: 0.30 ms ['SEARCH orders USING INTEGER PRIMARY KEY (rowid>?)']
```

32 倍。计划说穿了原因：`OFFSET 199990` 的语义是「丢掉前 199990 行」，SQLite 只能顺着 rowid 全扫并数数；锚点法把「翻到第 N 页」翻译成「从 id=199990 开始」，B+ 树直接下潜到叶（§2.4 的对数下潜），拿 10 行收工。这是优化器边界的标准形态：**它可以在等价方案里挑最便宜的，但你给它的语义本身贵，它无权改**。「WHERE id>= 上次末尾」是应用层的状态，SQL 里没有等价物。通用化：深分页、N+1 查询、`SELECT *` 拖全列，都属于「语义级浪费」，任何优化器都救不了。

## $\rm \S \, 5.6$ 实测三：优化器选错的那一刻

最后看优化器真正失手的现场。给 §5.4 的库补一个 `orders(user_id)` 索引后重跑同一查询：

```text
无索引:            17 ms  ['SCAN o', 'SEARCH u …rowid']
建 idx_o_user 后:  54 ms  ['SCAN u', 'SEARCH o USING INDEX idx_o_user (user_id=?)']
```

计划翻了个面：从「扫订单、逐个查用户」变成「扫用户、按索引查订单」，优化器看到索引就切换了驱动方，但**实测慢了 3 倍**。它没有 bug：按成本模型，索引探测便宜；错的是估算与现实的偏差（实际行数分布、缓存局部性、回表的随机 I/O 模式都比模型复杂）。这引出两条工程纪律：

1. **计划会变，要有办法钉住**：`INDEXED BY` 子句（或 `NOT INDEXED`）可以强制/禁用某个索引，生产环境「昨晚还快今早慢了」的排查第一步就是对比执行计划有没有翻面；
2. **加索引不是免费的**：§3 实测过 32 倍写放大，本节又看到读侧也可能变慢。每个索引都要拿真实查询负载（而不是想当然）来验收。

倾斜数据的另一组读数（20 万行、95% 集中在 kind=1、带 idx_kind、回表查询）：`kind=1`（19 万行）走索引回表 **125 ms**，`kind=2`（1025 行）**5 ms**，同一个索引、同一种计划，选择性差 190 倍导致耗时差 25 倍。`ANALYZE` 之后耗时略降（173→125 ms）但计划不翻：SQLite 的成本模型对索引有系统性偏爱，宁可采了统计也不放弃，这不是缺陷声明，而是「估算终究是估算」的又一条证据。

## $\rm \S \, 5.7$ EXPLAIN 读法小结

`EXPLAIN QUERY PLAN` 每行四个字段的末列是主文，三种关键词的读法：

1. `SCAN t`：全表（全索引）扫，行数大就是罪状，行数小无所谓；
2. `SEARCH t USING … (…) `：走了索引，括号里是可用的约束（`rowid=?` 主键等值、`kind=?` 二级索引、`rowid>?` 范围）；`COVERING INDEX` 标记不回表；
3. `USE TEMP B-TREE FOR …`：为排序/去重临时建树，出现 `DISTINCT`/`ORDER BY` 拿不到索引序时才付这笔钱。

排障流程固定三步：先看有没有 SCAN 大表、再看有没有 TEMP B-TREE、最后看驱动顺序（谁 SCAN 谁 SEARCH），三个问题各对着一个等价律。

> **竞赛生迁移提示**：OJ 的方法论是「枚举做法 → 按复杂度选 → 提交实测」，优化器是「枚举计划 → 按**估算**选 → 从不试跑」。你能接受「估算错了 TLE 再换」，数据库也一样。工程动作不是骂优化器，而是跑 ANALYZE 喂统计、必要时 INDEXED BY 钉计划：把 OJ 里「读题补条件」的那一步，换成「喂对情报」。

## $\rm \S \, 5.10$ 本章自测答案

### $\rm \S \, 5.10.1$ 关键概念回顾答案

1. 生成候选靠等价变换律（下推、交换、改连接算法），挑方案靠统计信息＋代价公式。不试跑因为执行本身就是开销：优化器对每个查询都要在毫秒内出计划，试跑等于把查询执行 N 遍。（§5.1）
2. ${\sigma_{p}(A \Join B) = \sigma_{p}(A) \Join B}$，前提是谓词 ${p}$ 只涉及 A 的列（否则过滤不了 A）。（§5.2）
3. OFFSET 的语义就是「数过前 N 行再开始返回」，任何等价计划都得数；锚点法把「第 N 页」翻译成「主键大于锚点」，**换了语义**（从偏移量变成范围条件），才有 B+ 树对数下潜可用。优化器无权做这种语义替换。（§5.5）
4. 都不全是：索引本身合法，优化器的成本估算在真实数据分布/回表随机 I/O 上偏差了。纪律一：用 `INDEXED BY`/`NOT INDEXED` 钉计划并对比计划变化；纪律二：加索引前后用真实负载验收读写两侧。（§5.6）
5. SCAN 对应「该下推没下推/缺索引」；SEARCH 括号对应可用约束；TEMP B-TREE 对应排序去重没吃上索引序。（§5.7）

### $\rm \S \, 5.10.2$ 应用与辨析答案

1. ① 保存/对比 `EXPLAIN QUERY PLAN`（前后各跑一次），计划翻了查统计与数据量（是不是跨过了某个阈值、`ANALYZE` 该不该重跑）；② 计划没变则查数据量（表涨了多少倍）与缓存状态（冷热）；③ 查系统级：锁等待（§7）、磁盘延迟（操作系统分册 §10.2）。（§5.6、§5.7）
2. 反驳：§5.4 实测两种写法计划逐字相同（17/21 ms），优化器已代劳下推；手写展开不带来计划收益，还损失可读性。真正动手的时机是语义级改写（§5.5 深分页）；那不是「展开」，而是换问题。（§5.4、§5.5）
3. kind=1 占 95%，索引回表比全表扫更贵（§5.6 倾斜读数 125 ms 正是此形）。反向方案：直接全表扫并把 `NOT INDEXED` 钉上；或按 kind 做分区/部分索引（`CREATE INDEX … WHERE kind<>1` 之类），让报表走扫描、其余走索引。「优化」不一定等于「建索引」。（§5.6）
