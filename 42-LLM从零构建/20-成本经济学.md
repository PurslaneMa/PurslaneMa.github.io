# $\rm Chapter \, 20$ 训练成本经济学：GPU 市场与每 token 账

前十八章解决了「怎么做」，这一章解决「多少钱」。大模型产业的一切戏剧——谁敢训 405B、谁把 8B 白送、API 怎么定价、开源是慈善还是战争——背后都是同一本账：GPU 的租金怎么算、一次训练烧多少、一个 token 卖多少才有的赚。本章把这本账拆成三块：GPU 市场的结构（租金从哪来、随什么波动）、训练的三段账（算力、数据、人力）、推理的毛利账（每百万 token 的成本拆解与三因子敏感性实测）。学完你能对任何一个大模型项目问出那几个要命的问题：卡的量级对不对、账里有没有算人力、毛利在哪一层。

> **开始前自检**：本章假设你已经会：
>
> 1. □ 训练算力账 ${C\approx 6ND}$ 与推理每 token ${2N}$ FLOPs 的来历（§1.3）；
> 2. □ MFU 的定义与经验带（§1.3、§6.2）；
> 3. □ roofline 与算术强度、访存受限与算力受限的判定（§6.2）；
> 4. □ decode 为什么访存受限、batch 为什么能近乎免费增大（§12.2）；
> 5. □ 过训练的摊销逻辑（§8.3.3）。

## $\rm \S \, 20.1$ 需要的前提

1. **卡时（GPU-hour）**：一张卡租一小时的计费单位。训练成本的通用报价方式就是「卡时单价 × 卡时总量」，云厂商官网、现货市场、中介经纪商报的都是这个数。
2. **利用率（utilization）**：付费时间里真正在产出 token 或在有效训练的比例。买了卡时不等于用了卡时——排队、空闲、抢占、坏请求都往分母里跑。本章记作 ${u}$。
3. **租金记号**：本章把每卡时租金记作 ${R}$（美元/卡·时）。市场价随型号、量、期限、地域大幅波动，本章只锁量级做演示：${R=2.5}$，即「每小时几美元」这一档。
4. **白话开场**：成本核算的全部难点不在乘法，在「哪些成本被悄悄漏掉了」。本章的每个公式都配一张「这个公式没算什么」的清单——漏项才是成本账的常态。

## $\rm \S \, 20.2$ GPU 市场结构：租金、周期与两种买法

白话：先搞清你租的那张卡，钱被谁赚走了、价签为什么会动。

### $\rm \S \, 20.2.1$ 租金为什么动：三个周期

训练卡市场的供给侧高度集中：高端 AI 加速器的年产量以百万张计，而需求方是几个巨头加一群想成为巨头的公司，供需的小失衡会直接写进租金。价格随三个周期波动。

1. **产品周期**：新一代卡发布前后，上一代卡租金松动、新卡溢价；升级窗口的采购时点能差出两成的价（量级直觉）。
2. **需求周期**：头部实验室开新训练项目的时段，大集群被整包锁走，散货市场收紧；反过来项目间歇期，市场上会多出一批「退役训练卡」转做推理，价格回落。
3. **政策周期**：出口管制等区域性约束造成同一张卡在不同地区价差数倍（只写机制，不写具体行情）。

三层叠加的结果是：租金没有「标准价」，只有「当下、此地、此量」的报价——所以所有严肃的成本模型都把 ${R}$ 当参数而不是常数，本章也是如此。实操上，买算力像买大宗商品：多家询价、按量谈梯度、报价单上注明「含不含互连与存储」，这三个习惯能省下的钱比多数模型层优化都多。

### $\rm \S \, 20.2.2$ 两种买法：现货与合约

1. **现货/按需（on-demand 与 spot）**：随开随用，spot 竞价盘便宜得多——但平台随时可以把卡收回去（抢占）。
2. **合约/预留（reserved）**：签期买量换折扣，一年期与三年期价差可观，代价是押注「三年后这张卡还值这个价」。

第 7 章讲过的那条纪律在这里变成生死线：**用可抢占算力训练，checkpoint 就不是「最好有」，是唯一的安全带**（§7.10 的环境与保活实操原样适用）。工业惯例是混搭：基线负载走合约锁底价，峰值与实验走现货吃弹性。

### $\rm \S \, 20.2.3$ 隐性结构：卡不是单卖的

真训得动大模型的是「集群」——卡、机内互连（NVLink）、跨机网络（IB）、存储、网络拓扑是一套打包商品，租的时候按集群粒度谈，报的价里已经含了机柜与网络。这就是为什么「单卡租金 × 卡数」永远小于真实报价：互连与机时是集群溢价的主要成分（§7.1 的 TP 跨机慢一个量级，就是这套硬件在背后定价）。自建机房还有第三层账：电费与冷却在整机寿命成本里占比可观，选址（电价、气候、政策）是巨头们买岛圈地的原因——这一层在租用模式下已经折进 ${R}$，自建时要自己掏。

本节小结：租金是参数不是常数，随产品、需求、政策三个周期波动；现货换弹性、合约换折扣，抢占风险用 checkpoint 纪律对冲；报价按集群不按裸卡。

## $\rm \S \, 20.3$ 训练成本三段账：算力、数据、人力

白话：「训一个模型花了多少钱」这句话，至少要拆成三本账再加一个系数。

### $\rm \S \, 20.3.1$ 算力账：唯一能算的那段

算力账有公式：${C=6ND}$（§1.3），除以「单卡有效算力 × 3600」就是卡时。实测走一遍（`_lfs_work/exp20/result.txt` 第 1 节）：8B 模型训 15T token（Llama 3 8B 的配置，据 Dubey et al. 2024），

$$
C = 6ND = 6 \times 8\times 10^{9} \times 15\times 10^{12} = 7.2\times 10^{23}\ \text{FLOPs}
$$

按 MFU 0.4（单机经验带上沿，千卡集群实际更低，§6 实录）折算：单卡要烧 505,561 卡时——约两千年；铺 1000 张卡是 21 天。按 ${R=2.5}$ 折租金下限约 126 万美元。说「下限」是因为它假设了全程满 MFU、零失败、零重跑——真实项目这三个假设一个都不成立。对照锚：据 Llama 3 技术报告，405B 的预训练用了 30.84M H100 卡时，按同一租金折约 7,700 万美元，而这只是卡钱。

### $\rm \S \, 20.3.2$ 数据账与人力账：不显眼但刚性

数据账是第 2 章的产线在账本上的投影，拆开是四笔：网络爬取与存储带宽、语料授权采购（新闻、图书、代码的授权在大模型预算里能占到可观比例）、清洗与去重的算力、标注与评测的人力。它的特点是「不随训练天数波动，但没它整个项目停摆」。

人力账：前沿团队是几十上百名研究与工程师的数年投入。按人年单价折算，在小模型项目里它可能反超算力账；在大项目里它通常比算力小一个量级——但「最贵的人决定最贵的卡怎么花」，人的效率折进 MFU 与重跑率里，实际影响远大于工资单。这解释了一个招聘现象：训练团队的工资看似离谱，除以它省下的卡时之后常常是全公司回报率最高的岗位。

### $\rm \S \, 20.3.3$ 重跑系数：新人的头号漏项

训练不是一次成功：loss spike 回滚（§14）、超参搜索、scaling 阶梯的消融预算（§1.4 的 5–10% 惯例）、最终冲刺前的废案——工业惯例把「有效算力」除以一个 1.2 到 2 之间的系数才是预算。报预算不报重跑系数，是新人成本表最常见的漏项；反过来，老手做规划时先把「失败预算」名正言顺地写进表里，评审时反而显得可靠。

三段账的相对比例随规模变化：越大越偏算力（卡钱吞掉一切），越小越偏数据与人力（几十万卡时以下的项目，人的时间常常是最贵的资源）。这也解释了产业分工——巨头拼算力，中小玩家拼数据与工程效率。

本节小结：训练成本＝算力账（${6ND}$ 除以 MFU，再乘重跑系数）＋数据账＋人力账；8B×15T 的租金下限百万美元级，405B 的真实卡钱数千万美元级。

## $\rm \S \, 20.4$ 推理毛利账：每百万 token 的成本拆解

白话：训练是花一次的大钱，推理是每小时都在流的小钱——而小钱的设计空间大得多。这是本章实测的主角，先把公式立起来。

### $\rm \S \, 20.4.1$ roofline 与临界 batch

推理一个输出 token 的最低工作量：把全部权重读一遍显存（§12.2 的访存受限），配合 ${2N}$ FLOPs 的前向（§1.3）。roofline 两段式：batch 为 $b$ 时，每步时间取「权重读时间」与「计算时间」的较大者，

$$
t(b) = \max\left(\frac{N \cdot 2\ \text{字节}}{\mathrm{BW}},\ \frac{2Nb}{P\cdot\mathrm{MFU}}\right)
$$

读法：分子分母都是「这一步绕不开的量」——权重 ${N\times 2}$ 字节必读一遍，${2Nb}$ FLOPs 必算一遍；左边是访存墙、右边是算力墙，谁慢听谁的。一个漂亮的巧合藏在里面：decode 的算术强度恰好是 ${b}$（${2Nb}$ FLOPs 除以 ${2N}$ 字节），所以临界 batch 就是

$$
b^{*} = \frac{P\cdot\mathrm{MFU}}{\mathrm{BW}}
$$

——机器平衡点（§6.2 的 295 FLOPs/字节）乘以 MFU。${b<b^{*}}$ 时访存受限、吞吐随 ${b}$ 线性涨（多开的请求几乎免费）；${b\ge b^{*}}$ 后算力受限、吞吐封顶在 ${P\cdot\mathrm{MFU}/(2N)}$。

### $\rm \S \, 20.4.2$ 成本地板与漏项清单

把吞吐除进租金，得到成本地板：

$$
c_{\min} = \frac{R\cdot 10^{6}}{3600\cdot u}\cdot\frac{2N}{P\cdot\mathrm{MFU}}
$$

这行在说：每百万 token 成本＝卡时单价摊到秒、除以利用率、乘「每个 token 的 FLOPs」再除以「每秒有效 FLOPs」。三个可动因子全在里面：${\mathrm{MFU}}$（工程调优）、${u}$（运营水平）、${b}$（决定你离地板多远）。

「这个公式没算什么」清单：KV cache 的读写与显存占用（§12.2 的账，长上下文时反过来挤占可用的 batch 空间）、注意力对长序列的平方项、prefill 的输入 token 成本、量化对权重字节的折半（§12.6）、调度与网络的损耗。所以本账是**下限**——真实成本在下限的 2 到 5 倍是常态（工业惯例量级），但下限的相对关系不会翻：能让下限降一倍的操作，真实成本也降一倍。

本节小结：decode 成本由 roofline 决定，临界 batch＝平衡点×MFU，成本地板由 ${R}$、MFU、${u}$ 三个因子乘出来；公式是下限，漏项清单与公式一样重要。

## $\rm \S \, 20.5$ 实测：单 token 成本敏感性表

白话：三个因子各动一动，成本动多少？用 §20.4 的公式算一张表，数字全部来自 Python 计算（`_lfs_work/exp20/result.txt`，纯算术无随机数；口径为下限）。

### $\rm \S \, 20.5.1$ 设置

8B 模型、单卡 H100（bf16 峰值 989 TFLOPS、带宽 3.35 TB/s，据 NVIDIA 规格）、${R=2.5}$。先看临界 batch：MFU 0.5 时 ${b^{*}=148}$，MFU 0.3 时 ${b^{*}=89}$——MFU 掉四成，可用的 batch 窗口跟着缩。

### $\rm \S \, 20.5.2$ 主表：固定 MFU 与利用率，扫 batch

主表固定 MFU 0.5、${u=0.9}$：

| batch ${b}$ | 每步时间 | 吞吐（tok/s） | 受限于 | ${\$}$/1M tokens |
| --- | --- | --- | --- | --- |
| 1 | 4.78 ms | 209 | 访存 | 3.69 |
| 4 | 4.78 ms | 838 | 访存 | 0.92 |
| 16 | 4.78 ms | 3,350 | 访存 | 0.23 |
| 64 | 4.78 ms | 13,400 | 访存 | 0.058 |
| 256 | 8.28 ms | 30,906 | 算力 | 0.025 |
| 1024 | 33.1 ms | 30,906 | 算力 | 0.025 |

访存段的吞吐公式是 ${b\cdot \mathrm{BW}/(2N\ \text{字节})}$——每多一路并发请求，吞吐精确地多一份：${b}$ 从 1 到 64，吞吐从 209 涨到 13,400，正好 64 倍。这就是「批量摊薄权重读」的算术：权重读一遍 4.78 ms 是固定的，这一遍里顺带算几个请求，每个请求的边际成本趋近于零（§12.2 的结论在这里落成了价格）。

### $\rm \S \, 20.5.3$ 读法四条

1. **batch 是杠杆最长的因子**：${b=1}$ 到 ${b=256}$，成本从 3.69 降到 0.025，整整 147 倍——这是 §12.2「连续批处理」的经济学注脚：调度器省下的每一分空闲，都是真金白银。
2. **过临界点后 batch 不再省钱**：${b=256}$ 与 ${b=1024}$ 同价，算力墙封顶；多攒 batch 只换来延迟（每步 33 ms，TTFT 变差，§12.7 的 SLO 拆账在此会合）。
3. **MFU 只在算力段起作用**：访存段（${b\le 64}$）里卡在等数据，算得快慢无关紧要——MFU 从 0.5 掉到 0.3，成本纹丝不动（角点表里 ${b=64}$ 列上下两行同价）；算力段（${b=4096}$）里同样的 MFU 滑坡让成本从 0.025 涨到 0.042。调 MFU 之前先看自己站在哪段墙上。
4. **利用率永远全额生效**：${u}$ 从 0.9 掉到 0.6，两段的成本同比例上涨五成（成本正比于 ${1/u}$）——它是唯一一个「无论站哪」都在扣钱的因子，也因此是最诚实的运营指标。

### $\rm \S \, 20.5.4$ 三因子角点与 55 倍

| 配置 | ${b=4096}$（算力段） | ${b=64}$（访存段） |
| --- | --- | --- |
| MFU 0.5，${u=0.9}$ | 0.025 | 0.058 |
| MFU 0.5，${u=0.6}$ | 0.037 | 0.086 |
| MFU 0.3，${u=0.9}$ | 0.042 | 0.058 |
| MFU 0.3，${u=0.6}$ | 0.062 | 0.086 |

最好角点 0.025，最差角点（${b=4}$、MFU 0.3、${u=0.6}$）1.38——**同一个模型、同一张卡，运营水平差距就是 55 倍成本差距**。这个数字比任何「模型架构优化」都大一个量级：服务层的调度、批处理与利用率管理，比模型层的省算术更值钱。量化在这张表上的位置也清楚了：int4 权重把访存墙的时间从 4.78 ms 压到约 1.2 ms，访存段的吞吐整体翻四倍——量化省的不是算术，是那趟「读权重」的搬运（§12.6 的 W4A16 在这里的账）。

### $\rm \S \, 20.5.5$ 毛利算例

假设售价 0.50 美元/1M 输出 token：好运营（${b=1024}$、MFU 0.5、${u=0.9}$）成本 0.025，毛利率 95%；差运营（${b=16}$、MFU 0.3、${u=0.6}$）成本 0.35，毛利率 31%。注意即便「差运营」也有毛利——真实世界里把毛利吃掉的是漏项：长上下文请求的 KV 开销、冷启动、突发流量的溢出租金、以及「免费额度与内部用量」。API 定价的常见设计都能从这张表里找到成本侧的影子：输入 token 走 prefill、天然站在算力段，所以便宜；缓存命中的输入连 prefill 都免了，所以更便宜（§12.4 的 prefix cache 定价映射）。

本节小结：batch 决定你离地板多远（最大 147 倍杠杆）、MFU 只在算力段管事、利用率两头都收税；三因子合成的运营差距是 55 倍，比模型优化大一个量级。

## $\rm \S \, 20.6$ 开源权重的经济学：谁在补贴、为什么

白话：把训练几百万美元的权重免费放出来，这不是慈善，是定价策略。看懂「谁在出钱」，才看得懂开源的边界在哪。

1. **云厂商的账**：模型越开源，模型本身越不值钱、跑模型的需求越旺——算力是他们的商品，开源是把「模型租金」转化为「算力租金」的定价武器。
2. **实验室的账**：开源权重买的是生态位——下游开发者在你家模型上微调、蒸馏、建工具，迁移成本就是护城河；附带的人才信号与招聘红利也是实打实的回报。常见打法是「双旗舰」：开源一个次旗舰占生态，闭源旗舰收溢价，两者共享底座技术。
3. **挑战者的账**：榜首位置短期拿不到，就把「够用的免费」做成对收费者的价格锚，压缩对手的 API 溢价空间。
4. **公共部门的账**：科研与主权需求（数据不出境、可审计）要的是权重在手，政府资助与学术声誉在补贴这一档。

### $\rm \S \, 20.6.1$ 权重免费之后：两张新账

第一张是**使用者的运维账**。权重免费，运维不免费：自托管要付卡时（§20.5 的整张表）、要养推理服务团队（§12 的全套）、要自己扛安全补丁。**自托管与 API 的分界在量**：流量小，API 的溢价买走了你的运维成本，划算；流量大到 API 账单超过一张自建集群的折旧加人力，权重开源的模型就是你的成本地板——这也是为什么开源权重的主要受益者是中大型用量客户与云厂商自己。

第二张是**许可账**。「权重开放」不等于「许可无限制」：开源权重许可证对商用、改名再分发、服务条款各有各的约束，有的还按年收入设门槛。拿权重之前读 license 是法务动作，也是成本动作——违反许可的赔偿风险，比省下的 API 费用贵得多。

### $\rm \S \, 20.6.2$ 蒸馏与 API 依赖的战略账

由此推出本章最后一个战略账：**蒸馏与 API 依赖**。用别人的闭源 API 蒸馏自家小模型（§18.5 的文本通道），短期是白捡的老师，长期是三重依赖：能力依赖（老师的代差变成你的天花板）、条款依赖（主流厂商服务条款对「用输出训练竞品」普遍设限，据各家公开条款的常见约定）、成本依赖（API 涨价你没有替代项）。对冲方式就是本节的产业结构本身：把「蒸馏老师」多源化（开源权重教师没有条款问题）、把自托管能力留在手边。蒸馏的 2.9 倍训练账（§18.7）之外，原来还有一张政治账。

本节小结：开源是四类补贴方的定价策略；权重免费、运维与许可不免费，自托管与 API 的分界在流量；蒸馏 API 的便宜里藏着条款与代差两笔隐性负债。

## $\rm \S \, 20.7$ 工程实录：成本车间的师傅账

1. **成本按「卡时 × 利用率」报，不按裸卡时**。现场做法：任何训练或服务的成本汇报都拆成 ${R}$、卡时、${u}$ 三行，利用率单独出曲线。为什么：裸卡时把空闲藏起来了，三个月后复盘「钱花哪了」时对不上账的从来都是 ${u}$；把它单列，问题会自己浮出水面。出处：工业惯例。
2. **新集群先测 MFU 再签大单**。现场做法：拿到集群先跑标准负载（§6 的 profiler 流程）量出真实 MFU，用实测值代入 §20.4 的公式做预算，不用厂商峰值。为什么：峰值与 MFU 之间隔着两到三倍的价差，按峰值签的预算必然超支；实测 MFU 还是硬件质量的验收标准——同型号卡的实测 MFU 离散度大，说明有慢节点（§7 的落后节点检测）。出处：工业惯例（各实验室的集群验收流程）。
3. **每 token 成本进看板，与 PPL 同级**。现场做法：训练看板六条曲线之外（§7.10），服务侧加「每 1M token 成本」与「毛利率」两条，按模型版本与流量分段。为什么：成本回退常常先于质量回退被发现——某版本 batch 打不满、某时段溢出买现货，看板当天就红；等财务月报再发现，损失已经落地。出处：工业惯例。
4. **长尾请求单独算账**。现场做法：把请求按上下文长度分桶（短、中、长、超长），每桶单独报成本与毛利率。为什么：长上下文的 KV cache 把显存吃满、把有效 batch 压小（§12.2 的账），10% 的超长请求可能吃掉一半的毛利；不分桶，这部分被平均数完美隐藏。处置手段是分级定价与长度门槛（工业惯例，各 API 的阶梯定价即此逻辑）。
5. **现货与合约的配比写进风险清单**。现场做法：基线流量的七成走合约锁价，弹性与实验走现货；现货占比、抢占率、checkpoint 恢复演练通过率三项按月复盘。为什么：现货折扣是真的、抢占也是真的，第 7 章那句「checkpoint 是唯一安全带」在账本上的名字就是「抢占率 × 未保存步数 × 重跑单价」。出处：工业惯例。
6. **供应商锁定的对冲留到没出事的时候做**。现场做法：关键管线至少验证过第二条路——另一家云、另一套推理栈、或可自托管的开放权重模型；对冲成本（适配与测试的人工）按保险费入账。为什么：迁移成本在出事当天是天文数字，在平时是几个工程师的两周；CUDA 生态的粘性是真实的，账上要为它留一笔对冲费。出处：工业惯例。
7. **「省钱的三层」按顺序翻**。现场做法：成本优化先动运营层（${u}$ 与 batch，本实测杠杆最大），再动系统层（量化、prefix cache、投机解码，§12），最后才动模型层（蒸馏、小型化，§18）。为什么：三层的工程风险与回报相反——运营层改动小杠杆大，模型层动一次要重训重评；新手常见错误是上来就砍模型，把最贵的选项当第一招。出处：本实测的杠杆排序加工业惯例。
8. **汇率与账期也是成本项**。现场做法：跨境买算力的合同把结算币种与账期写死，大额合约做对冲。为什么：算力合同周期以年计，币种波动与账期占款在真实报表上能吃掉一两个点的「MFU」；这类「非工程成本」在跨国团队是例行议题，纯本地团队常整项漏掉。出处：工业惯例。

本节小结：成本车间的手艺在「把账拆到能被管理」——卡时拆成 ${R}$ 与 ${u}$、MFU 先测后签、长尾分桶、现货配比、锁定对冲、按杠杆顺序省钱、币种账期入表；账拆得越细，钱漏得越少。

## $\rm \S \, 20.8$ 常见错误与证据

1. **按峰值 FLOPS 折预算**。用 989 TFLOPS 除训练 FLOPs 得出「一个月训完」，忘了 MFU 与重跑系数——预算直接少算三到六倍。症状：项目中途申请追加预算。修法：§20.3 的三段账加重跑系数，MFU 用实测值。
2. **把训练账当全部成本**。发布会只报「训练花了多少卡时」，没报数据采购、清洗、人力与评测——对外讲故事可以，自己立项照抄会饿死。修法：三段账分列，比例随规模自查（§20.3.3）。
3. **忽略利用率**。买了卡不等于在产 token：排队、空闲、抢占都按全额计费。§20.5 的角点表里 ${u}$ 是唯一「两头都收税」的因子，从 0.9 掉到 0.6 就是成本涨五成（成本正比于 ${1/u}$）。修法：${u}$ 进看板、按天出曲线（§20.7 第 1 条）。
4. **只算输出 token 的账**。输入 token 的 prefill、长上下文的 KV、缓存未命中的重算，都是成本表外的真实支出；以短问答为主的产品按「输出 token 单价 × 流量」报预算，月末账单能差出一倍。修法：按请求分桶实测，别用单一单价乘总量。
5. **把开源权重当免费**。权重 0 元，自托管的卡时、团队与安全运维照单全收——流量小的团队自托管比 API 更贵。修法：按 §20.6.1 的流量分界先算交叉点，再决定路线；license 条款一并过目。
6. **在访存段调 MFU**。看到「MFU 偏低」的告警就加人调 kernel，结果成本一分不降——因为服务流量小、站在访存墙上，算力本来就闲置。症状：优化立项一个月，${\$}$/1M 纹丝不动。修法：先按 §20.5.2 判断自己站在哪段墙，访存段的杠杆是 batch 与量化。

## $\rm \S \, 20.10$ 应用与辨析

## $\rm \S \, 20.11$ 本章自测答案

> 先闭卷作答 §20.9 与 §20.10，再核对。

### $\rm \S \, 20.11.1$ 关键概念回顾答案

1. 产品周期（新旧卡换代）、需求周期（大项目包走集群）、政策周期（区域性管制造成价差）；租金没有标准价、只有当下此地此量的报价，模型必须把 ${R}$ 留成可调参数。（§20.2.1）
2. 现货换弹性与低价、合约换折扣与保底；可抢占算力把 checkpoint 纪律变成生死线——断一次就丢全部中间进度。（§20.2.2）
3. 算力、数据、人力三段，外加重跑系数 1.2 到 2；重跑来源是 spike 回滚、超参搜索、scaling 阶梯消融与废案。（§20.3）
4. ${7.2\times 10^{23}}$ FLOPs；MFU 0.4 下 505,561 卡时；按 ${R=2.5}$ 约 126 万美元，且这是零失败、满 MFU 的下限。（§20.3.1）
5. ${t(b)=\max\big(N\cdot 2\ \text{字节}/\mathrm{BW},\ 2Nb/(P\cdot\mathrm{MFU})\big)}$，${b^{*}=P\cdot\mathrm{MFU}/\mathrm{BW}}$；decode 的算术强度恰好等于 batch ${b}$。（§20.4.1）
6. ${R}$（市场与采购）、MFU（工程调优）、${u}$（运营管理）；分别由采购、系统、运营三方控制。（§20.4.2、§20.5）
7. 147 倍（3.69 到 0.025）；过 ${b^{*}}$ 后算力墙封顶，吞吐停在 ${P\cdot\mathrm{MFU}/(2N)}$，多攒 batch 只增加延迟不减成本。（§20.5.3）
8. MFU 只在算力受限段起作用（访存段里成本对 MFU 不敏感），利用率 ${u}$ 在两段都全额生效——它是唯一「站哪都收税」的因子。（§20.5.3）
9. 云厂商（模型贬值、算力增值）、实验室（生态位与人才信号）、挑战者（价格锚压缩对手 API 溢价）、公共部门（主权与可审计需求）；分界在流量——API 溢价买走运维成本，量大后自托管的卡时账更划算；此外必须检查许可证的商用与再分发条款。（§20.6.1）
10. 能力依赖（老师代差即天花板）、条款依赖（输出训练竞品的条款限制）、成本依赖（涨价无替代）；对冲：多源化蒸馏老师、自托管开源权重教师、保留自建能力。（§20.6.2）

### $\rm \S \, 20.11.2$ 应用与辨析答案

1. 算力账初判：${C=6\times 15\times 10^{9}\times 3\times 10^{12}=2.7\times 10^{23}}$ FLOPs，约为 8B×15T 的 0.375 倍；MFU 0.4 下约 19 万卡时，租金下限约 47 万美元，乘重跑系数后 60 万到 95 万美元——量级上可能，但只留给算力。必须追问的三笔：数据账（3T token 的采集、授权与清洗预算）、人力账（团队规模 × 时长）、评测与失败重跑的余量；小项目里后两笔反超算力不稀奇。（§20.3）
2. 病因一：利用率下滑（供应商抢占、排队变长）——症状：${u}$ 曲线掉档、现货占比升高。病因二：batch 打不满（流量时段化、长请求挤占显存压小有效 batch）——症状：实时 batch 曲线均值下移、访存段占比升高。病因三：长上下文流量占比上升——症状：请求长度分桶的毛利恶化、KV 显存命中率变化。三种病因的合并特征是「单价涨了而 FLOPs 没涨」——都在 §20.4.2 的漏项清单里。（§20.5、§20.7）
3. 要收集：请求量与增长、上下文长度分布、可用性要求（能否容忍自建故障）、团队运维能力、数据敏感等级。判断公式：自托管月成本≈「所需卡数 × ${R}$ × 730」+人力+冗余，其中卡数由峰值吞吐需求除以单卡吞吐（§20.5.2 主表按其流量结构取数）反推；与 API 月账单比较。分界逻辑：量小、峰值抖动大、要 SLA——API；量大平稳、数据敏感、有运维团队——自托管；中间地带用「API 保底 + 自托管吃基线」的混合。（§20.5、§20.6.1）
4. 解释一：模型更小或训得更少（token 数不同，${6ND}$ 差一个量级很正常）。解释二：算力来源不同（自家集群折旧口径、合约低价、或者只报了卡钱没报数据与人力）。解释三：口径不同（只算最后一次成功运行，重跑系数没进账）。解释四：MFU 与利用率确实更高（工程真功夫）。甄别：追问卡时总量与型号、是否含数据与人力、重跑次数；答不出的按口径问题处理。（§20.3、§20.8）
