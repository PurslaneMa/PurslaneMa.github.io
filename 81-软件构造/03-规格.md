# $\rm Chapter \, 3$ 规格

> **本章假设你已经会**
>
> 1. 静默错误的形状：`"12" + "13"` 得 `"1213"`，异常零个、值全错，见第 1 章 §1.3。
> 2. 预言机的来历：单元测试判定对错的依据要自己写，四条性质预言机得从 spec 的文字里抄，见第 2 章 §2.1 与 §2.3。
> 3. B3 的漏检根因：原地排序的变体返回值完全正确，违约的是「不改输入」这条没进预言机的承诺，三套测试对它的漏检率都是 100%，见第 2 章 §2.3。
> 4. 替身的戏份：桩必须履行被顶替函数的合同，替身该演什么由依赖的 spec 决定，见第 2 章 §2.5。

第 2 章把「合同」这个词用了四次：B3 的抓取率被预言机卡死，预言机该查什么要从 spec 里抄，替身要按合同演戏，而 spec 本身还只是一句写在 docstring 里的中文。一句中文的问题在于它没法被机械地对待：哪句话是要求调用方的、哪句是承诺调用方的、两句话谁更严、改一句算不算破坏老用户，全凭读的人自己掂量。本章把这份合同升级为正式工具：先拆出合同的两种条款，前置条件与后置条件（§3.1）；再把整份合同形式化为一个集合，让「谁强谁弱」「行为等价」变成可判定的问题（§3.2）；然后用锚点实验程序化判定六组有教益的 spec 对的强弱关系，并用 64 个实现的小域穷举校验判定方法的正确性（§3.3）；接着回答合同改动方向的安全问题，「加强前置+加强后置」的替换为什么会让老调用方踩空（§3.4）；最后补上合同里最容易漏的一类条款，副作用（side effect），把 B3 的漏检闭环（§3.5）。本章实验全部在 WSL2（python 3.12.3）上真跑过，脚本与完整输出见本册实验记录 `expSW03/result.txt`，两个脚本总耗时 0.1 秒。

## $\rm \S \, 3.1$ 合同的两种条款：前置条件与后置条件

先立任务。给 `top_pages` 写过测试的人都知道，判定「返回值对不对」之前得先说清「对是什么」，这件事 docstring 里那句中文已经做了，但它同时干了两个性质相反的活。把那句话抄下来拆开读：「k<0 或 k>len(records) 时抛 ValueError」。前半句在说**调用方**：你传进来的 k 必须落在 0 到 len(records) 之间，这不是实现的承诺，是对调用方的要求；后半句「返回 pages 最大的 k 条记录」才是**实现**的承诺。两种话写在一行注释里，工具没法分别对待，测试不知道哪些该抄进预言机，§2.3 的 B3 就是这么漏的。

把两种条款分开命名。**前置条件**（precondition）是调用方在调用前必须保证成立的条件；**后置条件**（postcondition）是前置成立时实现必须兑现的承诺。两者合起来就是一条正式的**规格**（specification，简称 spec），第 2 章已经用过这个名字，从本章起它指这份两条款的合同。把 `top_pages` 的合同按条款誊清：

```text
top_pages(records, k):
    前置：0 <= k <= len(records)
    后置：返回恰好 k 条记录，按 pages 从大到小排序（并列时保持原有先后），
          且返回的每条记录确实来自 records
```

> **经验规则**：这份合同该在写实现之前成文。§2.1 的测试先行要求测试先失败一次来校准自己，而测试的内容全靠从合同里抄，合同缺席时抄无可抄。先立合同、再写测试、最后写实现，三者的次序就是「承诺先于检查、检查先于兑现」的次序；先写完实现再补合同，补出来的多半是实现现状的描红，错也跟着描进去。

最小例子再看一遍这份合同的运行方式，它是双向的义务交换。调用方的义务：保证 k 在范围内；作为交换得到的权利：k 合法时返回值必定满足后置的全部字句，且不必再检查。实现的义务：k 合法时兑现后置；作为交换得到的权利：k 为负或超界时想干什么都行，抛异常、返回垃圾、甚至死循环，合同一概不管。竞赛代码的习惯是把防御做进函数体：`if k < 0: raise ...` 写在实现里。正式 spec 把这件事反过来说：非法 k 根本不在合同管辖内，实现里的 raise 不是义务，只是合同外行为的任意一种。

前置条件省下的是什么？看它的反面：一份没有前置条件的合同，实现必须对**所有**输入给出正确答案。整数域上的开方函数 `sqrt` 就是现成的例子，若合同不设前置，负数输入必须也有「正确答案」，而实数域里无解，整数域里更无解。合同逼着实现处理无解的输入，要么硬造一个错答案，要么自己发明报错规矩。前置条件把这类「无正确答案可给」的输入划出地盘，实现的全部精力花在地盘内。顺带补一句严谨话：x≥0 并没有把无解输入划干净，非完全平方数（如 x=2）在整数域里同样开不出方，严格的前置还应加上「x 是完全平方数」。前置要划到实现真能兑现承诺为止，划得不够细的合同只是把无解从一处挪到另一处。这个道理在标准库函数上到处可见：`list.pop()` 对空表、`dict[k]` 对缺失的键、`"abc".index("z")`，都靠前置条件把不可能兑现的情形请出合同。

> **竞赛生迁移提示**：OJ 题面的「数据范围」段落就是前置条件，n ≤ 10⁶、边权非负，这些话约束的是你的输入，不是判题器的承诺；「输出」段落才是后置条件。竞赛里你从不怀疑这个分工，因为题面把两段用标题分开了。开发里的 spec 缺的正是这两个标题。

合同也有失效边界：它只约束签字的两方。前置外的输入不受合同保护，也不受合同追究，调用方传非法 k 不能怪实现返回垃圾，实现也不用对垃圾负责。这句话听着冷酷，它却是 §3.4 调用方踩空事故的全部根源：合同改了地盘，老调用方还站在旧地盘上。

白话：spec 是一份劳务合同，前置条件是雇主要保证的活儿范围，后置条件是工人在范围内必须交付的质量；范围外的活儿，爱干不干，合同不问。

> 本节小结：spec 由前置条件（调用方的义务、实现的豁免权）与后置条件（实现的承诺、调用方的权利）两种条款构成；前置条件把无解输入划出地盘，让实现不必处理无正确答案的情形；合同只约束签字两方，前置外行为既不保护也不追究。

## $\rm \S \, 3.2$ 行为等价与强弱序：把合同变成集合

「k>len 时抛 ValueError」和「k 超过记录数时报错」是同一份合同吗？「我尽量返回最大的 k 条」比「返回精确最大的 k 条」弱在哪？两个实现都通过了我的测试，它们等价吗？这些问题用中文掂量不出答案，需要给比较一个共同维度。办法是把整份 spec 压缩成一个数学对象：对每个输入 $x$，spec 规定一个**可接受输出集合** $A(x)$，即所有不违约的输出 $y$ 组成的集合。后置条件直接生成这个集合；前置条件管辖外的输入，合同不提任何要求，约定为全输出域：

$$
A_S(x)\;=\;\{\,y \mid \mathrm{post}(x,y)\,\}\,,\qquad \mathrm{pre}(x)\ \text{为假时约定}\ A_S(x)\,=\,Y
$$

读法：$A_S(x)$ 是 spec $S$ 认为输入 $x$ 之下合格的输出集合；$Y$ 是全部可能的输出。一个实现 $f$ 满足 spec $S$，当且仅当它对每个输入交出的答案都落在可接受集合里。满足一份 spec 的全体实现也构成一个集合，记作：

$$
I(S)\;=\;\{\,f \mid \forall x:\ f(x)\in A_S(x)\,\}
$$

拿一个最小例把定义走一遍。spec 取 §3.1 补严谨后的平方根合同（前置：x≥0 且 x 是完全平方数；后置：y²=x 且 y≥0），实现一 $f_1$ 交出 x 的平方根向下取整、实现二 $f_2(x)=x+1$。逐点核对：$f_1$ 在 x=0,1,4,9 处分别交出 0,1,2,3，全部落在各自的 $A(x)$ 里，且非完全平方数处前置为假、合同不管，所以 $f_1$ 满足这份 spec；$f_2$ 在 x=0 处交出 1，而 $A(0)=\{0\}$，一票否决，不满足。满足性是全称命题，一处违约即出局；测试只查有限个点，查不到的点上是黑是白它不表态，这道鸿沟在 §2.3 的 C 行已经见过一次。

有了集合，强弱就有了共同维度。spec $S_2$ **强于** $S_1$（记作 ${S_2 \Rightarrow S_1}$），定义为：每个满足 $S_2$ 的实现都自动满足 $S_1$，也就是 ${I(S_2) \subseteq I(S_1)}$。越强的 spec 圈进的实现越少、对实现越苛刻。对这个逐点式的定义，强弱判定可以进一步化简，不用去数实现，只比集合：

$$
S_2 \Rightarrow S_1\quad\Longleftrightarrow\quad \forall x:\; A_{S_2}(x)\subseteq A_{S_1}(x)
$$

为什么逐点比子集就够了？两个方向各看一眼。若每处 ${A_{S_2}(x) \subseteq A_{S_1}(x)}$，满足 $S_2$ 的实现处处交出 $S_2$ 认可的答案，而这些都是 $S_1$ 认可的，故它满足 $S_1$。反过来，若某处 ${A_{S_2}(x) \not\subseteq A_{S_1}(x)}$，从差集里挑一个 $y$，造一个在 $x$ 处返回 $y$、其余输入处都守 $S_2$ 的实现：它满足 $S_2$ 却在 $x$ 处违反 $S_1$，所以并非满足 $S_2$ 就必满足 $S_1$。§3.3 的实验会用穷举全部实现来证实这个化简没有偷换概念。

两条 spec 互为强弱（两个方向的蕴含都成立）时，称它们**行为等价**（behaviorally equivalent）：从实现与调用的角度看，签哪份都一样，写法可以不同，约束必须相同。行为等价是 spec 层面的概念，别与实现层面的等价混淆：P5 那份「y∈{x, x+1}」的合同下，f(x)=x 与 g(x)=x+1 两个实现都守约，但对调用方而言它们给的结果不同，弱合同给实现留的自由，恰恰以调用方不可依赖具体行为为代价。强弱序与直觉容易顶牛的地方有一处，必须现在钉死：**前置条件的「强」与 spec 的「强」方向相反**。把前置从 x≥0 收窄到 x≥1，对调用方的要求变多了（x=0 不许再传），对实现的豁免变大了（x=0 爱咋咋），这份合同变**弱**了。后置条件的方向才与 spec 一致：承诺越多合同越强。混掉这两个方向，§3.4 的替换判断就会整个翻转。

顺带把第 2 章欠的账记清楚：§2.3 的 B 套件用了四条性质预言机（长度等于 k；返回的 pages 序列不增；选出来的确实是最大的 k 个；调用后输入与调用前相等），前三条都是「${f(x) \in A(x)}$」在具体输入上的展开，第四条的对象是调用后的输入状态，它警告 spec 里还缺一类条款，§3.5 正式处理。

白话：把 spec 想成招聘要求，spec 越强，达标的人越少；前置条件是「报名门槛」，门槛抬得越高，这份要求越好混过去。注意门槛高低和要求松紧说的是两个方向，别混。

> 本节小结：spec 形式化为逐点的可接受输出集合 $A(x)$，前置外约定为全域；强弱 = 满足集包含 ${I(S_2) \subseteq I(S_1)}$ = 逐点子集比较，行为等价 = 互为强弱；前置条件收窄使 spec 变弱、后置条件加强使 spec 变强，两个方向相反，这是后续一切替换判断的地基。

## $\rm \S \, 3.3$ 锚点实验：程序化判定 spec 强弱

上一节把强弱判定化简成了逐点子集比较，但「化简后的方法对不对」要靠动手验证。本节的实验做两件事：其一，把六组有教益的 spec 对形式化为约束集合，程序化判定强弱关系；其二，在一个小域上穷举全部实现，验证「点序子集法」与「直接数实现」两种判定给出相同答案。前者是约束求解问题的穷举简化版，通用的 spec 强弱判定要用 SMT 求解器处理无穷域上的公式，有限域上穷举就够了。

形式化约定写在脚本头注释里：一条 spec 是从输入到可接受输出集合的映射，前置为假时该集合取全域。核心判定代码（完整脚本 `expSW03/exp1_spec_judge.py`）：

```python
def spec(pre, post):
    def S(x):
        if not pre(x):
            return ALL                       # 前置外：合同不约束，什么输出都可接受
        return frozenset(y for y in Y if post(x, y))
    return S

def relation(S1, S2, domain=X):
    s2_implies_s1 = all(S2(x) <= S1(x) for x in domain)   # A2 ⊆ A1：S2 强
    s1_implies_s2 = all(S1(x) <= S2(x) for x in domain)   # A1 ⊆ A2：S1 强
    return s2_implies_s1, s1_implies_s2
```

六组 spec 对按教学意图配置：P1 只加强后置、P2 只加强前置、P3 前置后置都加强、P4 换措辞不改约束、P5 后置留自由度、P6 涉及副作用条款（细节见 §3.5）。运行方式（WSL Bash，当前目录 `expSW03`，只读脚本、输出重定向到 `result.txt`，两个脚本合计 0.1 秒；成功验证是六组判定齐全、末行穷举校验为 True）：

```bash
python3 exp1_spec_judge.py > result.txt
python3 exp2_caller_trap.py >> result.txt
```

实测判定结果一张表收拢（域 X=0..7，Y=−7..7；P6 的域是三个列表）：

| 组 | S1 | S2 | 判定 |
| --- | --- | --- | --- |
| P1 只加强后置 | x≥0，y²=x | x≥0，y²=x 且 y≥0 | S2 更强 |
| P2 只加强前置 | x≥0，y²=x 且 y≥0 | x≥1，y²=x 且 y≥0 | S1 更强 |
| P3 前置后置都加强 | 0≤x≤7，\|y\|=x | 0≤x≤5，y=x | 不可比 |
| P4 换措辞不改约束 | x≤3，y=2x | x≤3，y=x+x | 行为等价 |
| P5 后置留自由度 | y=x | y∈{x, x+1} | S1 更强 |
| P6 副作用条款 | 返回排序结果且输入原样 | 只承诺返回排序结果 | S1 更强 |

逐行读，每行都钉一个结论。

1. P1：y≥0 这半句把 x=4 处的可接受集合从 {2, −2} 压到 {2}，处处收窄、一处未放，判定 S2 更强。加强后置使 spec 变强，方向与直觉一致。（非完全平方数处 y²=x 无解，两份合同的可接受集合同为空集，不影响判定，但可见这两份合同按 §3.1 的标准还欠一道前置。）
2. P2：x=0 一处，S1 的可接受集合是 {0}，S2 因前置为假放开成全域，全域不会是任何集合的子集，判定 S1 更强。加强前置使 spec 变弱，§3.2 钉死的方向反转在这里兑现。
3. P3：两个方向都不成立。x=0..5 段 S2 更苛刻（只收 y=x，不要 y=−x），x=6,7 段 S1 更苛刻（还在管辖，S2 已撤防），谁也包含不下谁，判定不可比。这组的分量到 §3.4 才显出来。
4. P4：y=2x 与 y=x+x 是同一个约束的两种措辞，每处可接受集合逐一相同，判定行为等价。措辞的分歧与约束的分歧是两回事，行为等价只认后者。
5. P5：承诺 y=x 比承诺「y 是 x 或 x+1 之一」严格，后置里留的自由度直接折算成 spec 的弱度，判定 S1 更强。
6. P6：把调用后的输入状态也算进「输出」之后，含「输入原样」条款的合同处处更窄，判定 S1 更强，留到 §3.5 展开。

穷举校验的结果照抄 `result.txt` 原文：在 X={0,1,2}、Y={−1,0,1,2} 的小域上穷举全部 $4^3=64$ 个实现，对四组 spec 对的每个强弱方向（共 8 组判定），分别用「逐个实现检查满足集包含」与「点序子集比较」判定，8 组全部一致，末行打印 `八组判定全部一致：True`。这证实 §3.2 的化简没有偷换概念：不用枚举天文数字的实现，比 8 次集合子集就得到同一个答案。代价也要记账：穷举 64 个实现的脚本整体 0.06 秒跑完，这个代价随域大小指数增长，把域放大到 §2.3 那种 30000 例的规模就已吃力，这正是通用场合需要 SMT 求解器的原因。

P6 的关键数字现在就能看到价值：脚本把 B3 的行为，输入 (3, 1, 2) 被原地排序，产生「返回值 (1, 2, 3)、调用后输入也被改成 (1, 2, 3)」，作为候选输出去查两份合同的可接受集合，实测落在宽松合同的可接受集合内（True）、落在含「输入原样」条款的合同外（False）。B3 在「只承诺排序结果」的合同下是守约实现，在「输入保持原样」的合同下违约。第 2 章 C、D、E 三套测试漏掉它的根因，至此有了精确的说法。

白话：spec 强弱判定像量两份合同谁的管束大，把每条情形下「哪些交货算合格」列成清单逐条比大小就行；穷举全部工人来数谁达标是笨办法但不会错，实测两种办法答案一致，笨办法就退役成了校验员。

> 本节小结：六组 spec 对的程序化判定给出四种结果各一例，加强后置更强、加强前置更弱、双加强不可比、换措辞等价；64 实现穷举证实点序子集法与直接数实现完全一致；B3 的行为对宽松合同守约、对含副作用条款的合同违约，漏检根因闭环。

## $\rm \S \, 3.4$ 替换原则与调用方踩空

判定的意义在改动时兑现。代码库里的合同不是刻在石头上的：实现方要重构、要加缓存、要把「尽量对」升级成「精确对」，每一步都在动 spec。问题是怎么动才不炸。P1 与 P2 的判定结果给出两个方向的单向答案，加上 P3 的组合情形，合同改动的三种走向齐全：

1. 只加强后置：spec 变强，所有老实现自动守新约，但老实现可能交不齐新承诺，重担压在实现方，调用方稳赚。
2. 只加强前置：spec 变弱，实现立省事，重担甩给调用方，站在被撤防地盘上的老客户直接暴露。
3. 前置后置都加强：两股力量顶住，spec 不可比，谈不上变强还是变弱，替换安全性无从谈起。

把两个条款的改动方向合成一张决策表，四种组合各有归宿：

| 前置改动 | 后置改动 | 强弱判定 | 替换安全性 |
| --- | --- | --- | --- |
| 削弱 | 加强 | 变强 | 对调用方安全，实现方补齐新承诺 |
| 加强 | 削弱 | 变弱 | 实现省事，老客户踩空 |
| 加强 | 加强 | 不可比（P3 实测） | 无安全方向，须重谈 |
| 削弱 | 削弱 | 不可比 | 同上 |

后两行为什么不可比，以「削弱+削弱」为例看一眼：地盘扩大让新客户多得好处（这一半朝变强走），后置缩水让老承诺失去保证（这一半朝变弱走），一个方向上有得、另一个方向上有失，集合包含在两处各断一次，判定器如实回答「两个方向都不成立」。决策表的用法是先定方向、再谈收益：任何一次 spec 改版，先在表里找到自己那行，再看这一行的安全性结论接不接受。

真正的安全事故来自第三种，P3 那组「前置后置都加强」就是现场。把故事讲全：老合同 S_old 是 0≤x≤7 且 |y|=x。实现方做了一次自认为双赢的改版，新合同 S_new 是 0≤x≤5 且 y=x，论据是后置从「绝对值对」收紧成「精确值」，承诺更硬了；前置只是把地盘「说清楚」。判定结果是不可比：收紧后置的方向它确实变强了，撤掉 x=6,7 管辖的方向它又变弱了，两股力量顶住，谁也说不比谁强。不可比的合同之间没有安全的替换方向：不能指望它兼容老客户，也不能指望它兼容老实现。

老客户踩空的实测（`expSW03/exp2_caller_trap.py`，输出在 `result.txt`）：按新合同写的两个实现，一个前置外抛 `ValueError`，一个前置外随手返回 −1，脚本的守约核验行打印 `f_raise=True, f_silent=True`，两个都严格满足 S_new。按老合同写的调用方遍历 x=0..7（老合同下全部合法），实测结果：

```text
  [实现一 前置外抛异常] x=6: 老客户当场崩溃 -> ValueError: x=6 超出新合同约定的 0..5
  [实现二 前置外返回-1] x=6: 老客户静默拿错值，期望 |y|=6，实际 y=-1
```

同一个 x=6，两个守约实现给出两种死法：崩溃，或者更糟的静默错值，而后者正是第 1 章 §1.3 那种 180 天后才在审计里现形的形态。两种死法的成本也不同：崩溃自带 traceback，五分钟定位；静默错值没有现场，要等下游对账才能追回来。把事故链条拆开看：调用方没有违约，它按老合同在 x=6 调用；实现方也没有违约，新合同对 x=6 不提任何要求，抛异常和返回 −1 都在新合同的自由裁量权内。唯一的违约发生在改合同那一步：老客户签的是旧约，没人通知它地盘缩了，而指望老客户主动来重读合同不现实，代码库里被调用的模块成百上千，改约方必须按「没人会重读」来设计改动。

这就是**替换原则**（substitution principle）的内容：模块对外的 spec 被替换时，替换必须对调用方安全，判据就是 §3.2 的强弱序。两个方向合起来构成唯一安全通道：**削弱前置、同时加强后置**，spec 单调变强，老调用的一切输入仍在新地盘内，且新承诺只多不少。P3 那种双加强改出了不可比合同，两头不讨好；只加强前置更是直接把老客户请出地盘。

工程上的分寸也要说清：spec 不是越强越好。P5 判定「y∈{x, x+1}」更弱，可弱是它的功能，后置里留的自由度是留给实现方的活动空间，前置里留的地盘是留给调用方的便利。合同是两方谈判的结果，替换原则管的是「改动不伤对方」，不管「往哪个方向改是进步」。

> **竞赛生迁移提示**：你在 OJ 上见过这类换约。题面更新把数据范围从 n ≤ 10⁵ 收紧到 n ≤ 10³、同时把时限砍半，这是一次「加强前置+加强后置」的合同改版：老题解在新题面下重新评测，范围收窄对老客户无害甚至有利，砍半的时限却可能直接判 TLE（踩空），而出题人对范围外行为不负任何责任，与 x=6 的遭遇同构。

白话：改合同像商场改营业时间，只许「营业更久、服务更多」，不许悄悄关门；「范围缩小但质量更高」听起来两全，实际上既有老顾客被关在门外，又没人能说清新店到底算升级还是缩水。

> 本节小结：加强后置对调用方安全但压实现方，加强前置对实现方省事但调用方踩空，双加强得到不可比合同、无安全替换方向；实测两个都守新约的实现让老客户在 x=6 分别崩溃与静默错值；唯一安全通道是削弱前置+加强后置，即 spec 单调变强。

## $\rm \S \, 3.5$ 副作用条款：没写的就是允许的

P5 与 P6 之间隔着合同起草的一条基本原则。先给它命名：合同约束没写到的行为，实现享有完全自由，这叫**未完全确定规格**（underdetermined specification）。这个词听起来像缺陷，其实是 spec 的核心设计。P5 判定 y=x 比「y∈{x, x+1}」更强，弱的那份给实现留了选择余地，留白越多的合同实现越好做，这是留白的正面。留白的反面在 P6：把输入状态也算进「输出」之后，对比「返回排序结果且输入保持原样」与只承诺「返回排序结果」两份合同，实测后者更弱。只承诺排序结果的合同里，调用后输入是什么没有任何条款约束，于是按留白原则，**改成什么都行**。

这里要正式定义本章开头预告的现象。**副作用**（side effect）指函数对返回值之外、调用方可见状态的影响：修改传入的参数、改全局变量、写文件，都算。关键纪律是一条：**副作用必须写进合同，没写的就是允许的**。直觉上「我调 sort 是为了拿排好序的结果，你顺手改我的输入总不算违约吧」，合同的语言里没有「顺手」二字：条款只说返回排序结果，输入被改就属于未约束地带，实现自由。B3 正是这样一位守约公民，P6 的实测行给出判定：它产生的结果落在宽松合同的可接受集合里（True），落在含「输入原样」条款的合同外（False）。第 2 章 C、D、E 三套测试对 B3 的漏检率 100%，根因至此闭环：不是测试没写好，是预言机抄的那份合同漏了条款，测试再密也只能抽查合同写下的承诺。

起草一份完整的 spec 因此有一个固定格式的条款清单：前置（requires）、后置（ensures）、副作用（modifies），第三项专门声明函数有权动哪些调用方状态，清单之外的动不得。把 §3.1 誊清的 `top_pages` 合同补全成三段格式：

```text
top_pages(records, k):
    requires: 0 <= k <= len(records)
    ensures:  返回恰好 k 条记录，pages 从大到小，并列保持原序，每条来自 records
    modifies: 无（records 在调用前后逐元素相同）
```

第 2 章预言机抄的四条性质与这三段条款正好对上：长度等于 k、序列不增、确实选了最大的 k 个，三条是 ensures 的逐句展开；「调用后输入与调用前相等」一条是 modifies 的展开。§2.3 表格 C 行漏掉 B3 的那一格，在 modifies 条款出现后被填上了。modifies 的性质也要说准：它是**申报**而不是许可，写「modifies: 无」是承诺什么都不动，写「modifies: records」是申报只动 records，调用方据此决定要不要做防御性拷贝；申报写得越宽，调用方设防的成本越高，与前置条件一样，这里同样存在两方之间的分寸。倒过来读也成立：一条副作用都没写的 spec，等于授权实现任意改写调用方的世界，这份授权书多数起草者并不想签。

白话：合同不写的就是允许的，这条原则对「宽松点好实现」是润滑剂，对「忘了写副作用」是定时炸弹；调用方读到一份没提改不改输入的合同，只能按「会改」设防，要么合同补条款，要么调用方做防御性拷贝，两头总得有一头付账。

> 本节小结：未完全确定规格意味着合同留白处实现自由，留白是 spec 的功能而非缺陷；副作用是对返回值之外调用方可见状态的影响，必须显式写进 modifies 条款；实测 B3 对缺条款合同守约、对含条款合同违约，第 2 章的 100% 漏检根因闭环。

## $\rm \S \, 3.6$ 关键概念回顾

1. 前置条件和后置条件分别是谁的义务、谁的权利？一份没有前置条件的整数开方合同，实现方会多出什么负担？
2. 把前置条件从 x≥0 收窄到 x≥1，spec 变强了还是变弱了？用 P2 的实测判定结果支持你的回答。
3. 为什么强弱判定可以化简成逐点的可接受输出集合比较？用「从差集里挑一个输出造反例」的论证说明反方向为何成立。
4. P3 的两条 spec 为什么不可比？「双加强」的改版在 x=0..5 和 x=6,7 两段上分别朝哪个方向动了强弱？
5. 替换原则的安全通道是哪个方向？老调用方踩空的直接原因是什么，为什么说两个实现都没有违约？
6. 什么是未完全确定规格？它对实现方的正面价值和对调用方的风险各是什么？

## $\rm \S \, 3.7$ 应用与辨析

1. 同事把 `merge(left, right)` 的 spec 从「返回合并排序结果」改成了「返回合并排序结果，且两表含相等元素时 left 中的排在前（稳定）」。这个改动朝哪个方向动了强弱？老调用方会不会踩空？老实现还能继续用吗？
2. 你要给一个「从字典取值，缺失时返回默认值」的函数 `get(d, k, default)` 写 spec。写出前置、后置、副作用三段条款；再说明如果漏写副作用段，调用方按 §3.5 的原则只能怎么设防。
3. 有人主张「把 spec 写得越强越好，反正承诺多是好事」。用 P5 的判定结果与 §3.4 的分寸说明这个主张哪里错；再给出一个应当主动加强后置的真实场景，并说明那个场景里加强的代价与收益。

## $\rm \S \, 3.8$ 本章自测答案

概念回顾答案：

1. 前置条件是调用方的义务、实现的豁免权；后置条件是实现的义务、调用方的权利。没有前置条件的整数开方必须对负数也给出「正确答案」，而负数开方无解，实现要么硬造错答案、要么自创报错规矩，处理无解输入的负担全压在实现方（来源：§3.1）。
2. 变弱。P2 实测判定 S1 更强（x≥0 那份更强）：x=0 处收窄版的前置为假、可接受集合放开成全域，全域不是 {0} 的子集，满足收窄版的实现不再自动满足原版。前置条件的「强」与 spec 的「强」方向相反（来源：§3.2、§3.3）。
3. 强弱定义为满足集包含：满足 S2 的实现都满足 S1。逐点比子集是它的充分条件；必要性靠反例构造，若某处 ${A_{S_2}(x) \not\subseteq A_{S_1}(x)}$，从差集挑一个 y、让实现只在 x 处返回 y、其余处守 S2，就得到满足 S2 却违约 S1 的实现。64 个实现的穷举校验证实两种判定 8 组全部一致（来源：§3.2、§3.3）。
4. x=0..5 段 S2 更苛刻（后置只要精确值，不要负根），x=6,7 段 S1 更苛刻（S1 还管辖、S2 已撤防），两段方向相反，两个方向的集合包含都不成立。双加强是「半边变强半边变弱」，合成不可比（来源：§3.3、§3.4）。
5. 安全通道：削弱前置、同时加强后置，spec 单调变强。踩空的直接原因是老调用方的输入落到了新前置之外，从此进入合同不约束的地带；两个实现都没违约，因为新合同对 x=6 不提任何要求，抛异常与返回 −1 都在新合同的自由裁量权内，违约的是「改了合同却不管老客户」这一步（来源：§3.4）。
6. 未完全确定规格指合同未约束的行为实现享有完全自由。正面：留白给实现活动空间，弱 spec 门槛低，实现替换起来余地大；风险：调用方不能依赖任何未写明的行为，包括输入不被修改，没写就是允许改，调用方要么按「会改」设防、要么逼合同补条款（来源：§3.5）。

应用与辨析答案：

1. 后置条件加强（多承诺了稳定性），前置未动，spec 单调变强。老调用方不踩空：一切老输入仍合法，新承诺只是把原来未写明的行为升级成书面条款，老客户按旧约做的检查照常通过。老实现未必能继续用：返回不稳定合并结果的实现不再满足新 spec，是否要换实现取决于现有实现是否恰好稳定（来源：§3.4）。
2. 条款：前置是 d 是 dict（若团队有并发约定，再加「调用期间 d 不被其他线程修改」）；后置是 k 在 d 中时返回 d[k]，否则返回 default；副作用是不修改 d，也不修改 default 若它是可变对象。漏写副作用段时，按未完全确定规格原则，调用方只能假定 d 与 default 都可能被改：要么先做防御性拷贝再调用，要么在代码评审时要求合同补上 modifies 条款，两头总有一头付账（来源：§3.5）。
3. 错在把「强」当无条件优点：P5 实测「y=x」更强，但弱的那份留给实现的选择余地正是实现方的活动空间，无脑加强后置等于没收实现自由，可能逼走所有负担不起精确承诺的实现、抬高成本；spec 是两方谈判的结果，替换原则只管改动不伤对方，不管方向是否进步。应当主动加强后置的真实场景：调用方开始依赖某个未写明的行为（比如一直拿到的都是稳定结果），此时把该行为写进后置是把事实约定升级成书面承诺，代价是收敛实现自由，收益是调用方不再依赖口头传说（来源：§3.4、§3.5）。

**你现在能做什么**：拿起你写的任何一个函数，你能在两分钟内把它的 docstring 拆成前置、后置、副作用三段条款，并对「这版改动是否安全替换旧版」给出强弱方向上的判断。

函数级合同到这里立住了：条款怎么写、强弱怎么判、改动怎么不伤人。但 spec 一直只管单个函数的进与出，还没管过「一组函数共享的那份数据如何不被人改坏」，那是下一章的对象：抽象数据类型、表示不变量与抽象屏障，合同从函数层升级到类型层。
