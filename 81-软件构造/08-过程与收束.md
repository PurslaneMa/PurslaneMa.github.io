## $\rm \S \, 8.1$ Git 哲学：把「改坏了就回去」变成常态

先立任务。OJ 上不存在这个问题：一份代码提交判题，判完就完。工程里的代码要被改几十次、几百次，每一次改动都可能把改之前的好状态毁掉，而「改之前长什么样」如果没被存下来，就永远找不回来。改动的全部风险可以压成一句话：回不去。

Git 的哲学一句话说完：**把「这一刻全部论证都成立」变成可验证的检查点，把「改坏了」变成可回退的普通事件**。机制第 7 章已经用过一半：**提交**（commit）是带父指针的完整快照，一串提交链出一条可以任意回走的历史，命令层《Git与团队协作》§19.1 与 §19.4 已经给过，这里补它的哲学账，三条纪律：

1. **每个提交都应当通过全部测试**。测试全绿才提交，历史就成了一条每个点都被验证过的链。这不只是洁癖：§7.3 的二分调试整条建立在这上面，好与坏沿提交历史单调的前提，就是每个提交都处于「被测试判过」的状态。混进去一个测试全红的提交，单调性就破了，二分会把分界线指到错的地方。
2. **改坏了就回退，不现场抢救**。发现新提交引入了问题，第一反应用可恢复的撤销（`git revert`，§19.4）回到验证过的状态，再离线排查；在坏代码上直接改改看，是 §7.1 批评过的老毛病换了个场合。
3. **变更在分支里隔离**。分支是同一项目的平行世界（§19.3）。重构恰恰是最需要隔离的改动：它要动很多文件，行为上却应当零变化，动到一半必然两头不靠。开分支让主干始终保持测试全绿，重构分支上重新全绿才合并。

三条纪律落到日常操作上长这样（Bash，仓库根目录；每条命令动哪个对象写在注释里，成功验证是合并前 `git log` 里主干的每个提交都对应一次测试全绿）：

```bash
git checkout -b refactor-dedup        # 开分支：在平行世界里动结构，主干不动
# ……小步重构：每拆出一个小函数、补一支合同测试，就跑一遍测试套件……
git commit -am "拆出 dedup_key，补键定义单元测试"   # 全绿才提交，打一个检查点
git checkout main                     # 回主干：主干自始至终没见过半成品
git merge refactor-dedup              # 分支上重新全绿，才合并回来
```

提交还有一条尺寸纪律：**小步提交**。检查点打得太稀，回退时要扔掉的好工作就多，§7.3 二分调试的分界线精度也随提交粒度下降（同样的历史，10 个提交只能定位到十分之一区间，100 个提交能定位到百分之一）。小步的代价是提交信息要多写几十个字，买回的是定位与回退的双向精度。

第三条把本章的核心问题顶到了面前：合并前「测试全绿」是必要条件，它够不够？重构成什么样才算成？这两个问题分别是 §8.2 与 §8.3 的任务。

白话：Git 像游戏的存档系统，每个存档点都验过伤才能存；打 Boss 打残了读档重来，不丢进度也不丢脸。不存档就硬闯的玩家，死了只能从头练起。

> 本节小结：提交是带父指针的快照，三条纪律把时间维度变成论证的一部分：全绿才提交、坏了先回退、变更在分支隔离；测试全绿是重构的必要条件，不是充分条件。

## $\rm \S \, 8.2$ 锚点实验一：重构的判据与缺陷注入的存活率

**重构**（refactoring）指在不改变可观察行为的前提下改善代码的内部结构。判据有两半：行为不变，结构变好。本节先钉第一半：行为不变怎么证明？直觉答案是「跑一遍现有测试」，这个答案差多少，用实验量出来。

场景取论文资料管理器的管道：同一份 spec（输入含 title、year、pages 的记录列表，标题规整为去空格加小写，按规整标题与年份去重、每组保留首次出现，返回 pages 最大的 k 条、并列保持原相对顺序，返回新列表不改输入）。两版实现：一版按前六章的工序写，五个小函数各带合同（规整、去重键、去重、选前 k、拼装）；另一版是重构要逃离的样子，一个长函数把全部逻辑内联，就地改写输入，没有任何条款。第 0 步先做等价校验：两版对独立预言机在 300 组随机输入上全部一致，但坏味道版带着 §3.5 预言过的病——返回值完全正确，调用者的输入却被就地改写（title 从 `'AI'` 变成 `'ai'`），副作用没写进任何合同。

**代码坏味道**（code smell）指暗示深层结构问题的表面症状，长函数、就地改写、无合同都是典型。实验一的问题：坏味道只是难看，还是会真金白银地放走缺陷？做法：往两版各注入同一组 8 个语义缺陷，一次一个；给两版等预算的 24 个测试。坏味道版 12 个黑盒端到端加 12 个随机典型端到端（长函数没有缝，只能从外面堆端到端用例）；重构版同样 12 个黑盒，另 12 个换成按小函数合同定向投放的单元测试。每个缺陷的生死判据：24 个测试里任一失败即为抓到。实测（`expSW08/exp1_defect_injection.py`，种子固定，输出在 `result.txt`）：

| 注入缺陷 | 坏味道版（12 黑盒 + 12 典型端到端） | 重构版（12 黑盒 + 12 单元） |
| --- | --- | --- |
| B1 去重保留最后一次出现 | 抓到：typ03、typ06 | 抓到：u01、u02、u04、u10 等 4 处 |
| B2 并列时顺序反转 | 漏检 | 抓到：u05（稳定条款单元测试） |
| B3 pages 按字符串比较 | 抓到：bb02 等 3 处 | 抓到：同 3 处加 u06，共 4 处 |
| B4 先选后去重 | 抓到：bb06 | 抓到：bb06 加 u10，共 2 处 |
| B5 去重键漏了去空格 | 漏检 | 抓到：u02、u09 |
| B6 去重键漏了年份 | 漏检 | 抓到：u03、u09 |
| B7 降序写成升序 | 抓到：10 个黑盒用例 | 抓到：同 10 处加 u06、u08、u10，共 13 处 |
| B8 空输入返回 None | 漏检 | 抓到：u11（空输入单元测试） |

汇总行：坏味道版抓到 4/8、存活 4/8（存活率 50%）；重构版抓到 8/8、存活 0/8（存活率 0%）。数字要读出两条机理，不能只读胜负：

1. **抓到不是运气，是缝**。重构版抓到的缺陷大多由单元测试钉住，失败名单直接指认违反合同的函数：B6（键漏年份）被 `u03_dedup_year` 与 `u09_key_direct` 抓住，测试名就是被违反的条款名。坏味道版即便被抓，失败信息也只有「流水线输出与预期不符」一句，它只有一条外壳合同，案子破不了只能含糊结案。
2. **漏检有形状**。坏味道版放走的 4 个缺陷（B2、B5、B6、B8）撞在同一堵墙上：端到端用例按「真实数据长什么样」取样，看不见内部结构，等价类（§2.2）挑不中「并列页数」「带空格标题」「空列表」这类要知道合同才觉得可疑的输入。单元测试能抓，是因为合同把「可疑」写明白了：稳定条款、键的定义、空输入的后置条件，一条测试盯一条。抓死 B2 与 B5 的两支测试长这样（摘自实验脚本）：

```python
def u_topk_tie_stable(bug):
    # 合同：并列 pages 时保持原相对顺序。三条全并列，前两名必须是 a、b
    src = [R("a", 2000, 5), R("b", 2000, 5), R("c", 2000, 5)]
    got = top_k(deepcopy(src), 2, bug)
    assert [r["title"] for r in got] == ["a", "b"]

def u_key_direct(bug):
    # 合同：去重键 = (规整标题, 年份)。直接喂一个带空格、大写的标题核对键值
    assert dedup_key(R(" AI ", 2020, 1), bug) == ("ai", 2020)
```

第一支把「并列」造成常态而不是巧合，专钓违反稳定条款的实现；第二支绕过整条管道，直接核对去重键这个最小合同单元，B5 与 B6 两个键缺陷在它面前无处藏身。这两支测试在坏味道版上根本无法编写：长函数没有「键」这个可以单独调用的缝，想核对键定义只能从头跑到尾。

对照还有一个容易忽略的公平性设计：两版预算相同，各 24 个测试。不等预算的对照会把「测试更多」误记成「结构更好」的功劳；等预算之下，剩下的唯一解释是同样的测试数量，单元版用在了合同指定的地方。

### 排查实录：汇总行为什么和明细表打架

这组数字进入本册之前，先讲一段它自己经历的排查，它是 §7.1 循环的现成教材。现象：初版输出的明细表里，重构版 8 行全部写着「抓到:u01……」带测试名单，紧随其后的汇总行却是「重构版：抓到 0/8，存活 8/8（存活率 100%）」。两份证据出自同一次运行，不可能同时为真，明细与汇总必有一个在撒谎。按循环走：

1. **复现**：实验种子固定，重跑输出逐字相同，是确定性错误，不用拉宽窗口。
2. **假说一**：汇总只把黑盒端到端算进重构版、漏了单元测试。这是第一嫌疑，因为两版的测试构成确实不同。检验：读统计代码，重构版的失败名单 `fr` 先由黑盒端到端填入，紧接着 12 个单元测试的失败也并进同一个 `fr`，明细表里 u 开头的名单正是从这个 `fr` 打出来的。同一份名单既喂明细又喂汇总，漏算假说被排除。
3. **假说二**：累加判据反了。看汇总行上游的两行：

```python
tot_s += (not fs)    # fs 是失败测试名单：非空 = 抓到
tot_r += (not fr)
```

`not fs` 在名单为空、也就是**存活**时才为 True。计数器累加的是存活数，打印时却标着「抓到」：统计口径整个反了。
4. **解释与修复**：坏味道版抓到 4、存活 4，两个口径数值恰好相等，那一行碰巧看不出毛病；重构版抓到 8、存活 0，被印成 0/8 与 100% 存活，与明细正面相撞。修复是把两行改成 `bool(fs)` 与 `bool(fr)`，重跑后汇总与明细自洽。回归动作与其说是补测试，不如说是立合同：汇总统计自己也是代码，它对读者的承诺是「与明细一致」，验证手段是让两种来源对账，正如 §2.1 的预言机必须独立于实现，一个数字若只有一个来源，它撒谎时无人对证。

白话：明细表像证人逐个出庭，汇总像书记员的一句总结；书记员把「无罪」记成「有罪」，八个人全招供了他说全员释放。核对的办法老一套：让总结和证词当面对质。

> **竞赛生迁移提示**：OJ 上没有重构，但对拍思想与这个实验同构：暴力解当预言机、随机数据抽查，就是黑盒端到端测试。工程多出来的一步，是把预言机的知识按合同拆给单元测试，让每支测试只盯一条条款。对拍只回答「对不对」，工程的测试还要回答「谁违反了什么」。

> 本节小结：重构判据的前一半「行为不变」靠测试保证，但测试的抓取力取决于长在哪：端到端抽查外壳，单元测试按合同定向设卡，实测等预算下存活率 50% 对 0%；汇总数字也是代码，口径反了比不统计更骗人，明细与汇总互相独立，必须对账。

## $\rm \S \, 8.3$ 锚点实验二：圈复杂度是烟雾报警器

重构判据的后一半「结构变好」需要一个可数的量，否则「更好」退化成口味之争。**圈复杂度**（cyclomatic complexity）是沿用最广的一个：数控制流里的判定点（if 与 elif、复合条件、循环），每个判定点给代码一条多出来的路。它为什么值得数？先做机理演示（`expSW08/exp2_complexity.py` 的 A 部分）：造 60 个合成模块，判定点数从 1 到 12 不等，每个判定点以 ${q = 0.1}$ 的概率独立藏一个缺陷，则一个模块的缺陷数期望满足：

$$
\mathbb{E}[D] \;=\; q \cdot d
$$

读法：$D$ 是一个模块的缺陷数，$d$ 是它的判定点数，$q$ 是每个判定点藏缺陷的概率。实测 41 个缺陷、平均每模块 0.68 个，对上理论值 ${q \cdot \mathbb{E}[d] = 0.62}$；按组拟合斜率 0.091，对理论 0.100；分组缺陷密度从判定点 1 到 2 组的 0.10 一路爬到 11 到 12 组的 1.14（摘自 `result.txt` 的 A 段）：

```text
  分组缺陷密度（每模块平均缺陷数）：
    判定点  1- 2：n=10  密度 0.10  （理论 0.15）
    判定点  5- 6：n= 9  密度 0.78  （理论 0.55）
    判定点 11-12：n= 7  密度 1.14  （理论 1.15）
  同组方差演示：判定点=8 的模块实测缺陷数分布 [0, 1, 1, 0, 1, 0]
```

皮尔逊相关 ${r = 0.299}$，弱相关：缺陷还有大量与判定点无关的来源，圈复杂度只解释其中一角。最要紧的一组数字是同组方差：判定点同为 8 的 6 个模块，实测缺陷数 ${[0, 1, 1, 0, 1, 0]}$。度量给期望，不给命运：判定点多不是必坏，是每模块的期望坏账更高，它是利率，不是判决书。

机理立住了，再看它在真实代码上量出什么（B 部分，AST 实测）。同一 spec「每月天数」两版实现：if 链版圈复杂度近似 15（1 加 12 个月分支，再加闰年判断与复合条件）；表驱动版把 12 个月的分支全部变成字典数据，圈复杂度降到 5，数据出了控制流，只剩闰年判断。行为对账：两版对 60 组（年、月）输入与 calendar 预言机逐组一致。但这笔账要诚实地读：可写错的条目，if 链版是 13 个返回常量，表版是 12 个字典值加一个闰年式。缺陷机会没有消失，只是从控制流挪进了度量看不见的数据里。

盲区演示（C 部分）把这句话钉死：往表驱动版塞一个错条目「4 月 31 天」，圈复杂度纹丝不动仍是 5，一个分支都没多；可 `days_in_month(4, 2023)` 返回 31，calendar 预言机说 30，行为已坏。结论一句话：圈复杂度是烟雾报警器，告诉你哪里容易着火；它不是验收员，判断不了有没有着火。验收的岗哨还是 §2 的测试与 §7.4 的断言。三者的分工：度量回答「哪里要多看一眼」，测试回答「这里对不对」，重构时先让度量挑出热点、再让测试守住房间，两件工具接力而不是互相替代。

复现方式（WSL Bash，当前目录为本册实验记录 `expSW08`，两个脚本输出合并重定向到 `result.txt`，全程不足 1 秒；成功验证是第 1 步汇总「坏味道版 4/8、重构版 8/8」且与明细逐行对得上，A 部分斜率落在 0.09 到 0.10，C 部分「复杂度仍 5、行为已坏」两行同时成立）：

```bash
python3 exp1_defect_injection.py > result.txt
python3 exp2_complexity.py >> result.txt
```

落地姿态也有讲究：圈复杂度适合挂进持续集成当**趋势线**而不是红线。设一条硬阈值（比如超过 15 就拒绝提交）会逼出把一个分支硬拆成十行 if 的花招，判定点少了、可读性反而更差；趋势线只回答「这个模块是不是在变糟」，把注意力引向增量最大的改动，判断仍留给人。度量进流程的位置与 §7.4 的日志同级：它提供信号，不代替决策。

白话：圈复杂度像老城区的火灾风险地图，标出哪几条巷子电线老化、该优先检修；但今天有没有着火，得靠烟感和巡检（测试与断言）说了算，地图不报警。

> 本节小结：圈复杂度数判定点，实测缺陷数随它近似线性增长（斜率 0.091 对理论 0.100），它指出重构值得下手的热点；但同组方差与数据缺陷盲区证明它给期望不给判决，行为不变的最终验收永远是测试与断言。

## $\rm \S \, 8.4$ 全册收束：六件套合同地图

本章是本册最后一章正文，把前七章收成一张地图。全书的心智模型只有一句话：**正确性是论证出来的，spec 是合同，测试是抽查，抽象屏障是防火墙**。六件套各守一段论证：

| 工序 | 首次立约 | 管什么 | 一句话合同 |
| --- | --- | --- | --- |
| spec | §3.1 | 函数的进与出 | 前置、后置、副作用三样写全，没写的就是允许的 |
| 测试 | §2.1 | 合同的抽查 | 预言机独立于实现，覆盖率不等于抓取率 |
| ADT 与 RI | §4.2 | 共享数据的边界 | 构造器建立、每个操作保持，checkRep 站岗 |
| 接口 | §5.1 | 变更的隔离 | 调用方只认操作集合，不认实现，实现才换得动 |
| 并发 | §6.6 | 多只手 | 「线程安全」必须写明承诺的是哪一种 |
| 调试 | §7.1 | 论证的漏洞 | 假说检验，一次一个变量，修完回归 |

六件套不是并排的六个工具箱，是一条流水线上的六道工序：写 spec 定条款，测试先行让预言机从 spec 抄而不是从实现抄，实现时 RI 与 checkRep 守内部，接口把会变的轴隔离出去，并发场景给合同补上交错条款，全绿提交打一个快照检查点，出事了按第 7 章兜底。Git 的快照链（§8.1）垫在流水线底下，每转一圈留下一个可回退的点：

```mermaid
flowchart LR
    S[spec 定条款] --> T[测试先行<br>预言机从 spec 抄]
    T --> I[实现<br>RI 与 checkRep 守内部]
    I --> F[接口隔离变更]
    F --> C[并发补交错条款]
    C --> G[全绿提交<br>快照检查点]
    G -->|出事| D[调试兜底<br>假说检验]
    D -->|回归成测试| T
```

末尾那条回到「测试先行」的回路就是第 7 章 §7.1 的回归步骤：每次故障修完都变成一支新测试，流水线转一圈，防线厚一层。

再往深压一层，六件套其实是同一件事在六个尺度上的重复：**立合同，独立验证，留失效边界**。spec 立合同，测试独立验证它，前置条件划定失效边界（调用方违约后果自负）；RI 立合同，checkRep 独立验证它，抽象屏障是失效边界（防火墙外的代码碰不到 rep）；线程安全条款立合同，§6.5 的四份实现对账独立验证它，锁与不可变是失效边界。以后遇到任何新工序、新框架、新语言，先找这三样，找到就算入了门。

白话：六件套像一场官司的完整流程：spec 是写清的契约，测试是举证，ADT 与接口是法庭纪律，并发是多方签合同，调试是案发后的侦查，Git 是卷宗归档，每一页都可回查。

> 本节小结：六件套在流水线上各守一段：spec 定条款、测试做抽查、ADT 守数据、接口隔变更、并发补交错、调试兜底；贯穿的心智模型是合同、抽查与防火墙，三样东西（合同、独立验证、失效边界）在六个尺度上重复出现。

## $\rm \S \, 8.5$ 全站接口：这套论证在整站的位置

本册讲的是单机、单进程、小团队尺度上的正确性论证。走出这个尺度，其余各册把同一套论证方式接了过去：

1. **《Git与团队协作》§19**：本册第 7、8 两章时间维度的底座。快照链（§19.1）、可恢复撤销（§19.4）、`git bisect`（§19.7）的账本册已经补过；§19.9 的 pre-commit hook 值得专门回头一看：它把 §7.6 审查清单里机械可查的条目（调试代码、格式）交给提交前的自动脚本，人只审判断题，清单里机器能管的都不该浪费人眼。
2. **《数据库系统》§6**：事务的 ACID（§6.2）把「一组 UPDATE 要么全做要么全不做」的原子性合同卖给存储层去兑现，WAL（§6.4）与回滚实测（§6.5）是兑现的方式。与本册 §6.3 的锁对照着读：应用层的锁护复合操作，存储层的 WAL 护跨语句原子性，同一主题的两层。
3. **《计算机网络》§1.3 与 §8.4**：协议就是两台机器之间的 spec。分层模型（§1.3）给每层一句职责，正是「一个抽象屏障一层合同」的网络版；报文边界（§8.4）讲 HTTP 怎么在字节流上切消息，前置条件是报文格式。网络合同的特别之处在失效方式：违约不抛异常，而是连接挂起或解析错位，没有 traceback 替你报信。
4. **《操作系统》§6.5 与 §6.7**：本册 §6.3 站在用锁者的位置记了两笔账；锁怎么用原子指令造出来（自旋到睡眠的三层实现）与粗锁细锁的权衡，OS 册已经算完，两边拼起来才是并发问题的完整答案。
5. **《计算机安全》§1.3 与 §8.1**：最小权限原则是「没写的权限就是没有」这条 spec 纪律在权限上的推广；依赖树放大账（§8.1）提醒你签收的合同不止自己写的，每个第三方依赖都是别人递来的 spec，条款在黑箱里兑现，所以入口要按最小权限收窄。

下一站是本册的复习总结：把六件套闭卷取出来，跨章交错排练，然后带着这套论证去读整站其余各册。

白话：本册教的是在自家院子里立规矩，其余各册讲的是外面的世界怎么执行同样的规矩：数据库替你守原子性，网络把合同写进报文，操作系统造好锁递给你，安全册提醒你门外的合同未必善意。

> 本节小结：走出本册尺度，同一套「立合同、独立验证、留失效边界」换了场地继续成立：Git 管时间、数据库管原子性、网络把合同写进协议报文、操作系统造锁、安全册管黑箱依赖；读它们时先找这三样，就能把新知识挂到这张地图上。

## $\rm \S \, 8.6$ 关键概念回顾

1. 重构的两个判据各是什么？「行为不变」由什么保证，「结构变好」由什么度量？测试全绿在其中占什么位置？
2. 缺陷注入实验里，重构版 8/8 对坏味道版 4/8 的差距来自哪里？端到端测试放走的四个缺陷有什么共同形状？
3. 汇总口径 bug 的根因是什么？坏味道版那一行为什么碰巧没错？这个案例给「汇总数字」立了什么合同？
4. 圈复杂度度量什么、不度量什么？「烟雾报警器不是验收员」分别对应 §8.3 的哪两组实测？
5. 六件套各自的一句话合同是什么？它们在流水线上按什么顺序排，Git 的快照链在流水线的哪个位置？

## $\rm \S \, 8.7$ 应用与辨析

1. 同事说：重构不用写新测试，跑一遍现有测试全绿就能合并。用 §8.2 的实验说清他漏了什么；再想一步，什么情况下他恰好是对的？
2. 一个 800 行的长函数，圈复杂度 87，现有测试全绿。给出重构的操作顺序：先立什么、再拆什么，每一步分别靠什么保证没改坏？
3. 把排查实录的教训变成机器检查：给实验一的汇总写一个自动对账脚本，至少两条核对。分别核对什么、什么情况算违约？

## $\rm \S \, 8.8$ 本章自测答案

概念回顾答案：

1. 两判据：可观察行为不变，内部结构变好。前者由测试与断言保证，后者由圈复杂度这类度量指出热点、由代码审查判断结构是否真的变好。测试全绿是必要条件，实验一证明它远不充分：等预算下坏味道版也有 4/8 存活（来源：§8.2、§8.3）。
2. 差距来自测试长在哪：单元测试按合同定向投放，失败名单直接指认违约函数；坏味道版只有外壳合同，只能靠端到端撞。放走的四个缺陷全是要知道合同才觉得可疑的输入形态：并列顺序、键漏去空格、键漏年份、空输入的后置条件（来源：§8.2）。
3. 根因是累加判据反了：`not fs` 在存活时为 True，计数器累加存活数却打印成抓到数。坏味道版抓到与存活恰好都是 4，两个口径数值相等，那行碰巧没错。给汇总立的合同：与明细一致，且明细与汇总彼此独立，必须对账（来源：§8.2 排查实录）。
4. 度量控制流判定点的数量，不度量数据里的错误。「烟雾报警器」对应 A 部分的线性增长（斜率 0.091 对 0.100）与同组方差，「不是验收员」对应 C 部分：塞错数据后圈复杂度仍是 5，行为已坏（来源：§8.3）。
5. 见 §8.4 的表。流水线顺序：spec 到测试到实现（RI 与 checkRep）到接口到并发条款到全绿提交，出事后调试兜底；Git 垫在流水线底下，每转一圈打一个快照检查点（来源：§8.4、§8.1）。

应用与辨析答案：

1. 他漏了：现有测试的抓取力是按旧合同投放的，实验一里坏味道版「测试全绿」的缺陷有 4 个，重构前全绿的套件照样放走它们。正确顺序是先给要拆的缝补合同定向的单元测试（§2.1 测试先行反过来用），再动结构。他恰好对的情况：现有套件里已有针对这些缝的定向测试，抓取力经得起 §8.2 那张表的对账（来源：§8.2、§2.1）。
2. 先立：读出这个函数隐含的阶段划分，把它们写成 spec 条款，并按 §2.1 给每个阶段补预言机独立的单元测试，确认全绿（此刻测的是旧结构）。再拆：按圈复杂度从热点拆起，每拆出一个小函数就跑全套测试，每步一个提交（§8.1），坏了 revert；拆完用度量确认热点降下来了，但最终验收是测试，不是度量数字。期间 checkRep 与断言（§7.4）随拆随布（来源：§8.2、§8.3、§8.1、§7.4）。
3. 第一条：把明细表每行「抓到/漏检」计数求和，与汇总行的抓到数、存活数对账，不等即违约，这直接封死本次的口径反转。第二条：抓到名单与存活名单互斥，并集恰为全部 8 个缺陷编号，防止两处口径各错各的还能碰巧对上。两条都用代码断言实现，让违约退出码非零（来源：§8.2 排查实录、§7.4）。

**你现在能做什么**：面对一段「测试全绿但结构难受想动」的代码，你能说出重构的两个判据，给出第一步（按合同补定向单元测试）与第二步（用圈复杂度挑热点、每步一个全绿提交），并且知道汇总数字要和明细对账。

全册从一例类型错误在两界的暴露时机开始，到这里收束成一张合同地图：spec 是合同，测试是抽查，抽象屏障是防火墙，调试为论证的漏洞兜底，Git 让每一次改动可回退。论证到此交卷，剩下的事是提取：复习总结章会把六件套变成闭卷题，请你在不看正文的情况下把它们取出来。带着这张地图，整站其余各册讲的都是同一种游戏的新场地。
