# $\rm Appendix \, F$ 软件设计与大型代码库生存

> 到本章为止，你写的程序都是"一个人的项目"——你知道每一行代码在哪里、做什么。真实软件工程的核心挑战不是"写出能工作的代码"，而是**六个月后的你（或你的队友）仍然能理解、修改和扩展这段代码**。本章讲三件事：在十万行陌生仓库里找到路、画出模块边界、让代码经得起时间。

你应该已经写过多文件 C++ 或 Python 项目，使用过 Git，至少读过一两个开源仓库的 README。本章不依赖任何特定语言或框架。

## $\rm \S \, F.1$ 如何阅读一个陌生仓库

### $\rm \S \, F.1.1$ 你拿到一个新仓库，从哪开始

不是从第一行代码。按这个顺序建立"代码地图"：

1. **README**——项目是什么、怎么构建、怎么运行
2. **构建文件**——`CMakeLists.txt`、`Makefile`、`pyproject.toml`、`package.json`——告诉你入口在哪、依赖是什么
3. **目录结构**——`ls` 或 `tree -L 2`——顶层目录名暗示了架构：`src/`、`lib/`、`tests/`、`docs/`、`include/`
4. **测试**——`tests/` 目录是最可靠的"文档"。测试告诉你每个模块的**输入**和**预期输出**——比注释更诚实
5. **主入口**——`main.cpp`、`app.py`、`index.js`——从入口函数开始，跟踪调用链
6. **最近修改**——`git log --oneline -20`——最近活跃的区域通常是项目当前焦点

```bash
# 快速探索一个陌生仓库的标准流程
git clone <url> && cd <project>
tree -L 2                          # 看结构
git log --oneline -20              # 看历史
grep -r "main(" --include="*.cpp"  # 找入口
ls tests/ 2>/dev/null || ls test/ 2>/dev/null  # 找测试
head -50 README.md                 # 看构建命令
```

### $\rm \S \, F.1.2$ 调用链追踪

找到入口函数后，沿着调用链往下读——不是广度优先地读所有文件。用一个具体用例（如"用户输入搜索关键词后发生了什么"）驱动阅读：

```text
main()
  → parse_args()
  → PaperManager::search(keyword)
      → Database::query("SELECT ...")
      → Paper::from_row(row)
      → format_results()
```

每个函数只看它的**输入**、**输出**和**它调用了谁**。不深入被调用函数的实现细节（除非那个细节就是你当前关心的）。

## $\rm \S \, F.2$ 模块边界：代码的"产权"

### $\rm \S \, F.2.1$ 为什么"一个文件一万行"是问题

不是因为看起来不舒服——是因为：
- 修改一行可能影响文件内任何位置
- 两个人同时改这个文件 → merge conflict
- 测试只针对整个大文件，不能针对独立功能
- 重用一个功能 = 复制整个文件或依赖整个文件的编译

**模块**（module）**不是 C++20 的 modules 关键字**——它是一个概念：把相关的函数和数据组织在一起，对外暴露明确的**接口**（interface），隐藏内部**实现**（implementation）。

### $\rm \S \, F.2.2$ 接口与实现：藏在头文件背后的思想

你在 C++ 中已经用过它——`.h` 是接口，`.cpp` 是实现。但接口不只是"头文件中的声明"：

```cpp
// ❌ 头文件暴露了太多内部细节
class PaperDatabase {
public:
    std::vector<Paper> papers;     // 任何人都可以直接修改
    sqlite3* db;                    // 暴露底层数据库类型
    std::string db_path;
};

// ✅ 接口只暴露"能做什么"，不暴露"怎么做"
class PaperDatabase {
public:
    std::vector<Paper> search(std::string keyword) const;
    void add(const Paper& paper);
    int count() const;
private:
    sqlite3* db_;                   // 实现细节——调用者不需要知道
    std::string db_path_;
};
```

> **经验规则**：设计接口时假设调用者**只读你的头文件、不看你的 .cpp**。如果调用者需要知道内部实现才能正确使用这个类——接口设计有问题。

## $\rm \S \, F.3$ 耦合与内聚：两个最重要的设计直觉

### $\rm \S \, F.3.1$ 耦合：模块之间的依赖程度

**耦合高** = 改模块 A，模块 B 也要跟着改。**耦合低** = 模块 A 和 B 各自独立，通过明确的接口通信。

降低耦合的实际方法：
- **依赖接口，不依赖实现**——`search(keyword)` 而不是 `db->execute("SELECT ...")`
- **数据传递，不共享全局变量**——函数参数 > 全局变量
- **单向依赖**——A 知道 B，但 B 不知道 A（而不是 A↔B 互相知道）

### $\rm \S \, F.3.2$ 内聚：一个模块内部是否"在做同一件事"

**内聚高** = 模块内的所有函数围绕同一个职责。**内聚低** = 一个模块里既有文件解析、又有网络请求、又有日志格式化。

检测内聚的简单方法：用一个句子描述这个模块的职责——如果句子中出现"和"、"以及"、"另外"超过三次，内聚可能太低。

## $\rm \S \, F.4$ 何时抽象，何时接受重复

### $\rm \S \, F.4.1$ 抽象的代价

每增加一层抽象，你在当前代码中获得灵活性，同时付出了理解成本。三次出现以下模式时才开始考虑抽取：

- 同样的代码出现了**三次以上**——Rule of Three
- 不是因为巧合而形式相同，而是**语义相同**——抽取后函数名能准确描述它在做什么
- 预期的未来变化确实是**同一个方向**——不要为"可能"的未来需求抽象

### $\rm \S \, F.4.2$ 过早抽象的常见后果

```python
# 原来：两个简单的函数
def validate_email(email): ...
def validate_phone(phone): ...

# 过早抽象后：
class Validator(ABC):
    @abstractmethod
    def validate(self, value, rules, locale, error_callback): ...
```
现在加第三种验证需要理解整个抽象体系，而不是写一个简单函数。DRY（Don't Repeat Yourself）不是绝对律令——当抽象的成本超过重复的成本时，接受重复。

## $\rm \S \, F.5$ 技术债务与安全重构

### $\rm \S \, F.5.1$ 技术债务不是"代码写得烂"

**技术债务**（technical debt）是"为了短期速度而做出的、长期需要偿还的设计妥协"。它不总是坏的——就像贷款不总是坏的，只要你**知道自己在借、有还款计划**。

```text
// 技术债务的健康管理：
// TODO(zhangsan): 当前 O(n²) 的匹配算法在 n>10000 时需要重构为索引方案
// 临时方案支撑 3 个月的 MVP 发布，计划在 Q3 重构。
```

> **经验规则**：记录技术债务的位置、原因和触发条件。没有记录的债务不是债务——是陷阱。

### $\rm \S \, F.5.2$ 安全重构的前提：有测试

在没有测试的情况下重构大型代码库 = 蒙着眼睛换发动机。最小安全重构流程：

1. **确保有测试覆盖你要改的区域**——如果没有，先加测试（至少一个表征测试——记录当前行为）
2. **小步提交**——每次只改一个逻辑块，改完就提交
3. **每个提交后跑全部测试**——确保没有回退
4. **IDE 的重命名功能优于手工替换**——`F2`（Rename Symbol）理解作用域，`sed` 不理解

## $\rm \S \, F.6$ 关键概念回顾

1. 阅读陌生仓库的标准顺序是什么？
> README → 构建文件 → 目录结构 → 测试 → 入口函数 → 最近提交。不是从第一行代码开始。

2. 耦合和内聚分别衡量什么？
> 耦合衡量模块之间的依赖程度——越低越好；内聚衡量模块内部功能的一致性——越高越好。

3. Rule of Three 是什么？为什么不是 Rule of Two？
> 同样的模式出现三次才开始抽取抽象。两次可能是巧合——第三次出现时模式真的存在。过早抽象的成本（理解负担、错误抽象）往往超过复制的成本。

4. 安全重构的最小前提是什么？
> 有测试覆盖待重构区域。没有测试的重构不是重构——是赌博。至少加一个表征测试记录当前行为再动手。

## $\rm \S \, F.7$ 应用与辨析

1. "把能复用的代码全抽成函数"是正确的吗？
> 不完全是。复用是目的，但抽取得看语义——两个函数碰巧形式相同但含义不同，抽取后命名困难且未来会分化。判断标准：抽取后的函数能否用一个清晰的名称描述它在做什么。

2. 微服务比单体架构"更好"吗？
> 不是。微服务用网络延迟和运维复杂度换来了独立部署和团队自治。如果团队只有三个人，单体通常更适合——架构选择取决于组织规模、团队结构和变更频率，不是技术标签。
