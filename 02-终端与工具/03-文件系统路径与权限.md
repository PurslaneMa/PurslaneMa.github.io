# $\rm Chapter \, 3$ 文件系统与路径

> 在[终端、Shell与命令行](02-终端Shell与命令行.md)中你学会了在目录之间移动、查看文件和运行程序。但你一定遇到过这种情况：资源管理器里明明能看到的文件，终端却说“找不到”；或者双击就能打开的程序，在终端输入名字却提示找不到该命令（各 Shell 的报错文案不同，§2.4 见过 PowerShell 那条）。本章回答：文件到底在哪里，程序怎样找到它。而“谁可以访问这些文件”——`Permission denied` 为什么发生、怎么处理——属于访问控制的范畴，由下一章[权限与用户管理](04-权限与用户管理.md)回答。

> **开始前自检**：本章假设你已经会：
>
> - □ 会在终端运行命令并阅读输出（§2.4）
> - □ 用 cd、pwd 在目录之间移动（§2.5）
> - □ 用 cat、echo 查看或生成过文件（§2.6）

## $\rm \S \, 3.1$ 文件系统是一棵树（有时是一片森林）

在[终端、Shell与命令行](02-终端Shell与命令行.md)中，你已经在用 `cd` 在目录间移动。现在把镜头拉远，看看这些目录是怎样组织起来的。

### $\rm \S \, 3.1.1$ 根目录：所有路径的起点

一个磁盘或分区的文件系统，本质上是一棵倒置的树：最上层是一个**根目录**（root directory），下面分支出子目录和文件，子目录再分支出更多内容。

在 Windows 上，每个盘符都有自己的根，形成一片“森林”：

```text
C:\                    ← C 盘的根
├── Users\
│   └── Alice\
│       └── projects\
D:\                    ← D 盘的根
├── data\
└── tools\
```

在 Linux/macOS 上，所有存储设备挂载到同一棵树下，只有一个根 `/`：

```text
/                      ← 整个文件系统的根
├── home/
│   └── alice/
│       └── projects/
├── mnt/
│   └── data/          ← 可能是另一块硬盘挂在这里
└── tmp/
```

这就是为什么 Windows 路径以 `C:\` 或 `D:\` 开头，而 Linux 路径以 `/` 开头——它们只是组织方式不同，树状结构的思想完全相同。

> **竞赛生迁移提示**：目录结构看起来就是一棵多叉树——根目录是根节点，`..` 是父节点指针，`.` 是节点自身，从根出发沿着子节点走下来的路径就是你在终端看到的目录路径。当多叉树看，已经够你理解路径和遍历了；遇到符号链接（§3.6）时要当心：同一个目标可能出现在多条路径里，甚至形成环，那种“无脑递归”会重复走甚至绕不出来，遍历时必须记录已访问过的节点。

### $\rm \S \, 3.1.2$ 文件名、目录名和路径分隔符

路径由一串名字用分隔符连接而成。Windows 传统用反斜杠 `\`，Linux/macOS 用正斜杠 `/`。

现在许多 Windows 开发工具（包括 PowerShell 的许多命令）也接受 `/`，但 **不要假设所有工具都一样**。使用文件资源管理器的地址栏或 Tab 补全时，得到的仍然是反斜杠路径。跨平台项目中，优先使用正斜杠，或在代码中让语言/库处理分隔符差异。

一个完整的路径包含：

```text
C:\Users\Alice\projects\main.cpp
 ↑       ↑        ↑       ↑
盘符   目录名   目录名   文件名（含扩展名）
```

文件名和目录名在各自父目录中必须是唯一的。**目录本质上也是一种文件**，只是它存储的是“里面有什么”的列表，而不是普通数据。

## $\rm \S \, 3.2$ 绝对路径与相对路径

这是文件系统最核心的概念，也是“找不到文件”的第一大来源。

### $\rm \S \, 3.2.1$ 定义

- **绝对路径**：从根目录出发，完整写出到达目标的每一级。无论当前在哪里，它都指向同一个位置。
- **相对路径**：从当前工作目录出发。同一段相对路径，在不同当前目录下指向不同位置。

Windows 绝对路径的例子：

```text
C:\Users\Alice\projects\data\papers.json
D:\backup\2024.tar.gz
```

Linux/macOS 绝对路径的例子：

```text
/home/alice/projects/data/papers.json
/tmp/log.txt
```

相对路径的例子（两个平台通用）：

```text
data/papers.json          ← 当前目录下的 data 子目录中的文件
../backup/old.tar.gz     ← 上一级目录中的 backup 子目录中的文件
./main.cpp               ← 明确指当前目录中的文件（. 可以省略）
```

在[终端、Shell与命令行](02-终端Shell与命令行.md)中你已经见过 `.`（当前目录）和 `..`（上一级目录）——它们是相对路径的构建块。多层 `..` 也是合法的：

```text
../../global_config.json  ← 上两级目录中的文件
```

### $\rm \S \, 3.2.2$ 什么时候用绝对路径，什么时候用相对路径

**绝对路径**适合：
- 配置文件中的固定位置（如日志目录、数据目录）；
- 脚本中引用的系统工具路径；
- 跨项目引用一个不会移动的资源。

**相对路径**适合：
- 项目内的文件引用——整个项目目录移动到另一台机器或另一个位置后，相对路径仍然有效；
- 构建脚本、`#include`、`import` 等，它们通常相对于当前文件或项目根解释。

一个常见的坑：你在 `C:\Users\Alice\projects` 中写了一个脚本，里面用了 `data/input.txt`。后来你把脚本复制到 `D:\tools` 去运行，`data/input.txt` 就会相对于 `D:\tools` 解释，而不是原来的位置。

> **经验规则**：如果你希望移动项目目录后一切照常工作，用相对路径。如果你引用的资源固定在系统中某处，用绝对路径。不确定时，先确认当前目录。

### $\rm \S \, 3.2.3$ `~` 是什么

在[终端、Shell与命令行](02-终端Shell与命令行.md)中你见过 `~` 这个符号。在 Linux/macOS 和 PowerShell 中，`~` 通常展开为当前用户的**主目录**（home directory）：

```bash
# Bash
cd ~/projects     # 等价于 cd /home/alice/projects
```

```powershell
# PowerShell
Set-Location ~/projects   # 等价于 Set-Location C:\Users\Alice\projects
```

`~` 不是文件系统的一部分——它是 Shell 在解析命令时帮你替换的简写。在程序代码中（如 C++ 的 `fopen`）`~` 通常不会被展开，你需要写完整路径。

### $\rm \S \, 3.2.4$ 在终端中验证

任何时候不确定当前目录，先查看：

```powershell
# PowerShell
Get-Location
```

```bash
# Bash
pwd
```

构造一个路径后，用 `Test-Path`（PowerShell）或 `ls`（Bash）立即验证：

```powershell
Test-Path "C:\Users\Alice\projects\data\papers.json"
# 返回 True 或 False
```

```bash
ls /home/alice/projects/data/papers.json
# 文件存在则显示文件名，不存在则报 No such file or directory
```

> **经验规则**：`Test-Path`/`ls` 适合验证已知路径。当你只记得文件名、不知道它在哪时，用系统级搜索：Windows 的 **Everything**（voidtools.com，直接读 NTFS 的 MFT 索引，比系统自带搜索快几个数量级）、macOS 的 **Spotlight**（`Cmd+Space`；第三方 **Alfred** 更强大、支持工作流）、Linux 的 `locate`（部分发行版需先安装并 `updatedb` 建索引）。共同点：全盘索引，一秒钟内找到文件。

## $\rm \S \, 3.3$ 隐藏文件：不显示不代表不存在

有些文件默认不在文件管理器和普通 `ls` 中显示——它们被标记为“隐藏”。

### $\rm \S \, 3.3.1$ Unix/Linux/macOS：点号前缀

文件名以 `.` 开头即视为隐藏：

```text
.gitignore
.config/
.bashrc
```

`ls` 默认不显示它们。使用 `-a` 选项（all）才会列出：

```bash
ls        # 不显示隐藏文件
ls -a     # 显示包括 . 和 .. 在内的全部文件
ls -A     # 显示隐藏文件，但不包括 . 和 ..
```

大量开发工具把配置和状态保存在隐藏文件中——`.git` 目录存储了 Git 仓库的全部历史；`.vscode` 保存了 VS Code 的工作区设置。它们有意不打扰日常浏览，但当你排查配置问题时，要知道它们是存在的。

### $\rm \S \, 3.3.2$ Windows：文件属性

Windows 使用文件系统中的“隐藏”属性标记文件，与文件名无关。在 PowerShell 中查看和设置：

```powershell
# 查看隐藏项目（包括隐藏文件和目录）
Get-ChildItem -Hidden

# 同时显示隐藏和非隐藏
Get-ChildItem -Force
```

Windows 还有一个“系统”属性用于操作系统关键文件，用 `-System` 查看。

### $\rm \S \, 3.3.3$ 什么时候你会遇到隐藏文件

- 跟着教程做项目时，教程说“编辑 `.env` 文件”，你却在文件管理器中找不到——它可能被隐藏了。
- 复制一个目录给别人的时候，隐藏文件（如 `.git`）可能被漏掉，导致对方拿到的项目不完整。
- 排查磁盘空间时，某个隐藏目录可能占了大量空间但你一直没看到。

## $\rm \S \, 3.4$ 文件扩展名：约定，不是魔法

### $\rm \S \, 3.4.1$ 扩展名帮助程序判断类型

`main.cpp` 的 `.cpp` 部分就是扩展名。它的作用是告诉程序和人类“这可能是什么类型的文件”。编辑器根据扩展名选择语法高亮，编译器根据扩展名决定按哪种**语言**编译（`.cpp` 交给 C++ 编译器，`.c` 按 C 处理），文件管理器根据扩展名选择图标和默认打开方式——至于用哪一版**语言标准**（C++11 还是 C++17），扩展名管不着，要靠 `-std=c++17` 这类编译选项指定（第 1 章的编译命令里见过）。

但在文件系统层面，**扩展名只是文件名的一部分**。把 `photo.jpg` 改名为 `photo.cpp` 不会把 JPEG 图像转换成 C++ 源码——它仍然是一段二进制数据，只是系统现在会对它尝试 C++ 的打开方式。

### $\rm \S \, 3.4.2$ Windows 常见陷阱：隐藏已知扩展名

Windows 资源管理器默认**隐藏已知文件类型的扩展名**。当你看到一个名为 `README` 的文件时，它的真实完整名称可能是 `README.md` 或 `README.txt`。同样是右键新建的文本文档，你在资源管理器里看到的名字是 `新建文本文档`（`.txt` 被隐藏了）；把它改名为 `data.json` 时，系统并不会替换扩展名，只是把主文件名改成了 `data.json`——真实文件名是 `data.json.txt`，程序仍然按文本文件对待，这就是“改了名却不被识别”的原因。

**建议**：在文件资源管理器的“查看”选项卡中勾选“文件扩展名”，始终显示完整文件名。

### $\rm \S \, 3.4.3$ 没有扩展名和多个扩展名

Linux 上许多可执行文件和配置文件没有扩展名。`.tar.gz` 有两个扩展名，表示“先经过 tar 打包，再经过 gzip 压缩”。习惯上从右向左读：最右边是最外层格式，打包与压缩这两层操作会在[文本、编码、压缩包与常见数据格式](06-文本编码压缩包与数据格式.md)中详细展开。

## $\rm \S \, 3.5$ 通配符：用一个模式匹配多个文件

Shell 提供了一组字符，帮你用模式批量指定文件，这叫 **globbing**（或通配符展开）。

### $\rm \S \, 3.5.1$ 基本通配符

| 通配符 | 含义与示例 | 平台差异 |
|---|---|---|
| `*` | 任意长度的任意字符：`*.cpp` 匹配所有 C++ 源文件 | 两平台一致 |
| `?` | 恰好一个字符：`data_?.csv` 匹配 `data_1.csv`、`data_a.csv`，不匹配 `data_10.csv` | Bash 与 PowerShell 的 `-Path`、`-like` 一致；PowerShell 的 `-Filter` 把模式交给 Windows 文件系统 API，那里的 `?` 可匹配 0 或 1 个字符 |
| `[abc]` | 方括号内任意一个字符：`file_[0-9].txt` 匹配 `file_0.txt` 到 `file_9.txt` | 两平台一致 |
| `[!abc]` | 方括号内字符之外的任意一个字符：`[!0-9]*` 匹配不以数字开头的文件 | 仅 Bash/Zsh（也可写 `[^abc]`）；PowerShell 不支持这种取反，会把 `!`、`^` 当成集合里的普通字符 |

在 C++ 中你学过字符类和范围——`[0-9]` 这个语法你应该不陌生，但要记住两边对“取反”的处理不同：不确定时先用 `ls` / `Get-ChildItem` 实测一次匹配结果，再把它放进删除、移动这类命令里。

### $\rm \S \, 3.5.2$ 在命令中使用

PowerShell：

```powershell
# 列出当前目录下所有 .cpp 文件
Get-ChildItem *.cpp

# 列出当前目录及其子目录下所有 .cpp 文件
Get-ChildItem -Recurse *.cpp
```

Bash：

```bash
# 列出当前目录下所有 .cpp 文件
ls *.cpp

# 列出当前目录及子目录下所有 .cpp 文件
# Bash 需先 shopt -s globstar 启用递归通配符（zsh 默认支持）
ls **/*.cpp
# 如果不确定当前 Shell 的通配行为，用 find 更可靠：
find . -name "*.cpp"
```

### $\rm \S \, 3.5.3$ 通配符不是正则表达式

一个常见混淆：`*` 在通配符中表示“任意字符序列”，在正则表达式中表示“重复前一个模式零次或多次”。它们是两套不同的系统。Shell 的文件通配符是 glob 模式，`grep` 和 `sed` 搜索的是正则表达式。如果不确定，先在小范围实验。

### $\rm \S \, 3.5.4$ 危险边界

```bash
rm *.log        # 删除当前目录下所有 .log 文件；rm 删文件不进回收站，删完无法撤销
rm -r test_*    # 递归删除（-r）所有以 test_ 开头的目录及其内容——不能这样直接敲，见下
```

`rm` 做的事是“从目录里摘掉这个名字、释放它占的数据”；加上 `-r` 它就能对目录生效，把目录连同里面的全部内容一起删，而且**删除前不会逐个向你确认**。所以在执行带通配符的删除、覆盖、移动之前，先用只读命令确认匹配了哪些文件：

```bash
ls *.log         # 第一步：先看匹配了什么，核对范围
# 确认列表里正是你要删的那些文件，再执行第二步
rm *.log
```

`rm -r test_*` 这种“通配符 + 递归删除”的写法，只有同时满足两个条件才允许动手：当前目录是 §3.9 里自己创建的 `path-lab`，并且已经用 `ls -d test_*/` 看过匹配结果。集合里混进任何不认识的目录，就停下来改用逐个写名字删除：

```bash
ls -d test_*/         # -d 让 ls 列出目录本身，而不是目录里的内容
# 预期输出：test_1/ test_2/ 这类你自己建的目录
rm -r test_1 test_2   # 确认无误再删：写全名字比通配符保险
```

## $\rm \S \, 3.6$ 符号链接与快捷方式：一个位置，多个入口

### $\rm \S \, 3.6.1$ 概念

有时你希望同一个文件或目录出现在两个不同的路径下——不是复制，而是同一个东西有多个名字。

- **符号链接**（symbolic link / symlink）：文件系统级别的“指针”。访问符号链接时，系统自动跳转到目标。删除符号链接不会删除目标；删除目标后，符号链接变成“悬空”状态，指向不存在的位置。
- **Windows 快捷方式**（`.lnk` 文件）：是普通文件，由 Windows Shell 而非文件系统解释。许多命令行程序不识别 `.lnk` 文件，会把它当成普通文件。
- **硬链接**（hard link）：同一个文件数据对应多个文件名，删除任意一个不影响数据和另一个名字。限于同一文件系统内，不适用于目录（POSIX 限制）。日常开发中符号链接更常见。

### $\rm \S \, 3.6.2$ 创建和识别

PowerShell：

```powershell
New-Item -ItemType SymbolicLink -Path link_name -Target target_path
```

Bash：

```bash
ln -s target_path link_name
```

`New-Item -ItemType SymbolicLink` 新建的是 `link_name` 这个链接文件，`target_path` 只被记录、不会被改动；Windows 上创建符号链接通常需要管理员权限或已开启“开发者模式”，否则会报权限错误。Bash 的 `ln -s` 要留意参数顺序：**目标在前、链接名在后**，写反了会在当前目录造出一个多余的链接。

查看链接指向哪里：

```powershell
Get-Item link_name | Select-Object Target
```

```bash
ls -l link_name
# 输出显示 link_name -> target_path
```

### $\rm \S \, 3.6.3$ 典型用途

- 把某个大目录（如数据集）从位置 A 链接到项目中的方便位置，而不移动或复制原始数据。
- Python 虚拟环境和 Node.js 的 `nvm` 使用符号链接管理当前激活的版本。
- 系统中多个路径需要指向同一动态库的不同版本。

### $\rm \S \, 3.6.4$ inode、硬链接与符号链接的精确区别

每个文件在磁盘上都有一个**inode**（索引节点）——它存储文件的元数据（大小、权限、时间戳、数据块位置），但**不包含文件名**。文件名只是指向 inode 的标签。

> **平台说明**：inode、`ls -li`、`df -i` 都是 Unix/Linux 的概念。Windows 的 NTFS 由 **MFT**（Master File Table，主文件表）记录承担同样角色，只是没有 `df -i` 这样的等价命令；这一小节在 Windows 上以理解概念为主，命令留到 WSL 或 Linux 服务器上再练。

```bash
ls -li                    # -i 显示 inode 号
# 123456 -rw-r--r-- 1 alice staff 1024 Aug 10 paper.txt
# ↑ inode                          ↑ 硬链接计数 = 1
```

**硬链接**（hard link）：两个文件名指向**同一个 inode**。删除任何一个文件名，数据仍然存在（只要至少还有一个硬链接指向它）。硬链接不能跨文件系统，不能指向目录。

```bash
ln paper.txt paper_backup.txt    # 创建硬链接
ls -li                           # 两个文件有相同的 inode 号，硬链接计数 = 2
rm paper.txt                     # 删除原文件名——数据仍通过 paper_backup.txt 可访问
```

**符号链接**（symlink / soft link）：是一个**独立的文件**，内容就是“目标路径”这个字符串。删除目标文件后，符号链接仍然存在但指向无效路径（broken link）。

| | 硬链接 | 符号链接 |
|---|---|---|
| 本质 | 同一个 inode 的另一个名字 | 一个“指向路径”的小文件 |
| 跨文件系统 | ❌ | ✅ |
| 指向目录 | ❌ | ✅ |
| 目标删除后 | 数据仍在 | 断链（dangling link） |
| `ls -l` 显示 | 普通文件 | `link -> target` |

### $\rm \S \, 3.6.5$ 原子重命名：为什么同文件系统内的改名是原子的

```bash
mv old_name new_name    # 改名或移动：同一文件系统内，这一步是原子的
```

`mv` 做的是“给文件换个名字或换个目录”，同一个文件系统内它只修改目录项、让新名字指向同一个 inode——不复制数据、不修改 inode 内容，也不会出现“写到一半崩溃、新旧文件都不完整”的情况。执行后用 `ls` 确认新名字在、旧名字不在即可。这就是为什么很多程序通过“写临时文件 → `mv` 覆盖目标文件”来保证数据完整性。

有一条隐蔽的默认行为要记住：**目标已存在时 `mv` 会静默覆盖它，不提示**。所以移动或改名之前，先 `ls` 看一眼新名字是否已被占用；重要文件加 `-i` 让它在覆盖前先询问（`mv -i old_name new_name`）。

### $\rm \S \, 3.6.6$ 磁盘满与 inode 满：两种不同的“满了”

```bash
df -h     # 只读命令：看磁盘空间还剩多少（“还有多少 GB”）
df -i     # 只读命令：看 inode 还剩多少（“还能创建多少个文件”）
```

一块磁盘的 inode 数量在格式化时固定。如果程序创建了海量小文件（如 `node_modules` 十万个文件），即使磁盘空间还有很多 GB，`df -i` 可能显示 inode 已耗光——此时 `touch newfile` 会报 `No space left on device`，即使 `df -h` 显示还有空间。

两条命令都只打印信息、不改动任何东西，看到 `IUse%` 接近 `100%` 就是 inode 快满了。想再往下找是哪个目录在消耗 inode，可以估着数一数：

```bash
ls -f /data | wc -l      # 粗略数 /data 下有多少个条目（-f 跳过排序，条目多时也不至于卡住）
```

`ls -f` 按目录里的原始顺序输出、不排序，配合 `wc -l` 数行数；它只数当前这一层，要连子目录一起数得用 `find`（第 7 章的工具箱）。

## $\rm \S \, 3.7$ 不同系统的换行符：一个看不见的差异

这是跨平台开发中最隐蔽的问题之一。[计算机程序与开发全景](../01-基础观念/01-计算机程序与开发全景.md)中提过“换行格式：Windows 常见 CRLF，Linux 常见 LF”，这里再具体一点。

### $\rm \S \, 3.7.1$ 行是怎么结束的

当你按下回车键，编辑器和操作系统会在文本中插入一个看不见的“换行记号”。不同系统的默认记号不同：

| 系统 | 记号 | 转义表示 | 可见名称 |
|---|---|---|---|
| Windows | CR + LF | `\r\n` | 回车 + 换行 |
| Linux/macOS (现代) | LF | `\n` | 换行 |
| macOS (极早版本) | CR | `\r` | 回车 |

在 C++ 中你用过 `'\n'`，它被标准库翻译为当前平台的换行约定（文本模式下）。但当你从网上下载一个文件、从 Git 克隆一个仓库、或者在不同系统间移动文件时，换行符可能被保留为原始形式。

### $\rm \S \, 3.7.2$ 出问题时的症状

- 在 Windows 记事本中打开 Linux 文件，所有内容挤在一行；
- 在 Linux 终端中 `cat` 一个 Windows 文件，每行末尾出现 `^M`（即 `\r` 的可视化表示）；
- Git diff 显示“整个文件都改了”，实际上只是换行符变了；
- Shell 脚本在 Windows 编辑后上传到 Linux 执行时报 `\r: command not found`。

### $\rm \S \, 3.7.3$ 如何发现和解决

[文本、编码、压缩包与常见数据格式](06-文本编码压缩包与数据格式.md)会展开讲文本编码的完整排查。这里先给一个最小检查方法——在 PowerShell 中把文件转成十六进制看：

```powershell
# 输出开头部分即可判断行尾（PowerShell 5.1 与 7+ 都能用）
Format-Hex file.txt | Select-Object -First 2
# 输出里左边的偏移量是列号，中间是十六进制字节
# 文本行末出现连续的 0D 0A，就是 CR + LF（CRLF）；只有 0A 则是 LF
```

这里 `0D`、`0A` 都是十六进制数：`0D` 是回车 CR，`0A` 是换行 LF。例如一个内容是 `1` 加 CRLF 的小文件，第一行会显示 `31 0D 0A` 加一个 `1..` 的字符示意。

> **版本差异**：PowerShell 6+ 的 `Get-Content` 有 `-AsByteStream`，可以直接取原始字节；Windows 自带的 5.1 没有这个参数（写了会报“找不到与参数名称 `AsByteStream` 匹配的参数”，5.1 的对应写法是 `-Encoding Byte`），而且它输出的是一串十进制数字（同样的字节显示成 `13 10`，不是 `0D 0A`）。`Format-Hex` 在两版都能用，所以上面用它；注意它会一直打到文件结尾，5.1 又没有只取前 N 字节的 `-Count` 参数，别拿很大的文件试。

Git 可以在提交时自动转换换行符（通过 `core.autocrlf` 配置），这个配置会在[Git与团队协作](../05-开发工作流/19-Git与团队协作.md)一章讲到。现在只需要知道：**不同系统的换行符不同，这是正常的，有工具可以处理，不需要手动逐行修改。**

## $\rm \S \, 3.8$ 常见错误及其证据

### $\rm \S \, 3.8.1$ “明明文件在，终端说找不到”

**最可能的原因（按频率排序）**：

1. **当前目录不是你想象的那个**。解决：先执行 `pwd` 或 `Get-Location`。
2. **相对路径写错了层级**。解决：用 `ls` 或 `Get-ChildItem` 逐级验证路径中的每个目录都存在。
3. **文件名拼写或大小写问题**。Linux 区分大小写，`Readme.md` ≠ `README.md`。解决：`ls` 确认精确文件名。
4. **扩展名被 Windows 资源管理器隐藏了**，实际文件名多了 `.txt`。解决：在资源管理器的“查看”选项卡中勾选“文件扩展名”显示完整文件名——这就是[3.4 节](#342-windows-常见陷阱隐藏已知扩展名)讲的陷阱。
5. **程序在 PATH 中找不到，而你没有写 `./`**。当前目录通常不在 PATH 中，运行当前目录下的程序要写 `./app`——[终端、Shell与命令行](02-终端Shell与命令行.md)的 2.9 节详细讲过。

## $\rm \S \, 3.9$ 动手实践

三个实践都在一个新建的练习目录里做，不会影响系统和其他项目。先建好目录再进去（沿用第 2 章的 `mkdir`；Bash 里也可以写成一行 `mkdir path-lab && cd path-lab`）：

```bash
mkdir path-lab
cd path-lab
```

下面几步用到 `echo >` 造文件（第 2 章学过）；`cat` 是读文件，PowerShell 里换成 `Get-Content`。

### $\rm \S \, 3.9.1$ 实践一：绝对路径 vs 相对路径

1. 确认自己在 `path-lab` 里：`pwd`（PowerShell：`Get-Location`）。
2. 创建两个子目录：`mkdir src data`。
3. 在 `data` 里造一个文件：`echo "hello path" > data/input.txt`。
4. `cd src`，用相对路径读它：`cat ../data/input.txt`（PowerShell：`Get-Content ../data/input.txt`）。预期输出 `hello path`。
5. `cd ~` 回到主目录，再用绝对路径读同一个文件：`cat ~/path-lab/data/input.txt`（PowerShell 同样支持 `~`）。预期输出应与第 4 步完全一致。
6. 记录：哪种写法更短？哪种在任何当前目录下都不会找错？

### $\rm \S \, 3.9.2$ 实践二：通配符

1. 回到练习目录：`cd ~/path-lab`。
2. 造测试文件：`echo 1 > test_1.txt`、`echo 2 > test_2.txt`、`echo 10 > test_10.txt`、`echo d > demo.txt`、`echo b > test_backup.bak`。
3. Bash 运行 `ls test_?.txt`，PowerShell 运行 `Get-ChildItem test_?.txt`。预期两边都只列出 `test_1.txt`、`test_2.txt`，**不列出 `test_10.txt`**（`?` 只顶一个字符）。
4. 再比较 `ls *.txt` 和 `ls *.bak`（PowerShell：`Get-ChildItem *.txt` / `Get-ChildItem *.bak`）：前者列出四个 `.txt` 文件（含 `demo.txt`、`test_10.txt`），后者只列出 `test_backup.bak`。
5. 记住这条边界：带通配符的删除命令只在这种自己造的练习目录里试（§3.5.4）。

### $\rm \S \, 3.9.3$ 实践三：制造并诊断“找不到文件”

1. 先 `cd src`，当前目录变成 `path-lab/src`。
2. 直接读：`cat input.txt`（PowerShell：`Get-Content input.txt`）。预期报错——Bash 显示 `No such file or directory`，PowerShell 显示 `找不到路径…，因为该路径不存在`；原因是 `input.txt` 在 `data` 子目录里，不在 `src` 里。
3. 用相对路径访问：`cat ../data/input.txt`，这次读到 `hello path`。
4. `cd ..` 回到 `path-lab`，再敲一次 `cat input.txt`——**仍然失败**：`input.txt` 在 `data` 里，要写 `cat data/input.txt` 才对。同一条命令在不同当前目录下指向不同文件，这就是“文件明明在，终端却说找不到”的第一大来源（§3.8.1）。

做完之后清理练习目录：先用 `pwd`（PowerShell：`Get-Location`）确认当前**不在** `path-lab` 里面，`ls` 看清 `path-lab` 就在眼前，再执行删除——Bash 用 `rm -r path-lab`，PowerShell 用 `Remove-Item -Recurse path-lab`，最后 `ls` 确认它已消失。删除不可撤销，前面那两条确认不要省。

## $\rm \S \, 3.10$ 文件描述符：文件被打开之后发生了什么

### $\rm \S \, 3.10.1$ 一个反直觉的现象：删掉的文件还在占磁盘

夜深了，程序还在往 `app.log` 里写日志，日志文件涨到了 $20 \, \text{GB}$。你删掉它，`ls` 里确实没有这个文件了——可 `df -h` 显示磁盘占用一点没降。再写几条日志，`df` 显示的空间反而继续变小。文件已经“不存在”了，谁还在往里写？

```bash
# 前置：Linux（或 WSL）的 Bash；当前目录任意
rm big.log
df -h /            # 磁盘占用几乎不变，甚至继续上涨
```

要解释这件事，需要引入本章 §3.6.4 的 inode 之后的第二个概念：**文件描述符**（file descriptor，缩写 fd）——进程打开一个文件时，内核在进程自己的“打开文件表”里登记一条记录，并返回一个小的非负整数作为它的编号。之后程序读写文件用的都是这个编号，而不是文件名；`open()` 系统调用返回它，`close()` 系统调用归还它。惯例上 0、1、2 三个编号已经被标准输入、标准输出、标准错误占用，所以程序自己打开的文件通常从 3 开始编号。（这套机制在[内存、文件与输入输出](../03-计算机系统/12-内存文件与输入输出.md) §12.1 会从 I/O 角度再讲一遍；本章只用到它跟删除有关的那一面。）

关键在于：**文件名和 inode 是两回事，inode 和“文件是否还在被使用”又是两回事**。`rm` 做的事只是从目录里摘掉那个名字（unlink），让这个名字不再指向 inode；而 inode 上还有一个内核维护的引用计数——每有一个文件描述符指向它，计数就加一。所以删除的真实条件是两件事同时成立：

```text
目录里没有名字指向它  +  没有任何文件描述符指向它  →  数据块才真正释放
```

那个还在写日志的程序始终开着这个文件的 fd，`rm` 之后引用计数不为零，inode 和数据块都留着——磁盘当然不会释放。程序继续用 fd 写入也完全合法，写进去的数据进了这个已经没有名字的 inode，谁也读不到，直到进程关闭它（或进程退出，内核替它关闭全部 fd），空间才立刻回收。

> **Windows 的行为完全不同**。NTFS 上打开中的文件默认带独占共享模式，删除会直接失败，而不是“删掉名字、留下数据”。PowerShell 里 `Remove-Item` 会抛 `The process cannot access the file because it is being used by another process`（Git Bash 的 `rm` 报 `Device or resource busy`）——文件仍然在那里，占着空间，也仍然可见。所以“删了不释放空间”是 Unix 特有的现象；Windows 上你遇到的是“根本删不掉”。两者的共同点只有一个：**持有它的进程才是关键**。

### $\rm \S \, 3.10.2$ 找到持有者并回收空间

排查分三步：确认现象、找出持有者、决定怎么放掉它。

```bash
# 第 1 步：确认磁盘确实没释放（前置：Linux/WSL 的 Bash，只读命令）
df -h /var          # 看 Used 与 Avail

# 第 2 步：用 lsof 找出指向“已删除文件”的 fd
#   需要装 lsof（Debian/Ubuntu：sudo apt install lsof；Windows 与 Git Bash 通常没有）
lsof +L1
# 输出每行一条记录，关键列：COMMAND 程序名、PID 进程号、NLINK 硬链接数（0 表示已经没有名字）、
# NAME 文件路径后面带 (deleted) 的就是它
```

`lsof +L1` 是“列出链接数小于 1 的打开文件”，也就是那些已经没有名字、但还被 fd 引用的文件。拿到 PID 和 fd 编号之后，有三种处理方式，按侵入性从小到大：

```bash
# 方式一：让那个进程正常结束（最优）。先用 ps 确认它是什么、在做什么
ps -p 12345 -o pid,user,etime,comm,args
# 确认可以停：优先用 kill（默认 SIGTERM，程序有机会优雅退出）；确认无响应时再考虑 kill -9
kill 12345

# 方式二：不停进程，直接截断（适用于日志这类只需“清空”的文件）
#   fd 用第 2 步输出里的编号，例如 3
: > /proc/12345/fd/3     # 把该 fd 当作文件写一个零长度内容，等价于 truncate -s 0
#   注意：编号写错就会破坏别的文件；只对确定是日志/数据文件的 fd 使用

# 方式三：复制内容后清空（想留证据时）
cp /proc/12345/fd/3 /root/rescue.log   # 需要相应权限；先确认目标目录有足够空间
: > /proc/12345/fd/3
```

处理完再跑一次 `df -h /var`，`Avail` 立刻变大，说明空间回来了；`lsof +L1` 里也应该不再有那条记录。三种方式里最容易被忽略的是方式一：**有时候“磁盘满”的真正修法是重启那个服务**，而不是删文件。

> **经验规则**：给日志做清理时，用 `: > app.log`（原地清空）而不是 `rm app.log` 再 `touch app.log`。前者把 inode 保留下来，正在写日志的进程完全不受影响，空间当场回收；后者会重演本节开头的现象——旧 inode 被进程继续持有，新文件是另一个 inode，磁盘上同时躺着两份数据。这条规则对“日志轮转”同样重要，[日常系统管理：软件、用户、服务与日志](../03-计算机系统/13-系统服务日志与软件安装.md)讲的 `logrotate` 就是按这个原理工作的。

### $\rm \S \, 3.10.3$ 描述符的完整生命周期

一个 fd 从生到死，中间会发生这样几件事：

```text
open()/creat()  →  返回一个 fd（引用计数 = 1）
dup()/dup2()    →  把同一个打开文件再登记一个编号（引用计数 = 2，两个编号读写同一位置）
fork()          →  子进程复制父进程的 fd 表，父子各自持有引用（引用计数继续加）
close()         →  该进程的这个编号失效，引用计数减一
引用计数归零     →  内核释放这个打开文件：文件没名字就回收空间
```

这里要分清两个概念，它们经常被混着说：fd 只是**进程自己表里的编号**，同一个编号在别的进程里可以指向完全不同的东西；内核里那个“打开文件”对象才是真正记录读写位置、打开模式的东西，多个 fd（甚至跨进程的 fd）可以共同引用同一个对象。这就是为什么重定向和管道能工作——Shell 在启动程序前，把子进程表里的 0 或 1 换成了文件或管道（[终端、Shell与命令行](02-终端Shell与命令行.md) §2.10），程序自己毫不知情。`fork`、`exec` 与 fd 继承的细节在[操作系统、进程与线程](../03-计算机系统/11-操作系统进程与线程.md) §11.5 展开。

> **平台说明**：下面两小节讲的是 Unix 的做法。Windows 上对应的概念是**句柄（handle）**，但句柄默认不跨进程继承，也没有 `ulimit -n` 这样一个按进程生效的计数上限，权限与打开模式的规则也不同——Windows 用户读这两小节请配合 WSL 实操。

### $\rm \S \, 3.10.4$ 上限与 `Too many open files`

fd 需要占用内核里的表项，所以每个进程有一个数量上限。看当前 Shell 的软上限和硬上限：

```bash
ulimit -n        # 软上限：当前实际生效的值，如 1024
ulimit -Hn       # 硬上限：普通用户能提高到的最多值
```

当程序打开的文件（包括网络连接——socket 也占 fd）达到软上限，下一次 `open()` 或 `socket()` 就会失败，报 `Too many open files`（errno 24，`EMFILE`）。这是服务器最常见的故障之一，典型症状是：服务跑着跑着突然无法接受新连接，但 CPU 和内存都很正常。

```bash
# 排查：该进程当前打开了多少个 fd
ls /proc/12345/fd | wc -l        # Linux：目录里每个条目就是一个 fd
lsof -p 12345 | wc -l            # 用 lsof 数（需自装）

# 看该进程的上限（和你在自己 Shell 里看到的值可能不同，因为限额是按进程的）
grep -i "open files" /proc/12345/limits
```

修法取决于这个上限是谁设的。临时验证假设可以在启动前改：

```bash
# 前置：Linux Bash；只在当前 Shell 会话内有效，退出即恢复
ulimit -n 8192
./server            # 在同一会话里启动服务，它会继承这个上限
```

要让服务长期生效，得改设限额的地方，两种常见来源：

```bash
# 来源 1：登录会话的限制（apt 安装的传统守护进程常见）
# 编辑 /etc/security/limits.conf，追加两行（需要 sudo）：
#   paper-mgr soft nofile 65535
#   paper-mgr hard nofile 65535
#   影响：该用户以后登录的会话 fd 上限提高；已运行的进程不受影响，要重启服务
#   恢复：删掉这两行，重新登录

# 来源 2：systemd 管理的服务（现代 Linux 上更常见，因为 unit 文件里的设置优先）
# 在 /etc/systemd/system/paper-manager.service 的 [Service] 段加一行：
#   LimitNOFILE=65535
sudo systemctl daemon-reload
sudo systemctl restart paper-manager
#   验证：grep -i "open files" /proc/$(systemctl show -p MainPID --value paper-manager)/limits
```

> **别只把数字调大**。fd 用光经常是泄漏的信号——程序打开文件或连接后没有 `close()`（比如每次请求都新建数据库连接却不归还）。先把数字提上去让服务恢复，同时用 `ls /proc/PID/fd | wc -l` 连续观察计数是不是只涨不落；只涨不落就要回到代码里找没关的那一处。另外提高硬上限通常需要 root 或 `CAP_SYS_RESOURCE` 权限，这不是普通用户能自己解决的。

## $\rm \S \, 3.11$ 文件锁：多个程序怎么约好“同一个文件只能一个人动”

考虑两个程序同时写一份 `papers.csv`：每个都读进来、改一改、写回去。如果时间重叠，后写的那个会覆盖前一个的修改——两个进程谁都没做错，是“没有约定”这件事本身错了。更常见的场景是防止同一个脚本被启动两次：第二次启动应该立刻退出，而不是和第一次抢着做同样的事。

进程之间需要一种跨进程的互斥机制，这就是**文件锁**（file lock，这里说的是 `flock` 提供的那种“咨询锁”）：内核在某个打开文件对象上记录“已被谁锁住”，其他进程尝试锁同一个文件时会等待或直接失败。

```bash
#!/bin/bash
# 前置：Linux（含 WSL）的 Bash；flock 来自 util-linux，几乎各发行版自带，Git Bash 里通常没有
# 用途：同一个脚本同时只允许跑一个实例；-n 表示“拿不到就立刻失败，不要等”
set -euo pipefail

exec 9>/var/lock/paper-sync.lock   # 9 是随便挑的一个高位 fd，把锁文件挂在这个 fd 上
flock -n 9 || { echo "上一次同步还在运行，本次退出" >&2; exit 0; }
# 成功判据：第二次运行同一脚本时立即打印这行并退出 0，第一次的运行不被打断

echo "开始同步……"
sleep 10                            # 真正的工作
echo "同步完成"
# 脚本结束时 fd 9 被关闭，锁自动释放——不需要手动解锁
```

几个容易混淆的点：

**`flock` 命令和 `flock()` 系统调用不是一回事，但目的相同**。`flock` 命令是 util-linux 提供的小工具，做的就是把 `flock()` 包一层，方便在 Shell 脚本里用；你的 C++/Python 程序里可以直接调用系统调用或语言封装（Python 用 `fcntl.flock(fileobj, fcntl.LOCK_EX | fcntl.LOCK_NB)`）。所以“用 flock”在脚本语境里通常指那个命令。

**锁跟着文件描述符走，不跟着进程名走**。这是它比“锁文件”可靠的根本原因：fd 被关闭（包括进程崩溃、被 `kill -9`）时，内核一定释放锁，不会留下任何陈旧状态。所以上面的脚本不需要写任何清理代码。

**别用“写一个含 PID 的锁文件”来做互斥**。这种做法在教程里很常见，写起来像这样：检查 `/var/run/x.pid` 是否存在，不存在就写入自己的 PID——但它在两个方面都不可靠。一是**竞态**：“检查存在”和“写入 PID”是两个分开的动作，两个进程可能同时检查、同时认为文件不存在，然后都启动，互斥失效。要消除竞态就得用 `O_CREAT | O_EXCL` 这样的原子创建，等于自己在重造一把锁。二是**陈旧锁**：如果进程被 `kill -9`，锁文件会留在那里，后来的进程只能猜“这个 PID 还活着吗”——而 PID 会被回收给新进程，猜测结果可能是错的（[操作系统、进程与线程](../03-计算机系统/11-操作系统进程与线程.md) §11.5 讲的进程树与 PID 回收是同一件事）。要可靠地判断“持有者是否还活着”，等于把内核已经做好的事再做一遍。

```bash
# 对照：flock 的阻塞语义在命令行里使用（同一台 Linux 机器）
flock /tmp/demo.lock -c 'echo 拿到锁了; sleep 2'
# 若另一个进程正持有该锁，这条命令会一直等到它释放；加 -n 则立即以非零码失败
```

**边界**：`flock` 是**咨询锁**（advisory lock）——内核只负责在大家都来申请锁时维持互斥，它不会阻止你直接 `echo x > file`。所以锁文件一般单独用一个空文件（如 `/var/lock/xxx.lock`），被保护的数据文件本身不参与加锁。另外，网络文件系统（NFS）上的锁语义与本地文件系统不同，跨机器互斥不要假设它一定有效。

## $\rm \S \, 3.12$ 名字里带 `-` 和带空格的敌人

### $\rm \S \, 3.12.1$ 以 `-` 开头的文件名

大多数命令行程序按位置区分“选项”和“参数”：**看到以 `-` 开头的词就当成选项**。所以一个叫 `-draft.txt` 的文件会被当成一组选项字母：

```bash
# 前置：Bash（Linux/WSL/Git Bash）；当前目录是你自己建的练习目录
touch -- -draft.txt       # 造一个以 - 开头的文件
cat -draft.txt            # 失败
# cat: unknown option -- d  （措辞随版本略有差异，重点是它把 -draft.txt 当成了选项）
```

`--` 是命令行里的**选项结束标记**：它告诉程序“从这里往后全是参数，不要再解析选项了”。这不是某个工具的特殊规则，而是 POSIX 的通用约定，绝大多数 GNU 工具都遵守：

```bash
cat -- -draft.txt         # 成功：打印文件内容
cat ./-draft.txt          # 也成功：显式写成当前目录下的路径，第一个字符不再是 -
rm -- -draft.txt          # 删除它；删错时的报错会提示 "Try 'rm ./-draft.txt'"
```

两种写法都只在**你自己造的练习目录**里用；`--` 不是“忽略一切错误”的开关，它只影响选项解析。顺带一提，`rm` 的报错里那句 `Try 'rm ./-draft.txt'` 就是它主动给出的正确写法，看到这类提示不要跳过。

### $\rm \S \, 3.12.2$ 空格、换行与 `-print0`

文件名里可以包含空格、制表符甚至换行符（Unix 上只有 `/` 和 NUL 不能出现在文件名里）。依赖“空格分词”或“按行读取”的命令接上这类文件名就会做错事，最危险的是删除：

```bash
# 反例：无法这样运行，只需要理解错在哪
# 假设目录里有一个文件名叫 "my paper.txt"（中间是空格）
rm $files              # 未加引号的变量被按空格切成两段，实际执行的是 rm my paper.txt
                       # 即分别删除 my 和 paper.txt —— 两个完全不同的文件
```

这类错误在通配符场景下更隐蔽：`rm *.txt` 由 Shell 负责展开，Shell 会把带空格的名字当作**一个**参数交给 `rm`，所以它是安全的；但如果把文件列表用管道交给 `xargs`，而 `xargs` 按空白切分输入，文件名就会被拆碎，甚至把一个文件的半截名字当成另一个文件去删。所以**任何“把文件名列表传给下一个命令”的场合，都要用 NUL 而不是空白作为分隔符**：

```bash
# 前置：Bash（Git Bash 也有 find/xargs）；当前目录下的文件可能含空格或换行
find . -name '*.tmp' -print0 | xargs -0 rm -- -i
#   -print0 让 find 用 NUL 分隔输出；-0 让 xargs 按 NUL 切分；-- 保证以 - 开头的名字不被当成选项
#   删之前先核对：find . -name '*.tmp' -print 看清单，确认范围正确再换成上面这条
```

`find`、`xargs` 的完整用法（`-exec` 与 `xargs` 的选择、统计行数的陷阱）在[开发者命令行工具箱](07-开发者命令行工具箱.md) §7.2.7；这里只补上安全边界的那一半：**NUL 分隔 + `--` 是处理“名字不可信”的标准组合**。PowerShell 不用这套：它传递的是对象而不是文本，`Remove-Item` 收到的是文件对象，空格不构成歧义。反过来说，任何把外部程序输出（`find`、`ls`、日志解析结果）再拼成命令字符串执行的做法，在 Bash 里都要按“名字里可能有空格和 `-`”来设计。

## $\rm \S \, 3.13$ 分区、文件系统与挂载点

前面几节一直在用“一块磁盘”“一个文件系统”这样的说法。到了给服务器加盘、给虚拟机动扩容、或者往移动硬盘上装系统的时候，这几个词就会被混着用，而它们指的不是同一件事。

**磁盘**（disk）是物理设备，`/dev/nvme0n1`、`/dev/sda` 这样的设备文件代表它。**分区**（partition）是磁盘上的一段连续区域，用分区表（MBR 或 GPT）描述，例如 `/dev/sda1`、`/dev/sda2`。**文件系统**（filesystem）是格式化的产物：在某个分区（或整个磁盘、或一个 LVM 逻辑卷）上建立起来的、能存文件和目录的组织结构，`ext4`、`xfs`、`APFS`、`NTFS` 都是文件系统的类型名。**卷**（volume）是更上层的逻辑概念，一个卷对使用者呈现为“一块可以存放文件系统的空间”，它背后可能是一个分区、多个分区拼成的逻辑卷，或一块云盘。四者的包含关系是：

```text
磁盘 /dev/sda
 ├── 分区 /dev/sda1  → 格式化 → 文件系统 ext4  → 挂载到 /home
 └── 分区 /dev/sda2  → 格式化 → 文件系统 xfs   → 挂载到 /var
```

**挂载点**（mount point）是文件系统接入目录树的位置。§3.1 说过 Unix 只有一棵树，但这棵树并不都在同一块盘上——`/home` 可以来自第一块盘，`/var` 来自第二块，`/mnt/backup` 是一块移动硬盘。一个目录一旦成为挂载点，它原先的内容就被挡住了，直到卸载（unmount）才重新可见。这正是“磁盘满”为什么总发生在**某个具体位置**而不是“整个系统”：空间是按文件系统算的，写满 `/var` 的日志不会自动借用 `/home` 的空闲空间。

```bash
# 前置：Linux（WSL 也可）。Git Bash 下 mount/df 存在但输出是 MSYS 的模拟映射，数值不代表真实分区
mount | column -t        # 谁挂在哪里，以及文件系统类型与挂载选项
df -h                    # 每个已挂载文件系统的容量；Mounted on 一列就是挂载点
lsblk                    # 树状列出磁盘→分区→挂载点（部分发行版需装 util-linux）
```

读 `df -h` 时最实用的一条对应关系是：**一行输出 = 一个挂载的文件系统**，因此“这台机器有几个盘”看 `lsblk`，“我的程序到底写在哪个空间里”看 `df` 的 `Mounted on`。判断一个进程当前目录属于哪个文件系统，可以这样确认挂载点：

```bash
df -h .                 # 当前目录所在文件系统的容量与挂载点
df -h /var/log          # 某个具体路径所在文件系统——排查日志写满时最常用
```

> **平台说明**：Windows 的模型不同。“分区”和“卷”在磁盘管理里基本是同一个东西，每个卷通常直接对应一个盘符（`C:`、`D:`）或一个挂载目录（如 `C:\Data`），文件系统多为 NTFS；没有 `/etc/fstab`，也没有卸载的概念。`Get-PSDrive -PSProvider FileSystem` 或 `Get-Volume` 可以看到各卷的容量与剩余空间，对应 `df -h` 的角色。跨平台开发中真正需要记住的差异只有一条：**Linux 上“空间”的边界是挂载点，Windows 上是盘符**。

## $\rm \S \, 3.14$ setuid 与 sticky：两个特殊权限位

权限位还有三个不常用的位置：所有者的 `x` 位上如果是 `s`，表示 **setuid**（Set User ID）；组权限的 `x` 位上是 `s`，表示 **setgid**（Set Group ID）；其他人权限的 `x` 位上是 `t`，表示 **sticky**（粘滞位）。它们解决的都是“普通用户需要完成一件只有特权身份才能完成的事”这一类问题，只是解法不同。

`passwd` 是最经典的例子。每个用户都能改自己的密码，而密码的哈希存在 `/etc/shadow` 里——这个文件只有 root 能读（更不用说写）：

```bash
# 前置：Linux（WSL 也可）；只读命令
ls -l /etc/shadow
# -rw-r----- 1 root shadow ... /etc/shadow
ls -l /usr/bin/passwd
# -rwsr-xr-x 1 root root   ... /usr/bin/passwd
#   ↑ 所有者权限里是 s 而不是 x
```

`passwd` 的所有者是 root 且带 setuid 位，所以**任何用户执行它时，这个进程的有效身份都临时变成 root**；程序内部再用这个特权去写 `/etc/shadow`。也就是说：普通用户并没有获得 root 权限，只是被允许运行一段 root 写好的、只做一件事的代码。这个区别是整套机制的价值所在。

代价同样明显：如果带 setuid 的程序有任何漏洞（缓冲区溢出、路径未校验、调用了可被替换的外部命令），攻击者就能借它获得 root——这类漏洞在历史上出现过很多次。所以：

> **安全警告**：不要给自己写的程序随手加 setuid。`sudo chmod u+s ./my-script` 正确的前提是“你完整审查过这段代码、确认它不会执行攻击者可控的输入”，而脚本文件本身几乎总是错的选择（解释器会忽略脚本上的 setuid 位，这也是多数系统的有意设计）。需要让普通用户执行特定特权操作时，正确的工具是 `sudo` 配置——它把“谁能以什么身份运行哪条具体命令”写成可审计的规则，而这属于系统管理范畴，本章不展开。你能做的是：看到 `-rws` 先停下来想一想这是谁装的、是否还在用。

sticky 位解决另一个问题。`/tmp` 必须让所有用户都能创建文件，所以它是 `drwxrwxrwt`——注意最后那个 `t`：

```bash
ls -ld /tmp
# drwxrwxrwt ... /tmp
```

如果只有 `rwxrwxrwx`，任何人都能删除别人的文件（回忆 §3.1：删除文件靠的是对**父目录**的写权限，与文件自身权限无关）。sticky 位给目录加了一条额外规则：**在这个目录里，只有文件的所有者、目录的所有者或 root 才能删除/改名它**。于是任何人都能在 `/tmp` 建文件，但删不掉别人的——这正是程序用 `/tmp` 放临时文件却互不干扰的机制保障。而实际的防护要求比这还高一层：因为 `/tmp` 全局可写，程序必须用带随机性的名字创建文件（`mktemp` 就负责这件事），否则别人可以抢先占住一个可预测的名字或抢在你之前创建同名符号链接。名字的好处在于攻击成本，这一点在[终端进阶](25-终端进阶.md) §25.8 会从脚本角度再讲。

```bash
# 前置：Linux（WSL）；这些命令改了权限位，练完请对照恢复
chmod +t shared_dir/    # 给目录加 sticky（setuid/setgid 同理：chmod u+s / g+s）
ls -ld shared_dir       # 确认输出里出现 t
chmod -t shared_dir/    # 恢复
```

顺便说清楚它们在家里和服务器上的默认状态：`/tmp` 的 sticky 是发行版预置的，`/usr/bin/passwd` 这类工具的 setuid 也是系统装的，**日常开发不需要自己动这两类权限位**。它们出现在本章的意义是让你在 `ls -l` 里认出 `s` 和 `t`，知道它们各自防的是哪一类问题，以及在看到陌生程序带 setuid 时保持警惕。

## $\rm \S \, 3.15$ 总结

本章和[终端、Shell与命令行](02-终端Shell与命令行.md)加在一起，给了你完整的“文件系统与路径操作能力”。容易踩的地方其实集中在四条：

- **路径从哪算起**：Windows 是多个盘符根组成的“森林”，Unix 只有一棵树；绝对路径从根出发，相对路径从当前目录出发，`.` 和 `..` 是它的积木。
- **“看不见”有两种机制**：隐藏文件默认不显示，Windows 还默认隐藏已知扩展名——两者都是“文件明明在，却不被识别”的常见来源。
- **通配符先确认再动手**：删除、覆盖、移动前先用只读命令看清匹配集合；`?` 在 Bash 与 PowerShell 中的含义并不完全一致（§3.5.1）。
- **链接不是副本**：删符号链接不等于删目标；换行符（Windows CRLF、Linux/macOS LF）的差异也是跨系统搬文件时才咬人。

## $\rm \S \, 3.18$ 本章自测答案

> 先闭卷作答本章“关键概念回顾”与“应用与辨析”，再核对以下答案。

### $\rm \S \, 3.18.1$ 自测答案 · 关键概念回顾
1. Windows 每个盘符有自己的根（C:\、D:\，形成“森林”）；Linux/macOS 所有存储设备挂载到唯一根 `/` 之下，所以只有一棵树。
2. 绝对路径从根目录（Windows 的盘符根、Unix 的 `/`）出发，任何位置下都指向同一目标；相对路径从当前工作目录出发。
3. `*` 匹配任意长度的任意字符，`?` 匹配恰好一个任意字符；不是一回事——Shell 通配符是 glob 模式，`grep`/`sed` 用的是正则表达式（其中 `*` 表示“重复前一个模式”）。
4. Windows 用 CRLF（`\r\n`），Linux/macOS（现代）用 LF（`\n`）；Windows 文件在 Linux 上 `cat` 时行尾出现 `^M`，Linux 文件在 Windows 记事本中会挤成一行。
5. 内核在进程的打开文件表里登记一条记录并返回一个小整数编号，之后程序读写都通过这个编号进行——用编号而不是名字，是为了在 `open` 时一次性完成“解析路径 + 检查权限”，并在文件改名之后仍能继续访问同一份数据。`rm` 只摘掉目录里的名字（unlink），只要还有 fd 指向这个 inode，数据块就不释放：磁盘空间要等进程关闭 fd（或进程退出）才回收（§3.10）。

6. `../data/file.txt`：先 `..` 到上一级 `/home/alice`，再进入 `data` 目录。
7. 你看到的名字不是完整文件名：把“新建文本文档”改名为 `data.json` 时扩展名并没有被替换，真实文件名是 `data.json.txt`——需要 `.json` 的程序因此不认它（§3.4.2）。
8. 磁盘是物理设备；分区是磁盘上的一段连续区域；文件系统是在分区/卷上格式化出来的组织结构；卷是更上层的逻辑概念，呈现为“一块可存放文件系统的空间”，背后可以是一个分区、多个分区组成的逻辑卷或云盘；挂载点是文件系统接入目录树的位置。`df -h` 的 `Mounted on` 一列就是挂载点，因此一行输出对应一个已挂载的文件系统（§3.13）。
9. `/usr/bin/passwd` 带 setuid 位且所有者为 root，任何用户执行它时进程的有效身份临时变为 root，于是能写只有 root 可写的 `/etc/shadow`——普通用户并没有获得 root 权限，只是运行了 root 写好的、只做改密码这一件事的代码。`/tmp` 的 `t`（sticky）让目录里只有文件所有者、目录所有者或 root 能删除/改名文件，别人仍可在里面新建文件，但删不掉别人的。setuid 程序一旦有漏洞就等于把 root 借给攻击者（这类漏洞历史上多次出现），所以要给它加 setuid 前必须先完整审查代码；用 `sudo` 规则做“允许执行特定特权命令”比散落 setuid 程序更可审计（§3.14）。

### $\rm \S \, 3.18.3$ 自测答案 · 加练
① `cat -draft.txt` 报 `cat: unknown option -- d`——文件名被当成选项解析了；正确写法是 `cat -- -draft.txt` 或 `cat ./-draft.txt`，让名字的第一个字符不再是 `-`（§3.12.1）。
② `flock -n` 拿不到锁就立即以非零码退出；锁由内核记在打开文件对象上，进程退出或崩溃（包括 `kill -9`）时 fd 被关闭，锁自动释放，所以不存在需要清理的陈旧状态。对比之下，写 PID 的锁文件先是“检查存在 + 写入”两个动作之间有竞态（两个进程可能同时通过检查），再者进程被强杀后锁文件会残留，而 PID 会被回收给新进程，靠它判断持有者是否还活着并不可靠（§3.11）。
③ `-print0` 让 find 用 NUL 分隔文件名，`-0` 让 xargs 按 NUL 切分——空格和换行都不再被当成分隔符，以 `-` 开头的名字也不会被解析成选项（§3.12.2）。

> **练习二**（可随时重做）：在本章自己造的练习目录里做三件事——① 用 `: >` 与 `rm` 各清一次临时日志，比较 `df` 的变化；② 用 `flock -n` 让同一个脚本互斥（Linux）；③ 用 `find ... -print0 | xargs -0` 安全处理一个名字含空格的文件。
