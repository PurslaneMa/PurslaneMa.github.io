# $\rm Chapter \, 6$ 隔离与沙箱

> **本章假设你已经会**
>
> 1. 系统调用是用户程序进内核的唯一一扇门：执行时 CPU 从用户态切进内核态，内核做完再交回结果，见《操作系统》§1.3 与《计算机速通》§11.1。本章 §6.1 把这扇门的「宽度」实测出来。
> 2. 最小权限与纵深防御两条设计原则（§1.3），以及完美安全不存在、安全是抬成本曲线的说法（§1.6）。本章的全部机制都在给这两条原则找工程抓手。
> 3. canary、NX、ASLR 各防什么（§2.4 与 §2.5）。本章回答一个它们没回答的问题：当缓冲区溢出仍然发生时，一个被劫持的进程最多能伤害到哪儿。
> 4. 同源策略是浏览器给 Web 画的院子（§4.1）。本章 §6.4 讲这个院子被加固成实体围墙的过程。
> 5. 会在 WSL 的 Bash 里编译运行 C 程序（第 2 章的实验环境）。本章实验脚本与输出存 `_uni5_work/expSEC06/`。

前五章的攻击有一个共同前提：攻击代码与受害数据处在同一个进程里。栈溢出劫持的是本进程的控制流（第 2 章），XSS 执行的是本页面的解释器（第 4 章）。本章研究的前提变了：**防御失效是常态，问题是失效时的爆炸半径**。一个被完全攻陷的进程，凭它的身份最多能做哪些事？这件事由「隔离」决定：用户与内核之间隔着一扇门，用户与用户之间隔着权限位，进程与自己的危险能力之间可以再装一道过滤器，站点与站点之间隔着一栋栋独立的楼，系统与系统之间隔着内核或 hypervisor。这些边界强度不同、代价不同，本章逐个量过去。全册心智模型在这里的表现形式很直接：隔离就是给目录里的每种失效方式划定它够不着的下一层。

## $\rm \S \, 6.1$ 先量出被保护的东西：系统调用面

一个被攻陷的进程能对系统做什么？这个问题的答案出奇地干净：它能动用的一切特权，都来自它能发起的系统调用。第 2 章劫持控制流拿到的是进程自己的全部权力，而进程的权力清单就写在系统调用表上。所以谈隔离之前，先把这份清单量出来。

实测环境：WSL2（Ubuntu 24.04，内核 6.6.87，strace 6.8，gcc，python 3.12.3），脚本与完整输出在 `_uni5_work/expSEC06/`。内核暴露的系统调用入口总数直接数头文件：

```bash
# Bash（WSL）。统计 x86-64 系统调用表里的入口数
grep -c '#define __NR' /usr/include/x86_64-linux-gnu/asm/unistd_64.h
# 输出：373
```

再对一个「什么都不干」的 C 程序和一个等价的 python 一行程序各跑一次 `strace -c`，把每次调用按内核服务类别归类：

| 程序 | 用过的调用种类 | 总次数 | 大头在哪 |
| --- | --- | --- | --- |
| `hello.c`：一次 `write` 后返回 | 17 | 30 | mmap 8 次、mprotect 3 次（动态链接装内存）；openat 2 次（找 libc） |
| `python3 -c "print('hi')"` | 32 | 540 | newfstatat 119 次、fstat 61 次、read 48 次、openat 46 次（扫描模块路径）；rt_sigaction 66 次 |

采集命令与原始输出节选（`strace -c` 不逐条打印，只在结束时给汇总表，要读的是 calls 与 errors 两列）：

```bash
# Bash（WSL）。脚本与完整输出在 _uni5_work/expSEC06/
gcc -O2 -o hello_c hello.c            # hello.c 全文：一次 write("hi\n") 加 return 0
strace -c ./hello_c
strace -c python3 -c "print('hi')"
```

```text
% time  seconds  usecs/call  calls  errors  syscall      ← hello_c 汇总表节选
 27.62  0.000372         46      8        mmap
 13.44  0.000181         90      2        openat
  8.31  0.000112        112      1   1    access
  4.08  0.000055         55      1        write
------ ----------- ----------- ----- ------  -------
100.00  0.001347         44     30   1    total
```

30 次里只有最后那次 `write` 是业务，其余 29 次是进程出生的手续：动态链接器用 `openat` 找到 libc、`mmap` 把它装进地址空间、`mprotect` 给代码页上只读执行保护。python 那边 540 次的大头是 `newfstatat` 与 `openat` 反复探测模块搜索路径，也是手续。errors 列里藏着一个容易被漏看的观察：python 的 26 次 `ioctl` 全部报错仍不影响它正常打印，因为那是在探测「stdout 是不是终端」，被拒绝本身就是探测的预期结果。所以量攻击面要看「用过的种类」，不是「成功的种类」。

两个数都远小于 373，但 python 的面是 C 版本的两倍宽、调用量是十八倍。攻击面（attack surface）这个词在进程粒度上可以给出精确含义：

$$
A(P) = \{\, s \in \mathcal{S} \;\mid\; \text{进程 } P \text{ 在运行中可以发起系统调用 } s \,\}, \qquad |\mathcal{S}| = 373
$$

读法：$\mathcal{S}$ 是内核开门受理的全部业务清单，$A(P)$ 是进程 $P$ 实际递得进来的申请单种类；一个被劫持进程的破坏力上限，就是 $A(P)$ 里那些调用在它权限下能做成的事的总和。

白话：系统调用像政务大厅的窗口，一共 373 个窗口，但一个只会打一行字的小程序其实只走了 17 个窗口；剩下三百多个窗口对它照样开着，只是它没去办过业务。沙箱要干的事，是把用不着的窗口直接焊死。

这给出本章的第一条主线：**程序需要的面和内核暴露的面之间有大片空隙**。哪怕一个程序 373 个调用一个都不多要，它在被劫持后仍能申请全部 373 项业务，除非有人提前把空隙填掉。谁来填、怎么填，是后面三节的内容。

**本节小结**：被攻陷进程的权力上限等于它的系统调用面；实测一行 C 程序用了 373 个内核入口中的 17 种、一行 python 用了 32 种，空隙巨大，收缩空间也巨大。

## $\rm \S \, 6.2$ 权限位与能力模型：最老的隔离，防的是谁

进程与进程之间的第一道隔离早于一切现代机制：文件上的九个权限位。先看实测（ext4 文件系统上，普通用户 `purslane`，uid 1000）：

```bash
# Bash（WSL，家目录下，ext4；为什么不能在 /mnt/c 上做，见下面踩坑记录）
echo "vault content 20261106" > vault.txt
chmod 000 vault.txt        # 三组权限全部清零，ls -l 显示 ----------
cat vault.txt              # cat: vault.txt: Permission denied
echo hack >> vault.txt     # bash: vault.txt: Permission denied
```

同一个 `cat`，换成 uid 0 再跑一遍（WSL 里用 `wsl -u root`，等价于 sudo）：

```text
# uid 0 下
---------- 1 purslane purslane 23 ... vault.txt
$ cat vault.txt
vault content 20261106          ← 读到了，权限位形同虚设
```

一个真实踩过的坑先记在这里，它顺带暴露了权限位的本质。同样的三条命令搬到 `/mnt/c`（WSL 挂载的 Windows NTFS 分区）重跑：`chmod 000` 不报错，`ls -l` 显示的却是 `-r-xr-xr-x`（只清掉了写位），`cat` 照样读出全文，退出码 0（对照组输出存 `_uni5_work/expSEC06/result.txt` 第 7 节）。原因：九个位的存储与比对是具体文件系统实现代码里的逻辑，ext4 在内核里老老实实记着它们，每次 `open` 都查一遍；NTFS 经 drvfs 驱动挂载时默认不保存这套元数据，`chmod` 退化成一场模拟表演，读与执行根本拦不住。教训：隔离机制不是命令自带的魔法，它寄生在某一层具体实现上，换一层存储，同一道门就不存在了。这个「门是哪段代码在哪看守的」之问，后面每一节都要问一遍。

机制只有两句话。第一句：检查发生在内核。进程发起 `open` 时，内核取出进程的有效 uid/gid 与文件的属主 uid、属组、九个权限位，按下面这条规则选一组三位来比对（$r{=}4$，$w{=}2$，$x{=}1$）：

$$
\text{比对位} =
\begin{cases}
\text{属主三位}, & \text{进程 uid} = \text{文件属主 uid} \\
\text{属组三位}, & \text{进程 gid 命中文件属组} \\
\text{其他三位}, & \text{前两条都不满足}
\end{cases}
$$

读法：先挑「你是谁」对应的那一列，再检查该列里有没有请求的位；三列互为备胎，前面的命中就不再看后面。`chmod 000` 把三列全部清零，uid 1000 的比对无论走哪列都拿不到 $r$ 位，于是被拒。

第二句解释 root 的行为：检查是内核做的，而内核的比对代码里有一条例外条款，uid 0 直接放行。uid 0 不是权限更高的人，是检查规则本身给他的免检通道。

这条免检通道正是要害。传统 Unix 把 uid 0 当成一个不可拆的大权限：要改系统时间、要监听 80 端口、要挂载磁盘，都得整个当 root。于是守护进程被迫以 uid 0 运行，任何一个漏洞都等于整机沦陷。Linux 的能力模型（capabilities）把这包大权限拆成了可单独授予的小项，本机内核 6.6.87 的头文件数出 41 项（从 CAP_CHOWN=0 到 CAP_CHECKPOINT_RESTORE=40）：监听低端口只需 CAP_NET_BIND_SERVICE，改时间只需 CAP_SYS_TIME，其余照旧不给。root 从「全有」变成「41 张单独的票，默认全持，可以只发几张」。

白话：权限位像小区门禁，管得住住户互串门；root 是物业总管，一张卡刷开所有门；能力模型是把总管的那张万能卡换成 41 张单门卡，请人帮忙修水管时只发管网道的卡，丢了一张不至于全楼失守。

但权限位隔离有一个结构性局限，值得停下来说清：它划界的单位是「用户 vs 文件」，不是「进程 vs 文件」。同一个 uid 下跑着十个进程，任何一个被攻陷，另外九个能读的文件它照样能读——第 2 章那种控制流劫持拿到的是完整用户身份，权限位对此一步都不拦。划界单位必须从用户降到进程，这就是下一节。

**本节小结**：权限位在内核里按 uid/gid 比对九个位（实测 chmod 000 拒掉 uid 1000、放行 uid 0）；root 是免检通道，能力模型把它拆成 41 张单门卡；这套隔离防用户互踩，不防同用户的单个进程沦陷。

## $\rm \S \, 6.3$ seccomp：把 373 个窗口焊到 2 个

新问题很具体：能不能不给整个用户降权，只给这一个进程收缩 $A(P)$？Linux 的答案是 seccomp（secure computing mode）：进程可以主动申请在系统调用门口装一个过滤器，此后每次发起系统调用，内核先让过滤器裁决，放行才真正执行。过滤器本身是一小段 BPF 程序（Berkeley Packet Filter，内核里的一种可验证字节码），逻辑就是白名单。

实测走一遍。下面的程序先正常打印，然后安装「只允许 `write` 和 `exit_group`」的过滤器，再试着调用 getpid 和 open（完整源码 `seccomp_min.c`，WSL gcc 编译运行）：

```text
[before] getpid() = 710
[after ] getpid() 返回 -1, errno = 1 (Operation not permitted)
[after ] open("/etc/passwd") = -1, errno = 1 (Operation not permitted)
[after ] 进程仍在运行：被拒绝的只是那两次系统调用，不是整个进程
退出码 0
```

同一个进程，装过滤器前后判若两界：装上之后，内核 373 个窗口里还肯真正办业务的只剩 2 个，其余一律当场退单。用 §6.1 的记号说，从「发起即执行」变成「白名单才执行」，$A(P)$ 里能落地的那部分被裁成了名单本身：

$$
\text{decision}(s) =
\begin{cases}
\text{ALLOW}, & s \in \{\text{write},\ \text{exit\_group}\} \\
\text{ERRNO(EPERM)}, & \text{其余 } 371 \text{ 个}
\end{cases}
$$

读法：过滤器是挂在大厅门口的一张白名单，命中名单的窗口照走，其余申请当场退回；返回 EPERM 而不是杀死进程，是为了让程序有机会优雅降级，把拒绝当错误码处理。

名单不是配置文件，是一小段真正的程序。`seccomp_min.c` 里那个白名单长这样（逐条横着读：每条指令要么取一个字段，要么比较跳转，要么返回裁决）：

```c
struct sock_filter prog[] = {
    BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof(struct seccomp_data, arch)),
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, AUDIT_ARCH_X86_64, 1, 0),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_KILL_PROCESS),  /* 架构不符：杀进程 */
    BPF_STMT(BPF_LD | BPF_W | BPF_ABS, offsetof(struct seccomp_data, nr)),
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_write, 0, 1),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),         /* write：放行 */
    BPF_JUMP(BPF_JMP | BPF_JEQ | BPF_K, __NR_exit_group, 0, 1),
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ALLOW),         /* exit_group：放行 */
    BPF_STMT(BPF_RET | BPF_K, SECCOMP_RET_ERRNO | 1),     /* 其余：EPERM */
};
```

头一查的不是调用号而是体系结构号：x86-64 之外还有 32 位兼容层，两边系统调用编号表不同，只看调用号的白名单会被兼容层绕成筛子，所以架构不符的裁决是最重的杀进程而不是退单。完整源码与编译命令在 `_uni5_work/expSEC06/`。

源码里还有三个设计点，每个都对应一条原则。其一，白名单只放 `write` 和 `exit_group`，是 §1.3 最小权限的极端形式：宁可先饿死再逐项放开，也不从「全开」出发。其二，内核的 BPF 验证器在装载时逐条检查这段代码没有循环、没有越界读写，保证过滤器本身不会成为新的攻击面，这是「检查者不可被检查对象攻破」。其三，安装前必须置 PR_SET_NO_NEW_PRIVS 标志：此后进程及其所有子进程即使 exec 一个带 setuid 的程序也拿不到新权限，过滤器代代继承，防止「装了沙箱再借外挂提权」的绕路。

代价也要记在账上（§1.6 的成本曲线）：白名单必须枚举程序真正需要的每个调用，枚举漏一个，程序在某个没测过的路径上突然报错；枚举放一个，攻击面就回来一分。所以实践中 seccomp 很少单独用，而是嵌进一整套进程级限制里：namespace 裁剪它的可见世界（《操作系统》§13），cgroup 限额它的资源用量，再叠加 seccomp 收缩它的申请单种类。这套组合在应用层有个俗名，沙箱（sandbox）。Chrome 浏览器的渲染进程、systemd 服务单元的 `SystemCallFilter=` 指令、OpenBSD 的 pledge，都是同一思想在不同系统里的落法。

白话：§6.2 的能力模型是把物业总管的万能卡换成单门卡，seccomp 则更进一步：直接规定这个人除了「投递」和「下班」，其余窗口连申请资格都没有，而且这张资格清单写进他的劳动合同，换岗（exec）也不清零。

**本节小结**：seccomp 在系统调用门口装白名单过滤器，实测把一个进程的面从几十种收缩到 2 种；它的价值不在这一道闸，而在与 namespace、cgroup 组合成进程粒度的沙箱。

## $\rm \S \, 6.4$ 浏览器沙箱与站点隔离：把逻辑边界砌成实体墙

同一套思想在浏览器里有一场更大规模的施工。第 4 章讲过，同源策略是浏览器执行的规则：一份文档的脚本读不到另一源的响应（§4.1）。注意这条防线的性质：它是**逻辑边界**，存在形式是浏览器代码里的一堆 if 判断。攻击者的目标于是不是「翻墙」，而是「骗过查岗」：第 4 章的 XSS 让恶意代码混进受害页面内部，从院子里发难；更彻底的一类（如 2018 年公开的 Spectre 类侧信道攻击）连院子都不进，直接利用硬件的推测执行从旁测量受害页面的内存。逻辑边界对后者毫无办法，因为推测执行不经过浏览器的检查函数。

加固的思路是把逻辑边界落到操作系统已经造好的物理边界上，分两步。第一步，站点隔离（site isolation）：浏览器不再把所有网站塞进一个进程，而是每个站点一个渲染进程。进程边界意味着地址空间隔离（虚拟内存保证《操作系统》§4），一个进程的指针再怎么越界也够不到另一个进程的内存；侧信道要跨进程测量，难度抬升一大截。Chrome 在桌面版从 2018 年的 Chrome 67 起默认全开站点隔离，这是一条可验证的行业事实，不是经验规则。

第二步，把每个渲染进程按 §6.3 的路数关进 OS 级沙箱。渲染进程的 $A(P)$ 被砍到接近于零：没有文件系统、没有网络、没有新进程，373 个窗口几乎全部焊死。它想下载文件、发网络请求，只能通过 IPC（进程间通信）向父进程提交申请，由持权进程审查后代办。这个结构叫 broker 模式：危险能力集中在一个审查点，被隔离者只留一条受监督的申请通道。回头看本章的语言，两步各对应一个收缩：站点隔离把「能读谁的内存」收缩到本进程，沙箱把「能发起什么系统调用」收缩到近乎空集。同源策略那张门禁名单还在，但它背后多了实体墙，查岗被骗的代价不再是失守全城。

白话：原来全城住户共用一个院子，保安（同源策略）靠一张名单查岗，骗子表演一下就能混进去顺走邻居的东西；现在每家公司一栋独立楼（进程隔离），楼里的人连楼门都出不去（沙箱），买饭取快递都得打电话让前台代办（broker），前台不批就没有。

**本节小结**：同源策略是逻辑边界，Spectre 类攻击证明逻辑边界可被硬件层绕过；站点隔离把它落到进程边界，broker 模式再落到系统调用边界，逻辑防线第一次有了实体承重墙。

## $\rm \S \, 6.5$ 虚拟机与容器：两种隔离的账

把镜头拉到最外层：操作系统本身被攻陷怎么办，或者，多个互不信任的负载要挤在同一台机器上怎么办。两个主流答案《操作系统》已经拆过账：容器是 namespace 加 cgroup（《操作系统》§13），虚拟机是硬件虚拟化加独立内核（《操作系统》§14）。这里按本章的口径重记一遍：**共享什么、不共享什么、门在哪**。先固定一个词的用法：逃逸（escape），指突破一道隔离边界、拿到边界之外权力的事件，「容器逃逸」即容器内进程获得了宿主层面的权力。比较隔离强度，比的正是「实现一次逃逸需要接连攻破什么」。

| 维度 | 虚拟机（VM） | 容器 |
| --- | --- | --- |
| 内核 | guest 自带一个，与宿主无关 | 共享宿主那一个内核 |
| 隔离机制 | 硬件虚拟化：CPU 多一层态，敏感指令陷入 hypervisor | namespace 裁剪视图，cgroup 限额用量 |
| 进程身份 | guest 内核眼里的进程，宿主管不着 | 就是宿主上的普通进程（《计算机速通》§11.8.2） |
| 「门」在哪 | hypervisor 的 hypercall 与虚拟设备接口 | 宿主内核的 373 个系统调用 |
| 逃逸的含义 | 攻破 hypervisor 本身 | 在宿主内核里完成一次提权 |

表里最重要的行是最后一行，它直接接回 §6.1 的账。容器内进程发起系统调用，走的就是宿主内核的 373 个门，内核里一个可从用户态触发的漏洞，对所有容器与宿主同时成立，因为它们本来就是同一个内核。虚拟机把这条路堵住了：guest 里无论怎么闹，特权操作最终都要穿过 hypervisor 这一层的接口出去，而 hypervisor 暴露的接口面（hypercall 加虚拟设备）比 373 个系统调用窄得多，guest 内核的漏洞还需要第二跳才能出去。所以「VM 隔离强于容器」不是玄学，是攻击面宽度的账：跨出 VM 要连破两道更窄的门，跨出容器只需一道更宽的门。这句话是经验规则而非定理——hypervisor 的漏洞历史上确实存在过，届时两道窄门一样会被跨过去。

那为什么容器没有因此被淘汰？因为隔离从来是成本曲线（§1.6）：容器启动毫秒级、密度高、运维简单，VM 每个实例要养一个完整内核，启动以十秒计、内存以 GB 计。工程实践按信任边界选型：跑别人的不可信代码，用 VM（CI 服务给租户起虚拟机）；跑自己团队的多个服务，用容器加纵深（只读根文件系统、非 root 用户、seccomp 白名单、capabilities 白名单全上）。同一台机器上两层也可以叠用——容器跑在 VM 里， Docker Desktop 在 macOS 与 Windows 上正是这么实现的（《计算机速通》§11.8.2）。

白话：容器是合租，一间大公寓隔成几间，房租便宜、搬进来快，但厨房自来水是同一套，房子地基（内核）裂了大家一起塌；VM 是每人一栋小楼，连地基都是各自的，贵，但邻居炸厨房与你无关。合租要想安全，得给每个租客上满 §6.3 那一整套约束。

**本节小结**：VM 与容器的差别不是「隔离旋钮的档位」，而是门的位置：容器的门就是宿主内核的全部系统调用，VM 的门是窄得多的 hypervisor 接口；按信任边界与成本曲线选型，而不是背一个「谁更安全」的定论。

## $\rm \S \, 6.7$ 应用与辨析

1. 同事说：「我们服务已经用非 root 用户跑了，权限位管着，不需要 seccomp。」指出这句话混淆了哪两层的隔离，并给出一个权限位完全无能为力、seccomp 却能拦下的具体攻击场景。
2. 论文资料管理器的后端要部署成 systemd 服务。利用本章三个机制各设计一道闸：说明每道闸收缩的是 $A(P)$ 的哪个维度，以及一道闸被绕过时另外两道如何兜底（纵深防御，§1.3）。
3. 某团队图省事，把不受信任的用户代码直接跑在宿主机的 Docker 容器里，理由是「容器就是沙箱」。用 §6.5 的账说明这句话错在哪，并给出最低成本的正确做法。

## $\rm \S \, 6.8$ 答案

6.6.1：$A(P) = \{\, s \in \mathcal{S} \mid P \text{ 可以发起系统调用 } s \,\}$，$\mathcal{S}$ 是内核系统调用表，本机实测 $|\mathcal{S}| = 373$（§6.1）。一行 C 程序用到 17 种、30 次，一行 python 用到 32 种、540 次：程序对内核的依赖集中于少数窗口，而未用到的窗口对被劫持进程照常开放，这个差就是沙箱的收缩空间（§6.1）。

6.6.2：uid 1000 被拒是因为权限比对发生在内核，uid 1000 无论按属主、属组还是其他列比对，`chmod 000` 后都取不到 $r$ 位（§6.2 第一句）；uid 0 成功是因为内核检查代码里有免检通道，root 的权力来自检查规则本身（§6.2 第二句）。能力模型把传统 uid 0 的整包权力拆成 41 项单独授予的小能力，解决的是「守护进程被迫持全套 root 权力，一个漏洞整机沦陷」的问题（§6.2）。

6.6.3：返回 EPERM 让被拒调用退化成一个普通错误码，程序可以捕获、降级、继续跑完该做的事，沙箱从「处决者」变成「审查窗口」，也便于发现枚举漏项（§6.3）。NO_NEW_PRIVS 堵的绕路是：装完过滤器后 exec 一个 setuid-root 程序借外壳提权；置位后子进程不再获得新特权，过滤器随 exec 继承（§6.3）。

6.6.4：同源策略划的是浏览器解释层的逻辑边界，存在形式是检查代码里的规则，可被 XSS 这类混入院内的攻击与 Spectre 这类绕过检查的侧信道绕过（§6.4）；站点隔离把它落到进程边界，沙箱再落到系统调用边界。区别在于：逻辑边界由一段代码的判断保证，判断被绕过即作废；物理边界由地址空间隔离与特权级保证，绕过需要攻破内核或 CPU 这类更底层的部件（§6.4）。

6.6.5：容器逃逸意味着在宿主内核完成一次提权，因为容器内进程走的就是宿主内核的 373 个门（§6.5）；VM 逃逸意味着攻破 hypervisor 本身，guest 的特权操作必须穿过它的接口。前者只要内核有一个可从用户态触发的漏洞，后者还需要跨过第二道更窄的门，所以内核漏洞比 hypervisor 漏洞常见得多（§6.5，经验规则）。

6.7.1：混淆的是「用户间隔离」与「进程间隔离」两层：权限位划界单位是用户，同一 uid 的任意进程共享全部文件权限（§6.2）。具体场景：服务进程被第 2 章式的 ROP 劫持后，攻击者以服务用户身份发起任意系统调用，读属于同一用户的其他凭据文件，权限位一步不拦；而 seccomp 白名单直接让 openat 返回 EPERM，攻击在系统调用边界就断了（§6.3）。

6.7.2：其一，`User=` 以专用低权用户运行，收缩的是文件系统维度：属主列拿不到 $r$ 位，碰不了其他用户的文件（§6.2）；其二，`SystemCallFilter=`（seccomp）收缩调用种类维度：HTTP 服务留 read/write/epoll 一族，execve、ptrace 一律 EPERM（§6.3）；其三，`NoNewPrivileges=` 与 capability 白名单收缩特权维度，防止借 setuid 或保留能力提权（§6.2）。兜底关系：即使服务被劫持，低权用户限制了它作为 uid 能做什么；即使它尝试借道提权，NoNewPrivileges 与 capability 过滤在内核层拦截；即使前两道配置有漏项，SystemCallFilter 使多数危险操作连申请资格都没有。任一单道被绕过，其余两道仍把损失限制在 §1.3 最小权限的范围内。

6.7.3：错在把「视图隔离」当成了「信任边界」：容器内进程是宿主普通进程（《计算机速通》§11.8.2），它的门就是宿主内核的 373 个系统调用，用户代码里一个内核漏洞触发表（如第 3 章的 UAF 类内核可触发路径）即可对所有容器与宿主同时成立（§6.5）。最低成本的正确做法：宿主与不可信负载之间加一层 VM，用户代码跑在 VM 内的容器里（云 CI 的通用做法），并在容器内照常上非 root、只读根文件系统与 seccomp（§6.3、§6.5）。

> 你现在能：用 `strace -c` 与一个 grep 把一台机器的系统调用面量出来；解释 chmod 000 在 uid 1000 与 uid 0 下的不同结果来自内核哪两句话；读懂一段 seccomp 白名单并说出 NO_NEW_PRIVS 堵的是哪条路；对任意一段「隔离」宣称，追问它共享了什么、门在哪、逃逸等于攻破什么。

本章给目录里的失效方式画了边界：内核的 373 个门、用户的免检通道、进程的白名单、浏览器的实体墙、hypervisor 的窄门。但到目前为止，门都画在同一台机器上。攻击者与防御者之间还隔着网络这道看不见的墙：数据出门之后，谁在听、谁能改、你怎么知道对端就是它声称的那一个？下一章把三条威胁（窃听、篡改、冒充）与把它们一并关门的 TLS 摊开来讲。
