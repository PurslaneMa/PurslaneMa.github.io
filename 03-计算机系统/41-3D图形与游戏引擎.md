# $\rm Chapter \, 41$ 3D 图形与游戏引擎入门

> 你玩过带有逼真光影的 3D 游戏。屏幕上每一个像素的颜色——无论是阳光透过树叶的光斑还是一把枪上的金属反射——都是 GPU 在 1/60 秒内算出来的。这些像素不是“画”出来的，是经过一整套数学流水线计算出来的：三维空间中的三角形→二维屏幕上的投影→每个像素的着色→后处理。这一章拆解这条流水线，但不是让你会写游戏引擎——而是让你理解“那个游戏画面到底是怎么来的”。

> **开始前自检**：本章假设你已经会：
>
> - □ 理解光栅图像与像素（第 39 章 §39.1.1）
> - □ 学过基础几何与向量运算（竞赛基础；本章 §41.1.2 会用到顶点坐标与法线）
> - □ 玩过或看过 3D 实时渲染画面（不是前置要求；本章 §41.1 从“画面是怎么算出来的”讲起）

## $\rm \S \, 41.1$ 渲染的核心思想：模拟光的行为

### $\rm \S \, 41.1.1$ 光栅化 vs 光线追踪：两种画 3D 世界的方式

**光栅化**（rasterization）是实时渲染（游戏）的标准方法。它的流程是：

```mermaid
flowchart LR
    A["3D 模型<br/>（三角形网格）"] --> B["顶点着色器<br/>计算每个顶点的位置"]
    B --> C["光栅化<br/>三角形→像素"]
    C --> D["像素着色器<br/>计算每个像素的颜色"]
    D --> E["输出合并<br/>深度测试、混合"]
```

每一步都在[GPU 与显卡](38-GPU-CUDA与AI计算.md)里面执行——顶点着色器和像素着色器是你写的“着色器程序”（shader），在 GPU 的几千个核心上并行执行。

**光线追踪**（ray tracing）是相反的思路——从摄像机发出一条射线穿过每个像素，追踪这条射线在场景中弹跳的过程，直到它击中光源或能量耗尽。结果极其逼真（真实的反射、折射、软阴影），但计算量巨大——直到 RTX 20 系列（2018 年）才在消费级 GPU 上实现实时。

### $\rm \S \, 41.1.2$ 三角形：3D 世界的基本单位

3D 模型不是用“体积像素”表示的——是用**三角形网格**（triangle mesh）。任何一个曲面都可以用足够多的三角形逼近：

```text
球体的三角形网格：
   /\  /\  /\
  /__\/__\/__\
  \  /\  /\  /
   \/__\/__\/
```

每个三角形有三个**顶点**（vertex），每个顶点有：
- 三维位置 `(x, y, z)`
- 法线方向 `(nx, ny, nz)`——这个面“朝向”哪边，用于光照计算
- 纹理坐标 `(u, v)`——从纹理图片的哪个位置取颜色

一个典型的游戏角色模型有几千到几十万个三角形。一部皮克斯电影的模型有数百万个——它们不用实时渲染（可以花几小时算一帧）。

### $\rm \S \, 41.1.3$ 纹理与材质

三角形给了形状，但要让它看起来像木头而不是金属，需要**材质**（material）和**纹理**（texture）：

- **纹理**是一张 2D 图片，“贴”在三角形表面上。一张 1024×1024 的砖墙纹理贴在墙模型上，近看会模糊（分辨率不够）；一张 4096×4096 的纹理需要更多显存但细节更多。
- **材质**定义了这个表面如何与光交互——是粗糙的还是光滑的？是金属的还是电介质（木头/塑料/皮肤）的？不同的材质在同一光照下看起来完全不同，即使用的是同一张纹理。

在[GPU、显卡与AI计算](38-GPU-CUDA与AI计算.md)中你见过**各向异性过滤**——就是当纹理被斜着看（如远处的地面）时，在不同方向上使用不同的采样率来保持清晰。

## $\rm \S \, 41.2$ 游戏引擎不只是“渲染器”

渲染器只画画面。**游戏引擎**（game engine）包含了让游戏运转的全部系统：

| 系统 | 职责 | 类比 |
|---|---|---|
| **渲染器** | 画画面 | 整个引擎的“显示器” |
| **物理引擎** | 模拟重力、碰撞、布料、流体 | 引擎的“物理定律” |
| **音频系统** | 播放音效、3D 空间音频 | 引擎的“耳朵” |
| **脚本系统** | 定义游戏逻辑（“玩家按跳→角色向上加速”） | 引擎的“大脑” |
| **AI 系统** | NPC 行为、寻路 | 引擎的“其他玩家” |
| **网络系统** | 多人同步 | 引擎的“电话线” |
| **资源管理** | 加载/卸载纹理、模型、音频 | 引擎的“后勤” |

### $\rm \S \, 41.2.1$ 主循环

游戏引擎的核心是一个无限循环（每帧执行一次）：

```text
1. 处理输入（键盘、鼠标、手柄）
2. 更新物理（计算碰撞、移动物体）
3. 更新 AI（NPC 决策、寻路）
4. 渲染画面（光栅化/光线追踪）
5. 播放音频
6. 等待下一帧（如果超前则休眠）
```

60fps 意味着上面整个循环必须在 1/60 ≈ 16.7 毫秒内完成。某一帧明显超时（比如某帧花了 50 毫秒）就会被玩家感知为“卡顿”——偶发的单帧超时表现为顿一下，持续超时则整段画面掉帧。

### $\rm \S \, 41.2.2$ 主要游戏引擎

| 引擎 | 语言 | 特点 | 代表作 |
|---|---|---|---|
| **Unity**（unity.com） | C# | 上手门槛较低、2D/移动/VR 生态强、Asset Store 资源多 | Hollow Knight、Genshin Impact |
| **Unreal Engine**（unrealengine.com） | C++ / Blueprint | 高画质能力突出、自带 Nanite（虚拟化几何）+ Lumen（动态全局光照） | Fortnite、Black Myth: Wukong |
| **Godot**（godotengine.org） | GDScript / C# | 完全开源、轻量、无授权费 | Cassette Beasts |
| **Bevy**（bevyengine.org） | Rust | ECS 架构、WASM 目标、社区活跃（Rust 编译时间较长，首次构建尤其慢） | 新兴独立游戏 |

Unity vs Unreal 的选型不是“谁更好”的问题：Unity 更适合 2D、移动、独立开发；Unreal 的内置高画质管线更成熟，但学习曲线更陡。Godot 在独立游戏开发者中快速增长。

## $\rm \S \, 41.3$ 游戏开发中的“非游戏”技术

### $\rm \S \, 41.3.1$ 着色器语言

着色器是运行在 GPU 上的小程序。**GLSL**（OpenGL）、**HLSL**（DirectX）、**MSL**（Metal）是不同平台的着色器语言——语法和 C 类似，但没有动态内存分配、没有递归，也没有 C++ 那样庞大的标准库（只有一批内建函数）。

```glsl
// 最简顶点着色器
#version 330 core
layout (location = 0) in vec3 aPos;   // 顶点位置（从 CPU 传进来的属性）

void main() {
    gl_Position = vec4(aPos, 1.0);    // 输出：这个顶点的屏幕位置
}
```

### $\rm \S \, 41.3.2$ 物理引擎

物理引擎解决的核心问题：检测碰撞（两个物体是否碰到了？）和解决碰撞（碰到后怎么弹开？怎么滑动？）。常用的物理引擎有 **NVIDIA PhysX**（Unity/Unreal 内置）、**Bullet**（开源）、**Box2D**（2D、轻量）。

### $\rm \S \, 41.3.3$ 寻路

游戏中的敌人需要从 A 点走到 B 点——这就是寻路（pathfinding）。很多游戏用 **A\*** 算法（读作 A-star）：它就是 Dijkstra 加上启发式估价函数的版本——$f = g + h$，$g$ 是起点到当前点的实际代价，$h$ 是“到终点大概还有多远”的估计（竞赛里的启发式搜索）；$h$ 恒为 0 时就退化成 Dijkstra。导航网格（navmesh）是预先计算好的“哪些区域可以走”的地图。

## $\rm \S \, 41.4$ 跨媒体：游戏技术“溢出”到其他领域

- **Unreal Engine 用于影视制作**：迪士尼的《The Mandalorian》用 Unreal Engine 做实时虚拟背景——演员在 LED 屏幕墙前表演，背景是 Unreal 实时渲染的 3D 场景。替代了绿幕+后期合成的传统流程。
- **Unity 用于建筑可视化**：建筑师在 Unity 中构建可交互的建筑漫游，客户戴上 VR 头显“走进”还没建成的房子。
- **NVIDIA Omniverse**：基于 USD（Universal Scene Description）的协作式 3D 平台——多个设计师同时编辑同一个 3D 场景，各自用不同的工具（Maya、Blender、Unreal）。

## $\rm \S \, 41.5$ 动手实践

### $\rm \S \, 41.5.1$ 实践一：在浏览器中写着色器

起始目录与前置条件：打开 **Shadertoy**（shadertoy.com），只需浏览器，不需要安装任何东西。

打开后直接写 GLSL，实时看到渲染结果。尝试修改别人的炫酷 shader——改颜色、改参数，观察实时变化。预期输出与判据：改动后画面在约 1 秒内刷新；成功标志是颜色/形状按你的改动变化。编译失败时左下角的信息面板会给出错误行号与原因；不同 shader 依赖的输入（时间、鼠标）不同，改之前先看 `iTime`/`iMouse` 的用法。

结束与清理：只发生在浏览器里，无需清理；注意网上他人的作品有各自的许可，不要原样当成自己的提交。

### $\rm \S \, 41.5.2$ 实践二：下载 Godot 做一个最简场景

起始目录与前置条件：从 godotengine.org 下载 Godot（免费开源，编辑器压缩包约 50–100 MB，解压即用、无需安装）；显卡驱动需支持 OpenGL 3.3 / Vulkan。

1. 下载 Godot，解压后启动（首次启动会让你新建或导入项目，选“新建项目”）。
2. 创建一个 3D 场景：添加一个立方体、一个光源、一个摄像机。
3. 运行——你看到一块被照亮的立方体在屏幕中间。
4. 修改立方体的材质颜色，再次运行。

预期输出与判据：按 F5（运行项目）弹出一个窗口，中央是有明暗的立方体；第 4 步后颜色变化。若窗口全黑，先更新显卡驱动，或换用兼容渲染后端。

结束与清理：关闭运行窗口与编辑器；试验项目只是磁盘上的一个文件夹，删掉它即可，不影响系统。

### $\rm \S \, 41.5.3$ 实践三：用 Blender 打开一个 3D 模型

起始目录与前置条件：从 blender.org 下载 Blender（开源免费，安装包数百 MB），确认系统满足其最低要求。

下载后打开，观察默认的立方体模型——它由三角形网格组成。切换到线框模式（Wireframe）看三角形结构。这不是为了让你学会用 Blender——只是为了亲眼看到“3D 模型是什么”。预期输出与判据：默认场景里有立方体、摄像机和光源；按 Z 或左上角的视图模式切到 Wireframe，能看出立方体由三角形（或四边形，导出时会被三角化）拼成。

结束与清理：不需要保存——直接退出即可，不要覆盖默认启动文件；如果保存过，删掉那个临时 `.blend` 文件。

## $\rm \S \, 41.6$ 总结

- 3D 渲染 = 3D 模型（三角形网格）→ 顶点变换 → 光栅化（三角形→像素）→ 像素着色 → 屏幕。
- 光栅化是实时渲染的标准（游戏），光线追踪更逼真但更昂贵。现代 GPU 两者都做。
- 游戏引擎 = 渲染器 + 物理 + 音频 + 脚本 + AI + 网络 + 资源管理。Unity（上手门槛较低）、Unreal（内置高画质管线成熟）、Godot（开源轻量）。
- 着色器是运行在 GPU 上的小程序——和你在 CPU 上写的 C++ 程序本质不同（几万核心并行、无动态内存）。

## $\rm \S \, 41.9$ 本章自测答案

> 先闭卷作答本章“关键概念回顾”与“应用与辨析”，再核对以下答案。

### $\rm \S \, 41.9.1$ 自测答案 · 关键概念回顾
1. 光栅化把三角形网格投影到屏幕、逐像素着色（快，能满足 1/60 秒一帧）；光线追踪从摄像机发射射线、追踪它在场景中的弹跳（逼真但昂贵）。实时渲染用光栅化，影视渲染用光线追踪。
2. 任意曲面都可以用足够多的三角形逼近；三角形只有三个顶点、处理简单，GPU 的硬件流水线就是为并行处理三角形和像素设计的。
3. 渲染器之外还有物理引擎、音频系统、脚本系统、AI 系统、网络系统和资源管理——渲染器只负责画画面，让游戏“运转”的是其余系统。
4. 顶点着色器计算每个顶点在屏幕上的位置；光栅化把三角形变成屏幕像素；像素着色器计算每个像素的最终颜色（光照、纹理、混合）。

### $\rm \S \, 41.9.2$ 自测答案 · 应用与辨析
5. Unity 上手门槛较低、2D/移动/VR 生态强，适合独立开发和跨平台；Unreal 内置高画质管线（Nanite/Lumen）更成熟、学习曲线更陡，适合追求画质的 3A 项目——没有“谁更好”，取决于项目类型和团队经验。
6. A* = Dijkstra + 启发式估价函数 $h$：优先扩展 $f = g + h$ 最小的节点，用“到目标大概还有多远”引导方向，通常比 Dijkstra 扩展更少节点；$h$ 恒为 0 时就是 Dijkstra，所以本质上是同一家族的推广。
7. 着色器在 GPU 的数千个核心上并行执行、没有动态内存和递归、没有标准库——每个线程只处理一个顶点或像素，写的不是“一个程序的逻辑”，而是“对每个元素做同样的计算”。
