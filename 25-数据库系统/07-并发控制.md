# $\rm Chapter \, 7$ 并发控制：锁、隔离级别与三种读异常

第 6 章结了「崩溃」的账，本章拆第二个假设：「数据库只有一个用户」。两个连接同时读写同一批行，会出现三类教科书级的怪事：读到别人没提交的数据、同一行两次读出不同值、同一个查询两次数出不同的行数。它们叫三种读异常，隔离级别就是「允许哪几种」的旋钮。本章先用实验亲眼看到它们（以及看到 SQLite 替你挡掉了哪些），再讲旋钮背后的机制，即两阶段锁与写冲突的真实代价。

> **开始前自检**：本章假设你已经会：
>
> 1. □ 说明 ACID 里 I（隔离性）防的是「并发互相插队」（§6.2）；
> 2. □ 解释 SQLite 库级单写锁如何让「交叉写死锁」结构上不可能（操作系统分册 §7.4）；
> 3. □ 知道事务的 BEGIN/COMMIT 圈出可见性边界（§6.5 实验）；
> 4. □ 用两个连接同时操作同一个库文件（§6.5 的杀进程实验用过子进程）。

## $\rm \S \, 7.1$ 三种读异常：各是什么怪事

并发事务交错执行，读侧能撞见三种怪事（按严重程度排）：

1. **脏读（dirty read）**：读到别人**还没提交**的修改，对方一 ROLLBACK，你读到的值从没存在过。依据一个可能蒸发的中间态做决策（转账放行、库存扣减）等于赌博；
2. **不可重复读（non-repeatable read）**：同一事务内两次读**同一行**，值变了：别人在两次读之间提交了对这一行的 UPDATE。单看每次读都是「真」数据，拼起来却自相矛盾（第一次算报表 5000，交表时别人改成了 4800）；
3. **幻读（phantom read）**：同一事务内两次执行**同一查询**，行数变了：别人 INSERT/DELETE 了满足条件的行。与不可重复读的区别在「改的是已有行」还是「行的集合变了」：统计类查询（COUNT/SUM）对幻读最敏感。

三种异常都是**读**的问题（写写冲突由锁直接挡住，§7.3 展开）。一张时序图把「不可重复读」的交错现场画清楚（其余两种同构）：

```mermaid
sequenceDiagram
    participant R as 读者事务
    participant W as 写者事务
    R->>R: 读 id=1 得 100
    W->>W: UPDATE v=200
    W->>W: COMMIT
    R->>R: 再读 id=1 得 200
    Note over R: 同一事务内两次值不同——非重复读
```隔离级别的意义就是声明「我接受哪种怪事」：级别越低越能并发、怪事越多；级别越高越像串行、吞吐越差。SQL 标准的四档名字与挡掉的异常对照（READ UNCOMMITTED / READ COMMITTED / REPEATABLE READ / SERIALIZABLE）在 §7.4 展开，先看机制。

**本节小结**：脏读＝读到没提交的、不可重复读＝同一行两次值不同、幻读＝同一查询行数不同；三种都是读侧的怪事，写写冲突不归它们管，由锁直接挡（下一节亲眼看到）。

## $\rm \S \, 7.2$ 实测一：事务内快照 vs 跨事务直读

SQLite 开 WAL 模式（§8 章细讲它，本章先用）后，两个连接同时活动。第一个实验把「可重复读」这件事的两个面摆出来（复现：两连接 `isolation_level=None`、`PRAGMA journal_mode=WAL`，初始 v=100）：

```python
conn1.execute('BEGIN')
a1 = conn1.execute('SELECT v FROM t WHERE id=1').fetchone()[0]   # 100
conn2.execute('UPDATE t SET v=200 WHERE id=1')                    # c2 提交
a2 = conn1.execute('SELECT v FROM t WHERE id=1').fetchone()[0]   # ?
conn1.execute('COMMIT')
a3 = conn1.execute('SELECT v FROM t WHERE id=1').fetchone()[0]   # ?
```

本机实测输出：

```text
c1 事务内两次读: 100 -> 100（快照不变）；提交后再读: 200（看到新值）
```

关键机制：BEGIN 之后 c1 的读被**快照（snapshot）**锚定，此后无论别人提交什么，c1 看到的都是自己开始时那个瞬间的一致版本；COMMIT 之后重新取快照，新值才可见。这就是「不可重复读」在快照隔离下的消失方式：不是把别人挡在外面，而是把自己冻结在里面。

同一个库、同两个连接，把 BEGIN/COMMIT 拿掉（每次 SELECT 各自一个自动提交事务）：

```text
两次独立 SELECT: 200 -> 300（跨事务看见了别人提交的修改）
```

「不可重复读」的形态出现了。但注意**这不是异常**：两次读本来就属于两个事务，看见提交后的新值是 READ COMMITTED 的正确行为。判定的分水岭始终是「这两次读在不在同一个事务里」，而不是值变没变。

**本节小结**：同一组实验换一个条件答案翻转——事务内快照把读冻结（100→100），跨事务直读如实反映世界（200→300）；「不可重复读」只在同一事务内才算异常，事务边界就是判定边界。

## $\rm \S \, 7.3$ 实测二：写冲突的真实代价

读有快照，写呢？第三个实验让两个连接同时写（复现：`BEGIN IMMEDIATE` 抢写锁）：

```python
conn1.execute('BEGIN IMMEDIATE')               # c1 显式拿写锁
conn1.execute('INSERT INTO t VALUES (2, 1)')
try:
    conn2.execute('INSERT INTO t VALUES (3, 1)')   # c2 立刻写
except sqlite3.OperationalError as e:
    print('c1 未提交期间 c2 写入被挡:', e)
```

实测输出：

```text
c1 未提交期间 c2 写入被挡: database is locked
c1 提交后 c2 写入成功, 行数 = 3
```

三条读数。第一，写写互斥由**锁**保证：c1 未提交前 c2 的写直接被挡（SQLite 是库级锁，操作系统分册 §7.4 讲过它为什么这么粗）；第二，`database is locked` 出现在 c2 的**第一条写**上，不是深水区，冲突检测前置；第三，c1 提交后 c2 立刻成功：锁的生命周期恰好是事务（拿锁到提交/回滚才放），这就是**两阶段锁（2PL）**的形状：增长阶段拿锁、收缩点在事务末尾统一释放。2PL 的严格版足以保证可串行化，代价是吞吐与死锁风险（数据库分册的行级锁版本会遇到，SQLite 的库级锁用粗粒度换了「死锁结构上不可能」）。

> **工程视角**：写锁的粒度是「并发写吞吐」的第一决定因素：SQLite 整库一把（简单、无写写死锁、单机应用友好）；PostgreSQL/MySQL 到行级（并发高、要死锁检测）。选数据库的第一刀常常就从这里切：嵌入式单写者场景 SQLite 完胜，多写者高并发必须行级库。

挡回来的 `SQLITE_BUSY` 在应用侧的正确姿势是**重试**：等待-退避-重来（写侧的幂等设计在这时救命）。ignore 它不是选项，那等于丢一次写。

**本节小结**：读走快照不挡人，写走互斥必排队——锁的生命周期就是事务本身，这正是两阶段锁的形状；粒度（库级 vs 行级）是并发吞吐的第一刀，BUSY 的正确姿势是重试不是忽略。

## $\rm \S \, 7.4$ 隔离级别：异常 × 级别对照表

把 §7.1 的三种异常与 SQL 标准四档对上（✓=允许发生，即挡不住）：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 一句话 |
| --- | --- | --- | --- | --- |
| READ UNCOMMITTED | ✓ | ✓ | ✓ | 什么都能读到，几乎没人敢用 |
| READ COMMITTED | — | ✓ | ✓ | 只读提交过的（多数数据库默认档） |
| REPEATABLE READ | — | — | ✓ | 行不变了，集合还能变（MySQL/InnoDB 默认） |
| SERIALIZABLE | — | — | — | 效果等同排队执行 |

对照实测读两条：§7.2 的事务内快照行为落在 REPEATABLE READ 一档（行级不重复变）；SQLite 的快照隔离顺带也基本消除了幻读（整个事务锚定一个版本），接近 SERIALIZABLE，代价是写锁粗、写并发低（§7.3 的库级锁）。另一个常被忽略的维度：隔离级别越严，**长事务杀伤力越大**：REPEATABLE READ 下的长事务把旧版本数据钉在快照里（§8 讲版本存哪），事务越长、要留的版本越多。所以「提高级别」的配套纪律永远是「缩短事务」：事务里不要 sleep、不要等外部 API、不要算大循环。

级别选择的工程直觉：**业务能否容忍「读到稍旧但一致」的数据**。报表、展示类用 READ COMMITTED 足够；「读-判-写」的决策链（查余额-判够-扣款）必须 REPEATABLE READ 以上，否则两次读之间的世界已经变了。
一句话背下这张表：**每上一档，就把上一档放行的那个怪事也挡住**：名字本身就是承诺。

> **常见误区**：隔离级别挡的是「读的怪事」，不挡「丢更新」：两个事务都读到 v=100、各自加 100、先后提交，最终 200 而不是 300。这是写写冲突的变体，要么靠锁（SELECT … FOR UPDATE 把读升级为加锁读），要么靠原子 UPDATE（`SET v=v+100` 一条语句，数据库自己保证原子），要么靠乐观并发（带上版本号 WHERE old_version）。隔离级别旋钮拧到头也救不了「读了旧值还基于它写」的应用逻辑错。

**本节小结**：这张表的读法是「每上一档，把上一档放行的怪事也挡住」；级别越严、长事务代价越大，提级别的配套纪律永远是缩短事务；丢更新不在表内，要用原子 UPDATE/加锁读/乐观并发另配药。

## $\rm \S \, 7.7$ 本章自测答案

### $\rm \S \, 7.7.1$ 关键概念回顾答案

1. 脏读读到从未存在过的值（对方未提交/回滚）；不可重复读是同一行两次值不同（别人提交了 UPDATE）；幻读是同一查询两次行数不同（别人 INSERT/DELETE）。严重程度＝基于它做决策的荒谬程度：脏读依据蒸发数据、不可重复读依据被偷换数据、幻读依据被篡改的集合。（§7.1）
2. BEGIN 时把读锚定到一个一致的旧版本，之后所有读都看这个版本。它与「挡住别人」的差别：别人照常写照常提交，只是我看不见：读不阻塞写、写不阻塞读（并发度更高），代价是我的世界暂时旧。（§7.2）
3. 增长阶段（执行中按需拿锁，只增不减）与收缩阶段（事务末尾统一释放）。锁的生命周期＝整个事务：从第一条写（或 BEGIN IMMEDIATE）到 COMMIT/ROLLBACK。（§7.3）
4. READ COMMITTED 挡脏读（只认提交过的数据）；REPEATABLE READ 再挡不可重复读（行不再变）。各自仍放行后面的异常。（§7.4）
5. 丢更新是「读了旧值、基于旧值写」的应用逻辑漏洞：两个事务都合规，合并结果错。修复：①原子 UPDATE（SET v=v+?，一条语句内读改写）；②加锁读（SELECT…FOR UPDATE 把读升级）；③乐观并发（WHERE version=旧值，冲突方重试）。（§7.4）

### $\rm \S \, 7.7.2$ 应用与辨析答案

1. §7.2 第二组实验即是：c1 两次独立 SELECT 之间 c2 提交了 UPDATE，读到 200→300。不是异常，因为两次读分属两个事务：READ COMMITTED 的合同就是「每次读看到当时已提交的最新值」，变化恰好证明合同被履行。（§7.2）
2. 竞态：判库存够与扣减之间别人扣走了最后一件，超卖。修复一：原子 UPDATE（UPDATE stock SET n=n-1 WHERE id=? AND n>=1，影响行数=0 即失败），最简、无锁等待；修复二：REPEATABLE READ/串行化＋ SELECT…FOR UPDATE 加锁读：语义直白但并发度低、要处理死锁。高并发秒杀选一，低频后台管理选二都行。（§7.4）
3. 普通 BEGIN 是延迟取锁：第一条写才升级为写事务（读快照期间别人可写）；BEGIN IMMEDIATE 在开始就抢写锁。当事务要「先读一串、再写」（读的结论决定写的内容）时必须用 IMMEDIATE，否则读到快照后拿写锁时世界已变，要么 busy 要么基于旧快照写。（§7.2、§7.3）
