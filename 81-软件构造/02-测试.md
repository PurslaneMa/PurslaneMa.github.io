第 1 章把检查排成了三界光谱，结尾留了一个缺口：类型集合对了，答案仍可能是错的，mypy 对 `total_pages(12, 13)` 的 47 无话可说。补这个缺口的是本册第二件论证工具：测试。它站在光谱里一个特殊的位置，检查器不是语言自带的，而是你亲手为「值该是什么」写下的一段代码。本章先立测试的基本形状，把「跑一遍没报错」升级成带预言机的抽查（§2.1），再回答「无穷输入里挑哪几个」的设计问题（§2.2），然后用本章锚点实验给出定量答案：同一个函数埋三个 bug，五套测试策略的抓取率从 0 到 100% 各不相同（§2.3）；接着拆解「覆盖率 100% 却一个 bug 都没抓到」这个最常见的谎言（§2.4），最后一瞥测试替身，让不归你管的世界关在门外（§2.5）。本章实验全部在 WSL2（python 3.12.3）上真跑过，脚本与完整输出见本册实验记录 `expSW02/result.txt`，五个脚本总耗时不足 1 秒。

## $\rm \S \, 2.1$ 从「跑一遍没报错」到抽查

先立任务。竞赛代码的核对流程你闭着眼都会：提交，判题器返回 AC 或 WA。这个流程里有三个零件，值得拆开看：你交的是**被测代码**；判题器拿输入算出标准答案，这是**预言机**（oracle），即判定对错的依据；跑多少组数据、什么数据，这是**抽查方案**。到了开发里，零件二消失了：没有判题器替你判定「这个函数的返回值对不对」，你得自己写。把这三个零件用代码拼起来，就是**单元测试**（unit test）：一段代码，调用被测函数，把返回值和期望值比较，不符就报告失败。

最小例子来自贯穿项目的清洗管道。挑选逻辑按 spec 应该是：`top_pages(records, k)` 返回 pages 最大的 k 条记录，按 pages 从大到小排序。给它写的第一个测试：

```python
def test_top_pages_basic():
    records = [{"title": "A", "pages": 15}, {"title": "B", "pages": 9}]
    assert top_pages(records, 1) == [{"title": "A", "pages": 15}]
```

`assert` 语句在条件为假时抛 `AssertionError`：测试失败就是异常，测试通过就是无声。本章为免装依赖用原生 `assert` 手搓；真实项目用 pytest 这类框架自动收集和运行测试函数，那层是工具皮，不是新知识。跑它的命令（Bash/Zsh 通用，当前目录为脚本所在目录，只读脚本、输出打印到终端，不改任何文件；成功验证是没有任何 `AssertionError` 输出，报错含义直接写在异常消息里）：

```bash
python3 exp1_testfirst.py
```

这个测试该在什么时候写？经验规则是：写实现之前。这个次序叫**测试先行**（test-first），它不是仪式，而是给测试本身做的一次校准：测试先于实现存在，就必然先失败一次，你亲眼看到它抓住「函数还不存在」这个状态，之后它转绿才有说服力。实测这一过程（`expSW02/exp1_testfirst.py`）：同一份测试，实现前运行报 `NameError: name 'top_pages' is not defined`，写出最小实现后重跑通过。反过来，一个从没失败过的测试要打个问号：它可能在检查一个永远为真的条件，比如断言返回值「是个 list」，那它什么也抓不到，§2.4 会拿它开刀。

白话：单元测试就是你自己给自己雇的判题器；竞赛时判题器是现成的，开发时这件东西要亲手造，而「先看到它失败」是验收判题器的唯一办法。

> 本节小结：单元测试 = 被测代码 + 预言机 + 抽查方案的代码化；开发里预言机要自己写，这是测试的主要成本；测试先行的价值在于先看到测试失败，证明它真的在检查什么。

## $\rm \S \, 2.2$ 等价类与边界值：无穷输入里挑哪几个

测试先行的次序好定，可测试的内容难定：`records` 可以是任意长度、页码可以是任意整数，用例只能写有限个，挑哪几个？瞎挑的抽查等于没抽查，这一节给两条挑签的原则。

第一条叫**等价类**（equivalence class）。观察一个事实：`top_pages` 对「k 在 1 到 n−1 之间的一大批输入」走的是完全相同的代码路径，行为大概率一致，那么对这一整类输入，测一两个代表就够了。按这个思路把输入空间切成类，每类抽代表，就是等价类划分。给 `top_pages` 的输入空间切一遍：k 分成负数、0、1、正常中间值、等于 n、大于 n 六类；records 分成空表、单条、pages 并列、无并列四类；页码本身分成值域两端（0 与极大值）、常规值几类。

第二条叫**边界值**（boundary value）：类与类的接缝处。切完等价类后，重点测的恰恰不是每类的正中心，而是接缝上的点：k=0 与 k=1、k=n 与 k=n+1。原因写在代码的构造方式里：切片 `[:k]` 的端点、循环的起止下标、比较符 `<` 与 `<=` 的选择，全都在接缝处起作用。第 1 章 §1.2 的坏点埋在第 847 条，暴露条件是「执行路径踩到坏点」，而 off-by-one 一类错误的坏点几乎全埋在边界上，所以边界值的命中密度远高于随机值。

把这套动作落到贯穿项目的挑选函数上，§2.3 将实测的 9 例边界套件就是照上面的清单抄出来的：

```python
def R(p, t):
    return {"title": t, "pages": p}          # 一条论文记录：pages 页，标题 t

BOUNDARY = [
    ([], 0),                                 # records 空表类
    ([R(5, "a")], 0),                        # k 下边界：k=0
    ([R(5, "a")], 1),                        # k 上边界：k=len
    ([R(5, "a")], 2),                        # 边界外：k=len+1
    ([R(3, "a"), R(7, "b")], 1),             # 常规类代表
    ([R(9, "a"), R(9, "b"), R(1, "c")], 2),  # pages 并列类
    ([R(0, "a"), R(99, "b")], 1),            # 页码值域两端
    ([R(9, "a"), R(15, "b")], 1),            # 数位宽度接缝：1 位 vs 2 位
    ([R(2, "a"), R(2, "b"), R(2, "c")], 1),  # 全并列类
]
```

最后两例值得多看一眼：`0` 与 `99` 是值域边界，`9` 与 `15` 是「数位宽度从 1 位变 2 位」的接缝，后者是 §2.3 里 B2 类 bug 唯一的暴露点，凭直觉挑代表往往挑不到它，这正是边界清单要先列类再挑点的用处。

> **竞赛生迁移提示**：这套动作你在竞赛里做过，只是没叫这个名字。造对拍数据时先出小随机、再出 n 取上界的极限数据，后者就是边界值思维；「极限数据专治数组开小」是这条原则的 OJ 版本。差别在于：竞赛造数据赌的是判题器会抓错，开发里预言机也得自己配，见 §2.3 的 B3。

白话：等价类是把无穷的输入空间切成有限的格子，边界值是专门盯格子之间的墙缝；墙缝比格子中心危险一个数量级。

> 本节小结：用例挑选的两条原则，等价类每类取代表、边界值专测类间接缝；接缝危险是因为切片端点与比较符都在那里工作；竞赛的「极限数据」就是边界值，只是当时预言机是现成的。

## $\rm \S \, 2.3$ 锚点实验：三个 bug，五套测试的抓取率

挑签原则有了，现在回答本章的核心问题：一套测试到底多能抓？空口说不算数，本节用实验定量。被测对象是同一个函数 `top_pages` 的四个变体：一个正确版，三个各埋一个 bug 的版本。三个 bug 的品种是精心挑的：

```python
def make_variant(bug):
    def top_pages(records, k):
        if k < 0:
            raise ValueError("k 不能为负")
        if k > len(records):
            raise ValueError("k 超过记录数")
        if bug == "B1":   # 边界 off-by-one：多给一条
            return sorted(records, key=lambda r: r["pages"], reverse=True)[:k + 1]
        if bug == "B2":   # 类型混淆：排序键悄悄从 int 换成 str
            return sorted(records, key=lambda r: str(r["pages"]), reverse=True)[:k]
        if bug == "B3":   # 状态污染：原地排序，改掉调用方的列表
            records.sort(key=lambda r: r["pages"], reverse=True)
            return records[:k]
        return sorted(records, key=lambda r: r["pages"], reverse=True)[:k]  # 正确版
    return top_pages
```

先立靶子：整个实验对照着一份写在函数 docstring 里的 spec 跑，四个变体共用它。

```python
"""spec：top_pages(records, k) 返回 pages 最大的 k 条记录，按 pages 从大到小
排序（pages 相同保持原有先后）；不修改 records；k<0 或 k>len(records) 时抛 ValueError。"""
```

三个品种各有来历。B1 是边界 bug 的标准形态：`[:k + 1]` 在 k 小于 n 时多给一条，在 k 等于 n 时切片截断反而正确。B2 是第 1 章 §1.3 静默形态的返场：`str(9)` 与 `str(15)` 按字典序比较时 `"9"` 排在 `"15"` 前面，类型层面完全自洽、异常零个、值是错的。B3 是 §1.3 可变默认参数的同族病：spec 承诺不动输入，实现原地排序把调用方的列表改了，返回值本身却完全正确。

五套测试策略按「输入从哪来」与「查什么」两个维度配置。运行方式（WSL Bash，当前目录 `expSW02`，只读脚本、输出重定向到 `result.txt`，实验总耗时不足 1 秒；成功验证是五张统计表齐全、每个抓取数都在 0 到 200 之间）：

```bash
python3 exp2_catch.py > result.txt
```

实测结果一张表收拢（A、B 两套是随机套件，在 200 个独立种子上各跑一个 20 例的套件，表里是抓到该 bug 的套件占比；C、D、E 是确定性套件，抓到即 100%、漏即 0%）：

| 套件 | 用例数 | 预言机查什么 | B1 | B2 | B3 |
| --- | --- | --- | --- | --- | --- |
| A 随机输入，只查不崩溃 | 20×200 | 只看抛不抛异常 | 0% | 0% | 0% |
| B 随机输入+性质预言机 | 20×200 | 四条 spec 性质 | 100% | 72.5% | 100% |
| B′ 同 B，页码换窄分布 | 20×200 | 同上 | 100% | 0% | 100% |
| C 等价类+边界值 | 9 | 期望返回值 | 100% | 100% | 0% |
| D 穷举小域（页码 0..9 全对） | 300 | 期望返回值 | 100% | 0% | 0% |
| E 穷举大域（页码 0..99 全对） | 30000 | 期望返回值 | 100% | 100% | 0% |

这张表值得逐行读，每一行都是一个教训。

A 行：只查不崩溃的随机测试，抓取率 0%。三个 bug 全是静默的，没有一个抛异常。这行是 §1.3 的数字重演：不崩是最便宜的预言机，也是最聋的。

B 行：预言机换成四条从 spec 直接抄下来的性质（长度等于 k；返回的 pages 序列不增；选出来的确实是最大的 k 个；调用后输入与调用前相等），同样的随机输入，抓取率跳到 100%、72.5%、100%。B1 靠「长度等于 k」抓，200 个套件无一漏网；B3 靠「输入未被修改」抓，同样无一漏网；B2 只有 72.5%，因为它的暴露需要签筒里恰好同时出现一位数页码（如 9）和两位数页码（如 15），抽 20 例仍可能一例都没抽中。

B′ 行：同一个套件、同一条性质，只把页码分布从 0..99 换成 0..9，B2 的抓取率从 72.5% 掉到 0%。原因在数位：单位数页码的字符串排序与整数排序完全一致，窄签筒里根本不存在能暴露 B2 的签。抽查的抓取率由签筒决定，这条纪律对随机测试与等价类同样生效：C 套件里 `0` 和 `99` 的组合抓不到 B2，`9` 和 `15` 才抓得到。

B 行的抓取率随用例数怎么涨，实测曲线（前 m 例的抓取率，200 种子）：B1 从 69%（m=1）到 100%（m=5）；B3 从 54% 到 100%（m=10）；B2 从 8% 爬到 72.5%（m=20）。把这条曲线和抽样模型对上。单个用例抓到某 bug 的概率记 $p$，$m$ 个用例的套件抓到它的概率记 ${P_{\text{det}}(m)}$，用例独立抽取时：

$$
P_{\text{det}}(m) \;=\; 1-(1-p)^{m}
$$

读法：$p$ 是单例命中率，${(1-p)^{m}}$ 是 m 例全放过的概率，1 减它就是至少一例命中。拿实测校准：B3 的 $p=0.54$，代入 $m=20$ 得 ${1-0.46^{20}}$，与 1 的差距在小数点后六位，实测 200/200，吻合；B1 同样吻合。B2 偏了：$p=0.08$ 代入预测 81%，实测 72.5%。偏差方向是单向的，只会偏低：同一种子的 20 例共用同一个记录数生成器，例与例不独立，小记录数的用例对 B2 完全无杀伤力，它们扎堆时整支套件都哑火。独立模型给出的是上限，相关性只会让真实抽查更差，这是把公式用到工程里时必须记住的符号。

C 行：9 个手写用例的等价类+边界值套件，抓住 B1（k=0 那例期望空列表、B1 给一条）与 B2（9 与 15 那例），漏掉 B3。漏的原因不在输入，在预言机：期望值预言机只盯返回值，「不许改输入」这条承诺写在 spec 的文字里、不在返回值里，只对着返回值写断言的人永远不会发现它被违反。

D 行与 E 行：穷举是唯一敢说「完备」的策略，但完备只在域内。300 个用例穷遍页码 0..9 的全部有序对，B2 安然无恙，因为这个域里字符串排序与整数排序根本不会分家；把域扩大到 0..99，用例数涨到 30000（平方级代价），B2 被抓住。而 B3 在 D、E 两行全漏，理由与 C 行相同，穷举一百倍的花费买不来预言机里没写的那条检查。

把六行合起来读，结论有三条。第一，三个 bug 没有被任何单一套件全部抓住，最好的单套件战绩是 2/3，测试的抓取力等于「输入覆盖」与「预言机强度」两个因子的乘积，缺一个因子另一个再强也白搭。第二，B3 的漏检率在三套输入策略下全是 100%，它的预言机「输入未被修改」只能从 spec 里来，这把第 3 章的 spec 推到了前台：合同写得含糊，测试就永远漏这一条。第三，最贵的穷举（30000 例）不如最便宜的 9 例边界套件会挑地方，钱要花在签筒和预言机上，不是无脑堆用例数。

白话：测试像海关缉私，等价类和边界值决定开箱抽检哪些行李，预言机决定开箱之后认不认得出违禁品；只查「箱子没炸」的海关，抓不到任何静默走私。

> 本节小结：三个 bug 五套件的实测矩阵给出抓取率从 0 到 100% 的全谱；抓取力 = 输入覆盖 × 预言机强度；随机套件的抓取率由分布决定且随用例数按 ${1-(1-p)^m}$ 增长（相关性使实测低于模型）；穷举的完备性只限于域内且代价平方级增长；「不改输入」这类不落在返回值里的承诺，只能靠从 spec 抄下来的性质预言机检查。

## $\rm \S \, 2.4$ 覆盖率及其谎言

上一节比较了不同套件的抓取率，这一节拆一个更流行的指标。**语句覆盖率**（statement coverage）的定义：测试运行时被执行到的语句行，占全部可执行语句行的比例。直觉上它该衡量「测得全不全」，实测一把就知道这个直觉差多远。

实验设计（`expSW02/exp3_coverage.py`，用标准库 `sys.settrace` 自行统计被执行行号）：两个套件，被测函数带两个 `raise` 分支共 6 条可执行语句行。弱套件 4 个用例：正常一例、k=0 一例、k 为负一例、k 超界一例，页码全是单位数，断言只有一条「返回值是 list、不崩」。性质套件 20 例，即 §2.3 的 B 套件。实测：

| 套件 | 用例数 | 行覆盖率 | 对 B1/B2/B3 战绩 |
| --- | --- | --- | --- |
| 弱套件 | 4 | 100%（6/6，含两条 raise 行） | 放行 0/3 |
| 性质套件 | 20 | 67%（4/6，两条 raise 行没跑到） | 抓到 3/3 |

数字先看懂再说理。弱套件怎么做到 100%：k 为负踩进第一条 raise，k 超界踩进第二条，正常路径跑完最后两行，6 行全热。把口径收紧到分支也一样：两条 raise 行被执行说明两个 `if` 的 True 支都走到，最后一行被执行说明两个 `if` 的 False 支都走过，分支覆盖率同样是 100%。它怎么做到 0/3：k=0 的用例喂给 B1 返回一条记录，断言「是个 list」通过；页码 5 和 3 都是单位数，B2 的字符串排序不犯病；所有断言都只看返回值的类型，B3 改输入它根本不看。性质套件恰好相反：随机生成器给不出负数 k 和超界 k，两条 raise 行永远冷着，覆盖率只有 67%，但四条性质预言机把三个 bug 全部按住。

于是覆盖率的真实含义浮出来：它量的是**哪里被跑到**，而抓 bug 靠的是**跑到之后查了什么**。被跑到是抓到的必要条件（§1.2 的暴露公式在这里同样成立），但远不是充分条件：每一条语句都被踩过、每一个 bug 都被放过，两者同时成立毫无矛盾。弱套件就是那个反例：覆盖 100%，抓 0 个。

这不是说覆盖率没用，是说它的用法有方向性。低覆盖率是确定的坏消息：67% 意味着至少两条 raise 从没被任何测试踩过，那里有什么问题测试一概不知。高覆盖率却不是好消息：它不排除「每行都踩了但什么都没查」，甚至可能激励人为了凑数写弱断言用例，弱套件就是这么来的。把它当地板指标用（低于某个数说明明显没测够），别当天花板指标追（追 100% 会买来 §2.3 表里 A 行那种聋子测试）。

白话：覆盖率像点名册，人人到场不等于人人干活；点名缺席肯定有问题，全员到齐也未必干成了任何一件事。

> 本节小结：语句覆盖率 = 被执行语句行占可执行语句行的比例；实测 100% 覆盖配 0/3 战绩、67% 覆盖配 3/3 战绩；覆盖是抓到 bug 的必要条件而非充分条件，缺的那一半是预言机；覆盖率当地板指标用，别当天花板指标追。

## $\rm \S \, 2.5$ 替身一瞥：把世界关在门外

管道的挑选逻辑测顺了，往上游走一步就撞上新麻烦：`pipeline(fetch, k)` 要先调 `fetch()` 拿数据，而 `fetch` 的真实现要发 HTTP 请求。给它写单元测试，难道每次都跑真的网络？不行，理由有三条：慢（一次请求几百毫秒，测试要跑几千次）、不稳（远端服务挂了你的测试跟着挂）、不可控（你没法让真服务器随时返回「恰好含并列页码」的数据）。

解法是给 `fetch` 发一个**测试替身**（test double）：一个履行同一份合同、但零网络开销的假函数，最简单的品种叫**桩**（stub），直接返回写死的数据。实测（`expSW02/exp4_stub.py`）：

```python
def fetch_records():
    raise OSError("网络调用不应发生在单元测试里")   # 真实现，测试里碰它就现形

def pipeline(fetch, k):
    return top_pages(fetch(), k)

def fake_fetch():   # 桩：履行「返回记录列表」的合同，零网络
    return [{"title": "A", "pages": 15}, {"title": "B", "pages": 9}, {"title": "C", "pages": 12}]

print(pipeline(fake_fetch, 2))
print(pipeline(empty_fetch, 0))   # 空库替身：合同允许返回空列表吗？测了才知道
```

输出两行：`[{'title': 'A', 'pages': 15}, {'title': 'C', 'pages': 12}]` 与 `[]`；若误把真实现传进来，`OSError` 当场炸出，证明测试全程没碰网络。

替身的边界要划清：它证明了「归你写的拼接逻辑」正确，不证明「真 fetch」正确，`fetch` 自己的行为要靠它自己的测试，两类测试各管一段。而替身能演什么、该演什么，答案是它必须履行 `fetch` 的合同：返回什么类型、空列表合不合法、出错时抛什么。合同写在纸面上，替身才知道往哪个方向假，这正是第 3 章规格（spec）要正式解决的问题：把「调用方可以指望什么」写成条款，让测试、替身和静态检查都对着同一份契约工作。

白话：替身是替身演员，戏份（合同）得和正主一模一样，但它不会真跳楼；你测的是导演怎么调度它，不是替身的演技本身。

> 本节小结：依赖网络的代码用测试替身隔离，桩直接返回履行合同的数据；替身换来的是快、稳、可控；替身只担保你自己的逻辑，不担保被顶替的依赖；替身该演什么由依赖的 spec 决定，合同要落在纸面上。

## $\rm \S \, 2.8$ 本章自测答案

概念回顾答案：

1. 三零件：被测代码、预言机（判定对错的依据）、抽查方案（跑哪些输入、多少例）。竞赛里预言机（判题器算标准答案）是现成的，开发里预言机要自己写，这是测试的主要成本（来源：§2.1）。
2. 测试先于实现存在，第一次运行必然失败，这次失败证明测试真的在检查什么；从没失败过的测试可能在断言一个恒真条件（如「返回值是 list」），对静默错误全聋（来源：§2.1、§2.4）。
3. 等价类负责把无穷输入切成有限类、每类取代表；边界值负责专测类与类的接缝。接缝危险是因为切片端点、循环起止、比较符选择全在那里生效，off-by-one 的坏点几乎全埋在边界（来源：§2.2）。
4. 理论抓取率 ${1-(1-0.08)^{20}}$ 约 81%。实测 72.5% 偏低，因为同一种子的 20 例共用记录数生成器、例与例不独立，小记录数用例对 B2 无杀伤力且会扎堆；独立模型是上限，相关性只会让真实抓取率更低（来源：§2.3）。
5. 漏在预言机：三套策略的断言都只盯返回值，而 B3 的返回值完全正确，违约的是「不修改输入」这条承诺。这条预言机的内容要从 spec 的文字里抄，合同没写它就永远漏（来源：§2.3）。
6. 对 B1：k=0 用例下 B1 返回一条记录，断言只查「是 list」，通过；对 B2：页码全是单位数，字符串排序与整数排序在窄域里不分家，值错但断言查不出；对 B3：断言不看输入列表，B3 原地改掉调用方数据它无从知晓（来源：§2.4）。

应用与辨析答案：

1. 能抓到 0 个：静默错误（值错型）不改变返回值的类型，`isinstance` 断言对它全聋，95% 覆盖率只证明每行都被踩过、不证明任何一行查出了值错。要求：把断言换成对返回值内容的具体期望（期望值预言机），并对「不修改输入」这类承诺补性质断言；覆盖率数字不用动（来源：§2.4、§2.3）。
2. 等价类与边界值清单：两表皆空；一空一非空；无重叠（最大值分属两表）；全部重叠；left 长 right 短与反向；单元素表；表中含相等元素。需要抄进预言机的性质：结果非降、结果长度等于两表长度之和、结果是两个输入的同一个多重集合；只盯返回值的某个具体期望值会漏「恰好排对但丢了元素」一类错误，且合并稳定性这类承诺若 spec 有写也必须单列检查（来源：§2.2、§2.3）。
3. 对的部分：按公式 ${1-(1-p)^{m}}$，m 从 20 加到 2000，理论抓取率从 81% 升到约 1 减 ${0.92^{2000}}$，趋近 1。不对的部分：一是实测的相关性让真实值低于模型，B2 在 §2.3 的偏差方向是单向的；二是 B′ 行给出致命反例，页码分布换成 0..9 后，用例数再大抓取率也是 0%，签筒里没有的签抽一万次也抽不中。加量不如先查签筒（分布覆盖）与预言机（来源：§2.3）。

**你现在能做什么**：拿到一个你写的函数，你能先写测试看着它失败，再用等价类+边界值列出用例清单，并说出你的断言漏了哪些不落在返回值里的承诺。

测试解决了「挑中的输入上值对不对」，但三个 bug 没有任何一个套件能全抓，B3 的抓取率始终被预言机的完备性卡住，而预言机该查什么，答案写在 spec 里。下一章把合同本身升级为正式工具：前置条件、后置条件、行为等价与替换原则，让测试、替身和类型检查对着同一份契约工作。
